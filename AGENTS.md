# Working in this repository

- Read [POLICY.md](POLICY.md) for repository CI, integration and release authority; its [Work units, review and integration](POLICY.md#work-units-review-and-integration) section holds the work-unit, review and integration rules. Read [CONTRIBUTING.md](CONTRIBUTING.md) for the contribution path. `dev` is the default integration branch; `main` mirrors a verified release commit and is advanced only by the owner-authorized release workflow; there is no promotion PR.
- This repository holds the skill instructions under `plugins/crw/skills/` and the `crw` runtime (one Go binary) under `cmd/` and `internal/`. `crw-dev skills link`, the checks and the package all read the path the manifest declares; the root `skills` compatibility link to that directory left in todo 44, so an installation that still links through it is reported as a CONFLICT to relink. Read the target skill and its linked references before editing. Keep skill names, folder names, UI prompts, and relative links consistent.
- `plugins/crw` is the published plugin package and `.agents/plugins/marketplace.json` is its marketplace entry. Installation copies the plugin root verbatim, including untracked and ignored files, so what may live there is `.codex-plugin/`, `LICENSE` and the components the manifest declares: today `skills/` and `wiring/`. A component nobody declares installs without ever loading, so adding a directory means declaring it. Run `go run -tags dev ./cmd/crw-dev ci plugin` after touching the package, the manifest or the skills; it derives the permitted roots from the manifest. See [plugin packaging](docs/plugin-packaging.md).
- `plugins/crw/wiring` holds the declared Stop hook and MCP server. Both reach the Go runtime through the installer pointer `$HOME/.local/share/crw-runtime/current/bin/`: the Stop command runs `crw hook --plugin-launch; exit 0`, and the server runs the `sh` launcher `crw-bridge.sh`, which execs the pointer's `codex-thread-bridge` (the installer's link to `crw`) with `--plugin-launch`. In that mode the runtime applies the plugin-owner and record checks the Python launchers made (docs/port/decisions.md section 26). Nothing there bundles a runtime: the version cache is replaced wholesale on every install. The Python launchers `crw_stop_hook.py` and `crw_bridge_mcp.py` left the package after the cutover commit (todo 43), so do not put a Python launcher, or any file the declarations neither name nor start, back into `wiring/`; the copies kept with the pre-native declarations in `internal/pluginwiring/testdata/pre-native-wiring` left with the Python implementation in todo 44, and the tests replay their recorded answers. A Stop command a turn fixed before the native wiring falls back to `<CODEX_HOME>/crw-stop-hook.py` once its version directory is gone. `scripts/runtime_install.py` placed that copy, launcher before settings, `crw install` leaves it as it finds it, and the operator removes it from the host by hand once no turn can still reach it ([retention](docs/port/cutover.md#retention)). One owner registers each surface; `crw install` (and `scripts/runtime_install.py` until the cutover) writes the records they read and refuses the second owner. See [runtime installation](docs/runtime-install.md) and [the cache lifetime](docs/plugin-packaging.md#the-cache-lifetime).
- Maintain the `plugins/crw/skills/crw-*` directories together. Shared workflow rules live in `plugins/crw/skills/crw-canon/references/` (indexed by `plugins/crw/skills/crw-canon/SKILL.md`); rules only planning reads stay in `plugins/crw/skills/crw-plan/references/integrations.md`; operation-specific rules stay in their owning skill.
- The Python packages the runtime was ported from left in todo 44. `packages/codex-thread-bridge` keeps the bridge's upstream MIT notice (`LICENSE`, which the release archives ship) and its `PROVENANCE.md`; preserve both. The relay's normative documents are under `docs/relay/`. The runtime, installer, wiring and CI do not depend on Python: the port checkers and the allow-list that excused them left in todo 48, and `crw-dev ci validate` refuses any `.py` file or python-shebang script, tracked or untracked and not ignored, outside the `scripts/` and `examples/` directories of a skill (`plugins/crw/skills/*`, which holds the skills ported from CXC too), whose helper scripts are original assets an agent runs when it needs them (`internal/dev/ci`'s `TestTrackedPythonStaysInSkillAssets` holds the tracked files in `make test`), so add Python nowhere else; CI installs no Python and runs no skill script.
- Keep product documents in the tracking repository ([tracking model](plugins/crw/skills/crw-canon/references/tracking-model.md)) and private receipts outside this repository. Do not vendor credentials, session history, or generated runtime state.
- CXC v0.2.40 (lidge-jun/codexclaw, MIT) is the origin of the port: its MIT notice is kept in [NOTICE](NOTICE) and its provenance in [docs/port-cxc/provenance.md](docs/port-cxc/provenance.md), and CRW runs without it. The defects found while porting are in [docs/port-cxc/known-defects.md](docs/port-cxc/known-defects.md), one file per issue in [docs/port-cxc/known-defects/](docs/port-cxc/known-defects/).
- Use a task branch for substantial changes. Internal work integrates by one integrator, who merges the candidate into a local integration tree over `dev`, verifies that tree with the configured verifier (`local`: `crw-dev ci local`, or `github-actions`: the configured workflow; both require a `verification-record/1` PASS) and fast-forwards `dev` to it; an external contribution may still arrive as a pull request. Preserve dirty work. A development session pushes the task branch it has verified without asking each time: that is the owner's standing delegation, the same one a child carries under [Default dev integration](plugins/crw/skills/crw-canon/references/delivery.md#default-dev-integration). Internal work reaches `dev` by one of two landings. Direct landing is the integrator's push-only integration above, and work landed that way opens no pull request. PR-unit landing belongs to a child (project session): the target `base_ref` of its plan names its milestone integration branch, so the run's `crw.integrate` lands each node there as it would land it on `dev`; the project session opens one pull request from that branch toward `dev` naming the issues it carries (`crw flow pr open`) and puts it into the dev queue (`crw manage integrate --enqueue-pr`), which merges its head onto `dev` in its own tree, verifies it with the repository's verification, runs the repository's configured review command and fast-forwards `dev` only after both; nobody merges that pull request on GitHub, it holds the record and the review, and the gate is the `verification-record/1` ([the integration queue](docs/relay/integrator.md#pull-requests-pr-unit-landing)). A plan whose target is `dev` keeps the direct landing. The delegation is no force-push, no tag and no change to branch protection, CI permissions, credentials or security settings; a release, installation and deployment keep their own authorizations. Checked-in policy does not prove server-side protection is active.
- A candidate of a DAG plan is integrated by the owner of its own plan: the child that holds the node's execution edge, and for an agent node the child (project session, [the level table](plugins/crw/skills/crw-canon/references/hierarchy.md#the-levels)) whose run holds its current execution (`dag-integrate` reads that actor with `executionOf`). The check that a child integrates only its own nodes is unchanged and gives no authority over another plan. Integrations into one target are serialized by the compare-and-swap of the ref move: the branch moves and a push succeeds only while the tip is the base the candidate was verified on, a candidate whose base moved is merged again onto the new tip and verified again before it lands, and only a head the relay verified and moved the branch onto is pushed. There is no standing integrator and no lease; the host's `heavy_slot.sh` bounds the verifications that run at once.
- `crw-dev skills link` (`internal/dev/skills`, run as `go run -tags dev ./cmd/crw-dev skills link --check|--apply`) links this checkout into Codex. It must remain idempotent and refuse to replace existing directories or foreign links. Its Python predecessor, `scripts/install.py`, left with the Python execution path in todo 44.
- Validate changed skills with the bundled `skill-creator/scripts/quick_validate.py` when available, check relative links and `git diff --check`, and test installer changes in a temporary destination. Do not use text-matching tests as proof of workflow behavior.
- Editing source does not change an installed bridge or relay, a running service, an MCP registration, or an operational database. Report source, installation and live operation as separate facts.
- For instruction changes, reuse valid evidence and run focused scenario review when behavior changes. Live tracking writes and worker launches require scope covering those actions.
- Installed skills may be symlinks to this checkout. Source edits affect subsequent reads immediately; report installation and live execution as separate facts.

## Development loop

- Use one worktree and one task branch from `origin/dev` per issue; do not edit another agent's files, and change shared documents only in your own section.
- Set `TMPDIR` to a host-appropriate temporary work directory with no Git repository (`.git`) at or above it.
- Add and run a failing test first, then fix the cause; never skip tests or merely increase waits to obtain a pass.
- Test changed packages and their dependent packages with `-count=1`, then run `make lint-changed`; run `crw-dev ci validate` when skill documentation changes.
- Run one independent review, fix P0/P1 findings and do not re-review; then commit.
- Before full verification, fetch and merge `origin/dev` into the task branch; its author resolves conflicts.
- Use the configured verifier with `verifier.kind=github-actions` for full verification on GitHub Actions; on shared development machines, do not run full `crw-dev ci local` or full `make lint`.
- Push task branches without asking again, retain remote branches, and never push `dev` directly: only the integration queue updates it. Protection on `dev` rejects deletion, force-push and missing or unsuccessful required `dev-gate` status; passing checks do not authorize a direct push.
- `CLAUDE.md` is a relative symlink to `AGENTS.md`, so Claude Code reads these same instructions; do not maintain a second copy.
