# DAG scheduler

The scheduler runs a stored DAG plan ([DAG plans](dag-plans.md)). It computes which nodes may start, says why every other node may
not, and (in the later sections of this page) releases a ready node to a Codex child, records what the parent accepted and what
landed, and judges merge eligibility. It is code in `internal/relay/dagsched`, reached through `crw relay dag-*` commands that read
and write the relay store the other relay commands use. It holds no goal, runs no loop, starts no daemon and opens no database of
its own: a goal-free parent calls it when a relay result, a block or a decision request wakes it, acts on the answer and ends its
turn. No predicate here depends on a model's judgement.

The page follows the DAG execution contract (CRW-182) sections 2, 3, 4, 7 and 8; where the code departs from the contract's wording it
says so in [Departures](#departures-from-the-contract).

## The goal-free parent's turn

The parent holds no goal and runs no loop. A session that starts (the first one, a restart, or a replacement) begins with `dag-coordinator-claim` and `dag-restart` ([The coordinator epoch](#the-coordinator-epoch), [Restart and adoption](#restart-and-adoption)). When a relay result, a block or a decision request wakes it, one turn goes like this, and it ends when only waiting remains:

1. `dag-ready --plan P` (add `--record --actor A` to keep the pass): the nodes that are ready, in release order, and for every other live node its one reason. The store is the truth and a wake is only a hint: the same reading is
   right whether the wake was the first, a duplicate or a late one.
2. For each ready node, `dag-release` (a node that is already owned is `skip:already_owned` in the reading and a replay in the release: no second child).
3. For a result that is reported and verified: `dag-accept`; for a correction: `dag-correct --prepare`, the `needs_changes` ruling carrying the line, `dag-correct`; for a decision edge: `dag-decision-record`. A receipt that arrives is measured: `git fetch` in the parent's checkout, then `dag-conflict-sweep --trigger receipt --node N` (the acceptance runs the same sweep for the receipt it takes in, [Conflict observations](#conflict-observations)).
4. For an accepted pull request: `dag-merge-request`, the merge lane's own commands, `assignment-mark merged`, `dag-integration-observe` (which also runs the conflict sweep the landing owes), and `dag-landing-result-record` once the dev run of the merge commit has been read (green, red or reverted: [Release policy](#release-policy)). The merge order is read from the reading's `merge_order` ([The merge-order constraint](#the-merge-order-constraint)).
5. For the plan's Linear summary: `dag-summary-status --plan P`; when a document is owed or out of date, `dag-summary-enqueue` and the claim, write, read back and confirm of [the summary outbox](dag-outbox.md). It writes the summary table only, so it never
   re-runs a child or re-sends a correction.
6. End the turn. Nothing is resident: the scheduler is a library the relay's commands call over the relay's one store; it adds no daemon, no listener and no database of its own
   (`TestNoNewStoreOrDaemon`, `TestForkJoinLeavesNoStoreOfItsOwn`).

The scheduler re-implements no I-17 loop or skill, and contract section 10 names no I-17 output that this issue needs.

## The ready set

`crw relay dag-ready --plan P` reads the plan at its head revision and the relay's execution records and answers, for every live node,
one disposition and (except for a ready node) one reason from a closed set. A reading writes nothing, reads no clock and opens
no second connection, so with unchanged store rows and artifact bytes two readings are byte-identical (a command that carries the [host memory bound](#host-memory), as `dag-ready` and `dag-release` do, also depends on the host sample it took). Its `input_digest` hashes the plan identity, the node states and dispositions, the selected order, the capacity summary, the host memory sample (when the command reads the host) and the hashes of the artifact files it checked;
it is not a fingerprint of every source row read. A store with no DAG zone, or a plan it does not hold, answers `unregistered_scope` and is left as it was.

Beside its disposition and reason a node may carry objects that are not reasons: `stale` (what its accepted result no longer matches), `release` (how a candidate is released and on what basis), `merge_order` (its place in the measured merge order) and `stagnation` (how often it has failed the same way and which repair comes next, [A node’s stagnation counter](#a-nodes-stagnation-counter-and-the-repair-ladder)). Each is absent when it does not apply.

Beside its disposition and reason a node may carry four objects that are not reasons: `stale` (what its accepted result no longer matches), `release` (how a candidate is released and on what basis), `merge_order` (its place in the measured merge order) and `stagnation` (how often it has failed the same way and which repair comes next, [A node’s stagnation counter](#a-nodes-stagnation-counter-and-the-repair-ladder)). Each is absent when it does not apply.

A node is a **candidate** when it is not owned and every incoming edge is satisfied (the predicates are [Edge satisfaction](#edge-satisfaction)).
Candidates are then checked against what lies outside the plan, ranked, and cut by free slots and by exclusive edit-region overlap. Other overlaps are released and settled when the branches meet ([Edit regions](#edit-regions)).

### Edge satisfaction

An edge is satisfied by what the store holds now. Every predicate is scoped to the plan: node and edge ids are plan-local.

* `artifact_verified`: the predecessor has an active acceptance that digests to its id, has every required column, belongs to an
  execution of the node, stands on the plan's and the relationship's criteria (a later re-verification counts), is still the head of the
  generation it stands on while the relationship lives (its own, or after a [base refresh](#a-base-refresh-of-an-accepted-node) the later one the
  record names), rests on the active acceptances of its own inputs, and, for a code edge, carries the head, the pull request and the forge identity
  the edge pins. The latest merge check of the pull request, if any, must digest to its evidence and name the head the acceptance stands on: the
  accepted head, or after a base refresh the head the record names. A check made under a head the acceptance stood on before a record moved it (its
  own, or an earlier record's) is history and says nothing about now; a check made under any other head is not a reading of the acceptance and reads
  `blocked:stale_head`. A cancelled predecessor satisfies nothing.
* `integrated`: an observation says the accepted head is an ancestor of the target branch, no later observation says otherwise, the parent marked
  the same revision merged, and, when a merge turn carried the observation, that turn landed the same head on the same branch. A landing does not make a result current: as on an artifact edge, the acceptance
  must also be whole and digest to its id, belong to an execution of the node, stand on the plan's and the relationship's criteria now, and rest on active acceptances. The head's own currency is not asked, because what landed is in the target.
* `decision`: an active, approved decision of the subject with the plan's digest by an authority kind the edge names, or a settled supervisor
  directive with that digest. Authority text is opaque: it is compared, never read.
* A predecessor the plan **cancelled or archived** satisfies no artifact or decision edge and an integrated edge only when its landing is observed (the observation is refused for a cancelled node, so
  there it has to have been observed before the cancel; an archived node's landing can still be observed): the edge reads
  `blocked:predecessor_cancelled` or `blocked:predecessor_archived`, as it does for a predecessor whose relationship was cancelled. The same follows what an accepted predecessor consumed
  ([Pause, resume, cancel and archive](#pause-resume-cancel-and-archive)).

### Invalidation

A plan revision can change what an accepted node was built from. The reading judges that every time it is computed and never stores it: staleness is derived from the plan, the acceptances and the manifests, like every other node state, so it clears by itself when the cause is repaired. Two readings of one store state are equal byte for byte, as every reading is (no clock is read; the rebuild below takes the author, the time, the base, the volatile snapshots, the rule version and the size of an artifact from the manifest the node consumed, and hashes no file).

* **Seeds.** An accepted node that has not landed is a seed when what it consumed is no longer what the plan and the store ask for:
  * its slice digest ([DAG plans](dag-plans.md#digests): its spec, its title included, and its incoming edges) is not the one recorded by the manifest its acceptance consumed: a node edited, an edge added into it, an edge retired from it. The cause is read from the consumed inputs' edge ids against the current incoming edges (`edge_added`, `edge_retired`, else `slice_changed`);
  * the criteria its output stands on are not the plan's: the effective criteria of its acceptance, the latest re-validation or else the criteria it was accepted with, differ from the plan's (`criteria_changed`, contract 3.2, E-11). This is asked whether or not the slice moved, so a plan that went back to the criteria the acceptance was made with, after the output had been re-verified against others, makes the node a seed again: its slice is the consumed one and its output is not verified against the plan's criteria. Re-verifying the same output against the plan's criteria resolves it with no new generation (E-21), so the mark goes away. A change of the criteria together with another change of the spec reads as the slice change;
  * an acceptance it consumed is no longer the active acceptance of its node, a predecessor accepted again (`input_changed`, contract 3.1, E-25). This is what keeps a node stale after the node above it is repaired, until it is accepted again itself.

  A node that landed is never stale (E-20): its result is in the target branch, so a revision above it makes a new node, not a rerun.
* **Descendants.** Only the seeds and the nodes below them in the current graph are judged; a node outside that closure reads as before.
* **Judgement by value.** A seed is stale without a rebuild: for a changed slice its digest is part of its manifest, so the manifest digests cannot be equal, and a criteria or consumed-acceptance seed is stale by the facts named above. A descendant is rebuilt with `BuildManifest`, as it consumed, and its manifest digest is compared with the one its acceptance consumed. Equal means current, however much changed above it. A difference counts when an incoming edge, in id order, explains it: an `artifact_verified` or `integrated` predecessor whose accepted result is stale (asked directly, whatever other reason the edge shows: a change of slice and criteria together is not hidden by `blocked:stale_criteria`), or a satisfied edge whose consumed value differs: the acceptance, the head an integration landed, the decision (id, digest and revision, as the manifest records them). An integrated landing is unchanged when an observation of the current containment run names the landed commit the node recorded (the same acceptance, repository, base branch and head, positive and not reverted, with a landed carrier): the tip an observation read is not a value the node consumed. A difference that has no such edge (a moved head or a cancelled predecessor, other readings of the edges) is not a stale result, so the node stays accepted.
* **The edge gate.** An `artifact_verified` edge (a code pin included) from a stale predecessor is not satisfied: it reads `blocked:stale_predecessor` and its detail names the edge, the predecessor and why it is stale, so no node is released onto it (contract 8.2, E-25). It is the last check of the edge, after the criteria, head and consumed-input checks, so those reasons are the ones shown when several hold; the judgement itself does not depend on them. An `integrated` edge is gated the same way once a landing would satisfy it: a stale result that landed in some of its targets and not in all (one that landed in every target is never stale) hands nothing over, wherever its head landed, and an edge whose target has not landed keeps reading `wait:edge:<edge_id>`. A node that was accepted on such a landing is stale with it (`stale:edge:<edge_id>`, cause `predecessor_stale`), so its own successors and its pull request are held back too, until the predecessor has landed everywhere or the node is accepted again. `decision` edges are not gated: what they hand over is a recorded decision, not a result under review.
* **The merge lane.** A stale result never merges (contract 8.2): `dag-merge-judge` and `dag-merge-request` refuse a stale accepted pull request with `disposition_conflict`, naming the stale reason, and write no judgement row and no merge turn for a result that is already stale when the call is made. A revision that lands after a judgement has recorded an `eligible` row leaves that row in the history and creates no turn (see [Merge eligibility](#merge-eligibility)). No outcome and no refusal reason is added.
* **Containment does not follow dev.** The `integrated` predicate asks whether the accepted head is contained in the target, and ancestry is monotone, so a merge that moves dev changes no answer. The observation that satisfies the edge is the earliest positive one of the current containment run (the first after the last negative observation), so the landed commit that consumers' manifests name, and the time the edge became satisfied, stay as they were when the integration is observed again at a newer tip (contract E-27). A manifest recorded under the earlier choice of the newest observation is still read as unchanged for the same run.

A stale node reads state `stale`, disposition `stale`, reason `stale:slice_changed`, `stale:criteria_changed` or `stale:edge:<edge_id>` (when the reason rests on an incoming edge: an edge added or retired, a stale predecessor, a consumed value that changed), and a `stale` object beside the detail, printed for stale nodes only:

| Field | Meaning |
| --- | --- |
| `cause` | `slice_changed`, `criteria_changed`, `edge_added`, `edge_retired`, `predecessor_stale` (the predecessor over `edge_id` is stale) or `input_changed` (the value that satisfies `edge_id` is not the consumed one) |
| `seed_node_id` | the node the staleness stems from (the node itself when its own slice changed) |
| `edge_id`, `predecessor_node_id` | the incoming edge the reason rests on and the node on its other end (null when only the node's own slice or criteria changed) |
| `consumed_acceptance_id`, `current_acceptance_id` | the predecessor version consumed over the edge and the acceptance that satisfies the edge now |
| `consumed_decision`, `current_decision` | over a decision edge, `<decision id>@<revision>` consumed and now |
| `consumed_slice_digest`, `current_slice_digest` | the slice digest the consumed version rested on and the plan's now (the node's own, or the predecessor's for `predecessor_stale`) |
| `consumed_manifest_digest`, `rebuilt_manifest_digest` | the manifest the acceptance consumed and the one built now (null for a seed, which is not rebuilt) |
| `action`, `action_detail` | what is done about the stale result and the sentence that says why: `revalidate`, `correct`, `hold` or `redefine` ([Handling a stale node](#handling-a-stale-node)) |

The detail also carries the edge, the predecessor and the short acceptance ids, so the pass records and the reading's input digest hold them. A stale implementation node keeps holding its edit regions until its head lands. The relationship's own state comes first in the reading (a paused node reads paused, an evicted one `blocked:evicted`), while the gate on the edges built on the node follows the judgement.

What it does not do: the judgement marks and nothing else; what is owed to a marked node is [Handling a stale node](#handling-a-stale-node). It does not adopt a restarted run, pause or cancel, or answer a progress query. A node whose consumed manifest cannot be read is not judged (the edges out of it report `blocked:manifest_tampered`, or `blocked:acceptance_incomplete` when the manifest is not stored). A criteria re-registration without a plan revision is not a slice change here. The function that later issues ask is `staleOf`. Behind a landed node a mix of two acceptances of one predecessor is not a stale result, and the closure of B-14 (`blocked:inconsistent_inputs`) is what finds it.

### Handling a stale node

The reading says why a node is stale and, in the `action` of the stale object, what is owed to it. The route is derived with the rest of the reading from the stale reading and the relationship the node stands on (contract 3.2, 5 and 8.4); it is never stored and reading it writes nothing.

| `action` | When | What is done | What is never done |
| --- | --- | --- | --- |
| `revalidate` | only the node's criteria changed (cause `criteria_changed`) and everything it consumed is still current: no acceptance it consumed was replaced and the manifest rebuilt as it consumed it is complete and digests to the same name | the same output is ruled again under the plan's criteria and `dag-accept` records a revalidation of the same acceptance (E-11, E-21): the criteria registered for the relationship change, the parent rules the output `verified` under the new set, and accepts it again | a new generation or a new child |
| `correct` | everything else on a node whose relationship is active: its spec, an edge into it or an input it consumed changed, or a change of criteria that also moved an input | the output is reworked by the same child, as the next generation of the same relationship: `dag-correct --prepare`, then either the `needs_changes` ruling that carries its instruction or a generation opened by hand ([below](#three-ways-to-open-the-generation)), `dag-correct`, then `dag-accept --supersedes` for the reworked result | a child made again |
| `hold` | the node rests on a stale predecessor (whatever its own cause: cause `predecessor_stale`, or a replaced input, or a change of criteria on a node that does), or an input is not there (an incoming edge that is not satisfied now: a predecessor nobody has accepted yet, a decision that was rejected), or the plan holds the node (paused, or the whole plan paused), or its relationship is paused, or a correction generation of it is already open | nothing on this node: the detail names what to wait for | |
| `redefine` | the relationship has ended (archived, superseded or cancelled), so there is no child to send a correction to | the parent decides whether to redefine the node: a new relationship registered with `supersedes` (contract 5, ID-4), which makes a new child | |

Decision D-08 (how far a redefinition reuses the same child) is read from contract 5 and nothing wider: a **correction** is a new generation of the same relationship, the same child and the same node with a manifest rebuilt as the plan holds the node now; a **node redefinition** is a new relationship with `supersedes`, which is a new child. The scheduler routes between the two and refuses what the contract forbids; it never registers the new relationship.

Two refusals keep the routes apart. Both are `disposition_conflict` with the reason in the detail, so no refusal reason is added, and neither writes a row.

* `dag-accept` does not record a revalidation for a node that is stale for any reason but its criteria, or whose criteria and an input both changed: ruling the old output again resolves nothing, and the refusal names the route. A node that is not stale can still be revalidated, a node that landed included: a landing does not make a result current, and an outgoing `integrated` edge reads `blocked:stale_criteria` until the same output is ruled under the plan's criteria ([Edge satisfaction](#edge-satisfaction)).
* `dag-correct`, in both its steps, refuses a node whose accepted head landed in every target, whatever kind a later revision gives the node (a node that landed reads `done:integrated` whatever its kind). A node that landed is never run again (E-20): it is never stale, `dag-release` of it replays the release it recorded (or is refused when it recorded none) and makes no child, no correction is prepared for it, and a generation the relay opened for it is not recorded as its own. What changed above it is carried by a successor node of a new plan revision, which is released like any other node: its edges name what it consumes, and one built on a stale result reads `blocked:stale_predecessor` until that result is current.

What a node's siblings keep is whatever this page never touches. A revalidation writes one row of `dag_acceptance_revalidations` and a correction one row of `dag_node_executions`, both for the node asked about; the acceptances, executions and slot tenures of the nodes that are not stale, and of the nodes that are stale for another reason, stay as they were. This build has no separate ledger of the cost of a node's work: those records are what it keeps.

#### Three ways to open the generation

The correction goes to the same child as the next generation of the same relationship, and the generation is opened in one of three ways. `dag-correct --prepare` prints the instruction line, the manifest digest and the dispatch request id for the first two.

* **A ruling.** The relay's verdict writer takes another ruling on an event it already ruled `verified` in two cases ([Ruling an event that is already ruled](README.md#ruling-an-event-that-is-already-ruled)). The first is while a review is open, which the relay opens when the criteria registered for the relationship are no longer the set the head was ruled under (`delivery/ack.go`, re-review; the accepted event must still be the head of the current generation). The second is a `needs_changes` ruling before anything rests on the verified ruling: no acceptance of the event, no merged mark, no merge turn that is merging, of unknown effect or landed. Once the plan has accepted the event and no review is open, the writer refuses a second ruling with `disposition_conflict`, and the second way below is the route. The parent rules `needs_changes` with the instruction as the restoration finding, the writer opens the generation and sends the instruction, and `dag-correct` binds the manifest the finding names. A plan revision that changes the node's criteria digest, with the new set registered for the relationship, opens that review.
* **A generation opened by hand.** When the head is ruled `verified` under the criteria registered now, which is the case of a node made stale because an input it consumed was replaced and nothing else, the writer refuses a second ruling on the accepted head (`disposition_conflict`, naming this route) and opens no generation. The relay has a route for that, written in the coordinator's skill (`crw-run`, "A fresh execution generation"): the coordinator opens the generation with `generation-open --reason needs_changes_revision` under the dispatch request id `dag-correct --prepare` printed, sends the instruction line to the child in the message that dispatches the re-review, and binds that turn with `generation-bind`. Then `dag-correct --manifest-digest D` binds the generation to the manifest. A node whose stale reading says `correct` takes this route, and so does an accepted node that is still current when its generation's reason states a correction (below): `dag-correct --prepare` succeeds for any node, and a generation opened for a node whose route is `revalidate` or `hold` would be refused when it is recorded.

What the second way binds is bounded, so it cannot make a rerun or bind a manifest other than the one the generation was opened for: the node's accepted result must be stale, or accepted and still current with a reason that states a correction ([Correcting a result that was accepted and is still current](#correcting-a-result-that-was-accepted-and-is-still-current); a result that is not accepted yet is corrected by a ruling, and a generation that only merged the base is recorded by [`dag-base-refresh`](#a-base-refresh-of-an-accepted-node) instead: the writer refuses a ruling on it and this route refuses it because it is not a correction; a node that landed was refused before); the manifest must be named with `--manifest-digest`, be the one stored for this node at its current slice and criteria, and still rest on the inputs the node's edges are satisfied by now (it is judged against the store again, the file bytes aside, as release does when it records its own intent: a predecessor accepted again after the prepare leaves another input than the one the child was told to consume, and nothing is bound); the generation must have been opened under the dispatch request id derived from that manifest (`CorrectionRequestID`: the plan, the node, the manifest and the generation), so it was opened for this manifest and no other; it must be bound to a dispatch turn, because a child reports in a bound generation only; and it must be the generation right after the one the accepted result stands on, so a correction that is already open is not skipped by opening another beside it (opening one moved the relationship past the generation that correction is accepted on: the refusal is reported and no further generation is opened, as when the plan moved the node). Each refusal is `disposition_conflict` with its reason in the detail and writes nothing. What is recorded of how the instruction reached the child is that request id (in `managed_request_id` of the execution row, which a ruling leaves empty) and the turn the generation is bound to; the answer says `opened_by` (`ruling`, `generation_open` or `decision_reply`), `dispatch_request_id` and `dispatch_turn_id`, and a repeated `dag-correct` answers the same as a replay. The generation is not recorded for a node whose route, without that generation, is anything but a correction: a change of the criteria alone is ruled again and opens no generation, and what rests on a stale predecessor or on an input that is not there waits.

What the second way does not prove: the relay does not read the child's thread, so the request id and the bound turn are the coordinator's statement of how the instruction was delivered, where a ruling's restoration note is compared with the instruction line. The child checks the manifest file against the digest and sha256 the line names and answers `blocked_needs_input` on a mismatch. The child's first receipt in the generation carries no `--supersedes-revision` (the generation has no earlier revision to supersede). A generation opened by hand is also not recoverable by dag-correct if the plan moved the node between the opening and the recording: the recording is refused (the manifest was prepared for another version of the node), preparing again names the next generation, and recording that one is refused at the gap (`generation 3 of R follows generation 2, and the last recorded execution of N is 1`). Open no further generation: report the refusal and stop, since the same holds for a ruling that opened its generation before the plan moved.

**A decision reply.** A child that stopped with `blocked_needs_input` is answered with `decision-reply` ([Replying to a blocked receipt](README.md#replying-to-a-blocked-receipt)), and a `split_approval` or `scope_change` opens generation g+1 of the same relationship in the reply's own transaction (reason `decision_reply`, dispatch request id `decision-<decision event id>`). Nothing is prepared and no ruling is needed: the child was told its new criteria by the decision, and `dag-correct` (no `--prepare`, no `--manifest-digest`) binds that generation to the node.

What the third way binds is bounded, so it cannot record a generation the child was not told about or a node the child was not dispatched as. Each refusal is `disposition_conflict` (`criteria_set_changed` where said) with its reason in the detail, writes nothing and adds no refusal reason.

* The generation must name a `split_approval` or `scope_change` of this relationship that advanced to it.
* The node must differ from what the child was dispatched with by its criteria alone (the predicate the stale reading uses). A change of the node's issue, kind, title or edges after the dispatch is refused, because the decision tells the child its criteria and nothing else; the way out is to restore the node (the same slice digest, its edges included) or to redefine it.
* Those criteria must be the plan's now: a decision that named a set the plan does not hold is refused `criteria_set_changed`, and revising the plan to the decided set lets the same call through.
* The decision must have been dispatched: its delivery is `dispatched` or `acknowledged` and the generation is bound to the turn it was dispatched into. A queued decision, or a generation that is not bound yet, is retried after the relay's next pass (`decision-show` prints where the delivery stands). A generation bound by hand to another turn is never rebound, so a decision dispatched into a turn other than the bound one stops the node there: the refusal names both turns, nothing more is opened, and the way out is a redefinition. Do not `generation-bind` a decision generation.
* The manifest recorded is the one the child was dispatched with, brought up to date: the dispatch manifest with the node's slice and criteria digests as the plan holds them, the plan revision, epoch, author and time of the recording, and a digest recomputed. Its inputs, base, volatile snapshots and rule version are what the child was dispatched with. It always passes the manifest verification (without the file bytes) against what the node's edges are satisfied by now, so a predecessor accepted again or superseded since is refused with the child's manifest named: the child was not told what moved, no retry of the same call reaches that (the superseded acceptance is not reactivated and the new one has another id), and the way out is a redefinition. When nothing in the node moved (the plan never changed it) the dispatch manifest is bound as it is and `carried_over` is true.

The row is a `correction` execution whose `managed_request_id` is the decision request id. The answer says `opened_by` `decision_reply`, that request id and the turn the generation is bound to, and a repeated `dag-correct` answers the same as a replay. A supplied `--manifest-digest` only cross-checks the derived one.

What a decision does not do to a generation: `answer` and `stop` keep it, so there is nothing to record and `dag-correct` replays the generation already recorded. A result in g+1 is accepted as any result is (`dag-accept`, with `--supersedes` when the node already had an accepted result), and the node reads accepted and not stale, because its manifest carries the plan's slice and criteria digests. The generation must be recorded before anything else opens another one: a second advancing decision, or a ruling's generation, before g+1 is recorded leaves a gap that `dag-correct` refuses for good (generation g+2 follows a generation that is not recorded), and the way out is a redefinition. A paused plan, node or relationship is refused as for every correction, and the same call is recorded after the resume.

#### Correcting a result that was accepted and is still current

A blocking defect can be found in a result that the plan already accepted and that is still current, before it lands: a bundle review that finds one in an accepted member is the case. Nothing above the node changed, so the reading gives it no stale object and no route, the relay's verdict writer takes no second ruling on the head it ruled `verified` (`disposition_conflict`), and `dag-accept` refuses a generation that is not recorded as an execution of the node. The result is corrected by the same child as the next generation of the same relationship, opened by hand, with the same steps as the stale case and one more: the reason the generation is opened under states the correction.

1. `dag-correct --prepare` rebuilds the node's manifest as the store holds it now and prints the instruction line, the manifest digest and the dispatch request id.
2. `generation-open --relationship <rel> --dispatch-request-id <the id the prepare printed> --reason accepted_result_correction` (or `--reason needs_changes_revision`, the default; both state a correction) opens the next generation. The instruction line is sent to the child in the message that dispatches the re-review, and that turn is bound with `generation-bind`.
3. `dag-correct --manifest-digest D` records the generation as a `correction` execution of the node (`opened_by` `generation_open`), under every check the stale case has: the generation right after the one the acceptance stands on, the manifest stored for the node at its current slice and criteria, the dispatch request id derived from that manifest, a bound dispatch turn, and the inputs as they stand now. The node must not have landed, and a node whose result is not accepted yet keeps the ruling route.
4. The child reports in the generation, the parent rules it and takes the result with `dag-accept --supersedes <the acceptance it replaces>`. Until then the previous acceptance stays active and the node still reads `done:accepted`; the edges that take its result read `blocked:stale_head` from the moment the corrected generation is open (the relationship is then on a later generation than the acceptance stands on) until `dag-accept --supersedes` takes its result, so nothing downstream consumes the corrected generation before it is accepted.

   The accepted head is held back while the correction is open, not only after the child pushes. The merge gate reads the relationship's live execution generation against the generation its active acceptance stands on: while the live one is later, the node is **under correction** and its old head is not a merge candidate. The single-lane judgement (`dag-merge-judge`, `dag-merge-request`) is refused `disposition_conflict` naming the open generation and writes no row and no turn, and the bundle open, verify and land refuse a member the same way (see [Merge eligibility](#merge-eligibility)). Without this, a bundle or a lane turn taken between opening (or recording) the generation and the child's first push would carry and land exactly the head the correction is repairing, because until that push the pull request still shows the accepted head. The gate is about the correction being open, not about the head: `dag-accept --supersedes` of the new generation's result moves the acceptance to the stand generation and the node is judged again, a withdrawn generation puts the live generation back and the old head may ride again, and a generation recorded by [`dag-base-refresh`](#a-base-refresh-of-an-accepted-node) moves the stand generation with the live one, so a base refresh is not a correction.

   A turn's repository is matched against the accepted node's repository and its forge repository (the owner/name recorded with the acceptance) by one rule. A forge slug is compared trimmed and case-insensitively. A local path is compared by the repository git names for it: the common git directory of the path, with symlinks resolved, so a checkout, its `.git` directory, a symlink to it, a linked worktree and that worktree's administrative directory are one repository, while a directory whose name ends in a space is still its own name. A path that git cannot name (it is not a repository here, git is missing, or it does not answer in time) is compared by its exact text, and nothing else. The lane gate and the in-flight guard of a correction apply the same rule, so a turn spelled any of these ways is held the same way.

Recording is refused while the accepted head may already be on its way to the base: a merge turn of the node is `merging`, of unknown effect or `landed` (resolve it first, `merge-turn-resolve`), or a live bundle (opened or verified) carries the node's stand head as a member (close it first, `merge-train-close`). A bundle refusal is not a dead end: the coordinator closes the bundle and repeats step 3 with the same manifest digest. A turn that is `merging` or `unknown` is resolved first, and once it resolves to `returned` step 3 can be repeated. A turn that is already `landed` is refused, and `merge-turn-resolve` does not return it, so this route does not record the correction of that node; the parent reports it. In every case the generation opened in step 2 stays unrecorded and no other generation is opened. Preparing again and opening another generation would leave the unrecorded one behind, and the next correction would be refused for not following it.

What notes the route is the generation's own `reason` column: no column, table, schema, refusal name, CLI flag or `specs.json` entry is added. A generation opened under a reason that states no correction (the assignment itself, a returning tenure, a reply) is refused by the same step, naming the reason it carries, and a generation opened for a base refresh is not bound here either: [`dag-base-refresh`](#a-base-refresh-of-an-accepted-node) records that one. A generation opened for this route and never sent is withdrawn like any other ([A generation opened by hand and never sent](#a-generation-opened-by-hand-and-never-sent)).

### Input checks

When all incoming edges of a candidate are satisfied, the artifacts it would consume are read again. These file checks apply to non-code `artifact_verified` inputs (a code-pinned input consumes the accepted head instead), and a frozen copy of the manifest is checked when the receipt records its reference: every file the predecessor's receipt declared must still
exist, hash to the declared digest and size and lie under the predecessor's artifact roots; a frozen copy of the manifest must read and agree; an artifact
edge that hands over no artifact is blocked, never an empty success; the list of artifacts a receipt declares must hash to the revision the parent accepted (so an artifact left out of the list, or added to it, is found even when every remaining file is intact); and following the consumed acceptances down through their manifests, no node may appear
under two acceptances. The first violated path decides the reason.

### Ranking and selection

Candidates are ordered by the hop count of the longest chain each starts (critical path), then by the nodes below it, then by the stored time it became ready,
then by node id. There is no wave barrier: a long independent node does not hold back a short dependent chain, because a node waits for its own predecessors. Capacity and edit-region conflicts may still defer a candidate. The first candidates
that fit the free slots and do not overlap exclusively are ready; each candidate cut is deferred with `defer:no_capacity`, `defer:capacity_unmeasured`, `defer:host_memory` or `defer:edit_overlap`, and the pass records which limit decided
the first cut: `none`, `no_capacity`, `edit_overlap`, `capacity_unmeasured` or `host_memory`.

### Capacity

Free slots are the smallest headroom over the initiative above the project, the project and the store, counting held execution slots against each `runs` ceiling
the way `slot-reserve` does (a ceiling of 0.5 still allows one reservation). The DAG never runs more children than the standing cap of 6 unless a cap basis for that
limit revision is recorded in `dag_cap_basis` (decision D-05 is not made, so no value above 6 is assumed). An enforced ceiling on another dimension without a usage
observation leaves no slot free.

### Host memory

A release starts one more child on a host that other jobs already load. `dag-ready` and `dag-release` read MemAvailable and swap from `/proc/meminfo`, and memory pressure `some avg60` and `full avg10` from `/proc/pressure/memory`, once per command. Swap occupancy is information by default: idle pages can remain swapped out with ample available memory and little pressure. Available memory and the two pressure signals hold new releases; an operator can explicitly enable an occupancy ceiling. The `some avg10` is retained as information and decides nothing.

While any measured value crosses its threshold, every candidate that no edit overlap cuts is deferred with `defer:host_memory` (also when no slot is free, so the reason is the host's). `dag-release` refuses a new release with the existing `capacity_exhausted`, the closed reason and measured values in its detail; nothing is written and no slot is reserved. Running children are untouched. The next reading within the thresholds releases the same nodes again; there is nothing to clear.

| Variable | Default | Holds new releases when |
| --- | --- | --- |
| `CRW_DAG_HOST_MIN_AVAILABLE_GIB` | 15 | MemAvailable is under this many GiB (0 never trips) |
| `CRW_DAG_HOST_MAX_SWAP_PERCENT` | 100 | swap use, in percent of SwapTotal, is over this; off by default (100 never trips, 0 trips on any use) |
| `CRW_DAG_HOST_MAX_PRESSURE_SOME_AVG60` | 10 | memory pressure `some avg60` is over this (100 never trips, 0 trips on any pressure) |
| `CRW_DAG_HOST_MAX_PRESSURE_FULL_AVG10` | 5 | memory pressure `full avg10` is over this (100 never trips, 0 trips on any pressure) |
| `CRW_DAG_HOST_PROC_ROOT` | `/proc` | not a threshold: where `meminfo` and `pressure/memory` are read |

**Signal and window.** The operating logs sampled every 30 seconds contain PSI **avg10**, as confirmed in the logger; the assignment's description of those values as avg60 was incorrect. Across 1,798 captured rows, 299 high-swap samples (at least 95 percent used, at least 34 GiB available and some avg10 below 3) have full avg10 at most 2.83. Full avg10 exceeds 5 in 18 captured rows; recorded pressure includes 7.42 and 16.86, while available memory drops to about 11 GiB in another interval. The full ceiling of 5 clears the specified calm samples and detects the recorded stalls. These sample counts are not a time-based hold rate. The available floor of 15 GiB and some avg60 ceiling of 10 are retained; the logs do not contain historical some avg60 or the cited 18:46 freeze, so synthetic tests model that incident's described low-available/high-pressure shape rather than claiming a historical replay.

The full signal uses the kernel's existing 10-second average in the same pressure-file read: no second sample, sleep, vmstat read or cross-command state is added. Some pressure still uses its 60-second average, while full pressure can hold a release during a shorter stall even with ample available memory. A swap-in rate is not used because these logs contain no swap-in counter and deriving a rate would require a separately justified sampling window.

Thresholds are strict (a reading exactly at one is within) and come from the command environment. Existing variables keep their meaning; an empty value is unset, and a non-finite number or a value outside its range is a usage error (exit 4) naming the variable. Only `dag-ready` and `dag-release` read them: `dag-progress` and `dag-restart` remain functions of the store. Each pressure line is read independently. An absent or malformed signal is null and recorded as unmeasured with its cause, holds nothing itself, and is neither pressure nor proof of safety. Other measured dimensions can still hold releases; when all four are unread the state is `unmeasured`. A host without swap has a measured use of 0.

**What the reading says.** `pass.host_memory` prints `state` (`within`, `deferring` or `unmeasured`), `limits` and `limits_from` (`default` or `environment`), `measured` values, `exceeded` and `unmeasured` dimension names (available, swap, pressure, pressure_full), and `unread` causes. `measured.pressure_full_avg10` and `limits.max_pressure_full_avg10` extend the existing object; `pressure_some_avg60` remains judged and `pressure_some_avg10` remains informational. The input digest covers every value. `dag-ready --record` keeps the same object in the existing `dag_pass_host_memory.host_json`, beside the pass row; no table or column is added. The shipped `dag_passes.deciding_limit` set stays unchanged: host cuts are stored there as `no_capacity`, and the side table's `reading_limit` keeps `host_memory` for measurements.

**Limits.** A command judges one sample, but the host can change before the child starts, and ready and release commands can see different full avg10 values. Faster full-pressure changes can also change the input digest more often. A replay of an already decided release is not a new release and is not held. Children started outside DAG releases are not bounded. Explicitly selecting an occupancy ceiling below 100 restores the stock-based hold, including its possibility of holding a host with idle swapped pages. No automatic swapoff or host tuning is performed.


### Edit regions

`crw relay dag-region-declare --plan P --node N --actor A --regions @file` declares the places an implementation node will edit, before it is released: 1 to 64 regions of
a repository, path, kind (`tree`, `file`, `symbol` with its symbol), change (`edit`, `rename`, `delete`) and grade (below). A repository is a forge `owner/name` or an existing local
checkout (the directory its absolute path reaches, links resolved); whitespace inside a path component is kept and the path is cleaned before it is stored, while surrounding whitespace and control characters are refused. A delete, a rename and the hotspots (lockfiles, anything under `.github/`, a Makefile or Dockerfile, `.sql` files, a `schema` or `migrations` directory) are exclusive at their own place, whatever grade was declared (they are stored as the `exclusive` grade), and
nowhere else: they conflict with the regions that share the place, which are the same path whatever the kind or symbol of the other region, a tree that covers it and, for a tree they delete or rename, what lies under it. A symbol
key is not a smaller place for them: two symbols of one `.sql` file, or a deleted symbol beside another symbol of its file, are one place, so two nodes that change the same `.sql` file or delete the same path run one after the other,
while a node that deletes a file, one that adds a `.sql` file, one that changes `.github/workflows/ci.yml` and every node that does not share their place are released together. A rename is held at the path it moves away from: a region names one
path, so declare the destination as a region of its own (an `edit` of the new path) when another node could write it. A hold of the whole repository is the declarer's word and nothing else: a region that carries
`"exclusive": true` conflicts with every other region of its repository (a repository-wide rename, say), and the answer prints it as `exclusive: true`; a delete, a rename or a hotspot declared without it prints `exclusive: false` and the `exclusive`
grade. The declaration stores what was stated for every region, in `dag_node_region_holds`, and keeps the `exclusive` column of `dag_node_regions` as an older runtime reads it (set for a rename, a delete, a hotspot and a stated hold).
A node with no declaration counts as overlapping every other node: it waits while any node holds regions, and every declared node waits while one
undeclared node holds. Regions are held from release until the head lands; once a node holds them a declaration may only narrow them ([Narrowing a held declaration](#narrowing-a-held-declaration)). A forge slug and a checkout path of one
repository are two keys; a plan names one spelling per repository.

A region is a signal for the merge order and for the handling of a conflict, and not a gate on release: the scheduler is there to run nodes in parallel, so only an overlap that cannot be settled when the branches meet holds a release back.

#### Grades

Every region carries a grade, which says how an overlap on its place is settled:

| Grade | The region claims | Against an overlapping region |
| --- | --- | --- |
| `independent` (the default) | nobody else edits this place | the claim is contradicted: the overlap is judged `exclusive` |
| `mechanical` | the result of an overlap is fixed by a rule it names | released, and left out of the overlap count |
| `local` | the same file, another clause or symbol, a small hunk | released as `local-optimistic`; the later child resolves it at its base refresh |
| `exclusive` | an overlap cannot be settled at merge time | `defer:edit_overlap` |

A `mechanical` region names its rule, `union` (both sides add rows or lines to one list), `renumber` (a clash of ids or numbers is renumbered) or `regenerate:<command>` (the file is derived and the command rebuilds it; the command is not blank, has no whitespace at its ends or control character, and the rule is at most 200 bytes). A mechanical region without a rule, a rule that is not one, a rule on any other grade and a grade that is not one of the four are refused as `malformed_receipt`: the relay's existing reason for a region that is not valid. A region declared without a grade is `independent`, which is how every declaration made before grades existed reads (it has no row in `dag_node_region_grades`), and so an overlap with one defers exactly as it did (a delete or a hotspot among them is read as the next section says).

The scheduler records and judges these rules and applies none. What settles a mechanical conflict at merge time is the parent's check, `crw skill base-refresh mechanical` (crw-run's `references/merge-readiness.md`, "Resolve a mechanical conflict yourself"): a `union` keeps every line of both sides, a `regenerate` command is run twice at the root of a fresh checkout of the head and leaves its files as they are, and `renumber` has no check, so such a conflict goes to the child.

The grade of an overlap is judged on the place two regions of one repository share (a tree contains what lies under it, a path is itself, two symbols of one file are apart unless they are the same symbol or either side makes the file one place: a delete, a rename, a hotspot or a listed shared contract file), from both grades: an `exclusive` side makes it `exclusive`, and so does an `independent` side, whose claim the overlap contradicts; two `mechanical` sides are a `mechanical` overlap when they name the same rule, and a `local` one when they name two (neither rule covers the other side's change); every other mix is `local`. The shared contract surfaces are exclusive whatever grade is declared: `contract/schema`, `contract/golden` and `contract/fixtures` and what lies under them, any `testdata/golden` directory, and the CLI spec `internal/relay/argparse/specs.json`. That list holds the place and not the repository: a symbol key means nothing on a listed file, so two commands of the CLI spec are one place, and an overlap whose common place is a tree that holds a listed path (two trees above the CLI spec, or two `testdata` directories, say) is exclusive too, while two trees that hold none, or a tree and a file under it that is not listed, stay graded by their own grades. The judgement reads declarations and not the repository, so a tree further above a golden directory (a package directory) is not looked into: it claims everything under it, and a `testdata/golden` it holds is exclusive only if the tree stops at or below `testdata`. Declare a tree that stops short of those paths where the work does not touch them. A declaration stores the grade a region is judged at (a listed path as `exclusive` with no rule), and the judgement applies the list again when it reads, so a row stored before the list grew cannot sit below it.

#### Declarations made before holds were narrowed

A build before CRW-431 stored every delete, rename and hotspot with the `exclusive` column set, because the classifier set it, and judged the column as a hold of the whole repository; a hold the declarer stated is stored the same way, so such a row
cannot say which it was. A row with no entry in `dag_node_region_holds` (every declaration made before this table, graded or not) is read as follows, and a store whose zone predates the table reads every row so:

| Stored by an earlier build with the column set | Read as | Why |
| --- | --- | --- |
| a delete or a hotspot | exclusive at its own place | the classifier set the column; the hold protected nothing outside the place (a delete has no destination, a hotspot is the file) |
| a rename | still a hold of the whole repository, until the node is declared again | the hold also protected the rename's destination, which a region cannot name; reading it narrower would release a node that edits the destination |
| any other path | still a hold of the whole repository | only the declarer can have set the column |

This changes the judgement of existing declarations that carry no grade (and of those that do), in one direction: a delete or a hotspot stops holding regions it does not share. It follows the principle the scheduler runs on, that only a
change two branches cannot both make holds a release back: the classifier's reading held every unrelated region for a change whose conflicts are confined to its own place, and no declarer is shown to have asked for it. A node that deletes one file, a node that
adds a `.sql` file and a node that changes a workflow file, declared by the earlier build, are released together without a new declaration. What it cannot keep is a hold the declarer stated on a delete or a hotspot, which reads at its
place; a node that does not hold regions yet restates it by declaring again with `"exclusive": true`. A node that already runs keeps the regions it was released with unless a declaration narrows them ([Narrowing a held declaration](#narrowing-a-held-declaration)): a declaration re-sent for a row that reads differently is a changed declaration, and is judged as one. A rename without the word gives up the hold of the whole repository the row implied, which is a narrowing and is accepted (the hold also protected the rename's destination, which a region cannot name, so declare the destination as a region of its own in the same declaration when another node could write it). A stated hold on a delete or a hotspot claims more than the node holds and is
refused as `disposition_conflict` until its head lands, and a rename that is not re-sent still reads as a hold until then.

#### Narrowing a held declaration

A node that holds its regions (its child runs, or its release is decided, and its head is not accepted yet) may declare again only to narrow them. `dag-region-declare` accepts the new declaration when it passes both of these tests, judged on the declarations as stored (grades folded, `foldedGrade`):

1. **Every new region lies inside what the node holds, and is held at least as strictly.** It is covered by a held region of the same repository spelling: a region that holds the whole repository (only the declarer's word, `Region.Exclusive`, or a rename a build before CRW-431 stored) covers every region of it and is covered only by one that does; a tree covers what lies under it, a file itself and the symbols in it, a symbol that symbol (a symbol of a hotspot, a deleted or renamed file, or a shared contract file is its file: they are one place). A rename, a delete and a hotspot hold only their own place, so they are covered like any other region at that place, and are always held as `exclusive`. Its grade weighs at least as much as that of every held region that covers it: mechanical 1, local 2, independent and exclusive 3 (against an overlapping region `independent` and `exclusive` both make the overlap exclusive, so either may be declared for the other). A mechanical region keeps its rule: another rule is another claim, because two mechanical regions with two rules overlap as `local`.
2. **Every held place stays at least as strictly held.** Regions nest or are disjoint, so a new region over a held one must not hold that place less strictly than the node did: `{pkg tree local, pkg/sub/x.go file exclusive}` cannot become `{pkg/sub tree local}`, because x.go would then be held as local, while `{pkg/sub tree local, pkg/sub/x.go file exclusive}` can.

Dropping a held region is a narrowing. A declaration that fails a test is refused `disposition_conflict`, which names the first region that widens and says why, and writes nothing; one identical to the stored declaration is a replay. An accepted narrowing is the next `declaration_seq`, the answer says `narrowed`, and the next pass judges the places the node gave up as free for other nodes (nothing is released by the declaration itself). Two cases keep the old refusal: a node whose head is accepted, because the declaration of an accepted head describes its pull request and the conflict sweeps grade and mark drift from the latest declaration, and a node that holds regions it never declared, which holds everything and so has no declaration to narrow. Whether a node stays inside what it declared is not checked here: the [drift](#the-sweep) of the conflict sweeps says when it did not.

#### The release rule

For each implementation candidate the reading judges what it overlaps among the nodes that hold regions (the nodes running or accepted and not yet landed, and the candidates already released in this pass). Per holder the worst grade over every pair of regions counts once. The candidate is released under a rule:

| Rule | When | Released |
| --- | --- | --- |
| `independent` | it overlaps nothing that is held | yes |
| `mechanical` | every overlap is mechanical | yes |
| `local-optimistic` | the worst overlap is local | yes |
| `defer` | an overlap is exclusive, or a side is undeclared, or the worst overlap is local while the [release policy](#release-policy) has local-optimistic release off | no: `defer:edit_overlap`, and the pass's deciding limit is `edit_overlap` as before |

The rule is in the node's `release` object, and in nothing the release path reads as a hold: a released node is a plain ready node with no reason and no detail. A deferred node keeps its reason and its detail names the rule, the row that decided it and the counts. The `release` object has the `rule`, the `overlaps` by grade (`mechanical`, `local`, `exclusive`: the holders it overlaps, each by the worst grade of their overlap) and the `basis`: one row per overlapping pair of regions, worst grade first, at most 16 kept with `basis_omitted` counting the rest. A row names the `holder`, the `repository` and `path` of the place both touch (the deeper of the two paths), the `grade` of the overlap, the grade and rule each side was judged at (`candidate_grade`, `candidate_rule`, `holder_grade`, `holder_rule`), and what the plan's recent conflict observations say of that place: `recent_observations` (the latest twenty by the time they were stored), `recent_conflicts` (those that conflicted in a file of the place, under the repository name the region was declared with) and `unattributed_conflicts` (those that conflicted without naming any file in that repository: observed before files were recorded, in another repository, or under a name that could not be tied to it). An undeclared side has a row of its own with `undeclared` set to `holder` or `candidate` and no place. The decision follows the grades alone; the observations are evidence about the places.

`dag-conflict-observe` records the files git could not merge in `dag_conflict_observation_files`, under each name the observed checkout is known by: its path with links resolved and, when its `origin` remote names `owner/name` on the forge the relay talks to (`GH_HOST`, else `github.com`), that slug. A checkout whose origin is unset, local or on another host is known by its path alone, and a linked worktree's path is not its main checkout's, so the two meet only through the slug. The origin is read at the observation for this evidence only (it is never given to the isolated repository the merge runs in), and a repeat of an observation writes nothing, so changing the origin afterwards changes no row.

A candidate that is not an implementation node edits no repository and is not judged. A candidate that the judgement released can still be cut by capacity, and keeps the rule its overlaps earned.

### Release policy

Optimism has a cost. A local overlap that is released is settled when the branches meet, and when that settling takes long, or a merge turns dev red, the overlap should not have been released. A plan may therefore hold a **release policy** (CRW-411) that switches local-optimistic release off from what the last landings show, and on again after a run of clean ones (the shape of a gate that shrinks its window on a failure and grows it back on success). It is recorded with `dag-release-policy-record` and read by every `dag-ready` and `dag-release` of the plan. A plan with no policy is released as before, prints nothing new and digests as before.

| Setting | Meaning |
| --- | --- |
| `window` | how many of the latest landings are read (1 to 64) |
| `handling_seconds` | a landing is **slow** when the conflict it handled took more seconds than this (1 or more) |
| `red_merges` | red or reverted landings in the window that switch it off (1 to the window) |
| `clean_run` | clean landings in a row that switch it on again (1 to the window) |

The values are rows of `dag_release_policy`: the highest `policy_seq` of a plan is in force, the same values again are a replay, a different set is the next row and the earlier ones stay as the ledger. The command is the parent's and takes the coordinator epoch; the row keeps the epoch it was recorded under (`coordinator_epoch`), as the other decision rows do. No value is built in, because this build has no measured basis for one; a `clean_run` of 2 or more keeps a policy from alternating with every landing.

**A landing** is a node of the plan whose accepted head the scheduler reads as landed (contained in every target, marked merged, its merge turn landed: the predicate of `done:integrated`), at the latest time any of its targets became integrated. Landings are ordered by that time and then by node id. Each has:

* **conflict handling seconds**: from the first conflict sweep that measured the node's head against a tip and found a conflict, to the landing. Only sweeps at or after the node's first acceptance count, a conflict seen while the node still ran is not handling time, and a replayed member counts at the sweep's time, whatever the age of the observation it points to (`dag_conflict_sweeps.observed_at` of a `dag_conflict_sweep_members` row of kind `tip`, status observed or replayed, conflicts above 0). Times are compared as instants. A landing with no such sweep has no handling time: it reads absent, and it is not slow.
* **post-merge red or reverted**: a `dev_red` or `reverted` result the parent recorded for the node ([Results the parent records](#results-the-parent-records)).

**The state** after a list of landings is off when some landing in the last `window` of them is slow, or `red_merges` of them are red or reverted, unless the last `clean_run` landings are all clean (neither slow, red nor reverted). With no landing it is on. It is a pure function of the landings in order, the results recorded for them and the settings in force, all stored rows, so two readings of one store state agree. It changes when a landing is added, when a result is recorded (a red recorded late for a landing counts as of the landing it belongs to) or when the settings change. The switches are found by reading the state after each prefix of the landings, so they name the landing at which the state changed; a `clean_run` of 1 lets a slow, clean, slow, clean history alternate.

**What it does.** While the state is off, a candidate whose worst overlap is local is judged by the rule `defer`: the node reads `defer:edit_overlap` (the existing reason: no reason is added), the pass's deciding limit is `edit_overlap`, its `release` object carries `held_by_policy` true, and the detail names the policy, why it is off and the first local overlap. Independent, mechanical and exclusive judgements are unchanged. It is advice to the scheduler's own release judgement: it stops no child, revokes no release already made (a node released while it was on stays released) and changes no merge gate.

**What the reading says.** A plan with a policy prints `release_policy` beside `pass`: its `settings` (with `policy_seq`), `local_optimistic` (`on` or `off`), `reason`, `landings` (how many there are), `window` (the landings it read, oldest first, each with `node_id`, `landed_at`, `conflict_handling_seconds` or null, `slow`, `post_merge_red` and `reverted`), `transitions` (the last eight switches, each the landing at which the state differs from the one before, with `from`, `to` and `because`) and `transitions_omitted`. The input digest covers it. `dag-ready --record` keeps the same object in `dag_pass_release_policy`, so each pass of such a plan carries the state it saw and the switches up to it.

**Limits.** The state reacts to what is recorded: a red nobody records never trips it, and a conflict nobody sweeps has no handling time. A clean landing of any release rule counts as clean (the rule a node was released under is not stored), so a run of landings that never tested optimism can switch it back on. The times are the parent's clock (`observed_at`).

#### Results the parent records

`crw relay dag-landing-result-record --plan P --node N --actor A --kind K --evidence E [--commit SHA]` records what the parent states about the work of an implementation node after the fact, because the store reads no forge for it: `dev_green`, `dev_red` or `reverted` for a pull request that landed, `duplicate` or `discarded` for work that did not. The relay keeps the statement and its evidence (required, at most 1000 bytes: the run, the pull request or the reason) and checks neither. The actor is the registered parent of the plan's project and takes the coordinator epoch, which the row keeps (`coordinator_epoch`). The node is a live implementation node of the plan, or one the store holds an acceptance or an execution of (a plan revision that retired the node, or changed its kind, after its pull request existed leaves the landed work as it was, so what dev did with it can still be stated). The id is a digest of the plan, the node, the kind, the commit and the evidence, so the same statement again is a replay (`replayed`), and a node may carry several kinds (a `dev_red`, then a `reverted`). A `reverted` row counts toward the release policy and the measurements and changes nothing the scheduler calls landed: the observation that the head is contained still stands. Refusals: `malformed_receipt` (a kind that is not one, a commit that is not 7 to 64 lower-case hex digits, evidence missing, too long or with a control character), `scope_role_mismatch`, `unregistered_scope` (a plan, or a node the plan has not got and never had a pull request of), `disposition_conflict` (a node that edits no repository) and `stale_coordinator_epoch`.

### Pass records

`crw relay dag-ready --plan P --record --actor A` keeps the reading as a row of `dag_passes`: the ready node ids in order, the free slots, the ceiling, the held slots, the
deciding limit and the node dispositions, each judged node with its `release` object (the rule, the overlaps by grade and the basis). The reading's `pass` object adds `overlaps` (the overlaps the pass judged, by grade, summed over its candidates) and
`overlap_count` (the local and exclusive ones: mechanical overlaps are released and left out of it), and `order_constraints` (the pairs of live nodes the reading puts in a merge order, [The merge-order constraint](#the-merge-order-constraint)); each node’s `merge_order` object is kept with its disposition. A pass is a fact and never a decision; a duplicate wake records another pass. A plan with a [release policy](#release-policy) also keeps the policy state the pass saw in `dag_pass_release_policy` (one row per pass: the object `release_policy` prints), so the switch of local-optimistic release and its basis are in the pass record. A command that carries the [host memory bound](#host-memory) keeps its verdict in `dag_pass_host_memory` as well (one row per pass: `state`, `reading_limit` and the object `pass.host_memory` prints).
`pass.stagnation` counts the nodes that carry a `stagnation` object, one key per rung, and each node’s object is kept with its disposition like `merge_order` ([A node’s stagnation counter](#a-nodes-stagnation-counter-and-the-repair-ladder)); the pass record keeps it in the same `dispositions_json` column, so no table or column is added.

## Releasing a node

`crw relay dag-release --plan P --node N --actor A --request @file --marker-root DIR` (with the explicit `--state` and `--socket` a managed start needs) gives a ready node to a Codex child through the managed-start
engine. The actor is the project's registered parent: it owns the slot and the child. The request document, `dag-release-request/1`, carries what the plan and the store do not hold: for an
implementation node the base (repository and ref; the commit is read from the target, never given; a correction reads it the same way, see [Corrections](#corrections)), the rule version the node is dispatched under (skills digest, model, effort, prompt template, relay build:
every field required), volatile snapshots (see below), the instructions, the criteria, the criteria source and scope reference, the artifact roots, the allowed recipients, and the parent's and the child's host and
settings. The lists are bounded: at most 256 criteria, 64 artifact roots, 64 allowed recipients and 512 volatile snapshots (one entry per file, each with its own sha256 in the manifest), and the criteria and the artifact roots are not empty. A list over its bound is refused with `malformed_receipt` naming the list, the number of entries it holds and the limit (`volatile has 513 entries; the limit is 512`).

The release is idempotent and never creates a second child. In order:

1. **Replay first.** An already-bound release returns its recorded execution without repeating the continuation checks below; they apply only to an unbound intent. An intent already recorded for the node is continued from the exact request bytes frozen with it (`dag_release_requests`) and never rebuilt: the managed engine fingerprints the whole
   request, while the manifest digest leaves out fields that are still in the prompt, so a clock or a base tip that moved would read as a second release. A replay of an intent whose slot was returned meanwhile reserves it again under the same ceilings, and is refused `capacity_exhausted` when none is free. A replay presented with another spelling of the marker
   root, the socket or the state selector than the intent was frozen under is refused (`disposition_conflict`) before the engine is asked; a stored manifest or request that no longer digests to what was recorded is
   `revision_mismatch`.
2. **Judge, without a transaction.** The reading says the node is ready (or deferred only for capacity: the ceiling is enforced in step 4, where the contest is recorded). A node held by the host memory bound is refused here, before anything is built. For every pinned predecessor the relay reads
   the pull request itself from the forge, by the owner/name it recorded at acceptance, and refuses when its head is no longer the accepted one after recording a `stale_head` observation (E-10); an unreadable or
   incomplete read is the host's failure, nothing is written, and a retry is allowed; a closed or merged pull request is fine, only the head is compared (a merged one is classified by [its own rule](#the-forge-reading-of-a-merged-pull-request)). The request's criteria must digest to the plan's. The manifest is
   built and verified, every artifact and volatile snapshot hashed again.
3. **Assemble the request.** Its id is derived from the plan, the node and the manifest digest only (`dag-` and 40 hex characters; node ids are plan-local and request ids are global to the store): no attempt counter, so a replay is the same request. The prompt carries the manifest inline,
   or the path and hash of its frozen copy (`<first artifact root>/dag-input-manifests/<sha256 of the bytes>.json`, see *The frozen copy* below) when it exceeds 60000 UTF-8 bytes, and tells the child, in English, to
   verify every uri, hash and size before consuming an input and to report `blocked_needs_input` on any mismatch.
4. **Write the intent.** The acceptance whose pull request was read in step 2 must be the one the manifest consumes (a predecessor accepted again meanwhile is a head that was never checked: `disposition_conflict`, repeat the release). One transaction judges the store half again (a plan revision, an acceptance or a registration may have moved), checks the slice, the criteria and the incoming edges against the manifest,
   decides capacity, reserves a slot of subject kind `dag_node` and key `plan/node` (a character neither id may contain) (decision D-15) and writes the manifest, the frozen request and the release together, or nothing. When no slot is free the
   contest is recorded and `capacity_exhausted` answered; a refusal of the reservation itself (another parent, a ceiling at initiative or store scope) leaves its conflict row and no intent, and any other failure of the store rolls the whole transaction back.
5. **Start the child**, outside any transaction, with the frozen bytes. A refused or incomplete start (a creation whose outcome is unknown, settings that differ from what was asked) leaves the intent and the slot; the
   same call again reaches this step again and the engine reconciles with the creation it already made (an unknown creation by observing the App Server: [A creation whose outcome is unknown](#a-creation-whose-outcome-is-unknown); a known interrupted standby: [A standby interrupted by a restart](#a-standby-interrupted-by-a-restart)). A request another caller is advancing waits for that caller to bind its child.
6. **Bind** the child to the node (`dag_node_executions`, kind `initial`). The engine already refuses a creation whose model, effort, sandbox or approval policy differ from the request; the bind refuses a
   relationship that is not this node's issue and parent.

**What a replay does not repeat.** A replay continues a frozen intent; it is not a new release. It repeats the checks that decide whether the intent may continue (a tombstoned managed start, the slot's parent and
project, a returned slot reserved again under the same ceilings, the frozen request's and the stored manifest's digests, the selectors) and sends the same bytes. It does not re-run the reading, the freshness of the
pinned pull requests, the plan's slice, the base tip or the hashing of the input files: the intent's manifest is what it is, a change that invalidates it is the business of invalidation and adoption (a later issue), and
the child verifies every input against the manifest before consuming it. A start that was released after its slot was reserved leaves the slot held and the node `blocked:release_abandoned`, and a replay refuses it (`disposition_conflict`): the engine refuses a released request id for good. Returning the slot frees capacity but does not revive the request, and changing the node's slice does not replace its recorded intent. The way on is [Recovering an abandoned release](#recovering-an-abandoned-release).

The slot is held from step 4 until the parent releases it with the acceptance of a non-PR node or the integration of an implementation node, or an operator does.

### A creation whose outcome is unknown

The App Server can create a thread and fail to answer within the bridge's ack bound (a `PhaseTimeout` on `thread/start`, `thread/name/set` or `turn/start`), or the process that was creating it can stop in the middle. The bridge then keeps a creation receipt that is `outcome_unknown` (`in_progress_or_unknown` for the second case) and never runs it again. A repeat of the same `dag-release` sends the same frozen bytes to the managed engine, which no longer answers `creation_unknown` from that receipt alone: it asks the App Server what the creation left, under the same managed request.

| What the engine finds | What the repeat does |
| --- | --- |
| the reservation row already records the creation's accepted identity: `receipt_status` `accepted`, a `child_task_id` and a `standby_turn_id` that are valid segments, and that `child_task_id` equal to the thread this receipt names | adopts that recorded child and standby turn before it reads the host at all (no `thread/read`, no `thread/turns/list`): a completed identity continues exactly as the recognition row below does (`adopted`, that turn recorded as the standby turn, the detail `the reservation recorded standby turn <turn> for thread <thread>`), no standby send and no `turn/start`. A row whose child differs from the receipt's thread, or whose standby turn is blank, falls through to the rows below unchanged; a receipt that names no thread at all does too, because a threadless receipt is one no accepted row can have recorded for it |
| a thread with no turn: the one the receipt names, or, when it names none, the only loaded thread that fits (the request's working directory, model and effort, created after the creation began, no first message, a name that is empty, the request's title, or the name the engine sets - that title with the issue key prefix when the prefixed value fits the bridge's create title limit) | continues the same request on it: the standby turn under a standby operation of its own, the title after the standby is accepted, then the business turn; the child is that thread |
| a thread that has a turn, or a receipt whose `turn/start` may have been sent (it is among the attempted effects, or the receipt kept the title and no effects were saved) | stops with `thread_has_turn` or `standby_turn_unknown`: an unanswered `turn/start` is not sent again ([I-488](invariants.md), I-473) |
| a thread the receipt itself names, whose `thread/turns/list` (limit 2, itemsView summary) holds exactly one turn with no next page and whose whole first user message is byte for byte the bootstrap the creation sends, when the receipt recorded `turn/start` among its attempted effects | recognises that turn as the standby turn this creation sent: a completed turn continues exactly as a creation receipt that carried its `turnId` does (`adopted`, that turn recorded as the standby turn, no standby send and no `turn/start`); an `inProgress` turn stops with `pending` and `repeatAfter`; two or more turns, other text, `failed` or `interrupted`, input it cannot read and a listing error keep the `thread_has_turn` or `standby_turn_unknown` answer above. A thread the scan found, and a receipt without `turn/start`, are unchanged. The message has to be the bootstrap whole: exactly one text part carrying it, or the item's own text with no content beside it or that same one text part. A second part, a part that is not text, and an item text that differs from the content are not this creation's standby and keep the stop above. The part's other keys are the host's and are not read, so the recorded message the first recognition shipped with (one text part and the host's empty `text_elements`) stays recognised |
| no thread, within 2 minutes of the receipt's last update | stops with `pending` and `repeatAfter`: a thread may still appear |
| no thread, after those 2 minutes and with the listing read to its end | creates again under the same request, with a bridge operation id derived from the request and the attempt number (at most three creations); the newest attempt that has a receipt is the one every later repeat continues |
| a named thread the host no longer knows or cannot read from its rollout, or a retained standby recovery refused at read/resume before any turn or verified resume with `thread not found`, `missing source rollout` or `no rollout found` (the texts `observe` reads as unreadable) | abandons that orphan and creates the next attempt; connection establishment failures and settings findings do not qualify |
| the second case above, where the refusal is the retained standby recovery's: the orphan is read again and, still turnless, is archived before the next attempt is created, with one `managed_orphan_archive` journal row marking the attempt (`archive`: `attempting`) written before `thread/archive` on a context the caller's cancellation cannot take away and one result row (`ok`, or `failed` with the error) after the reply, so one attempt archives at most once and an archive that was sent and never answered still leaves the mark that stops a repeat from sending it again | an orphan the host does not hold is not archived (`skipped`, one row), one that has become active or has a turn is left alone (`skipped`, one row), and an archive that fails or is withheld is recorded without stopping the recreation; a re-read that ends without a conclusion on an error other than cancellation creates nothing, writes no row, and stops the call with the existing `unobservable` state, so a repeat decides again; the read-only `observe` path archives nothing |
| several threads that fit, a listing that cannot be read, more than 64 candidate threads to inspect, another host error, no creation time in the receipt | stops with `ambiguous` or `unobservable` and the detail; nothing is created or sent |

Every stop answers `creation_unknown` and carries `creationReconciliation` (`state`, `detail`, `attempt`, `attemptRequestId`, `thread`, `repeatAfter`) in the `managed` answer; the node stays `blocked:creation_unknown` until a repeat continues or creates again. A repeat that continues or creates again answers the same object with the state `adopted` or `recreated`, and the answer of a start that reconciled nothing has no such key.

What this does not establish. A thread that was created, never got a message and was unloaded again is in no listing, so "no thread" is a statement about loaded threads, and the grace period and the loaded listing are the whole of the evidence; a thread of an earlier attempt that appears after a later one was created is an orphan with no turn and no writer, never registered and never sent to. Several fitting threads, or a host that cannot be read, stop every repeat until the host answers or the stray thread is archived; the engine never picks one. A refused recovery is never sent again. A refusal to resume an unloaded thread licenses abandonment only before any turn or verified resume; a transient resume error can therefore leave one usable orphan. It has no turn and no writer, is never registered or sent to again, and its ID is excluded from later scans, from both earlier creation and recovery receipts. Busy threads, settings findings, connection establishment failures and uncertain sends remain stopped.

The scan prunes UUIDv7 IDs outside the receipt's creation window before reading them: from `startedAt` through the later of `startedAt` and `updatedAt` plus the grace period, with one minute of ID clock slack on either side. Non-UUIDv7 IDs retain the bounded read-and-match path. The listing still has to end; filtering is not permission to declare an unfinished listing empty.

A profile-free request already armed before MCP profiles were declared continues under the child role's declared default during this managed start. Its frozen bytes and recorded settings are unchanged. NEW or merely reserved requests still require an explicit profile; an armed request also stays refused if the role declares no default. The default is applied and verified on this start's creation and marker-bearing resumes, while unrelated later sends keep the legacy record's absence of a profile.

### A standby interrupted by a restart

An accepted creation or standby-recovery operation can name a standby turn that a restart ended
`interrupted` (or the host ended `failed`). Repeating the same `dag-release` continues its frozen
managed request: once the host is ready for direct input (idle or not loaded, unarchived, with no
paused or limited goal), the engine proceeds to the business turn without sending another standby.
The standby is an inert bootstrap; its original turn remains the registration and generation anchor
([I-489](invariants.md)). The retained operations prevent repeated releases from duplicating either
the standby or business turn. The existing creation reconciliation and its per-attempt IDs are unchanged.
The daemon excludes the original standby identified by that attached request, permanently, including
after a later generation opens. It rechecks the same association under the settlement writer lock
before synthesis, so a tick that selected the turn before registration cannot report false failed
work. Skipping creates neither an observation nor a settlement and changes no terminal status.
Ordinary/revision anchors and genuine business failures still report. Previously delivered failure
observations are not retracted by this source change.

A missing, unknown or still-running standby remains `standby_incomplete`. A known host hold
returns its reason without beginning the business operation, and an unreadable host returns an error;
repeating after the hold clears can continue. Serving policy, settings, scope and the final business
guard still apply. Host observation and turn start are not atomic: a thread that becomes busy in
between can still leave a failed business receipt. Failed or unknown attempted standby-recovery and
business sends are retained and not resent; this recovery does not resolve those send outcomes.
An accepted business receipt is admission evidence even if that business turn later fails or is
interrupted: managed start does not wait for business completion.

### Recovering an abandoned release

A managed start that was released before it created a child (`managed-release`, possible only before the request is armed) is a tombstone: the engine refuses its request id for good, and a release's request id is derived from the plan, the node and the manifest digest only, so the same manifest can never start under it again. The node reads `blocked:release_abandoned` (its detail names the request id), its slot stays held, and a replay of `dag-release` refuses. Two steps end that.

1. `crw relay dag-release-close --plan P --node N --actor A --manifest D --request-id Q --reason R` (every option is required). The actor is a registered parent of the plan's project and the node is live. Q must be the node's open request, released and with nothing bound to the node, under manifest D. One transaction records the closure (a `closed` row of `dag_release_recoveries` with the slot and the frozen copy it dealt with) and returns the slot with the reason `dag_release_closed`: a slot an operator already returned is skipped, and one held by another parent or project is `disposition_conflict`. A running release, one whose start is still in flight, another manifest and an unknown request are `disposition_conflict`, an actor that is not the parent is `scope_role_mismatch` and a missing reason or request is `malformed_receipt`. The command starts nothing and creates no child. The same request again answers the recorded closure with `replayed: true` (and `successor_request_id` when the node was released again since), so a retry of a close whose answer was lost never closes a later abandoned intent of the same manifest: that one needs its own request id. After the commit, in a transaction of its own, the copy the closed intent's frozen request names is removed unless something live names it (see [The frozen copy](#the-frozen-copy)); `frozen_copy.removed` says whether the file is gone, and a repeat of the close tries again if it is not.
2. The ordinary `dag-release`. A closed intent no longer owns the node, so the reading says it is ready again, and the release judges it from scratch (steps 2 to 4 above). A manifest that changed since (a moved base tip, a predecessor accepted again) is an ordinary new release under its own digest and request id. The same manifest cannot take its old request id, so it takes `RecoveryRequestID`: `dag-` and 40 hex characters of the hash of the canonical list [`recover`, plan, node, digest, the closed request]. It is recorded as a `rereleased` row of `dag_release_recoveries` that holds the successor id and the exact request bytes and selectors, as `dag_release_requests` does for the first release (the shipped release rows are unique on the digest and cannot take a second request). A release after a close of an older manifest of the node is the successor of that manifest's last closed request.

The node's open intent is the `dag_releases` row or `rereleased` row whose request has no `closed` row; there is at most one, and the intent transaction checks that again before it writes, so two calls that release a closed node at once create one child (the loser replays the winner's intent). A replay of a successor sends the successor's own frozen bytes and checks them and their selectors as a first release's replay does. A live child still stops a release: the judgement refuses `duplicate_assignment` while a relationship or a managed start owns the issue. A foreign child that takes the issue after the intent was recorded makes the engine refuse the start without writing a managed row; that is an intent waiting for the issue (it keeps its slot, decision D-15) and not an abandoned one, and the same `dag-release` continues it once the issue is free. A store whose zone predates `dag_release_recoveries` reads as before (a read-only open creates nothing).

A start that was armed is not closed by `dag-release-close`, whatever the observation says: its creation may own a thread, and closing it would return the slot and let `RecoveryRequestID` create a second child beside the first. The way on for an armed start whose creation is unknown is the repeat described in [A creation whose outcome is unknown](#a-creation-whose-outcome-is-unknown), and the close refuses it (`disposition_conflict`) as before.

Not covered: the intent of a node that a plan revision retired (`dag-release-close` needs a live node; invalidation and adoption own it), and any judgement that a manifest is stale (it is made when the node is released again, from scratch).

### Input manifest

The manifest (`dag-input-manifest/1`, contract 4.2) is content-addressed and records, for every incoming edge, the value that satisfied it, read from the very rows the edge's predicate used (the observation that proved an integration, the decision that settled a decision edge): the acceptance and its revision, the pinned head, the artifacts with
uri, sha256, size and the artifact root they lie under, the landed commit, or the recorded decision; the node's slice and criteria digests; the base; the rule version; the volatile snapshots. A manifest is released
only when it is whole: a missing, mismatched or altered input, an unreadable store, or an empty rule-version field is never an empty success. The violated paths of contract 4.4 map onto the relay's existing refusal
reasons:

| Path | Reason in the reading | Refusal |
| --- | --- | --- |
| B-01, B-16 | `blocked:manifest_incomplete` | `malformed_receipt` |
| B-02, B-07 | `blocked:manifest_tampered`, `blocked:acceptance_tampered` | `revision_mismatch` |
| B-03, B-04, B-17 | `blocked:input_missing`, `blocked:input_hash_mismatch` | `manifest_unverified` |
| B-05 | `blocked:input_out_of_scope` | `scope_escape` |
| B-09 | `blocked:stale_head` | `merge_candidate_moved` |
| B-10 | `blocked:stale_criteria` | `criteria_set_changed` |
| B-13 | `blocked:evidence_mismatch` | `revision_mismatch` |
| B-06, B-08, B-11, B-12, B-14, B-15 and every other reason | as named | `disposition_conflict` |

A node that is owned already is `duplicate_assignment`, an unmeasured ceiling `capacity_unmeasured`, overlapping regions `region_overlap`. The closed reason travels in the refusal's detail.

A volatile snapshot is a file the node reads that can change (a Linear document, an issue) captured before dispatch: its source must be an absolute path under one of the child's artifact roots (B-05), exist (B-03) and hash to
the digest the request names (B-04). Before a release or prepared correction stores its manifest, the relay keeps the verified bytes in its state directory and replaces `snapshot_uri` with the retained path. The manifest digest covers that path and the input hash. The child receives and verifies the retained bytes, even if the source is overwritten later. Release verification, correction preparation and store-only revalidation use that same path; only an exact per-plan digest pathname gets this additional input-read scope. The delivery instruction authorizes those paths as read-only inputs and gives them precedence over source paths mentioned in earlier instructions. Output artifact roots and child settings do not change.

A request that still names an altered source with the old hash remains B-04 (`manifest_unverified`). When the retained copy can be read and rehashed successfully, the detail names it and says to copy its bytes back to the source and recheck the hash, or explicitly supply the retained path as `snapshot_uri`. A missing, altered or linked retained copy is refused without falling back to the source. Sources are never chmodded or restored automatically; updating an unreleased node's source and supplied hash remains free. Existing manifests and pending correction instructions that name original sources remain compatible, but have no recoverable copy unless one was retained separately; this change cannot reconstruct bytes already lost.

### Retained input bytes and cleanup

Copies live at `<relay-state>/dag-input-snapshots/<sha256 of the UTF-8 plan id>/<input sha256>`, beside the selected relay database. The plan directory can also be found as the parent of a retained `snapshot_uri` in its manifest. Inputs with identical bytes share one file within that plan; payload storage is the sum of unique input sizes, plus filesystem overhead. The relay streams a stable authorized source into a temporary file, hashes it, syncs it, sets mode 0400 and publishes it by an exclusive rename (`renameat2` with `RENAME_NOREPLACE`). Publication leaves no temporary hard-link alias whose removal could change the retained inode during a concurrent read. Directory traversal, creation and publication use no-follow, descriptor-relative Linux operations, so planted directory links cannot redirect writes. An existing copy is rehashed before reuse. Linux and filesystem support for that exclusive rename is required; other platforms refuse this operation, as they do authorized artifact reads.

Retention is deliberately independent of oversized manifest JSON cleanup. A refused release or preparation can leave a completed, unreferenced input copy; abrupt process death can leave a `.pending-*` file. Ordinary failures remove their own temporary file. No running scheduler sweeps these copies, because another release, retry or correction may still consume them.

The cleanup path is operator-controlled removal of one plan directory after retiring the plan, ending all its child relationships and ruling out any remaining retry, prepared correction or stored-manifest consumer. Archive the plan's manifests and retained inputs first if later reproduction is needed, then remove only that plan's directory, including its abandoned temporary files. Do not remove a directory merely because one node was integrated, withdrawn or its release closed: another node of the plan may share its bytes. This release does not clean existing state directories or add a cleanup command, table or column.

"Under" a root, here and for the artifacts a predecessor handed over, is the store's own rule for authorizing a read (`store.IsWithin`): containment by path component, both sides normalized, a root of `/` holding every absolute path. A path that leaves a root by `..` is out of scope (B-05) at that check, not only when the file is hashed. The scope a manifest records for an artifact is the root as it was given, the longest one that holds the path; a root of `/` is the answer only when no longer root holds the path, and the scope recorded for a normalized path that an earlier build already answered is unchanged.

## Accepting a result

`crw relay dag-accept --plan P --node N --actor A --rule-version @file [--repository OWNER/NAME --pull-request N [--checkout DIR]] [--event E] [--supersedes ID]` records that the parent accepted a node's result (contract 4.3).
The child's end of task, its report, the transport acknowledgement and the parent's acceptance are four records, and only the last one opens an edge. The acceptance is written when P-AV-1 holds **now**, read from the rows in one transaction:

1. the result is the one head of its generation: a final, unsuppressed `ready_for_review` event (the `--event` the parent names must be that head; an older event is `superseded_revision`, an event of another generation `stale_generation`);
2. its acknowledgement was accepted, verified by the host, and rests on evidence above the `unverified` tier;
3. the parent's ruling on it is `verified`, still current, and made under managed verification;
4. the criteria registered for the relationship are the ones the ruling was made against, and the plan's criteria for the node are the same set;
5. the relationship is active, and the caller is its parent.

For an implementation node the head is never given: the relay reads the named pull request from the forge itself and accepts only an open, non-draft pull request whose snapshot is consistent. The accepted head, the pull request and the forge identity are recorded
(P-AV-2); a statement in a child's report never becomes the head. A plan revision that changes the node while the pull request is being read refuses the acceptance, because the verification no longer describes the plan.

**The head the ruling fixed (CRW-731).** A parent that refreshes a pull request's branch after the verdict (`update-branch`, or a merge of the base it makes itself) leaves the forge showing a head N that is not the head P the verdict was about. The verdict records P with the ruling (`verdict --verified-head`, `dag_verified_heads`, one row per event), and `dag-accept` reads P from that row of the event it accepts: the call carries no head, so a head the parent pushed by hand cannot be named as the ruled one. Three cases follow. An event with no row (a ruling given before the flag, or without it) is accepted as it always was, with no proof and no proof row, and `verified_head_sha`, `refresh_id` and `manual_paths` in the answer are null; recording the head becomes required once every parent's lane passes it. P equal to N is accepted with no checkout and no proof row, and the answer names `verified_head_sha`. Any other N is proved before anything is written: `--checkout DIR` (an absolute path to a clone that holds P, N and the tip of the pull request's base branch, fetched beforehand; without it `malformed_receipt`, and a missing commit is `merge_target_unreadable` naming the fetch) is read by the same prover `dag-base-refresh` uses (`proveBaseRefresh`, then `applyMechanical` with the plan's declared regions, the contributors' heads and the built-in plugin-manifest version rule). N is accepted only when every commit from P to N is a merge of the base that git reproduces from its parents, or a conflict a declared region or the built-in rule settles. Anything else is `disposition_conflict` with the prover's code (`tree_differs` for a hand resolution no rule proved: the call takes no `--resolved`, so the head goes back to the child), no row is written, and the acceptance a `--supersedes` would replace stays active. The proof is made before the transaction; a call whose caller is not the active relationship's parent, or whose generation is neither an execution nor a carried one, is refused before any declared regeneration command runs; the transaction reads again what it rested on (the ruling's row, the head and generation of the output, the plan's regions, the contributors' heads, the active acceptance, and the pull request's head, base and state and the tip of its base branch from the forge and the checkout's readers; the forge snapshot read again is classified as the first one was, so a snapshot that is stale or unknown is refused as `merge_candidate_moved` or as the host's failure whatever its head says) and refuses with `disposition_conflict` (call again) when any of it moved, then writes the acceptance, the forge row and the proof row (`dag_acceptance_refreshes`: the ruled head, the accepted head, the base tip and the chain) together. A replay or a re-validation, and an acceptance recorded before this rule, never read the checkout. The guarantee is: **the accepted head is the head the parent recorded at the verdict plus merges of the base, and nothing else**; it says nothing about a ruling that recorded no head, and nothing about the base's content, which the merge lane's own checks cover. The answer carries `verified_head_sha`, `refresh_id` and `manual_paths` (always empty when a proof was made, because a path the rules did not prove refuses the acceptance).

**The target of an implementation node's acceptance** is the forge repository of its pull request, and the acceptance records it (`dag_acceptances.repository`, beside the forge identity in `dag_acceptance_forge`). The single repository the node's outgoing `integrated` and code-pinned `artifact_verified` edges name has to be exactly the `owner/name` the call gives (`--repository`, compared as written), and a node with no such edge (a terminal node) takes the pull request's repository. A local checkout is where Git objects are read (`dag-base-refresh --checkout`), never a repository an acceptance is judged against, so an edge whose target is an absolute path is refused `disposition_conflict` (`the outgoing edges of N name local checkout PATH as their target; an implementation node is accepted on its pull request's forge repository R. Set target_repository to R and use --checkout for dag-base-refresh when local Git objects are needed`). The plan does not check how a target is spelled, so every other target that is not the pull request's repository is refused `disposition_conflict` as well (`the outgoing edges of N land on T and the pull request is in R`): a relative path, a bare name, a malformed repository and the same repository in another case included. Edges that name more than one repository are `malformed_receipt` and are asked first. The check is made in the acceptance's own transaction, so a replacement that is refused leaves the acceptance it would have superseded active and writes no row. Only a new acceptance asks. A replay or a re-validation of an acceptance recorded before this rule, which may carry a local checkout as its target, finds that acceptance and keeps the target it stored; replacing it is a new acceptance, accepted once the plan's edges land on the forge (a plan revision that retires the edge and adds one that does).

The same output accepted again is a replay when it names the pull request recorded with the acceptance and the forge still shows the accepted head there (a head that moved is `merge_candidate_moved`, another pull request `disposition_conflict`; a pull request merged at the accepted head is still the same output, [classified as a merged one is](#the-forge-reading-of-a-merged-pull-request)). The same output ruled again under re-registered criteria is a **revalidation** of the same acceptance (`dag_acceptance_revalidations`, contract E-11): no second acceptance, generation or child. It is recorded only when the criteria are all that is stale ([Handling a stale node](#handling-a-stale-node)). A new output replaces a node's active
acceptance only with `--supersedes <that acceptance>`; without it the call is `disposition_conflict`. The acceptance digest names the plan, the node, the manifest, the execution (relationship and generation), the event and revision, the criteria, the verdict and, for an implementation node, the head, the repository and the pull request number, so a changed row reads as `blocked:acceptance_tampered`. The evidence digest, the rule version, the acknowledgement tier and the times are recorded and left out of the identity, so a re-run of a check never changes what was accepted.
The rule version (skills digest, model, effort) is recorded with the acceptance and left out of its identity. A non-PR node's slot is returned by its acceptance; an implementation node's slot is held until it is integrated. A parent that refreshes a branch whose base moved (crw-run's merge readiness) therefore does it before this acceptance: the head read here is the head that has to land, a pull request that moves afterwards reads `stale_head`, and the same output cannot be accepted again at the new head, so a base that moves after the acceptance goes back to the child for a new generation, which the parent records with [`dag-base-refresh`](#a-base-refresh-of-an-accepted-node) when the generation only merged the base; the pull request is then judged, and merged through the lane, at the head that record names. A parent that opened a generation by hand for that refresh before the acceptance and then refreshed the branch itself withdraws the generation that was never sent first ([A generation opened by hand and never sent](#a-generation-opened-by-hand-and-never-sent)).

## The forge reading of a merged pull request

Every command that takes a pull request from the forge classifies the reading with one function, `ClassifyPullRequest` (`internal/relay/dagsched/forge.go`). They are the freshness check of a release, `dag-accept`, `dag-merge-judge` and `dag-base-refresh` (which first turns away a pull request that is neither open nor merged, a closed one, with `disposition_conflict`). The rule is fail closed. A verdict of `unknown` (evidence unreadable, truncated or unstable) is the host's failure (exit 3): nothing is written and a retry is allowed. A verdict of `stale` (the candidate or its gates moved while it was read) is a refusal, `merge_candidate_moved` or `merge_evidence_malformed`. `ready` and `not_ready` pass, because a failing check or an open thread is a judgement and not a read failure.

A merged pull request is the one reading whose verdict is `unknown` by construction. Nothing is left to hand over, so its snapshot says `candidate_not_open`, and the forge reports no merge state for it, so it says `candidate_unknown`. Those two problems are set aside and the reading is classified by what is left, for a merged state and for an `unknown` verdict that carried at least one of them. A merged reading whose only problems are those two is therefore readable. One that also carries a read failure (a truncated listing, an unstable review set, an unreadable code) is still the host's failure, one whose candidate moved while it was read is still `merge_candidate_moved`, and one that also carries a judgement problem (an unresolved thread, a stale check) is not a read failure, as for an open pull request. An `unknown` verdict that names neither of the two (a merged reading with no problem at all, which the collector never gives) stays the host's failure, and the same two problems on a pull request that is open, or closed without having merged, are not set aside: the classification gives the host's failure for them.

Passing the classification says only that the reading is complete. What a merged pull request means is each command's own decision, from the state of the reading:

| Command | A merged pull request |
| --- | --- |
| release (the pinned predecessors) | allowed: only the head is compared with the head the acceptance stands on, and another head is `stale_head` and `merge_candidate_moved` |
| `dag-accept` | the same output accepted again is a replay (or a re-validation) when the head is the one the acceptance stands on; a new output is `disposition_conflict`, because only an open, non-draft pull request is accepted |
| `dag-merge-judge` | `disposition_conflict`: only an open, non-draft pull request goes to the merge lane |
| `dag-base-refresh` | read like an open pull request: the proof starts from its head |

A pull request closed without merging is not covered. Its reading has not been measured, so it is classified by its verdict as above and an `unknown` one is the host's failure.

## Integration

`crw relay dag-integration-observe --plan P --node N --actor A [--target REPOSITORY@REF ...]` records whether the accepted head is contained in the branches it has to land on, as a fact the relay reads: `git merge-base --is-ancestor` against a local checkout, the
compare API (`behind_by` 0) for a forge repository; the compare call is bounded by the same 30 seconds as the merge lane's branch-tip read (`mergeturn.ForgeCallTimeout`), plus at most five more seconds for a process that outlived the kill to let go of the output pipe, and a forge that does not answer in that time is a host failure (exit 3) that records nothing. The parent's order is accept, merge, `assignment-mark merged`, observe. The required targets are those of the node's outgoing `integrated` and code-pinned edges, every target the acceptance already has an
observation for (a negative one included, so observing a subset never completes a node) and the ones observed now; a terminal node names its target with `--target`. A node is **integrated** when every required target contains the head and the `merged` mark exists on
the same revision of the same generation (the head, generation and revision the acceptance stands on: after a [base refresh](#a-base-refresh-of-an-accepted-node) those the newest valid record names, which are the acceptance's own generation and revision when the parent refreshed the branch in its merge turn and a later generation's when the child did). The observation alone, or the mark alone, integrates nothing. A squashed or rebased landing leaves a head that is not an ancestor: when a merge turn recorded that it landed this head on the branch, the reading says `blocked:integration_unprovable` rather than guessing; without such a turn the node simply keeps waiting.
Observations are append-only: an identical reading (same head, same tip, same answer) is a replay, and any change is the next observation. A paused or cancelled relationship records none (contract 3.2); observations already written stay. The targets are read from the plan as it stands when the observation is written, and the node's newest slot tenure is returned, by name, when it integrates.

## Commit acceptance and local integration (CRW-965)

An implementation node needs no pull request. It is accepted by its commit:

crw relay dag-accept --plan P --node N --actor A --commit HEAD --base BASE --checkout DIR --verification RECORD --rule-version ...

The relay reads the receipt head of the node's current generation (dag_verified_heads) and refuses unless the commit is that head (head_not_receipt_head), descends from the base in the checkout at DIR (merge_base_mismatch), and the verification record is reusable for this commit (below). The same output again is a replay, and the --pull-request path is unchanged. The proof stands on the event, revision and generation read before the write transaction; the transaction reads the current head again and refuses a head that moved (stale_generation), so the head it stores is the one proved.

A verification record is the one CRW-964's writer (crw-dev ci local) leaves: camelCase members (schema, runner, repository, baseCommit, headCommit, treeHash, ciDigest, tools, pins, goFlags, goEnv, pinMismatch, dependencies, os, arch, result, jobs, digest). The reader pins those names and recomputes the digest from the record's own bytes (sha256 of the sorted-key JSON without the digest member, no HTML escaping). A record is reusable only when every reuse key holds. A record that does not pass (result other than pass, a pinMismatch, a member absent (pins included), a pins member that is null, a pin the verified commit declares that the record lacks or holds at another version, a digest that does not match, a ci.yml, dependency, base, os or arch that differs from the commit's and the host's) is disposition_conflict with its own detail. A record of another tree (treeHash) is revision_mismatch. A file that is not a verification-record/1 is malformed_receipt. headCommit is not a reuse key: the same tree under another commit is the same verification.

crw relay dag-integrate --plan P --actor A --checkout DIR --integration-ref BRANCH --base BASE --verify COMMAND [--node N ...] [--expect-epoch E]

is the one integration command. It is parent-only: --actor must be the parent of every candidate's relationship, and the coordinator epoch goes through the fence dag-accept uses (a stale epoch is refused as stale_coordinator_epoch). It takes the plan's ready candidates (or the named ones). A candidate is ready when its active acceptance is current: not stale under the scheduler's own judgment, its relationship active and on the generation the acceptance stands on, and its node live and not held by the plan. Before git runs, each candidate is frozen (an intent row in dag_integration_stages), so the marks name the acceptance and event the merge stood on.

A candidate belongs to the batch when its acceptance names the checkout: a commit-accepted node carries the checkout path, and a node accepted on its pull request carries the forge slug of that pull request, which is the checkout's when the checkout's `origin` remote names that slug (`owner/name`) on the forge host the relay talks to (`GH_HOST`, else github.com). Pull-request and commit candidates of one plan are one batch; each merges at the head its acceptance stands on now (the accepted head, or the head a recorded base refresh carried it to), and a pull-request node keeps its forge slug and the edge's base ref as its observation target. A candidate whose slug the origin does not name, or any slug when the checkout has no origin, is another repository's and is judged there (`disposition_conflict` when named with `--node`).

The batch merges the candidates in node-id order with merge commits in a temporary detached worktree of the integration branch (or of the base when the branch does not exist yet). It runs the --verify command in that worktree, split into arguments and never through a shell, with CRW_VERIFY_RECORD (a fresh path that did not exist before the run), CRW_VERIFY_BASE and CRW_VERIFY_HEAD (the merged commit) in its environment. The run passes only when the command exits 0, the record exists and the record passes the check above for the merged tree. A non-zero exit is a failure whatever the record says. The temporary worktree is removed on every path.

When the merged tree fails, the batch bisects the ordered candidates to the first failing prefix. That candidate and every candidate that depends on it through the plan's edges are left out with the reason verification_failed (the candidate itself) or depends_on_<node>. A candidate that did not merge cleanly is not judged failing: it is deferred, and once the surviving set is verified each deferred candidate is retried once, in order, on top of it. A retry that merges cleanly joins and the new merged tree is verified again; one that still conflicts stays out with the reason conflict_with_<node>, and one that fails verification with verification_failed. A candidate that conflicted only with a removed candidate therefore integrates.

The integration branch moves only to a tree whose record passed, by a compare-and-swap on the head the batch read: refs/heads/BRANCH is updated from that head, or created from the zero object id when the branch does not exist (create-only). A branch that moved under the batch is refused (stale_mark_context), and nothing is overwritten. After the move the batch row is written and each merged candidate gets the parent's merged mark, written from its frozen acceptance and event. A mark that cannot be written (a paused node, a changed acceptance) is recorded as mark_pending with the refusal, and the batch stays visible as ref_moved. The next dag-integrate run completes pending marks from the frozen rows, for a batch whose merge commit is an ancestor of the integration branch; a mark already present for that revision counts as done.

crw relay dag-integrate-push --checkout DIR --integration-ref BRANCH --remote origin --remote-ref dev

moves the remote branch to the integration commit by a fast-forward only. An equal remote is up_to_date. A remote that holds a commit the integration branch contains is advanced. A remote that holds a commit the integration branch does not contain is refused with merge_base_mismatch, and nothing is pushed; there is no force. A remote that cannot be reached (a GitHub outage) defers the push with outcome deferred and exit 0. The batch and the merged marks already stand, so run the same command again once the remote answers.

Completion on this path is counted by observation, not by a merged pull request: dag-integration-observe --plan P --node N --actor A --target DIR@BRANCH reads the integration branch as the target, and the node is integrated when the commit is contained there and the merged mark exists. dag-progress then counts it as integrated, with no pull request link. The new path uses no merge turn, no merge train and no merge evidence.

Verification command example. The command is split into arguments and run without a shell, so it cannot expand the variables itself. Give it a script that reads them from its environment, for example a file verify-merged.sh whose first line is #!/bin/sh and whose second line is: exec go run -tags dev ./cmd/crw-dev ci local --commit "$CRW_VERIFY_HEAD" --base "$CRW_VERIFY_BASE" --record "$CRW_VERIFY_RECORD" --runner local. Then pass --verify /absolute/path/to/verify-merged.sh. The batch runs the script in the merged worktree, so crw-dev ci local verifies the merged tree, and the record it writes is the one the batch judges. The tests use a stub script that exits 1 when a bad.txt marker is present in the worktree and writes its record through the same judge; they never run the real crw-dev.

The relay judges a verification record by its reuse keys: the tree, the base, the ci.yml and dependency digests, the platform, the result, the pin mismatch list and the digest, and the tool pins (below). The pins of a record are required (CRW-1026). The required set is what the verified commit itself declares: the go.mod `toolchain` line (`go`), the `honnef.co/go/tools` require (`staticcheck`), the `scan_version` of `scripts/ci/secrets.sh` (`gitleaks`), and `node`, the distinct `node-version` values of the `actions/setup-node` steps of that commit's ci.yml, sorted and joined by a comma, only when that ci.yml has such a step. The judge never reads the PATH of the host it runs on. For each required tool the record must pin it, carry it in tools, and both must equal the version the commit declares; a pin or a tool that is missing, that differs from the commit's declaration, or a tool that differs from its own pin, is `disposition_conflict` and names the tool. A pins member that is missing or null is refused the same way. A record of an older tree whose ci.yml has no setup-node stays valid without a node pin, and a tree that declares nothing requires nothing. Keys that carry no declaration (not built from a commit) refuse every record, except for a caller that states it cannot read the commit (`runtime-upgrade` holds a tree id and no checkout): its records are judged for the pins member and for each pin against its tool, not against a declaration. The Go flags and the Go environment stay the writer's to judge: the relay cannot know the environment of the host that wrote the record, so it only requires their members to be present, empty values included. CRW-964's writer refuses to write a reusable record on a pin mismatch, and its reuse mode compares the tools, the Go flags and the Go environment with the current environment before it answers. A batch reuses only its own covering PASS: a stored verification of a head stands for a candidate only while the tree, the ci.yml and dependency digests, the platform and the candidate's criteria set digest still match the ones it was judged under. Otherwise the batch runs the verify command again on that head, and the command may reuse a record through crw-dev ci local.

A criteria change of a node is the scheduler's revalidation: the node's acceptance is stale until it is revalidated, and a candidate whose criteria changed is not ready until then. A node that already integrated is not a candidate and is never verified again by a batch; its changed criteria make it stale (stale:criteria_changed) until its parent re-rules it, which dag-progress shows. The verification criteria are the keys of the record judge: the ci.yml digest, the dependency digests, the pins and the platform. A branch head that a batch marks from a verified head is covered only while the keys that verification was judged under still hold for the head's tree. When they no longer hold, the batch verifies the head again without a merge, and only that PASS covers the candidates, so a batch whose candidates are all already contained runs the verifier exactly when those keys changed. Every frozen candidate row of a batch names the criteria set the batch verified the candidate under. An explicit --node that names a node already integrated is refused disposition_conflict, with the reason that the node is already integrated.

An accepted implementation node satisfies a code-pinned artifact_verified edge through either of its two acceptance shapes: a pull-request acceptance (its forge row and pull request number) or a commit acceptance (its verification record row). A commit-accepted node completes on the local integration branch its batches moved. Its outgoing integrated and code-pinned edges must name the same checkout, compared as written, but the edge's base ref is not part of what integrated means for it: the completion targets are the checkout and the integration ref each batch recorded, and dag-integrate names that ref in its targets output. A pull-request node keeps the edge's base ref. A node with neither acceptance row stays acceptance_incomplete.

A replay of a commit acceptance is the same output: a record for the same head and tree replays the acceptance or revalidates it, whatever its bytes (job timings, for example). The relay judges the supplied record with the same judge and compares the verified head and tree with the stored ones; the first record stays the evidence. A record naming another head or tree is a different output and is refused.

A batch moves the branch in one fenced transaction: the coordinator epoch is checked, the compare-and-swap runs and the moved record is written before the commit. The verification runs outside that transaction, and the planned intent (the verified head, its tree and its keys) is committed before the swap. If the process dies after the swap, the next run reconciles a planned intent whose head the branch holds and that has no moved record: it records the move once and makes no second move. A planned intent whose head the branch does not hold is reported as abandoned. A push that GitHub answers with an HTTP 500, 502, 503 or 504 status is an outage: the push is deferred, and the local integration stands.

**The judgement boundary of a record (D1, with CRW-1026).** The judge compares the record with the reuse keys above, each tool value with the pin the record carries for that tool, and the pins and tool values with what the verified commit declares. It does not compare goFlags, goEnv or the tool values with the relay host, because the relay cannot read the environment the writer ran in: those are the writer's judgement (CRW-964 refuses to write a reusable record on a pin mismatch, and its `--reuse` compares them with the current environment). A batch reuses only its own covering PASS: a stored verification of a head covers a candidate only while the tree, the ci.yml and dependency digests, the platform and the candidate's criteria set digest still match the ones it was judged under. A candidate whose criteria set changed after a revalidation is verified again on its head, with no merge.

**What a batch verifies (criterion c2).** A change of a node's criteria is revalidation, which the scheduler's staleness already handles: a node that integrated is not merged or verified again, and a candidate whose criteria changed is not ready until it is revalidated, after which the next batch verifies it afresh. The integration branch is not re-verified for a criteria change, because its tree did not change. The verification criteria are the ci.yml digest, the dependency digests and the platform. A head a batch recorded as verified stands only while those keys hold for its tree (the stored row carries the tree, the digests, `os` and `arch`); when a key no longer holds, the batch verifies that head again on a worktree of it, with no merge, and only that PASS covers the candidates it contains.

**Currency at the swap (D3).** Each merged candidate is proved current again inside the fenced transaction that moves the branch, by the same predicate candidate selection uses: a live node, the active acceptance on the frozen head, an active relationship on the acceptance's generation, and no staleness. A candidate that is no longer current refuses the batch with `merge_candidate_moved`: the branch does not move and nothing is marked, and the next batch freezes again without that candidate and verifies again.

**Bisection and its limitation (D5).** When the merged set fails, the batch finds the first failing prefix by bisection. This assumes that a prefix which fails keeps failing when more candidates follow. When a later candidate repairs an interaction, an innocent candidate can be left out of this batch; that is safe, because only a PASS moves the branch, and it costs one more batch. A candidate the bisection leaves out is reported as `not_proven_failing` unless it fails when verified alone (`verification_failed`), and it keeps its ready state with no mark.

**Completion targets (D4).** A commit-accepted node completes on the integration ref that a batch with a moved record has moved on its checkout. One function gives those refs to the scheduler's edges and to the observation. A planned, abandoned, deferred or failed intent adds no target, and the edge's base ref is not part of it.

**The push (D6).** `dag-integrate-push` reads the relay store and pushes only a tip the relay moved the branch onto: a batch with a moved record whose new head is the tip and whose verification passed. A commit added on top of such a move, or a branch the relay did not verify, is refused with `merge_base_mismatch` before the remote is read, and the remote keeps its commit. The push stays fast-forward only, with no force, and a GitHub outage defers it.


## The pre-merge record (CRW-952)

An implementation node's acceptance needs the pre-merge evaluation record, `premerge-record/1`, and the relay judges that record itself. The record names the issue, the node, the head it evaluated, the dev commit, the criteria digest the plan held when the head was judged, the grader, the criteria with their verdicts, the defects, the score, the summary and the parent's dispositions. Its schema is `contract/schema/premerge-record.schema.json`. The validator, the canonical digest (sha256 of the keys-sorted, whitespace-free UTF-8 form) and the judgment live in one package, `internal/relay/acceptance/premerge`; every relay call uses that judgment, and internal/manage imports the same package.

`dag-accept` takes `--premerge @file` (or the record inline) for a new acceptance, for a `--supersedes` acceptance, for a re-validation, and to attach a record to an acceptance that has none. A pure replay of a stored acceptance needs no record. Each refusal has its own name, registered in `contract/schema/relay-exit-codes.json`:

- `premerge_missing`: no record, or a record that is not a `premerge-record/1`, or one that lacks a member the judgment reads.
- `premerge_subject_mismatch`: the record names another issue or node.
- `premerge_head_mismatch`: the record head is not the accepted head, and no allowed chain links them.
- `premerge_after_evaluation_missing`: the accepted head is a plain commit after the evaluated head, and `dispositions.afterEvaluation` is shorter than 20 characters.
- `premerge_criteria_stale`: the record was judged against criteria the node no longer holds.
- `premerge_undisposed`: a criterion that is not PASS, or a P0 to P2 defect (or one with an impact other than minor_separable), has no disposition.
- `premerge_blocked`: a disposition is `blocking`.
- `premerge_separable_forbidden`, `premerge_carried_forbidden`: a `separable` or `carried` disposition breaks its rule (P0, P1, failed criteria, introduced or regression defects, in-promise findings, a follow-up key that is not an issue key, a missing reason).
- `premerge_disposition_invalid`: an unknown class, or a `not_applicable` or `already_resolved` without a code-evidence note.

The head rule depends on the path. On the commit path (`--commit`), the accepted head may be the evaluated head, a chain of up to four merges whose second parent lies in `--base` and whose tree is git's automatic merge of the two parents (dev-only merges keep the evaluation), or a plain commit after it, which then needs the `afterEvaluation` statement. A hand-resolved merge, a merge whose second parent is outside `--base`, and a fifth merge are `premerge_head_mismatch`. On the pull-request path (`--pull-request`), the record head equals the pull request head exactly.

A passing record is stored with its acceptance in `dag_acceptance_premerge`: the record text, its digest, the evaluated head, the accepted head, the actor and the coordinator epoch. The table is append-only, and the judgment reads the stored text. Editing the record file after the acceptance changes nothing.

A re-validation changes the criteria digest of an existing acceptance, so its record is a second, later record for that acceptance. It is stored in `dag_revalidation_premerge`, one row per revalidation, tied to the revalidation row. The acceptance keeps the record it was accepted with, so the rule reads as one record per acceptance output and one per revalidation. A re-validation is judged on the head the acceptance stands on, which after a base refresh is the carried head: on the pull-request path the record must name that head exactly, so a refreshed head needs its own evaluation before it is re-validated.

An acceptance taken before the gate has no record. `dag-integrate` leaves it out as `premerge_missing` and does not touch its row. The attach path adds the record once, under the same acceptance id, judged by the same rules; a second attach is refused as `disposition_conflict`.

`dag-integrate` judges each active candidate from its stored record: the latest revalidation's record when there is one, otherwise the acceptance's own. A candidate whose judgment fails is left out of the batch with its `premerge_*` reason, in the same shape other left-out reasons take, and naming it with `--node` refuses with the same name. The intent row of a batch records the digest of each candidate's record, and the check that moves the branch uses the same judgment.

Two readings of the integrate side follow from the existing stale rule. A candidate whose criteria were re-registered without a re-validation is not a ready candidate any more: the stale rule removes it before its record is read, so `dag-integrate` names it with the stale refusal the DAG feature already uses (`disposition_conflict`), not with `premerge_criteria_stale`. A candidate whose criteria change after the batch selected it, while the batch verifies the merged tree, is refused by the check inside the moving transaction with `merge_candidate_moved`, and the branch does not move. Both refusals are reused names, not new ones. After a base refresh, the stand head is the head integration judges: a record of the head the acceptance carried before the refresh is held as `premerge_head_mismatch` until the refreshed head has its own record. That record is given with `dag-accept --pull-request` (the same pull request, now at the refreshed head) and `--premerge` naming the refreshed head (CRW-1033): the output is the one already accepted, so the call is a replay of the same acceptance that judges the record on the head it stands on and appends it as a re-validation under the same criteria (`dag_acceptance_revalidations` and `dag_revalidation_premerge`), the record `dag-integrate` reads. A record of another head is `premerge_head_mismatch`, and a second record of the head the acceptance already holds one for is refused as a second attach (`disposition_conflict`).

## A base refresh of an accepted node

The parent accepted a node's result and the base moved afterwards, so the pull request cannot land as it stands. `dag-base-refresh` is the route out of both shapes of that: it records that the acceptance also stands on a head the base was merged into, after the relay has proved from git that the head is the accepted head plus merges of the base branch and nothing else. Which generation the record names depends on who refreshed the branch. A node whose plan revision also changed its criteria reads stale (`criteria_changed`, route `revalidate`) and is not refreshed until it is re-validated; no generation is opened by hand for it ([An accepted node whose plan revision changed only its criteria](#an-accepted-node-whose-plan-revision-changed-only-its-criteria-crw-1036)).

**The parent refreshed the branch itself, in the acceptance's own generation (CRW-916).** This is the lane case. A bundle leader is accepted before `merge-train-open`; when no bundle forms (no members, or the leader's plugin-manifest version line collides with the base) the leader falls to the single lane, and the lane's turn has to refresh the branch before it merges (`update-branch`, or the manifest's version line recorded again). The relationship never leaves the generation the acceptance was recorded on, so the record names that generation, its own head event and revision, and the head the parent produced; integration is judged on that head and on that generation's own merged mark (the same generation, so the same revision), and the bundle's stand-head check reads the same record.

**The child merged the base in a generation the coordinator opened by hand.** A second ruling on an accepted head is refused, and a hand-opened generation is refused by `dag-correct` because a result that is current is not stale, so this is the route that goes back to the child. The child merges the base in a generation the coordinator opens by hand (`generation-open`, `generation-bind`), the parent rules that generation `verified`, the pull request lands and the parent marks the merge on generation 2's event. Integration needs the mark on the acceptance's own revision, so the node read `is_ancestor` true, `integrated` false and `mark_present` false, and kept its slot; the record names that later generation, after the relay has proved from git that its head is the accepted head plus merges of the base branch and nothing else.

`crw relay dag-base-refresh --plan P --node N --actor A [--checkout PATH] [--resolved PATH ...] [--expect-epoch E]` (answer `dag-base-refresh/1`). The caller names no commit and no pull request. The relay reads:

1. the node's active acceptance, its relationship and generation, its head, and the pull request the acceptance recorded (`dag_acceptance_forge`); the pull request head and base branch from the forge, open or merged (a closed one is refused), and the tip of that base from the target reader, all in the same call. The forge reading is fail closed as an acceptance reads one: evidence left unreadable or truncated is the host failure (exit 3) and nothing is written; a merged pull request is classified by the rule of [The forge reading of a merged pull request](#the-forge-reading-of-a-merged-pull-request), like every other reading;
2. the relationship's current generation through the same chain an acceptance applies to a head (the final report, acknowledged and verified by the host, ruled `verified` under the criteria the plan fixed for the node, under managed verification), asked before any commit is read. When that generation is a later one of the same child and its work report names a head, the head the forge shows has to be it (a prefix of seven characters or more is enough), because the ruling describes the commit the report names. When it is the acceptance's own generation, that generation's report names the accepted head, which a refresh moves past by construction, so the proof from the accepted head stands in for the comparison and a pull request still at the accepted head is refused, because there is nothing to refresh;
3. the commits themselves, in a local checkout: the clone named with `--checkout` (an absolute path that has fetched the accepted head, the pull request head and the base tip; git objects are content addressed, so any clone that holds them answers alike, and a commit it does not hold is refused `merge_target_unreadable` with the fetch to run). An acceptance is taken on its pull request's forge repository ([the target of an implementation node's acceptance](#accepting-a-result)), so the clone is always named. An acceptance recorded before that rule on a local checkout reads that checkout, and naming another is refused `malformed_receipt`. Every git command that computes runs in a throwaway bare repository that borrows the clone's objects and has no configuration, hooks or refs of its own; the clone is only read.

The proof walks the first parents from the pull request head back to the accepted head. Every commit on the way is a merge of exactly two parents, the previous commit first and a commit on the **first-parent line of the base tip** second (not merely in its ancestry: a branch the base merged is not the base), and holds the tree `git merge-tree --write-tree` writes from those two parents, with the attributes committed in the first parent (so the built-in merge attributes committed there, such as `union`, are honoured, as they were when the child merged). A merge git cannot do cleanly is accepted only when its tree differs from git's tree in the files git could not merge and nowhere else; each such file must carry no conflict markers (a start line and an end line of seven characters or the width the `conflict-marker-size` attribute of the first parent gives: a file committed with git's own markers or with any others was never resolved), whereas a conflict that has no markers, a binary file for one, may be resolved by keeping git's own side; either way the file and the blob the head holds are recorded. A single-parent commit on the way is accepted only when its parent is a merge this chain already proved and the only thing it changes is the plugin manifest's version line: the manifest equals its parent's apart from the version it records, with the same release and the same file mode, and that version is the one the commit's own payload derives. It is recorded as a `regenerate:plugin-version` step and needs no `--resolved` name; a single-parent commit that changes anything else, changes a second path, or records a version its payload does not derive keeps the `not_a_merge` or `tree_differs` refusal it had. For each hop, automatic mechanical classification requires agreement from the refreshed node and every identifiable contributing node. The proof walks all new first-parent landings of that hop's base parent and reads each landing's path delta against its first parent, without path-history simplification. A merge landing's second parent, or an exact single-parent landing tip, must match another node's active accepted head or a valid recorded refresh head in this plan and repository. Every touching declaration must cover the whole file mechanically with the same rule. Any unidentified path-changing landing, absent declaration or disagreement leaves that file manual. Declaration and contributor-head snapshots are checked again in the deciding transaction.

For `union`, the existing evaluator keeps precisely both sides' additions in their order. Automatic `regenerate:<command>` acceptance is restricted to entirely generated files: independently in the previous head, the hop's base parent and the new head, two fresh temporary checkouts must recreate the original file's bytes and mode from absent output. Each witness removes every tracked path covered by any candidate regeneration declaration, including nonconflicting outputs and other commands' outputs. It replaces the borrowed Git metadata with a fresh repository containing only remaining inputs, so HEAD/history and circular output copies cannot supply the missing output. The command runs each original tree's own code and inputs. A command failure, timeout, unreadable or missing output, or mismatch in any witness leaves that file manual. Commands that need original Git history or another declared generated intermediate may therefore require manual names. This trusts the declared code and remaining inputs; it is not a semantic ownership detector.

A partly generated file such as `plugin.json`, whose updater needs the existing file and only records its version, requires `--resolved`. One file is the exception: the plugin manifest `plugins/crw/.codex-plugin/plugin.json`. When the declarations given name it no single agreed mechanical rule, the checker applies its own built-in rule `regenerate:plugin-version` to it whether or not a declaration touches the path (a declaration that does settle the path with one agreed rule keeps its say), so the step carries that `rule` and the path needs no name; the rule holds the manifest to both parents apart from the version line, to the same mode and release, and to the version the head's own payload derives, and any other difference in the file is still refused. Eligible paths still pass the existing head evaluator (two runs, the second seeded from the hop's base parent). A matching file carries `rule` in the step and needs no `--resolved`. The remaining files carry no `rule`; the parent reads and names exactly their sorted union across all hops with `--resolved` (`git -C CHECKOUT show HEAD:PATH`). A missing, duplicate or extra name is refused. A symbol, shared contract surface, nonmechanical overlap or another repository's region gives no file-wide rule. A failed rule is `disposition_conflict` with `tree_differs` and the file and rule in the detail, even if the file is named; an evaluator error is `merge_target_unreadable`. `renumber` remains unchecked and is refused. A build that does not link the skill checker falls back to manual names. Regeneration executes the declared command with the caller's rights and the existing per-run timeout, not in a sandbox; the coordinator epoch is checked before evaluation and again before writing. Existing valid records replay their stored classification and names without re-executing regeneration, including older records where every file was manual. At most `MaxRefreshHops` (32) merges lie between the heads, and the first-parent line that is read is bounded by `MaxBaseLine` (200000) commits.

Anything else is `disposition_conflict` whose detail carries one closed code, and nothing is written: `no_update` (the head is the accepted head), `not_built_on_accepted` (the accepted head is not under the first parents of the head: parents swapped, or another branch merged in), `not_a_merge` (a commit between the heads has not two parents: it is the child's own work), `not_from_base` (a merged commit is not on the first-parent line of the base tip, also when the base moved after the tip was read: read again and call again), `tree_differs` (content that git does not merge from the parents, or an unresolved conflict) and `chain_too_long`. The node must be an implementation node with an active acceptance and a forge identity, not landed (nothing to refresh) and not stale (a stale node goes through its route, [Handling a stale node](#handling-a-stale-node), which this path does not change); the relationship must be at the acceptance's own generation or at a later one of the same child, not paused, cancelled or superseded, and the caller must be its parent (`scope_role_mismatch`). The pull request's base must be one of the targets the node lands on. No new refusal reason is registered.

The record is one row of `dag_base_refreshes` (appended and never changed: acceptance, sequence, relationship, generation, event and revision of the generation the record names, the pull request head, the base repository, branch and tip, the proof as canonical JSON (each conflict path and blob, with an optional proved `rule`) and the manual resolved paths); its id digests all of it, so a row written by hand is ignored by every reader. **The acceptance is not replaced.** Its id and digest stay, so every node that consumed it stays current; a superseding acceptance would turn each of them `blocked:stale_predecessor`. What changes is what the acceptance **stands on**: its own head, generation, event and revision, or, after a record, those of the newest valid record (the generation may be the acceptance's own - the lane refresh of CRW-916, which moves the head and not the generation - or more than one past the accepted one; the mark has to sit on that generation itself). The same head and pull request head again is a replay of the same record; a pull request that moved on (the base was merged in once more) is the next sequence number, proved again from the accepted head.

Readers follow what the acceptance stands on. `dag-integration-observe` observes that head (earlier observations of the accepted head stay in the run) and matches the `merged` mark on that generation's event and revision, so the node is integrated when every target contains the refreshed head and the parent marked it, and its slot is returned then, by the same call that returns any implementation node's slot. The edges that wait for the node's landing and the node's own reading follow, since they ask the same question. So do the readers of a node that turns stale after a refresh, as the generation the acceptance stands on is the refreshed one: the stale route does not read that generation as an open correction, `dag-correct` takes the generation after it (and refuses the refresh generation itself as not a correction), the relay's review of the accepted head is the review of the refreshed generation's head, `dag-accept` of that same output is a replay or a re-validation of the acceptance (the refresh generation has no execution of its own, and any other output there is refused `stale_generation` as before), and the relay's settling (`relationship-close-merged`) counts the newest record of an active acceptance as an acceptance of the marked head. A store that predates the table reads as a node with no record. A call that proves while another record lands is refused (`disposition_conflict`, "changed while this one was being proved") and repeated, so a slow proof never puts the acceptance back.

The lane follows the record too (CRW-447, [Merge eligibility](#merge-eligibility)). `dag-merge-judge` and `dag-merge-request` compare the pull request with the head the acceptance stands on, so a refreshed pull request at the head the newest record names is judged like any accepted one and gets its merge turn for that head; an artifact edge out of the node reads the generation and the head event the acceptance stands on and the head its latest merge check names; the release freshness check of a successor that pins the node reads the pull request against the same head. The readers that look a node's merge turn up by its candidate head (the unknown-effect reading, the merge-order lane position, the live head the conflict sweep measures) use the head the acceptance stands on, and the first also every earlier head it stood on.

**The coordinator's steps.** In the lane case (the acceptance's own generation) the parent refreshes the branch inside its own turn, fetches the commits where the relay reads them, records the refresh with `dag-base-refresh`, and runs the lane at the head the record names; nothing is ruled again, because the generation's ruling is the one the acceptance already rests on. For an accepted node whose child merged the base in a generation opened by hand, the steps are (the exact commands are in crw-run, [a base refresh the child made after the acceptance](../../plugins/crw/skills/crw-run/references/merge-readiness.md#a-base-refresh-the-child-made-after-the-acceptance)): rule the later generation `verified` as for any report; `git -C CHECKOUT fetch origin`; `dag-base-refresh` (the first call may be refused naming the files to read and name with `--resolved`); then the lane as for any accepted node: `dag-merge-judge`, `dag-merge-request`, the merge lane's own `merge-turn-check`, the merge on the forge and `merge-turn-land` for the head the record names, `assignment-mark --mark merged --expected-event` that generation's event, `dag-integration-observe`. An observation made before the record is a fact and stays; observing again after it integrates the node.

What this does not do, so a reader does not look for it: it does not make a stale node current, and it does not turn a generation that holds the child's own work into a refresh (that is a correction). The hand resolution of a conflicted file is the one thing it cannot prove. A pull request at a head no record names (the child pushed again, or the head holds more than merges of the base, for which no record can be made) is `stale_head` as before: a record is made again for the new head, from the accepted head, or the generation goes back to the child. What stays on the accepted head: the manifest of a release pinned to the node (it names the accepted head, which the refreshed head contains, and a record does not change it), the `head_sha` that `dag-progress` shows for the node, and B-13 (the digest of a merge check covers the evidence it holds, as before, and not the heads of its row). A record that lands between the freshness check of a release and its intent is the window a push after the forge was read has always been. The merge lane compares the candidate with the head the newest generation's report names exactly, while the record accepts a report head of seven characters or more: a report that names an abbreviated head is refused by `merge-turn-check` until it names the whole head.

## A generation opened by hand and never sent

A parent rules a node's report `verified`, finds before `dag-accept` that the base moved, and opens the next generation by hand (`generation-open`) to send the child the merge of the base. Then it refreshes the branch itself ([crw-run, refresh the base yourself](../../plugins/crw/skills/crw-run/references/merge-readiness.md#refresh-the-base-yourself-when-only-the-base-moved)) and never sends the generation. The relationship now stands on a generation that holds nothing, and no other route takes the node: `dag-accept` reads the relationship's current generation and refuses `stale_generation` (it is not recorded as an execution of the node); `dag-correct` refuses because the accepted result is not stale (and nothing is accepted yet); a second ruling on the event of generation 1 is refused because the event is not the head of the current generation; `dag-base-refresh` needs an acceptance; and the merged mark of generation 1's event is refused `revision_ambiguous`, because the relationship's current generation has no report to mark.

`crw relay dag-generation-withdraw --plan P --node N --actor A --relationship R --generation G --reason TEXT [--expect-epoch E]` (answer `dag-generation-withdraw/1`) is the counterpart of `generation-open` for the plan's node. It closes the generation and puts the relationship back on the generation before it; the commands that follow are the ordinary ones. The answer carries `relationship_id`, `withdrawn_generation`, `restored_generation`, `dispatch_request_id`, `reason` and `replayed`.

**What the relay requires, all read in one transaction.** The caller holds the plan's epoch; the relationship named with `--relationship` (`assignment-show` prints it) is an execution of the node and the caller is its parent; the plan does not hold the node (paused, cancelled, archived); the relationship is active and not superseded; `G` is 2 or more and is the generation the relationship stands on (`stale_generation` otherwise); the generation's row is an anchor still pending, with no dispatch turn and no bind time, and carries a reason `generation-open` gives (`initial_assignment`, `needs_changes_revision` or `accepted_result_correction`: the generation of a returning tenure has none, and a withdrawal does not undo a tenure); no event of any outcome belongs to it (a report, a revision request, a decision reply); no turn was admitted to it; no `needs_changes` ruling opened it; and no execution of a node was recorded on it (`dag-correct` and `dag-adopt` record one). A generation that fails one of these was sent, used or recorded, and the refusal is `disposition_conflict` naming what was found, exactly as `dag-accept` refuses it today. A poll the daemon stored for an older turn under the generation's number is not read: it says nothing about the generation.

**What it writes.** One row of `dag_generation_withdrawals` (appended, never changed: relationship, generation, plan, node, the dispatch request id it was opened under, the reason it was opened for, the generation the relationship stands on again, the coordinator's reason, who withdrew it, the epoch and the time), the relationship's `execution_generation`, and a `generation_withdrawn` journal row. The generation's own row stays. **A number is never reused**: the next generation, whoever opens it (`generation-open`, a ruling, a decision reply, a tenure), takes one more than the highest the relationship ever held, so after a withdrawn generation 2 the next is 3. A generation that was withdrawn is final: `generation-open` repeated under its request id, `generation-bind` and the anchor binders of delivery are refused `stale_generation` (the daemon's binder skips it), so it cannot come back. The generation a correction follows is the nearest one that was not withdrawn, in the relay's currency (the predecessor a child's first report declares) and in `dag-correct`. Nothing else is written; the command does not touch a delivery: a generation-open leaves only a `stale_generation` note on older deliveries that were not yet delivered, the delivery pass reads the current generation, so an older delivery that was queued then can become eligible again under the delivery policy as it stands. The same relationship and generation again are a replay, also after the node was adopted by another relationship: the relationship is named so that a repeated call can never withdraw the generation of another relationship that has the same number.

**Why a withdrawal and not `dag-accept` taking the last recorded generation.** The relay's readers of the relationship take its current generation as the one the work stands on: the merged mark, the assignment's state and head, the merge turn's grant, and the node's own reading (`blocked:stale_head` when the acceptance's generation is not the relationship's). An acceptance of generation 1 while the relationship stays on generation 2 could not take the merged mark and the node would never integrate. Moving the relationship back is the one change they all follow, and it is a record of a fact the coordinator states (the generation was never sent) next to the facts the relay can show.

**The coordinator's steps** (the exact commands are in crw-run, [a generation opened by hand and never sent](../../plugins/crw/skills/crw-run/references/merge-readiness.md#a-generation-opened-by-hand-and-never-sent)): `assignment-show` shows the relationship on the unsent generation; `dag-generation-withdraw`; `assignment-show` shows the generation-1 event as the head again; `dag-accept` (it reads the pull request at the head the branch has now); the merge lane (`dag-merge-request`, the grant, the check, the merge, the landing); `assignment-mark --mark merged --expected-event` the generation-1 event; `dag-integration-observe`. A node whose result was already accepted before the generation was opened takes the same first step and keeps its acceptance: the acceptance and the head it names are not touched, so the pull request has to be at the accepted head (a parent that refreshed the accepted branch itself records that with [`dag-base-refresh`](#a-base-refresh-of-an-accepted-node) in the acceptance's own generation, and a base the child merged after the acceptance goes to that child as a new generation, recorded the same way).

**What the relay cannot show.** It does not read the child's thread. A message about the generation that reached the child outside the relay leaves a child that works in a generation that was never bound: its receipt there was refused `unbound_generation` and, once withdrawn, the generation can no longer be bound, so that work is ignored. The coordinator's `--reason` is the statement that nothing was sent.

**Rollback.** An older runtime opens a store that carries the table without reading it. It fails to open a new generation after a withdrawal (the number it computes is the withdrawn generation's, and the primary key refuses it), so it never reuses a number silently; it does not know a withdrawal, so its replay of the old request id and its binder can bring the withdrawn row back. A store with a withdrawal is not handed back to a runtime that predates this command.

## Decisions

`crw relay dag-decision-record --plan P --actor A --subject S --digest D --disposition approved|rejected --authority-kind K --authority-ref R` writes the decision a `decision` edge waits for. Only the project's one registered parent records. Recording is not authority: the
edge compares the authority kind with the kinds it names and reads the digest, so a decision by another authority or about another digest records and opens nothing. The text of the authority is opaque (D-09). The same decision again is a replay; any other decision of the subject
supersedes the active one and keeps the history, so a rejection after an approval is a fact.

## Corrections

A correction goes back to the same child (contract 3.2): a `needs_changes` ruling opens the next generation of the same relationship and the existing verdict writer sends the correction message in the same transaction, so a manifest cannot be placed in that
generation afterwards. The protocol therefore puts the manifest into the one text the relay itself sends. `dag-correct --prepare --manifest-request @file` rebuilds and verifies the node's input manifest as the store holds it now (the base it records is read from the named target branch as a release reads it: the request names the repository and the ref, and a `sha` it states is checked against the branch tip and refused as `merge_base_mismatch` when the branch reads another commit, with nothing stored; the recorded commit is always the one the branch reads), stores it, and prints an English
instruction line that names the manifest, a copy of its canonical bytes kept under the child's first artifact root (the file the child reads, since it cannot read the relay's store; see *The frozen copy*) and the sha256 of that file; the parent submits that line as the **restoration** finding of its `needs_changes` ruling. (When no ruling can open the generation, the coordinator opens it by hand under the dispatch request id the same step prints and carries the line in its own dispatching message: [Three ways to open the generation](#three-ways-to-open-the-generation). A result the plan already accepted and that is still current has no ruling to open it, and its generation is opened by hand under a reason that states the correction: [Correcting a result that was accepted and is still current](#correcting-a-result-that-was-accepted-and-is-still-current).) After the ruling, `dag-correct` (without `--prepare`) binds the generation the ruling opened to the manifest that finding names
(`dag_node_executions`, kind `correction`) once the manifest is stored for this node at its current slice and criteria and the restoration note carries, word for word, the instruction that manifest was prepared with (this generation, the path of the copy and its hash). No file is read when the generation is recorded: the child checks the copy against the hash in the line it was sent. The bound digest is derived from what the child was told: a digest in an ordinary finding does not bind, a restoration block that names two different manifests is refused, a ruling without the block leaves the previous manifest in force (`carried_over`), and a `--manifest-digest` that differs
is refused, also when the generation is already bound. A node whose accepted head landed in every target is refused in both steps ([Handling a stale node](#handling-a-stale-node)). The previous acceptance stays active and reads `blocked:stale_head` until the parent accepts the corrected result with `--supersedes`; what consumed the old acceptance then reads stale ([Invalidation](#invalidation)).

### An accepted node whose plan revision changed only its criteria (CRW-1036)

A plan revision that changes only a node's `criteria_set_digest` makes its accepted result stale as `criteria_changed`, and its route is `revalidate`: the same output is ruled again under the plan's criteria and accepted again with `dag-accept`, with no new generation and no new child ([Handling a stale node](#handling-a-stale-node)). Nothing is sent to the child, so a generation opened by hand for it is a dead end: `dag-correct` refuses to record it (`the route of N is revalidate, not a correction by hand`) and `dag-accept` refuses a generation that is not recorded as an execution of the node (`stale_generation`), after the child has already worked in it. The relay now refuses the dead end where it starts. `generation-open` (whatever reason it is given: `needs_changes_revision`, `accepted_result_correction` and `initial_assignment` alike, since `dag-correct` records none of them on this route) and `generation-bind` ask the node's route first, in the transaction that opens the generation or binds its anchor (a plan revision between the check and the write is seen), and refuse an accepted node whose route is a re-validation with `disposition_conflict`, naming that route; nothing is written. A generation a `needs_changes` ruling opened, a decision reply, a correction of a stale node whose route is `correct`, a correction of an accepted node that is not stale ([CRW-906](#correcting-a-result-that-was-accepted-and-is-still-current)), a node that was never accepted and a relationship that executes no plan node pass as they did.

What the parent does instead, for the node that reads `stale:criteria_changed` with the action `revalidate`:

1. Register the plan's criteria for the relationship with `criteria-register` when the reading says the registration is the old set (the revalidate `action_detail` ends with that sentence while the registered set differs from the plan's). Without it the ruling is refused `unknown_criterion` or `criteria_set_changed`.
2. Rule the same output `verified` under the plan's criteria, and accept it again with `dag-accept` (a revalidation of the same acceptance, E-11).
3. Then base-refresh, merge and integrate as for any accepted node; a base that moved is `dag-base-refresh` after the revalidation, never a generation opened first.

A generation opened by hand before this rule was written, and not recorded by `dag-correct` before the plan revision, is read as such: the node's `action_detail` says the route is a re-validation and that the generation cannot be recorded, and names `dag-generation-withdraw` for the generation that was never sent. A generation already bound to a turn cannot be withdrawn, and the relay has no route that records it for a node whose route is a re-validation; its code is integrated through git, and the node's record is left as it is (the decision of the management session on CRW-966, CRW-833: git is canonical). The rejected design, a recovery that skips the hand-opened generation and accepts the later head with `dag-accept --supersedes`, is not built; CRW-864 (a correction generation opened by a ruling after a bound hand-opened one) is a separate narrower exception and is not in this code. A correction that `dag-correct` recorded before the plan revision is an execution of the node and not this case: its reading keeps the open-correction words (record, wait for the report, `dag-accept --supersedes`) and adds the `criteria-register` step while the registered set is the old one, and its result, ruled under the plan's criteria, is accepted with `dag-accept --supersedes`.

A **non_pr** node (a decision document) has no head to land and no integration to observe (`dag-integration-observe` refuses it: `it has no head to observe`). Its parent's `assignment-mark merged` on the revision its acceptance stands on is its integration, so `child-cleanup` no longer asks for an observation first. This rests on the accepted result having no head, not on what the plan now calls the node: a node a later revision turned into a non_pr one keeps the code head it was accepted with and is still judged on the observation of that head, and a non_pr node a revision retired keeps the answer its headless acceptance gave. The cleanup of its child is judged on the mark, the relationship being closed, nothing owed and no other live relationship naming the child, as for any node.

### The frozen copy

A manifest that a child has to read from a file (an oversize release prompt, or a correction) is kept as `<first artifact root>/dag-input-manifests/<sha256 of its canonical bytes>.json`. The name is the hash of the
bytes, not the manifest digest: two bodies of one manifest differ in what the digest leaves out (the time of the build, the rule version), so they are two files. An existing regular file of that name is reused only after the authorized, byte-for-byte check below. A newly created file is created exclusively with mode 0600, in a directory that must be a directory of its own (a link is refused), and is read back through the relay's authorized
open (inside the root, no link on the way, a regular file, never blocking on a pipe) and compared byte for byte. The child owns its artifact root, so a link or a pipe planted there makes the freeze fail and never makes it wait. A link planted between the check of the directory and the creation of the file, or an artifact
root that is itself a link, can leave one file outside the root (it holds only a manifest the relay wrote); the read-back then refuses and nothing is bound. An artifact root with a control character is refused when a correction is prepared,
because the relay's message joins the lines of a finding and the child would read another path. A correction uses the body the store holds for the digest, so preparing twice from the same inputs gives the same file and the same line. The directory is created by the freeze. A release that ends without recording an intent of its own takes back the copy it froze, and closing an abandoned release takes back its own:

* **Moment.** The end of a `dag-release` call that recorded no intent (a refusal after the manifest was frozen, such as `capacity_exhausted` or a later refusal of the request; a write of the new copy that failed part way, such as a full disk; a store failure inside the intent transaction; a race lost to a call that recorded the same release), and the settling step of `dag-release-close`. A crash between the freeze and the intent leaves the file, and nothing sweeps the directory.
* **Target.** In a release, only a file this call created (the exclusive create succeeded); a file that already existed was only reused. At close, the file named by the header line of the closed intent's own frozen request (the line the relay wrote at the head of the prompt, for the manifest being closed: the operator's instructions are never read for a path), and only when its bytes are that manifest. Always only `<root>/dag-input-manifests/<sha256>.json`, a regular file whose bytes hash to its name, with one exception for the file this call created: when its own write failed part way, the file holds a strict prefix of the bytes it meant to write (possibly none) and is taken back as well, because a prefix cannot be a manifest copy anything relies on. A file that holds other bytes stays.
* **Reliance, never removed.** A copy a live intent's frozen request names (a bound release, an accepted node's, a release still waiting for its start) or a stored manifest holds exactly these bytes (an accepted node's, a prepared or recorded correction's). At close the stored manifest counts only when its digest is bound to an execution, is accepted, or an open relationship owns the issue, because the closed intent's own stored body is what its copy holds. The check runs in the same write transaction as the unlink, so no intent can commit between them, and the intent transaction freezes its copy again before it records the intent, so a copy that another call took back is there when the intent names it.
* **Mechanism.** `store.UnlinkPinned` opens every component of the root and of the directory with `O_NOFOLLOW` from `/`, each relative to the one before, opens the file relative to the directory's descriptor (`O_NONBLOCK`, so a FIFO is refused and cannot hold the transaction), reads at most 16 MiB, asks the retention check, compares the name with the file it read (device and inode) and unlinks on the directory's descriptor: a link in any component, or a component swapped meanwhile, cannot lead it elsewhere. It needs Linux, as every artifact read does; elsewhere the copy is kept. A mount point on the path and a file replaced in place between the last check and the unlink are not stopped.
* **Evidence.** A journal row per decision: `dag_manifest_copy_removed` or `dag_manifest_copy_kept` with the path, the sha256, the byte count, the reason (`relied_on`, `reliance_unknown` (a stored manifest could not be read), `link_in_path`, `not_a_copy`, `bytes_differ`, `too_large`, `changed`, `remove_failed`, `name_differs`, `unsupported_platform`) and the cause (the refusal reason that ended the release, or `closed`); a removal states the cause as its reason, or `incomplete_write` for the partial file a failed write left (its byte count is that of the file removed). The unlink comes first and the row after it in the same transaction, so a failure of the commit after the unlink loses the row of a file nothing referenced, never a referenced file. The cleanup never replaces the call's own error.

## Merge eligibility

`crw relay dag-merge-judge --plan P --node N --actor A [--repository OWNER/NAME --pull-request N]` decides whether the accepted pull request of an implementation node may go to the merge lane (criterion c8). The relay reads the pull
request (by the forge identity recorded with the acceptance) and the base branch itself; then one transaction applies these rules in order, the first decisive one winning, and appends the judgement to the node's history in
`dag_merge_checks` (a judgement that restates the latest one writes nothing, so the history is readable afterwards: the retry, the stale head, the eviction).

| Outcome | When |
| --- | --- |
| `evicted` | a required check failed again on the same head after its retry (decision D-12). Final for that head of that pull request, whichever acceptance recorded it, under whichever spelling of the repository (the forge does not tell owner/name apart by case) and whichever pull request carried the commit: nothing later, green checks and a fresh acceptance of the same head included, brings it back (the acceptance in force is given the eviction in its own history); a new head needs a new acceptance and starts with its own retry. The reading says `blocked:evicted` |
| `stale_criteria` | the plan's or the relationship's criteria are no longer the ones the acceptance stands on |
| `stale_head` | the pull request is at another head than the one the acceptance stands on (E-10): the accepted head, or after a [base refresh](#a-base-refresh-of-an-accepted-node) the head the newest record names; the row stores that head and the head seen, so the reading blocks the edges built on it |
| `predecessor_not_landed` | an incoming `integrated` edge, or an incoming code-pinned edge (a stacked pull request), whose predecessor's accepted head is not yet in the edge's target |
| `stale_base` | the base branch tip is not contained in the head, so the required checks did not run on the tree that would land. The dev ruleset is strict (D-11), so a head that contains the tip is that tree; the pull request's own base field says nothing about what the checks ran against and is stored for information only. The local ancestry check needs the head fetched into the checkout; a head it does not have is a failure of the host and writes nothing |
| `checks_pending` | a required name has no run on the exact head, or one of its runs has not finished, or the checks are not usable evidence |
| `retry_same_sha` | every required check has finished and one failed, and no retry was spent on this head: run the failed checks again on the same head (no new generation, no reassignment). The same snapshot read again is the same judgement |
| `eligible` | every required check passed. After a recorded failure the reason says so |

**The head that is judged** is the one the acceptance stands on: the accepted head, or, once the parent has recorded a [base refresh](#a-base-refresh-of-an-accepted-node), the head of the newest record. The judgement reads it before it reads the forge and again in the transaction that writes, and a record that lands in between is a reading older than the history (`merge_candidate_moved`, nothing written). The row keeps that head as `head_sha` (the answer's `accepted_head`) and the head the pull request showed as `observed_head_sha`; a judgement that repeats the latest one under another head is a new row, and the reason of a judgement made on a refreshed head names the record. An evicted head stays evicted in the history; a pull request back at it once a record moved the acceptance on is `stale_head` (it is no longer the head the acceptance stands on). Nothing about a node that no record moved changes.

A stale accepted result is not judged at all: a stale result never merges (contract 8.2, [Invalidation](#invalidation)). The call is refused `disposition_conflict` naming the stale reason, ahead of every rule above (an evicted head included), and writes no row of the history. The judgement is asked again inside the transaction that writes, so a plan revision that lands between the read of the pull request and the write is seen; `dag-merge-request` asks it once more in the transaction that creates the turn (after the criteria and the predecessors, so a criteria change that lands in that gap is `criteria_set_changed` and an integrated or code-pinned edge added in it, whose predecessor has not landed, is the unmet predecessor), and a revision that lands after the judgement has recorded an `eligible` row leaves that row in the history and creates no turn. A result that is current again (the plan repaired, the node accepted again) is judged as before.

A result that is **under correction** is not judged either, and this one is about the generation rather than the head: while the relationship's live execution generation is later than the generation its active acceptance stands on, a correction generation is open over the accepted result and has not been accepted over yet, so the head the acceptance stands on is the very result being repaired. The call is refused `disposition_conflict` naming the open generation and the generation the acceptance stands on, and writes no row of the history; `dag-merge-request` makes the same judgement, so it creates no turn. The refusal is made where the head would otherwise be judged, so a head the history already evicted keeps its eviction (that eviction is final and is restated, never lifted) and a pull request at another head is still stale_head; either way the head is not eligible and no turn is created. The reading is taken with the acceptance in one statement and asked again in the transaction that writes, so a generation opened while the pull request is being read is seen. It is the guard [Correcting a result that was accepted and is still current](#correcting-a-result-that-was-accepted-and-is-still-current) rests on before the child has pushed: without it, a bundle or a lane turn taken between opening (or recording) the generation and that first push would carry and land the accepted head, which the pull request still shows. A correction accepted over with `dag-accept --supersedes` moves the acceptance to the stand generation and the node is judged as before; a withdrawn generation puts the live generation back and the old head may ride again; a generation recorded by [`dag-base-refresh`](#a-base-refresh-of-an-accepted-node) moves the stand generation with the live one, so a base refresh is not a correction. The merge train's own gate (`trainStandRefusal`) refuses a bundle member the same way at open, verify and land, naming the open generation.

A required check is read the way merge-evidence and the merge lane's own check read it: of every run only its newest attempt counts, every run of a required name must be a `success` (a skipped or neutral run is not one, so a head the judgement lets in is not refused by the lane for the same check), a required (name, integration) pair needs its own run (a name that two integrations must answer needs both), and the opaque run identities are never ordered. Failures count only when every required check has finished, so one red job seen beside a running one never uses up the retry. A second, different failure after the retry round opened evicts. A failure is told from another by the run's identity, its attempt and the time the forge last changed it (a commit status has no attempt and a check run can be reset in place), and a failure of a run that a judgement saw not failing (running or passing) since it failed is a new failure whatever its identity; another check running again says nothing about this one. Everything is computed from the newest reading of each run (a listing that still carries a failed first attempt beside the passing second one judges as the second), a failure counts once a judgement recorded it (a red job beside a running one is not counted), and a reading of a run that is older than one already judged (an earlier attempt, or an earlier completion of the same attempt, arriving late) is not judged: it is `merge_candidate_moved` and the caller reads again. So is a reading of the pull request that was in flight while another judgement of the node was recorded: it is older than the history whatever it contains, and nothing is written. Times are compared as instants (the forge's spelling does not matter). A forge that returns an older state of a run after a newer one was judged cannot always be told from a run that was reset: a reading that goes backwards without a time and with no judgement between the two (a run read as running after its completion) can count as a rerun, so a head can be evicted one failure early. Two failures that carry the same identity and the same time and that no judgement saw apart read as one failure: the node is not eligible either way, but it can take more than one retry. A pull request whose list of
required checks cannot be read is not judged (`merge_evidence_malformed`, nothing written): ignorance is not "none required". A draft, closed or merged pull request is `disposition_conflict` (a merged one once its reading is classified, [The forge reading of a merged pull request](#the-forge-reading-of-a-merged-pull-request)); evidence the relay could not read
completely is the host's failure; both write nothing. A row of the history that no longer digests to what was recorded (B-13) is `revision_mismatch`, and the edges built on it read `blocked:evidence_mismatch`.

`crw relay dag-merge-request --plan P --node N --actor A --host H` judges again now (never from the history) and, only when the node is eligible, asks the existing merge lane for a turn with the head the acceptance stands on, the pull request and the
relationship, in one transaction that reads again the acceptance, the relationship, the criteria, the predecessors that have to have landed, whether the result is stale, and the latest judgement (its head, and the evidence it recorded digested again): a pause or a change that lands between them creates no turn and no grant. A node that is not eligible gets no turn and the refusal is the relay's own reason (`merge_candidate_moved` for a stale head, `merge_currency_stale` for a stale base, `criteria_set_changed` for stale criteria,
`disposition_conflict` naming the outcome for the rest); the judgement stays in the history, which is what counts the retry. The lane is not changed: a holder has one live claim per target, so the parent merges one pull request of
a project at a time (a second request while the first turn is open, even for another node accepted at the same commit, is `disposition_conflict` naming that turn), and turns of different projects are served first in, first out (D-16, `requested_at` then turn id). The parent's order is
accept, `dag-merge-request`, acknowledge the grant, `merge-turn-check`, merge on the forge, `merge-turn-land`, `assignment-mark merged`, `dag-integration-observe`. A pull request that went through `dag-merge-request` is
the only kind the DAG path lets into the lane, so every landed tree of it has an `eligible` judgement of the very head that landed.

## Pause, resume, cancel and archive

The plan holds or ends a node by a revision ([DAG plans](dag-plans.md#pause-resume-cancel-and-archive)): `pause_node`, `resume_node`, `cancel_node`, `archive_node`, `pause_plan` and `resume_plan`.
The scheduler reads that state at the revision it reads the plan at and obeys it in the reading and in the commands that advance a node. It reaches nothing in the relay: no relationship is paused
or cancelled by a plan change, a child keeps running and reporting, and a slot stays held until an explicit `slot-release` (contract 7.4 and 3.2). What the plan stops is the scheduler releasing a node,
accepting its result, correcting it or sending it to the merge lane. A lifecycle change releases no slot: a slot a node holds stays held, and keeps counting against the ceilings, while the node is paused or
ended and while the plan is paused, until it is returned as it always is (an explicit `slot-release`, the acceptance of a non-PR node, or the integration of an implementation node, which an archived node can still reach).

**The reading.** The plan's hold is read before the edges, so a held node is never a candidate whatever its edges say. The reason is the first that applies of: the node is cancelled or archived, the
plan is paused, the node is paused. The state word is the node's own lifecycle when it has one and `planned` for a node of a paused plan:

| The plan says | A node nobody owns reads | A node with a release or an execution reads |
| --- | --- | --- |
| the node is paused | state `paused`, `defer:node_paused` | the state its execution is in, with `defer:node_paused` in place of `skip:already_owned` |
| the plan is paused | state `planned`, `defer:plan_paused` | the same, with `defer:plan_paused` |
| the node is cancelled | state `cancelled`, `skip:node_cancelled` | the state its execution is in, with `skip:node_cancelled` in place of `skip:already_owned` and `done:accepted` |
| the node is archived | state `archived`, `skip:node_archived` | the same, with `skip:node_archived` |

Three readings are kept whatever the plan says, because the plan cannot take them back or an operator has to act on them: `done:integrated` (a landing is a fact; a cancel does not revert it),
every `blocked:*` reason (a creation of unknown outcome included: its detail says that a repeat of the release is refused until the plan lets the node run) and, for a pause only, `done:accepted` (a pause does not
invalidate an acceptance). A node the plan paused, cancelled or archived carries `lifecycle` in its reading and a paused plan carries `plan_state` at the top; both keys are absent otherwise, and the pass
record keeps the same optional key. Edit regions follow the relationship and not the plan: a child that still runs after the plan cancelled its node still holds its regions.
A stale node the plan cancels or archives reads as ended (state `cancelled` or `archived`, no stale object) and its detail keeps what made it stale; a stale node the plan pauses keeps its stale reading.

**What is blocked downstream.** A node the plan cancelled or archived is never released again, and nothing is released from its result: its artifact and decision edges stay unsatisfied
(`blocked:predecessor_cancelled`, `blocked:predecessor_archived`) until the plan is revised, and its integrated edge only when the landing is observed (see the edge rules above). The same gate follows what an accepted
node consumed: following the manifest of its acceptance, and then the acceptances its inputs rest on, an input whose node the plan cancelled or archived blocks the edges out of it, so a node accepted on the
result of A is not a base for what follows it once the plan cancels A. An integrated input is not followed (what it handed over is in the target). This is a gate and not an invalidation: no acceptance
row changes, and whether an acceptance is stale is the invalidation reading's, above.

**The commands.** A node the plan paused, cancelled or archived, and every node of a paused plan, is refused the work: `dag-release` (a new release, and a frozen unbound intent that would create its child:
nothing is created and no slot is reserved), `dag-accept` and `dag-correct` (prepare and record; the manifest of a correction is stored in the transaction that asks again, and the file and the instruction
follow only after it committed). A frozen release is also refused when the plan ended a node whose result its frozen manifest consumed since the intent was written, by the same gate as a new release. The landing of an accepted pull request (`dag-merge-judge`, `dag-merge-request`, `dag-integration-observe`)
is refused for a paused or cancelled node and a paused plan, and not for an archived node, as it is not for an archived relationship. A refusal is `disposition_conflict` with the closed reason and the node in the
detail, writes nothing, and is made again inside each command's transaction, because a pause moves neither the slice digest nor the criteria digest those transactions compare. A release already bound to its
child answers as it always did. `dag-decision-record` and `dag-region-declare` record facts and are not refused, and neither is `dag-release-close`: it ends an abandoned intent and creates no
child, so the operator can still return the slot of an abandoned release of a node the plan holds. The release that follows the close is refused like any other while the node is held, and the successor
request a close leads to is a frozen release, which the check below stops until the plan lets the node run.

A release asks again at the last point the DAG can stop a child: just before the managed start, for a new release and a continuation alike, and a node that left the plan (retired or replaced) is refused there as
`unregistered_scope`; the refusal leaves the intent and the slot where they are, and the resume lets the same release go on. That last check is a read, so a pause that commits after it, including while the managed
start is running, cannot undo a creation already begun outside the store: the child is then bound as it always is, and the node reads as running under the plan's hold (`defer:node_paused`); pausing or cancelling its
relationship is the relay's own operation.

**What a pause leaves alone.** An acceptance recorded before the pause is a value the pause does not touch: it stays active, the edges it satisfied stay satisfied, and the node reads `done:accepted` with
`lifecycle` beside it. A result that a child reports after the pause is recorded by the relay as every report is, but it is not accepted while the pause lasts, so the edges it would satisfy stay open and no successor
is released from it; after the resume the parent accepts it and the successor becomes ready. The child itself is not stopped: pausing or cancelling the relationship is the relay's own operation and a plan change does not do it.

## Conflict observations

`crw relay dag-conflict-observe --plan P --actor A --repository PATH --left-node N --right-node M --left-head SHA --right-head SHA` records how many files git cannot merge between the heads of two parallel branches of a plan
(`git merge-tree --write-tree`, git 2.38 or newer; 2.40 or newer to read the attributes committed in the commits), the number criterion c7 asks to be recorded. The checkout is whatever git says it is (a working tree, a linked working tree or a bare repository, at any path). The merge is computed in memory in a throwaway bare repository that reads the checkout's objects through an alternates file and has nothing else of it: the checkout's configuration (a merge driver is a command it would run), its working tree and an uncommitted `.gitattributes` can neither run code nor change the answer (the attributes are the ones committed in the left head, read by git 2.40 and newer), and the checkout gains no objects; git's NUL separated answer is read for the file names, and an answer without the shape of a merge result is a failure and never a count of zero. A submodule changed on both sides counts as a conflict, because git decides it by looking inside the submodule and the throwaway repository has none: the count can be higher than the merge's, never lower. The nodes are stored in sorted
order with their heads, so asking either way round is one row, and the same two heads over the same base are a replay. It is a measurement: nothing in the reading waits for it. It also appends a one-member sweep (trigger `manual`) to the ledger, so that the measurement is ordered among the others of its pair.

### The sweep

A landing and a receipt each leave the live heads of a plan in a new relation to each other and to the tip of the branch they land on, so each is measured: a **sweep** runs git merge-tree over every unordered pair of the live heads and over every live head against a tip, and records the result. A live head is the head of an
implementation node that holds its edit regions (running, or accepted and not landed). The head is the first of these that exists: the one the parent named (`--head NODE=SHA`); the head of the node's current accepted result, meaning the acceptance stands on the relationship the node runs on, on that relationship's current
generation and on the generation's current head event (a correction generation, or a newer report of the same generation, makes the acceptance history, since it stays active until the new result is accepted); the `HEAD` of the checkout the node's child works in (`child_cwd`, which managed start records), when that is a worktree of the
sweep's repository (one git common directory) and not the sweep's own working tree. A work report is not a source: this build has no writer of one. The relay never fetches: a head, or a tip, that the checkout does not have is a member that says so.

A sweep writes, in one transaction after git has answered, the observations (a pair in `dag_conflict_observations`, a head against a tip in `dag_tip_conflict_observations`, each with its files), the declaration drift, a row of the ledger `dag_conflict_sweeps` and its members in `dag_conflict_sweep_members`. A member is
a pair or a tip and has a status: `observed` (a new observation row), `replayed` (the same heads over the same base were recorded before: the existing row stands) or `unmeasured` with a reason from a closed set: `head_unknown` (no source names a head), `checkout_mismatch` (the child's checkout is another repository, or the sweep's own
working tree), `commit_missing` (a head is not in the checkout: fetch it), `no_common_ancestor` and `tip_unreadable` (the tip could not be read, or is not in the checkout). A failure at any point leaves nothing, so the same call can be made again. The ledger orders the measurements: the member of the highest sweep is the latest measurement of a pair, even when its
observation is an older row that the same heads replayed.

**Drift.** A node whose latest declaration has no region over a path it conflicted on (with another node's head, or with the tip) has a row in `dag_conflict_drift` for that path: the declaration did not describe the work. A path no node declared is drift for every node that edited it; a path only one node declared is drift for the other. A tree region covers what lies
under it, a file or symbol region its file. It is recorded with the observation (the answers carry it as `drift`), by the sweep and by `dag-conflict-observe` alike. An observation recorded by an earlier build (no drift, no member of any sweep) has its drift marked by its first replay, from the measurement and the declarations as they are then.

**What prompts a sweep.** `dag-integration-observe` runs the sweep a landing owes (trigger `landing`, resting on the observation of the head in the one target that contains it, or on all of their observations when several do, so a later landing on another target is swept too; with the tips it just read); `dag-accept` runs the sweep of the receipt it takes in (trigger `receipt`, resting on the acceptance, against the tip of the pull request's base branch
read through the tip reader); `dag-conflict-sweep` runs one on demand (trigger `manual`, or `landing` or `receipt` with `--node`), against `--target REPOSITORY@REF` or, without one, the base frozen in the manifest of the node's current execution (the manifest of its current relationship and generation, else of its open release; a manifest only stored, such as a prepared correction, is not it; without a base the tips are unmeasured).
A landing or an accepted receipt is swept once: the trigger reference is unique in the ledger (a partial unique index), so a repeat finds the sweep and writes nothing, two writers leave one row, and a sweep that failed before it wrote anything (its answer says `failed`, with the reason) is run again by the repeat of the command. A sweep with no checkout to measure in (`Scheduler.Checkout`, else the `parent_cwd` of a relationship
of the plan that is a git checkout, else the command's `--repository`) is `skipped`; the command it followed is never failed by it. A manual sweep repeats freely and each leaves a ledger row.

A sweep answers with a `state` (`recorded`, `already_swept`, `skipped` or `failed`), its `sweep_seq` and its members. Each member names where the heads it measured came from, `left_head_source` and `right_head_source`: `explicit` (the parent named it), `acceptance` (the head of the node's current accepted result) or `child_checkout` (the child's own checkout); the right side of a head
against a tip is the tip, which has no source.

**Receipt arrival is approximated.** Delivery writes the receipt into the relay's store and the scheduler does not run in that path (`dagsched` imports `delivery`; `delivery` imports nothing of `dagsched`, and a hook there would run git inside the relay daemon, which has no parent checkout). A receipt is measured when the parent takes it in (`dag-accept`) and, for a receipt that is not accepted yet (a correction
round), when the parent runs `dag-conflict-sweep --trigger receipt --node N`, which the crw-run procedure puts at the start of every receipt-resumed turn, after a `git fetch`. A head that the relay can only know from its child's checkout is the child's `HEAD` at the time of the sweep.

## The merge-order constraint

A conflict that two live heads really have, and that no rule both nodes declared settles, is a reason to merge one before the other: the one that lands second refreshes its base after the first has landed, and resolves the conflict there. The reading says which node is which, on what measurement. It is a reading and not a gate: nothing here pauses or
stops a child, changes a node's disposition, reason or detail, or refuses a release, so the children keep running and the parent orders its merges by it. The sibling channel between children is not in this build, so the reading alone records the constraint.

`dag-ready` derives it from stored rows only (no git, no clock, so two readings of one store state are the same): for every pair of nodes that hold their regions, the latest measurement of the pair (the member of the highest sweep that observed or replayed it) gives an observation; a pair with no conflict, or whose every conflicting file is settled by a
rule, has no constraint. A file is settled only when every pair of regions, one of each node, that both cover it is mechanical (`union`, `renumber` or the same `regenerate` command: a mechanical file with a local symbol inside it is not settled). A file one of the nodes did not declare (`local` for it, `exclusive` when the node that did declare it holds that place by a delete, a rename or a hotspot), an observation that named no files (recorded before files were kept) and any local or exclusive pair keep the constraint. A region the declarer states as holding the whole repository (`"exclusive": true`, the exclusive flag of a region) makes a conflict anywhere in it `exclusive` for that node's hold, whether or not the node declared the path; a rename, a delete or a hotspot holds its own place only, so a conflict in a path the node did not declare is `local` for it. Whether a node declared the path is what drift says, and drift stays by path. A node that landed holds no regions, so its constraints are gone; a later clean
measurement of the pair clears it; a replay of conflicting heads after a clean measurement of other heads constrains again, because the ledger and not the age of the observation row says which measurement is the latest.

Which node lands first is the merge lane's own order. A node is in the lane only while its accepted result is the one it would merge (the acceptance stands on the node's current relationship, generation and head event: a correction generation or a newer report of the generation makes it history) and the plan does not hold it so that it cannot merge (the node paused or cancelled, or the plan paused; an archived node's accepted pull request may still land, so it keeps its place). Of those, a node with an open merge turn of its relationship for its accepted head (waiting, holding, merging or unknown) is in the `turn` lane and is ordered by `requested_at` and turn id (decision D-16); an accepted result nothing holds back (the reading says `done:accepted`: not blocked, stale, paused or cancelled) is in the `accepted` lane, by the time it was accepted;
every other node that holds regions (running, reported, verifying, correcting, paused, blocked, stale, paused or cancelled by the plan, in a paused plan, or accepted and out of the lane) is `working`, by the creation time of the earliest relationship of its executions, which a correction or a handover does not move, or, for a node that holds regions before it has a child, the stored time its release was decided. The lanes rank `turn`, `accepted`, `working`, then the time, then the turn id and node id, so the
order is total and the constraints of any number of nodes cannot form a cycle; the later of three that conflict lists the earlier two in landing order. A superseding acceptance moves the time it was accepted and can reverse an order between two readings.

A node in a constraint has a `merge_order` object beside its `release` object, and a plain reading has none: `after` (the nodes that land before it) and `before` (the nodes that land after it), each row with the other node, the `observation_id`, `conflicts`, `files` (at most eight), the worst `grade` (`local`, or `exclusive` when the declarations say so), `drift_nodes`, `unattributed`, `heads_current` (whether the measurement was made at the heads the store holds
now: `yes`, `no`, or `unknown` for a node whose head the store does not hold, which is every node that has not been accepted), and the `lane` and `since` of the other node; `tip`, the latest measurement of the node's own head against a tip when it conflicts (`observation_id`, `tip_sha`, `head`, `head_source`, `heads_current`, `conflicts`, `files`, `drift_nodes`): the base refresh the node needs whatever lands first, unless `heads_current` is `no` (the measured head is not the head the store holds now, and the reason says to measure again); and `reason`, one sentence. The pass counts the constrained pairs in
`order_constraints`; the recorded pass keeps each node's object and the input digest covers it.

The constraint is advisory (decision D-16: merge order stays first in, first out until measured, and an observed conflict is the measured exception). The relay does not hold a merge back for it: the parent does (see [Release by region grade](../../plugins/crw/skills/crw-run/references/region-grades.md)). A conflict nobody measured is not seen: without a sweep there is no constraint.

## A node’s stagnation counter and the repair ladder

A node that keeps failing the same way is counted, and the repair that comes next is named. The reading is derived from rows the store already keeps and adds no writer for them, so the count clears by itself once the cause is repaired, exactly as invalidation does. It reads no clock, writes nothing and refuses nothing: two readings of one store state return the same object.

The counter has two causes, and the reading names the one whose run is longer:

| Cause | Read from | Meaning |
| --- | --- | --- |
| `repeated_finding` | the node’s correction generations (`dag_node_executions`, kind `correction`) with the finding of the `needs_changes` ruling that opened each | consecutive corrections carried the same findings |
| `repeated_check_failure` | the node’s merge-check history (`dag_merge_checks`, the failed required checks of each judgement) on the head the acceptance stands on now | distinct failed attempts of the same required checks, again after the merge lane’s one retry and again after a fresh acceptance |

A correction generation’s **finding identity** is the canonical-JSON sha256 of the ruling’s `verdict_context.findings` entries that are **not** the restoration block, each entry as the relay stored it. The restoration entry is excluded because its note carries this generation’s manifest digest, which differs every round; that is why the identity is taken over the remaining entries rather than over the whole text. Two corrections of one node share an identity exactly when the ruling carried the same findings. The ruling that opened a generation is the one on the generation it follows, and the generation it follows is the nearest one below it that was not **withdrawn** (`store.LiveGenerationBefore`, the lookup `dag-correct` itself makes): a withdrawn generation is neither counted nor a break, so a correction opened around a withdrawn one still finds its ruling and continues the run. A generation the coordinator opened by hand has no ruling and no findings at all ([Three ways to open the generation](#corrections)), and a correction whose ruling carried no findings reads the same way: neither carries an identity, so both break the run and raise no `repeated_finding` count.

The reading reads its correction rows to the end and closes them **before** it looks up the ruling and the live generation below it. The store has one connection and `dag-release` reads this reading outside a transaction, so a query issued while those rows were still open would wait for the connection they hold until the context deadline, and one node with a correction generation would stop every release of its plan.

A repeated check failure is a run of the newest merge-check rows that all failed the same non-empty set of required checks: the same failure seen again after the retry, and again after a head is accepted a second time. The **failed check names** are the failure’s identity, and a **failed attempt** is the (name, run, attempt) of every failed required check of one judgement; the count is the number of **distinct attempts**, not the number of rows. So the same attempt observed again — the writer appends a row when the evidence digest changes (an optional check’s result), or the merge lane copies the eviction onto a fresh acceptance of the same head — counts **once**. A `checks_pending` row is neither counted nor a break: it is a re-run in progress, and the run continues through it however many of them sit between two failures. A row that failed nothing, or failed another set of names, ends the run. The `round_no` is carried in the history but is not the identity: a head accepted again restarts the round without restarting the failure. A check failure has no finding text.

What counts is the node as it stands now. An **acceptance is the repair**: the correction generations before the accepted one are the history of a result that was already repaired, and the check rows of a head other than the one the active acceptance **stands on now** are another head’s history, so neither is counted. The head a node stands on is the one its acceptance stands on after any recorded base refresh (`standOf`): a record moves it, the head it stood on before the record becomes that head’s history, and the rows of the head it stands on are gathered from **every** acceptance of the node, whatever the acceptance’s state — the checks ran on the commit, so a head accepted again keeps the failures an earlier acceptance of the same head recorded. A node with no active acceptance counts every correction generation it has, and reads no repeated check failure at all: it has no head it stands on, and a check row is evidence about the commit it ran on.

The rungs are closed, and the count names one of them:

| Count | Rung | What the parent does |
| --- | --- | --- |
| 1 | `retry_same_packet` | rerun the node as it was released (`dag-release`) |
| 2 | `edit_packet` | correct the node’s inputs and instructions (`dag-correct`) |
| 3 | `split_node` | a plan revision with `replace_node` |
| 4 | `neighbour_repair` | a plan revision with `replace_node` for the sibling it keeps conflicting with |
| 5 and above | `full_replan` | a plan revision |

The threshold is 2: one correction is not repetition, and the object appears once the same finding has been carried by two consecutive corrections of the node, so it is absent from a reading of a plan nobody has corrected twice. A count past the last rung keeps naming `full_replan`, and the reading names no further rung.

**What the reading says.** A node whose count has reached the threshold carries a `stagnation` object beside its `release` and `merge_order` objects: `node_id`, `count`, `cause`, `rung`, `next` (the rung the ladder names after this one, null at `full_replan`), `finding_digest` (null for a repeated check failure) and `last_event_id` (the event the newest counted row belongs to). The pass counts the nodes that carry an object in `pass.stagnation`, one key per rung (`retry_same_packet`, `edit_packet`, `split_node`, `neighbour_repair`, `full_replan`), each zero when nothing stagnates. The input digest covers the object and the counts, so a stagnating node is a changed world.

The object is advisory, like the merge-order constraint: the reading names a rung and stops there. Nothing is refused and nothing is written, because a reading that mutated the ladder would make two `dag-ready` calls differ. A later issue that wants the last rung refused would add that refusal where the triggering command runs, reusing the existing `disposition_conflict`. A node that landed reads no object whatever the rows say: it is never run again (E-20).

## Measurements

`crw relay dag-measurements --plan P` reads the measurements of a plan from the store (CRW-411): one query, no write and no clock. It is there for the comparison of DAG runs and for a parent that wants to see what its optimism cost. Every measure prints `samples` (the rows it rests on) and either its values or an `absent` reason; a measure with no data prints no value at all and never a zero. A zero that is printed is a count over rows that exist (a landing that was judged and never found behind the base has zero stale-base judgements; a grade at which no measured pull request conflicted has zero pull requests). The reasons are a closed set: `no_recorded_pass`, `no_landings`, `no_observations` (landings or pull requests exist and nothing measured the thing), `not_recorded` (the store keeps no record of it in this build), `none_recorded` (the parent has recorded no statement of the kind) and `table_missing` (a store whose zone predates the table that holds it).

| Measure | Read from | Values | Absent |
| --- | --- | --- | --- |
| `parallelism` | the passes kept with `dag-ready --record` (`dag_passes`) | `held_slots` and `free_slots` of the latest pass with the largest held, the smallest free and the means, `ceiling_latest`, and `limited_by`: how many passes each limit decided (`host_memory` appears once the host memory bound has cut a pass) | `no_recorded_pass` |
| `conflicts_by_grade` | the observations of two heads and of a head against a tip, with their files, graded by the declarations as they are when the query runs | `by_grade.mechanical`, `local`, `exclusive`: `prs` (pull requests that conflicted at the grade), `files` and `files_per_pr` (null when no pull request conflicted at it); `against_tip` the same without a grade; `unattributed_observations` (a conflict that names no file); `hunks`. `samples` is the pull requests an observation measured (a sweep member, or an observation row recorded before sweeps kept a ledger) | `no_observations`, `table_missing`; `hunks` is always absent, `not_recorded`: an observation keeps the names and the number of the files git could not merge |
| `conflict_handling` | the landings that have conflict handling seconds ([Release policy](#release-policy)) | `median_seconds`, `mean_seconds`, `max_seconds` | `no_landings`, `no_observations` |
| `base_refresh` | `dag_merge_checks` and `dag_node_executions` | `stale_base_judgements`: the merge judgements that found the base moved, per landed node that was judged (`total`, `mean_per_landing`, `max`); `returns_to_child`: the correction generations `dag-correct` recorded, per landed node; `round_trips` | each under `no_landings` or `no_observations` (no landed node was judged); `round_trips` is always absent, `not_recorded` |
| `post_merge` | the results the parent recorded ([Results the parent records](#results-the-parent-records)) | `with_a_result`, `dev_green`, `dev_red`, `reverted`, as landed nodes; `samples` is the landings | `no_landings`, `none_recorded` (no landing has a result), `table_missing` |
| `duplicated_or_discarded` | the same results | `duplicate_nodes` and `discarded_nodes`: distinct nodes with a statement of the kind | `none_recorded`, `table_missing` |
| `cancelled_after_release` | the plan and `dag_node_executions` | `nodes`: the nodes the plan cancelled after a child was created for them; `samples` is the nodes of the plan | never: a plan always has its own record |

The answer also lists the landings it read (the latest 64): `node_id`, `landed_at`, `conflict_handling_seconds`, `stale_base_judgements` (null for a node that was never judged), `returns_to_child` and the `results` recorded. What each measure does not say: a stale-base judgement is a judgement, not a round trip (a parent that refreshes the base itself records none, and a repeat with other evidence records another), and a return to the child has any reason, a review finding included, because the store records neither why a node was sent back nor when a parent's own refresh began and ended; the parallelism is that of the recorded passes, not of the children running between them; an observation of two heads is graded as a whole (the worst grade over its files, and a conflict every file of which a rule settles is mechanical) and each of its files counts at that grade for both nodes; duplicated and discarded work is what the parent stated, and the nodes the plan cancelled after a child existed are counted apart because a cancel does not say that a pull request was discarded.

## Cap basis

`crw relay dag-cap-basis-record --limit L --revision R --w-minutes W --w-source S --s-minutes S --s-source S --actor A` records the evidence a runs ceiling above the standing cap of 6 rests on. The reading honours such a
ceiling only for a limit revision that has a row here, and clamps it to 6 otherwise. The value of a ceiling is decision D-05, which is not made: this writes evidence and raises nothing. Only the task that declared the limit or the

## The coordinator epoch

A plan is driven by one parent session at a time, and a parent is replaced: by a new session of the same task (a restart, or a context that lost its picture), or by another task that took the project over. The epoch is how the store tells the session that holds a plan from one that used to. It is a fence for DAG commands and nothing more: it does not make the path from a release to a landing exactly-once, and no existing command (`verdict`, `assignment-mark`, `managed-start`, `merge-turn-*`) gains an epoch (decision D-07).

**Claim.** `dag-coordinator-claim --plan P --actor A --session-nonce N [--project K]` raises the plan's epoch to the next number (one above the newest claim, 1 for the first) in one transaction and answers it. The actor must hold the live parent binding of the plan's project (a binding that is active or paused and was not replaced: `scope_role_mismatch` otherwise). The row records the epoch, the binding and its revision, the task, the session nonce and the time. The nonce names the session once and is never reused: the same call again while it is still the newest claim answers the same epoch and the same replaced claim (`replayed: true`, `previous_epoch` and `previous_task_id` as the first answer gave them); the nonce of a session that was replaced, or one another task used, is `stale_coordinator_epoch`, so a replaced session cannot take the plan back by repeating itself. A plan that has no revision yet has no header and so no project: the first claim names it with `--project`, and from then on the plan's project is the one that claim was made under (a claim naming another project is `malformed_receipt`, so a parent of another project cannot take the plan over before its first revision, and a replacement parent claims without naming it). A session claims before its first decision and keeps the epoch the claim answered: it sends it with every command that decides. A session that reads the newest epoch from the store and sends that has not claimed, and the fence cannot tell it from the holder (the contract's fence has no nonce); keeping the claim's answer is the session's discipline.

**Fence.** The commands that decide name the epoch they hold (`--expect-epoch E`; in a revision document `coordinator_epoch`) and check it as the first statement of the transaction that writes, before any replay is recognised, so a stale session is told nothing about what the plan holds and writes no decision (the early form of `dag-plan-put` runs the same check before it judges the revision, so a stale session hears `stale_coordinator_epoch` from it too, not `plan_revision_conflict` or a plan rejection; a request that names an epoch when there is no store has no claim to stand on and is refused the same way, and creates no store; no row of any table the fence guards, no managed start, no slot, no merge turn, no child: they are as they were). The one thing a refused release may still do is the housekeeping it always did: a release that froze an oversized manifest copy before it was refused takes the unreferenced copy back and journals that. A plan with a claim is fenced strictly: the epoch must be the newest, the claim must be the actor's, and the parent binding it was made under must still be a live parent binding of the plan's project. A plan nobody has claimed is unfenced, as every plan was before the fence existed: a write that names no epoch passes, and one that names an epoch is refused. The first claim fences a plan from then on; the rows a plan has before it carry epoch 0. Every refusal is `stale_coordinator_epoch` (exit 2), whichever of the three conditions failed, and its detail says which.

The checks sit at the head of: `dag-plan-put`, `dag-release` (before any replay, and again in the transactions that write the intent, replay it and bind the child, and in the one that appends the stale_head row of a pinned predecessor whose pull request moved) and `dag-release-close` (closing an abandoned release lets the node be released again, so it is a decision), `dag-accept`, `dag-decision-record`, `dag-integration-observe` (the only writer of an observation, and so of the withdrawal of a landing: a later negative observation), `dag-correct` (the preparation checks before it reads or builds anything and again in the one transaction that stores the manifest; the file it then keeps under the child's artifact root is inert until a ruling names its manifest, which only the fenced recording can bind), `dag-region-declare`, `dag-merge-judge`, `dag-merge-request`, `dag-adopt` and, for a project limit, `dag-cap-basis-record`. A basis belongs to a limit and has no plan, so the recorder names the plan it coordinates (`--plan`, which must be a plan of that project) and the fence runs for that plan. Once any claim was made under a parent binding of the project (the claim of a plan that has no revision yet counts, and so does a claim whose binding was replaced since), a basis without a plan, or for a plan that has no claim of its own, is `stale_coordinator_epoch`: an unclaimed second plan is no way round the fence. A limit of a wider scope is declared by a supervisor, who coordinates no plan: it takes no plan and is not fenced.

The rows a decision leaves carry the epoch of the session that decided it (the release, the acceptance, the decision, the revision and the manifest body), so a plan's rows show who decided what. The epoch stays out of every digest except the request digest of a revision: a request id sent again under another epoch is `plan_revision_conflict`, so a restarted parent reads the log and does not resend. Rows written before the first claim keep epoch 0.

**What it does not do.** A read is not fenced: a new parent reads before it claims. `dag-ready --record`, `dag-conflict-observe` and `dag-conflict-sweep` record measurements and decide nothing. The summary queue's writers (`dag-summary-enqueue`, `dag-summary-claim`, `dag-summary-complete`, `dag-summary-fail` and `dag-summary-retry`) decide nothing either: a summary states the store's current progress, and the claim token, not the epoch, fences a replaced session's confirmation ([DAG summary outbox](dag-outbox.md)). A write that started before the first claim lands is ordered by the store's write lock: the claim first and the unfenced write is refused at its fence, or the write first and it commits at epoch 0. A release that is cut by a claim between its intent and its bind leaves an admitted child unbound, and a new session of the same task replays it and binds it.

## Restart and adoption

Nothing is resident, so a restart loses nothing: the plan, the releases, the executions, the acceptances and the merge records are in the store, and `dag-ready --plan P` answers what may start from the store alone. `dag-restart --plan P --actor A` is the picture a parent that starts again needs first. It reads, writes nothing and reads no clock: the same store gives the same answer, and a lease, a heartbeat or a deadline that ran out never makes an owned node ready again or reassigns it. For the newest claim it says whether the actor holds it, and for every node somebody owns what to do:

| Resume | Meaning |
| --- | --- |
| `adopt` | a live child whose relationship this actor holds: release nothing, carry on |
| `adopt_needed` | the node's relationship was replaced by one this actor holds, for the same child: run `dag-adopt` |
| `reconcile` | an effect whose outcome is not known (a creation whose response was lost, a release started and not bound, a merge turn whose effect is unknown): resolve it by replaying the same request (`dag-release` reads the host's record of the creation before it creates anything, and observes the App Server when that record says the outcome is unknown) or by observation (`dag-integration-observe`), never by doing it again. A merge turn whose effect is unknown is `reconcile` for the parent of the accepted result's relationship, the only one that can observe; for another parent it is `needs_operator` |
| `needs_operator` | nothing in this build moves it on, and the detail says why |
| `none` | nothing is outstanding (a node with an acceptance: the acceptance is the node's value and belongs to no session) |

A managed start that was released before it created a child is `needs_operator` first (the reading derives it as releasing). A node whose relationship was replaced is judged before its derived state, which reads the replaced relationship as closed.

**Adoption.** After a replacement the new parent has registered the child under a new relationship with the old one superseded and has taken the project over (the relay's own commands), and the node's executions still stand on the old relationship, which is archived. `dag-adopt --plan P --node N --actor A --expect-epoch E` binds the successor to the node as an execution of kind `parent_handover` with the manifest the child was released under. The successor is resolved and validated on every call, a replay included: live (active or paused, not replaced), the same issue, the same child, held by the actor. Its relay state word must be one of a child that is working on, or reporting, the result (a paused successor is adopted and nothing proceeds until it is resumed). Nothing is created, no generation is opened, nothing is reserved, and a node that has an acceptance is refused. The slot stays held under the task it was reserved for. `dag-accept` of a non_pr node and `dag-integration-observe` of an implementation node return it, as that task, when the node's current parent calls: only when the slot is held for the plan's project and its holder is the parent of a relationship in this node's own execution chain (any other holder is refused as before), with no reservation, so a lowered ceiling or a blocking measurement cannot refuse it. The slot then reads as released by the former parent; the reason (`dag_accepted`, `dag_integrated`) is unchanged.

What each kind of restart recovers:

| Restart | Recovered |
| --- | --- |
| a new session of the same parent task | every boundary: before the intent, after the intent, the creation response lost, started and not bound, bound, the result stored, the ruling stored, accepted. One child and one release row per node; the pending effect is reconciled by replaying the same request; results and rulings stored before the crash are used. `dag-restart` says `reconcile` up to the bind, `adopt` from the bind to the ruling and `none` once accepted |
| a replacement parent task | a bound child whose result is not accepted, by `dag-adopt`. The previous parent's writes are refused |
| a replacement parent task | not recovered, and said so (`needs_operator`, no child created): a release that never bound its child (the managed start is frozen under the previous parent), a result accepted and not landed (its merge turn and merged mark belong to the previous parent), and results stored under the replaced relationship (the child reports under the successor) |

An unknown merge turn stays unknown until the head is observed; the merge lane answers the holder's repeated request with the turn it already has or refuses it, and no second turn exists. Elapsed time is not an observation.

## Bundle candidates (CRW-810)

`dag-bundle-candidates --plan P [--exclude N]...` answers which nodes of the head revision a parent could bundle into one issue. It reads the stored plan and the release records and writes nothing. `dag-ready` carries the same reading, with no exclusions, as `bundleCandidates` (the `bundles` and `excluded` lists). The candidates are read in the same transaction as the ready reading, and with `--record` in the transaction that keeps the pass, so the pass and `bundleCandidates` describe one plan revision and one set of releases.

The candidates are the live implementation nodes with no `dag_releases` and no `dag_release_requests` row for the plan. Every other live node is listed in `excluded` with one reason:

- `non_pr`: the node opens no pull request.
- `released`: a release or a managed start is on record.
- `parent_excluded`: named by `--exclude`. The plan carries no urgency or security mark, so the parent passes such a node here. A name the plan does not hold is an argument error (exit 4).
- `other_plan_exclusive`: a node of another plan that is live and not integrated holds the same repository and path exclusively, by the exclusive flag or the `exclusive` grade of its latest declaration. The holder's node kind does not matter: a node that declared regions and was later made a `non_pr` node by `update_node` keeps its declaration and its hold.

Two candidates are joined by one of two rules, and a pair that meets both carries both reasons:

- `same_region`: their latest declarations name the same file, or two files in one directory other than the repository root. A mechanical region does not count, because its rule settles it.
- `chain_slice`: the plan has an edge A→B where B has no other incoming edge and A has no other outgoing edge.

A bundle is a connected group of two or more candidates (cut as the `regions` paragraph below says when its union would be too large to declare). It reports its `nodes`, the `reasons` and `pairs` that join them, the union of the members' regions, and `internalEdges`, the edges whose both ends lie in the group. Every list is sorted, so one store state gives one answer.

The `regions` of a bundle hold one entry for each place (repository, path, kind, key), in the shape `dag-region-declare` reads, so a parent can pass the list to it unchanged whenever it is not empty. A bundle is offered only when its union holds at most 64 places (`MaxRegions`, what one declaration takes). The list is empty when none of the members declared a region (two undeclared nodes joined by `chain_slice` are still a bundle): a declaration takes 1 to 64 places and refuses none, so there is nothing to pass on, and the merged node declares the places it edits. A bundle in which some members declared holds exactly their places. A connected group whose union would hold more is cut into groups that each fit: a group starts at the smallest node id not yet placed and takes, one at a time, the smallest unplaced node joined to it by a pair, while the union still fits; a node that fits no group of two or more stays a candidate outside any bundle with its own declaration. No place is dropped from a union to make it fit. Members that declare one place differently are merged so that the entry never holds the place less strictly than any member did:

- `exclusive` is true when any member stated it.
- `change` is the strictest of `edit`, `rename`, `delete`, in that order.
- `grade` is the strictest of `mechanical`, `local`, `independent`, `exclusive`, in that order. Two `mechanical` grades keep their `rule` when it is the same one and become `local` when the rules differ, and a rule is kept only on a `mechanical` grade.
- The result is then folded the way a declaration is: a stated whole-repository hold, a rename, a delete, a hotspot and a shared contract surface hold the place `exclusive` whatever the members said.

The merge is the same whichever member declared which, so one store state gives one answer.

The reading merges nothing. Merging nodes is a plan revision the parent writes.

## The store

The scheduler adds tables to the DAG zone ([DAG plans](dag-plans.md#the-store)) as appended statements. `dag_passes` and `dag_node_regions` are described above; `dag_release_requests` freezes the request of a release with its intent; `dag_release_recoveries` holds the closure of an abandoned release and the successor release of a closed one (see Recovering an abandoned release);
`dag_tip_conflict_observations` (with `dag_tip_conflict_observation_files`) holds the same for one node's head against a tip, which `dag_conflict_observations` cannot, because a tip is not a node; `dag_conflict_drift` the nodes whose declarations did not cover a conflicting path; `dag_conflict_sweeps` (with its partial unique index `dag_conflict_sweeps_trigger`) the ledger of sweeps and `dag_conflict_sweep_members` what each measured (see [Conflict observations](#conflict-observations));
`dag_conflict_observations` holds the merge-tree conflict counts of parallel branches and `dag_conflict_observation_files` the files they could not merge, by repository name; `dag_node_region_grades` holds the grade and rule of each declared region and `dag_node_region_holds` whether the declarer stated a hold of the whole repository on it (both are side tables of `dag_node_regions`, because a shipped statement is never edited); `dag_base_refreshes` holds the base refreshes of accepted nodes ([A base refresh of an accepted node](#a-base-refresh-of-an-accepted-node)); `dag_generation_withdrawals` holds the generations withdrawn by hand ([A generation opened by hand and never sent](#a-generation-opened-by-hand-and-never-sent)); `dag_merge_checks`, `dag_acceptance_revalidations` and `dag_acceptance_forge` hold what the relay observed of an accepted pull request, re-verification of an accepted
output under new criteria, and the forge identity of an accepted implementation node. `dag_summary_outbox` is the queue of the project's Linear summaries (see [DAG summary outbox](dag-outbox.md)). `dag_release_policy` is the ledger of a plan's release policy, `dag_landing_results` the statements the parent records about landed, duplicated and discarded work, and `dag_pass_release_policy` the policy state a recorded pass saw (see [Release policy](#release-policy)); all three are side tables appended to the zone. `dag_pass_host_memory` is the host memory bound a recorded pass saw ([Host memory](#host-memory)), appended the same way.

## How the acceptance path is verified

The tests drive the real Go store, the real managed engine and bridge adapter over a fake App Server, a real git repository, the relay's own verdict writer and renderer, and the merge lane's own check and landing.
Two things are scripted and say so: the forge (a pull request's head, base and checks are what the test scripts, since no forge is reachable), and the child's report. The rows of a verified report (the final event, its
lineage, the acknowledgement and its evidence, the ruling and its context, the registered criteria) are written by a test helper in the shape the intake, acknowledgement and verdict writers give them; the verdict
writer itself is exercised for corrections (`needs_changes`, the generation it opens, the revision request the child receives and its rendering) and for a ruling accepted afterwards. The whole path from a child's
completion receipt through delivery and acknowledgement to a ruling is therefore not run end to end here; it is the relay's existing, separately tested path, and a real-model run of it is part of the installed
proof (M4). A forged `completed` (a report that was only staged, never acknowledged, never ruled, ruled for another head, or whose criteria moved) opens no edge: each link of P-AV-1 has a case that breaks only that link.

The pause, resume, cancel and archive of a node or a plan is covered the same way (`lifecycle_test.go`): revisions written as an operator writes them, the real store and scheduler, and the real merge lane over a real git
repository for the landing commands. The guards that sit inside a transaction are tested with the pause landing between the command's unlocked read and its transaction, from a test seam, and each case checks that the
seam fired. What is not run is a real child: a paused node's child is a seeded report, not a live Codex task.

## Departures from the contract

Where the code reads the contract differently, or adds to it, and why:

* Contract 7.2 names hotspots, renames and deletes as exclusive; CRW-431 reads that as exclusive at their own place and not across the repository, with a hold of the whole repository only where the declarer states it ([Edit regions](#edit-regions); the existing declarations are read as [that section](#declarations-made-before-holds-were-narrowed) says). It names an unknown declaration as overlapping everything, and the grades (independent, mechanical, local, exclusive), the release rule and the list of shared contract surfaces are added to it by the active parallel release design, in which a region is a signal for the merge order and not a gate. A pass that records the rule needs no new column: it rides in the node dispositions of `dag_passes`.
* Contract 7.2 names the `edit_regions` tables for regions; those are two-project agreements keyed by base revision with no unknown or hotspot rule, so per-node declarations have their own table and reuse only the place vocabulary.
* The managed request id of a release is derived from the plan, the node and the manifest digest (contract 2.6 names the node and the digest): node ids are plan-local and request ids are global to the store. Every predicate carries the plan id, which the contract's SQL predates. The acceptance digest includes the plan id too: acceptance ids are a store-wide key and node ids are plan-local.
* The reading's vocabulary adds `blocked:release_abandoned`, `blocked:evicted` (D-12) and `blocked:stale_predecessor`; `blocked:stale_epoch` is not emitted (the fence refuses writes, a read is not fenced). A `blocked_needs_input` receipt reads as `blocked:input_unverified_at_consumption` (B-15).
* No new refusal reason: an unmet ready predicate reads `disposition_conflict` with the closed reason in the detail, tamper `revision_mismatch`, missing or altered inputs `manifest_unverified` and `scope_escape`, a stale head `merge_candidate_moved`, stale criteria `criteria_set_changed`.
* A node's pause, resume, cancel and archive and the plan's pause and resume are revision changes (CRW-281, see [DAG plans](dag-plans.md#where-this-page-reads-the-contract)); the relay's relationship status
  is a separate fact the reading honours as before. There is no plan-level cancel or archive: the contract names none.
* Archive has no row in the contract's transition table. A node the plan archived is read as the archived relationship is where the code already had a rule (its accepted pull request may still land and be observed) and as a
  cancelled node where the contract has a rule for cancel (it is never released and what follows it is blocked, as `blocked:predecessor_archived`).
* Contract 7.4 keeps an acceptance across a pause and blocks the node's new acceptance. Here the edges a pre-pause acceptance satisfied stay satisfied (an edge is not held by its predecessor's pause), and a result that arrives
  after the pause is not accepted until the resume, so what it would release stays closed.
* The contract's cancel row blocks the edges that leave a cancelled node. The reading also follows what an accepted node consumed, so a node accepted on the result of a node the plan ended does not release its successors; an
  integrated input is the exception, and no acceptance is revoked.
* P-DEC-1 reads the plan's project scope; the decision subject stays opaque and a directive satisfies an edge only when its digest equals the edge's (D-09).
* B-13 is evaluated on `dag_merge_checks` rows, which keep the evidence body; `dag_acceptances.evidence_digest` excludes its body (contract 4.3) and cannot be recomputed.
* `defer:merge_window` is emitted for a target whose merge turn is in a state that can move the tip (merging, unknown), not for a waiting or holding turn; `defer:ownership_unverified` is a project without exactly one registered parent.
* E-11 against the shipped one-row-per-output index: the same output ruled again under re-registered criteria is a row of `dag_acceptance_revalidations`, not a second acceptance.
* After a close, the release of the same manifest takes a request id derived from the closed request (`RecoveryRequestID`): contract 2.6 names the node and the digest only, and the engine refuses a released request id for good.
* A release freezes its exact request bytes (`dag_release_requests`): the managed engine fingerprints the whole request, so a replay must send the same bytes.
* `stale_base` means the base tip is not contained in the head (strict ruleset, D-11), not that the pull request's own base field differs; contract E-27 only requires `merge_currency_stale` against the new tip.
* Coordinator epoch (contract 6): the fence reads a live parent binding as `status IN ('active','paused') AND superseded_by IS NULL`, as the rest of the relay does, not as `status = 'active'` (a paused binding is not a stale epoch). A plan nobody has claimed is unfenced, so plans written before the fence, and the callers that rely on them, keep working; the first claim fences the plan, and claiming before the first decision is the parent's duty. The cap basis has no plan: it is fenced through the plan its recorder names. The epoch is also written into the manifest body (outside its digest). No zone statement is appended: `dag_coordinator_claims`, the epoch columns and the `parent_handover` kind were already shipped.
* Corrections: the manifest of a correction is prepared before the ruling and travels as a line of the ruling's restoration finding, because the verdict writer opens the generation and sends the message in one transaction.
* An unknown edit region overlaps everything; a node that edits no repository (`non_pr`) never conflicts.
* The reading adds the disposition and state `stale` with the reasons `stale:slice_changed`, `stale:criteria_changed` and `stale:edge:<edge_id>` (contract 3.1 `stale:<seed>`), and an artifact edge, or an integrated edge a landing satisfies, from a stale result reads `blocked:stale_predecessor`; the merge judgement refuses a stale result with the existing `disposition_conflict`. No refusal reason, outcome or zone statement is added. Contract 4.2 lists the landed commit among the consumed values: the integrated predicate takes the earliest positive observation of the containment run, so a manifest names a stable landing, and a landed commit that an observation of the same run names is read as unchanged ([Invalidation](#invalidation)).
* The stale reading carries a route, `action` and `action_detail` (`revalidate`, `correct`, `hold`, `redefine`), which the contract leaves to the parent. Decision D-08 is read from contract 5: a correction is a new generation of the same relationship and a node redefinition a new relationship with `supersedes`; the scheduler never registers the second. No refusal reason, reading reason, outcome or zone statement is added: a revalidation of a node that is not stale for its criteria alone, and a correction of a node that landed, are refused with `disposition_conflict`.
* Contract 3.2 and E-19 send a correction to the same child through the existing path. That path opens a generation with a `needs_changes` ruling, and the relay's verdict writer takes a second ruling on a head it ruled `verified` only while a review is open or, for `needs_changes`, before the plan accepted it, and refuses it with `disposition_conflict` otherwise. For a stale accepted node whose criteria did not change the generation is opened by hand with the relay's `generation-open` and `generation-bind` (documented for the coordinator in `crw-run`), and `dag-correct` binds it to the prepared manifest under the conditions of [Three ways to open the generation](#three-ways-to-open-the-generation). No refusal reason, zone statement or table is added: the dispatch request id is kept in the existing nullable `managed_request_id` column of `dag_node_executions`.
* A result the plan accepted and that is still current, with a blocking defect found in it before it lands, is corrected the same way and not by a new route: the generation is opened by hand under a reason that states the correction (`accepted_result_correction`, or the `needs_changes_revision` default), and `dag-correct --manifest-digest` records it under the checks the stale case has ([Correcting a result that was accepted and is still current](#correcting-a-result-that-was-accepted-and-is-still-current)). The reason the generation carries is what notes the route, so no column, table, schema, refusal reason, reading reason, CLI flag or `specs.json` entry is added; the acceptance stays active until `dag-accept --supersedes` takes the new result. The contract's 3.2 and E-19 speak of a stale result; this case is the contract's silence on a defect found after the acceptance, and the parent's answer to it is recorded here.

* Contract 3.2 and E-10 read the pull request head against `dag_acceptances.head_sha`. A node whose acceptance stands on a recorded base refresh ([A base refresh of an accepted node](#a-base-refresh-of-an-accepted-node)) is read against the head that record names, because the lane's own check wants the head the newest generation's report names, which is that head; an unrecorded head, or a head no record can be made for, is E-10 as written. `dag_merge_checks.head_sha` holds the head the acceptance stood on when the check was made, which is the accepted head unless a record moved it. No refusal reason, outcome or zone statement is added.
* The conflict sweep (CRW-410) and the merge-order constraint are not in the contract. Contract 7.2 says an observed conflict is the measured exception to a first in, first out merge order (D-16); the sweep, the ledger, the drift and the constraint are how this build measures that exception and says it. The constraint is advisory: the merge lane's own order and its checks are unchanged, and nothing refuses a merge for it.
* Receipt arrival is approximated: the sweep of a receipt runs when the parent takes it in (`dag-accept`) or when it asks for it (`dag-conflict-sweep --trigger receipt`), not where delivery writes the receipt ([The sweep](#the-sweep)).
* No new refusal reason and no new reading reason: a sweep refuses with `malformed_receipt`, `scope_role_mismatch`, `unregistered_scope`, `disposition_conflict` and `merge_target_unreadable`, and a constraint is an object of the reading, not a reason. Five tables and one index are appended to the zone; the zone’s route through the swap gate is the same as for the region grades (`EXTENDS_ZONE`, with `--backup-state-to`).
* A node’s stagnation counter and the repair ladder (CRW-801) are not in the contract either: contract 7.1 closes the reasons and the reading adds none. The count and the rung are an object of the reading, derived from `dag_node_executions`, `dag_merge_checks` and `dag_acceptance_revalidations`, with no writer, no refusal and no zone statement. Contract 4.1 says a digest is taken over the canonical JSON of what it covers: the finding identity is the sha256 of the ruling’s findings minus the restoration entry, whose note carries this generation’s manifest digest and differs every round.

* Contract 7.2 holds a node's regions from release until its head lands and says a declaration is made before the release. A node that holds them may now declare again to narrow them, when its head is not accepted yet ([Narrowing a held declaration](#narrowing-a-held-declaration)): the contract's purpose, that another node is not released onto a place the holder still edits, is kept, because a narrowing frees only what the holder no longer holds and never holds a place less strictly. The refusal of a widening is the existing `disposition_conflict`.
* The release policy and the measurements (CRW-411) are not in the contract. Contract 7.3 says a ceiling is lowered by observation and raised only slowly after clean merges, and 8.6 lists what to measure before an evaluation; the policy is the observation applied to local-optimistic release (it never touches the ceiling, which stays 6 unless a cap basis says otherwise: decision D-05 is not made), and the measurements are those of 8.6 that this build can read from the store. Post-merge dev red, revert, duplicated and discarded work are the parent's statements (`dag_landing_results`); hunks and base refresh round trips are absent because the store does not record them.
* No new refusal reason and no new reading reason: the policy hold reads `defer:edit_overlap` with `held_by_policy` in the `release` object, a widening is `disposition_conflict`, and the three commands refuse with `malformed_receipt`, `scope_role_mismatch`, `unregistered_scope`, `disposition_conflict` and `stale_coordinator_epoch`. Three side tables are appended to the zone (`dag_release_policy`, `dag_landing_results`, `dag_pass_release_policy`), through the same route of the swap gate as the region grades (`EXTENDS_ZONE`, with `--backup-state-to`); no shipped statement is edited.
* The host memory bound (CRW-468) is not in the contract. Contract 7.3 lowers a ceiling by observation and 7.1 attributes every idle slot with a ready node to a `defer:*` reason; the bound is that observation for memory: the reading reason `defer:host_memory`, the limit `host_memory`, one side table appended to the zone (`dag_pass_host_memory`: `EXTENDS_ZONE` through the swap gate, like the other side tables) and the verdict in the reading's `pass`. No new refusal reason: a release held by the host is `capacity_exhausted`. Only `dag-ready` and `dag-release` carry the bound; `dag-restart` calls the same reading and `dag-progress` projects it, and neither carries one, so what they answer is still a function of the store.

* A generation opened by hand and never sent (CRW-446) is closed by `dag-generation-withdraw`, a command the contract does not name: contract 3.2 has no row for a node whose relationship stands on a generation that holds nothing.
