# CRW-1152 — doctor harness: one unreadable record loses the report, a FIFO stops it, and declared types are not checked

Source: CXC v0.2.40 (commit 3c1459ac). Oracle files: `plugins/codexclaw/components/cxc-ops/src/doctor.ts`
(`checkPabcdHealth` :166-181, the inline skills and agents checks :291-323, `runInstalledRootCheck` :401-445,
`manifestTargetChecks` :228-254), `plugins/codexclaw/components/cxc-ops/src/manifest-targets.ts` (`readJson` :76-83 and the
hooks and mcpServers walks) and `plugins/codexclaw/components/cxc-ops/src/hook-trust.ts` (`identityHash` :96-139,
`listHookEntries` :162-216). Go files of the port: `internal/runtime/doctor/harness_install.go`, `harness_run.go`,
`harness_bounded.go` (the bounded reader and the step guard), `rooted_read.go`, `hooktrust_entries.go`,
`hooktrust_identity.go`, `manifest_targets.go`, `harness_drift.go` and `hooktrust_config.go`. The byte and depth bounds are limited to
the harness path (`crw doctor harness`): the readers `crw doctor retrust` shares (`ListHookTrustEntries`,
`ReadInstalledPluginKeys`, `DiagnoseHookTrust`, the plugin discovery and key resolution) still read a manifest, a hook
document and `config.toml` of any size, and only refuse what is not a regular file instead of waiting on it; the default
`crw doctor` JSON and exit contract are not touched. Found by the 10-10 CXC
improvement review (A7-06, P2 confirmed).

## Defects

- `checkPabcdHealth` reads the sessions directory with `readdirSync` outside its catch, the inline skills and agents checks do
  the same, and `runInstalledRootCheck` reads the home outside its try; a failure there aborts `runDoctor`, so one directory
  permission problem loses every check (`crw doctor harness --json` on an unreadable `.crw/sessions`: exit 1, stdout empty,
  the earlier checks not reported) (source `doctor.ts:166-181`, `:291-323`, `:402`); port: fixed (each of those three checks
  answers a WARN that names the failure and says the check was skipped, in Node's error shape, and the report carries every
  independent check; every step of `RunHarnessDoctor` also runs under `harnessRunGuard`, which turns any panic into one WARN
  named after the step, so a future check cannot lose the report. The CLI boundary's catch stays for an option error, an
  unresolvable root and a failed `getwd`. Pinned by `TestHarnessBoundedUnreadableSessionsKeepsTheReport`,
  `TestHarnessBoundedUnreadableSkillsAndAgentsKeepTheReport`, `TestHarnessBoundedUnestablishedHomeIsAWarn`,
  `TestHarnessBoundedAPanickingCheckIsContained`, `TestHarnessRunDoctorKeepsTheReportOfAnUnreadableSessionsDirectory` and the
  `unreadable` case of `TestHarnessInstallPabcdRecorded`).
- A session slot, the plugin manifest, a hook or MCP document and `config.toml` were read with `readFileSync`, and the port's
  `os.ReadFile` and `os.Root.Open` blocked on a FIFO until a writer appeared (a `pipe.json` slot or a FIFO hook file ran past
  the caller's two second deadline and needed a second SIGINT), read a file of any size and parsed it to any depth (source
  `doctor.ts:166-181`, `manifest-targets.ts:76-83`, `hook-trust.ts:144-156`; the port's `hooktrust_entries.go`,
  `rooted_read.go`); port: fixed (a record the harness does not control is opened with `O_NONBLOCK`, its type is judged on the
  opened descriptor, a file that is not regular is refused as `not a regular file` and a regular file is read up to 4 MiB
  (`harnessReadLimit`), a longer one is refused as past the read limit; JSON is parsed to `pyjson.MaxDepth` (10000) and a
  deeper document is refused as nested past the depth limit, where JSON.parse accepted it. A refusal is an explicit finding,
  never an absent file or a PASS: a session slot is listed as corrupt with the reason, a refused manifest-target document
  fails its own kind (`unreadable hook json (not a regular file): <path>`), and the other findings stay. A link that stays
  inside the plugin root or the sessions directory is still followed; only the open itself no longer waits. Pinned by
  `TestHarnessBoundedFIFOSessionSlot`, `TestHarnessBoundedLargeAndDeepSessionSlots`, `TestHarnessBoundedSessionLinkIsFollowed`,
  `TestHarnessBoundedFIFOManifestAndHookFiles`, `TestHarnessBoundedLargeAndDeepDocuments` and the `deep_10001` case of
  `TestHarnessInstallPabcdRecorded`). The `config.toml` bound is the harness check's own: the exported `ReadInstalledPluginKeys`
  and `DiagnoseHookTrust`, which `crw doctor retrust` shares for its reads and its pre-write verification, read the file whole
  as before, so a large valid `config.toml` is still retrusted; only `HarnessHookTrustCheck` reads it bounded and reports a FIFO
  or an oversized file as a FAIL (pinned by `TestHarnessRound2SharedConfigReadersAreUnbounded`,
  `TestHarnessRound2HarnessConfigReadIsBounded` and `TestHookTrustRetrust_initializes_a_config_past_the_harness_read_limit`).
  The plugin documents follow the same rule: the 4 MiB bound is chosen by the harness caller
  (`hookTrustEntriesReadContainedLimit`, `listHookTrustEntries` with `harnessReadLimit` from `HarnessHookTrustCheck`), while
  `hookTrustEntriesReadContained`, `ListHookTrustEntries`, the retrust plugin discovery (`hookTrustRetrustDeclaresHooks`) and key
  resolution read a valid manifest or hook document past 4 MiB whole, as dev did (pinned by
  `TestHarnessRound3SharedPluginReadersAreUnbounded`, `TestHarnessRound3HarnessPluginReadsAreBounded` and
  `TestHookTrustRetrust_retrusts_a_plugin_whose_documents_are_past_the_harness_read_limit`).
  A document is refused as nested past the depth limit only when the depth is all that is wrong with it (the same reader with
  `Deep` set accepts it); a document with a syntax error, before or after the deep containers, keeps the reader's own error
  (pinned by `TestHarnessRound2SyntaxErrorBeforeDepthIsNotTooDeep`). That check does not build the document: it is a
  `pyjson.LoadOptions.Skim` reading, which keeps one byte for each open container and no value, so a 4 MB document of two
  million brackets is refused with a few MiB of allocation, not a frame and a value for each level (pinned by
  `TestHarnessRound3DepthRefusalDoesNotMaterializeTheDocument` and, for Skim's agreement with the Deep reading,
  `TestLoads_skim_agrees_with_the_deep_reading`).
- A stat failure on the sessions, skills or agents path that is not "absent" (an unsearchable parent such as a `.crw` with mode
  000) was read as an absent directory: the pabcd check passed as `no .crw/sessions/ directory (clean state)` over a state it
  could not see (source `doctor.ts:64-70` `isDir`, which reads every stat failure as false); port: fixed (`harnessInstallStatDir`
  tells absent, or a parent that is not a directory, from every other stat failure; the latter is a skipped WARN that names the
  failure in Node's shape, for the sessions, skills and agents checks alike. Pinned by
  `TestHarnessRound1UnsearchableParentIsNotCleanState` and `TestHarnessRound1UnsearchableParentOfSkillsAndAgents`).
- `manifestTargetChecks` stops at the first document it cannot use and leaves the other kind unevaluated, so a hook document the
  harness refuses (a FIFO, past a limit, malformed) hid a shape or missing-target finding of the MCP kind and the reverse, and
  the findings a kind had made before it stopped were dropped (source `doctor.ts:228-254`, `manifest-targets.ts` walks);
  port: fixed (`validateManifestTargetsByKind` runs the hook and the MCP validation independently over one manifest read, and
  `HarnessManifestTargetChecks` reports each kind with the findings it made plus the reason it stopped; the kind whose
  documents are fine is evaluated. A manifest that cannot be read, is malformed or is JSON null still stops both, as one
  failure of the manifest. `ValidateManifestTargets` keeps its error contract: any stop returns the error alone. The recorded
  oracle cases `unparseable_hook`, `unparseable_mcp` and `nonparse_failure` keep the oracle's answer for the failing kind and
  assert the other kind's own result (`harnessInstallIndependentKinds`). Pinned by `TestHarnessRound1TargetKindsAreIndependent`).
- The optional report fields (plugin version, codex version, active surface) were read outside the step guard, so a probe that
  panics there lost the whole report (the oracle has no such failure: its probes return values); port: fixed
  (`harnessRunMetadata` answers nil for a field whose read panics and the checks stay. Pinned by
  `TestHarnessRound1MetadataPanicKeepsTheReport`).
- `targetCheck` of the manifest-target validator accepted any existing path with a nonzero size, so a directory (which reports
  a size) was a valid hook command target or MCP server script (source `manifest-targets.ts` target check; the port's
  `targetCheck`); port: fixed (a target must stat, following links, to a regular file; a directory, FIFO or device is
  `target is not a regular file: <rel>`, and a link to a regular file is still a file. Pinned by
  `TestHarnessBoundedTargetTypes`, "a non-empty directory is not a file target", "a FIFO target is not a file target" and
  "a link to a regular file is a file target", and the empty-directory step of `TestManifestTargetsExactEscapeAndShapes`).
- The validator passed over a manifest `hooks` member that is not an array (`"x"`, a number, an object, a boolean), a
  `mcpServers` member that is not a string, a hook document whose `hooks` is not an object and an MCP document whose
  `mcpServers` is not an object, so the check reported all targets present for a manifest that declared none (source
  `manifest-targets.ts` hooks and mcpServers walks; the port's `ValidateManifestTargets`); port: fixed (each is a finding of
  its kind: `manifest hooks must be an array of hook file paths: <value>`, `manifest mcpServers must be a string file path:
  <value>`, `hooks must be an object: <ref>`, `mcpServers must be an object: <ref>`; an absent or null member declares
  nothing and is not a finding. Pinned by "hooks that is not an array", "mcpServers that is not a string" and "hooks and
  mcpServers members of the declared files" in `TestHarnessBoundedTargetTypes`, the `manifest_hooks_not_an_array` case of
  `TestHarnessRunDoctorRecorded` and the shapes step of `TestManifestTargetsExactEscapeAndShapes`).
- Supersedes known-defects.md, section "Found by the hook trust identity port (CRW-347)", item beginning "`identityHash` resolves the event through a plain
  object lookup": now port: fixed (an event that is a member `Object.prototype` lends every object, the eleven function members
  and `__proto__`, is not one of the ten event labels; `HookTrustIdentityHash` and `ListHookTrustEntries` refuse it with
  `unsupported hook event: <name>` like any unknown event, and the manifest-target validator reports it as `hook event is not
  supported: <name>`. The validator judges every event by the same ten-label table (`hookTrustIdentityEvent`), so any name
  outside it (a misspelling such as `stop`, an invented `DefinitelyNotAnEvent`) is the same hooks finding, where the oracle's
  walk passed over it; pinned by `TestHarnessRound2UnsupportedHookEventsAreFindings`. The ten labels keep their hashes, trust keys and containment unchanged. The recorded `proto_*` oracle
  cases stay as the oracle's record; the tests that replay them assert the refusal. Pinned by
  `TestHarnessBoundedPrototypeEventsAreRefused`, the `proto_*` cases of `TestHookTrustIdentityHash_recordedCases` and
  `TestListHookTrustEntries_recordedCases`, and "an Object.prototype event" in `TestHarnessBoundedTargetTypes`).
- Supersedes known-defects.md, section "Found by the hook trust entry listing port (CRW-601)", item beginning "`listHookEntries` writes the event into the key
  through a template literal": now port: fixed (the same refusal; an inherited name never reaches the key).
