# CRW-1097 — a transition-ledger row lost between the state publication and its append

Source: CXC v0.2.40 (commit 3c1459ac) `plugins/codexclaw/components/pabcd-state/src/hook.ts`
`handleOrchestrateCommand` (:1360 then :1395, the bound all-done close :1145-1149) and
`plugins/codexclaw/components/pabcd-state/src/orchestrate-cli.ts` (the reset :562-563, the I>P override
:653-655, the ordinary edge :1119 then :1123, the unbound close :740-748 and the all-done close :891-908).
The port is the session's ledger outbox, `internal/pabcd/state/outbox.go` with `AppendLedgerLine` in
`internal/pabcd/state/ledger.go`, drained through `hook.DrainSessionLedger`
(`internal/pabcd/hook/ledger_outbox.go`) by the chat command (`internal/pabcd/hook/prompt_orchestrate.go`),
the bound chat close (`internal/pabcd/hook/prompt_dclose.go`), every locked chat write
(`promptSubmitWriteStateReason`) and the orchestrate CLI (`internal/pabcd/cli/orchestrate_transition.go`,
`internal/pabcd/cli/orchestrate_dclose.go`). Cases: `internal/pabcd/state/outbox_test.go`,
`internal/pabcd/hook/prompt_orchestrate_outbox_test.go` and `internal/pabcd/cli/orchestrate_outbox_test.go`.
Found by the isolated real-use trial r1 (S4-F3: 5 to 9 of 300 SIGKILLed chat `orchestrate A` hooks ended
with phase A and no row) and the A2 review of the kept entries listed below.

- The oracle publishes the session state and then appends the transition row with nothing in between, so
  a writer that dies, or an append that fails, after the publication leaves an applied phase change that no
  ledger row records, and nothing repairs it: the phase has moved, so the same request is refused
  (`hook.ts`:1360 then :1395, `orchestrate-cli.ts`:1119 then :1123); port: fixed (a lost-record defect, the
  class the parity rule revision of 2026-10-03 fixes during the port: inside the session lock the row is
  prepared as a pending event of the session - `<state file>.ledger-outbox/<seq>-<id>.event`, written and
  fsynced before the state - then the state is published, then the outbox is drained. A failure before the
  rename drops the event again, so no row ever describes a transition that did not happen. A pending event
  that outlives its writer is drained by the next locked writer of the session, which decides from the state
  it finds - the digest of the state before and after, then the phase, then the stored `updatedAt` - whether
  the transition was published, appends the row once or drops the event; `TestPromptOrchestrateFailedAppendIsRecordedByTheNextHook`,
  `TestPromptOrchestrateStoppedAfterPublishIsRecordedByTheNextHook`,
  `TestOrchestrateCommitFailedRowIsRecordedByTheNextCall`, `TestOrchestrateCommitStoppedAfterPublishIsRecorded`,
  `TestLedgerOutboxDropsAnUnpublishedTransition`).
- The chat command answered nothing at all when its append failed (cli.ts catches the throw); port: fixed
  (the answer is the transition's directive with the line "the transition was applied, but its ledger row
  could not be written yet (...); the row is kept pending and the next hook or orchestrate command of this
  session records it", and the CLI's warning names the same pending row).
- The rows of one session can be appended in the reverse of the order its states were published, because
  the chat append ran after the session lock was released (`hook.ts`:1395 has no lock at all); port: fixed
  (the append runs inside the session lock, after every row an earlier writer left pending; a drain whose
  append fails stops there, so a later row never overtakes an earlier one;
  `TestPromptOrchestrateRowsKeepTheStateOrder`, `TestLedgerOutboxKeepsTheOrderAcrossAFailedAppend`).

The rows keep the oracle's bytes: the event's identity is the outbox record (its id, the row's exact bytes
and the ledger size when it was prepared), and a row counts as recorded when that exact line stands in the
ledger at or after that size, so no key is added to a row and no recorded fixture changes
(`TestLedgerOutboxAppendsAPublishedTransitionOnce`, `TestLedgerOutboxOnlyLooksPastTheRecordedSize`). A
session with nothing pending keeps no outbox directory. A killed writer still leaves its session lock
behind; reclaiming that lock belongs to the trial's S4-F2 issue (the session lock lane of the 10-10 review), and until it lands the operator removes the stale lock
by hand as `state/lock.go` documents, after which the next hook records the pending row. The session's
resume (SessionStart) does not drain on its own; its next prompt does.

trial's `killfuzz.py` with a follow-up prompt after each kill, against the dev binary and this branch's.
