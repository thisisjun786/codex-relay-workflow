# CRW-1097 — a transition-ledger row lost between the state publication and its append

Source: CXC v0.2.40 (commit 3c1459ac) `plugins/codexclaw/components/pabcd-state/src/hook.ts`
`handleOrchestrateCommand` (:1360 then :1395, the bound all-done close :1145-1149) and
`plugins/codexclaw/components/pabcd-state/src/orchestrate-cli.ts` (the reset :562-563, the I>P override
:653-655, the ordinary edge :1119 then :1123, the unbound close :740-748 and the all-done close :891-908).
The port is the session's ledger outbox, `internal/pabcd/state/outbox.go` with `AppendLedgerLine` in
`internal/pabcd/state/ledger.go`, drained through `hook.DrainSessionLedger`
(`internal/pabcd/hook/ledger_outbox.go`) by the chat command (`internal/pabcd/hook/prompt_orchestrate.go`),
the bound chat close (`internal/pabcd/hook/prompt_dclose.go`), every locked chat write
(`promptSubmitWriteStateReason`) and the orchestrate CLI (`internal/pabcd/cli/orchestrate_transition.go`,
`internal/pabcd/cli/orchestrate_dclose.go`). Cases: `internal/pabcd/state/outbox_test.go`,
`internal/pabcd/hook/prompt_orchestrate_outbox_test.go` and `internal/pabcd/cli/orchestrate_outbox_test.go`.
Found by the isolated real-use trial r1 (S4-F3: 5 to 9 of 300 SIGKILLed chat `orchestrate A` hooks ended
with phase A and no row) and the A2 review of the kept entries listed below.

- The oracle publishes the session state and then appends the transition row with nothing in between, so
  a writer that dies, or an append that fails, after the publication leaves an applied phase change that no
  ledger row records, and nothing repairs it: the phase has moved, so the same request is refused
  (`hook.ts`:1360 then :1395, `orchestrate-cli.ts`:1119 then :1123); port: fixed (a lost-record defect, the
  class the parity rule revision of 2026-10-03 fixes during the port: inside the session lock the row is
  prepared as a pending event of the session - `<state file>.ledger-outbox/<seq>-<id>.event`, written and
  fsynced before the state - then the state is published, then the outbox is drained. A failure before the
  rename drops the event again, so no row ever describes a transition that did not happen. A pending event
  that outlives its writer is drained by the next locked writer of the session, which decides from the state
  it finds - the digest of the state before and after, then the phase, then the stored `updatedAt` - whether
  the transition was published, appends the row once or drops the event; `TestPromptOrchestrateFailedAppendIsRecordedByTheNextHook`,
  `TestPromptOrchestrateStoppedAfterPublishIsRecordedByTheNextHook`,
  `TestOrchestrateCommitFailedRowIsRecordedByTheNextCall`, `TestOrchestrateCommitStoppedAfterPublishIsRecorded`,
  `TestLedgerOutboxDropsAnUnpublishedTransition`).
- The chat command answered nothing at all when its append failed (cli.ts catches the throw); port: fixed
  (the answer is the transition's directive with the line "the transition was applied, but its ledger row
  could not be written yet (...); the row is kept pending and the next hook or orchestrate command of this
  session records it", and the CLI's warning names the same pending row).
- The rows of one session can be appended in the reverse of the order its states were published, because
  the chat append ran after the session lock was released (`hook.ts`:1395 has no lock at all); port: fixed
  (the append runs inside the session lock, after every row an earlier writer left pending; a drain whose
  append fails stops there, so a later row never overtakes an earlier one;
  `TestPromptOrchestrateRowsKeepTheStateOrder`, `TestLedgerOutboxKeepsTheOrderAcrossAFailedAppend`).

The rows keep the oracle's bytes: the event's identity is the outbox record (its id, the row's exact bytes
and the ledger size when it was prepared), and a row counts as recorded when that exact line stands in the
ledger at or after that size, so no key is added to a row and no recorded fixture changes
(`TestLedgerOutboxAppendsAPublishedTransitionOnce`, `TestLedgerOutboxOnlyLooksPastTheRecordedSize`). Two events
that spell the same line (the same millisecond, the same edge) are told apart by order: a drain looks for an
event's line only after the end of the row of the event before it, and carries that end into the next event's
file before the earlier one is removed, so each records its own row
(`TestLedgerOutboxRecordsDistinctEventsWithIdenticalRows`, `TestLedgerOutboxCarriesTheRowEndToTheNextIdenticalEvent`).
A row counts as recorded only once the ledger file and its directory are fsynced; a failed sync leaves the event
pending, published, and the next drain finds the row, syncs, and removes it
(`TestLedgerOutboxKeepsAnEventWhoseLedgerSyncFailed`). An append that fails stops the appends but not the
judgment: every event behind the blocked one is judged against the state the drain read and the verdict is kept
in its file (a published event is marked published, an unpublished one dropped), so transitions applied one after
another while the ledger is blocked - a round trip back to an earlier phase included - are all recorded, in order,
once it works again (`TestLedgerOutboxKeepsEveryPublishedEventAcrossABlockedLedger`,
`TestLedgerOutboxJudgesTheEventsBehindABlockedAppend`, `TestOrchestrateRoundTripsDuringALedgerFailureAreAllRecorded`). Status stays a read
(`phase-control.md`: "`status` is read-only"): it reports the number of pending events of the session it selects
("pending ledger rows: N", `pendingLedgerEvents` in `--json`) and records nothing, whichever way the session was
selected, so the unverified latest-file fallback gains no write authority; the next hook or orchestrate command
of the session records the rows (`TestOrchestrateStatusOnlyReportsAPendingRow`). An all-done
chat close whose ledger lookup of the close key fails still prepares its close row, so the next writer records it
(`TestPromptDcloseAllDoneLedgerReadErrorKeepsARecoverableRow`). A
session with nothing pending keeps no outbox directory. Three properties keep the record true when
other writers touch the session in between (the pre-merge evaluation of 3fceb240). The holder of the session lock
judges, as soon as it holds the lock and before it changes anything, every pending event that no judgement has
reached (`state.JudgeLedgerOutbox`, called by `WithSessionLock` itself): a published one is marked so in its file,
one that was not is dropped. Every writer of the session therefore leaves a verdict behind it, the memory grants,
scans, evidence, idle-edit, Stop and PostCompact writers included, and a later drain never mistakes such a write
for the transition of the event (`TestLedgerOutboxAnUnrelatedWriteIsNotTheUnpublishedTransition`,
`TestLedgerOutboxAPublishedTransitionSurvivesALaterUnrelatedWrite`); a transition that keeps its phase and whose
state matches neither side of the event is not shown to have been published, so it gets no row
(`TestLedgerOutboxAStateMatchingNeitherSideIsNotAPublication`) - a row must never describe a transition that did not
happen. A verdict the holder cannot keep refuses the holder (the verification of 80d8d69f): an outbox that cannot
be listed, a published verdict that cannot be written and an unpublished event that cannot be removed answer
`state.ErrLedgerJudgment` from `WithSessionLock`, the callback does not run and the state stays the one the
event's writer left, so the next holder judges again and a published same-phase reset keeps its row
(`TestLedgerOutboxLockRefusesTheWriterWhenAPublishedVerdictCannotBeKept`,
`TestLedgerOutboxLockRefusesTheWriterWhenAnUnpublishedEventCannotBeRemoved`,
`TestLedgerOutboxLockRefusesTheWriterWhenTheOutboxCannotBeRead`). A session state that cannot be read is no
refusal: the events wait, and every writer refuses to write over such a state itself (CRW-646). The sequence of an event is the clock's nanoseconds but always above every sequence still pending in the
session's outbox (allocated under the session lock), so a clock that steps backwards cannot put a later
transition's row before an earlier one (`TestLedgerOutboxSequenceFollowsPreparationOrderAcrossABackwardClock`).
A ledger the process may append to and not read (mode 0200) keeps taking rows, as the appender always took them:
the event records that its row was appended, so a retry only syncs (`TestLedgerOutboxAppendsToAWriteOnlyLedger`,
`TestLedgerOutboxDoesNotAppendTwiceToAWriteOnlyLedger`); an event prepared while the ledger could not be read, whose
row may already be there, waits for a ledger it can search. Before every append of a row the event's file records,
durably, that an append begins and the ledger's size before it (`appendStarted`, `appendSize`), so a writer killed
between the append and the event's next write leaves that mark: a retry that cannot read the ledger appends again
only when the ledger's size is still the recorded one, and otherwise keeps the event pending until the ledger can be
searched, where the row is found and recorded once (`TestLedgerOutboxWriteOnlyLedgerKilledAfterTheAppendIsNotAppendedTwice`,
`TestLedgerOutboxWriteOnlyLedgerKilledBeforeTheAppendAppendsOnce`,
`TestLedgerOutboxReadableAppendKilledThenWriteOnlyIsNotAppendedTwice`; red on 63b65d5b, where the retry appended the
row a second time). The prompt hook, the Stop and PostCompact hooks and every
orchestrate command drain (`TestPostCompactRecordsAPendingRow`). A killed writer still leaves its session lock
behind; reclaiming that lock belongs to the trial's S4-F2 issue (the session lock lane of the 10-10 review), and until it lands the operator removes the stale lock
by hand as `state/lock.go` documents, after which the next hook records the pending row. The session's
resume (SessionStart) does not drain on its own; its next prompt does.
