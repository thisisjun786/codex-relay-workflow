# CRW-974 — append-only zone tables refuse INSERT OR REPLACE of a stored key

Source: the port's own product code, `internal/relay/store/dag_zone.go` (the zone's statements and their UPDATE and DELETE triggers) and `internal/relay/store/store.go` (the connection settings, which do not set `recursive_triggers`). No CXC v0.2.40 source or corpus fixture is involved: the DAG zone is the port's own addition and the oracle has no counterpart of it to record.

- The zone's append-only tables refuse UPDATE and DELETE by trigger, but an `INSERT OR REPLACE` that repeats a key deletes the stored row without running a DELETE trigger while `recursive_triggers` is OFF, and no UPDATE happens, so a writer that skips the store's own insert could rewrite a row the table promises never changes (CRW-728 post-merge evaluation, P1); port: fixed (one `BEFORE INSERT` guard per key, for every table that has a `<table>_no_delete` trigger, 17 tables and 25 key guards plus 51 rowid guards and the table `dag_zone_rowid_marks` they keep a mark in, appended to the statements and never edited into a shipped one: the primary key, each UNIQUE and each partial UNIQUE with its WHERE, raising the exact text SQLite gives a plain INSERT of that key; `PRAGMA recursive_triggers` is left as it is, because turning it ON changes what every trigger means on every connection. Pinned by `TestDAGZoneRefusesAnInsertOrReplaceOfAStoredKey` for every key, `TestDAGZoneRefusesAnOutboxReplaceThatKeepsTheSummaryIDAndTakesTheNextSequence`, `TestDAGZoneKeyGuardsKeepThePlainInsertRefusal` (text, class, no store refusal), `TestDAGZoneKeyGuardsKeepThePriorityAmongKeys` (every subset of repeated keys answers as the old zone did), `TestDAGZoneKeyGuardsLeaveTheNormalPathsAlone` (UPDATE, retirement, a free partial key), `TestDAGZoneKeyGuardsKeepTheNullMeaningOfUnique`, `TestDAGZoneUpgradeAddsTheKeyGuardsAndKeepsTheRows`, and `TestDAGZoneKeyGuardsRefuseAnOutboxReplaceWithANullAttempts`, `TestDAGZoneRefusesAnInsertOrReplaceOfAStoredRowid`, `TestDAGZoneRowidMinusOneIsWrittenAndItsReplaceIsRefused`, `TestDAGZoneAssignedInsertsFollowARowidOfMinusTwo`, and `TestDAGZoneKeyGuardsAreTheTemplateAndCoverEveryAppendOnlyKey`, which reads the guard list from the catalog so a later append-only table without its guards fails).
- The extended result code of a repeated key of these tables is now 1811 (`SQLITE_CONSTRAINT_TRIGGER`) where it was 1555 (primary key) or 2067 (unique); the primary code (19, `IntegrityError`) and the text are unchanged, and no product code branches on 1555 or 2067 for these tables (`internal/relay/store/domain.go` names 2067 for the six guard indexes of the frozen v1 tables, which are not touched); port: kept (a RAISE inside a trigger carries the trigger code and cannot carry the index's).
- A row that repeats a key and also breaks a CHECK or a NOT NULL of its own table is now refused with the key's text where the CHECK's text came first, because SQLite runs BEFORE triggers before it checks the row's constraints; the row is refused either way and nothing is written. A table's own earlier BEFORE INSERT trigger keeps its message (the guards of `dag_summary_outbox` and `dag_plan_revisions` stand aside for `dag_summary_outbox_order` and `dag_plan_revisions_parent`); port: kept (pinned by `TestDAGZoneKeyGuardNamesTheKeyBeforeACheckOfTheSameRow` and `TestDAGZoneKeyGuardsLeaveTheEarlierTriggerItsMessage`).
- `INSERT OR IGNORE` and `ON CONFLICT DO NOTHING` that repeat a stored key of a guarded table are refused as well, because `RAISE(ABORT)` is not softened by the statement's conflict clause; port: kept (no product writer uses either on the 17 tables, proved by `TestNoProductWriterRelaxesAGuardedTable`; the idempotent writers, `release.go` for `dag_node_executions`, `internal/relay/dag/manifest.go` for `dag_input_manifests` and `livesweep.go` for `dag_conflict_drift`, write tables that have no `_no_delete` trigger and no guard, and `TestDAGZoneIdempotentWritersStayNoOps` pins that they stay no-ops).
- The unique key `(plan_id, document, seq)` of `dag_summary_outbox` has no guard; port: kept (`dag_summary_outbox_order` refuses every entry whose `seq` is not `MAX(seq) + 1` of its stream, a repeated `seq` is never that, so neither INSERT nor REPLACE can repeat the key, and a guard would carry that trigger's condition and never fire; `TestDAGZoneOutboxSequenceKeyIsRefusedByTheOrderTrigger`).
- A store that predates the guards gains them on its first write open of this build (the zone's all-or-nothing install), keeps every row (a BEFORE INSERT guard cannot touch an existing one), and is an `EXTENDS_ZONE` arrival for the swap gate like any appended zone object. `store.MissingZoneKeyGuards` is the read-only check after an install that every guard is present; port: fixed.
- Verification round 1 found two ways around the guards, both fixed in the same statements (they are this issue's own, not yet shipped, so they are edited in place and `testdata/dag_zone_shipped.json` holds no earlier text of them): (1) a guard that stands aside for an earlier trigger used `NOT (<that trigger's WHEN>)`, which is NULL when the WHEN is NULL (an explicit `attempts = NULL` in `dag_summary_outbox`: `NEW.attempts <> 0` is NULL, so `dag_summary_outbox_order` did not fire either, and REPLACE then turned the NULL into the column default and replaced the stored entry); the guards now carry `NOT COALESCE((<WHEN>), 0)`, true exactly when that trigger does not fire, which is the template for the tables of R04; (2) the tables are rowid tables, so an `INSERT OR REPLACE` that names the rowid of a stored row (`rowid`, `_rowid_` or `oid`) replaced it whatever the declared keys said. Each of the 17 tables now has `<table>_rowid_guard` (BEFORE INSERT, raises `UNIQUE constraint failed: <table>.rowid`, the text a plain INSERT of a stored rowid gets, created after the key guards so it fires first as SQLite checks the rowid first, standing aside for the same earlier trigger). A BEFORE INSERT trigger reads -1 as `NEW.rowid` for every row whose rowid SQLite assigns afterwards, so that guard cannot tell an explicit -1 from an assigned insert and stands aside for it; rowid -1 is guarded by the two triggers of verification round 2 below. The catalog test requires the table to be a rowid table without an INTEGER PRIMARY KEY alias (for which the key guard's message would be the right one). Pinned by the tests named above; port: fixed.
- Verification round 2 found that the round-1 `<table>_rowid_reserved_guard` (AFTER INSERT, refusing every row stored under rowid -1) made a table whose largest rowid is -2 unwritable: SQLite assigns the largest rowid plus one, so every insert that leaves the rowid to SQLite was given -1 and refused, the refusal rolled back, and the largest rowid stayed -2, on a store the build created and given a row under -2 as on an old zone that held one before the upgrade (P1). It is replaced in place (not yet shipped) by `<table>_rowid_minus1_mark_guard` (BEFORE INSERT, WHEN `NEW.rowid = -1`: clears the table's mark in `dag_zone_rowid_marks`, then sets it when a stored row has rowid -1) and `<table>_rowid_minus1_guard` (AFTER INSERT, WHEN `NEW.rowid = -1` and the mark: raises `UNIQUE constraint failed: <table>.rowid`). When a row already has rowid -1 an assigned rowid is the next above the largest, never -1, so a row that lands under -1 then is the REPLACE of the stored one, and the statement is rolled back with its deletion; triggers fire per row, so a multi-row statement reads its own mark per row. A row may now be stored under -1 and an assigned insert is never refused; `dag_zone_rowid_marks` holds no row in a store whose tables hold no rowid -1 (a mark stays for a table that holds one, refreshed by its next insert). Pinned by `TestDAGZoneAssignedInsertsFollowARowidOfMinusTwo` (two committed assigned inserts after a rowid -2, created and upgraded, then REPLACE of -1, 0 and -2 refused) and `TestDAGZoneRowidMinusOneIsWrittenAndItsReplaceIsRefused` (REPLACE of a stored -1 by `rowid`, `_rowid_` and `oid`, plain INSERT, REPLACE INTO, a multi-row statement, INSERT OR IGNORE a no-op, created and upgraded); port: fixed.
