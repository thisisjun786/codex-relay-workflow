# CRW-974 — append-only zone tables refuse INSERT OR REPLACE of a stored key

Source: the port's own product code, `internal/relay/store/dag_zone.go` (the zone's statements and their UPDATE and DELETE triggers) and `internal/relay/store/store.go` (the connection settings, which do not set `recursive_triggers`). No CXC v0.2.40 source or corpus fixture is involved: the DAG zone is the port's own addition and the oracle has no counterpart of it to record.

- The zone's append-only tables refuse UPDATE and DELETE by trigger, but an `INSERT OR REPLACE` that repeats a key deletes the stored row without running a DELETE trigger while `recursive_triggers` is OFF, and no UPDATE happens, so a writer that skips the store's own insert could rewrite a row the table promises never changes (CRW-728 post-merge evaluation, P1); port: fixed (one `BEFORE INSERT` guard per key, for every table that has a `<table>_no_delete` trigger, 17 tables and 25 guards, appended to the statements and never edited into a shipped one: the primary key, each UNIQUE and each partial UNIQUE with its WHERE, raising the exact text SQLite gives a plain INSERT of that key; `PRAGMA recursive_triggers` is left as it is, because turning it ON changes what every trigger means on every connection. Pinned by `TestDAGZoneRefusesAnInsertOrReplaceOfAStoredKey` for every key, `TestDAGZoneRefusesAnOutboxReplaceThatKeepsTheSummaryIDAndTakesTheNextSequence`, `TestDAGZoneKeyGuardsKeepThePlainInsertRefusal` (text, class, no store refusal), `TestDAGZoneKeyGuardsKeepThePriorityAmongKeys` (every subset of repeated keys answers as the old zone did), `TestDAGZoneKeyGuardsLeaveTheNormalPathsAlone` (UPDATE, retirement, a free partial key), `TestDAGZoneKeyGuardsKeepTheNullMeaningOfUnique`, `TestDAGZoneUpgradeAddsTheKeyGuardsAndKeepsTheRows`, and `TestDAGZoneKeyGuardsAreTheTemplateAndCoverEveryAppendOnlyKey`, which reads the guard list from the catalog so a later append-only table without its guards fails).
- The extended result code of a repeated key of these tables is now 1811 (`SQLITE_CONSTRAINT_TRIGGER`) where it was 1555 (primary key) or 2067 (unique); the primary code (19, `IntegrityError`) and the text are unchanged, and no product code branches on 1555 or 2067 for these tables (`internal/relay/store/domain.go` names 2067 for the six guard indexes of the frozen v1 tables, which are not touched); port: kept (a RAISE inside a trigger carries the trigger code and cannot carry the index's).
- A row that repeats a key and also breaks a CHECK or a NOT NULL of its own table is now refused with the key's text where the CHECK's text came first, because SQLite runs BEFORE triggers before it checks the row's constraints; the row is refused either way and nothing is written. A table's own earlier BEFORE INSERT trigger keeps its message (the guards of `dag_summary_outbox` and `dag_plan_revisions` stand aside for `dag_summary_outbox_order` and `dag_plan_revisions_parent`); port: kept (pinned by `TestDAGZoneKeyGuardNamesTheKeyBeforeACheckOfTheSameRow` and `TestDAGZoneKeyGuardsLeaveTheEarlierTriggerItsMessage`).
- `INSERT OR IGNORE` and `ON CONFLICT DO NOTHING` that repeat a stored key of a guarded table are refused as well, because `RAISE(ABORT)` is not softened by the statement's conflict clause; port: kept (no product writer uses either on the 17 tables, proved by `TestNoProductWriterRelaxesAGuardedTable`; the idempotent writers, `release.go` for `dag_node_executions`, `internal/relay/dag/manifest.go` for `dag_input_manifests` and `livesweep.go` for `dag_conflict_drift`, write tables that have no `_no_delete` trigger and no guard, and `TestDAGZoneIdempotentWritersStayNoOps` pins that they stay no-ops).
- The unique key `(plan_id, document, seq)` of `dag_summary_outbox` has no guard; port: kept (`dag_summary_outbox_order` refuses every entry whose `seq` is not `MAX(seq) + 1` of its stream, a repeated `seq` is never that, so neither INSERT nor REPLACE can repeat the key, and a guard would carry that trigger's condition and never fire; `TestDAGZoneOutboxSequenceKeyIsRefusedByTheOrderTrigger`).
- A store that predates the guards gains them on its first write open of this build (the zone's all-or-nothing install), keeps every row (a BEFORE INSERT guard cannot touch an existing one), and is an `EXTENDS_ZONE` arrival for the swap gate like any appended zone object. `store.MissingZoneKeyGuards` is the read-only check after an install that every guard is present; port: fixed.
