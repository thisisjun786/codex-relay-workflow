# CRW-1200 — the resume walk and the suffix boundary: replay rule, joins, thread fork

Source: CRW's own design (0.5.0-alpha, issue F07), not the CXC oracle: CXC v0.2.40 (commit 3c1459ac) has no flow engine, so there is no oracle line. The Go side is `internal/flow/engine/{walk,digest,suffix,hold,checkpoint,opcall,resume,call,scriptvm,workflow,tierstep,classify}.go`, `internal/flow/backend/agent/{fork,worktree,agent}.go`, `internal/flow/ops/{gitsnap,proofs}.go` and `internal/bridge/appserver/fakehost/threads.go`; the rule is written in `docs/flow/journal.md`, "The resume walk". The tests are `internal/flow/engine/{suffix_test,suffix_host_test}.go`, `internal/flow/journal/resume_test.go`, `internal/flow/backend/agent/fork_test.go` and `internal/flow/ops/{restore_test,proofs_test}.go`.

- The body names the edit regions `internal/flow/engine/suffix.go` and `suffix_test.go`, `backend/agent/fork.go`, `ops/gitsnap.go`, `fakehost/` and `docs/flow/journal.md`; the walk also needed `walk.go`, `digest.go`, `hold.go`, `checkpoint.go` and `opcall.go` in `internal/flow/engine/` (the region names the whole directory) and a change to `ops/proofs.go`, the proof F06 wrote. The tests that need real git, real thread requests and the fake host run in the external package `engine_test` of `internal/flow/engine`, because `backend/agent` imports the engine; port: kept.
- `crw.commit`, `crw.verify`, `crw.review`, `crw.accept`, `crw.integrate` and `crw.hold` do not exist in this tree (F08, CRW-1201, comes after this issue). Only the interface they need is here: `engine.Op` and `Config.Ops`, an op taking a position, a completed row with an `input_digest`, a replay only while `Op.Proven` says the effect is there, and the same call id and `RequestID` when it runs again. The zero-live, crash, accepted-node and fix-boundary tests register ops of their own (a world with one effect per request id; `crw.commit` over real git). The engine reads three op names itself: `crw.commit` (the node and commit that move a node's boundary), `crw.accept` (a node that was accepted is refused, not rebuilt) and the rows' `node`, `commit` and `tree` members; the real ops have to write them. port: kept (F08 registers the real ones).
- The signal and batch paths (`signal:<milestone>:<k>`, `batch:<milestone>:<k>`, `crw.dag` lanes) belong to F09 and are not here; the walk's rules for a lane under a design revision a suffixed signal produced are not implemented. `crw.dag` is a join like `parallel`, so the sibling-lane rule is the join rule and is tested through `parallel` and `pipeline`. port: pending (F09).
- The body says an accepted node whose spec or packet changed gets "refusal and route". The refusal is a call result (`refused`, reason `accepted_node_changed`, a new member of the closed reason set) whose row names the routes in text (`update_node`, `dag-correct`); the engine does not write the plan revision or read the relay for whether the acceptance is stale: the accepted node is the one with a `crw.accept` row in the journal. port: kept.
- `input_digest` of a `prepared` row was the digest of the prompt; it is now the digest of the whole input (prompt, schema, role, pair, node, options, context boundary, the joins before the position) and the prompt digest has its own member, `prompt_digest`. The context boundary of a continuation that had to start from a checkpoint is the one it asked for (the fork); the checkpoint digest is on the `checkpoint_started` flow row, so a call replays whichever way it was started. port: kept.
- A call whose outcome is unknown and not cleared replays as unknown even when the walk puts it in a suffix or its input changed: a new attempt of it would send a request that may still be at work on the host and would end the state its hold is read from (a `prepared` row resets it). The hold outlasts the walk. The body does not say; port: kept.
- A held call whose reason is `worktree_failed` is not resumed in place (nothing it needs was made); it runs as the first position of a suffix, with a new `prepared` row. port: kept.
- `p_held` of a held executor that is not the worktree's snapshot when the suffix preserves the worktree is kept on a second ref, `...-held-<call>`, beside `refs/crw/flow/<run>/superseded/<lineage>/<path>@<node>` (the node follows the path so two nodes of one path keep one each; the path is percent-encoded into one component, so no ref is the prefix of another). The body names the first ref only. port: kept.
- The reason of the superseded row of a call whose own input changed in a resume is `superseded_by_resume` (it was `superseded_by_attempt`); the calls of the node's earlier attempt a new attempt ends keep `superseded_by_attempt`. `TestSupersedeInterruptsLiveTurnFirst` asserts the new reason.
- The fork tests of F05 (`TestAckLostForkAdoptsByCwdAndForkedFrom`, `TestForkAckLostTwoExactPrefixAdoptEarliest`, `TestForkAckLostBoundaryMismatchIsForeign`) made their restored worktree by hand (`restoreAfter` writing a `worktree_restored` row for a pending tree no call had recorded); the walk proves the replayed prefix against the restored worktree, so they now run the prefix in a first process and the continuation in a resumed one (`restoreFork`, `runToLostFork`), and the suffix makes the restore. The hand-made restore stays in the tests of the allocator (`worktree_test.go`), which do not resume.
- `ops.Prover.Node` reads only the node's current worktree; a restored worktree is now also the proof of the prefix it carries (the calls up to the one whose pending tree is its P), and `ops.Preserve`, `ops.Restore` and `ops.PreserveTree` are new. `ops.RequestID` is `engine.RequestID`. port: kept.
- The fake host has two knobs for this (`TurnsPageSize`, `ForkKeepsAllTurns`). `thread/fork` is sent with `excludeTurns: true` and no request asks for the history to be hydrated.
- What a real host does with `thread/fork` `lastTurnId` and what a long executor thread costs to fork are measured after the runtime is installed (G-V2, F17); here the host is the fake. port: pending.
