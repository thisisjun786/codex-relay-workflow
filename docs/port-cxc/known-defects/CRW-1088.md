# CRW-1088 — Stop progress and plateau judged on comparable current-work rows

Source: CXC v0.2.40 (commit 3c1459ac) `plugins/codexclaw/components/pabcd-state/src/hook.ts` `observeProgress` (:1465-1490) and `objectivePlateau`/`handleStop` (:1773-1782, :1855-1863), and `metrics.ts` `checkObjectivePlateau` (:207) and `readExplicitObjectiveKind`. The Go side is `internal/pabcd/hook/stop.go` (`stopObserveProgress`, `stopObjectivePlateau`, `stopCounted`), `internal/pabcd/metric/metrics.go` (`JudgeNewRows`, `PlateauOf`, `InferObjectiveKind`, `ReadExplicitObjectiveKind`) and `internal/pabcd/state` (`stopDivergenceWindow`). Found by the 10-10 CXC improvement review (A3-02).

- `observeProgress` counts a new metric row as an improvement whenever `checkObjectivePlateau` is not flat, and the insufficient-data result (fewer rows of the latest metric than the window) is not flat, so a singleton recharges the per-phase budget: five Stops each after a row of a new metric name at value 1 kept the count at 1 (hook.ts:1465, metrics.ts:207); port: fixed (the judgment has three outcomes, `metric.JudgeNewRows`: each row since the cursor is compared only with the earlier row of the same metric and work phase, a gain over it is improving, a row with such a predecessor and no gain is non-improving, and a row with none (a singleton) is unknown. Only improving recharges; the direction stays maximize, so a genuine gain in a satisfy session still recharges. Pinned by `TestCRW1088AlternatingSingletonMetricsDoNotRecharge` (the count climbs and the fourth Stop releases), `TestCRW1088ComparableRowsRechargeOnlyWhenRising` (two rising rows recharge once, an equal or falling row does not) and `TestCRW1088JudgeNewRows`. Red output: `/state/crw/crw-lane-pabcd-stop/evidence/red-1088.log`).
- `objectivePlateau` judges the latest ledger row's metric and work phase, not the bound goalplan's active work phase, so while wp-new was in progress two flat rows of a finished wp-old answered B with the re-plan/divergence block before wp-new had any evaluation, and the same plateau was asked for again on every Stop (hook.ts:1773-1782, 1855-1863); port: fixed (with a bound goalplan, `stopObjectivePlateau` judges the rows of the active work phase (`goalplan.EffectiveActiveWorkPhaseID`) and the rows recorded without one (`default`, what `metric record` writes without `--work-phase`, the documented legacy scope); rows of another work phase are left out, and a bound plan with no active work phase keeps only the unscoped rows. A session without a bound goalplan keeps the oracle's scope over all its rows. The window judged is named by its metric, work phase and row count and written with the counter as the state's `stopDivergenceWindow` (CRW-only, omitted until set, so no oracle state changes shape) when the plateau block is answered; the next Stop in the same window gets the ordinary continuation, and a new row of that metric and work phase is new evaluation evidence and a new window, judged again. Answering the block is not taken as the plateau being handled: only new evidence changes the window. The 2-row window, the 3-block stagnation budget and the 24-block turn cap are unchanged. Pinned by `TestCRW1088PlateauIsJudgedOnTheActiveWorkPhaseOncePerWindow`; `TestStopPlateauBlock`, `TestStopPlateauBlockNamesDiscardedCandidates` and `TestStopPlateauBlockKeepsTheObservationAdvisories` keep the oracle's text).
- `readExplicitObjectiveKind` does not look at the kind file's `sessionId`, and the file is named by the sanitised session id, so a file another session wrote (`k/x` and `k-x` share `k-x.json`), or one naming another session by hand, arms that session's maximize for this one (metrics.ts); port: fixed (`ReadExplicitObjectiveKind` reads the kind only when the file's `sessionId` is this session's id, or is absent: a legacy file written without the field keeps its kind. A `sessionId` naming another session, one that is not a string, or one holding U+FFFD gives no explicit kind, and the kind falls back to the inference from the session's own rows. Pinned by `TestCRW1088AKindFileOfAnotherSessionIsNotExplicit`; the recorded oracle scenarios `kind_file_names_and_bodies`, `kind_alias_collision` and `kind_raw_files` of `internal/pabcd/metric/testdata/scenarios-metrics.json` carry the changed answers with their reasons).
- (verification round 1) the progress judgment of a bound goalplan used every ledger row, so a finished work phase's rising row recharged the budget the active work phase had spent; port: fixed (`stopObserveProgress` judges only the active work phase's rows and the legacy `default` rows, the same scope as the plateau, through `stopScopeRows`; the cursor and its high-water still count the whole ledger and the first new row keeps its place, so rows before the cursor stay old. Pinned by `TestCRW1088InactiveWorkPhaseImprovementDoesNotRecharge`: a rising row of the finished wp-old releases, a rising row of the active wp-new recharges once. Red output: `/state/crw/crw-lane-pabcd-stop/evidence/red-1088-r1.log`).
