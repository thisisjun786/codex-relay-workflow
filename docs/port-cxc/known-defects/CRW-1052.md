# CRW-1052 — relay store: attach confirms the connection's own file, and the diagnostic read's open is already inside the registry

Source: the residue CRW-967 left (its handoff, head 7830b517): `liveStoreRef.attach` in internal/relay/store/storefile.go and the diagnostic read opens in internal/relay/store/diagnostic.go and diagnostic_read.go. The Python oracle (CXC v0.2.40, commit 3c1459ac) has no store-file handle registry (the registry is the Go port's answer to CRW-846), so the oracle files cited by the other records here do not apply; the Go files are storefile.go (liveStoreRef, attach, confirm), connfile.go (connectionFileKey), store.go (open, the connect seams), hold.go (the read-only openers, Projection) and diagnostic.go (holdDatabase, openHeldWith).

- `attach` compared the identity the path named after the connection opened with the identity recorded before it, so a path moved aside while SQLite opened it and put back before the check made a connection that held another file pass for the original and the table recorded the wrong inode (storefile.go, liveStoreRef.attach; CRW-967 residue); port: fixed (attach reads the file the connection itself holds: it takes the checked-out connection through `Conn.Raw`, asks SQLite for the unix VFS file object of the main database (`sqlite3_file_control` with SQLITE_FCNTL_FILE_POINTER), reads the descriptor that object holds and fstat's it, and compares that (device, inode) with the reference's. The path comparison stays as a second condition, since the sidecars SQLite keeps are named by the path. Every opener that attaches passes its `*sql.DB`: store.open, OpenReadOnlyStore, OpenReadOnly, openExamined (OpenInPlace, OpenStopRead) and Projection, which now connects the copy before it attaches. Cases: TestStoreFileAttach_aConnectionOnAnotherFileIsRefusedWhenThePathCameBack and TestStoreFileAttach_readOnlyOpenersRefuseAConnectionOnAnotherFile, red on the tree before the change with the output kept with the handoff, and TestConnectionFileKey_isTheFileTheConnectionOpenedWhereverThePathGoes and TestConnectionFileKey_refusesAConnectionItCannotRead for the accessor itself).
- The modernc driver offers no accessor for the descriptor of a connection's database file, so the accessor is ours and depends on two things of the driver this module pins (modernc.org/sqlite v1.59.0): the unexported `db` and `tls` fields of its connection type, read through reflect, and the layout of os_unix.c's `unixFile` (the descriptor `h` after three pointers); port: kept (a deviation from "no new dependency on the driver's internals". It fails closed: a connection the accessor cannot read, a driver whose fields are not the ones it expects, or a file object that is not open makes the open an error naming what was missing, never an assumed match. TestConnectionFileKey_isTheFileTheConnectionOpenedWhereverThePathGoes reads the real key from a writable store and an immutable in-place read, and so fails at once on a driver upgrade that moves any of these. modernc.org/libc becomes a direct requirement of go.mod, at the version it already had).
- The diagnostic read's open (`metadataBy`'s `open(resolved)` and the held reads of diagnostic.go) was said to open without a reference in the registry; port: kept as found, nothing to fix (every diagnostic read opens its store file through `holdStoreFile`, which puts the inode in the registry's `byKey` for the life of the process before any SQLite connection is made, and `closeOrKeepStoreFile` and `closeOrKeepStoreFileDescriptor` consult `byKey` as well as the live table, so a descriptor-closing reader is refused or its descriptor kept whether or not a store is open on that file; the metadata copy reads the source through the same held handle and connects only to a private temporary copy. The case TestStoreFileDiagnosticRead_otherStoreClosingKeepsTheHolderLock holds a diagnostic read open while a second store on the file closes and an artifact read is pointed at it, and passes on the tree before this change as well, the output of that run kept with the handoff; the CRW-846 end-to-end test TestStoreFileHolderProcess already covers the product paths from a separate process).
