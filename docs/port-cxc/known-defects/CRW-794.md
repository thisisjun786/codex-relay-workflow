# CRW-794 — goalplan write-lock acquisition does not retry a lock the holder removed

Source: CXC v0.2.40 (commit 3c1459ac) `plugins/codexclaw/components/pabcd-state/src/goalplan.ts`,
`withGoalplanWriteLock` (:806-873). The oracle's lock is the `mkdirSync` alone (:823); when a
holder removes the directory, the next attempt's `mkdirSync` simply succeeds, so a removal is
retried by the loop. The port added a descriptor check the oracle has no counterpart for:
`internal/pabcd/goalplan/open.go` `boundFile` (:46-62), `openAt` (:64-75); the acquisition
loop is `internal/pabcd/goalplan/lock.go` (:179-211); the descriptor path comes from
`internal/pabcd/goalplan/open_linux.go` (:10-12).

- A writer waiting on the lock directory opened it with `openAt` (`lock.go:194`) and the holder's
  `releaseLock` (`open.go:80-101`, `unix.Unlinkat` at :99) removed the directory before
  `boundFile`'s descriptor check (:58-60) read it. The descriptor then named the expected path
  with the Linux ` (deleted)` suffix, the exact compare failed, and the acquisition returned
  `goalplan descriptor path "<dir> (deleted)" is not "<dir>"` instead of retrying — the
  intermittent `TestSteeringApplyConcurrentBatchesKeepEveryKey` failure (reproduced on the
  baseline 1bf52f024b289cc0b3f04faa5c6c15de8b60c1c4: 3 failures / 800 runs at
  `-count=400 -cpu 1,2`); port: fixed by CRW-794. Only the acquisition path of
  `WithGoalplanWriteLock` changed: a vanished lock (the expected path plus ` (deleted)`) counts as
  released and the existing retry budget is reused. `boundFile`, `openAt` and every other caller
  are unchanged, and a descriptor naming any other path is still an error.
- The recognition is name-based: a noncooperating actor that renamed the live lock to a sibling
  literally named `.goalplan.lock (deleted)` would satisfy the equality and be read as vanished.
  A cooperating writer may not remove or relocate an active lock (`open.go:14-15`), and the
  consequence is a retry-then-acquire inside the same plan directory rather than a containment
  escape; port: kept (deliberate, recorded).
- Darwin: `F_GETPATH` (`open_darwin.go:13-22`) fails on an unlinked directory instead of returning
  a decorated path, so the re-read yields an error and the predicate is false; the same race still
  errors there rather than retrying. The reproduction and CI are Linux; port: kept (out of the
  issue's scope, recorded).
- Two sibling windows keep their existing behavior because the issue scopes the change to the
  acquisition path only: the status probe's `openAt` (`lock.go:72-78`) can still return an error
  instead of `Exists=false` under the same interleaving, and the post-`mkdir` open (`lock.go:185`)
  has the window against a noncooperating remover; port: kept (out of scope, recorded).
