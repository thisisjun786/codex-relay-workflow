# CRW-1124 — one spawn event reads the role settings once and resolves the dispatch root once

Source: CXC v0.2.40 (commit 3c1459ac) `plugins/codexclaw/components/subagent-config/src/spawn-attach-hook.ts:420-449` (`dispatchSources`
reads the settings), :926 (`resolveSpawnConfig` reads them again) and :1086 (the fallback notice reads them a third time), and
`fallback-dispatch.ts:237-267` (`managedSpawn` and `issueManagedSpawn`, which runs `managedSpawn` again inside); the Go port's
`spawnHookSettings`, `spawnDispatchSourcesWith` and the snapshot in `spawnHookAssembleWith` (`internal/role/spawn/hook.go`,
`hook_managed.go`), the notice read in `spawnHookRoute` (`hook_route.go`), and `ManagedSpawn`, `IssueManagedSpawnSelection` and
`IssueManagedSpawnEnv` in `internal/role/managed_spawn.go`. Found by the 10-10 CXC improvement review (A5-06); the latency gain was
not measured.

- One spawn event read the helper role store up to three times (the dispatch sources, the role resolution and the fallback
  notice), so an edit of the store between the reads could give one event the prompt of one version and the model or notice of
  another (source :420-449, :926, :1086); port: fixed (the event reads one `role.SettingsSnapshot`, only when a step needs it, and
  every step reads that snapshot; the next event reads the store again, and nothing is cached between events. Pinned by
  `TestSpawnHookReadsSettingsAndTheRootOnce`, which counts one read for a direct and for a managed spawn, and
  `TestSpawnHookOneEventOneSnapshot`, which changes the store after the first read).
- A managed spawn resolved the dispatch root (`git rev-parse --show-toplevel`) and read the record outside the lock three times:
  the preview, the issuance, and the preview the issuance runs again inside itself (source `fallback-dispatch.ts:237-267`); port:
  fixed (the preview's selection keeps the canonical root and the attempt it read, and `IssueManagedSpawnSelection` pins the
  directory below that root, takes the record's lock and reads the record once under it; git runs once per managed event. The
  re-check under the lock stays and now also requires the role and the candidate the preview saw, so the candidate the hook answers
  with is the one the issuance checked; a record that changed after the preview (another attempt, another candidate, an issuance to
  another call, a dispatch no longer active) is refused and not written. `IssueManagedSpawnEnv` keeps its signature and runs the
  preview once before the same issuance. Pinned by `TestSpawnHookReadsSettingsAndTheRootOnce` (one git call through a logging
  `git` on `PATH`) and `TestManagedSpawnIssuanceRechecksTheRecordUnderTheLock`).
- Supersedes known-defects.md, section "Seeded from the corpus recording", item beginning "The spawn hook runs the same `git
  ls-files --error-unmatch` three times": now port: fixed (the port's hook runs no `ls-files` at all, since the project layer is gone
  (decision 7), and the one git call of a managed spawn is the dispatch root's, made once).
- The preview kept the root as a string, so a workspace replaced after the preview (renamed, with a link to another directory put in
  its place) made the issuance record into the other directory's ledger (verification round 1); port: fixed (the preview keeps the
  root's device and inode, `ManagedSpawnResolver.Preview`; the issuance opens the root and refuses a directory that is not that one
  before it creates or writes anything below it: "managed spawn root changed since its preview"; the spawn is denied and neither ledger
  is written. Pinned by `TestSpawnHookManagedRootReplacedBetweenPreviewAndIssuanceIsDenied`).
- A message wrapped in the guard offers one dispatch source for each role without a prompt, and each source ran git and read the
  record again (three git calls for the default settings; verification round 1); port: fixed (one `ManagedSpawnResolver` per event
  resolves the root once, with its error, and previews each distinct source once. Pinned by
  `TestSpawnHookGuardedManagedSpawnResolvesTheRootOnce`).
