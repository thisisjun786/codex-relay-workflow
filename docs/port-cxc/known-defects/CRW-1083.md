# CRW-1083 — recall index assumes an append from a size increase alone

Source: CXC v0.2.40 (commit 3c1459ac) `plugins/codexclaw/components/recall/src/ingest.ts:68,222-246` (freshness is size plus millisecond mtime; a larger file is read from the previous cursor on); the Go side is `internal/recall/ingest.go`, `internal/recall/indexdb.go` and `internal/recall/cli.go`. Found by the 10-10 CXC improvement review, A8-02.

- A rollout replaced or rewritten into a larger file was read from the old cursor: the old prefix stayed indexed, the new prefix was skipped, and the new size and mtime made the status report no stale file (source `ingest.ts:222-246`, recorded case `growth-rewrite-kept`); port: fixed (the file row stores the file identity, device and inode as `file_id`, and a `checkpoint`: a digest of the first and the last 4096 bytes of the prefix that was indexed. An append is chosen only when the file is the same file, grew, still holds those windows at the consumed offset, and has exactly the rows the cursor counts; anything else replaces the file's rows in the same write transaction, so old terms leave both FTS lanes and the new ones enter. Schema version 4. Pinned by `TestIngestReplacementByALargerFileDropsTheOldMessages` (in place and new inode), `TestIngestTruncationDropsTheCutMessages` (a cut file regrown past its old size), `TestIngestGenuineAppendStaysAnAppend`, `TestIngestPartialLineAppendIsAppendedOnceCompleted`, `TestIngestCursorDisagreeingWithTheRowsRebuilds`, and the recorded case `growth-rewrite-kept`, whose step 1 `TestIngestRecordedOracle` now expects replaced rows).
- A rewrite that kept the size and the integer-millisecond mtime was skipped, so its old text stayed indexed and freshness reported no change (source `ingest.ts:68-73,215`, recorded case `same-fingerprint-rewrite-kept`); port: fixed for a replacement by another file (the default fingerprint also compares device and inode, `TestIngestInodeReplacementWithTheSameMetadataIsRebuilt`) and for an in-place rewrite through the explicit strong path `crw recall chat index --verify` (`--status --verify` reports without writing). The default refresh stays metadata-only for an in-place rewrite that keeps size and mtime: the recorded case still holds there, and every search does not hash every rollout. `TestIngestVerifyCatchesASameMetadataRewrite`, `TestRecallChatIndexVerify`.
- Status distinguishes the two meanings: the metadata-only output and JSON are unchanged (existing consumers of `staleFiles` read the same thing), and the strong path adds `"freshness": "content-verified"` to the JSON and `(content-verified)` after the stale count in the text; `IndexFreshness.Verified` carries it in the library. `--verify` is not listed in `--help` or in the `crw-recall` skill: both are pinned by the corpus (14 help fixtures) and by the skill-port record; it is named here and in the tests.
- The checkpoint is bounded and does not prove an arbitrary prefix rewrite: a rewrite that keeps size, mtime, device, inode and both 4096-byte windows of the consumed prefix is not found, by either path. The producer of a rollout is assumed to append whole lines to the end of the file; a prefix up to 8192 bytes is covered entirely.
