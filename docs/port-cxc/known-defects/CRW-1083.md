# CRW-1083 — recall index assumes an append from a size increase alone

Source: CXC v0.2.40 (commit 3c1459ac) `plugins/codexclaw/components/recall/src/ingest.ts:68,222-246` (freshness is size plus millisecond mtime; a larger file is read from the previous cursor on); the Go side is `internal/recall/ingest.go`, `internal/recall/indexdb.go` and `internal/recall/cli.go`. Found by the 10-10 CXC improvement review, A8-02.

- A rollout replaced or rewritten into a larger file was read from the old cursor: the old prefix stayed indexed, the new prefix was skipped, and the new size and mtime made the status report no stale file (source `ingest.ts:222-246`, recorded case `growth-rewrite-kept`); port: fixed (the file row stores the file identity, device and inode as `file_id`, and a `checkpoint`: a digest of the first and the last 4096 bytes of the prefix that was indexed. An append is chosen only when the file is the same file, grew, still holds those windows at the consumed offset, and has exactly the rows the cursor counts; anything else replaces the file's rows in the same write transaction, so old terms leave both FTS lanes and the new ones enter. Schema version 4. Pinned by `TestIngestReplacementByALargerFileDropsTheOldMessages` (in place and new inode), `TestIngestTruncationDropsTheCutMessages` (a cut file regrown past its old size), `TestIngestGenuineAppendStaysAnAppend`, `TestIngestPartialLineAppendIsAppendedOnceCompleted`, `TestIngestCursorDisagreeingWithTheRowsRebuilds`, and the recorded case `growth-rewrite-kept`, whose step 1 `TestIngestRecordedOracle` now expects replaced rows).
- A rewrite that kept the size and the integer-millisecond mtime was skipped, so its old text stayed indexed and freshness reported no change (source `ingest.ts:68-73,215`, recorded case `same-fingerprint-rewrite-kept`); port: fixed for a replacement by another file (the default fingerprint also compares device and inode, `TestIngestInodeReplacementWithTheSameMetadataIsRebuilt`) and for an in-place rewrite through the explicit strong path `crw recall chat index --verify` (`--status --verify` reports without writing). The default refresh stays metadata-only for an in-place rewrite that keeps size and mtime: the recorded case still holds there, and every search does not hash every rollout. `TestIngestVerifyCatchesASameMetadataRewrite`, `TestRecallChatIndexVerify`.
- `--status --verify` on an index of an older schema (version 2 or 3: no `file_id`, no `checkpoint`) that no writer has migrated yet failed with "no such column: file_id"; port: fixed (the read-only status checks the columns first and, when they are missing, reports the counts from metadata with `"freshness": "rebuild-required"` (and `(rebuild-required)` in the text, `IndexFreshness.RebuildRequired` in the library) instead of `content-verified`; the status read does not change the index, and the next writing refresh rebuilds it. `TestVerifiedStatusOfAnOlderSchemaIndexSaysRebuildRequired`).
- Status distinguishes the two meanings: the metadata-only output and JSON are unchanged (existing consumers of `staleFiles` read the same thing), and the strong path adds `"freshness": "content-verified"` to the JSON and `(content-verified)` after the stale count in the text; `IndexFreshness.Verified` carries it in the library. `--verify` is listed in `crw recall chat index --help` (the synopsis `[--rebuild] [--status] [--verify] [--json]` and a flag line) and in the `crw-recall` skill (synopsis and flag notes; CRW-1168). The oracle's usage has no `--verify`, so the 13 replayed help fixtures that print the usage are claimed in `contract/notes/cxc/CRW-1083.json` (intentionally changed: the usage text only, no behaviour), the skill-port record `port/cxc/records/crw-recall.json` records the skill edit, and the unreplayed pending fixture `cli__memory-allow-write__non_allow_write_routes_to_recall` keeps the oracle's usage as recorded. `TestUsageListsChatIndexVerify`.
- The checkpoint is bounded and does not prove an arbitrary prefix rewrite: a rewrite that keeps size, mtime, device, inode and both 4096-byte windows of the consumed prefix is not found, by either path. The producer of a rollout is assumed to append whole lines to the end of the file; a prefix up to 8192 bytes is covered entirely.
- Opening the history store for the repeat penalty went through `openIndex`, whose schema step drops the derived rows of an index of another version, so the first SessionStart on an index written by an earlier version emptied it and no ingest followed; port: fixed (the hook's store, `openHitCountStore`, never applies the schema or resets derived rows: it opens the file, waits at most one second (less, near the end of the hook's time) for the lock and creates only `recall_hit_counts` when that table is missing. An index of another schema version is not served to a reader either: `openIndexReadOnly` refuses it with the version in the message, so the cwd listing and a `--no-refresh` search fall back to the scan ("index unavailable ... served by scan"), and only a writer that goes on to ingest (a refreshing search, `crw recall chat index`) resets and rebuilds it. The status keeps reading such an index (`openIndexReadOnlyAnySchema`) and says `rebuild-required`. `TestSessionStartHistoryLeavesAnOlderSchemaIndexAlone`, `TestOlderSchemaIndexIsNotServedToReaders`).
- The metadata-only freshness never read the stored file identity, so `--status`, a `--no-refresh` search and the session banner counted zero stale files for a rollout replaced by another file of the same size and millisecond mtime, which a refresh rebuilds; port: fixed (`measureIndexFreshnessMode` reads `file_id` whenever the index has the column and compares it as the refresh does. `TestStatusSeesAnInodeReplacementWithTheSameMetadata`).
- A directory that could not be listed was kept out of the pruning but not out of the verdict: the verified status said `content-verified` with an untruncated zero for files it never looked at; port: fixed (`IndexFreshness.UnreadDirs` counts them, the counts are then a lower bound (`Truncated`), nothing is `Verified`, and the report says `"freshness": "incomplete"` with `"unreadDirs"`; a refresh reports the number in `IngestResult.UnreadDirs` and on stderr, and a search of the index warns. `TestUnreadableDirectoryIsNeverReportedAsAComplete`).
- Stays as designed (the issue's own answer: the checkpoint does not claim to verify an arbitrary prefix, the producer is assumed to append, and not every search hashes every rollout): a grown or same-size in-place rewrite that keeps both 4096-byte windows of the consumed prefix and changes only the bytes between them is not found by the default refresh or by `--verify`; the bullet above on the bounded checkpoint is the record of that limit, and a larger or complete check would hash each consumed prefix on every append.
