# CRW-1298 — register refuses a child sandbox that cannot reach the daemon, and doctor and the skills match the daemon path

Source: CRW's own design, not the CXC oracle (CXC v0.2.40, commit 3c1459ac, lists `emit`, `intent-claim` and
`intent-disposition` among `OFFLINE_COMMANDS` and has no sandbox check at `register`). A child reports only through
the relay daemon's `control.sock` (CRW-1286.md), which Codex refuses to a sandbox without network access
(CRW-1296.md). The Go files are `internal/relay/registry/cli.go` (`registerPrecheck`, `refuseUnreachableChild`),
`internal/bridge/settings/relay_reach.go` (`RelayChildReaches`, the rule `internal/bridge/create.go`
`refuseReadOnlyChild` also asks) and `internal/relay/cli/commands_list.go`, `doctor.go` (`daemonRequiredCommands`).

- `relay register --child-settings` refuses a child whose recorded sandbox cannot connect to the daemon's `control.sock`:
  a `readOnly` policy (even with `networkAccess`, since a relay child writes its work), or a `workspaceWrite` one
  whose `networkAccess` is not true (an omitted one is the default false), or any other type (`externalSandbox`). It is
  an input error: exit 2, `{"error": "refused", "reason": "unsupported_sandbox_type", "detail": ...}`, answered by
  `registerValidate` (the dispatcher's `Validate`, which runs before it admits the store), so nothing is written and no
  state directory is created; the other input errors of register leave an initialized, empty store, as the fence's do. The detail names `danger-full-access` and
  `workspace-write` with network access as the two sandboxes that work and says the settings are never changed.
  `danger-full-access` and `workspace-write` with `networkAccess` true register as before, and `--parent-settings` is not
  judged. A sandbox that is not a readable policy object is not judged here; recording the settings refuses it
  (`settings_mistyped`, `unsupported_sandbox_type`) as before. The reason is the existing `unsupported_sandbox_type` of
  `contract/schema/relay-exit-codes.json`; no reason is added to the frozen set. One rule serves both entrances:
  `settings.RelayChildReaches` (bridge creation passes the sandbox mode and the expected policy, register passes the
  recorded policy); port: fixed in source, a deliberate deviation (CXC accepts any sandbox). Pinned by
  `TestRegisterRefusesAChildSandboxThatCannotReachTheDaemon`, `TestRegisterAcceptsAChildSandboxThatReachesTheDaemon`,
  `TestRelayChildReaches` and the create-time tests of CRW-1296.md, which stay green. `settings-record` is not judged:
  the issue names `register --child-settings`, and a record written by hand states what the host reported.
- `doctor`'s `actorReachability.offlineCommands` no longer lists `emit`, `intent-claim` and `intent-disposition`; they are
  the new `actorReachability.daemonRequiredCommands` (in that order), and `hostRequiredCommands` (the commands that need
  the App Server socket) is unchanged. Deviation from the CXC doctor, which lists the three as offline; port: fixed in
  source. Every golden and test that read the lists was found by `zgrep offlineCommands` over the goldens and by
  `grep` over the tests, and each is recorded here:

    `CLI20`, `CLI24`, `CLI25`, `CLI26`, `CLI27`, `CLI32`, `CLI33`, `CLI34`, `CLI37`, `TestDoctor_expect_inode_mismatch_refuses_with_python_reason`,
