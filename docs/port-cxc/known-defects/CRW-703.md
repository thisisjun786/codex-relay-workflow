This file records what the two 10-minute campaigns of this issue found (seed 20261006, head

## Defects

- The oracle's shell write destination reader misses a destination a real shell write reaches whenever a
  wrapper word or option hides the writing verb (`env -i sudo tee /m/a`, `nohup timeout 5 tee /m/a`,
  `timeout 5 perl -i -pe ... .`, `sudo -u root tee /m/a`), when the write hides in a nested `-c`/`eval`
  string (`bash -c 'echo x > /m/a'`), when the target follows `2>` or `<>` (`echo hi > /m/n.md 2> /m/err`,
  `cat <> /m/a`), or when an interpreter program's escape is not decoded (`python3 -c "open('/m/a\nb','w')"`);
  the port names these (source `shell-write-destinations.js:276-311,209-235,505-549`; port: fixed by
  CRW-517, security, and pinned `open` in `internal/dev/cxcfuzz/testdata/shellwrite/cases.json` so the
  campaign divergence stays visible).
- The oracle's `Path(...)` reader names the text between its first and last quote rather than the path
  Python builds (`Path('/tmp/b', '/m/a')`), and a `python3 -c` program's `\xNN` escape is not decoded, so a
  write the oracle never sees reaches the memories root; the port names the join of the literal parts and
  the decoded path (source `shell-write-destinations.js:535-549`; port: fixed by CRW-517, security, pinned
  `intentionally-changed` with the reason recorded).
- The oracle's reader does not read a triple-quoted Python literal's physical line breaks (CR/LF/CRLF) as
  Python's source decoding does, nor a same-quote run inside the literal, so a destination written that way
  is missed; the port reads it (source `shell-write-destinations.js:505-549`; port: fixed by CRW-650 and
  CRW-678, security, pinned `intentionally-changed`).
- The oracle's memory write gate compares the destination text only, so a symlink in the workspace that
  leads into the memories root, a `..` after such a link, and a `CODEX_HOME`/home that is itself a link are
  all allowed without a grant, although the write lands in the root; the port follows the link and denies
  them (source `memory-write-gate.js:122-126,154-160` and the root at :112-115; port: fixed by CRW-518,
  security, pinned `intentionally-changed`).
- The oracle's `patchTargets` reads `*** Add/Update/Delete/Move File:` and `+++ b/<path>` but not
  apply_patch's actual move destination `*** Move to: <path>`, so a move into the memories root is allowed;
  the port reads it (source `memory-write-gate.js:170-186`; port: fixed by CRW-518, security, pinned
  `intentionally-changed`).
- The two targets' comparators canonicalise a brand-carrying deny reason: the oracle's reason says
  `[codexclaw MEMORY-WRITE-GATE]` and `cxc memory allow-write`, and the port renames them to
  `[crw MEMORY-WRITE-GATE]` and `crw pabcd memory allow-write` (contract/schema/cxc/name-substitution.json
  R23/R32/R33 and the cli table). The `memorygate` comparator applies exactly those renames to both sides
  before comparing, so the difference is not reported as a divergence; the pinned `identical` cases record
  the oracle answer in the port's spelling for the same reason (source `memory-write-gate.js:238-258`;
  port: fixed by the rename table, no behaviour change).
- Not measured by this target, and left to a follow-up: the memory gate's authorization legs (the CLI grant
  and the prompt marker) are exercised with a fresh grant-less session, so a divergence in grant or marker
  consumption is outside what this campaign could find (source `memory-write-gate.js:262-293`; port:
  unchanged, the existing `internal/pabcd/hook/memorygate_test.go` covers those legs).
