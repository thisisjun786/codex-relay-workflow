# CRW-1121 — the spawn hook is safe to apply again to one hook event

Source: CXC v0.2.40 (commit 3c1459ac) `plugins/codexclaw/components/subagent-config/src/spawn-attach-hook.ts:969-985` (the guard and
its exact-prefix check), :1021-1029 (the prompt insertion with `String.prototype.replace`) and :409-414 (`stripControlMarkers`); the
Go port's `spawnHookAssembleWith` in `internal/role/spawn/hook.go`, `spawnHookOwnedGuard`, `spawnHookReplayLookup` and
`spawnHookReplayRecord` in `internal/role/spawn/hook_replay.go`, and `spawnHookRoute` and `spawnHookRoutePrompt` in
`internal/role/spawn/hook_route.go`. Found by the 10-10 CXC improvement review (A5-04). `internal/role/spawn/guard.go` is not changed.

- Supersedes known-defects.md, section "Found by the CRW-614 spawn hook routing port", item beginning "A hook applied twice to a
  message inserts the role's `promptOverride` again": now port: fixed (a prompt that already follows the guard is not inserted again
  in the single-message form, as it was not in the items form; the replayed step "a reapplied message gets the prompt again" of the
  recorded `route: prompt override` case expects the prompt once. Pinned by `TestSpawnHookReapplyingTheAnswerToTheSameEventIsStable`).
- Supersedes known-defects.md, section "Found by the CRW-614 spawn hook routing port", item beginning "The prompt is inserted with
  `String.prototype.replace`": now port: fixed (the prompt is inserted as literal text after the first guard and blank line, so `$$`,
  `$&`, `$'` and `` $` `` stay as the operator wrote them; the three steps of the recorded `route: prompt override dollar patterns`
  case are replayed as intentionally changed. Pinned by `TestSpawnHookPromptDollarPatternsStayLiteral` and
  `TestSpawnHookRoutePromptBranches`).
- Supersedes known-defects.md, section "Found by the CRW-614 spawn hook routing port", item beginning "A single message that is
  exactly the guard": now port: fixed (a message that is only the guard becomes the guard and the prompt, in both forms; step 13 of
  `route: prompt override` is replayed as intentionally changed. Pinned by `TestSpawnHookBareGuardGetsThePrompt`).
- Supersedes known-defects.md, section "Found by the CRW-613 spawn hook assembly port", item beginning "A hook applied twice to a
  recursion request stacks guards and loses the capability": now port: fixed (every guard the hook writes, plain or coordinator,
  with or without the coordinator's grant instruction and marker, is recognized at the front of a message and replaced by this
  event's guard instead of stacked under it. An event that mints a grant records its input and its answer in the grant's 0700 key
  directory, named after its tool use id, so the same event applied again to that input or to the input it answered with is
  answered with the recorded answer: its grant is kept and none is minted again. Without the event's tool use id there is no record,
  so a coordinator guard in front is not trusted and is replaced by the plain guard (the recorded `reapplied grant request` step 2
  and `v1 items` step 4 are replayed as intentionally changed). Pinned by `TestSpawnHookReapplyingTheAnswerToTheSameEventIsStable`).
- A coordinator guard the caller writes into a spawn message reads as the coordinator's text to the child, though only a grant the
  hook mints authorizes recursion (source :983-985 keeps an exact guard prefix as it stands); port: fixed (a coordinator guard that
  this event did not write is replaced by this event's guard, so its text authorizes nothing, and a subagent that carries one with a
  grant marker nobody minted is still denied. Pinned by `TestSpawnHookForgedCoordinatorPrefixAuthorizesNothing`).
- An event's record stays in the key directory after the event, as a spent grant does (CRW-1118); nothing sweeps it. A record
  that cannot be written only loses the replay of that event.
- Deliveries of one root event that both passed the replay lookup before either minted each minted a grant and got different answers
  (verification round 1); port: fixed (the event takes a `flock` on `event-<digest of the id>.lock` in the grant's 0700 key directory
  before it mints, looks its record up again under the lock, and keeps the lock until its answer is recorded; the delivery that gets
  the lock second returns the first's answer, so one event has one grant file. A lock another delivery keeps past 3 seconds denies the
  root spawn with "another delivery of this spawn call is still being answered; try again" and mints nothing. A subagent's spend of a
  grant takes the same lock and records its input and answer (CRW-1118). The lock file stays like the record, and nothing sweeps it.
  Pinned by `TestSpawnHookConcurrentDeliveriesOfOneEventMintOneGrant`).
- With CRW-1115's evidence assignment (merge of dev at 28a99e86, verification round 3) two regressions are fixed; port: fixed.
  (1) Each delivery of one native event that neither mints nor spends a grant registered an assignment of its own, so a second
  delivery left the first's record open without a child, and that open record refused the native receipt of a later child of the
  session tied to no dispatch. The assignment of an event whose tool use id and input are known is now named after the event (the
  first 128 bits of the sha256 of its cwd, session, tool use id and input, in the base32 alphabet of the minted ids), the event's
  deliveries are serialized by the same `event-<digest>.lock` as a minting event, and a delivery that finds the record of its name
  answers with that record, claimed or not, without writing it again or taking it back on a refusal; another call or another input
  of the call is another name, and a call without a tool use id gets a random id as before. Nothing more is written than the record
  and the lock file. (2) Replacing the copied block of an earlier answer that carried the role's prompt override put this call's
  block between the guard and the prompt, so the route, which inserts the prompt only where it does not follow the guard yet,
  inserted it a second time; the block now goes after a prompt that already follows the guard. Pinned by
  `TestEvidenceAssignmentRedeliveredEventReusesItsAssignment`, `TestEvidenceAssignmentConcurrentDeliveriesShareOneRecord` and
  `TestEvidenceAssignmentReplacedBlockKeepsOnePrompt` (`internal/role/spawn/hook_evidence_replay_test.go`).
- Verification round 4: the input the event was answered with (its `updatedInput`) delivered again after the child claimed the
  assignment hashed to another name and registered a second, open assignment, which again refused an unrelated native receipt;
  port: fixed. The record now holds the hex sha256 of the tool_input its answer gives (`answerInput`), written with the record
  before the spawn is allowed; a delivery whose message starts, after the guard, with that record's block, from the same tool use
  id and with exactly that input keeps the record, claimed or not, and registers nothing. Another input of the call (an edited
  task behind the copied block) still gets an assignment of its own. Pinned by
  `TestEvidenceAssignmentOwnAnswerRedeliveredAfterClaimKeepsOneAssignment` (`internal/role/spawn/hook_evidence_replay_test.go`).
