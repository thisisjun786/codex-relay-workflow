# CRW-758 — the crw pabcd orchestrate verb row and its corpus claim

Source: CXC v0.2.40 (`3c1459ac`) `plugins/codexclaw/components/pabcd-state/src/cli.ts` :143-152,
the terminal `orchestrate` branch, and the three libraries it reaches:
`orchestrate-cli.ts` `parseOrchestrateCliArgs` :218-300, `runOrchestrateCli` :466-1131 and
`renderOrchestrateParseError` :414-419. Ported to Go as `internal/harness/pabcd_cli.go`
`orchestrateVerb` plus the row in `internal/harness/pabcd.go` `Verbs()`, with the CLI-level cases
of `test/attest-batch.test.ts` and `test/attest-shape-hint.test.ts` as
`internal/harness/pabcd_orchestrate_test.go`. The orchestrate fixtures this row unblocks
(`cli__orchestrate*`, `cli-help__orchestrate*`) are claimed in `contract/notes/cxc/CRW-758.json`.

- The terminal branch and the library disagree about where a parse error goes. `cli.ts` :146-149
  writes `renderOrchestrateParseError(parsed)` to stderr and exits 1 before `runOrchestrateCli` is
  called, so the library's own parse-error arm (`orchestrate-cli.ts` :470-476, which returns the
  same text as a `CliResult`) is unreachable from the oracle's own entry point and would print it
  on stdout instead (source `cli.ts` :143-152 against `orchestrate-cli.ts` :470-476); port: kept
  (`RunOrchestrateRead` is the library's entry and keeps the arm, and the row reproduces the
  terminal branch by rendering the refusal on stderr itself, so `cli__orchestrate__unknown_verb_names_current_phase`
  replays identical; `TestPabcdOrchestrateRow/parse_error_goes_to_stderr` pins the stream).
- The oracle reads `process.env` only in this branch, so `CODEX_THREAD_ID` drives the implicit
  status session while every other `crw pabcd` row passes the library an empty environment (source
  `cli.ts` :151; the library's `nativeEnv` parameter defaults to `{}`, `orchestrate-cli.ts` :468);
  port: kept (the row passes the process environment for both `Native` and `Process`, which is what
  the terminal entry did, and no other row changes; the corpus fixtures that set `CODEX_THREAD_ID`
  replay identical).
- The oracle's terminal branch has no signal path at all: it is a short-lived process that parses
  argv, runs one command and exits, and the mutating half reaches its own session lock with no
  cancellation, so a SIGINT during a lock wait ends the process rather than the wait (source
  `cli.ts` :143-152 against `orchestrate-cli.ts` :549-1131); port: kept (the row is a plain `Run`
  row with no context, as the oracle's is, and `RunOrchestrateTransition` takes none; the
  interrupt-aware rows are the metric and divergence writers CRW-627/CRW-632 converted, whose
  library entry points do take a context).
- Supersedes `known-defects/CRW-384.md`, item beginning "The A>B review binding (source `:49-92`, `:688-691`)":
  now port: fixed (both halves closed: CRW-755 ported the two gates in `orchestrate_review_binding.go`,
  and this issue adds the `crw pabcd orchestrate` verb row the item also named, so the row now
  reaches `RunOrchestrateTransition` from the terminal).
- The row is registered with `Run`, so the invocation context `serve` cancels on the first SIGINT
  (`cmd/crw/main.go:71`) does not reach `RunOrchestrateTransition`, and a mutation whose lock wait
  is already past can still publish its state and ledger rows after that signal, where the oracle's
  process dies at once (source `cli.ts` :143-152 against the repository's SIGINT policy; found by
  the Devin review and the Codex review, `kind: bug`, Codex P1); port: pending (nine rows behave
  this way, `review-round` among them with the same bounded `state.WithSessionLock` retry loop;
  the two `RunContext` rows are the metric and divergence writers, whose lock waits had no deadline
  until CRW-627/CRW-632. Closing it needs the context threaded into
  `internal/pabcd/cli/orchestrate_transition.go`, which is another issue's file and outside this
  change's edit regions, so it is a follow-up candidate rather than a `RunContext` wrapper here
  that would only relabel a completed write as interrupted).
