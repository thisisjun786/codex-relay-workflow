# CRW-793 — a published goalplan write and the ledger rows that depend on it

Source: the goalplan writer is `plugins/codexclaw/components/pabcd-state/src/goalplan.ts` `writeGoalplan`
at CXC v0.2.40 (commit 3c1459ac): it writes a temp file, publishes it with `renameWithRetry`, and
returns whatever the publication threw. The steering transaction is
`plugins/codexclaw/components/pabcd-state/src/steering.ts` `applySteeringBatch` :253-333. The Go port is
`internal/pabcd/goalplan/write.go` (`writePublishAt`, `WriteGoalplan`) and
`internal/pabcd/goalplan/steering.go` (`steeringApplyLocked`), with the other callers listed below. The
oracle never syncs the published file or its directory (`known-defects.md`, "Found by CRW-479 state
publication durability"), so it cannot fail after the rename; CRW-479 added the directory fsync to the Go
port, which is what makes a post-rename failure reachable.

- `writeGoalplan` reports a failure that happened after the rename (opening the plan directory for the
  sync, or the directory sync itself) the same way it reports a failure that published nothing, so the
  caller cannot tell that the plan at the final path is the new one; `steeringApplyLocked` then returns
  that error without appending its ledger rows, and because the idempotency key is already in the
  published plan every retry is answered duplicate, so the `steered` row and the
  `dependency_registered` rows for that batch are lost for good (source
  `plugins/codexclaw/components/pabcd-state/src/goalplan.ts:915-942` with
  `steering.ts:276-333`; the oracle has no recorded case, because it never syncs after the rename);
  port: fixed (a record-file data-loss defect, fixed by decision: `writePublishAt` wraps the two
  post-rename failures in CRW-744's `*state.PublishedError`, and `steeringApplyLocked` treats
  `state.Published(err)` as a written plan, appends the `steered` and `dependency_registered` rows as
  on success and answers `applied` with the warning `goalplan '<slug>' was published but its directory
  could not be synced: <err>`; a pre-rename failure is still a plain error, the published plan is never
  rolled back, and the duplicate path is unchanged; no corpus fixture drives a directory sync failure, so
  none is retagged, and the cases are in `internal/pabcd/goalplan/steering_published_test.go`).
- The other `WriteGoalplan` callers have no reconciling step for a published-but-failed write. They were
  not changed by this issue, which fixes only `steeringApplyLocked`; the oracle's counterparts read the
  same way, so this is not a parity break (oracle `goalplan.ts` `writeGoalplan`; Go callers named
  below); port: pending.
  - `internal/pabcd/cli/review_round_run.go:201` (`review-round run`, open packet): a published round
    state whose directory sync failed is read as a failed write, so the launch is reported as failed
    though the plan holds it.
  - `internal/pabcd/cli/review_round_run.go:223` (`review-round abort`): the abort is reported as failed
    though the plan holds the closed round.
