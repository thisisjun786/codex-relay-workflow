# CRW-851 — a backslash-newline between the tokens of an exec callee hides the call from the memory gate

Source: the 2026-10-09 re-check (`/state/crw/mgmt/recheck-20261009/g4`, rows RC-851-v3 and RC-851-v3d) of the CRW-851 exec, eval
and compile reader on dev (`09e5c5bcc`), in `internal/pabcd/hook/shellwrite_verbs.go` (`shellWriteExecCallee`,
`shellWriteExecCalleeExpr`). Approved by the owner on 2026-10-09 as a single-bypass fix (Lina request
mgmt-approved-20261009-0651-951-851). The reproductions are the rows of `internal/pabcd/hook/testdata/shellir/rows/21-crw-851-line-continuation.txt`
(indexed in `reproductions.tsv`), judged by the memory gate, the GitHub post guard and the worktree guard in `TestReproductionRows`.

## 2026-10-09 line continuation in the callee

- `python3 -c 'import builtins; builtins \<newline>.exec("open(<memory>/a, ...).write(...)")'` and the parenthesized callee
  `(builtins \<newline>.exec)(...)`: Python joins two physical lines at a backslash directly followed by a newline anywhere
  between two tokens outside a string literal, so both run `builtins.exec`; the reader skipped only blanks around the attribute
  dot and between the callee and its parenthesis, so the call was not identified, the memory verdict was `none` and the file
  was created (shown with a temporary HOME and CODEX_HOME, no real home touched); port: fixed, security (the callee
  identification reads a backslash followed by a newline, also CR LF or a lone CR, as spacing wherever it skips blanks: before
  and after the dot, before the module name of a parenthesized callee, and between the callee and its parenthesis, for `builtins`
  and `__builtins__` and for `exec`, `eval` and `compile`; one helper, `shellWriteExecSkipSpaceBack`).
- The same cause hid a plain `exec \<newline>(src)` and `(builtins.exec) \<newline>(src)`; port: fixed (same helper).
- Allow counterexamples kept: the text `builtins \<newline>.exec(x)` inside a string literal that is only printed, `re \<newline>.compile(...)`
  and `(re \<newline>.compile)(...)` of a module that is not builtins, `runner \<newline>.exec(...)`, `mybuiltins \<newline>.exec(...)`, a call
  of `myexec`, and an ordinary program that uses a continuation; port: kept (memory verdict `none`; the worktree guard still denies
  a program that names exec, eval or compile as a run-time name, with or without the continuation, as before).
- A backslash with a blank before its newline is not a continuation (Python rejects it) and stays a character of its own; port: kept.
- Not changed, recorded: the same continuation between `open` and its parenthesis (`open \<newline>(file=..., mode="w")`) is still
  not identified by `shellVerbCallKind` and gives memory `none`; it is a separate residual outside this approval and is not fixed here.

## 2026-10-09 line continuation, correction round of the pre-merge evaluation (8fdf930c0)

- `python3 -c '... runner . builtins \<newline>.exec(x)'` (and `runner \<newline>. builtins.exec(x)`): `builtins` is an attribute of
  another object here, a different callee that writes nothing. The attribute-chain test in front of the module name looked only
  at the one raw character before `builtins`, so blanks or a continuation between the dot and `builtins` hid the chain and the
  call was read as `builtins.exec` (a false positive that asked a grant for a harmless program; the blank-only form
  `runner . builtins.exec(x)` had the same gap before the continuation fix). The test now looks back past blanks and
  continuations with `shellWriteExecSkipSpaceBack`, as the forward dot does; port: fixed. Rows `CRW-851-lc-b09` to `lc-b11`
  (memory none), `TestCRW851AttributeChainBeforeBuiltins`.
- The compile row `CRW-851-lc-07` could not fail when the continued `builtins.compile` was not recognised (the enclosing
  `exec(<call>)` is unreadable on its own and gives the same attempt). `TestCRW851ContinuedCompileNamesItsDestination` reads the
  destination of the continued compile itself (a program that only compiles and never calls exec on a literal) through
  `ShellWriteDestinations` and `memoryGateClassify`; it fails when the compile half of the fix is reverted; port: test added.
- `TestCRW851ContinuationRowsThroughTheMemoryGate` runs the rows of the continuation file through `HandleMemoryWriteGate`: an
  E row is denied without a grant and consumes one grant, a control passes with no grant and spends none.

## 2026-10-09 line continuation, correction round 2 (verifier P0 on 9f000f6a7)

- `python3 -c 'import builtins; x = ...<newline>builtins.exec("open(<m>/a,...)")'` (and `x = 1.<newline>builtins.exec(...)`) gave
  memory `none` and really wrote the file. The attribute-chain look-back added in the previous round used the reader's general
  spacing skip, which also crosses a plain line end, so the dot that ends the previous statement was taken for the dot of
  `runner.builtins`. A plain line end (LF, CR LF, lone CR) ends the logical line and is no spacing before the module name; only
  blanks and a backslash-newline continuation are skipped there (`shellWriteExecSkipInlineSpaceBack`). A chain split by a
  newline inside brackets is read as two statements: the module is treated as called, the side that over-reports. The
  regression came from the previous round, not from dev (dev read the one raw character before the module name); port: fixed,
  security. Rows `CRW-851-lc-12` to `lc-17` (memory attempt), `TestCRW851NewStatementBeforeBuiltins`; the controls
  `lc-b09` to `lc-b11` and `TestCRW851AttributeChainBeforeBuiltins` stay.
