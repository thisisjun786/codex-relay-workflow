# CRW-1488 — a subagent call had no go: the verifier's go_root reached crw.verify only

Source: CRW's own design, not the CXC oracle (CXC v0.2.40, commit 3c1459ac): the oracle has no flow engine. The Go files are `internal/crwconfig/verifier.go` (`VerifierTools.GoEnv`), `internal/flow/cli/repository_tools.go` (`repositoryTools`), `internal/flow/cli/process.go` (the run's `engine.Config.Tools`), `internal/flow/engine/tools.go` (`RepositoryTools`), `internal/flow/engine/session.go` (`sessionPacket`), `internal/flow/engine/call.go` (`ThreadSpec.Tools`, `ForkSpec.Tools`) and `internal/flow/backend/agent/thread.go` (`threadParams`, `SetRepositoryTools`), `internal/flow/backend/agent/agent.go` (`hold`), `internal/bridge/appserver/subscription.go` (`HoldThreadWith`), `internal/flow/engine/resumecli.go` (`ResumeHold.Tools`) and `internal/flow/cli/resume.go` (`resumeHold`). Found by the 1209 field trial (10-15, findings 12): the M2 architect wrote that Go was not on the subagent's `PATH` and still planned every check as bare `go`, and the design audit raised it as a P1; `verifier.go_root` was read only by `crw.verify` and the integration verifier (`laneops.go` `laneVerifierTools`).

- The go the verifier runs was given to no agent call of a run; port: fixed (with `verifier.go_root` set and the section usable, every call the run starts is given exactly the entries the verifier's command gets, `PATH=<go_root>/bin:<the run process's PATH>`, `GOROOT=<go_root>`, `GOTOOLCHAIN=local`, and nothing else: no `go_root`, an ignored section or an unreadable file give nothing, as before (`TestRepositoryToolsFromVerifierGoRoot`). An App Server call's thread/start and thread/fork carry them as the leaf config keys `shell_environment_policy.set.<NAME>`: Codex 0.154 builds one override layer from the server's `-c` overrides followed by the request's keys, each applied by its dotted path (app-server `config_manager.rs` `load_with_cli_overrides`, config `overrides.rs` `apply_toml_override`), so a leaf key changes that variable only, while a `shell_environment_policy` table would replace the server's policy (`inherit`, its own `set` entries); the fake host models that layer with a server policy of its own (`TestRepositoryToolsReachThreadShell`, `TestRepositoryToolsReachForkedThreadShell`, `TestThreadSpecCarriesRepositoryTools`). A cold `thread/resume` reloads the configuration and keeps none of the creating request's overrides (`thread_processor.rs` `thread_resume_inner`), so the run gives the backend its tools (`engine.ToolsTaker`) and every thread/resume it sends carries the same keys (`TestRepositoryToolsSurviveAColdResume`, `TestRunGivesTheBackendItsTools`), and every App Server turn's text ends with the `Repository tools` section, after the task (`TestAppServerTurnNamesRepositoryTools`). A foreground `crw flow resume RUN SCRIPT` runs the engine's resume, which gets the same tools through `engine.ResumeHold.Tools` (`TestScriptResumeGivesItsCallsTheRepositoryTools`); `crw flow run` of the engine's own command runs on the fake backend only and starts no shell, so it takes none).
- A session call's subagent could not be given an environment; port: kept (spawn_agent takes no environment and the subagent's shell is the owner session's, so the run cannot set it; the task packet of every session call, of every role, has a `Repository tools` section that names the go, the setting and its file, and the prefix `PATH=<go_root>/bin:"$PATH" GOROOT=<go_root> GOTOOLCHAIN=local` to put in front of every command that runs go and to write into every such command of a plan (`TestSessionPacketNamesRepositoryTools`); a run with no tools writes the packet of before (`TestSessionPacketWithoutRepositoryTools`). The packet's digest is journaled and never compared on a resume, so no journaled call runs again for it).
