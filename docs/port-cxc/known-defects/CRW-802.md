# CRW-802 — crwdir.Publish syncs the directory after the rename

Source: CXC v0.2.40 (commit 3c1459ac) `atomic-write.ts` (`renameWithRetry`; the oracle's rename is not followed by a directory
sync, and its writers `writeFileSync` in place). Go port: `internal/pabcd/crwdir/atomic.go` (`Publish`, `PublishChecked`,
`PublishContext`, `PublishDurable`, `syncDirIfReadable`), `swap.go` (`PublishedError`, `Published`), and the callers listed below.

- Supersedes CRW-1020.md, item beginning "crwdir.Publish itself stays without a directory fsync": now port: fixed (every
  `Publish`, `PublishChecked` and `PublishContext` fsyncs the directory that holds the file after the rename; `PublishDurable` is
  the same call. A failed sync is returned as a `*crwdir.PublishedError`, the crwdir form of `state.PublishedError`, worded "the new
  file is in place but its directory could not be synced"; `Published(err)` tells it from a failure before the rename, where
  nothing was published. Pinned by `TestPublishSyncsTheDirectoryAfterTheRename`, `TestPublishReportsAFailedDirectorySyncAsPublished`,
  `TestPublishFailureBeforeTheRenameIsNotPublished` and `TestPublishCheckedAndContextSyncTheDirectory`).
- A directory the process can write into but not open for reading (mode 0300, the write-only evidence directory of
  `crw pabcd receipt`) cannot be fsynced; the publication stands with no error, because the failed open says nothing about the disk;
  port: kept (pinned by `TestPublishInAWriteOnlyDirectoryNeedsNoDirectorySync` and `TestReceiptPublishInAWriteOnlyEvidenceDirectory`).
- Callers, each checked for what a post-rename failure means:
  - `internal/skill/search/cache.go`: a published cache file is a fresh entry; the failure is dropped, not served as a stale
    fallback; port: fixed (`TestCachePublishedWithoutDirectorySyncIsFresh`; a failure before the rename keeps the stale fallback,
    `TestCacheUnpublishedWriteStillFallsBackToStale`).
  - `internal/runtime/install/configguard` (`activationPublish`, `configLockPathsPublishChecked`: config.toml, the install manifest,
    the self-heal marker, the deactivation restore): the file is in place and the next steps depend on it (the manifest that
    undoes config.toml is written after it), so failing the activation after the rename would leave config.toml changed with no
    manifest; the publication counts as done and the sync failure is not reported; port: kept (`TestActivationPublishCountsAnUnsyncedPublicationAsDone`).
  - `activationBackup`: the staging file's own directory sync is ignored (it is renamed again), and the directory is synced after
    the final rename; a failure stops the activation before config.toml is rewritten; port: fixed.
  - `internal/review/command` (`execute`, `restore`), `internal/pabcd/cli/receipt.go`, `internal/pabcd/interview/freezecli.go`,
    `internal/pabcd/projectcfg/policy.go`: the error is returned as before, now with the file in place and the text saying so
    (the review and the freeze report the failure, the receipt run exits with it; none of them undoes the file); the review's kept
    copy already used `PublishDurable` and still fails the call before the record; port: fixed (no callers' control flow changes).
