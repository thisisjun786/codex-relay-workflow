# CRW-1185 — the self-heal report does not trust a legacy mtime cache, and an expired deadline drops nothing

Source: the CRW-1169 round-6 boundary case (a drop that starts after its deadline) and the CRW-1150 report-only leg. The oracle is CXC v0.2.40 `config-guard/src/self-heal.ts`; its mtime cache is recorded as `hook__session-start-healing-declared-features__mtime_cache_hit_skips_codex` in `contract/schema/cxc/specs/ops.json`, listed as pending under CRW-497 in `contract/notes/cxc/CRW-497.json`. The Go files are `internal/runtime/install/configguard/selfheal_report.go` (`SelfHealReport`, `SelfHealReasonCached`) and `selfheal_evidence.go` (`dropSelfHealEvidence`); the cases are in `selfheal_report_test.go` and `selfheal_evidence_test.go`.

- A recording whose deadline had already ended before its failed drop began still ran one non-blocking marker read, lock and write before it returned (the CRW-1169 deviation), so a stalled filesystem held the caller past its deadline (CRW-1185, the boundary case of CRW-1169). port: fixed (the drop does not start once the deadline has ended: no read, lock or write follows it, and the call returns at once. The legacy cache that the retirement existed for is no longer trusted by the report (below), and a probe record is still gated by its codex version and config and layer digests, so nothing it describes is vouched for past a change. A deadline that is still running is unchanged: the drop waits within it. Pinned by `TestSelfHealEvidenceFailedRecordingPastTheDeadlineDoesNotTouchTheMarker`, which stalls the marker write, expects the call to return within 2 seconds, expects the stalled write never to start and the marker bytes to stay, and expects the report to warn afterwards. Supersedes CRW-1169.md, item beginning "After CRW-1150 the publication of a verified measurement": its deviation paragraph is now port: fixed.)
- The oracle's mtime cache answered silently for a legacy-only marker (allEnabled true, cachedKeys covering the soft keys, a configMtimeMs equal to config.toml's mtime, and no probe evidence): no codex call and no output. The report path no longer trusts it (intentionally changed from the oracle, port: fixed). A marker without probe evidence is measured like any other, so a soft flag that is off still gets its notice at every SessionStart, and the report writes nothing. The cost is one `codex features list` at each SessionStart while such a marker stands, bounded by the round deadline (CRW-1150). Pinned by `TestSelfHealReportLegacyCacheIsNotTrustedAndStillWarns`, `TestSelfHealReportCacheMissOnMovedMtime` (a stale or matching mtime both measure) and the last part of `TestSelfHealEvidenceUnparsableRecordDoesNotRestoreTheLegacyCache`. Supersedes CRW-1150.md, item beginning "The oracle's own mtime cache (`allEnabled` + `cachedKeys` + `configMtimeMs`)": now port: fixed (intentionally changed; this record is its reason). `SelfHealReasonCached` is no longer returned, and the mtime helpers that only the cache read (`selfHealReportMtimeMs`, `selfHealReportCovers`) are gone; `selfHealReportMsOf` stays for the tests that write a legacy marker's configMtimeMs.
- The contract case `mtime_cache_hit_skips_codex` was claimed `identical` by `contract/notes/cxc/CRW-349.json`, so the cxc replay failed on the changed report. The claim is now intentionally-changed in `contract/notes/cxc/CRW-1185.json`, with one `set` entry: the report's `features list` call (`calls/0`), since the stub lists every soft flag on and the output stays silent. The loader refuses two non-pending claims on one fixture, so the one `identical` id was removed from `CRW-349.json`: a cross-file edit made only for that refusal, flagged for the integrator. Pinned by `TestDomain/cxc/hook__session-start-healing-declared-features__mtime_cache_hit_skips_codex`.
- Open, not changed here: the marker's `allEnabled`, `cachedKeys` and `configMtimeMs` fields are still parsed and written unchanged (the marker format is kept), and a legacy-only marker keeps its fields until a recording rewrites them. Whether the per-SessionStart probe cost of a legacy marker needs a different cache is for the owner to judge from the real hook timings.
