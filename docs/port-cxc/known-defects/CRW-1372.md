# CRW-1372 — a resumed session run's wakes staged nothing, next rebound the owner with the role store read again, and four smaller gaps

Source: CRW's own design (CRW-1316 §9 and §10, the CRW-1348 lane's evaluation), not the CXC oracle (CXC v0.2.40, commit 3c1459ac): the oracle has no session run. The Go side is `internal/flow/engine` (`sessionwake.go`, `engine.go`), `internal/flow/journal` (`sessionenv.go`, `resumeenv.go`), `internal/flow/cli` (`next.go`, `world.go`) and `internal/flow/bound` (`orchestrator.go`).

- The wake id was `(run, batch)` and a process counted its re-notifications from 0, while the relay keeps a message id for good: after a resume the first wake and as many re-notifications as the earlier process sent staged nothing ("already staged"), and the `session_wake` row still said `staged: true`; port: fixed (the run's n-th process, its n-th started row, wakes under `<batch>/e<n>`, the first process under `<batch>` as before, so a resume stages new messages; `journal.StageWake` reads the relay's answer and returns `engine.WakeNotStaged` with its reason when nothing was staged, and the row says `staged: false` with `reason`). Pinned by `TestSessionWakeIDCarriesTheRunProcess`, `TestSessionWakeThatStagedNothingIsRecordedAsSuch` and `TestStageWakeAnswersThatItStagedNothing`.
- `crw flow next` rewrote the owner's orchestrator line with the role store read again, while the live run checks its subagents against the pairs it pinned, so a role store edited while the run lived moved the hook's pairs and made every dispatch a `pair_mismatch`; port: fixed (a session run's started row pins `role_pairs`; next binds and prints the spawn formats with the newest started row's pairs and digest, and a store whose digest differs is warned about and recorded once as a `role_store_changed` row of the run, never written over the run's line; a run that recorded no pairs is bound with the store's, as before; the run process binds with the table it runs on, which is the one it pinned). Pinned by `TestSessionRunPinsItsRolePairsInItsStartedRow` and `TestNextBindsThePairsTheLiveRunPinned`.
- `agent.SessionHost.Warn` was never set, so the marker search's warnings (`no_ledger_line`, `ledger_op_differs`, `several_spawns`, `window_ended`) were dropped; port: fixed (`journal.SessionEnv` takes the run's journal and writes each as a `session_host_warning` row, for a start and a resume). Pinned by `TestSessionHostWarningsGoToTheRunJournal`.
- `BindOrchestrator` read the thread's last line and appended without a lock, so two near-simultaneous binds of one thread could both bind; port: fixed (the read and the append are one step under an exclusive lock of the flow-bound directory; the second bind reads the first's line and, the first run being live, is not bound). Pinned by `TestBindOrchestratorTwoNearSimultaneousStartsBindOne`.
- `next`'s hint said `wait_agent(targets=[<open agents>])` with no ids; port: fixed (the answer's `slots.agents` lists the open subagents and the hint names them). Pinned by `TestNextHintNamesTheOpenSubagents`.
- Deviation: the start still binds before its run process holds the run lock; with the directory lock, the run process's own bind (under its run lock) decides which of two starts holds the thread, and the other warns; the relay store's schema is unchanged (new `flow_events.kind` values and a new started-row member only); port: kept (warn and record, fail open).
