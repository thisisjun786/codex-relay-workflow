# CRW-1372 — a resumed session run's wakes staged nothing, next rebound the owner with the role store read again, and four smaller gaps

Source: CRW's own design (CRW-1316 §9 and §10, the CRW-1348 lane's evaluation), not the CXC oracle (CXC v0.2.40, commit 3c1459ac): the oracle has no session run. The Go side is `internal/flow/engine` (`sessionwake.go`, `engine.go`), `internal/flow/journal` (`sessionenv.go`, `resumeenv.go`), `internal/flow/cli` (`next.go`, `world.go`) and `internal/flow/bound` (`orchestrator.go`).

- The wake id was `(run, batch)` and a process counted its re-notifications from 0, while the relay keeps a message id for good: after a resume the first wake and as many re-notifications as the earlier process sent staged nothing ("already staged"), and the `session_wake` row still said `staged: true`; port: fixed (the run's n-th process, its n-th started row, wakes under `<batch>/e<n>`, the first process under `<batch>` as before, so a resume stages new messages; `journal.StageWake` reads the relay's answer and returns `engine.WakeNotStaged` with its reason when nothing was staged, and the row says `staged: false` with `reason`). Pinned by `TestSessionWakeIDCarriesTheRunProcess`, `TestSessionWakeThatStagedNothingIsRecordedAsSuch` and `TestStageWakeAnswersThatItStagedNothing`.
- `crw flow next` rewrote the owner's orchestrator line with the role store read again, while the live run checks its subagents against the pairs it pinned, so a role store edited while the run lived moved the hook's pairs and made every dispatch a `pair_mismatch`; port: fixed (a session run's started row pins `role_pairs`; the run's process binds the owner's line with the table it pinned, and next writes no line: it prints the spawn formats of the pairs and digest of the started row of the process that holds the run, and warns of a store whose digest differs, never writing it over the run's line; a run that recorded no pairs answers the store's, as before). Pinned by `TestSessionRunPinsItsRolePairsInItsStartedRow` and `TestNextBindsThePairsTheLiveRunPinned`.
- `agent.SessionHost.Warn` was never set, so the marker search's warnings (`no_ledger_line`, `ledger_op_differs`, `several_spawns`, `window_ended`) were dropped; port: fixed (`journal.SessionEnv` takes the run's journal and writes each as a `session_host_warning` row, for a start and a resume). Pinned by `TestSessionHostWarningsGoToTheRunJournal`.
- `BindOrchestrator` read the thread's last line and appended without a lock, so two near-simultaneous binds of one thread could both bind; port: fixed (the read and the append are one step under an exclusive lock of the flow-bound directory; the second bind reads the first's line and, the first run being live, is not bound). Pinned by `TestBindOrchestratorTwoNearSimultaneousStartsBindOne`.
- `next`'s hint said `wait_agent(targets=[<open agents>])` with no ids; port: fixed (the answer's `slots.agents` lists the open subagents and the hint names them). Pinned by `TestNextHintNamesTheOpenSubagents`.
- The start binds the owner before its run process holds the run lock, so a second start of a run of the same thread in that window found the first run not live, closed its line and bound itself, and the first run's process then bound over the second: both starts answered `bound: true` (evaluation d1 of a49bcbbc); port: fixed (a session start holds the run's start lock, `<state>/flow/<run>/start.lock`, from before it binds until the run's process holds the run lock or the start gave up on it, and the binding takes a run as live when its process holds the run lock or its start holds the start lock; the second start finds the first run live, warns and is not bound, and so does the second run's process). Pinned by `TestTwoNearSimultaneousSessionStartsOfOneOwnerBindOne` (two real `crw flow start`s, the second inside the first's spawn, then both run processes' binds).
- `crw flow next` read the pairs the run's newest started row pinned once, before it looked for the run's process: a next that resumed a run with no process recorded a `role_store_changed` row and a warning for a run no process held, printed the ended process's spawn formats and wrote its pairs over the line the resumed process bound with the role store it reads, and a next that waited while another command resumed the run did the same with the pins it had read at its start (Argon V5 F1 of 4d293b7b); port: fixed by the invariant of the next item (next takes the pairs of the started row of the process that holds the run, read when it holds it, and writes no line and no row). Pinned by `TestNextThatResumesARunTakesThePairsTheResumedProcessPinned`, `TestNextThatResumesARunTakesTheRoleStoreTheResumeReads`, `TestNextAfterAResumeLeavesTheRunsOwnLine` and `TestNextTakesThePairsOfAProcessThatTookTheRunWhileItWaited`, over stand-ins of the process in the order the run process keeps (run lock, started row, line).
- `crw flow next` still wrote the owner's line when it took it as missing and recorded `role_store_changed`, so two parties wrote the run's record and its line: a next that resumed a dead run left the open line the dead process had pinned (a line of the run counted as there, `KeepRunLine`) and answered the resumed process's spawn formats beside it, and a next that waited while another command resumed a paused run read the run as soon as the run lock was taken, before the resuming process wrote its started row, recorded a `role_store_changed` row from the ended process's pins and printed their spawn formats (Argon V5 G1 and G2 of fbed54e9); port: fixed (one party writes the owner's orchestrator line and records the pairs of a run process, and their change: the process itself, under its run lock, right after its own started row, through `engine.SessionConfig.Started`, for the run process and the foreground `crw flow resume RUN SCRIPT` alike, with its `policy_repinned` row before it when it repinned. The started row names the process by the token of its process lock, `<state>/flow/<run>/process.<token>.lock`, which the process holds from before the run lock until after it. `crw flow next` writes no line and no row (its bind, `bound.OrchestratorBinding.KeepRunLine` and the `role_store_changed` write are gone): it takes the newest started row as the holder's only when the process lock that row names is held (a row that names none, of a process of an earlier crw, when no process lock of the run is held), reads a run whose holder has not recorded its started row as `starting` again for up to 15 seconds whatever `--wait` says (and a holder that took its process lock less than 15 seconds ago and has not bound the owner's line under its row's digest yet), resumes nothing then and answers `starting` with no spawn formats when it still is; it warns, and records nothing, of an owner's line that is not the holder's, of a role store that reads other pairs than the holder pinned, and of a repin of the process it resumed, read from that process's `policy_repinned` row. A line that is missing while a process holds the run is reported and written by the run's next process, a resume, after its own started row; a start that binds before its process exists writes the first line, under its start lock, and next takes a run whose start holds that lock as `starting`, not as one to resume). Pinned by `TestNextThatResumesADeadRunAnswersWithTheLineItsResumedProcessBound` and `TestNextThatWaitsWhileAnotherCommandResumesTheRunRecordsNoRoleStoreChange` (the real run processes, `crw flow _run --resume` and `crw flow resume RUN`, held between the run lock and their started row; an ended process of an earlier crw and of this crw), `TestSessionRunCallsStartedAfterItsStartedRow`, `TestProcessLockIsHeldUnderItsTokenUntilItIsLetGo`, `TestNextHandsOutTheStepsOfTheBus` and the four tests of the item before.
- The preview's `owner_bound` fact took a run as live only when its process held the run lock, while the binding takes it as live when its start holds the start lock too, so a second start, or a preview, inside the first start's window read `pass` ("the start closes it and binds this run") and the start that followed was not bound (Argon V5 F3 of 4d293b7b); port: fixed (the fact reads liveness as the binding does, `runLive`, and warns that the thread binds that live run). Pinned by `TestOwnerBoundFactInTheFirstStartsWindowWarnsAsTheBindingRefuses`.
- Deviation: the start still binds before its run process exists (the hook decides the owner's spawns by the line, and the start answers whether it bound); a start lock that cannot be taken is warned about and the start binds as before; a process lock that cannot be taken is warned about and the process runs with a started row that names no process; a process of a crw before the process lock names none, and next reads its newest started row when no process lock of the run is held, as before, so a resume by such a process can be answered with the earlier pins in the window before its started row (next records nothing of it); `role_store_changed` is written by no command, so a role store that moves while a process holds the run is warned about by next and recorded only when a resume pins it (its started row and `policy_repinned`); the relay store's schema is unchanged (new `flow_events.kind` values and new started-row members only); port: kept (warn and record, fail open).
