# CRW-845 — chat orchestrate: the published state's answer and the applied transition's ledger row

Source: CXC v0.2.40 (`3c1459ac`) `plugins/codexclaw/components/pabcd-state/src/hook.ts`
`handleOrchestrateCommand` :860-937, :1287-1300 and :1355-1399 with `pabcd-state/src/state.ts`
:620-640, ported to Go as `internal/pabcd/hook/prompt_orchestrate.go` and
`internal/pabcd/hook/prompt_submit.go` with the chat-command cases of `hook.test.ts` as
`internal/pabcd/hook/prompt_orchestrate_test.go` and the new cases of
`internal/pabcd/hook/prompt_orchestrate_published_test.go`. No fixture in `contract/fixtures/cxc`

participating writer changed under the lock, so `contract/notes/cxc/CRW-845.json` claims none and
this issue makes no recorded case pass on its own.

- The oracle's state write does no directory fsync (`state.ts` :620-640), so it reports success after
  the rename and the handler appends its row; the port's `state.WriteState` fsyncs the directory and
  reports a post-rename failure as `*state.PublishedError` (`internal/pabcd/state/write.go` :225-234),
  which `promptSubmitWriteState` collapsed into `promptSubmitFailed`, so the chat handler answered
  "the session state changed or cannot be rewritten ... Nothing was written." although the state was
  already at its final path, and it skipped the ledger row, losing it for good (a retry on the same
  turn is silent and a retry on a new turn is refused `illegal transition P->P`); port: fixed (a
  data-loss defect, the class the parity rule revision of 2026-10-03 fixes during the port: the write
  now reports that case as `promptSubmitPublished`, so the change counts as written and is not rolled
  back, the orchestrate answer carries the CRW-797 durability sentence the CLI's CRW-744/793/811
  writers use, and the row is appended; the callers that judge only `== promptSubmitFailed` (the
  Stop-budget stamp, the loop-arm branch, `promptTriggerWrite`) are not edited and now treat a
  published write as written too, so where they used to end in silence they answer as the oracle's
  successful unlocked write does;
  `TestPromptOrchestratePublishedWriteAnswersApplied`,
  `TestPromptOrchestratePrePublicationFailureStillRefuses`).
- The oracle reads the session state once, without a lock, and derives both the persisted state and
  the ledger row from that one read (:861 against :1360 and :1395), so the two cannot disagree; the
  port's data-loss fix re-applies the transition inside the session lock, and the handler appended
  `result.Ledger` from the transition computed on the *pre-lock* read while writing the state the
  locked re-application produced. On I>P the interview gate decides `override` and `scanEvidence`
  from the tracker (`internal/pabcd/fsm/apply.go` :126-154), so a participating writer that records a
  contradiction between the handler's read and its lock made the persisted state and its ledger row
  describe two different transitions; port: fixed (`promptOrchestrateWrite` returns the row of the
  transition it applied under the lock and the handler appends that row; the pre-lock `result` keeps
  only its non-writing uses - refusal, the B>C source gate, status, the reset no-op;
  `TestPromptOrchestrateLedgerRowComesFromTheAppliedTransition`).
