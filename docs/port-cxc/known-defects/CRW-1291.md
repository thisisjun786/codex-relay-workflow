# CRW-1291 — a plan revision past the one a run pinned holds the run (plan_superseded)

Source: CRW's own design (0.5.0-alpha, the follow-up of CRW-1288 d1 and its final verification P3), not the CXC oracle: CXC v0.2.40 (commit 3c1459ac) has no flow release and no pinned plan revision. The decided answer is the Linear comment of 10-13 (Sion, delegated by Jun): hold, the run does not follow a new revision. The Go side is `internal/flow/ops/lane_design.go` (`releaseOp.hold`, `returnSlot`, `standingHold`, `ReasonPlanSuperseded`), `internal/flow/ops/seams.go` (`ReleaseResult.PinnedRevision`, `HeadRevision`, `HeldExecution`, `HeldRun`), `internal/flow/cli/schedrelay.go` (`SchedRelay.planChanged`) and `internal/relay/dagsched/agent_lifecycle.go` (`AgentReasonPlanSuperseded`); the script side is `superseded` in `internal/flow/workflows/lib/lane.js` and the `held` end of `project-lane.js`. The rule is written in `docs/flow/script.md` (the signal path), `docs/flow/journal.md`, `docs/flow/reporting.md` and `docs/relay/dag-scheduler.md` ("Giving a node up"). The tests are `TestRelayPlanChangedRaisesRunHoldAndReportsUp` and `TestSchedRelayPlanChangedNamesTheRevisionsAndReturnsTheSlot` (`internal/flow/cli/plan_hold_test.go`), `TestPlanSupersededHoldReleasesHeldSlot` and `TestPlanSupersededHoldStopsTheRunUntilADecision` (`internal/flow/ops/plan_hold_test.go`).

- Supersedes CRW-1288.md, item beginning "The issue body does not say what the lane does when the relay refuses a slice the flow cannot see": a release the relay refuses `plan_revision_conflict` while the plan the flow reads again is still the pinned one (`relay_plan_changed`) no longer leaves the node silently unreleased. It raises the run-level hold `plan_superseded`: an escalation of the node that asks the parent, with the revision the run pinned, the relay's head revision and the node, told to the orchestrator thread through the run's escalation notice (`crw manage send-parent`, kind `run_escalation` for the manager). While the hold stands no node of the run is released and the relay is not asked; a resume asks nothing again. The actions are the parent's: end or cancel the run and start a new run on the new revision, or answer the hold's question, which closes the node by escalation and lifts the hold. There is no automatic restart. CRW-1288.md's item now states the rule in the present tense. port: fixed.
- The execution and slot a refused replay leaves at the relay (CRW-1288 final verification P3): the relay's answer names the node's current execution and its run, and the hold closes it with the reason `plan_superseded` (state `cancelled`, the slot back in the same transaction) when it is the run's own, or records the execution and the run that owns it (`slot` `owned_by_run`) when it is another run's, whose cancel returns it. port: fixed.
- The body names a report-up to the parent. A run's upward path to the parent (the orchestrator thread that started it) is the escalation notice; `crw flow report-up` is the orchestrator's path to the initiative lead, which the orchestrator takes for a project-level blocker. The hold is that escalation, so no second report row is written. port: kept.
- Operating rule: a plan is not changed while a trial run runs on it (CRW-1209 is not blocked by this issue; CRW-1227 is). A change made anyway holds the run as above. port: kept.
