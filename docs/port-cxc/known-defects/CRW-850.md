# CRW-850 — the D close's ledger guards read a lone surrogate as U+FFFD

Source: CXC v0.2.40 (commit 3c1459ac) `plugins/codexclaw/components/pabcd-state/src/orchestrate-cli.ts`
`readJsonlObjects` (:431-435) with the two guards it feeds, `hasGoalplanRow` (:437-440) and
`hasPabcdCloseRow` (:442-453). The port is `internal/pabcd/cli/orchestrate_dclose.go`,
`orchestrateDcloseReadJSONLObjects` with `orchestrateDcloseHasGoalplanRow` and
`orchestrateDcloseHasPabcdCloseRow`; the case is pinned by `orchestrate_dclose_surrogate_test.go`.

- The oracle parses each ledger line with `JSON.parse`, which keeps a lone surrogate escape as a lone
  surrogate, while the port parsed it with `encoding/json`, which folds the escape into U+FFFD. The two
  guards then compared a folded value against the close's own id: a stored `"closed wp-\ud800"` row read
  as `"closed wp-<U+FFFD>"` and answered "row present" for a U+FFFD close, so the close skipped the
  `workphase_done` row it owed and lost it for good, and a stored `"closedWorkPhaseId":"wp-\ud800"`
  C -> IDLE row suppressed the close's own row the same way (source `orchestrate-cli.ts`:431-453; the
  issue classes both as data loss). The port now decodes the file bytes with `source.DecodeUTF8` (an
  invalid byte becomes U+FFFD, as Node's `readFileSync(path, "utf8")` and `goalplan read.go` do) and
  parses each non-empty line with `pyjson.Loads(line, LoadOptions{Surrogates: true, Map: true, Numbers:
  pyjson.SpelledNumbers})` (the reading rule the issue names; at this baseline `decodeCliAttest`,
  `orchestrate_args.go:96`, still uses `encoding/json` and moves to this rule in its own issue);
  port: fixed (a defect that loses a record row,
  fixed under the parity rule revision of 2026-10-03; the other reading rules are unchanged, and the two
  refusals whose text moved - a number past float64's range is now read, and text after the value reads
  as "trailing data after the JSON value" - are named in the pull request).
