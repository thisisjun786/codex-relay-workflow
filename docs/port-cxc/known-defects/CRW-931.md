# CRW-931 — the re-registration refused a valid record's spelling, and decided record_unchanged from a policy read outside the lock

Source: CRW's own design, not the CXC oracle. `crw install register-mcp --re-register-policy` and
`UpdateRegisteredPolicy` are the Go port of the Python runtime's bridge record writer
(`scripts/crw_runtime/bridgerecord.py` with `runtime_install.py`), and the re-registration path
itself was added with its own pull request (#794); CXC v0.2.40 has no `register-mcp` or
`bridgerecord` module and no fixture under `contract/fixtures/cxc` drives the path, so there is no
oracle file or line range to point at and no recorded case to replay. The pointer is the port:
`internal/runtime/install/mcp.go` — `UpdateRegisteredPolicy`, and at the base commit `9a7fcae2` the
canonical-form refusal at :731-740, the pre-lock policy read at :672 and the `record_unchanged`
branch at :747-751. Both defects were found by the evaluation of #794's merged diff (score 5, P1
twice) and confirmed on dev; the fixes are pinned in
`internal/runtime/install/mcp_policy_rawbytes_test.go` and in the changed case of
`mcp_policy_update_test.go`.

## Defects

- The re-registration refused any record whose bytes were not the installer's canonical form
  (`!bytes.Equal(before.raw, record.Encode(found))` answered `record_not_canonical`, :731-740 at the
  base commit), although only one member needed replacing: a version-2 record whose trailing newline
  had been dropped, or one written by an editor or another tool, could not be given a new policy at
  all, and the refusal ran before the `record_unchanged` branch, so it fired even when the policy
  was unchanged; port: fixed (the value bytes of the record's `executionPolicy` member alone are
  replaced: the member's value span is found by a token walk of the raw JSON, `memberValueSpan`, and
  the installer's form of the new value is spliced in, `reRegisteredBytes`, so whitespace, key order
  and a trailing newline present or absent are kept; a record the launcher refuses is still refused,
  as `record_malformed`; the read-back still compares the decoded record with the wanted one; pinned
  by `TestReRegisterPolicyKeepsEveryOtherByteOfTheRecord`,
  `TestReRegisterPolicyStillRefusesARecordTheLauncherRefuses` and the changed case of
  `TestReRegisterPolicyRefusesAndWritesNothing`).
- The re-registration read the policy file before it waited for the ownership lock and answered
  `record_unchanged` from that reading, before `policyFileComplaints` ran (:672 and :747-751 at the
  base commit), so a policy edited while the run waited for the lock was reported as unchanged with
  exit 0 while the launcher refuses the stale digest the record still names; port: fixed (the policy
  file is read again under the lock and its digest recomputed before any decision,
  `record_unchanged` is answered only when that in-lock reading equals the record, and
  `policyFileComplaints` runs before the unchanged branch; pinned by
  `TestReRegisterPolicyReadsThePolicyFileUnderTheLock`).
- The fix above kept a second reading of the policy file before the lock, which refused
  `execution_policy_unreadable` from the state the file was in when the command started: a policy
  another run was repairing while this one waited for the lock was never read as it stood, although
  the file the launcher would open was valid by the time the lock was held (found by the review of
  this change); port: fixed (the policy file is read once, under the lock, and that one reading
  drives the refusal and the digest; pinned by `TestReRegisterPolicyWaitsForAPolicyRepair`).
- The raw-byte walk read the record with `encoding/json`, which refuses the JSON constants
  `json.loads` accepts, so a record the launcher reads with `NaN` or an infinity in a member this
  path never replaces could not be re-registered at all - the same refusal for a valid record the
  first defect was about, over a different spelling (found by the review of this change); port:
  fixed (the walk scans the document's own bytes over json.loads' grammar - strings, containers,
  bare tokens, and the constants as the bare tokens they are - so only a document the launcher could
  not read is refused; pinned by `TestReRegisterPolicyKeepsARecordHoldingAJSONConstant`).
- The splice was taken from the bytes the look saw and interpreted after the record had been read
  again, so a record a writer that ignores the ownership lock replaced between the look and the read
  answered `record_update_failed` over bytes that were never the decision's, where the same change a
  moment later answers `record_changed_underneath`; and the spliced document was never read back
  against the record the run meant to write, so a mis-located span would have been published (found
  by the review of this change); port: fixed (the record's identity is compared with the look's
  before its bytes are interpreted, so a record that appeared, moved or was replaced answers
  `record_changed_underneath`, and `reRegisteredBytes` decodes what it spliced and refuses unless it
  reads back as the wanted record; pinned by the record-replaced-underneath case of
  `TestReRegisterPolicyRefusesAndWritesNothing` and the raw-byte tests).

## Supersedes

- Supersedes docs/runtime-install.md, section "Re-registering a changed execution policy", item
  beginning "That promise holds for a record this installer wrote": now port: fixed (that sentence
  said a record in another spelling is refused as `record_not_canonical`; the re-registration now
  edits the record's own bytes, so a record the launcher reads is re-registered whatever its
  spelling, and `mcp_policy_update_test.go` asserts the new behaviour in place of the refusal).
