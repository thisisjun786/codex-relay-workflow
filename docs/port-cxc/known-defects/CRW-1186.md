# CRW-1186 — the dev harnesses write only their own homes: the account home is refused

Source: not an oracle behaviour. CXC v0.2.40 (commit 3c1459ac) has no counterpart of the `crw-dev` harnesses; the defect is the port's own tooling, found when a `crw-dev parity` run left `<account home>/.codex/crw/switch.json` (`{"active":"crw", ..., "by":"laneparity"}`) in the real Codex home. The Go files are `internal/dev/homeguard` (the guard), `internal/dev/laneparity` (`switch.go` `seedPlan.seed` and `writeSwitch`, `declare.go` `GeneratePluginRoot`, `scratch.go`, `realhost.go`, `fire.go`, `latency.go`, `command.go`), `internal/dev/cxcfuzz` (`root.go`, `cases.go`, `cxcfuzz.go`), `internal/dev/cxccorpus/engine.go` `NewCase` and `internal/dev/ci/local.go` `localWorkRoot`.

- A harness took the Codex home of a step from the step's environment (`CODEX_HOME`, else `$HOME/.codex`) and only checked that it lay under the case root by name and by resolved links; a run or a test whose case root, scratch directory or `HOME`/`CODEX_HOME` was the account's own home passed that check and wrote the switch file, the runtime link and the plugin cache there. Every harness writer that takes a destination from its caller or from the environment now refuses, before it creates anything, a destination that is or resolves into `<passwd home>/.codex`, `<passwd home>/.crw` or `<passwd home>/.local/share/crw-runtime` (`homeguard.Refuse`; the account home is the passwd entry of the process's user, never `$HOME`). A test package installs `homeguard.RefuseAccountHome` in `TestMain` (laneparity, cxcfuzz, cxccorpus, ci, stopevents, trialledger), which fails the package when a writer was turned away from the real account home, even if the code swallowed the error, and when the real `switch.json` changed while the tests ran (a child process the in-process refusal cannot see). port: fixed.
- `stopevents` and `trialledger` write nothing (they read stores and ledgers); `TestReadOnlyHarnessesCallNoWriter` pins that, so a writer added later has to call `Refuse` and leave the list. port: kept (nothing to refuse).
- `crw-dev skills link --apply` links the repository's skills into `$CODEX_HOME/skills`, else `~/.codex/skills`: writing the account's Codex home is that command's purpose, an operator's explicit act that is a dry run without `--apply`. It is not guarded; its tests hand it an injected environment. `skillport` staging, the `cxccorpus` declarations and coverage files and the `ci` hook install write the repository checkout, which can itself lie below `~/.codex/worktrees`, so they are not guarded either. port: kept (a deviation from "every writer": a guard there would remove the command's job or refuse a managed worktree).
- `crw-dev ci local` writes outside its clean worktree only the verification record (with its `.canonical` sibling and the directories above them) and, for the tool-version probes, directories in `TMPDIR`. Both are guarded before the first probe, for a fresh run and a reuse alike (`localVerify`): a `TMPDIR` or a `--record` that is, or resolves into, the account's `.codex`, `.crw` or `.local/share/crw-runtime` is refused. The one exception is a record inside the checkout being verified when that checkout is itself a managed worktree below the account's `.codex` (`homeguard.RefuseUnlessWithin`: the destination and the way to it are taken physically, so a `..` or a link that leaves the checkout is refused as elsewhere); the default record path, in the checkout, is that case. port: fixed.
- The guard resolves a destination as the kernel does: the links on the way are followed in order, so a `..` after a link is taken from the link's target (`<outside>/link/../.codex/x` with `link` leading into the account home is refused), the cleaned spelling a caller's `filepath.Join` produces is checked as well, the physical place of a protected directory that is itself a link (`~/.codex` leading elsewhere) is protected too, and a link cycle ends after 40 links with an error that refuses the write. Output trees are guarded write by write (`homeguard.MkdirAll`, `WriteFile`, `Symlink` in `GeneratePluginRoot`, `cxcfuzz` cases, divergence, failure and summary files, case roots, scenario entries and the real-host fixtures), so an existing link inside an output directory that leads into the account home is refused where it is written. `homeguard.MkdirAll` also refuses each missing parent `os.MkdirAll` would make by the spelling it is given (`<home>/.codex/new/../../safe` makes `.codex/new` first), not only the destination. The corpus engine (`cxccorpus/engine.go`) guards every destination below a case root, because a scenario's `Given.Symlinks` may lead anywhere: the file a `Step.Write` or a given writes, each directory it makes, a given link's own place, a `Given.Modes` chmod, a `Given.Mtimes` or written-file stamp, a SQLite seed and a given repository or worktree. The check and the write are two steps (a link made between them is not seen). port: fixed. Stub names are file names of the case's `stubs` directory (`InstallStubs` refuses a name with a separator, `.` or `..`, and refuses the destination before the runtime's installer writes it), and the git metadata a given repository works on is guarded, not only its working directory: before every git command of a given the `.git` entry, the `gitdir:` a `.git` file names, the common directory the git directory's `commondir` file names (read whether or not git can read the repository yet, a relative one taken from the git directory) and the absolute and common git directories git reports are refused when they lie in the account's home. port: fixed.
- The runtime link of a step (`seedPlan.seed`) is judged by its own place (`homeguard.RefuseEntry`): the link is made, or an existing one is read for the digest comparison, and what it leads to is only read, so the build under test may be an executable in a managed checkout below the account's `.codex`. port: fixed (regression of the first guard, which followed the final link).
