# CRW-1189 — refusal and continuation wording that left the next action to a guess

Source: CXC v0.2.40 (commit 3c1459ac) `plugins/codexclaw/components/pabcd-state/src/hook.ts` `STOP_NEXT_COMMAND` (:1523-1537), `buildStopBlock` (:1577-1631), `memory-write-gate.ts` (the oracle has no command reader, so the shell-reader refusals have no oracle counterpart) and `subagent-config/src/spawn-attach-hook.ts` (:892-907, the managed dispatch refusal). The Go side is `internal/pabcd/hook/stop.go`, `internal/pabcd/state/lock.go`, `internal/pabcd/shellir/modules.go`, `internal/role/spawn/node_error.go` and `hook_managed.go`. Found by the isolated trial r3 (R3-S2-F1 to F4, S5-R3-F1) and confirmed by real-environment trial r1.

- The Stop block's example command for P, A, B and C carried `"workPhaseId":"<bound goalplan only>"` (and at C `"testReceiptPath":"<bound goalplan only: ...>"`) for every session, so a session without a bound goalplan was handed keys it cannot fill, and a bound one a marker in place of the id and the path (hook.ts:1523-1537); port: fixed. A session without a bound goalplan gets the command without those keys; a bound session gets its goalplan's active work phase id and, at C, the path `crw pabcd receipt test` writes (`.crw/evidence/<session>/test-receipt.json`) with a line that names the receipt command to run first. A bound plan with no runnable work phase has no id to give, so the key is left out. `planUnit` stays at P (the P to A gate asks for it of every session; the agent names the unit `crw pabcd plan init <slug>` creates). The rest of the text is the oracle's. Pinned by `TestStopBlockTextOfEveryPhase` (unbound, byte for byte) and `TestStopContinuationOf*` in `internal/pabcd/hook/stop_nextaction_test.go`; red output `/state/crw/crw-lane-guard-followup-1189/evidence/red-f1.log`. The replay claims of the four recorded fixtures with this text moved to `contract/notes/cxc/CRW-1189.json` (intentionally changed).
- A session lock that stayed held for the whole wait (the oracle's schedule, about 250 ms) ended `crw pabcd orchestrate` with the bare `crw cli failed: open <session>.json.lock: file exists`, which reads as corruption although the state is intact and the same command succeeds on a retry (isolated trial r3 R3-S2-F2; not reproduced in real-environment trial r1); port: fixed in the wording only. The error is now `session state is busy: another crw command is using this session; retry the same command in a moment (nothing was changed): open <lock>: file exists` (`state.SessionBusyError`, which wraps the lock file's `*fs.PathError`, so `errors.Is(err, fs.ErrExist)` and `errors.As` to the `*fs.PathError` answer as before). The wait, the schedule, the takeover rules and which callers give up are unchanged. Pinned by `TestCRW1189BusySessionLockSaysItIsRetryable` and `TestCRW1189OtherLockFailuresKeepTheirText` in `internal/pabcd/state/lock_busy_text_test.go`; red output `/state/crw/crw-lane-guard-followup-1189/evidence/red-f2.log`.
- The refusal of a carried program next to a module run (`awk <program> file | git apply --check; python3 -B -m unittest -v`) said `a carried program may rewrite module imports` and named no part of the text (isolated trial r3 R3-S2-F3, confirmed by real-environment trial r1); port: fixed in the wording, the decision kept (CRW-1178's conservative rule). The reason names the program (`the \`awk\` program`, `the script file \`x.sh\``, `\`tar\` (an archive extraction)`) and gives the way past: `run it in a separate command, before or after the module run`; a program that runs beside the module run (background, coprocess, process substitution, same pipeline) is named in that reason too. Pinned by `TestCRW1189CarriedProgramRefusalNamesTheProgramAndTheRoute` (`internal/pabcd/shellir/crw1189_test.go`) and `TestCRW1189GuardAnswersNameTheProgramAndTheCacheRemoval` (`internal/pabcd/hook/crw1189_test.go`, both guards, uncut); red output `/state/crw/crw-lane-guard-followup-1189/evidence/red-f3f4.log`.
- CRW-1178's cache refusal asked to `remove __pycache__`, which an agent spells `rm -rf __pycache__`, and the Codex 0.154 execution policy refuses (`rm -f style commands are not permitted`) (R3-S2-F4); port: fixed in the wording. The reason names the file and gives two forms the policy lets through: `` `rm` that file `` and `` `find . -name __pycache__ -prune -exec rm -r {} +` `` (the project is the working directory, where the inventory walks), each in a separate command first, then `python -B`. A compiled module outside a cache directory (`legacy.pyc`) gets the `rm` form. The decision, the file named and the 320-byte bound of a reader's reason in the hooks are unchanged (a name longer than 88 bytes is shortened for it). Pinned by `TestCRW1189CacheRefusalGivesACommandTheHostPolicyAccepts` and the updated route constant of `TestCRW1178*` in both packages.
- A spawn whose `[CRW-DISPATCH:<id>:<attempt>]` marker names a dispatch that was never started was refused with the bare `managed dispatch: ENOENT: no such file or directory, lstat '<root>/.crw/dispatches/<session>/<id>.json'`, which names neither the cause nor the next action (spawn-attach-hook.ts:892-907; isolated trial r3 S5-R3-F1, confirmed by real-environment trial r1); port: fixed. The refusal is now `managed dispatch: this marker has no dispatch record (ENOENT: ..., lstat '<path>'); use a marker that \`crw role helper dispatch\` returned (action start, then claim), or leave the marker out` (`spawnManagedRecordMessage` in `internal/role/spawn/node_error.go`, used by the managed loop of `hook_managed.go`; the oracle's text stays inside the parentheses). Only the lstat ENOENT of a record below a `dispatches` directory is reworded; an unclaimed attempt, an issued one, a full-history fork and the refusals of the issuance and replay paths keep the oracle's text, and the spawn is still denied. Pinned by `TestCRW1189MarkerWithoutADispatchRecordSaysWhatToDo` and `TestCRW1189OtherDispatchFailuresKeepTheOracleText` in `internal/role/spawn/hook_managed_norecord_test.go`; red output `/state/crw/crw-lane-guard-followup-1189/evidence/red-f5.log`. The replay claim of `hook__pre-tool-use-attaching-skills__managed_dispatch_refusals` moved from `contract/notes/cxc/CRW-1124.json` to `CRW-1189.json` (its step 1 answer is intentionally changed).
