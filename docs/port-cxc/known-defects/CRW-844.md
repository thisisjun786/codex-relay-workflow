# CRW-844 — doctor retrust atomic swap-then-verify publication

Source: CXC v0.2.40, commit `3c1459acadeb1906d97c00a598e1457327ae372d` —
`plugins/codexclaw/components/cxc-ops/src/hook-trust.ts` `writeAtomic` (:367-381), `verifyCodexConfig`
(:387-410) and `retrustHooks` (:412-477). Port: `internal/runtime/doctor/hooktrust_retrust.go` (the
swap-then-verify publication, the sidecar lock, the pre-write verification, the conflict/late/sync
reporting), `internal/pabcd/crwdir/swap.go` + `swap_linux.go` + `swap_darwin.go` (`PublishSwap`,
`PublishedError`/`Published`, `LockConfig`/`ConfigLock`), and
`internal/runtime/install/configguard/activate.go` (the lock around the activation publish of
config.toml).

## Guarantee statement (CRW-844, carried verbatim from the issue body)

- (a) Between CRW writers that take the lock: the read, the plan, the verification and the
  publication are serialized. retrust never plans from bytes another CRW writer has already changed,
  and a concurrent CRW writer is refused as busy. No unverified config is ever published.
- (b) Against writers that do not take the lock (Codex, an editor): there is no compare-and-swap.
  retrust does not delete content it did not create. The file the publication displaced is kept as
  the backup and checked, and a save between the last check and the publication is reported as a
  conflict with the preserved path (config.toml holds retrust's content). A save after the
  publication is reported and left in place. Residual limit: a writer that keeps the old file open
  and writes in place after the exchange leaves its content in the backup and not in config.toml —
  preserved, but it may not be reported if the compare has already run.

## Defects

- The oracle wrote the rewritten document and only then verified it, and its failure path restored
  the backup, so an unverified config was visible at the real path for the whole probe, and a
  non-cooperative save during the probe was overwritten and then overwritten again by the rollback
  (source `plugins/codexclaw/components/cxc-ops/src/hook-trust.ts:466-473`); port: fixed (the
  settings data-loss class the parity rule revision of 2026-10-03 fixes during the port: the plan is
  verified in a temporary Codex home before anything is published, the publication is an atomic
  exchange that keeps the displaced file as the backup, and no rollback path remains —
  `HookTrustRetrust`, `hookTrustRetrustVerifyNext`, `crwdir.PublishSwap`; pinned by
  `TestHookTrustRetrustCASVerificationFailureLeavesTheConfigAndReportsThePlan`,
  `TestHookTrustRetrustCASReportsAConflictAndKeepsBothPaths` and
  `TestHookTrustRetrustCASReportsASaveAfterThePublication`).
- The oracle's write renamed the temp file over config.toml unconditionally, so a save that landed
  between its read and its rename was gone with nothing keeping it (source
  `plugins/codexclaw/components/cxc-ops/src/hook-trust.ts:367-381`); port: fixed (same data-loss
  class: `crwdir.PublishSwap` re-reads the target after the temp file is written and fsynced, refuses
  when it no longer holds the bytes the plan was computed from, and otherwise exchanges the two files
  atomically, so the displaced file is the backup; pinned by
  `TestCrwdirSwapKeepsASaveFromBeforeTheExchange` and
  `TestCrwdirSwapNeverDeletesAnExistingBackup`).
- The oracle's write path did not fsync the directory that holds config.toml, so the rename could be
  lost by a power failure while the backup survived (source
  `plugins/codexclaw/components/cxc-ops/src/hook-trust.ts:367-381`); port: fixed (the directory is
  fsynced after the exchange; a sync-only failure is answered as `crwdir.PublishedError` and retrust
  counts the publication as written and reports a warning, the `state.PublishedError` rule —
  `crwdir.PublishSwap`, `hookTrustRetrustReport`; pinned by
  `TestCrwdirSwapDirectorySyncFailureIsPublished` and
  `TestHookTrustRetrustCASCountsASyncFailureAsWritten`).
- The oracle's failure text carried only the verification error and left the operator to find the
  backup by name (source `plugins/codexclaw/components/cxc-ops/src/hook-trust.ts:471-474`); port:
  fixed (J4, 2026-10-06: every outcome prints the changed or planned updated and appended keys, the
  backup path and which file holds what — `hookTrustRetrustReport`; pinned by
  `TestHookTrustRetrustCASReportsThePlanOnSuccess` and the refusal cases).
- The oracle had no lock, so two of its writers could interleave on one config.toml and the later one
  silently replaced the earlier one's bytes (source
  `plugins/codexclaw/components/cxc-ops/src/hook-trust.ts:412-477`); port: fixed (the sidecar lock
  `config.toml.crw-lock` is taken by retrust and by the configguard activation publish of config.toml,
  an flock created once and never unlinked per docs/port/decisions.md 7 — `crwdir.LockConfig`,
  `HookTrustRetrust`, `activationPublishConfig`; pinned by `TestCrwdirConfigLockIsExclusive`,
  `TestCrwdirConfigLockWaitsForAShortHolder`,
  `TestHookTrustRetrustCASRefusesWhileAnotherWriterHoldsTheLock` and
  `TestActivateTakesTheConfigLock`).
- The oracle's `writeAtomic` took the target's mode from `statSync(path).mode` and replaced a target
  the process could not open for writing (source
  `plugins/codexclaw/components/cxc-ops/src/hook-trust.ts:367-381`); port: kept (this is CRW-427's
  rule, not a defect of this port, and it is stricter than the oracle: `crwdir.PublishSwap` resolves
  the target through `crwdir.resolveTarget`, so a file the process cannot open for writing, a
  directory and a dangling link are refused rather than replaced — pinned by
  `TestHookTrustRetrust_refuses_an_unwritable_config`).

## Defects found by the pull request's reviews (all fixed here)

- The first publication reserved the backup path only by moving into it after the exchange, so a name
  already taken (a second run within the same timestamped second, or a file already at that path)
  left the target replaced with the displaced content only at the temporary path, and the command
  reported `config.toml unchanged; nothing was published`. Reported by both external reviews (the
  red bug and its P2 twin). port: fixed — the backup path is now refused before the exchange with the
  same exclusive create the oracle's `copyFileSync(target, backup, COPYFILE_EXCL)` used, and every
  failure after the exchange (the no-replace move, reading the backup back, the directory sync) is a
  `crwdir.PublishedError` whose `DisplacedAt` names the file that really holds the displaced
  content; the doctor report prints that path instead of assuming the backup path. Pinned by
  `TestCrwdirSwapRefusesAnOccupiedBackupBeforeTheExchange`,
  `TestCrwdirSwapKeepsTheDisplacedContentWhenTheMoveFails` and
  `TestHookTrustRetrustCASReportsAPostExchangeFailureAsPublished`.
- The activation publish took the lock only around its final `crwdir.Publish`, after its read and
  its `SetTableKey`. A retrust that published in that window was overwritten with content built from
  the pre-retrust bytes, losing the trust sections, and neither command reported it. Reported by both
  external reviews (the red bug and the P1 twin). port: fixed — `activationSetKeyLocked` holds the
  lock across the whole read-modify-write of `config.toml`. Pinned by
  `TestActivateTakesTheConfigLock`, which now drives the real `Activate` against a held lock and
  asserts the refusal and the untouched file.
- The report for a late save said the target "holds retrust's config" while `LateWrite` is set
  precisely because it does not. Reported by both external reviews (the yellow and its P2 twin).
  port: fixed — the line now says the target holds the newer save and the backup holds the content
  retrust displaced. Pinned by `TestHookTrustRetrustCASReportsASaveAfterThePublication`.
- The final `DiagnoseHookTrust` read after the publication returned its results with a nil error, so
  a hook that drifted between the pre-write verification and that read was printed as `drifted` or
  `untrusted` while the command still exited 0 as though retrust succeeded; the oracle's own
  post-write check failed on exactly that. Reported by the Codex review (P2). port: fixed — every
  final result must be `trusted`, else the command reports a post-publication verification failure
  and exits 1. Pinned by `TestHookTrustRetrustCASFailsWhenTheFinalDiagnosisDrifts`.

- The conflict error on stderr hardcoded the backup path while the stdout report already used the
  file that really holds the displaced content, so a conflict that followed a post-exchange failure
  sent the operator to a path that holds nothing (or an unrelated file). Found by the independent CXC
  review pass. port: fixed — `HookTrustRetrustResult.displacedPath` is the single source for both the
  report and the error. Pinned by
  `TestHookTrustRetrustCASConflictNamesTheDisplacedPathAndKeepsTheWarning`.
- The post-publication warning was printed only on a success, so a conflict or a late write that
  followed a post-exchange failure dropped the failure detail — the only place the operator learns
  where the displaced content really is. Found by the same review pass. port: fixed —
  `hookTrustRetrustWarn` runs on a success and on a failure alike. Pinned by the same test.

- EPERM at the exchange was classified with the unsupported-filesystem errnos, so a genuine
  permission failure would be reported as "this filesystem does not support an atomic exchange" and
  send the operator to give up on a filesystem that works. Found by the independent CXC review pass.
  port: fixed — the unsupported set is EINVAL, ENOSYS, ENOTSUP and EOPNOTSUPP on both platforms, and
  a permission failure is surfaced as itself. Pinned by
  `TestCrwdirSwapDoesNotCallAPermissionFailureUnsupported`.
