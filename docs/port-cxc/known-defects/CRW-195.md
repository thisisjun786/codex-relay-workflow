# CRW-195 — the skill reorganisation: goal mode and the parts of the port that still treat a project parent as a loop

Source: the routing rules of the skill reorganisation (a `$crw-loop` request with a Linear project goes to `crw-run` goal mode, the parent never follows the loop procedure, a child's workflow label is `crw-loop`), compared with the CXC v0.2.40 (commit 3c1459ac) hooks the port carries as they stood (`pabcd-state/src/hook.ts` `detectLoopArmRequest` :315-321 and `loopArmDirective` :491-508, `handleStop` :1805 with `buildGoalIdleBlock` :1694, `cxc-ops/src/map-affordance.ts` :179-187) and the Go files of the port (`internal/pabcd/hook/detect.go`, `internal/pabcd/hook/directives.go`, `internal/affordance/render.go`, `internal/relay/reception/packet.go`, `internal/skill/start_policy.go`). The skills are `plugins/crw/skills/crw-run/references/goal-mode.md`, `start-policy.md` and the staged `port/cxc/skills/crw-loop/SKILL.md`.

- The UserPromptSubmit loop-arm detector fires on `crw-loop` plus an action verb whoever the session is, and injects the ORCH-MANDATE directive ("Load $crw:crw-loop and $crw:crw-pabcd ... `crw pabcd orchestrate`", `directives.go:103-106`). A `$crw-loop <Linear project>` request that the skills hand to goal mode therefore also tells the project parent to enter the loop it is forbidden (`detect.go:210`); the skills text says the parent ignores it, and nothing in the hook does. Excluding a session the relay registry knows as a bound project parent is a deviation from the port, so it waits for the owner (the plan's Q1). port: pending.
- The Stop continuation that the PABCD hook composes into the single `crw hook stop` entry blocks a parent holding an active goal at phase `IDLE` and tells it to run `crw pabcd loop init`, the incompatibility `start-policy.md` records as measured on CXC 0.2.33 and 0.2.34; the continuation is not yet in the Go tree, and when it lands it needs the same registered-parent exclusion or goal mode keeps the 3-block, 24-total nudge budget. port: pending (Q1; the continuation itself is the Stop-continuation issue's).
- The SessionStart loop affordance (`map-affordance.ts:179-187`, `internal/affordance/render.go`) is injected into a project parent's session too and contradicts "the parent never follows the loop procedure". It is advisory, so it ports as it stands. port: kept (advisory text, the skills rule governs).
- `start-policy.md` named the run mode of a native parent goal `loop`, which after the split is the name of the PABCD loop. The value is now `goal` in the pairing table and in `crw skill start-policy` (`vocabulary`, `check`, `selftest`); a record that still says `loop` is outside the set and is re-adjudicated on its next re-read, exactly as any unreadable value is, and no alias maps it. port: fixed (the plan's Q2, chosen as the issue's wording "loop = the PABCD loop, goal mode = the parent's optional mode" requires; no recorded row of a live project is known).
- The relay packet check refused a policy whose workflow named `CXC Loop` under a mode other than `loop` (`internal/relay/reception/packet.go`, tokens `cxc`, `loop`); the skills now name the child's workflow `crw-loop`, so the same refusal reads `crw`, `loop` and the name `CXC Loop` is refused nothing. The recorded fixtures `Test23_RF_2_Scenario.json` and `Test23_SR_15_Scenario.json` still carry the literal `CXC Loop` as a launch-policy value that the corpus replays; renaming them is the Go-and-fixture naming issue's. port: fixed (check), pending (fixtures).
- `internal/relay/delivery/report_compose.go` still points a lost-context report at `codexclaw:cxc-lost-context` and a review-repair report at `codexclaw:cxc-review-repair`, skills no CXC tag v0.2.28 to v0.2.40 ships, and the other pointers still read `codexclaw:cxc-*` where the skills are `crw:crw-*`. Mapping or removing them is the Go-and-fixture naming issue's (the plan's Q7). port: pending.
