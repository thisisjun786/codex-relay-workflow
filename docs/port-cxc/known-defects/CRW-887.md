# CRW-887 - the state-copy apply left two windows in a created directory's identity

Source: the state-copy apply is CRW's own design,
[docs/port-cxc/state-migration.md](../state-migration.md) (the whole-scope preflight at :144-156, the
publication and mode rules at :150-152, and the M3 write step at :184-200), and the code is the Go port
in `internal/runtime/install/migrate`: `roots.go` (`Dir.EnsureChild` at :481-502 at the base commit
7b59814a, and `Pair.EnsureDest` at :132-146), `apply.go` (`ensureRoots` at :238-285,
`ensureDestDir` at :316-349 and `finishModes` at :601-638) and `publish.go`
(`Publisher.EnsureProjectRoot` at :214-250, `tempName` at :19-40 and `noReplaceRename` in the platform
files). The oracle has no state-migration command, so nothing here is a CXC v0.2.40 behaviour and no
fixture is claimed; the defect is Go-side and the same files fix it. The first and the fourth were
reproduced on dev 7b59814a (the racer's `01700` child directory ends `0755` with no note; under umask
`0477` the run stops at `open ... permission denied` with the root left `--wx------`), the second was
reproduced by the operator's pair evaluation of the earlier state-copy pull request, and the third was
named by the review of that pull request and of the bundle that carried it.

- `finishModes` decided that a destination directory was one an interrupted earlier run had left from
  the raw mode alone: the second condition `raw == applyTempRaw && entriesExpected` adopted any
  directory that happened to carry exactly the private marker mode `0o1700` and hold only plan-named
  entries, even when this run's own creation of that directory had ended in `EEXIST` and so belonged to
  another actor. A racer that made `sessions` at `01700` in the window between the lookup and the
  creation therefore ended at the source mode `0755`, with no note, and the other actor's mode was lost
  (source `apply.go:601-638`, `apply.go:316-349`; the design requires that a directory this migration
  did not create retains its mode and is reported, `state-migration.md:150`); port: fixed (the run
  records every destination its lookup found absent whose creation then ended in `EEXIST`,
  `applyRun.recordOwnership`, and `finishModes` reports such a directory as
  `existing directory kept its mode` without ever reaching the marker branch; the marker adoption stays
  for a directory that was already there at the lookup, so an interrupted earlier run's directory is
  still finished; the cases are `TestMigrateOwnedDirIdentityRacerMarkerModeIsNotAdopted` and
  `TestMigrateOwnedDirIdentityRacerRootMarkerModeIsNotAdopted`).
- `EnsureChild` created the directory at its final name and left the private marker mode to its caller,
  after two fallible steps: opening the child and syncing the parent directory. A failure at either left
  the directory at whatever mode `mkdirat` gave it, and because a host may drop the sticky bit from a
  directory's creation mode (Darwin does) the directory could carry no marker at all, so a rerun read it
  as an existing directory of another actor and never finished its mode (source `roots.go:481-502`,
  `apply.go:271-277`, `apply.go:340-345`, `publish.go:230-234`; the design requires a directory this
  migration created, or one an interrupted run left at the private mode it creates directories with, to
  have its source mode finished on a rerun, `state-migration.md:150`); port: fixed (`EnsureChild`
  creates the directory under a temporary name of this run, gives that name exactly the requested mode
  by name before anything opens it, opens it as a directory with no link followed, checks with `fstat`
  that it is a directory of this process at exactly that mode, and only then renames it into place with
  the package's no-replace rename, so the name is visible only once it carries its mode; the cases are
  `TestMigrateOwnedDirIdentityRerunAfterAFailedOpen` and
  `TestMigrateOwnedDirIdentityRerunAfterAFailedParentSync`).
- The same order was a replacement window: the directory was created at its final name and opened after
  that, so another actor that put its own directory at the name in between was adopted by this run,
  reported as its own, and given a mode. The identity of a created directory is now fixed before its
  name is visible: the temporary name is this run's own unguessable name, the pinned descriptor is
  checked against it, and a rename that ends in `EEXIST` is the other actor's directory (source
  `roots.go:481-502`; `apply.go:238-285` reads ownership from the creation's own result); port: fixed
  (a rename that ends in `EEXIST` reports `made` false, removes this run's temporary with `rmdir` and
  opens the existing name as it is, and the entry at the name is checked against the pinned descriptor
  after the rename; the case is `TestMigrateOwnedDirIdentityRacerAtTheRenameIsNotAdopted`).
- A umask that removes the owner's read or write bit (`0477`, `0777`) made `mkdirat(0o1700)` produce a
  directory this process could not open, so the `O_RDONLY` open that followed failed with `EACCES`
  before any mode had been given and the run stopped with the directory left `--wx------`; correcting
  the umask and rerunning did not help, because the run still could not open the directory it had made
  (source `roots.go:481-502`; the design requires new directory modes to be applied so that a
  read-only source directory stays reproducible, `state-migration.md:150`); port: fixed (the temporary
  name is given exactly the requested mode by name before the open, so the open never depends on the
  umask, and the descriptor is checked afterwards; the cases are
  `TestMigrateOwnedDirIdentityHostileUmask` and
  `TestMigrateOwnedDirIdentityHostileUmaskAfterAnInterruption`).

- Supersedes `known-defects/CRW-813.md`, the item beginning "The marker is what a rerun reads to
  recognise a directory this migration made": now port: fixed (that limitation said the window between
  a root's `mkdir` and its marker chmod "is one syscall wide"; the order it described was
  `mkdirat`, `openat`, `fstat` and the parent `fsync` before the caller's chmod, so two fallible steps
  stood in that window, not one, and neither is in it any more - the mode is given to the temporary name
  before the directory is opened, and the name becomes visible only after that).

- The first cut of the temporary-name creation left three holes of its own, all found by the review of
  this pull request and all closed here: the deferred removal of the temporary name was addressed by
  name alone, so an actor that swapped its own entry onto that name could have had it removed, or had
  the wrong entry left behind; a creation whose rename succeeded and whose sync then failed reported
  `made` false, so a retry with the same pinned pair read this run's own root as another actor's and
  never finished its mode; and the chmod fallback for a kernel whose `fchmodat` cannot express
  no-follow used a chmod that follows a link, which would let an actor that swapped a link onto the
  temporary name have this process change an unrelated file's mode (source `roots.go`, the
  `migrateOwnedDirIdentity*` helpers; `state-migration.md:150` requires a directory this migration did
  not create to retain its mode, and the design refuses an unsupported platform rather than falling
  back, `state-migration.md:152`); port: fixed (the removal compares the entry at the temporary name
  with the identity read when that name was created and removes only this run's own directory; a
  creation whose rename succeeded reports `made` true even when a later step failed, and `Pair`
  remembers it, so a retry with the same pinned pair finishes the root; and a kernel that cannot chmod
  a name without following a link is refused as an unsupported platform; the cases are
  `TestMigrateOwnedDirIdentityRerunWithTheSamePinnedPairFinishesTheRoot` and
  `TestMigrateOwnedDirIdentityChmodWithoutNoFollowIsRefused`).
- A directory's mode was corrected by name and the name then published without syncing the directory
  itself, so a crash could leave the final name durable while the corrected mode was not, which is the
  state this issue exists to make recoverable (source `roots.go`, `EnsureChild`; the design requires a
  directory this migration created to have its source mode finished on a rerun,
  `state-migration.md:150`); port: fixed (the pinned descriptor is synced after its mode is checked and
  before the rename publishes the name).

- The first cut of the temporary-name creation left one more hole of its own, found by the independent
  review of this pull request: the identity of the name this run had just created was read with a second
  syscall, and a failure of that read left the directory behind with no record of it, so the next run had
  a temporary it could not attribute (source `roots.go`, `migrateOwnedDirIdentityTemp`;
  `state-migration.md:152` requires an incomplete temporary to be reported or ignored and never adopted,
  which a leftover satisfies, but the creation this run can account for should not leave one); port:
  fixed (the read is the creation's own step, and a read that fails removes the directory this run just
  made; `TestMigrateOwnedDirIdentityUnreadableTemporaryLeavesNothing`).

Limitations, not defects, recorded so each is a decision rather than a surprise:

- The entry at the temporary name is checked against the pinned descriptor, but a same-uid process can
  still swap the entry at the final name after the rename and before the directory sync. The check
  narrows that window to the two syscalls between them, and a swap is reported as a refusal
  (`migrateOwnedDirIdentityRenamed`) rather than published into; closing it entirely would need a
  syscall the port does not have. The file publication carries the analogous residual, documented at
  `publish.go:80-81`.
