# CRW-887 - the state-copy apply left two windows in a created directory's identity

Source: the state-copy apply is CRW's own design,
[docs/port-cxc/state-migration.md](../state-migration.md) (the whole-scope preflight at :144-156, the
publication and mode rules at :150-152, and the M3 write step at :184-200), and the code is the Go port
in `internal/runtime/install/migrate`: `roots.go` (`Dir.EnsureChild` at :481-502 at the base commit
7b59814a, and `Pair.EnsureDest` at :132-146), `apply.go` (`ensureRoots` at :238-285,
`ensureDestDir` at :316-349 and `finishModes` at :601-638) and `publish.go`
(`Publisher.EnsureProjectRoot` at :214-250, `tempName` at :19-40 and `noReplaceRename` in the platform
files). The oracle has no state-migration command, so nothing here is a CXC v0.2.40 behaviour and no
fixture is claimed; the defect is Go-side and the same files fix it. The first and the fourth were
reproduced on dev 7b59814a (the racer's `01700` child directory ends `0755` with no note; under umask
`0477` the run stops at `open ... permission denied` with the root left `--wx------`), the second was
reproduced by the operator's pair evaluation of the earlier state-copy pull request, and the third was
named by the review of that pull request and of the bundle that carried it.

- `finishModes` decided that a destination directory was one an interrupted earlier run had left from
  the raw mode alone: the second condition `raw == applyTempRaw && entriesExpected` adopted any
  directory that happened to carry exactly the private marker mode `0o1700` and hold only plan-named
  entries, even when this run's own creation of that directory had ended in `EEXIST` and so belonged to
  another actor. A racer that made `sessions` at `01700` in the window between the lookup and the
  creation therefore ended at the source mode `0755`, with no note, and the other actor's mode was lost
  (source `apply.go:601-638`, `apply.go:316-349`; the design requires that a directory this migration
  did not create retains its mode and is reported, `state-migration.md:150`); port: fixed (the run
  records every destination its lookup found absent whose creation then ended in `EEXIST`,
  `applyRun.recordOwnership`, and `finishModes` reports such a directory as
  `existing directory kept its mode` without ever reaching the marker branch; the marker adoption stays
  for a directory that was already there at the lookup, so an interrupted earlier run's directory is
  still finished; the cases are `TestMigrateOwnedDirIdentityRacerMarkerModeIsNotAdopted` and
  `TestMigrateOwnedDirIdentityRacerRootMarkerModeIsNotAdopted`).
- `EnsureChild` created the directory at its final name and left the private marker mode to its caller,
  after two fallible steps: opening the child and syncing the parent directory. A failure at either left
  the directory at whatever mode `mkdirat` gave it, and because a host may drop the sticky bit from a
  directory's creation mode (Darwin does) the directory could carry no marker at all, so a rerun read it
  as an existing directory of another actor and never finished its mode (source `roots.go:481-502`,
  `apply.go:271-277`, `apply.go:340-345`, `publish.go:230-234`; the design requires a directory this
  migration created, or one an interrupted run left at the private mode it creates directories with, to
  have its source mode finished on a rerun, `state-migration.md:150`); port: fixed (`EnsureChild`
  creates the directory under a temporary name of this run, gives that name exactly the requested mode
  through a handle on it before anything else runs, checks with `fstat` that the handle is a directory of
  this process at the identity read when it was created, and only then renames it into place with
  the package's no-replace rename, so the name is visible only once it carries its mode; the cases are
  `TestMigrateOwnedDirIdentityRerunAfterAFailedOpen` and
  `TestMigrateOwnedDirIdentityRerunAfterAFailedParentSync`).
- The same order was a replacement window: the directory was created at its final name and opened after
  that, so another actor that put its own directory at the name in between was adopted by this run,
  reported as its own, and given a mode. The identity of a created directory is now fixed before its
  name is visible: the temporary name is this run's own unguessable name, the pinned descriptor is
  checked against it, and a rename that ends in `EEXIST` is the other actor's directory (source
  `roots.go:481-502`; `apply.go:238-285` reads ownership from the creation's own result); port: fixed
  (a rename that ends in `EEXIST` reports `made` false, removes this run's temporary, and opens the
  existing name as it is; the entry at the name is checked against the identity this run created after
  the rename; the case is `TestMigrateOwnedDirIdentityRacerAtTheRenameIsNotAdopted`).
- A umask that removes the owner's read or write bit (`0477`, `0777`) made `mkdirat(0o1700)` produce a
  directory this process could not open, so the `O_RDONLY` open that followed failed with `EACCES`
  before any mode had been given and the run stopped with the directory left `--wx------`; correcting
  the umask and rerunning did not help, because the run still could not open the directory it had made
  (source `roots.go:481-502`; the design requires new directory modes to be applied so that a
  read-only source directory stays reproducible, `state-migration.md:150`); port: fixed (the temporary
  name is given exactly the requested mode through a handle on it before the name is published, so the
  open never depends on the umask; the cases are
  `TestMigrateOwnedDirIdentityHostileUmask` and
  `TestMigrateOwnedDirIdentityHostileUmaskAfterAnInterruption`).

- Supersedes `known-defects/CRW-813.md`, the item beginning "The marker is what a rerun reads to
  recognise a directory this migration made": now port: fixed (that limitation said the window between
  a root's `mkdir` and its marker chmod "is one syscall wide"; the order it described was
  `mkdirat`, `openat`, `fstat` and the parent `fsync` before the caller's chmod, so two fallible steps
  stood in that window, not one, and neither is in it any more - the mode is given through a handle on the
  directory this run created, and the name becomes visible only after that).

- The first cut of the temporary-name creation left three holes of its own, found by the review of the
  first head and closed in the second: the deferred removal of the temporary name was addressed by name
  alone; a creation whose rename succeeded and whose sync then failed reported `made` false, so a retry
  with the same pinned pair read this run's own root as another actor's; and the chmod fallback for a
  kernel whose `fchmodat` cannot express no-follow used a chmod that follows a link (source `roots.go`,
  the `migrateOwnedDirIdentity*` helpers; `state-migration.md:150` requires a directory this migration
  did not create to retain its mode); port: fixed (the removal compares the entry at the temporary name
  with the identity read when that name was created; a creation whose rename succeeded reports `made`
  true even when a later step failed; and a kernel that cannot chmod a name without following a link is
  refused as an unsupported platform. The cases were
  `TestMigrateOwnedDirIdentityRerunWithTheSamePinnedPairFinishesTheRoot` and
  `TestMigrateOwnedDirIdentityChmodWithoutNoFollowIsRefused`; the second head reworked both - see the
  next items, which supersede them).
- The mode was corrected and the name then published without syncing the directory itself, so a crash
  could leave the final name durable while the corrected mode was not, which is the state this issue
  exists to make recoverable (source `roots.go`, `EnsureChild`; the design requires a directory this
  migration created to have its source mode finished on a rerun, `state-migration.md:150`); port:
  fixed (the handle is synced after the mode is set and before the rename publishes the name).

- The first cut of the temporary-name creation read the identity of the name it had just created with a
  second syscall and, when that read failed, removed the directory anyway, treating a matching owner as
  proof of ownership; another process's empty directory could have been deleted (source `roots.go`,
  `migrateOwnedDirIdentityTemp`; `state-migration.md:152` keeps an incomplete temporary reported or
  ignored and never removed on unproven ownership); port: superseded by H3 below, which leaves the
  directory in place and names it in the refusal.

- The second head's own review found that the first head still transferred ownership in three places,
  and the pre-merge evaluation of that head confirmed them. Each is fixed by the rule below, and each
  has a case that fails on the first head (red output kept under the issue's evidence root):

  - **H1, the same-pair retry:** the first head remembered this run's own creation of a root as a
    boolean, so a retry whose rename met `EEXIST` on a root another actor had put at the same path
    reported `made` true and `finishModes` finished that root at the source mode (source `roots.go`,
    `Pair.created` and `EnsureDest`; `state-migration.md:150` requires a directory this migration did
    not create to retain its mode and be reported); port: fixed (`Pair.created` is the identity of the
    directory this process's own creation put at the name, and a retry reports the root as this run's
    only while the name still holds that very directory - a replacement keeps its mode and is reported
    as kept; `TestMigrateOwnedDirIdentityReplacedRootIsNotAdoptedOnRetry`, red on the first head at
    0755 with no note).
  - **H2, the mode step before any check:** the first head gave the mode with a by-name chmod before any
    type or identity check, so a regular file or a hard link another same-uid writer put at the
    temporary name had its mode changed (source `roots.go`, the mode step; `state-migration.md:150`
    requires a directory this migration did not create to retain its mode, and the temporary name is
    visible in its parent, so it is not the private name the issue assumed); port: fixed (the temporary
    is opened as a handle that follows no link and needs no permission on the directory - Linux
    `O_PATH|O_NOFOLLOW|O_DIRECTORY` - and the mode is given through that handle, after `fstat` proves the
    handle is the directory this run created; a name that is not that directory is refused with no mode
    changed. Linux uses `fchmodat2` with `AT_EMPTY_PATH` where the kernel has it (6.5 and later) and the
    `/proc/self/fd/<n>` path otherwise, which is the call a libc `fchmod` makes on a descriptor and is
    why a kernel without `fchmodat2` is no longer refused. Where no such handle can be opened the name
    is checked with `fstatat(NOFOLLOW)` immediately before a by-name no-follow chmod; the cases are
    `TestMigrateOwnedDirIdentityRegularFileAtTheTemporaryIsNotChmodded`,
    `TestMigrateOwnedDirIdentityHardLinkAtTheTemporaryIsNotChmodded` and
    `TestMigrateOwnedDirIdentityFchmodat2AbsentUsesTheDescriptorPath`, all red on the first head).
  - **H3, cleanup without an identity:** the first head removed the temporary when the first identity
    read failed, treating a matching owner as proof of ownership, so another process's empty directory
    could be deleted (source `roots.go`, the cleanup; `state-migration.md:152` keeps an incomplete
    temporary reported or ignored and never removed on unproven ownership); port: fixed (a failed
    identity read leaves the directory in place and refuses with its path, so the next run's
    `OlderTemps` reports it; `TestMigrateOwnedDirIdentityUnreadableTemporaryIsLeftAndReported`, red on
    the first head).
  - **H4, the residual:** the two syscalls between this run's `mkdirat` of the temporary and the read
    that takes its identity are a window in which a deliberate same-uid racer can put its own directory
    at that name. No POSIX call returns a handle to a directory it creates, so the window is recorded as
    a residual here and is not claimed closed. What the change guarantees is that the run adopts,
    chmods and removes a directory only after checking the identity it recorded; the window above is the
    one place where a deliberate same-uid racer can still make it check the wrong identity.

- The generation-2 review and the pre-merge evaluation of that head found five more, all fixed here. The
  identity this process's own creation records is now the directory it holds open for the rest of the run,
  so a name whose entry carries that identity cannot be a different directory whose inode was reused after
  the original was closed. Darwin gets a handle of its own (`O_SEARCH|O_NOFOLLOW|O_DIRECTORY` and `fchmod`
  on it) instead of being treated as a platform without one, so the by-name chmod is no longer reachable
  on macOS. The by-name path itself now reads the mode back and checks the identity again before the
  rename, so a swap in the two-syscall window is refused rather than renamed into place. A destination
  root that does not exist yet has its temporary reported: the classifier now reads the directory that
  holds the root, where a run interrupted while creating it leaves that temporary, instead of walking only
  the root and what is below it. The sentinel error is a type rather than a package-level `errors.New`
  call, so no platform file adds an initializer that runs at program start. Each has a case:
  `TestMigrateOwnedDirIdentityCreatedRootHandleIsHeld`,
  `TestMigrateOwnedDirIdentityWithoutAHandleStillCreates`,
  `TestMigrateOwnedDirIdentityRootTemporaryIsReportedOnTheNextRun`, and the fchmodat2 case, which now
  skips on a platform whose open cannot give a handle instead of failing there.

Limitations, not defects, recorded so each is a decision rather than a surprise:

- The Darwin half of the defect - that Darwin drops the sticky bit from a directory's creation mode - is
  the behaviour the issue names and the reason the mode is given to the name before it is opened. It is
  not observed here: this host is Linux, and the cases model it through the package's own mkdir seam, as
  the earlier ownership cases already did.
- The adoption branch in `finishModes` still recognises a directory by the raw marker mode plus
  `entriesExpected`, so a foreign directory that already existed at the lookup, carried exactly that
  marker mode and held only plan-named entries would be adopted and finished at the source mode. The
  marker is chosen to be one no other writer in this repository uses (`apply.go` `applyTempRaw`), which
  is what keeps this out of reach in practice; the record of a creation this run's own mkdir was refused
  by now closes the same hole for a directory that appears in the run's own window.
- A temporary an older run left in a destination directory makes `entriesExpected` false for that
  directory, so its mode is never finished. That is the design's rule for older temporaries
  (`state-migration.md:152`: they are reported or ignored, never adopted or removed), recorded here so
  the consequence for the mode is known. A temporary this run creates is removed before its name can
  outlive the run, so only another run's can reach this.

- Two same-uid windows are recorded here rather than claimed closed. The first is H4 above: the two
  syscalls between this run's `mkdirat` of the temporary and the read that takes its identity. The second
  is between the read the cleanup makes and the `rmdir` that follows it, where a same-uid racer that swaps
  the temporary in that window can have its own empty directory removed; both need a call that returns a
  handle to a directory it creates or removes, which POSIX does not have. A third, on a platform with no
  descriptor-bound mode handle, is the `fstatat`-then-by-name-chmod pair in `migrateOwnedDirIdentityClaimByName`,
  which is Linux's `O_PATH` path only where the kernel refuses that open.
- A same-uid racer that puts its own directory at the temporary name between the mode step and the rename
  has that directory renamed to the final name; the identity check after the rename then refuses the run,
  so the racer's directory is displaced to the name and the run reports rather than adopting it. Closing
  that would need the rename and the check to be one operation, which no call provides.

- A same-uid process that puts its own entry at the final name between the rename and the pin that
  follows it is refused with a report rather than published into, because the run compares the entry
  against the identity it recorded. The H4 window above is the one place where such an actor can instead
  make the run check the wrong identity and adopt its directory; it is recorded there and not here. The
  file publication carries the analogous residual, documented at `publish.go:80-81`.
