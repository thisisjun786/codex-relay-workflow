# CRW-1274 — managed start checks the parent's declared settings against the live thread, and a settings refusal no retry fixes holds the delivery at once

Source: CRW's own design, not the CXC oracle (CXC v0.2.40, commit 3c1459ac, records the settings a start declares for the parent and compares nothing with the thread). Found by the real-environment trial r2 S6 (evidence `ev/S6/20261012T050218Z`, installed head dd11cba60, `triage-stall.json` and `triage-judge.json`). The Go files are `internal/relay/managed/parent_settings.go` (`checkParentSettings`, `readLiveParent`, `recordedParentSettings`), `internal/relay/managed/create.go` (`create`), `internal/relay/managed/run_steps.go` (`authorizeSettings`, `confirmParent`, `answerCreation`), `internal/relay/delivery/service.go` (`settle`, `settingsRefusalOf`, `settingsHold`, `journalSettingsHeld`), `internal/relay/delivery/reconcile.go` (`settleFromReceipt`, `write`), `internal/relay/delivery/policy.go` (`HeldSettingsMismatch`), `internal/relay/cli/status.go` (`currentSettingsHold`) and `internal/relay/registry/holds.go` (`SettingsHoldReading`).

- A parent whose thread ran other settings than its request declared was recorded with the declaration, and every later delivery to it stalled; port: fixed. The parent ran `anthropic/claude-opus-5-5` with no effort while the policy's `roles.parent` is sonnet-5-5 / xhigh. The parent's first `dag-release` was refused as `worker_policy_pair_mismatch`, the parent wrote a request that declared the policy's pair, and the relay recorded it as the parent's `authorized_settings` (source `managed_start`) from the request alone (`r.parent["settings"]`), with no look at the thread. Every delivery to the parent was then judged against a record the thread did not match: `settings_not_preserved` (model) and `setting_unobservable` (effort) at each resume, `withheld_pre_send`, six retries and `attempt_cap`. `managed.Start` reads the parent thread with `thread/read` right before the creation (after the readiness, scope, ledger and request checks, before `CreateThread`; `dag-release` goes through it) and compares the live model and reasoning effort with the declared ones. A difference refuses the start as `parent_settings_differ_from_thread`; a live value the host does not give (a refused read such as thread not found, an answer without a model or without the `reasoningEffort` field, an effort that is not text) refuses it as `parent_settings_unobservable`. The refusal is an answer (`state` refused, `stage` creation) with a `parentSettings` observation `{taskId, declared, live, differing | problem}`; nothing is created or recorded (the request stays armed), and the same request goes through once the thread runs what is declared. The record is written from the confirmed live values. A host that does not answer at all (a transport failure, not an RPC answer) is not turned into a refusal: it is a failed call of the start, as every other host call is, which `TestRunCharacterization_ErrorsPropagatePerCall` pins for every call of the start. A request whose creation an earlier call already answered does not reach the creation again, so it is not judged there; `authorizeSettings` reads the parent when the parent has no recorded settings yet and refuses at the stage `settings`, and an admitted request replays from what was recorded without asking the thread again. Pinned by `TestManagedStartRefusesADeclaredParentPairThatDiffersFromTheLiveThread`, `TestManagedStartRefusesAParentWhoseLiveEffortAloneDiffers`, `TestManagedStartRefusesWhenTheLiveParentSettingsAreUnobservable`, `TestManagedStartParentReadTransportFailureIsAHostFailureAndRecordsNothing`, `TestManagedStartRecordsTheLiveSettingsNotTheDeclaration`, `TestManagedStartArmedRequestReadsTheParentBeforeRecordingItsSettings`, `TestManagedStartAdmittedReplayIsNotRefusedForALaterParentChange`, and over the real bridge adapter and the fake App Server `TestDagReleaseRefusesADeclaredParentPairThatDiffersFromTheLiveThread`, `TestDagReleaseRefusesWhenTheLiveParentSettingsAreUnobservable` and `TestDagReleaseRecordsTheLiveParentSettings`.
- The thread/read of the parent adds a call to the managed start; port: kept, documented. The call order of a start (`TestRunCharacterization_*`) carries one more `HostCall(thread/read)@run`, directly before `CreateThread`. A start that is refused before the host is asked (a separator in an identity, a project scope, parent settings that differ from the recorded ones) still reaches the host with no call, as `TestPrecreate_RefusalsComeBeforeTheHostIsAsked` pins.
- A settings refusal no retry fixes was retried on the backoff to the attempt cap; port: fixed. `settings_not_preserved` and `setting_unobservable` mean the thread runs other settings than the record, or the host does not say what it runs; the send path scheduled the next try after 30 s, doubling to 900 s, and held the delivery at `attempt_cap` only after the sixth, so the recipient got nothing for about half an hour and no signal a person reads. The delivery is now held at the first such refusal, in the direct send (`settle`) and in the reconciliation of a lost answer (`settleFromReceipt`): `withheld_pre_send` with the hold `held_settings_mismatch`, `next_eligible_at` null (no retry schedule), and a `delivery_settings_held` journal row `{requestId, hold, reason, field, expected, observed}`. The attempt's settlement row carries `expected` and `observed` in `settingsRefusal` for these two codes, and `status` and `assignment-show` show the hold as the kind `capped` with the values beside it (`settingsHold.expected`, `settingsHold.observed`, `recovery`); the per-event delivery snapshot (`Service.SnapshotItem`) carries only `holdReason` and the reported state `held:held_settings_mismatch`, as before (a merge grant keeps `settingsHold` and `recovery` null there). The `delivery_stalled` fault stays, as the fault sweep raises it for any held delivery. The refusals a later attempt can clear (a refused thread/read, a busy recipient, `environments_unknown`) keep the backoff and the cap, and so does `settings_differ_after_load`, the name a settings-free resume (a supervisor, an exception, a role that allows several pairs) gives a model or effort difference: it is outside the two codes the issue names and keeps the backoff on purpose (a follow-up may hold it too). The decision is the coordinator's (CRW-1274, 10-12) and covers every field of `settings_not_preserved`; a mismatch of the MCP profile on a thread another client holds loaded used to clear when that client unloaded it and the daemon tried again, and is now an operator action (`settings-show`, re-record or `generation-open`). Pinned by `TestSettingsRefusalHoldsTheDeliveryAtOnce`, `TestSettingsRefusalFoundByReconciliationHoldsTheDeliveryAtOnce`, `TestTransientRefusalsStillBackOff`, `TestSettingsHeld_status_and_assignment_show_name_the_hold_and_the_values` and `TestDeliveryHeldOnSettingsMismatchStillRaisesDeliveryStalled`.
- The pump's fault collector does not deliver a fault to the management thread; port: kept, out of this issue (the coordinator's decision of 10-12); a new issue carries it.
