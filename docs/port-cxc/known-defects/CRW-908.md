# CRW-908 - cxcfuzz harness: link confinement, shell quoting and the doubled-brace f form

Source: the harness itself (`internal/dev/cxcfuzz`) has no oracle counterpart; its contract is the
CRW-701/CRW-743 issue bodies, and the three defects below were found by management's evaluation of the
merged CRW-857 pull request. The reader the shell-write generator feeds IS a port: CXC v0.2.40 commit
3c1459ac, `plugins/codexclaw/components/pabcd-state/dist/shell-write-destinations.js`
(`shellWriteDestinations` :25-36, `scriptWriteDestinations` :532-549), ported at
`internal/pabcd/hook/shellwrite.go` and `internal/pabcd/hook/shellwrite_verbs.go`. The scenario builder
has no oracle at all: the recorder shims only read the tree the harness materialises
(`internal/dev/cxcfuzz/testdata/{memorygate,shellwrite}/shim.mjs`).

All three are defects in the harness's own input side. None is an oracle-parity difference, and this
issue fixes all three. No line of `docs/port-cxc/known-defects.md` describes the scenario builder's
containment check, so this file carries no Supersedes line.

## Defects

- The scenario builder judged a symlink by its `filepath.Clean`ed target while it created the link with
  the raw target text, and it checked every entry before it built any, so a link an earlier entry had
  created was invisible to a later entry's check and a `..` the kernel applies after following a link was
  collapsed lexically first: `{a -> .}` then `{b -> a/../escape}` passed both checks and the kernel
  resolved `b` outside the case root (source `internal/dev/cxcfuzz/scenario.go` at 1927c4fb: `Scenarios`
  :28-54 checked then built, `linkTarget` :201-220 cleaned the target, `build` :256 stored the raw text;
  port: fixed - the entries are now built in order, each link is judged right after it is created against
  the tree built so far, the link stores exactly the target text that was judged, a `..` in a
  not-yet-existing remainder is refused, a final `EvalSymlinks` sweep resolves every link once more, and
  a refusal removes the case root before any target runs).
- `shellWriteShellQuote` escaped `$` before the ROOT placeholder was substituted, so the placeholder's
  `$` became an escape and the harness then wrote the case root inside it: a double-quoted program's
  destination gained a leading backslash, so the memory gate was asked about a path that is not the one
  the command writes (source `internal/dev/cxcfuzz/target_shellwrite.go` at 1927c4fb :276-282; port:
  fixed - the program is split around each placeholder and only the rest of each part is escaped, so the
  destination after substitution is byte for byte the chosen path; the record's assumption that a campaign
  root is an `os.MkdirTemp` path with no shell-special character is stated at the function, and a hostile
  root stays covered by the value-substitution unit test CRW-857 added).
- `shellWritePythonLiteralForms` wrapped the destination itself in doubled braces, emitting a literal
  Python evaluates to `{<destination>}`: the destination gained a leading brace, became a relative path,
  and the write the issue asked the memory gate to examine was never named. A generator test pinned that
  wrong string, so the defect was invisible to the suite (source `internal/dev/cxcfuzz/target_shellwrite.go`
  at 1927c4fb :288-301 and `internal/dev/cxcfuzz/target_shellwrite_test.go` :164-181; port: fixed - an f
  form now writes every brace INSIDE the destination doubled, so the literal evaluates to exactly the
  destination; a destination with no brace takes the plain f forms; the destination pool gained
  `${ROOT}/codex-home/memories/{x}.md` so the doubled form reaches a generated command, and the pinned
  string was corrected).

The braces of an exact ROOT placeholder occurrence are not doubled: the harness substitutes that token in
the decoded command after the program is built, so doubling the placeholder's own braces would leave the
literal placeholder text in the path, the substitution would find nothing to replace, and the interpreter
would name a relative path - the same coverage failure by a different route. That case is pinned by
`TestShellwriteFStringFormsKeepTheRootPlaceholder`.

## Generation 2 (c7): pre-merge evaluation fixes

The pre-merge evaluation of head 30a746c1 found three defects inside this issue's promise. They are fixed
in this pull request, and this section is the record of the change.

- Supersedes the third bullet above, the f-form defect: now `port: fixed` includes the whole literal-form
  set, not only the brace rule. `shellWritePythonLiteralForms` writes every form so it evaluates in Python 3
  to exactly the destination: a quote the form uses is escaped inside it, a backslash is doubled, a line
  break is written as its escape, a raw form is emitted only where it can hold the destination unchanged
  (no quote, no line break, no trailing backslash), a `b` form only for an ASCII destination, and a form
  that cannot hold the destination is not emitted. The f forms keep the c3 brace rule and the exact-ROOT
  placeholder rule. The same escaping is used for the destinations embedded directly in `shellWriteProgram`.
- A refused build's removal is now certain. `RemoveCaseRoot` first makes every directory under the root
  owner-readable, writable and searchable, descending by hand because a walk lists a directory before it
  can be told about it, and only then removes the root. A removal that still fails is returned as a
  `RemovalError` that names the root and is never a refused case a target may run on; the campaign answers
  it as its own error instead of the refusal case, and the callers' deferred cleanup uses the same helper
  and reports its error instead of discarding it.
- The test helper that modelled Python's f-literal rules is removed. It did not model the interpreter, so
  it could not prove the promise; the tests now evaluate every emitted form with the real interpreter
  (`python3` when it is on PATH, skipping with a message otherwise) over the actual destination pools of
  both targets, including the quote, backslash and brace paths.


## Found while fixing the f forms, not introduced here

- An f form is emitted for every destination, but two shapes in the shell-write destination pool make it
  invalid or wrong in Python, and both predate this issue (the pool at `target_shellwrite.go:120-123` and
  the f forms over it were added by CRW-857; this issue changed only the brace handling, which is a no-op
  for a destination with no brace): a destination holding a single quote makes the f literal
  `f'/m/a'b'`, a Python syntax error, so the form never reaches the interpreter; and a destination holding
  a backslash or a control escape (`/m/a\b`, `/m/a\nb`) is decoded by Python inside a non-raw literal, so
  `f'/m/a\b'` evaluates to a backspace where the destination holds a backslash. `python3 -c` confirms both.
  Not fixed here: neither is one of the three defects this issue names, both are baseline-identical, and
  choosing the corrected form set (raw prefixes, or quote-aware delimiters) changes which literal forms
  the generator emits for those destinations - a generator-grammar change the issue body does not ask for.
  Raised as a follow-up proposal in the handoff.
