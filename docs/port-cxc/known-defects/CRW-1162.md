# CRW-1162 — crw map launcher: the venv is ready only with its completion marker

Source: CXC v0.2.40 (commit 3c1459ac) `bin/codexclaw.mjs:383-406` (the one-time venv bootstrap: the venv counts as ready when its interpreter exists), read through `known-defects.md`, section "Found by the CRW-344 provider detection and map launcher port", and the `crw map` launcher the port inherited from dev. The Go file is `cmd/crw/repomap.go` (`bootstrapRepoMapVenv`, `cleanupRepoMapVenv`, `repoMapVenvReady`, `writeRepoMapMarker`); the tests are in `cmd/crw/repomap_marker_test.go` and `cmd/crw/repomap_test.go`. The item was split off CRW-1147 (disposition d2).

- The oracle takes a venv for ready as soon as `bin/python3` exists, and `python3 -m venv` creates it before pip has installed anything, so a bootstrap killed between the two (or during pip), and a `python3 -m venv` that exits nonzero after it made the interpreter, leave an interpreter without its requirements that every later run uses and that fails at the module import (`bin/codexclaw.mjs:383-406`); port: fixed (readiness is the interpreter and the completion marker `<CRW_HOME>/venvs/repomap/.crw-ready`, written by `writeRepoMapMarker` only after `pip install` exited 0: a temporary file in the venv directory, synced and renamed onto the marker, so the marker is absent or whole whatever kills the process. A run without the marker does not use the venv, with or without `CRW_MAP_BOOTSTRAP=1`; a run with it builds the venv again under the bootstrap lock. A marker without its interpreter is removed before that build, so a kill during the build cannot leave an interpreter that looks ready. A failed `python3 -m venv` is cleaned up like a failed pip: the directory is removed when this attempt created it; when the directory was there before its contents stay, and so does an interpreter that was there before (only an interpreter this attempt made is removed, because a legacy working interpreter is not this attempt's to delete and, without the marker, is not taken for ready anyway); a marker that cannot be written counts as a failed attempt. Pinned by TestRepoMapKilledBootstrapIsRebuiltOnce (a real `crw map` process killed with SIGKILL right after the fake `python3 -m venv` and in the middle of the fake pip, with a fake python3 and venv interpreter on PATH), TestRepoMapVenvFailureCleansUpWhatItMade, TestRepoMapFailedRebuildKeepsAnInterpreterThatWasThereBefore (red: `evidence/red-1162-fix1.log`), TestRepoMapMarkerIsWrittenAtomicallyAndAFailedWriteIsNotReady (the order create, write, sync, close, rename through injected file operations, the marker absent until the rename, and no marker and no temporary file after a failed rename), TestRepoMapStaleMarkerIsRemovedBeforeTheRebuild and TestRepoMapBootstrapWithFakesOnly/mk-fails*, red on dc758b3c7 (evidence `/state/crw/crw-lane-map-venv-marker/evidence/red-1162.log`).
- Migration of a venv from before the marker (no oracle line; a deviation the fix introduces): an existing `<CRW_HOME>/venvs/repomap` has an interpreter and no marker, so it is built again once. The next run with `CRW_MAP_BOOTSTRAP=1` runs `python3 -m venv <dir>` over the directory (no `--clear`: nothing in it is deleted, `pip install -r requirements.txt` reinstalls over it) and writes the marker; later runs build nothing. User impact: that one run needs the network and pays the pip install again. A run without `CRW_MAP_BOOTSTRAP=1` cannot build, so until an opted-in run has rebuilt the venv it no longer uses it and goes on to `uv` or bare `python3` (rungs 2 and 4 of the ladder, documented in `plugins/crw/skills/crw-repo-map/SKILL.md`). The directory crw does not own is never removed: a directory that existed before an attempt keeps its tree, and an interpreter that existed before keeps its file, even when the rebuild fails. Pinned by TestRepoMapRebuildsAnUnmarkedExistingVenvOnce; port: kept as a documented one-time rebuild.

The cxc replay claim for `cli__map__codexclaw_python_runs_repomap_with_it` is unchanged: its stub `python3 -m venv` fails without creating a directory, so the new cleanup removes nothing and the recorded calls, stderr and tree stay as `contract/notes/cxc/CRW-1147.json` records them.
