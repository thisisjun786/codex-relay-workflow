# CRW-1303 — a relay child's sub-agent thread is judged by the child push guard through the child's session_id

Source: CRW's own guard, no CXC oracle (the judgment is in [CRW-1284](CRW-1284.md), the wiring in [CRW-1300](CRW-1300.md), the warn-and-record modes in [CRW-1307](CRW-1307.md)); Go files `internal/relay/hook/childbinding.go`, `internal/harness/payload.go` (`IsSubagentHookPayload`), `internal/harness/guardmode.go` (`RecordDecision`) and the row `pre-tool-use-guarding-child-push` in `cmd/crw/component_hooks.go`. CRW-1303 started from the note in CRW-1300 (its evaluation's d4) that a sub-agent thread has a `session_id` the store does not hold as a `child_task_id`; the premise was checked and does not hold, so no Go code of the guard changed.

- The premise, checked against the live host on 2026-10-14 (read only, codex-cli 0.154.0). Every hook input a thread-spawned sub-agent produced carries the spawning session's `session_id` and the sub-agent's own thread id as `agent_id` (with `agent_type`). The host's decision records (`<CODEX_HOME>/crw/hook-decisions`) hold seven (`sessionId`, `agentId`) pairs; for each, the rollout of the thread `agentId` names has `session_meta.payload.session_id` and `source.subagent.thread_spawn.parent_thread_id` equal to `sessionId`, depth 1, and its own `id` equal to `agentId`. No sub-agent thread id appears as a `sessionId` in any of the twelve sessions recorded. This is the shape `IsSubagentHookPayload` (`internal/harness/payload.go`) already states. So `ChildBinding(session_id)` resolves a relay child's sub-agent thread to the child's relationship (the same `parent_cwd`, the child's own branch from its checkout), and the leg already judges its push as it judges the child's own; port: fixed in the record (the CRW-1300 sentence that a sub-agent push is not judged is rewritten), no code change.
- The lineage method of the issue (follow the parent thread to a relationship, or propagate the child's `CODEX_HOME` settings) is not needed and is not built: no lineage is read from the rollout and no environment is propagated, so no new capability, trust key or leg is added (35 declared legs, trust keys unchanged); port: kept.
- Fail-open. A relationship that cannot be read (settings that do not parse, a store that is not a database) makes a push in any session, a sub-agent thread's included, pass with the `[crw warning]` text and a `warn` decision record (leg, rule, session, and `agentId` of the sub-agent; never the command text), as CRW-1307 decided; the issue's fail-closed wording is superseded. The only block of the guard stays a force, delete or `--mirror` push onto `dev` or `main` by a session the store knows as a child, rule `shared-branch-history`, a sub-agent thread of that child included; the record of a block carries the sub-agent's `agentId` too; port: kept.
- Named limits. (1) Sub-agents deeper than one level: the rollouts of depth 2 and 3 threads name a root `session_id` different from `parent_thread_id`; the hook input they produce was not observed, since no such thread appears in the decision records. If the host stamped the immediate parent's thread id instead of the root session's, a depth 2 thread would have no binding and its pushes would not be judged, and nothing would be recorded; the guard does not read rollouts or thread lineage. (2) A session that is not a child (a parent, an integrator, a sub-agent of either) is not judged and leaves no record, as before. (3) The warning records of this guard share one rule name derived from the refusal text (`child-push-guard`), so an unreadable relay record is told from other warnings only by the warning text. (4) The evidence is the host's records and source and temporary-home tests, not a live hook run of this change.
