# CRW-1306 — an implementation node is accepted by its commit, and no later step waits for a forge row

Source: Jun's decision of 10-13 (relayed by Sion): an implementation node is accepted with a local verification-record/1 only, a pull request is optional, and GitHub is plain external storage, not a gate. The CXC relay (v0.2.40, commit 3c1459ac) accepts an implementation node only on its pull request, and every step after the acceptance reads that pull request through the forge identity recorded with it (`dag_acceptance_forge`). CRW-965 added the pull-request-less commit path (`internal/relay/dagsched/accept_commit.go`) and its integration (`dag-integrate`, `dag-integrate-push`), but several later steps still branched on the forge row. The Go files are `internal/relay/dagsched/mergejudge.go`, `baserefresh.go`, `accept.go`, `mergecheck.go` and `internal/relay/argparse/specs.json`; the tests are `internal/relay/dagsched/crw1306_pr_optional_test.go`.

- `dag-merge-judge` refused a commit acceptance with `disposition_conflict` ("has no forge identity recorded, so there is no pull request to read"). port: fixed (a commit acceptance is judged on the relay's records alone: the stale and under-correction refusals, `stale_criteria`, `predecessor_not_landed`, else `eligible` with a reason that names `dag-integrate`; no forge is read and no `dag_merge_checks` row is written, since that table is the history of what the forge showed). `dag-merge-request` refuses a commit acceptance with `disposition_conflict` naming `dag-integrate`, the route it lands by, because the merge lane carries pull requests. Pinned by `TestCommitAcceptedNodePassesTheMergeCheckAndDagIntegrate`; red output `/state/crw/crw-lane-pr-optional-1306/evidence/red-1-judge-mixed-at-acf226f94.log`.
- The predecessor rule of the merge check read a commit-accepted predecessor at the base ref its edge names, while such a node lands on the integration branches its batches moved (CRW-965, D4), so a pull-request successor stayed `predecessor_not_landed` after the predecessor was integrated and observed. port: fixed (a commit-accepted predecessor is read on its integration refs, as its `integrated` edge reads it). Pinned by `TestAPlanMixingPullRequestAndCommitAcceptancesDoesNotStall` (a plan with a commit node, a pull-request node and a pull-request successor of the commit node: edges, merge check and progress); red output in the same log.
- `dag-base-refresh` refused a commit acceptance with `disposition_conflict` ("has no forge identity recorded, so the pull request that carried the refresh cannot be read"). port: fixed (the head to refresh to is the head the later generation's ruling fixed, `dag_verified_heads`; the base branch is the one the node's outgoing `integrated` and code-pinned edges name in its checkout, else the base of the manifest it was released with; the tip is read in the checkout; the proof and the record are the pull-request path's). In the acceptance's own generation the ruled head is the accepted head, so the call answers that there is nothing to refresh. The record of the refreshed head is given with `dag-accept --commit <refreshed head>`, which is now a replay of the same acceptance when the acceptance stands on that head through a recorded refresh (before, the commit replay compared only the head of the stored verification record and refused it). A retry of the original `dag-accept --commit` (the first generation's head and record) is refused as it was before this change once the parent rules a later generation, refresh or not: the commit path takes only the head the current generation's ruling fixed, so it answers `head_not_receipt_head` without `--event` and `stale_generation` with the first generation's event; the refreshed record given once is a replay, the same call without a record again is a pure replay, and a pre-merge record named a second time is refused as a second attach, as on the pull-request path. Pinned by `TestCommitAcceptedNodeTakesABaseRefreshWithoutAPullRequest`, `TestTheOriginalCommitAcceptanceIsRefusedTheSameBeforeAndAfterABaseRefresh` (its part before the refresh also passes on acf226f94: `/state/crw/crw-lane-pr-optional-1306/evidence/round2/d1-old-behaviour-at-acf226f94.log`) and `TestCommitRefreshBaseIsReadFromTheEdgesOrTheManifest`; red output `/state/crw/crw-lane-pr-optional-1306/evidence/red-2-base-refresh-at-acf226f94.log`.
- The `dag-accept` refusal for an implementation node that names neither path said it "is accepted on its pull request", and its help put the pull request first. port: fixed (the refusal and the help name the commit path as the default and the pull request as optional; the refusal of a local-checkout edge on the pull-request path also names `--commit` as the way to accept the node on that checkout).
- Steps that already proceeded for a commit acceptance and are left as they are: `dag-integrate` and `dag-integrate-push` (CRW-965), the `integrated` and code-pinned edges (`commitIntegratedEdge`, `edgeStatus`), the completion targets (`commit_targets.go`), `dag-progress` (no pull request link, counted integrated), the re-validation guards (`acceptanceRepositories` reads the acceptance's own repository when there is no forge row), and a release's freshness check (a pinned predecessor accepted by its commit stands on a commit no push can move, so no pull request is read for it). port: kept. The merge train and the merge lane (`internal/relay/mergeturn`) keep their forge joins: a commit-accepted node never enters them.
- The stored format does not change: no table, column or migration is added.
