# CRW-834 — executable writes under syscall.ForkLock

Source: the port's own product code, `internal/runtime/install/archive.go:373` (the unpack that
writes `bin/crw`), and the Go test files of `internal/runtime/install` that write a file the same
test process then runs (`alias_test.go`, `decisions_test.go`, `features_test.go`,
`landing_internal_test.go`, `proc_internal_test.go`, `reclaim_test.go`, `remove_test.go`,
`unit_test.go`, `wiring_test.go`, `zone_test.go`). No CXC v0.2.40 source or corpus fixture is
involved: the race this issue fixes is in the port's own write path, and the oracle has no
counterpart of it to record.

No defect was found. This issue adds the `writeExecutable` helper
(`internal/runtime/install/execwrite.go`) and moves the writes of files this process then runs onto
it, so a fork cannot inherit a write descriptor and leave the path unexecutable (ETXTBSY,
golang/go#22315, the race CRW-734's parallel tests exposed). No oracle behaviour changes, so no
line of [docs/port-cxc/known-defects.md](../known-defects.md) is left pending, kept or fixed by it,
and none is carried over. The record exists because this issue's pull request creates it, as
[the directory's README](README.md) asks.
