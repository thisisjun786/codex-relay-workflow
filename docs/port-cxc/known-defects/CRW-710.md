# CRW-710 — differential fuzzing target: the doctor harness report

Source: CXC v0.2.40 (commit 3c1459ac) `plugins/codexclaw/components/cxc-ops/src/doctor.ts`
(`renderDoctor` :648-661, the report types :23-63, `buildDeclaredFeaturesCheck` :132-164) and
`plugins/codexclaw/components/cxc-ops/src/cli.ts` (:80-93, `JSON.stringify(report, null, 2)`),
through the port in `internal/runtime/doctor/harness_report.go` and `harness_run.go`, and the new
differential-fuzz target `internal/dev/cxcfuzz/target_doctor.go` with its oracle shim
`internal/dev/cxcfuzz/testdata/doctor/shim.mjs`.

The one item below is a difference the target's campaign found. It is not fixed here: this issue
pins it as a case and passes it on as a follow-up proposal (the issue body: this PR does not fix a
difference it finds).

- `harnessReportCut` measures the 160 UTF-16 unit cut by ranging over the Go string, and Go's range
  reads each byte of a WTF-8 lone surrogate as one U+FFFD unit, so a stderr holding one counts three
  units where JavaScript counts one and the cut can land inside the surrogate's three bytes: measured
  on this head, a stderr of 157 `x` followed by `U+DCED U+DCA0` (the harness's own `SurrogateEscapes`
  decoding of `"\\udced\\udca0"`) is cut to 156 `x` plus `ED B3` where the oracle keeps the whole
  `U+DCED` and `U+DCA0`, so the JSON writes `\\udced` plus U+FFFD bytes instead of the two escapes
  and the text loses one U+FFFD (source `plugins/codexclaw/components/cxc-ops/src/doctor.ts:137`;
  pinned by the case `features-cut-inside-a-wtf8-lone-surrogate` in
  `internal/dev/cxcfuzz/testdata/doctor/cases.json`, tag `open`, and by
  `TestDoctorOpenCaseIsTheCutDivergence`); port: pending, class wording (the severity, the
  PASS/WARN/FAIL decision, the exit status and the files read and written are identical; only the
  evidence string's bytes differ). The sibling case `features-cut-splits-an-astral-pair`, where the
  cut falls inside a valid surrogate pair, agrees with the oracle and is pinned `identical`, so the
  defect is the WTF-8 byte counting alone and not the cut boundary. The runner the harness builds
  (`harnessRunExec`, `harness_run.go`) decodes its streams with `source.DecodeUTF8`, which turns an
  invalid byte into U+FFFD, so a real `codex features list` probe cannot carry a WTF-8 surrogate and
  the difference is reachable only through a caller that hands `HarnessFeaturesCheck` a string the
  JSON decoder kept the escape in.
