Source: CXC v0.2.40 (commit 3c1459ac) `plugins/codexclaw/components/pabcd-state/src/steering.ts`
`applyOps` (:189-239, the annotate arm :193) and `applySteeringBatch` (:253-333, the duplicate scan :265-270,
the entry :271-276, the rows :278-306). The port is `internal/pabcd/goalplan/steering.go`
(`steeringApplyLocked`, `steeringEvents`, `steeringRecordEvents`, `steeringSameBatch`), the entry and its
reader in `internal/pabcd/goalplan/types.go` and `plan.go` (`SteeringEntry.Ops`, `SteeringEntry.Events`,
`reviveSteeringOps`, `reviveSteeringEvents`), the loop CLI in `internal/pabcd/cli/loop_mutate.go` and
`loop_render.go`, and the skill text in `plugins/crw/skills/crw-loop/references/durable-goalplan.md`.
Cases: `internal/pabcd/goalplan/steering_payload_test.go`, `internal/pabcd/cli/loop_steer_payload_test.go`;
red output in `/state/crw/crw-lane-orchestrate-atomicity/evidence/CRW-1111/`.

- `applyOps` validates an annotate op and then skips it, and the entry the batch commits holds only the key,
  the rationale, the evidence, the time and a summary, so the note of a successful annotate is recorded
  nowhere and is lost for good (`steering.ts`:193, :271-276); port: fixed (a lost-record defect, the class the
  parity rule revision of 2026-10-03 fixes during the port: the entry records the batch's normalised ops,
  the note and the dependency declarations included, the plan reader keeps them through every rewrite, and
  `loop show` lists each note as `  - note <key>: <note>`; `TestSteeringAnnotateNoteSurvivesTheRoundTrip`,
  `TestLoopSteerShowListsTheAnnotateNote`).
- The plan, which holds the idempotency key, is committed before the `steered` and `dependency_registered`
  rows are appended, and a retry with the same key answers duplicate at once, so a row an append failure or a
  stopped writer left out can never be written (`steering.ts`:265-270 against :278-306; CRW-793 fixed the
  directory-sync variant only); port: fixed (the entry records one event per row it owes with a stable id,
  `steer:"<key>"` and `steer:"<key>":op<i>` (the key is quoted, so no key can spell another batch's id); each
  row it appends carries that id as an added `eventId` member, in the way a round row carries `roundId`; the first
  attempt appends them in the oracle's order, and the same batch sent again under the same key appends, under the
  goalplan write lock, exactly the events whose id no row of the ledger carries yet - another batch's row of the same
  time and detail is not taken for them; a row an earlier build wrote without an id is matched by event, time and
  detail - and applies nothing again; a retry that finds a row in the ledger fsyncs the ledger and the plan directory
  before it counts it as recorded, since the earlier attempt may have written it whole and failed its fsync, and a
  sync that fails keeps the warning (`TestSteeringRetrySyncsARowItFindsBeforeCountingIt`); `TestSteeringStableIDsActuallyDeduplicate`,
  `TestSteeringRetryRecordsTheRowsAFailedAppendLost`, `TestSteeringRetryRecordsTheRowsAfterEachFailedAppend`).
- The same key with a different batch answers duplicate with the stored entry, so the different batch is
  reported done although nothing of it was applied (`steering.ts`:265-270); port: fixed (a recorded batch
  that differs - rationale, evidence or ops, a work phase's prerequisites compared as a set - is refused with
  `idempotencyKey "<key>" was already used at <time> for a different batch - send different content under a
  new key`, writing nothing; the add verbs keep their own conflict texts; `TestSteeringSameKeyWithAnotherBatchIsRefused`,
  `TestLoopSteerSameKeyWithAnotherBatchIsRefused`). This changes the CLI contract an agent sees: a different
  batch needs a new key.
- The oracle's failed-append warning ends "Re-running is a no-op because the key is recorded."; port: fixed
  (it ends "Re-running the same batch with the same key records the missing rows without applying it again.",
  which is now what a retry does).

An entry written before this change carries no ops or events (a legacy entry): it still answers duplicate for
its key, whatever batch is sent, and nothing it may have lost is reconstructed (`TestSteeringLegacyEntryIsLeftAsItIs`).
The two new fields are the format change: this build's reader keeps them, and an earlier build's lossless
write guard refuses to rewrite a plan that holds them (`goalplan '<slug>' holds steeringLog[0].events that
this build cannot keep; refusing to rewrite it`, shown with the dev build in
`evidence/CRW-1111/old-reader-refuses.txt`) while it still reads the plan. `schemaVersion` is not raised,
because its versions 2 and 3 mean the final gate. The ledger rows keep the oracle's bytes. Three recorded
fixtures change and are claimed intentionally-changed in `contract/notes/cxc/CRW-1111.json` (moved from the
identical list of `CRW-383.json`): `cli__loop__criteria_questions_and_steer`, `cli__loop__refusals` and
`cli__loop__work_phases_tasks_and_completion`.

- Supersedes CRW-793.md, item beginning "`writeGoalplan` reports a failure that happened after the rename",
  in its clause "the duplicate path is unchanged": the duplicate path now records the rows the entry still
  owes (port: fixed, above).
