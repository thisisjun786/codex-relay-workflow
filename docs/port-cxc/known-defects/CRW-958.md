# CRW-958 — per-use storage roots, tool environment and the storage check

Source: CRW's own design, not the CXC oracle (CXC v0.2.40, commit 3c1459ac, names no storage roots; the pointer is the port). The Go side is `internal/crwconfig` (`paths.go` the roots, `toolenv.go` the tool environment, `check.go` and `fs_*.go` the check behind `crw config check`), with the consumers `internal/relay/store/state.go` (the relay state selection), `internal/relay/job/spawn.go` and `internal/relay/evidence/runner.go` (tool roots for a job and an evidence command), `internal/dev/ci/local.go`, `internal/dev/ci/validate.go`, `internal/skill/merge_build_check_go.go`, `internal/manage/config.go`, `internal/manage/pump.go`, `internal/manage/relay.go` (`coreChildEnv`), `internal/manage/audit_grade.go`, `internal/manage/deliver_send.go`, `internal/manage/upgrade_steps.go`, `internal/manage/integrate.go`, `internal/manage/audit_package.go`, `internal/relay/service/record.go` and `launch.go` (the daemon log), `internal/runtime/doctor/doctor.go` and `internal/runtime/install/install.go` (the storage preflight). These are the places the issue's text and the coordinator's triage differ from what this change does.

- The triage proposed `manage_state` as the durable-state bundle root that owns the relay store, its WAL and its sidecars. The current canon and code keep the management tool's state and the relay's state apart (`internal/manage/config.go` `StateDir`, `internal/relay/store/state.go` `DiscoverStateDir`), so `manage_state` is unchanged and a new root, `relay_state`, is the relay's durable state: the parent of the per-scope store directories, each one bundle; port: kept (a deviation from the triage, decided by the verifier's correction). It is read in the relay's one state selection (`store.DiscoverStateDir`, behind `ResolveStateDir`), so a relay started directly, the registered services, the install commands and the relay the management tool starts choose the same bundle. Its precedence is `--state` (which is also how `manage.relay.state` reaches the relay), `CODEX_SESSION_RELAY_STATE`, the scope directory below a configured `relay_state`, then discovery below `XDG_STATE_HOME`; discovery's legacy-directory and recorded-store rules apply below the configured root unchanged, and the selection reports `source: config`. The management tool no longer derives a `--state` from `relay_state` (the first version did, which made the configured root win over `CODEX_SESSION_RELAY_STATE` and left a relay started directly on another store); it hands a `--config` file to the relay child as `CRW_CONFIG`. `crw config check` reports a placement already in use elsewhere as drift.
- The store, its WAL and its sidecars are one bundle: a `paths.relay_store`, `relay_db`, `relay_wal`, `relay_sidecar` or `relay_sidecars` key is refused (`state_split`) on its own, with or without a `relay_state` beside it (the first fix round returned before the split check when `relay_state` was not named), and for every source of the selection (`store.ResolveStateDir` calls `crwconfig.RelayStateSplit` before `--state` and `CODEX_SESSION_RELAY_STATE`), so the management tool, which refuses split keys when it loads its configuration, and a relay started directly refuse the same files; a store whose WAL or sidecar is a link into another directory is refused too. A configured `relay_state` is judged only where the selection uses it: the management tool no longer refuses an unusable `relay_state` when `manage.relay.state` or `CODEX_SESSION_RELAY_STATE` chooses the store, as a relay started directly never did; port: fixed.
- The relay's `daemon.log` is a log, not part of the bundle: a configured `log_root` moves it to `<log_root>/relay/<16 hex of the SHA-256 of the store's resolved path>/daemon.log` (`crwconfig.RelayLogFile`, read in `service.New`; the launched daemon's output, the journal notes and the tail a failed start reports all use it), and the pump log to `<log_root>/pump.log`. With `log_root` unset both stay where they were, so the Python-parity file layout of a store directory is unchanged. `state_split` no longer counts a `daemon.log` kept apart; port: fixed (the first round left `daemon.log` in the store directory and documented that as the bundle rule, which the issue's log-root criterion does not allow).
- Every child the management tool starts gets the configuration and the tool roots: the relay (as before), the audit and pre-merge grader (`auditRunGrader`), the bridge the deliveries dial (`deliverBridgeCommand`), the commands an upgrade runs (`upgradeRunCommand`) and the record-version and verification commands of the integration queue (`integrateChildEnv`, which sets `Runner.Env`), through one helper (`coreChildEnv`: a `--config` file as `CRW_CONFIG`, the configured `GOCACHE`/`GOMODCACHE`/`GOTMPDIR`, `build_work` made first, nothing added when nothing is configured); the integration queue builds the same values without making a directory (`coreEnvValues`) and prepares `build_work` through `Runner.Prepare` right before its gate, record-version or verification command starts, so `crw manage integrate --dry-run` makes no directory; port: fixed.
- The storage check is called outside `crw config check` and `crw doctor storage`: the plain `crw doctor` report carries it as `storage` (`doctor.StorageReport`), and `crw install install`/`update` run it as a preflight before the archive is read (`crwconfig.Preflight`): a structural fault of a configured root or a split refuses with nothing read or written, and a warning is the run's first step; port: fixed.
- Drift is read from the consumers, not from the defaults alone: the placements in use are the relay stores the scope registry and the installer's unit record (also when the XDG default is empty), the pump log in the management state directory (`manage.state_dir` or `manage_state`), the daemon logs in the store directories, Go's own caches and the populated defaults. Each one outside the configured root is a `drift` warning naming both paths and the record it came from; nothing is moved; port: fixed.
- The triage's evidence that `merge_build_check_go.go` makes `GOCACHE`, `GOMODCACHE` and `GOPATH` owned directories was wrong: the owned parts are the temporary directory and telemetry, and the caches are the caller's. The helper keeps the `HOME`, `GOENV`, `GOWORK`, telemetry and owned `TMPDIR`/`GOTMPDIR` isolation, names a configured `build_cache` and `module_cache` after everything else, and under a configured `build_work` makes its owned directory a `merge-build-go-*` subdirectory that it removes itself; port: kept.
- The sealed local CI run (`internal/dev/ci/local.go`) takes `build_cache` and `build_work` from the configuration and does not take `module_cache`: a module tree is trusted from a cache without the go.sum check, so the module cache is not part of what a sealed run may read (`TestLocal_a_step_never_sees_the_callers_module_cache`); port: kept.
- The socket path check counts the bytes of the whole path, suffix included (`<root>/<16 hex scope>/control.sock`), not the root's length. It is an error only for `relay_state`, whose suffix is known; `temp_root` and `scratch_root` hold the sockets of tests whose names are not known here, so a root with no room for the store-socket suffix is a warning there; port: kept.
- v2 flow nodes (F04) keep their per-call working directory under the durable flow state, which F05 uses as a persistent thread's identity; this change does not move it to a disposable temporary root and adds no sentence that does. The tree this change is made on carries no flow engine, so there is no call site to wire; port: pending (the flow engine's lane takes `crwconfig.ToolRoots` and `temp_root` for its tool starts and states the durable call directory's lifetime and recovery).
- The packet text of `plugins/crw/skills/crw-run/references/task-packet.md` already names `temp_root` and `scratch_root` and a short whole socket path; the `/var/tmp/crw-<n>` example in the triage is not in the current text. `internal/dev/cxcfuzz` built a host path (`/scratch/crw/fuzz`) into its default output root; port: fixed (it is `fuzz` below the resolved `scratch_root`, and `TestNoHostPathOrDeviceNameInProduct` fails on any such path in product code, skills and packet templates). The recorded-oracle checkout `/var/tmp/cxc-v0.2.40/...` that `internal/dev/cxcfuzz/echo.go` built in is gone: `cxcfuzz.OracleRoot` is the directory `CRW_CXC_ORACLE_ROOT` names, else `cxc-v0.2.40/plugins/codexclaw/components` below the configured `tools_root`, and `TestNoHostPathOrDeviceNameInProduct` also fails on `/var/tmp/cxc`; port: fixed. A host that kept the tree at the old place sets `CRW_CXC_ORACLE_ROOT` (or places the tree below its tools root) or the oracle-backed fuzz tests skip as they do on a runner with no tree.
- A configured `build_work` that does not exist is accepted by the read-only check and made by the consumer: `ToolRoots.Prepare` (called through `ApplyTo` and `ConfigureCommand`, and by `crw-dev ci local`, `ci validate`, the merge build check and the audit package expansion), because `go` makes its work directory with `os.MkdirTemp` directly below `GOTMPDIR` and fails with `creating work dir` when the parent is missing; port: fixed.
- The management-started relay and every background job and evidence command get the configured tool roots in their environment; with none configured they inherit the environment as before (`cmd.Env` stays unset); port: kept.
- A configured root keeps its raw spelling at every consumer: a root that mixes a symbolic link and `..` (`/a/link/../root`) names the directory the filesystem gives that spelling, so the relay's daemon log directory is made from the spelling (`service.rawDir`, not `filepath.Dir`), the merge build check makes its owned directory as spelled and then names it by its physical path (`filepath.EvalSymlinks`) in every value it gives the go tool (`XDG_CONFIG_HOME`, `TMPDIR`, `GOTMPDIR`, the darwin `HOME` and probe) and in its cleanup, because the go tool cleans what it joins below those values and would otherwise read no off telemetry mode and write at the lexically cleaned place, the fuzz output directory and its summary, divergence and failure files are joined with `crwconfig.JoinRoot` (`cxcfuzz.DefaultOut`), and the observed `state_split` walk reads the store's directories, databases and sidecars through the same spelling the relay's selection keeps; port: fixed (the first rounds cleaned the spelling at those last joins and tested only ordinary paths; the third round passed the raw spelling to the go tool, which a run of the real go tool shows reading telemetry mode `local` at the cleaned place, `TestMergeBuildToolEnvRawBuildWorkHoldsTheRealGoTool`).
- A registered service keeps the configuration it was registered with: `crw install register-service` writes `Environment=CRW_CONFIG=<file>` into the unit when the registering environment selected an existing file through `CRW_CONFIG` or `XDG_CONFIG_HOME` (`crwconfig.ExplicitFile`), because a user manager carries neither variable; a file at the default location and a missing file add no line. This changes the unit text for such a registration, so an existing unit of that kind reports `unit_differs` until it is removed and registered again; port: fixed.
- The sealed local CI engine treats `internal/crwconfig` as engine source (`localEngineSources`): the engine runs `LoadToolRoots` and `ToolRoots.Apply` from the caller's compiled source, so an edited, extra or deleted file there, or a binary built from a revision whose `internal/crwconfig` differs from the verified commit's, refuses the run with `engine_differs_from_commit`. The engine package's other import dependencies stay outside the byte comparison, as before this change (CRW-1025 listed only the three paths); port: fixed for the dependency this issue added.
