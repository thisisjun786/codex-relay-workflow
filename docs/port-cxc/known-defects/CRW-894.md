# CRW-894 — the shell family behind a pipe, a here-string, a here-document and -c (re-check of 10-09 on dev 09e5c5bcc)

Source: the original `worktree-guard.ts` allows these shapes too (it reads no program position at all), so the defects are
the original's; the port reads them through the CRW-1028 reader (`internal/pabcd/shellir`). The 10-09 re-check of dev
09e5c5bcc (probes under `/state/crw/mgmt/recheck-20261009/`) and the independent verifier (c9(c), c10(c)) found that the
shell list of the reader (`isShell` in `internal/pabcd/shellir/policy.go`) held bash, sh, dash, zsh and ksh only. A program
piped or given to any other POSIX or Korn shell was a plain command the reader did not judge, so all three gates (the
memory write gate, the GitHub post guard and the worktree deletion guard) allowed it. The rows are
`internal/pabcd/hook/testdata/shellir/rows/18-crw-894-shell-family.txt` (CRW-894-sf-01..86, indexed in
`reproductions.tsv`) and `rows/19-crw-894-eval-1688f7c5.txt` (CRW-894-ev-01..75, after the evaluation of 1688f7c5) and `rows/20-crw-894-verifier-4636e20a.txt` (CRW-894-vf-01..37, after the independent verifier of 4636e20a) and `rows/21-crw-894-verifier-5d41d266.txt` (CRW-894-vr-01..38); `TestReproductionRows` judges them and `TestShellFamilyThroughEntryPoints` sends the same rows
through `HandleWorktreeGuardPreTool`, `HandleMemoryWriteGate` and `HandleGitHubPostGuard`; the reader-level tests are in
`internal/pabcd/shellir/shell_family_test.go` and `stdin_alias_test.go`; `TestPipedProgramRunsUnderRealPrograms` runs the piped programs under the real shells and python.

- `printf x | python3 -m json.tool` (the issue's allow control): refused, as on dev; port: kept, and the allow control is withdrawn.
  The control's premise is that `json.tool` runs only standard modules. It does not: `python3 -m` puts the working directory first
  on `sys.path`, and `json.tool` imports `json` and, after it, `argparse`, `re`, `shutil`, `inspect`, `locale` and more (the list
  changes between pythons), so a `json/tool.py`, a `json.so`, an `argparse.py` or a `re.py` in the directory runs instead, and a
  text can create such a module (a copy, a redirection, a dangling link, an archive) in the same command. The real python 3.14 on
  the host runs a local `argparse.py` during `json.tool` (`TestPythonJSONToolRunsTheLocalModule`,
  `TestPythonJSONToolRunsALocalStandardModule`). Under the CRW-1028 rule (prove what runs or refuse) nothing in a text proves the
  directory holds no module, so every `python -m MODULE` is an option the reader does not model (`python3 option -m is not
  modelled`). Rows ev-52..58, vf-35..37 and vr-26..30, vr-37, vr-38 (the shapes that expected the module allowed) record the
  deviation `attempt/deny/deny`, row CRW-894-14 the same; the rows that refuse a shadowed or created module (ev-59..66, vf-26..34,
  vr-01..25, vr-31..36) are refused for `-m` itself. `TestPythonModuleIsRefused` holds the refusal in the directory readings
  and in the reading with no directory. A pipeline that must format JSON runs `jq .`, which is allowed.
- `printf 'echo hi' | bash </dev/null` (the other control of the issue's wording): refused on purpose; port: kept. The Bash tool runs
  its text under zsh, and zsh with MULTIOS (its default) opens a second input redirection of a command in a pipeline as the
  concatenation of the pipe and the file, so `bash` reads the pipe as well as `/dev/null` and runs the piped program. The real zsh
  shows it (`TestPipedProgramRunsUnderRealPrograms`, cases "zsh MULTIOS with /dev/null" and "zsh -f ..."; the same text prints the
  piped marker), so allowing the control would allow `printf 'rm -rf ../repo' | bash </dev/null`. A shell inside a carried text
  that reads `/dev/null` (`printf x | bash -c 'bash </dev/null'`) is allowed, because the inner shell is a new text (row CRW-894-12).

## CRW-1085 supersedes the blanket module refusal

Clean json.tool invocations and the other three fixed modules are modeled under CRW-1085's bounded file/discovery and import-shadow rules. Clean controls in the existing rows now allow; shadowed, rewritten and unordered imports still refuse. The earlier withdrawal of all json.tool controls is superseded; port: fixed. See [CRW-1085](CRW-1085.md).
