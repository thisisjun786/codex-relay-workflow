# CRW-894 — the pipe program position's residual forms: standard-input aliases, exec -a, a shell inside a piped -c program or eval, busybox and interpreters

Source: `plugins/codexclaw/components/pabcd-state/src/worktree-guard.ts` at v0.2.40 (commit 3c1459ac) —
`evaluateSegment` :347-446, `evaluateCommand` :453-486, `stripPrefixes` :263-278, `splitSegments` :191-219 and
`tokenize` :221-254 — and `plugins/codexclaw/components/pabcd-state/src/memory-write-gate.ts` —
`classifyMemoryWrite` :190-230; the port in `internal/pabcd/hook/worktreedel.go`
(`worktreeDelUnreadablePipes`, `worktreeDelUnreadablePipePiece`, `worktreeDelUnreadablePieceCommand`,
`worktreeDelUnreadableStdinRedirect`, `worktreeDelUnreadableStdinAlias`, `worktreeDelUnreadableScriptAlias`,
`worktreeDelUnreadableInterpreterStdin`, `worktreeDelUnreadablePipePrograms`, `worktreeDelWrapperOptionArg`,
`worktreeDelQuoteWrappers` and `worktreeDelUnreadableLineCommandAt`) and the memory gate's shell branch in
`internal/pabcd/hook/memorygate.go` (not edited by this issue; it reads `worktreeDelUnreadableProgram`).

- A redirection on descriptor 0 whose target reopens the same pipe was read as a file on descriptor 0, so the pipe
  suppression cancelled the pipe refusal: `printf 'rm -rf ../repo' | bash </dev/stdin`, `| bash </proc/self/fd/0`,
  `| bash 0</dev/fd/0`, `| bash </dev/fd/0` and `| bash </proc/1/fd/0` all ran the piped program; and a script
  operand or a `source`/`.` operand naming one of those paths was read as a script file: `| bash /dev/stdin`,
  `| bash /proc/self/fd/0`, `| sh /dev/fd/0`, `| source /dev/stdin` and `| . /dev/stdin` (source
  `worktree-guard.ts:347-446`, which reads none of them); port: fixed by CRW-894 (a security fix under the parity rule
  revision of 2026-10-03: `worktreeDelUnreadableStdinAlias` names /dev/stdin, /dev/fd/N, /proc/self/fd/N and
  /proc/<anything>/fd/N after a lexical Clean, `worktreeDelUnreadableStdinRedirect` no longer treats a redirection to
  one as a file on descriptor 0, and `worktreeDelUnreadableScriptAlias` plus the pipe rule's `source`/`.` branch
  refuse the operand form; `TestWorktreeDelPipeStdinAliasDenied` and `TestWorktreeDelPipeStdinAliasOperandDenied`).
- The shared wrapper table did not read exec's `-a NAME`, so the operand hid the command: `printf 'rm -rf ../repo' |
  exec -a x bash` and `exec -a x rm -rf ../repo` were allowed (source `worktree-guard.ts:263-278`, whose prefix set
  is sudo, command, builtin and env only); port: fixed by CRW-894 (`worktreeDelWrapperOptionArg` gives exec's `-a` one
  operand argument, so the pipe rule and the removal check, which share the table, both name the command behind it;
  `TestWorktreeDelPipeExecOptionDenied`).
- A shell inside the program a piped shell runs inherited the pipe but was never read: `| bash -c 'bash'`,
  `| sh -c 'exec bash'`, `| bash -c 'nohup bash'`, `| eval bash` and `| eval 'bash'` were allowed while the inner
  shell read the piped program (source `worktree-guard.ts:347-446`); port: fixed by CRW-894 (the pipe rule hands the
  region on to the program a listed shell's `-c` option or an eval operand holds, one reading depth deeper, and refuses
  at the reading-depth limit rather than allowing; `TestWorktreeDelPipeShellInsideProgramDenied` and
  `TestWorktreeDelPipeResidualNestingFailsClosed`).
- busybox was no wrapper, so its applet was read as the command itself: `printf 'rm -rf ../repo' | busybox sh` and
  `busybox rm -rf ../repo` were allowed (source `worktree-guard.ts:263-278`); port: fixed by CRW-894 (busybox joins
  `worktreeDelQuoteWrappers`, whose first operand names the applet, so `busybox sh` is a listed shell and
  `busybox rm` a removal; `TestWorktreeDelPipeBusyboxDenied`).
- An interpreter that reads its program from standard input was no program position: `printf x | python3`,
  `python3 <<< 'import os'` and `python3 <<EOF` were allowed while the interpreter read the piped program (source
  `worktree-guard.ts:347-446` and `memory-write-gate.ts:190-230`); port: fixed by CRW-894
  (`worktreeDelUnreadableInterpreterStdin` reads python, python3, py, perl, ruby, node, nodejs and php, including the
  versioned Python names the repository already knows (`shellVerbVersioned`), with no `-c`, `-e`, `-r`, `-m` or
  other program option and no script operand — a lone `-` asks for standard input — as a program read from the pipe,
  the here-string or a here-document on descriptor 0; `TestWorktreeDelPipeInterpreterDenied`,
  `TestWorktreeDelHereStringInterpreterDenied` and `TestWorktreeDelHeredocInterpreterDenied`).
- The memory gate reads the same discriminator, so the five forms above are write attempts of their own and the gate
  fails closed on them: `printf 'echo x > <memories>/a' | exec -a x bash` and the same with `| bash </dev/stdin` are
  denied without a grant with `(a program the gate cannot read: ` in the reason (`TestMemoryGatePipeResidual`;
  memorygate.go is not edited by this issue).
- Accepted over-denial of the interpreter rule: an interpreter whose operands are options the guard does not place, such
  as `printf x | python3 --version`, is refused although it prints its version and reads no program from standard
  input. The rule the issue fixes reads an interpreter with no program argument as a program read from standard input,
  and an unknown long option is no program argument the guard can read (source `worktree-guard.ts:347-446`); port:
  fixed as an accepted false positive of the security fix, in the shape CRW-726 recorded for its own pipe rule.
- Found by this pull request's Codex review (P1, security): the interpreter's option arguments were read as script
  operands, so `printf x | python3 -W ignore` and `printf x | node -r module` ran the piped program;
  `worktreeDelUnreadableInterpreterStdin` now skips the argument of an option that takes one
  (`worktreeDelUnreadableInterpreterArg`) and reads the attached form too. The same review's P1s — a lexical
  `/dev/./stdin` alias, the spaced here-document operator `python3 << EOF`, the versioned and alternate interpreter
  names, and `python3 /dev/stdin` as a script operand — are fixed by the Clean, by reading the operator word with its
  descriptor, and by `worktreeDelUnreadableInterpreter` and `worktreeDelUnreadableStdinAlias`.
- Found by this pull request's Devin review (yellow): `python3 3<<EOF` fed descriptor 3 and was still read as an
  interpreter program on standard input; the here-document branch now reads only a descriptor-0 operator
  (`worktreeDelUnreadableHereDescriptor`). The same review's busybox finding — `busybox --help rm` read the operand
  as an applet — is fixed by giving busybox's global modes no applet.
- Rebutted, not fixed (Devin, red, `kind: security`): the claim that `printf x | bash </dev/null </dev/stdin` restores
  the pipe because the later alias wins. It does not: bash 5.3.9 reads `/dev/null` there (the alias reopens the
  descriptor as it already stands, verified with a harmless stand-in), so the guard's answer — a file on descriptor 0
  replaces the pipe — is correct and the reported bypass does not exist. Making the last redirection win was tried and
  reverted: it denied the allowed `printf x | bash </dev/null </dev/stdin`.
