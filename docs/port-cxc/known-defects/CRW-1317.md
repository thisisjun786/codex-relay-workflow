# CRW-1317 — a plan put under the wrong project key ran 41 minutes before its first claim refused it

Source: CRW's own design, not the CXC oracle (CXC v0.2.40, commit 3c1459ac): the oracle has no DAG plan, no flow compile and no coordinator epoch. The Go side is `internal/flow/cli` (`start.go` `projectKeyFact`, `preflight.go` `FactProjectKey`, `schedrelay.go` `target`), `internal/relay/dag` (`epoch.go` `LiveParentScopes`, `PlanProject`), `internal/relay/dagsched/epoch.go` (`ClaimEpoch`) and `internal/flow/compile` (`compile.go`, `input.go` `Target.Branch`, `result.go` `Warning`, `cli.go`). Found by the 10-13 field trial (CRW-1315 items 41 and 26, D9): run-39ba54c04cc5's plan `P-CRW-140@1` was put under the Linear identifier `P-CRW-140` while the orchestrator's parent binding holds the project UUID, compile, plan-put and the preflight passed it, and the first `crw.release` was refused `scope_role_mismatch` after 41 minutes and 11.44M tokens of design loop.

- `crw flow start` never compared the plan's project key with the orchestrator's parent binding (`assignment_routed` counts the thread's live bindings and reads no scope key), so a plan under the wrong key ran until its first claim; port: fixed (before the run process starts, and so before any role call, the start reads the plan header's `project_key` and the scope keys of the owner thread's live parent bindings; a key the thread holds no binding of is the fact `project_key_bound`, `warn`, whose reading names both keys, printed with the preview, named on stderr and recorded in the run's spec as the other preflight facts are; the run starts. A key the thread is bound to prints nothing, and a plan with no revision in the store has no key to compare and prints nothing. Pinned by `TestStartWarnsWhenThePlanKeyIsNotTheThreadsBinding`).
- The claim refusal `scope_role_mismatch` (`ClaimEpoch`) named the plan's project and not the keys the task holds, so the wrong key could not be read off it; port: fixed (the refusal names the plan's project key and the project keys of the live parent bindings the task holds, or says it holds none. Pinned by `TestClaimEpochRefusalNamesBothKeys`, with `TestClaimEpoch` unchanged).
- `docs/relay/dag-plans.md` said a plan belongs to "the Linear project key" and the crw-plan skill did not say which key, so the planner wrote the Linear identifier; port: fixed (both state that the key is the `scope_key` of the project's parent binding, the Linear project's UUID, not its identifier).
- The crw-plan skill told the planner to write the target as OWNER/NAME and refs/heads/BRANCH, while an agent node run refuses a repository that is not an absolute path (`schedrelay.go` `target`) and the integration path adds `refs/heads/` itself (`integration_batch.go` `integrationBranchTip`, `integration_deps.go` `UpdateIntegrationRef`), so such a handoff could not integrate; compile checked only that both were set (item 26); port: fixed (compile warns `target_repository` on a repository that is not an absolute path and reads a `refs/heads/BRANCH` base ref as `BRANCH` with the warning `target_base_ref`; the warnings are printed on stderr and kept in the plan's `warnings`, and neither refuses the handoff. The plan's edges and the agent path's integration request both take the short name (`Target.Branch`), so the edge, the integration request and the observation name the same ref. A base ref that is only `refs/heads/` is refused as a target without a base ref. The skill and the closing check name the run-ready form, and the golden fixture keeps one project in the old form (its two warnings and its normalized edges are in `testdata/flow/compile/initiative.golden.json`) with the three others in the run-ready form. Pinned by `TestCompileTargetFormWarnsAndNormalizes`, `TestCLICompileAndDryRun`, `TestCompileGoldenInitiativeFixture` and `TestSchedRelayTargetIsTheShortBranch`).
- Deviation: a plan compiled before this change carries `refs/heads/BRANCH` in its integrated edges; recompiling its handoff retires those edges and adds them under the short name, which is the form the integration path observes; port: kept (one form of the ref across the plan, the request and the observation).
