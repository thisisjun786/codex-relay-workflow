# CRW-994 — the verdict of a lost policy write, and a response whose body ends mid-way

Source: CRW's own design, not the CXC oracle (CXC v0.2.40, commit 3c1459ac, has no execution policy screen and no policy write route; the pointer is the port). The Go side is `internal/policystore/policy_write.go` (the registration is decided after the file is replaced, on a context detached from the request); the screen side is `web/src/policy-state.ts` (`resolveLostNotice`, `saveHeading`, `noticeForWrite`) and `web/src/api.ts` (`postPolicy`). Both defects were found by the pre-merge evaluation of CRW-135 (`pr868-4bacab0f`, d1 and d2, criterion C5 PARTIAL) and handed to this issue.

- A lost write was judged stored when the freshly read policy's digest merely differed from the digest the change started from. Another tab's write, an `stale_digest` answer that was lost, or a read between the file replacement and the registration (before a failed registration puts the file back) all showed Saved, and the verdict was never judged again (CRW-135 evaluation d1); port: fixed (one function, `judgeLostWrite`, compares the change the request proposed with the file a registered reading returns: the file still at the starting digest is not stored; a moved file that does not hold the change is not stored; a file that holds the change while the wiring record still names another digest is unknown and awaiting its registration; the file holding the change under a record that names it is stored. `resolveLostNotice` runs it on every later registered reading, so a restore moves a Saved or awaiting heading to Not saved, and `lostRecheckDelay` makes the page read again every two seconds for at most 60 readings, the server's two minute decision bound, while a registration is awaited. Pinned by the tests in web/test/policy-state.test.ts from "a digest another write moved is not this change" to "the wait for a registration is bounded", `readingHoldsChange`, and the rendered headings in web/test/policy-screen.test.ts).
- A response whose body ended mid-way (a 200 header, then a reset) was returned as the real status with a null body, and the screen turned it into "Not saved" for a change the server had stored (CRW-135 evaluation d2); port: fixed (`writePolicy` throws when the body cannot be read, as a request that never answered does, and `noticeForWrite` turns a 200 that confirms nothing into the same lost write; `checkPolicy` is unchanged because the check writes nothing. Pinned by the two tests added to web/test/api.test.ts and "a 200 without a stored digest is a lost write that is read again").
- A lost write whose file is still at the starting digest is judged not stored from that reading; a request that was still waiting for the policy lock when the connection dropped may replace the file after that reading. The next reading (the Read the policy again button, or any later load) judges again and moves the heading; the page does not poll for this case; port: kept (the lock wait is bounded at ten seconds and only the awaiting-registration window, which the server detaches from the request, is polled).
- Verification round 1 found two gaps in that judgement; port: fixed. `readingHoldsChange` compared a row's efforts in the order the operator typed them, but the server stores them sorted (`allowedEntry` in internal/policystore/check.go), so a stored change typed in reverse order was judged not stored; both lists are now compared sorted. A read that failed while the registration was awaited cleared the reading and ended the two second re-reading for good; `lostRecheckDelay` no longer requires a reading, and a failed read spends one of the 60 bounded readings (`screenLoadFailed`). Pinned by "efforts typed in reverse order are the change the sorted file holds" and "a failed re-read while a registration is awaited keeps the timer going, within the bound".
