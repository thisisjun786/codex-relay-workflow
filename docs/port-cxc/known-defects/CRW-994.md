# CRW-994 — the verdict of a lost policy write, and a response whose body ends mid-way

Source: CRW's own design, not the CXC oracle (CXC v0.2.40, commit 3c1459ac, has no execution policy screen and no policy write route; the pointer is the port). The Go side is `internal/policystore/policy_write.go` (the registration is decided after the file is replaced, on a context detached from the request); the screen side is `web/src/policy-state.ts` (`resolveLostNotice`, `saveHeading`, `noticeForWrite`) and `web/src/api.ts` (`postPolicy`). Both defects were found by the pre-merge evaluation of CRW-135 (`pr868-4bacab0f`, d1 and d2, criterion C5 PARTIAL) and handed to this issue.

- A lost write was judged stored when the freshly read policy's digest merely differed from the digest the change started from. Another tab's write, an `stale_digest` answer that was lost, or a read between the file replacement and the registration (before a failed registration puts the file back) all showed Saved, and the verdict was never judged again (CRW-135 evaluation d1); port: fixed (one function, `judgeLostWrite`, compares the change the request proposed with the file a registered reading returns: the file still at the starting digest is unknown until the server's bound for a write has passed (see the verification round 2 entry); a moved file that does not hold the change is not stored; a file that holds the change while the wiring record still names another digest is unknown and awaiting its registration; the file holding the change under a record that names it is stored. `resolveLostNotice` runs it on every later registered reading, so a restore moves a Saved or awaiting heading to Not saved, and `lostRecheckDelay` makes the page read again every two seconds while the result is open, within the bounded readings. Pinned by the tests in web/test/policy-state.test.ts from "a digest another write moved is not this change" to "the wait for a registration is bounded", `readingHoldsChange`, and the rendered headings in web/test/policy-screen.test.ts).
- A response whose body ended mid-way (a 200 header, then a reset) was returned as the real status with a null body, and the screen turned it into "Not saved" for a change the server had stored (CRW-135 evaluation d2); port: fixed (`writePolicy` throws when the body cannot be read, as a request that never answered does, and `noticeForWrite` turns a 200 that confirms nothing into the same lost write; `checkPolicy` is unchanged because the check writes nothing. Pinned by the two tests added to web/test/api.test.ts and "a 200 without a stored digest is a lost write that is read again").
- Verification round 1 found two gaps in that judgement; port: fixed. `readingHoldsChange` compared a row's efforts in the order the operator typed them, but the server stores them sorted (`allowedEntry` in internal/policystore/check.go), so a stored change typed in reverse order was judged not stored; both lists are now compared sorted. A read that failed while the registration was awaited cleared the reading and ended the two second re-reading for good; `lostRecheckDelay` no longer requires a reading, and a failed read spends one of the bounded readings (`screenLoadFailed`). Pinned by "efforts typed in reverse order are the change the sorted file holds" and "a failed re-read while a registration is awaited keeps the timer going, within the bound".
- Verification round 2 found two more gaps; port: fixed. One reading at the starting digest was taken as the write's refusal: the heading said Not saved and the page stopped reading, although the request may still be waiting for the policy lock or be past its last cancellation check and about to exchange the file (`swapPolicy` in internal/policystore/policy_write.go), so a late publication and registration were never followed. Now that reading keeps the result unknown and the page keeps reading; the file still at the starting digest is not stored only once the server's bound for a write has passed (`LOST_SETTLE_MS`, 150 s: the header read, the ten second lock wait, the two minute decision phase and a margin; `LOST_RECHECK_LIMIT` = 76 readings at least two seconds apart), or at once when an earlier reading showed the file holding the change (the restore). And a reading that was not registered (unreadable, not registered) judged nothing and spent nothing, so a record that went away while a registration was awaited kept the page reading every two seconds for ever; every reading now spends one of the bounded readings whatever it returned, and the result stays unknown at the bound. A moved file that does not hold the change stays not stored at once: `Write` replaces the file only while it holds the request's `ExpectedDigest`, compared under the policy lock that serializes writes. Pinned by "a lost write re-read that still finds the starting digest stays Result unknown and reads again", "a write that lands after a first reading at the starting digest is followed to Saved", "a file still at the starting digest once the server's bound has passed is Not saved", "the bound covers the server's lock wait and its two minute decision phase", "readings that are not registered spend the bound, and the result stays unknown", and the rendered "the screen keeps a lost write Result unknown when the first re-read finds the starting digest, then follows a late write to Saved".
