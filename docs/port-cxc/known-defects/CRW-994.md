# CRW-994 — the verdict of a lost policy write, and a response whose body ends mid-way

Source: CRW's own design, not the CXC oracle (CXC v0.2.40, commit 3c1459ac, has no execution policy screen and no policy write route; the pointer is the port). The Go side is `internal/policystore/policy_write.go` (the registration is decided after the file is replaced, on a context detached from the request); the screen side is `web/src/policy-state.ts` (`resolveLostNotice`, `saveHeading`, `noticeForWrite`) and `web/src/api.ts` (`postPolicy`). Both defects were found by the pre-merge evaluation of CRW-135 (`pr868-4bacab0f`, d1 and d2, criterion C5 PARTIAL) and handed to this issue.

- A lost write was judged stored when the freshly read policy's digest merely differed from the digest the change started from. Another tab's write, an `stale_digest` answer that was lost, or a read between the file replacement and the registration (before a failed registration puts the file back) all showed Saved, and the verdict was never judged again (CRW-135 evaluation d1); port: fixed (one function, `judgeLostWrite`, compares the change the request proposed with the file a registered reading returns: the file still at the starting digest is unknown, however long the screen has read (see the verification round 2 and pre-merge evaluation entries); a moved file that does not hold the change is not stored when the wiring record names it, and unknown while the record names another digest; a file that holds the change while the wiring record still names another digest is unknown and awaiting its registration; the file holding the change under a record that names it is stored. `resolveLostNotice` runs it on every later registered reading, so a restore moves a Saved or awaiting heading to Not saved, and `lostRecheckDelay` makes the page read again every two seconds while the result is open, within the bounded readings. Pinned by the tests in web/test/policy-state.test.ts from "a digest another write moved is not this change" to "the wait for a registration is bounded", `readingHoldsChange`, and the rendered headings in web/test/policy-screen.test.ts).
- A response whose body ended mid-way (a 200 header, then a reset) was returned as the real status with a null body, and the screen turned it into "Not saved" for a change the server had stored (CRW-135 evaluation d2); port: fixed (`writePolicy` throws when the body cannot be read, as a request that never answered does, and `noticeForWrite` turns a 200 that confirms nothing into the same lost write; `checkPolicy` is unchanged because the check writes nothing. Pinned by the two tests added to web/test/api.test.ts and "a 200 without a stored digest is a lost write that is read again").
- Verification round 1 found two gaps in that judgement; port: fixed. `readingHoldsChange` compared a row's efforts in the order the operator typed them, but the server stores them sorted (`allowedEntry` in internal/policystore/check.go), so a stored change typed in reverse order was judged not stored; both lists are now compared sorted. A read that failed while the registration was awaited cleared the reading and ended the two second re-reading for good; `lostRecheckDelay` no longer requires a reading, and a failed read spends one of the bounded readings (`screenLoadFailed`). Pinned by "efforts typed in reverse order are the change the sorted file holds" and "a failed re-read while a registration is awaited keeps the timer going, within the bound".
- Verification round 2 found two more gaps; port: fixed. One reading at the starting digest was taken as the write's refusal: the heading said Not saved and the page stopped reading, although the request may still be waiting for the policy lock or be past its last cancellation check and about to exchange the file (`swapPolicy` in internal/policystore/policy_write.go), so a late publication and registration were never followed. Now that reading keeps the result unknown and the page keeps reading until `LOST_SETTLE_MS` (150 s: the header read, the ten second lock wait, the two minute decision phase and a margin) has passed, or at once not stored when an earlier reading showed the file holding the change (the restore). And a reading that was not registered (unreadable, not registered) judged nothing and spent nothing, so a record that went away while a registration was awaited kept the page reading every two seconds for ever; every reading now moves the clock whatever it returned, and the result stays unknown at the bound. Pinned by "a lost write re-read that still finds the starting digest stays Result unknown and reads again", "a write that lands after a first reading at the starting digest is followed to Saved", "a file still at the starting digest once the server's bound has passed is Not saved", "the bound covers the server's lock wait and its two minute decision phase", "readings that are not registered spend the bound, and the result stays unknown", and the rendered "the screen keeps a lost write Result unknown when the first re-read finds the starting digest, then follows a late write to Saved".
- The pre-merge evaluation of `711ab36e` (CRW-994 d1, d3; CRW-1001 d2; CRW-876 d1; CRW-914 d1; CRW-876 d2) found that the polling budget was still taken as proof that the request had ended, and that a moved file was judged too early; port: fixed. The bound was a count of readings (`LOST_RECHECK_LIMIT`), so rapid failed Retry reads spent it in seconds, and at the bound a file still at the starting digest became "Not saved" although the request can be inside the file exchange (`swapPolicy` checks the context once and the exchange has no deadline) and the server's two minute phase starts only after the exchange returns. The bound is now elapsed time since the answer was lost (`LostWrite.startedAt`, `LOST_SETTLE_MS`): inside it any number of readings keeps the screen reading; at it the screen stops reading and the result stays "Result unknown", with a sentence that says the screen cannot tell whether the request has ended and asks for a re-read. Not stored is reached only on evidence: the file put back after it was seen holding the change, or a moved file without the change whose bytes the wiring record names (another write finished; the server publishes only over `ExpectedDigest`). A moved file without the change under a record that names another digest may be another writer's provisional publication whose failed registration restores the starting bytes and lets this request publish, so it stays unknown and watched (CRW-1001 d2, CRW-876 d1). The page's effect is `startLostRecheck`, which the tests drive with a fake timer; an explicit "Read the policy again" drops the notice before the read (`screenReread`), so the later reading is shown as the file and is not judged against the lost write. Pinned by "a file still at the starting digest at the bound stays Result unknown, however many readings were spent", "a failed re-read while a registration is awaited keeps the timer going until the wait has run out", "the wait for a registration is bounded by time, and the result stays unknown at the bound", "a moved file without the change whose record names another digest stays unknown and is followed to Saved", "a moved file without the change settles Not saved only when the record names that file", "the page's recheck schedules one read per delay and cancels it with the effect", "the page follows a lost write across waits to the verdict, and stops at the bound without one", "an explicit re-read drops the lost write: no later reading is judged against it and no timer runs" and "Retry after a failed read keeps the lost write and its timer".
- The same evaluation found that a cancelled answer reported the digest of the bytes read under the lock as the file it left (CRW-994 d2, CRW-1001 d1, CRW-876 d3); port: fixed (see CRW-1001: the digest is read when the write ends, and the screen words it as what the file had then).
