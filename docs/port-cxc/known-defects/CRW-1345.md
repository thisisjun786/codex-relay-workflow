# CRW-1345 — the relay's issue identifiers and texts name the tracking record, not Linear

Source: CRW's own design (the GitHub transition, CRW 1.0 GitHub 전환), not the CXC oracle: CXC v0.2.40 (commit 3c1459ac) names Linear throughout its relay and has no tracking interface. The Go side is `internal/relay/routing/products.go` (`isIssueIdentifier`, `issueTeam`), `internal/relay/faults/notice_facts.go` (`isNoticeLink`), the texts of `internal/relay/supervisor` (`packet.go`, `notice_compose.go`, `proposal.go`, `selection.go`, `show.go`, `stage.go`), `internal/relay/reception` (`packet.go`, `ladder.go`), `internal/relay/registry/linkage.go`, `internal/relay/delivery/report_render.go` and the help of `internal/relay/argparse/specs.json`; the tracking ref is read by `internal/tracking.ParseRef`.

- The oracle's product routing took an issue identifier (a binding's `ref`, a follow-up's `issue`, a run's `currentIssue`, a completion reading's `subject`) only as a Linear key like `ABC-12`, so a scope keyed by a tracking ref `<owner>/<name>#N` could not be bound or completed; port: fixed (the identifier is a Linear key or a tracking ref `internal/tracking.ParseRef` reads, and nothing else; the refusal names both forms; the team of a test issue, which a test target pins, is a Linear key's prefix or a tracking ref's repository. `TestIssueIdentifierIsALinearKeyOrATrackingRef`, `TestIssueIdentifierFieldsTakeATrackingRef` and `TestTestBindingTeamOfATrackingRefIsItsRepository`, red first). Registry bindings, relationships and links take any key without `|` and needed no change; `TestTrackingRefScopeRunsThroughRegistryRoutingReceptionAndSupervisor` runs a scope keyed by `o/r#7` (milestone `o/r#3`, repository `o/r`) over a temporary store through registry binding and registration, routing's bind and completion check, reception's read of the relationship and the supervisor channel's walk to the milestone's supervisor, with no Linear identifier anywhere.
- The oracle's fault notice named the published issue by a link only when it was a Linear URL; port: fixed (`faults.notice_facts` also carries `https://github.com/<owner>/<name>/issues/<N>`, N from 1 to 999999999, owner and name not `.` or `..`; `TestNoticeFactsExternalRefLink`, red first). The ledger reads the URL itself and does not call `ParseRef`: `internal/relay/faults` must not depend on a network client package (`TestFaultsDependencyInventoryContainsNoNetworkClient`) and `internal/tracking` carries the GitHub client.
- The relay's comments, refusals and report texts that are not about a Linear behaviour named Linear (the record that discharges a report, the level a task is bound to, the scope a report names, the store seat's level, the project and scope flags' help); port: fixed (they say the tracking record, the tracking level and the tracking scope; the notes about the Linear summary outbox keep Linear: the document save, the blank line its save adds (CRW-513), the document id or URL, the connector's missing idempotency key). The change of the texts has no red-first log (the goldens that carry them were refreshed after the change, `CRW_GOLDEN=update`, and each refreshed file was compared with the old one under the text mapping: 16 files keep the old text because a fixture stores it and 6 gain a `supervisor_message_restated` journal row, see the next line).
- A message staged before this change and not yet sent carries the old text in its stored packet; port: kept (the design re-derives a staged row's content when its claim starts the transport, so such a message is restated, journalled `supervisor_message_restated`, and goes out with the new text; a message already sent keeps its text; no stored row is rewritten and no migration is needed).
- Stored and wire names that still say Linear are not renamed and get no migration: the progression stages `linear_done` and the source `linear_issue_status` (`reception/activation.go:63-64`, `ladder.go:15,28,135`) and the completion claim `linearDone` (`routing/completion.go:15,121`, `completion_record.go:104`; part of `completion-reading/1` and of the signatures a reading is recorded under); port: kept. Renaming would take an additive alias (`trackingDone` accepted beside `linearDone`, the stage and the source emitted under both names for one release) and a refresh of the goldens and skill text that name them. The schema's Linear comments (`store/relay-sqlite.sql:568,1129,1457,1468,1545` and the copy under `contract/schema/`) are comments of the schema text the contract copy mirrors and are left.
- `faults.IsNoticeIssue` and the notice facts' `issueKey` accept a Linear key or a UUID only, so a fault whose issue is a tracking ref names no issue in its notice (the field stays absent, nothing is refused); port: kept (not part of this issue's decided scope; one line in `noticeIssue` and its tests would take a tracking ref).
- `internal/relay/routing` now imports `internal/tracking` for `ParseRef`, which puts the GitHub client (`net/http`) in routing's dependency closure although the relay makes no tracker call; port: kept (the issue asks to reuse the one parser). A dependency-free leaf package for `Ref` and `ParseRef`, re-exported by `internal/tracking`, would keep the relay free of the client, as `faults` is.

The rest of the item stays: the ledger must not depend on a network client package, and `internal/tracking`, which carries the GitHub client, is still not imported by it.
