# CRW-987 — install migrate: a retry after a moved root, the Linux unsupported refusal, the macOS record, and receipt whitespace

Source: the CRW state-copy design in docs/port-cxc/state-migration.md (the sections that CRW-887 and CRW-879 cite) and the Go code of internal/runtime/install/migrate: roots.go (Pair.EnsureDest, the Claim step), publish_linux.go (ownedDirIdentityFchmod), and apply.go (migrateReviewFollowupDecodeManifest, migrateReviewFollowupPeekValue). The defects come from the pre-merge evaluations of CRW-887 (pr840-7f91398f, d1 to d3) and of CRW-879 (pr848-68e0f108, d1); this file cites them by name only.

- A same-pair retry whose first two parent syncs failed pinned the reopened root before its sync succeeded. When another actor then moved that root aside and put a 0700 directory at its name, the retry wrote the files into the displaced directory, set its mode, and reported success with no kept-mode note (roots.go, Pair.EnsureDest; CRW-887 pr840-7f91398f d1); port: fixed (the pin is taken only after the parent sync succeeds, every cached use compares the directory at the name with the pin, and a replacement is adopted as an existing root this run did not make, with its mode kept and reported). Cases: TestMigrateFollowupSecondSyncFailureDoesNotPinTheRoot and TestMigrateFollowupSecondSyncRetryFinishesTheRootWithoutAReplacement.
- On Linux, when neither fchmodat2 nor chmod through /proc/self/fd can change a directory's mode, the run failed with the /proc errno, so the report read a generic failure with no reason (publish_linux.go and roots.go, Claim; CRW-887 pr840-7f91398f d2); port: fixed (the answers that mean a mechanism is absent are classified as unsupported, and the run is refused with reason unsupported naming both mechanisms; any other answer stays an ordinary failure with its errno). Cases: TestMigrateFollowupNoChmodMechanismIsRefusedAsUnsupported, TestMigrateFollowupMissingFchmodat2UsesAUsableProcPath, and TestMigrateFollowupGenuineChmodFailureKeepsItsErrno.
- The defect record CRW-887.md said the by-name chmod is no longer reachable on macOS, but the code takes it when the O_SEARCH open answers EACCES or EPERM, which a hostile umask can cause (CRW-887 pr840-7f91398f d3); port: fixed (the record states the open's success condition, the fallback, and its replacement window; the code is unchanged because the fallback is a supported path). Cases: TestMigrateFollowupDefectRecordDoesNotCallTheFallbackUnreachable and TestMigrateFollowupDeniedPinTakesTheByNameFallback.
- The receipt reader looked at the first byte of a path or kind value only within its 64 KiB window. A longer whitespace run made it decode the whole value with json.RawMessage, so a container of any size under either key was held in memory, and the cost grew with the container (apply.go, migrateReviewFollowupPeekValue; CRW-879 pr848-68e0f108 d1, the CRW-999 follow-up); port: fixed (the first non-space byte is found by reading past the whitespace one byte at a time and handing back the bytes the decoder still needs, and containers are skipped with the token API). Cases: TestMigrateFollowupLongWhitespaceBeforeAPathArrayIsNotHeld, TestMigrateFollowupLongWhitespaceBeforeAKindObjectIsNotHeld, and TestMigrateFollowupWhitespaceBoundaryKeepsThePath.
- The DecodeManifest comment said an invalid UTF-8 path produces no key. The code normalises the path with source.DecodeUTF8, the reader's own normalisation of its whole input, and keeps the normalised text (apply.go, migrateReviewFollowupDecodeManifest); port: fixed (the comment now states what the code does).
- CRW-879.md said the container-under-field case was fixed, while a whitespace run before the value still decoded it whole (CRW-879.md, the item beginning "A path or kind value that was a container"); port: fixed (the item now states what the fix covers and names the cases that pin the whitespace path; the defect itself is the receipt reader item above).
- The pre-merge evaluation of 9e0219c0d found that a root another directory replaced after the pin was adopted through its marker mode: the pin moved to the replacement but the run still treated it as its own lookup result, so finishModes chmodded it to the source mode with no kept-mode note (roots.go, Pair.replaced; apply.go ensureRoots); port: fixed (a pair records that its name has been replaced, and the ownership record then treats that directory as one this run did not make, as it does a root absent when pinned). Case: TestMigrateFollowupReplacedExistingRootIsNotAdopted.
- The same evaluation found that the .gitignore judgement of a project root used the presence recorded on the directory the run had pinned, so an owner's .gitignore in the replacement was refused as differing (publish.go, EnsureProjectRoot); port: fixed (the presence is read on the directory the run publishes into whenever the pin has moved). Case: TestMigrateFollowupReplacedProjectRootKeepsItsOwnGitignore.
- The same evaluation found that the /proc descriptor path ran after any fchmodat2 error, so a genuine EPERM, EIO or EROFS from fchmodat2 was hidden when /proc succeeded (publish_linux.go); port: fixed (the /proc path runs only where fchmodat2 is absent, ENOSYS or EOPNOTSUPP, and any other fchmodat2 answer is returned with its errno). Case: TestMigrateFollowupGenuineFchmodat2FailureIsNotHiddenByProc.
- The independent review of the final head (P2, the residual in roots.go EnsureDest): if this run created root X, a racer moves X aside and puts Y at the name, so the pair re-pins Y and marks the name replaced; then a racer removes Y and moves X back, and the replacement branch re-pins X and reports made false. X, this run's own directory, keeps the marker mode and gets a kept-mode note instead of being finished to the source mode. Nothing unsafe follows: no foreign chmod happens, the note is true, copying into X is correct, and a fresh run finishes it through marker adoption; port: kept (carried to the low-priority sweep; no code change in this issue).
