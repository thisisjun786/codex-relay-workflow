# CRW-1026 — verification records that carry no pins, and the integrated nodes a push does not name

Source: CRW's own design, not the CXC oracle (CXC v0.2.40, commit 3c1459ac, has no commit-based acceptance path, no verification record and no integration branch; the pointer is the port). The Go side is `internal/relay/dagsched/verification_record.go` and `verification_pins.go` (the record judge and the declared pins), `integration_push.go` and `integration_stale.go` (the push and the stale-node list), and `internal/relay/integrate/cli.go` (the printed document). Both defects were found by the pre-merge evaluation of CRW-965 (`pr886-7c77e55e`, d1 and d2) and handed to this issue; d3 (the bisection retry) is not in this record.

- The record judge compared a record's tool values only with the record's own pins, so a record with empty pins, or with pins that agreed with its tools and not with the tree, was reusable although the toolchain it names is not the one the verified commit declares (CRW-965 evaluation d1); port: fixed (a record must carry the pins member, not null, and for every tool the verified commit declares through go.mod, the staticcheck require, scripts/ci/secrets.sh and, when its ci.yml has a setup-node step, node, the pin and the tool value must both equal that declaration; a missing or different one is `disposition_conflict` naming the tool, and the PATH of the host is never read; a record of a tree whose ci.yml has no setup-node needs no node pin; `runtime-upgrade`, which holds a tree id and no checkout, reads the same files of the release commit from the forge and judges the record against them, and refuses when a declaration cannot be read; a setup-node step is read whole, with `with:` before or after `uses:`, and one whose node-version cannot be read is refused; go.mod is read in every require form the go command accepts (single-line, block, `// indirect`, CRLF, quoted path) and an unreadable declaration refuses rather than drops the pin; ci.yml is read by its block structure, so a quoted `uses` is a setup-node step and the `with` of another step or job never stands in for a missing `node-version`. Pinned by verification_pins_test.go and the pins cases of upgrade_verification_test.go).
- `dag-integrate-push` pushed a head that held integrated nodes whose acceptance criteria had changed since, and said nothing: a node that already integrated is never a candidate again, so no batch verifies it, and the push read only the old `ref_moved` record (CRW-965 evaluation d2); port: fixed as a notice, not as a gate (the printed document gains `stale_nodes`, read through `integratedAcceptanceStale`, which asks of each integrated acceptance of the pushed head, across earlier batches, read from each durable move's merged list (a reconciled move's verified covered candidates) as well as from the marks, so a merge whose mark stayed pending, or that a batch stopped before marking, is included, whether the plan still has the node, whether the acceptance is still the node's active one, and whether the criteria set it stands on, revalidations included, is the plan's; the candidate predicate is not used. The push stays a fast-forward, the list never blocks it and writes nothing, and a list that cannot be read is named in `stale_nodes_error`. Deviation kept on purpose: a stale node is reported, not refused, because the head was verified and the criteria change is the parent's to re-rule. Pinned by integration_stale_test.go and push_output_test.go).
