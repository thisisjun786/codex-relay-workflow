# CRW-1141 — the config.toml editor reads TOML semantically

Source: CXC v0.2.40, commit 3c1459ac — `plugins/codexclaw/components/config-guard/src/toml-edit.ts` (`findTableHeader` :53, `findKeyLine` :154, the table-end scan :159, `readTableKey` :292), `config-set.ts` (:90-136) and `multi-agent-v2.ts` (:55-80). The Go port is `internal/runtime/install/configguard/toml.go` (the oracle grammar, now the replayed reference only), the new semantic boundary `internal/tomledit` (`Get`, `Set`, `Restore`, `Decode`, the scanner in `scan.go`), and its users in `configguard/semantic.go`, `activate.go`, `configset.go`, `deactivate.go` and `multiagentv2.go`. The finding is the 10-10 CXC improvement review A7-02 and the combined review B7-01.

- The writers found only a bare `[table]` header and a bare key, so `crw install features enable` on a table written `["memories"]` or `[ memories ]`, on a quoted key or on a root dotted key appended a second table or key line, and a line starting with `[` inside a multi-line array ended the table; the published config.toml did not decode and every full reader of it (`internal/runtime/install/mcp.go`, `internal/runtime/doctor/registration.go`, Codex itself) saw it as unreadable (source `toml-edit.ts:53,154,159`); port: fixed (the activation, config set/unset and the deactivation read and edit the managed key through `internal/tomledit`: the whole document is decoded with BurntSushi/toml, the key is found by its semantic path whatever the header or key spelling, a scanner that reads strings, arrays and inline tables whole locates the bytes, and the edit changes only that value, that line, or one appended line or table. Every candidate must decode, hold the value asked for, and decode to the original once the key is taken out of both, or nothing is written. Pinned by `TestFeaturesAndConfigCommandsKeepEveryTomlFormValid` in `internal/runtime/install`, which runs the real enable, config set, set, unset and disable over a quoted header, a spaced header, a quoted key, a root dotted key, a multi-line nested array, a header inside a string, an inline v2 table and mixed line endings, and by the `internal/tomledit` tests).
- A config.toml that did not decode was edited anyway, and the published candidate was never checked (source `config-set.ts:102`, `activate.ts:278`); port: fixed (the activation refuses before the backup and before any `codex features enable`; config set/unset, `config list`/`get`, the deactivation and the multi-agent switch refuse before writing; the multi-agent tuning repair is not published when it would not decode. Pinned by `TestFeaturesManagedKeyRoundTrips/"oops`, `TestConfigSetNoopOwnershipAndUnsupportedValues`, `TestMultiAgentV2RepairBoundaries/opener-eof` and `TestConfigGetShowsAFormItDoesNotEditAsSet`).
- Supersedes known-defects.md, section "Found by the config-guard TOML editor port", item beginning "The editor recognises only a bare `[table]` header": now port: fixed for every writer (see the first item; `SetTableKey` in toml.go keeps the oracle grammar as the reference `testdata/oracle-toml-edit.json` replays, and no writer calls it).
- Supersedes known-defects.md, section "Found by the config-guard TOML editor port", item beginning "The scan is line based and has no notion of an array": now port: fixed for every writer (the scanner reads an array whole).
- Supersedes known-defects.md, section "Found by the config-guard TOML editor port", item beginning "Any edit that changes the file rewrites all of it with the dominant line ending": now port: fixed for every writer (an edit splices bytes; an inserted line takes the line ending of the line it follows, and a new table the file's dominant one. Pinned by the mixed-ending case of `TestFeaturesAndConfigCommandsKeepEveryTomlFormValid` and `TestSetMinimalEdits`).
- Supersedes known-defects.md, section "Found by the config-guard TOML editor port", item beginning "`readTableKey` answers null both for an absent key": now port: fixed for every reader in this package (`tomledit.Get` answers absent, found, unsupported or invalid; `config list`/`get` show a key in a form crw does not edit as such, the activation and config set leave it alone, and the deactivation reports it as changed rather than missing. Pinned by `TestDeactivateDriftScenarios/unsupported_reads_as_changed` and `TestConfigGetShowsAFormItDoesNotEditAsSet`).
- Supersedes known-defects.md, section "CRW-531 — multi_agent_v2 settings library", item beginning "Inline detection matches `not_enabled = true`": now port: fixed (the v2 detection reads the decoded document: `[features] multi_agent_v2 = <bool>`, or the table or inline table with `enabled = <bool>`. Pinned by `TestMultiAgentV2SemanticReader`).
- Supersedes known-defects.md, section "CRW-531 — multi_agent_v2 settings library", item beginning "Read-only detection treats headers and enabled-like lines inside multiline strings as configuration": now port: fixed (same reader; a table and a scalar of one name do not decode, so neither shadows the other; pinned by `TestMultiAgentV2SemanticReader`).
- A document the decoder rejects reads as v1 in the multi-agent state, as a missing or unreadable file always did (source `multi-agent-v2.ts:46-53`); port: kept (the state is read-only; the switch itself refuses such a file).
- The multi_agent_v2 tuning (the keys of `[features.multi_agent_v2]` other than `enabled`) was put back after the CLI replaced the table by a bare-header regex, so a quoted or spaced header lost it silently; port: fixed (the tuning is read from the decoded document, located with `tomledit.Statements` so a header, an `enabled` line or a comment inside a string or array is not mistaken for one, and written back as it was, with its comments and multi-line values, in a `[features.multi_agent_v2]` table after the scalar the CLI wrote is removed. The candidate must decode, hold the flag and the tuning, and equal the runner's document otherwise. Tuning written as an inline table, as dotted keys or with sub-tables is refused before the runner runs, because the CLI would drop it and it cannot be put back exactly. Pinned by `TestMultiAgentV2TuningRestoredFromEveryTableSpelling` and `TestMultiAgentV2TuningInAFormCrwCannotRestoreIsRefusedBeforeTheRunner`; `PreserveMultiAgentV2Table` keeps the oracle grammar as the replayed reference only).
- A `[features.multi_agent_v2]` table with tuning but no `enabled` key, which the reader accepts, failed the repair check after the runner because the restored table gains `enabled` and the check compared key counts with it; the command failed with the runner's scalar in place and the tuning gone; port: fixed (the check compares the tuning keys and their values without `enabled`, and checks `enabled` separately against the requested value. Pinned by `TestV2TuningWithoutEnabledIsRestored`).
