# CRW-765 — an interpreter's program fed by a here-document

Source: `plugins/codexclaw/components/pabcd-state/src/shell-write-destinations.ts` at v0.2.40 (commit 3c1459ac) —
`shellWriteDestinations` :25-46 and `stripHeredocBodies` :57-100; the port in `internal/pabcd/hook/shellwrite.go`
(`ShellWriteDestinations`, `shellWriteDestinationsIn`, `shellWriteHeredocs`, `shellWriteHeredocDelimiter`) and
`internal/pabcd/hook/shellwrite_verbs.go` (`shellWriteHeredocKindOf`, `shellWriteHeredocProgramWrites`,
`shellWriteHeredocUnreadable`) and `internal/pabcd/hook/memorygate.go` (the shell branch of `memoryGateClassify`).

- `stripHeredocBodies` removes every here-document body before the reader runs, so a program an interpreter reads from
  standard input is deleted too: `python3 - <<'EOF'` / `open('<m>/a','w')` / `EOF` names no destination and the memory
  gate allows the write (the oracle is the same, and its intent was only that a body quoting the memories path is not a
  write); port: fixed (a security fix under the parity rule revision of 2026-10-03: before the bodies are stripped the
  reader recognises a here-document that feeds an interpreter reading its program from standard input and reads a
  quoted-delimiter body with that language's reader — Python through CRW-741/CRW-754's walk, node through the Node
  reader, a shell through `ShellWriteDestinations` at depth 8 — while an unquoted body the outer shell would expand,
  one holding `$` or a backtick, fails closed through `shellWriteHeredocUnreadable`; no recorded corpus fixture drives
  this, so none is tagged intentionally-changed).
- Accepted over-blocking of this fix: while the gate is on, an interpreter program in an unquoted here-document whose
  body holds `$` or a backtick is denied without a grant, because the outer shell expands the body and this reader is
  lexical; and a program nested deeper than 8 here-documents is denied as unreadable rather than read; port: fixed.
- Accepted false positive of this fix: a shell here-document body read as program text goes through
  `ShellWriteDestinations`, whose literal-redirect pass reports a `>` inside a quoted string of the body as a
  destination (the same conservative posture the literal pass already has for a top-level command); port: fixed.
- A shell here-document read as program text is not followed when the shell parses without running (`-n`, `-o noexec`),
  so a syntax check whose body names a protected path is not denied; a body read one level past the depth limit, and a
  program the nested `-c`/`eval` tokenizer cannot re-parse (a quote-bearing program its own escaping breaks), are
  refused or left unread rather than guessed; port: fixed.
- The deletion guard's matching gap (a shell reading its program from a here-document, worktreedel.go) is out of this
  issue's scope and was reported to the operator by the issue body; port: pending.
- A here-string (python3 - <<<'open(...)') or a pipe (echo open | python3 -) that feeds an interpreter its program
  is still not read, so a protected write in that program is not named; this issue covers the here-document form only
  and the here-string and pipe forms are taken by the CRW-851 item (4) (the shell reading its program from a pipe or a
  here-string); port: pending.
- The reader decides by a closed rule (CRW-765 corrections 3 and 4), not by extending the header parser shape by shape:
  a here-document's physical header line must first be proven to be exactly one simple command the way the shell reads it
  - no backslash anywhere on the line, no backslash ending the physical line before it, no `;`, `&`, `|`, `&&` or `||`
  outside quotes, and no function definition in any form (`name()`, `function name`, `function name()`) - and that
  command must be proven to be an interpreter that reads standard input; it is data (today oracle behaviour) only when
  the command is proven to be a non-interpreter; and otherwise fails closed when the canonical text (every quote
  character and every backslash deleted, the ASCII letters lowered) outside the here-document bodies names an
  interpreter anywhere. A `<<` inside a `$( ... )` or backtick substitution that a double-quoted word encloses is a
  here-document the collector cannot reach, so a command holding one fails closed when it names an interpreter; port:
  fixed.
- Rows whose expectation correction 4 changes (the closed rule supersedes the generation-2 shape rows; each is now
  denied as unreadable rather than read): `bash <<'EOF' | cat` and `python3 - <<'EOF' 2>&1 | tee x.log`, whose header line
  carries a pipe so the owning command is unproven; and `python3 <<\EOF`, whose header line carries a backslash; port:
  fixed.
- Over-blocking correction 4 adds and accepts: a here-document whose header line carries a backslash, a control
  operator, a second command or a function definition is denied when the command text names an interpreter anywhere,
  even where the shell would have run a non-interpreter; port: fixed.
- The reader decides by an allow list (CRW-765 correction 5, rules R0 to R2), because proving a command is *not* an
  interpreter let a name bound to one through: `eval bash <<'EOF'`, `hash -p /bin/bash b` then `b <<'EOF'`, `hash
  b=/bin/bash` then `b <<'EOF'`, `ln -sf /bin/bash X` then `X <<'EOF'` and `alias b=bash` then `b <<'EOF'` all run the
  body. R0: the verb of the owning command must be literal after its quotes and backslashes are removed, and a verb that
  still holds an expansion (a variable, `$()`, a backtick or a glob) is refused whatever the rest of the command says.
  R1: a here-document is data unconditionally only when its verb (last path element, case-insensitive) is one of cat,
  tee, head, tail, wc, grep, egrep, fgrep, sort, uniq, cut, tr, jq, base64 or read. R2: every other verb keeps the
  here-document as data only when the canonical text of the whole command outside the here-document bodies names no
  interpreter, and is denied when that text holds a name-binding construct (eval, source, `.`, alias, hash, ln, exec,
  enable, a function definition or an assignment to PATH) even with no interpreter named; port: fixed.
- Rule R1's `while`/`until read` loop form is read by the reserved-word path rather than as unconditional data: such a
  loop's here-document is data when the loop text names no interpreter and binds no name, and is denied when it does, so
  `while read l; do eval "$l"; done <<'EOF'` is denied instead of read as data; port: fixed.
- Over-blocking correction 5 adds and accepts: an unmodelled verb whose command text names an interpreter anywhere (a
  quoted word naming one included), and a command text holding a name-binding construct, are denied even where the shell
  would have read the body as data; and a verb that still holds an expansion is denied even when the command names no
  interpreter; port: fixed.
- Known limit of correction 5, a follow-up candidate of the file-identity kind (the same class as the script-file
  reader follow-up CRW-875): a link, a function, an alias or a PATH entry that an earlier, separate command (another
  tool call) set up cannot be seen by a reader that reads one command text, so `ln -sf /bin/bash X` in one call and
  `X <<'EOF'` in the next still reads the body as data; closing it needs the file identity behind the name, not its
  spelling; port: pending.
- Correction 6 (rules H1 and H2) closes the last shape of the same gap, which the earlier rule kept by design: an
  interpreter that runs an inline or script program of its own still reads the here-document, so `bash -c 'bash'
  <<'EOF'`, `sh -c 'exec sh' <<'EOF'`, `python3 -m code <<'EOF'`, a `node -e` program that evaluates its standard input
  and `awk -f /dev/stdin <<'EOF'` all ran the body while the reader kept it as data. H1 makes a here-document attached to
  a modelled interpreter verb (python, python3, pythonX.Y, node, nodejs, sh, bash, dash, ash, zsh, ksh, mksh; last path
  element, case-insensitive) always that interpreter's program, whatever its flags (`-c`, `-e`, `-m`, `-i`, `-n`, `-s`
  and the rest), operands (a script file included) or environment, with the write reading applied to the body. H2 makes
  a here-document attached to an interpreter whose language this reader does not model (awk, gawk, mawk, nawk, sed in
  its `-f` form, perl, ruby, php, lua, Rscript, tclsh, osascript) unreadable, so the gate refuses it; rule R1's data
  list stays data. R0 to R2 and G1 to G4 are kept; port: fixed.
- Accepted over-blocking correction 6 adds and the parent accepted: a data body fed to a script that reads like a
  writing program is denied, `node script.js <<'EOF'` whose body holds a write statement and `python3 script.py <<'EOF'`
  whose body holds an `open` included; the same holds for a syntax check (`bash -n <<'EOF'`), because the here-document
  belongs to the interpreter whatever the flag does; port: fixed.
- Rows whose expectation correction 6 changes (each was allowed before it and is denied now; the pull request body lists
  them): `python3 -c 'print(1)' <<'EOF'`, `python3 -m json.tool <<'EOF'`, `node -e 'console.log(1)' <<'EOF'`,
  `bash -c 'echo hi' <<'EOF'`, `bash -n <<'EOF'` (with `-o noexec` and the `-ne` bundle), `python3 script.py <<'EOF'`
  and `node script.js <<'EOF'` with a write statement in the body, `python3 -Z script.py <<'EOF'` and `bash --norc
  script.sh <<'EOF'`; port: fixed.
- The base refresh merged the deletion guard's own here-document rule (CRW-726) into this branch. It claims only a
  here-document a listed shell reads as its program, so the two rules overlap exactly there: `memorygate.go` runs the
  guard's check first, which keeps CRW-726's own reason for that case, and this reader answers for every other
  interpreter's here-document; port: fixed.
- Correction 7 replaces the deny list with one closed rule over the verb a here-document is attached to, because a list
  of names is only as good as the names on it: the sed option bundle (`sed -nf -`, `sed -Ef - x.txt`), `ed -s /dev/null`,
  `sqlite3` and `make -f -` all ran the body while the reader kept it as data. C1 makes the data verbs (rule R1's list,
  and a `git commit` that reads its message from standard input: `-F -`, `--file=-`, `--file -`) data as before; C2
  keeps the modelled interpreters (the python, node and sh families) read as that interpreter's program; C3 denies every
  other verb as an unreadable here-document program, so ed, ex, sqlite3, make, awk, perl and any verb never seen fall
  under that one rule. The sed exception reads its options letter by letter through every bundle, so `-nf`, `-Ef` and an
  attached `-f-` are all seen, and a bundle holding `f`, or a `--file` / `--file=` option, denies; without one its
  here-document is input data. R0, G1 to G4 and H1 are kept; port: fixed.
- Rows whose expectation correction 7 changes (each was allowed before it and is denied now; the pull request body lists
  them): the generation-6 control `mytool --input - <<'EOF'`, which is the unseen-verb row C3 now refuses, and the
  generation-6 rule-H2 rows for awk, gawk, mawk, nawk, perl, ruby, php, lua, Rscript, tclsh and osascript, which C3
  refuses under one rule instead of a name list; port: fixed.
- Accepted over-blocking correction 7 adds and the parent accepted: a verb outside C1 and C2 is denied even when the
  reader has never seen it and even when its here-document would have been input data, because the reader cannot rule
  out that the verb is an interpreter; a `git` invocation that is not `commit -F`-style is denied with it; port: fixed.
- Correction 8 closes the two ways a here-document still passed as data although a real shell runs it. The first is the
  unproven header: a line holding a control operator, a backslash or a reserved word went to Unknown, and Unknown denied
  only when the command text named an interpreter or bound a name, so `echo start; perl <<'EOF'`, `true | perl <<'EOF'`,
  `cd /tmp && mytool <<'EOF'`, `true; ed -s`, `true; sqlite3` and `sed -\f - <<'EOF'` passed while C3 held only behind a
  proven header. The second is a sed option the reader did not read the way the shell builds it: `sed -n$F -`,
  `sed -n$(printf f) -` and GNU sed's long-option prefixes `--fil` and `--fi=-`. Rules U1 to U3 and S8 close both: U1
  splits the here-document's line into commands at `;`, `&&`, `||`, `&` and `|` with the same quote-aware tokenizer and
  classifies the command that carries the operator by its own words under C1, C2 and C3; U2 lets a `while` or `until`
  loop that takes the here-document pass only when every command in its condition and body is a data verb (C1), `read`,
  or one of `echo`, `printf`, `true`, `false`, `:`, `test`, `[`, `break`, `continue`, with every word readable; U3
  denies everything the reader cannot take apart and drops the interpreter-name test as an allow condition; and S8
  reads sed's option words after the CRW-783 normalisation (quotes and backslashes removed), denies an expansion left in
  one, reads a short bundle letter by letter, reads a long option by its GNU getopt prefix, and reads nothing after `--`
  as an option. C1, C2, R0, G1 to G4 and H1 are kept; port: fixed.
- Rows whose expectation correction 8 changes (each was denied or allowed differently before it; the pull request body

- Correction 9 reuses the judgements the reader already has instead of adding another header shape, because the blind
  pre-merge evaluation found three protected-write bypasses and two regressions inside this issue's own promise. K1: the
  declaration collector now reads the same text the command reader does, so a word-initial `#` ends the physical line and
  a `<<` written inside a comment is no declaration - `cat <<'DATA' # <<'HIDDEN'` no longer swallows the `python3 <<'PY'`
  body that follows it. K2: an unquoted body is read as the shell delivers it before the interpreter reads it - `\\`, `\$`,

  body is refused the way a top-level one is; the depth limit is unchanged. K4: `<<<` is a here-string token and never a
  here-document, as the CRW-726 collector reads it, so `cat <<<hello` and `jq . <<<'{}'` need no grant. K5: the hidden

  example inside a quoted body (`cat > note.md <<'DOC'` holding `x="$(cat <<'INNER' ...)"`) is no longer read as a

- Correction 9, second pass: the blind pre-merge evaluation of head a742344da found two more protected-write bypasses
  inside this issue's own promise and one regression this change had introduced, all closed by making the collector and
  the hidden-operator scan read the text the shell reads. The collector now consumes a plain-state backslash with the
  character it escapes, so an escaped quote is a literal character and opens no quoted span: `echo \' <<'DATA'` used to
  swallow both real `<<` operators inside a bogus span, and the interpreter program that followed was never collected
  or read. The body reader now joins a backslash-newline before it matches the terminator, and only when the delimiter
  is unquoted, as the shell does: a terminator written `E\<newline>OF` closes the here-document in the shell, so the
  collector must not absorb the interpreter program that follows into a data body. The hidden-operator scan now blanks
  every here-document body, not only the ones judged data, so a `$( ... << ... )` inside a Node or Python program string
  is no longer misread as a shell command substitution the collector could not reach - `node <<'EOF'` holding
  `console.log("$(cat <<INNER)")` is allowed again, while a shell body keeps its own recursive judgement; port: fixed.
- Accepted over-blocking this second pass keeps: an unquoted here-document body that holds an expansion is still denied
