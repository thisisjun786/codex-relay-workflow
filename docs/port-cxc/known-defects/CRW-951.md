# CRW-951 — pathlib touch() and mkdir() are not read as writes by the shared shell reader

Source: the port's own shell write reader, not an oracle behaviour. The defect is in `internal/pabcd/hook`
(`shellIRWriteNames` / `shellIRPyUnattributedCall` in `shellwrite_structural.go` and `shellVerbWriteMethod` in
`shellwrite_verbs.go`). The rows that hold it are `testdata/shellir/rows/20-crw-951-touch-mkdir.txt`, run by
`TestReproductionRows` through the memory write gate, the GitHub post guard and the worktree guard.

## 2026-10-09: pathlib touch() and mkdir() (re-check RC-951, approved by Jun as mgmt-approved-20261009-0651-951-851)

- `Path(root).joinpath('a').touch()` and `Path(root).joinpath('a').mkdir()` with `root` inside the protected memories root:
  the memory gate judged them `none` and consumed no grant, while python3 really creates the file and the directory; port:
  fixed (touch and mkdir are read like write_text: a receiver that is a `Path(...)` call names its destination, any other
  receiver is an unknown destination when the program has a protected reference; see E4 below).
- A literal `Path(m).touch()` and `Path(m).mkdir()` with `m` inside the memories root, and `Path("<memories>/a").touch()`:
  the same bypass; port: fixed (the destination of the `Path(...)` receiver is read by the walk exactly as the
  destination of `Path(...).write_text(...)`; a protected destination is an attempt that needs and consumes a grant).
- Bound names, parenthesised receivers, the unbound method `Path.touch(Path(m))`, a method bound to a name and called later
  and a call inside an `exec` text: port: fixed (the unknown destination of c1e).
- Counterexamples that stay `none`: `Path('/w/x').touch()` and `Path('/w/d').mkdir()` in the work tree, `Path(m).exists()`,
  `is_dir()`, `stat()`, `os.path.exists(m)`, the text `touch()` as string data, bare names `touch` and `mkdir`; port: kept.
- Scope kept narrow: only the pathlib methods touch and mkdir. `os.mkdir`, `os.makedirs`, `os.utime` and the other
  creating calls are not read by this change and are not judged as before; port: kept (no widening, open for a later issue).

## 2026-10-09 (fix round 1): the touch and mkdir rule reads Python only, and not data text

An independent check of the fix above found three things; two are fixed here, the third (below) was kept open and is fixed in fix round 2.

- A Node program with its own `Path(x).touch()` or `.mkdir()` method (a function named `Path` that returns an object with such a
  method) was judged a protected write, although Node writes nothing there; the baseline reader judged it `none`. The names
  `touch` and `mkdir` had been added to the list shared by the Python and Node readers (`shellVerbWriteMethod`). Port: fixed
  (the two names are read for a Python program only; `write_text` and `write_bytes` keep their shared list).
- The text `p.touch()` or `p.mkdir()` inside a string literal or a `#` comment of a Python program that holds a file API was
  judged an unknown destination (the structural scan reads raw tokens), so `print("p.touch()", os.path.exists(m))` asked for a
  grant. Port: fixed (`shellIRPyDataMask` leaves comments and string literals without an f prefix out of the touch/mkdir scan).
  An f-string stays code (its replacement fields run), and a program that names a call which runs a string (`exec`, `eval`,
  `compile`, `system`, `subprocess`, `run`, `spawn*`, ...) is read as before, with every string as code.
- `Path(f"{root}/a").touch()` (a computed f-string argument of a direct `Path(...)` receiver) was `none`: see the pre-merge
  evaluation round below, which fixes it for every Path method together.

The real entry points are held by `TestPathlibCreateRealGate` (`HandleMemoryWriteGate`: refused without a grant, one grant spent,
refused again; `HandleGitHubPostGuard` for the passing commands). The rows are in `20-crw-951-touch-mkdir.txt`.

## 2026-10-09 (fix round 2): pre-merge evaluation of 8a68d4f01, coordinator decisions E1 to E6

The evaluation (record `crw951-8a68d4f0`) found six defects; each is fixed here with rows in `20-crw-951-touch-mkdir.txt`
and cases in `TestPathlibCreateRealGate`. The first three were grant-free protected writes.

- E1 (d1): a `Path(...)` argument that is an f-string with a replacement field (`Path(f"{root}/n.md")`) is a computed part,
  never the literal text with the braces in it, so the call is the unknown destination (criterion c1e). The Path argument decoder
  is shared, so `write_text` and `write_bytes` (dev behaviour too, not only touch and mkdir) get the same answer, and so do the
  other Path methods that use it (`rename`, `symlink_to`, ...). An f-string with no replacement field (`f"/w/x"`) is the literal
  `/w/x` and stays `none` for a work tree path. Port: fixed (security).
- E2 (d2): a literal program that the recursive walk decodes from `exec`, `eval` or `compile` gets the same structural write
  analysis as a top-level Python program, read in the scope of the text that holds it. `exec("p.\x74ouch()")` and
  `exec("p.\x77rite_text('x')")` are unattributed receivers and so attempts; `exec("print(1)")` stays `none`. Port: fixed
  (security).
- E3 (d3): the receiver spelled `os` is the os module for `mkdir` only when the program never rebinds it: every occurrence of the
  token `os` is in an import statement that binds the module (`import os`, `import os.path`, `import sys, os`) or is the receiver of
  a dot call. Any other occurrence (`os = Path(...)`, a parameter, a loop, with or except target, `import sys as os`, a def or
  class name) makes the receiver unknown, so `os=Path(m); os.mkdir()` is an attempt. `import os; os.mkdir("/w/d")` stays `none`.
  The final dev merge brings CRW-900's module proof for copy/rename/link calls. One shared proof now handles those calls and
  `mkdir`, keeping logical imports and rejecting rebinding. Port: fixed for mkdir (security).
- E4 (d4): the initial round left this as an over-block. The final correction follows CRW-951 item 3: a computed
  `touch()` or `mkdir()` asks for a grant only if the program contains a decoded literal mentioning `memories` or `.codex`,
  or the name `CODEX_HOME`. This includes enclosing programs of a decoded exec. Literal protected destinations still ask
  for a grant. Computed creates without any protected reference preserve the grant; the established dev treatment of
  other unknown writers is unchanged. Mentioning the protected area while creating an unrelated computed path still
  asks for a grant, an intentional conservative cost. Port: fixed.
- E5 (d5): the data mask reads an f-string as Python does: its literal text (and doubled `{{` `}}` braces) is data, only the text in
  its replacement fields is code. `print(f"p.touch()", os.path.exists(m))` is `none`; `f"{p.touch()}"` stays an attempt. Port:
  fixed.
- E6 (d6): the run-text check (`shellIRPyRunsText`) looks only at code tokens: the mask is built first and is dropped only when a
  token outside comments and string data runs text. The word `exec` in a string or `execute` in a comment no longer switches off
  the data reading; a real `exec("...p.touch()...")` call still does. Port: fixed. (The worktree deletion guard keeps its own
  raw exec-word check, unchanged: rows `CRW-951-runs-text-01/02` are `none/allow/deny`.)

## 2026-10-09 (fix round 3): verifier findings on 9701540a4

An independent check of the head after fix round 2 found two false positives that the round introduced and one older miss.
Rows are `CRW-951-fstring-data-03` to `-08` and `CRW-951-exec-02`, `-03` in `20-crw-951-touch-mkdir.txt`; real entry points in
`TestPathlibCreateRealGate`.

- P1, E5/E6 (fields): the data mask treated an f-string replacement field as code as a whole, so a string or a comment inside a
  field (`f"{'p.touch()'}"`, `f"{'exec'} p.touch()"`, `# execute` in a multi-line field) was read as a call, and a nested
  f-string's literal text (`f"{f'p.touch()'}"`) too. The mask now reads each field's expression with the same rules: strings
  and comments inside it are data again, an f-string nested in it is read recursively, only its own fields are code. A real call in
  a field (`f"{'a' + str(p.touch())}"`, `f"{exec('p.touch()')}"`) stays an attempt. Port: fixed.
- P1, E2 (decoded program): the structural analysis of a literal exec program was run over the enclosing text joined to the
  decoded text, so the outer `exec` token switched off the data mask for the decoded program's own strings
  (`exec("print(\"p.\x74ouch()\")")` became an attempt although it prints). The analysis now judges only the decoded text's tokens,
  with the data mask of the decoded text alone, and uses the enclosing text only as the scope (its file APIs, imports and names).
  Escaped real writes (`exec("p.\x74ouch()")`) stay attempts. Port: fixed.
- P2 (nested decoded exec): the scope of a nested literal exec used only its immediate enclosing text, so the file API and
  `p = Path(m)` of an ancestor were lost one level down and `exec("exec(\"p.\x74ouch()\")")` (written with hex escapes) was `none`.
  The scope is now the text of every enclosing program, carried with the import bindings. Port: fixed (older bypass; same on
  dev and 8a68d4f01).

## 2026-10-09 (fix round 4): verifier finding on 72bc2e989

An independent check of the head after fix round 3 found that the decoded exec program's data mask covered only `touch` and
`mkdir`: the other judged names of the structural analysis (`write_text`, `write_bytes` and the rest of the write names, the
run-time names such as `getattr`, the open-mode check and the computed-subscript check) still read a decoded program's strings
and comments as code. `exec("print(\"p.\x77rite_text()\")")`, the same with `write_bytes`, and `exec("# p.\x77rite_text()\nprint(1)")`
became attempts (a denial without a grant, a spent grant with one) although they only print; on dev and 8a68d4f01 the decoded
text had no structural analysis and they were `none`. Rows are `CRW-951-exec-04` to `-12` in `20-crw-951-touch-mkdir.txt`; real
entry points (grant kept) in `TestPathlibCreateRealGate`.

- P1: in a decoded exec program every judged token in its comment or string data is skipped, and the open-mode and
  computed-subscript checks read only its code (a data `[` opens no subscript). The mask is the decoded text's own and is still
  dropped when the decoded text itself runs text. Real decoded writes stay attempts: `exec("p.\x77rite_text(\"x\")")`,
  `exec("p.\x77rite_bytes(b\"x\")")`, a decoded `getattr(...)` call and a decoded computed subscript. Port: fixed.
- A top-level program keeps the dev reading of the write and run-time names (they are not masked there; only `touch` and `mkdir`,
  new in this issue, are), so no top-level decision changes in this round.

## 2026-10-09 (fix round 5): final verifier on 238c5d9d7

- P0: a decoded bytes program containing invalid UTF-8 (for example `exec(b"print(1)\n#\xff")`) made the data mask
  re-encode a one-byte invalid byte as a three-byte replacement character and panic. The recovering memory guard then
  returned silence, allowing a later protected Path write without a grant. Port: fixed (security). The mask uses the original
  string's byte offsets, preserving invalid bytes without clipping or omitting analysis. `TestMemoryGuardDecodedBytes` runs
  the real recovering harness leg: `write_text`, `touch` and `mkdir` are denied without a grant, consume one grant and are
  denied again.
- P1: the os-module proof used physical line boundaries, so `import sys, \\` followed by a newline and `os`, or
  `if True: import os`, made an ordinary `os.mkdir("/w/d")` ask for and consume a memory grant. Port: fixed. Explicit
  LF/CRLF continuations are joined for the module proof, and an import after a compound header's colon is recognized.
  `TestPathlibCreateRealGate` asserts these commands preserve their grant; an `os=Path(...)` rebinding after either form
  still needs and spends a grant. Only the mkdir module proof changes.
