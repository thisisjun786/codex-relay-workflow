# CRW-1120 — helper settings API and MCP tool sweep

Source: CXC v0.2.40 (commit 3c1459ac) `plugins/codexclaw/components/subagent-config/src/settings-api.ts:12-25` and `store.ts:125,210,220,237`
(the messages that print `String(value)`, and the write that is answered by a second read) and `mcp.ts:38-39,48,148-152,198` (the tool
definitions and the `catalog_list` handler); the Go port's `jsString` (`internal/role/jsstring.go`), `updateSettings`, `resetSettings`
(`settings.go`), `setRoleSettings` and `resetRoleReport` (`store.go`), and `MCPTools` and `HandleToolCall` (`mcptools.go`). Found by the
10-10 CXC improvement review (A5 kept items). Each item was reproduced by a failing test before its change (the red logs are kept with the
lane's evidence).

- The messages of `updateSettings` and `getSettings` print `String(value)` of a role, scope, mode or effort of the wrong type, and for an
  object with an own `toString` member that conversion throws `Cannot convert object to primitive value`, which hid the refusal the request
  deserved and, for an unknown MCP tool name, left the call with no reply (source `settings-api.ts:12` with `store.ts:125`, `:210`, `:220` and
  `:237`; `mcp.ts` unknown-tool message; cases `get_scope_to_primitive`, `update_to_primitive`, `unknown_names`); port: fixed (`jsString`
  converts nothing that can throw: an object prints as `[object Object]`, an array joins its elements, whatever members they have, so the
  message names the field and the type, for example `invalid scope "[object Object]"`, `invalid mode "[object Object]" (must be ...)`,
  `unknown role "[object Object]"`, and `unknown tool: [object Object]` as an isError result. The refusal order is unchanged, so a store the
  write refuses still comes before the conversion. Pinned by the `portFixedToPrimitive` rows of `TestSettingsOracleReplay`, `TestJSString` and
  the `unknown_names` case of `TestMCPToolOracle`).
- Supersedes known-defects.md, section "Found by the helper role spawn resolution and settings API port", item beginning "The messages of
  `updateSettings` and `getSettings` print": now port: fixed (above).
- `updateSettings` published through `setRole` or `resetRole` and then read the settings again, so when two updates ran at once the answer to one
  request could describe the state the other produced, although both writes were kept (source `settings-api.ts:19-25`; read from the
  source); port: fixed (the answer is read before the store's lock is released: `setRoleSettings` returns the settings the write left and
  `ResetReport.Settings` those the reset left, with the roles that stay unusable named as before (CRW-1119). A concurrent writer's change is kept
  in the store and appears in the next read, never in this request's answer. Pinned by `TestUpdateSettingsAnswersWithItsOwnWrite`, which lets a
  second writer in between the write and the answer through the `updateSettings` seam).
- Supersedes known-defects.md, section "Found by the helper role spawn resolution and settings API port", item beginning "`updateSettings` publishes
  through": now port: fixed (above).
- `catalog_list` did not catch a catalog read rejection, so the stdio queue swallowed it without a tool reply (source `mcp.ts:148-152,198`), and the
  library returned the error to its caller, which a transport registered later would have dropped the same way; port: fixed (the handler answers
  with one isError tool result whose text is `{"error":"<message>"}`, the way a `subagents_set` failure is answered, and returns no error; the only
  error `HandleToolCall` still returns is for params that are not JSON. Pinned by `TestMCPToolCatalogListReadFailureIsAnswered`).
- Supersedes known-defects.md, section "CRW-528 — Helper role MCP tool library", item beginning "`catalog_list` does not catch": now port: fixed (above).
- The retained tool descriptions and schemas advertised project scope although the absorbed settings API supports global scope only (source
  `mcp.ts:38-39,48`); port: fixed (decision 7: `subagents_get` and `subagents_set` list `"enum":["global"]` for `scope`, `subagents_get` says that only the
  global scope exists and a role with no override uses the original session, and the `inherit` description says the role inherits the original session. No
  project store is restored, and a `scope` of `project` is still refused by the settings API. The snapshot is `internal/role/testdata/mcptools/tools-global.json`;
  `TestMCPToolOracle` checks it differs from the oracle's recorded definitions in exactly those words, and that no definition mentions the project scope).
- Supersedes known-defects.md, section "CRW-528 — Helper role MCP tool library", item beginning "The retained tool descriptions and schemas advertise project
  scope": now port: fixed (above).
- The `catalog_list` and `GET /api/catalog` reads depended on the native configuration file since CRW-1132 resolved the native source before the cache lookup and
  the OCX run, so a FIFO `config.toml` made them wait for good with a working OCX; port: fixed under CRW-1132 (the configuration is opened without blocking and
  must be a regular file; see the CRW-1132 record, `TestLiveCatalogOcxDoesNotWaitOnTheNativeConfigFile`, whose cache-hit and `RunOcxModels` rows are the two paths
  this issue's sweep reaches).
