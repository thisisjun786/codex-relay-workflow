# CRW-1099 — deletion protection stays with the original session identity

Source: CXC v0.2.40 `pabcd-state/src/worktree-guard.ts:280-287`;
port: `internal/pabcd/hook/worktreedel.go` and `worktreedel_judge.go`.

- A cd or git -C moved the protected directory to the execution directory;
  unrelated temporary cleanup was denied and original checkout/slot ancestors
  could be removed. port: fixed. Resolve operands from the execution directory,
  compare them against the canonical original session cwd, checkout and slot and all their
  ancestors using path-component boundaries. The original cwd stays fixed even when a session starts below the checkout. Without a checkout, use the original
  session cwd as the fallback; never protect a directory merely because of cd.
- An unreadable command received a deletion/teardown instruction although no
  removal was observed. port: fixed. WORKTREE-GUARD-03 still denies, with the
  bounded `analysis-unavailable` code and instructions to use inspectable commands.
  The reader's raw error is never placed in the model's context.

`TestProtectionStaysWithOriginalCheckout` covers cd, git -C, subshells, carried
scripts, find, xargs and moves; `TestFixedProtectionPathBoundariesAndFallback`
covers symlink aliases, sibling prefixes, safe subdirectory cleanup and unknown
paths. `TestUnreadableWorktreeCommandGivesAnalysisRemedy` checks the module case.
CRW-895's `find . -delete` from a checkout subdirectory intentionally becomes
allowed: that directory is neither the checkout nor its ancestor. Its other
find/xargs checks remain. The guardian skill wording is owned by the separate
activation-dependent documentation item and is unchanged in this lane.

`TestOriginalSessionSubdirectoryRemainsProtected` pins the original cwd member of
the fixed set, including after cd and for a move; cleanup below it stays allowed.
The unreadable `su` case in the cxcfuzz seeds keeps its oracle answer and records
CRW-1099's analysis diagnostic as the intentional Go answer.

Post-evaluation safety corrections: port: fixed. The deletion guard opts into a
failure-aware directory reading. Only a simple, non-negated `cd` reached through
success on `&&` establishes the directory for the next command. `||`, unchecked
sequences and completed conditional chains retain uncertainty; relative deletion
is refused. Use `cd <literal> && <cleanup>` for external cleanup, including inside
subshells and carried scripts. Other shell-reader callers retain their behavior.
`TestDeletionGuardDoesNotAssumeFailedCDSucceeded` covers these cases without
executing deletion commands.

`find -L` can follow nested links back into the checkout despite an external
start point. The reader retains its effective traversal mode (last `-H/-L/-P`)
on actions and feeds. The guard refuses link-following `-delete` and removal
actions as analysis unavailable, including guarded matches and execdir; physical
`-P` cleanup and read-only traversal remain allowed. No filesystem scan is used
as a promise about what will exist when the shell executes.

The original expected answers of fourteen shell reproduction rows are retained;
their explicit deviations now record deletion-only refusal of unchecked cd before
a relative carried script/removal, or link-following deletion: CRW-984-05,
PR845-92799ae0-d5, PR845-ef89e0ed-d3, PR845-f30490c1-d5/d5b, CRW-895-c23/r9,
CRW-875-22-20/21/22/23/51/53 and CRW-1064-04. Memory/GitHub answers are unchanged.
Their remedies are success-gated cd (`&&`) and physical find traversal (`-P`).
Absolute deletion targets remain independent of directory uncertainty. The old
sequential-cd command-substitution control is intentionally refused for the same
failed-cd reason; no oracle fixture is rewritten.
