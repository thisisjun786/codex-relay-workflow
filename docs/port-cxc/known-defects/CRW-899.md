# CRW-899 — the activation and deactivation config-lock paths

Source: CXC v0.2.40, commit `3c1459acadeb1906d97c00a598e1457327ae372d` —
`plugins/codexclaw/components/config-guard/src/activate.ts` (`activate`, the caller's
`configPath` resolved at :201 and read at :214, :271, :278, :295) and
`plugins/codexclaw/components/config-guard/src/deactivate.ts` (`deactivate`, the single
`manifest read at :117 and the `configPath` read and write at :122, :132, :155).
Port: `internal/runtime/install/configguard/activate.go` (`Activate`),
`internal/runtime/install/configguard/deactivate.go` (`Deactivate`) and
`internal/pabcd/crwdir/swap.go` (`LockConfig`, `ConfigLock.Target`).

## Defects

- The activation took the sidecar lock keyed by `lock.Target` and then read, edited and hashed
  that resolved target instead of the caller's config path (CRW-844 pinned the key writes, CRW-877
  the hash and the pre-image read), so an injected `codex features enable` that atomically
  replaced a symlinked `config.toml` left the managed keys in the file the lock's target named
  while the live config, read through the caller's path, never received them, and the manifest's
  `postActivateHash` described the file the user no longer had. The oracle read the caller's
  `configPath` at every step (source `activate.ts:201,214,271,278,295`), so this was a
  regression of the port, not an oracle behaviour; port: fixed (CRW-899's answer: the lock stays
  keyed by `lock.Target` so two writers reaching one file through different spellings share
  one lock, while the pre-image read, the backup mode stat, the managed-key read-modify-write and
  the post-activation hash all use the caller's path — the rule CRW-891 gave
  `SetMultiAgentV2State`. Pinned by
  `TestConfigLockPathsActivateWritesThroughTheReplacedCallerPath` and the regular-file and
  write-through-the-link controls in `config_lock_paths_test.go`).
- The activation mapped every `crwdir.LockConfig` failure through an unlocked re-read of
  `config.toml`, so a contended lock over an unreadable file (mode 0200, or any file the
  process cannot read) answered the read path's message ("could not read ... (left unchanged)")
  instead of `crwdir.ConfigLockBusy`, hiding which writer the operator was waiting behind.
  The oracle had no lock at all (source `activate.ts:201-295`, no sidecar anywhere), so the
  busy text is this port's own contract and the substitution was the port's defect; port: fixed
  (CRW-899's answer: contention is returned as it is, before the re-read; the re-read that maps an
  unreadable or dangling `config.toml` to the read path's message runs only for a failure that
  is not contention. The comparison is `err.Error() == crwdir.ConfigLockBusy` because
  `LockConfig` builds that error once with `errors.New(ConfigLockBusy)` and never wraps it;
  the call site carries the comment pinning that coupling. Pinned by
  `TestConfigLockPathsActivateAnswersBusyWhenTheConfigIsUnreadable`).
- The deactivation compared the re-read manifest's `ConfigPath` with the path the lock was
  taken on as strings, so a manifest naming the same file through another spelling (a
  `CODEX_HOME` reached through a directory symlink, which `crwdirSwapResolvePath` leaves spelled
  through the alias because it follows only a symlink in the final component) was refused as
  "a different config file" and the owned keys were never restored. The oracle compared no paths
  at all (source `deactivate.ts:122` read one `configPath` and used it for both the read and
  the write), so the refusal is this port's own; port: fixed (CRW-899's answer: the comparison is
  file identity — the same string, or two paths the kernel resolves through their symlinks to one
  directory entry — and a path that cannot be shown to be the same target is still refused with
  today's message. Directory-entry identity rather than device and inode is deliberate: the restore
  publishes through the locked path with an atomic rename, which replaces that one pathname, so
  accepting a hard link would leave the managed key in the manifest's name while the command
  reported it restored. Pinned by
  `TestConfigLockPathsDeactivateAcceptsTheSameFileUnderAnotherSpelling` and
  `TestConfigLockPathsDeactivateRefusesAReallyDifferentConfigFile`, with
  `TestConfigLockPathsDeactivateRefusesAHardLinkedConfigFile` pinning the hard-link refusal).
- `ConfigLock.Target`'s doc comment told every caller that it "must read and publish that
  path", which CRW-891's `SetMultiAgentV2State` already did not do (source
  `multi-agent-v2.ts:53,60,67,70` reads the path it resolved once), so the comment described a
  contract the code had stopped keeping; port: fixed (CRW-899's answer: the comment now states that
  `Target` is the lock's key and the identity a caller compares against, and that a writer whose
  content path can change under an external runner reads and publishes through the caller's path).
- The deactivation's own content path stays `lock.Target` (`deactivate.go:129`,155,163,168`),
  so a concurrent external replacement of a symlinked `config.toml` between the lock and the
  restore is the same class as the activation defect above, with a narrower window because the
  deactivation's injected CLI calls run after its restore rather than between its read and its
  write (source `deactivate.ts:122,132,155`, one unlocked read and one write); port: kept
  (CRW-899's scope is the identity comparison on the deactivation side; the issue's three answers
  name only the activation for the caller's-path rule, so this is recorded rather than fixed here.
  Closing it needs the same caller's-path treatment for `Deactivate`'s read and restore).
  CRW-899's second generation narrowed the window further: the content path is pinned to the file
  the held sidecar belongs to and the restore publishes through that pinned path, so a directory
  alias retargeted after the pin now writes the file the lock guards rather than following the
  retarget.
- `configset.go` (`ApplyManagedKey`, :76 `target := lock.Target`) reads, decides and
  publishes through the lock's resolved target rather than the caller's path. It runs no injected
  CLI (`ConfigSetDeps` has no `Run` field, configset.go:14-18), so the deterministic
  runner-between-reads shape does not apply to it; what remains is an external concurrent path
  replacement window — an outside process that replaces the caller's pathname while this command
  holds the lock, which then publishes to a pathname the lock no longer names. The oracle used the
  caller's path throughout (source `config-set.ts`, the caller's `configPath`); port: kept
  (outside the issue's three answers and outside this change's edit regions; recorded here so the
  next reader of this file sees the third writer of the same shape rather than rediscovering it).


- The deactivation's identity comparison resolved both spellings again *after* the lock wait
  (`deactivate.go:61-74` and the call at :174), so a directory alias retargeted while the command
  waited made the republished manifest's new file compare equal to the alias's new resolution while
  the held sidecar belonged to the old file: the restore then wrote the other file without its
  lock, and a concurrent writer of that file could interleave with it. Found by the pre-merge
  evaluation of the first-generation head; port: fixed (CRW-899's second-generation answer, E1:
  immediately after the lock is taken the command resolves the config file's real path, requires the
  sidecar beside it to be the very file the lock holds (`crwdir.ConfigLock.HoldsSidecar`, fstat)
  and refuses when it is not; the comparison and the restore then use that pinned real path, never a
  path re-resolved after the wait. Pinned by
  `TestConfigLockPathsDeactivateRefusesARetargetedDirectoryAlias` and
  `TestConfigLockPathsHoldsSidecarContract`, with the guard's own failure path pinned by
  `TestConfigLockPathsPinnedRefusesARetargetedDirectoryAlias` and the pin's re-resolution by
  `TestConfigLockPathsComparisonDoesNotResolveThePinAgain`).
- The same comparison compared the two `filepath.EvalSymlinks` results as strings, and
  `EvalSymlinks` keeps a relative path relative, so one file named `real/config.toml` and
  `/x/real/config.toml` was refused as a different config file — the very promise c1 makes. A
  relative CODEX_HOME is supported (`internal/runtime/install/features.go:86-99` returns it unchanged),
  so the case is reachable; port: fixed (E2: links are resolved first and only then is a relative
  result joined to the resolved working directory, with no Clean, Abs or Join before the resolution.
  A spelling whose parent is a symlink followed by ".." is resolved by the kernel, not cleaned
  lexically. Pinned by `TestConfigLockPathsDeactivateAcceptsARelativeSpelling` and
  `TestConfigLockPathsSpellingWithDotDotResolvesThroughTheKernel`).
- The first attempt at the E2 fix treated every `filepath.EvalSymlinks` failure as "only the last
  component is missing" and applied the same recovery to the parent, so a manifest naming
  `/x/real/missing/../config.toml` (no such directory) was synthesised and folded back onto
  `/x/real/config.toml`, the locked file, without any evidence the manifest named it. The same
  attempt also failed a bare relative name with no parent component (`config.toml`, which a relative
  CODEX_HOME produces) once that file was removed, so an uninstall regressed from continuing to an
  early refusal. Both were found by the pre-merge evaluation of the second-generation head; port:
  fixed (the recovery is limited to the final component and the parent must resolve completely, and
  an empty parent uses the resolved working directory. Pinned by
  `TestConfigLockPathsMissingIntermediateDirectoryIsNotSynthesised` and
  `TestConfigLockPathsBareRelativeAbsentConfigResolves`; a third attempt at the same recovery
  dropped the root separator and resolved the working directory for a config named at the root,
  which the pre-merge evaluation of the third-generation head found and
  `TestConfigLockPathsRootParentKeepsTheRoot` now pins).
- The comparison accepted only an equal resolved string, so on a case-insensitive filesystem one
  directory entry named through a differently cased path was refused as a different config file,
  although the pin's own sidecar and the manifest's path name the same entry. Found by the
  pre-merge evaluation of the fourth-generation head; port: fixed (a differing string is accepted
  only when the two paths are one file AND one parent directory AND the directory holds a single
  entry for that name, which is what separates a case-insensitive spelling — one entry — from a
  hard link or a case-sensitive sibling, two entries that a rename over the locked path would not
  reach. Pinned by `TestConfigLockPathsAcceptsACaseVariantSpelling` where the filesystem is
  case-insensitive and by `TestConfigLockPathsRefusesACaseVariantHardLink` everywhere).
- The first attempt at that case-insensitive acceptance asked the filesystem about the pinned path
  again (stat of the pin, stat of its parent, a directory read), so replacing the pinned DIRECTORY
  after the pin made the replacement's file compare equal and the restore would have written it
  under the old file's lock. Found by the pre-merge evaluation of the fifth-generation head; port:
  fixed (the pin captures the file's and the directory's identities once, at lock time, and the
  comparison is judged against those captured values rather than re-resolving the pinned path as a
  comparison target. Pinned by `TestConfigLockPathsRefusesAPinnedDirectoryReplacedAfterThePin`).
- Capturing the identities once was not enough on its own: a directory replaced after the pin moves
  the held sidecar away from the pinned pathname while a manifest still matched the captured pair.
  Two success branches did that — the equal-resolved-string branch returned true without looking at
  the pin's identities at all, and the different-spelling branch accepted a manifest naming the moved
  file because that spelling's file and parent are still the pinned ones — so the restore published
  to the pinned path, which now held another file, under a lock that guarded neither. Found by the
  pre-merge evaluation of the sixth-generation head; port: fixed (the comparison first re-proves,
  through `configLockPathsPinHolds`, that the pinned path still names the very sidecar this lock
  holds, and refuses when it does not; the captured identities are only consulted after that proof,
  so a stale pin answers false rather than widening acceptance. Pinned by
  `TestConfigLockPathsDeactivateRefusesAPinnedDirectoryReplacedUnderTheSameSpelling` and
  `TestConfigLockPathsDeactivateRefusesAManifestNamingTheMovedDirectory`, both through the public
  `Deactivate` entry point).
- The deactivation's lock-time identity check was missing entirely in the first generation, which
  is what let the two defects above exist; the sidecar proof added for E1 is the port's own
  strengthening (the oracle had no lock at all, source `deactivate.ts:122,132,155`); port: fixed.
- The case-insensitive acceptance counted the directory entries by enumerating the parent directory,
  so a parent without read permission — which still allows the stat, open, create and rename the
  restore needs — made the comparison refuse a spelling that names the locked entry, and the owned
  keys and flags were left behind. Found by the pre-merge evaluation of the seventh-generation head;
  port: fixed (the count is per folded name and falls back to the file's own link count when the
  directory cannot be enumerated. Pinned by
  `TestConfigLockPathsOneFoldedEntryFallsBackWithoutDirectoryRead` and
  `TestConfigLockPathsDeactivateAcceptsACaseVariantUnderAnUnreadableParent`, the last through the
  public `Deactivate` entry point on a case-insensitive filesystem).
- The first fix for that defect used the inode's whole link count as the test for "one directory
  entry", so a hard-link backup under ANOTHER name — which leaves the entry the manifest names
  exactly one — made a valid case-insensitive alias compare as a different config file, and the
  owned keys and flags were left behind. Found by the pre-merge evaluation of the eighth-generation
  head; port: fixed (the readable-directory path counts only the entries whose name folds to the
  pinned file's name, so a separate hard link does not matter. Pinned by
  `TestConfigLockPathsOneFoldedEntryCountsOnlyTheFoldedName` and
  `TestConfigLockPathsDeactivateAcceptsACaseVariantWithAHardLinkBackup`, the last through the
  public `Deactivate` entry point).
- The unreadable-directory fallback then kept an inode link count captured at pin time, which is
  stale by the time the manifest is read: a hard link for the same inode created after the pin left
  the count at one, so the comparison accepted an entry the lock does not guard and the restore wrote
  the pinned file while the name the manifest uses kept the managed key. Found by the pre-merge
  evaluation of the ninth-generation head; port: fixed (the fallback asks the filesystem itself
  whether it folds case, by creating a probe in that directory and reading it back under a different
  case; a filesystem that folds case has one entry for the two spellings, one that does not can hold
  a second entry a rename would not reach. It needs only the create, stat and remove the restore
  already needs, and answers false whenever the probe cannot be made. Pinned by
  `TestConfigLockPathsDeactivateRefusesAHardLinkCreatedAfterThePin` and
  `TestConfigLockPathsDeactivateRefusesACaseSiblingWhenTheParentCannotBeRead`, both through the
  public `Deactivate` entry point, and by
  `TestConfigLockPathsDirFoldsCaseNeedsNoDirectoryReadPermission`).

## Supersedes
- Supersedes known-defects/CRW-877.md, section "Defects", item beginning "The activation's own
  `codex features enable` calls": now port: fixed (the fixed status stands unchanged — the
  lock is still taken once in `Activate` and held across the whole flow, pinned by
  `TestActivateHoldsTheConfigLockWhileItEnablesFlags` — and CRW-899 qualifies the sentence
  that describes that flow as covering "the post-activation hash": the hash is computed through the
  caller's path, not through `lock.Target`, so the critical section ends on the file the
  caller's path names).
- Supersedes known-defects/CRW-877.md, section "Defects", item beginning "The deactivation decided
  from the manifest it re-read inside the lock even when that manifest named a different config
  file": now port: fixed (the fixed status stands unchanged — the refusal still runs inside the
  lock, pinned by `TestDeactivateRefusesAManifestThatNamesADifferentConfigFile` and, for the case
  where both files exist, by `TestConfigLockPathsDeactivateRefusesAReallyDifferentConfigFile` —
  and CRW-899 narrows what "a different config file" means: the manifest must name a file the
  kernel proves different, and the same file under another spelling is accepted and restored).
- Supersedes known-defects/CRW-891.md, section "Defects", item beginning "The sidecar lock is keyed
  by the file the caller's path resolved to": now port: kept (the kept status stands unchanged — the
  window that item records for the multi-agent repair is the same window CRW-899 leaves on the
  activation and the deactivation sides, recorded in the two items above, and it is still closed
  by a lock keyed by the caller's path, a change to `crwdir` rather than to one writer).
- Supersedes this file, section "Defects", item beginning "The deactivation's own content path
  stays `lock.Target`": now port: kept (the kept status stands, with the window narrowed as
  recorded in that item — the pin and the publish through the pinned path mean a retarget after the
  pin writes the file the lock guards).
