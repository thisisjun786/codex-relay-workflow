# CRW-384 — orchestrate transition core

Source: CXC v0.2.40 (`3c1459ac`) `plugins/codexclaw/components/pabcd-state/src/orchestrate-cli.ts`, the transition half
:549-1131 and the helpers :96-103 and :431-465 it uses, ported to Go as `internal/pabcd/cli/orchestrate_transition.go`
with the `orchestrate-cli.test.ts` cases of that range as `internal/pabcd/cli/orchestrate_transition_test.go`. The
recorded corpus has no fixture this issue can claim: the orchestrate fixtures need the CLI verb row, which CRW-758
owns, so they stay pending and nothing here is tagged identical or intentionally-changed.

- The command's own contract says it never throws ("Execute a parsed orchestrate CLI command. Does its own state IO.
  Never throws."), yet three paths of the ported range let an exception escape to the caller: the source resolution of
  every phase verb (`orchestrate-cli.ts:572`, whose own catch handles only the refusal it raises itself), the B entry
  source capture (`:1070`) and the epoch nonce's `randomBytes` (`:97`) (source `orchestrate-cli.ts:423`, `:572`, `:97`
  and `:1070`); port: kept (the Go port has no throw, so it returns those as an error to the caller, which is the same
  answer at a different carrier; no refusal path of the range uses it).
- Two arms of the ordinary edge write can never run: the plan binding's "entering A another way" arm
  (`result.state.phase === "A" ? state.planUnit : null`, `orchestrate-cli.ts:1073-1074`) and the check epoch's
  "staying in C" arm (`state.phase === "C" ? state.checkEpoch : ...`, `:1077`). No legal edge is a self-edge, and P>A is
  the only edge into A, where the minted binding always wins the first arm, so both read as live rules that nothing
  reaches (source `orchestrate-cli.ts:1073-1077` against `fsm.ts`'s `VALID_TRANSITIONS`); port: kept (both arms are
  ported as they are, in `orchestrateTransitionPlanBindingOf` and `orchestrateTransitionCheckEpoch`, so the port's shape
  matches the oracle's; a later change may drop them).
- Supersedes known-defects.md, section "Found by the CRW-609 lossless rewrite guard", item beginning "A writer of the
  session file that does not ask the guard still replaces a lone surrogate": now port: fixed for this writer (the
  orchestrate transition is the writer that item named as a future one; each of its three session writes asks
  `cliVerdictsIntact`, which is `state.RewriteKeepsUnverified` plus the count the caller read, and refuses with
  "refusing to overwrite it" and no write at all, leaving state, both ledgers and the goalplan untouched; the general
  item stays for any writer that does not ask the guard).
- The transition publishes the state it read when the command started, with no lock, so a hook that writes the same
  session in between - a memory grant, an idle-edit counter, a verdict - is overwritten by the stale copy and its
  update is lost (source `orchestrate-cli.ts:163`, `:653` and `:1070-1131`; found by the Devin review of this port's
  pull request, `kind: bug`); port: fixed (a data-loss defect, the class the parity rule revision of 2026-10-03 fixes
  during the port: `RunOrchestrateTransition` holds `state.WithSessionLock` across the whole read, gate and write, so
  a concurrent writer serialises with it and its update survives, and a lock that cannot be taken is reported as an
  error rather than as a silent success; `TestOrchestrateTransitionHoldsTheSessionLock`).
- The ordinary edge publishes the session state before its transition-ledger row (source `orchestrate-cli.ts:1119`
  then `:1123`), so a failed row write leaves an advanced FSM whose row nothing can replay; the port writes the
  row first, so a failed append changes nothing and the same verb can be retried (found by the Codex review);
  port: fixed.
- The P>A housekeeping takes the epoch of only the FIRST open plan_audit round whose epoch differs from the new one
  and hands just that epoch to `supersedeStaleRounds`, so a plan holding open rounds of two or more old epochs keeps
  the later ones open, and an effective-round lookup can still return one of them (source `orchestrate-cli.ts:1088-1096`;
  found by the Devin review, `kind: bug`); port: kept.
- The housekeeping runs before the state write and is fail-open, so a P>A whose state write then fails has already
  closed the old rounds and cleared their cursor while the session stays at P, and the retry mints a different epoch
  and cannot restore them (source `orchestrate-cli.ts:1085-1119`; found by the Devin review, `kind: bug`); port: kept.
- The A>B review binding (`orchestrate-cli.ts:49-92`, `:688-691`) and the B>C source gate (`:701-717`) are not ported
  by this issue: `orchestrateTransitionReviewBinding` and `orchestrateTransitionSourceGate` are pass-through functions
  that the sibling issue which owns them fills, and nothing reaches them today because the `crw pabcd orchestrate`
  verb row is another sibling's scope, as the file's header comment states. Two review findings of `kind: security`
  name the gap (Devin `SEC_..._0001` and `SEC_..._0002`); the answer is that it is the deliberate split boundary of
  this issue, unreachable until the verb row lands, and not a behaviour this PR can change without taking over its
  sibling's scope; port: pending (the sibling issue that ports the two gates closes it).
