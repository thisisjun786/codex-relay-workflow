# CRW-977 — the SessionStart self-heal report: a cut-off feature list, and a codex that cannot run ahead of one that can

Source: CXC v0.2.40 (3c1459ac) plugins/codexclaw/components/config-guard/src/cli.ts:140-149 (makeRealRunner, `spawnSync` with no timeout) and the PATH search `spawnSync` does through libuv (`execvp` semantics). Go port: `internal/runtime/install/configguard/selfheal_report.go` (`SelfHealReportRunner`, `selfHealReportBinary`). Both differences were found by the evaluation of CRW-349 (`pr673`, P1 two) and are not the oracle's behaviour.

- The runner ignored the error `cmd.Run` returned after the five second `WaitDelay` (`exec.ErrWaitDelay`) and took exit status 0 for a complete answer. A probe that exits 0 while a descendant still holds its stdout open leaves the part of the list that arrived, and a cut list reads an enabled soft flag as off and warns about it. The oracle's `spawnSync` has no timeout and waits until the stdio closes, so it receives the whole list; port: fixed, with a recorded deviation (the runner treats `exec.ErrWaitDelay` as a failed run, exit 1, which `ReadDeclaredState` turns into an unavailable round and the hook into silence, as the issue says a failed list is passed over silently. Waiting without a bound as the oracle does would hold the session start past the hook's time limit for a probe whose descendant never closes the pipe, so the wait stays bounded by `selfHealReportWaitDelay` and a probe that does not close in time is a measurement failure instead of a list. The difference from the oracle: a probe whose descendants close the pipe later than five seconds after it exited is silent here and reported by the oracle). Pinned by `TestSelfHealReportTruncatedListingIsSilent` and `TestSelfHealReportRunnerMarksAWaitDelayAsFailed`.
- `selfHealReportBinary` took the first `codex` on PATH that had any execute bit, so a file the caller owns with mode 0001 (EACCES on execution) ended the search, the probe failed and the warning for a flag that is off disappeared. libuv skips a candidate it may not execute and goes on to the next PATH directory; port: fixed (the search checks `faccessat(X_OK)` with the effective ids, as `execvp` effectively does, and continues past a candidate that fails it; with no runnable candidate the error is still EACCES when some candidate exists and ENOENT when none does, so the round stays silent as before). Pinned by `TestSelfHealReportPathSearchSkipsAnUnrunnableCodex` and `TestSelfHealReportOnlyAnUnrunnableCodexIsSilent`.
