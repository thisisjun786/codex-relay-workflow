# CRW-1090 — the R-11 transcript guards read Codex records, and a compaction ends the old generation

Source: `plugins/codexclaw/components/pabcd-state/src/transcript.ts` (`hasStageMarkerForPhase` :57-64, `isContextPressureTail` :66-74) and its callers `hook.ts:803-816` (the R-11 guards of `handleUserPromptSubmit`) and `hook.ts:1805-1873` (`handleStop`) at CXC v0.2.40 (commit 3c1459ac). The Go side is `internal/pabcd/host/transcript_generation.go` (`ReadTranscriptGeneration`), called from `internal/pabcd/hook/prompt_trigger.go` and `internal/pabcd/hook/stop.go`. Found by the 10-10 isolated real-use trial (S4-F1, P1) and the 10-10 CXC improvement review (A1-02).

- After a compaction the next prompt did not get the phase directive back. PostCompact resets `lastInjectedPhase` to null, but the Codex rollout is append-only and its `compacted` record keeps the pre-compaction history (`replacement_history`, `guardian_history`), so the stage header `[crw — P: PLAN]` the compaction removed from the model's context was still inside the 64 KiB tail; `hasStageMarkerForPhase` found it, the handler wrote `lastInjectedPhase` back to the phase and answered nothing. Whether it happened depended on how far the compacted record reached into the tail (trial sessions s1-r3 and s1-r5 lost the directive, s1-r6 got it; reproduction `internal/pabcd/hook/testdata/crw1090`); port: fixed (the tail is read as whole JSONL records, the cut first line of a window that does not start the file is dropped, and only the records after the last compaction the tail shows count: the `compacted` record, or the `event_msg` item_completed of item type ContextCompaction that follows it, or the older `context_compacted` event; the compacted record's own histories are never read. A cursor PostCompact reset is never set again from the tail, so the prompt after a compaction injects the full directive (mode 2). Pinned by `TestCRW1090S4CompactionReinjectsThePlanDirective`, which drives the wired leg with the trial's state and rollout, and `TestCRW1090SameGenerationInjectionDedups`).
- Supersedes known-defects.md, section "Found by the host-state reads port", item beginning "`hasStageMarkerForPhase` finds the stage marker anywhere in the tail": now port: fixed (a stage marker counts only as the opening of a hook's additionalContext record, which a Codex rollout writes as a `response_item` message of role developer whose metadata names `hooks.additional_context` (a developer record without metadata, with null metadata or with metadata of another kind is not attributable to a hook and is not the marker; the state cursor then decides and the stage header goes in again, since a missing marker costs one re-injection and a wrong one skips the directive, `TestCRW1090AnUnattributedDeveloperRecordIsNotTheStageMarker`); a user prompt, an answer, a tool output or an event that quotes the marker, and another hook's context that quotes it (the recall hook's untrusted data), no longer suppress the injection. `TestCRW1090QuotedMarkersDoNotSuppressTheInjection`, `TestHasStageMarkerForPhaseMatchesBothForms`).
- Supersedes CRW-645.md, item beginning "`hasStageMarkerForPhase` and `isContextPressureTail` match their markers as unanchored substrings": now port: fixed (as the two items above and the one below).
- `isContextPressureTail` matched three phrases anywhere in the tail, so a user asking what "context window has been compacted" means, or an answer or tool output holding the phrase, released an ACTIVE goal's Stop and suppressed the prompt's passive injection; and no record a Codex rollout writes for a compaction carries any of the three phrases (the S4 rollouts hold none), so a real compaction was never pressure at all (source `transcript.ts:66-74`, callers `hook.ts:803-805` and the two Stop paths); port: fixed (pressure is a compaction record that no user prompt has followed yet: the user.text message, its UserMessage item, or the older user_message event ends the recovery window; the environment context Codex records as a user message after a compaction does not. The Stop leg releases inside the window without spending the budget and blocks again once a prompt was recorded after the compaction. `TestCRW1090QuotedPressureDoesNotReleaseTheGoalStop`, `TestCRW1090CompactionPressureLastsUntilTheNextUserTurn`, `TestStopContextPressureTailReleasesWithoutSpendingTheBudget`; the corpus fixture `hook__stop-checking-pabcd-continuation__context_pressure_tail_releases` is replayed with a compacted record as its transcript, contract/notes/cxc/CRW-1090.json).
- The prompt's passive injection no longer has a pressure suppression: Codex runs the UserPromptSubmit hooks before it records the prompt, so the prompt after a compaction always sees the compaction with no prompt after it, and suppressing there would withhold the directive the compaction removed, which PostCompact's cursor reset exists to restore (the oracle's "don't pile on" rule at `hook.ts:803-805`); port: fixed (a prompt is the boundary of the recovery window, not inside it; `TestPromptTriggerContextPressureNoLongerSuppressesReinjection`).
