# CRW-895 — the worktree deletion guard does not judge find -delete, find -exec and xargs targets

Source: the CXC oracle `worktree-guard.ts` does not read `find` or `xargs` as a deletion command, so a deletion whose target
a find start point or standard input names passes (found by the CRW-726 second-generation verdict, 10-07, and re-checked on
dev 09e5c5bcc on 10-09). The port reads the command with the shared reader (`internal/pabcd/shellir`, CRW-1028); the verdict is
`internal/pabcd/hook/worktreedel_judge.go`. The tests that hold it are `internal/pabcd/hook/worktreedel_crw895_test.go`,
`internal/pabcd/shellir/feed_test.go` and the rows `CRW-895-*` in `internal/pabcd/hook/testdata/shellir/rows/18-crw-895.txt` and
`19-crw-895-eval.txt`, `20-crw-895-round2.txt` and `21-crw-895-round3.txt` (indexed in `reproductions.tsv`), which give a verdict per gate for every shape. Red output on the
unfixed trees and green output on the final head are kept under `/state/crw/crw-895/evidence/`.

Two items, both a security class that the oracle also allows:

- `find` with `-delete`, or with `-exec`, `-execdir`, `-ok` or `-okdir` running `rm`, `rmdir`, `unlink`, `shred` or
  `git worktree remove`, deleted the managed worktree when a start point named it (`find ../repo -delete`, `find .. -delete`,
  `find .. -exec rmdir {} +`, `find ../repo -exec git worktree remove {} \;`); port: fixed (security; the oracle also
  allowed it). The start points are judged: a start that resolves to an ancestor of the worktree (the slot root and
  everything above it) is refused whatever tests follow; a start that is the worktree itself (the checkout, the directory
  the command runs in, a directory between) is refused unless a test stands before the action on every path that reaches it
  and leaves that start out; start points read at run time (`-files0-from`) are refused.
- `xargs` running `rm`, `rmdir`, `unlink`, `shred` or `git worktree remove` took its targets from standard input and deleted the
  managed worktree when the left of the pipe, a here-string or a here-document named it (`echo ../repo | xargs rm -rf`,
  `echo ../repo | xargs git worktree remove`, `echo ../repo | xargs rmdir`); port: fixed (security; the oracle also allowed
  it). The reader evaluates what the producer prints and splits it as xargs does, and a name that resolves to the worktree,
  its slot or an ancestor is refused when it is spelled other than `.` (`../repo`, an absolute path, `..`); a source the
  reader cannot read is refused (an unknown word such as `"$X"`, `$PWD`, `~` or a command substitution, `xargs -a FILE`,
  standard input from a file other than `/dev/null`, a producer the reader cannot trace).

Verdicts, as the issue and the 10-09 re-check and independent verification list them (before is dev 09e5c5bcc; the red
output is kept under `/state/crw/crw-895/evidence/`):

- `find . -name '*.o' -delete`, `find . -type f -delete`, `find . -newer x -delete`, `find ../repo -path '*/build/*' -delete`
  and `find {checkout} -name '*.o' -delete` were refused because `-delete` alone was judged; port: fixed (the issue's allow
  control: a start equal to the worktree with a test before the action is allowed). The tests are the primaries that
  test a file (`-name`, `-iname`, `-path`, `-regex`, `-type`, `-newer`, `-newerXY`, `-mtime`, `-size`, `-perm`, `-user`, `-empty`,
  and the rest of the GNU list); `-maxdepth`, `-mindepth`, `-prune`, `-print`, `-true` and an action are not tests. The
  expression is read as find reads it: `-o` and `,` start an alternative whose tests are its own, a parenthesised group
  guards an action after it only when every alternative of the group holds a test (and an action inside a group is reached
  through the tests before the group), and the operand of a primary (`-name -delete`) is not an action. A name or path
  pattern and a regular expression are evaluated against the start point as find prints it, so a test that matches the start
  point itself guards nothing (`-name '*'`, `-path '*'`, `-regex '.*'`, `-name '????'` or `-name 'r*'` against `../repo`,
  where find matches `-name` against `repo`); a bracket that names a POSIX class (`-name '[[:alpha:]]*'`, `'[[:print:]]*'`) ends at
  its own `]` and is evaluated. `-iname` and `-ipath` compare letters and ranges without case but test a class against the name as
  it is (GNU find selects `Repo` with `-iname '[[:upper:]]*'`), so a class is read as fitting either case and a negated bracket as
  fitting. Outside ASCII the locale decides what `?` and a bracket take (a byte in the C locale, a character in UTF-8, and a class
  fits letters of other scripts: `[[:alpha:]]*` selects `리포` in UTF-8), so a pattern with `?` or a bracket against a name or a pattern
  with such a byte is read as fitting, and a letter outside ASCII is matched as its UTF-8 bytes (`-name '리*'` fits `리포`). A collating
  symbol, an equivalence class or an unknown class is read as fitting as well (`[[.r.]]*` selects `repo`), so it guards nothing;
  `-name 'r*'` against `.` leaves the start out, because find matches `.`. Every
  other test, `-type` included, and a negated test are taken as ones that select. A leading `-H`, `-L`, `-P`, `-D opts` or
  `-Olevel` does not hide the start points, and no start point is the current directory.
- `find .. -exec rmdir {} +`, `find ../repo -exec shred {} +`, `find ../repo -exec unlink {} \;` and `find ../repo -exec git worktree
  remove {} \;` were allowed (only a recursive rm behind find was refused); port: fixed (the program that find runs carries
  the find's start points and guard, and `rm`, `rmdir`, `unlink`, `shred` and `git worktree remove` are judged by them).
- `echo ../repo | xargs git worktree remove`, `xargs rmdir`, `xargs unlink`, `xargs shred` and the non-recursive `xargs rm` were
  allowed; port: fixed (the program that xargs runs carries the names of its standard input). The names are what the producer
  prints, evaluated: `echo` (with `-n`, `-e`, `-E`; a backslash without `-e` is read both ways, as bash and dash differ),
  `printf` (`%s`, `%b`, `%c`, `%d`, `%i`, `%u` and `%%` without flags, width or precision; the format is repeated for the arguments
  and its escapes are decoded, so `printf '../%s\n' repo` prints `../repo`), `yes`, `pwd`, `ls -d`, the body of a here-string or
  here-document, and the start points of a `find` that only prints them. The text is split the way xargs splits it: blanks and
  newlines (`-0` and `-d` change the separator, `-I` reads lines), quotes group and a backslash keeps the next character, so
  `echo '.\./repo' | xargs rmdir` names `../repo`. `cat`, `tee`, `sort`, `uniq`, `head`, `tail`, `tac` and `grep` pass the lines
  of their standard input on when their options keep to a short list (no byte modes, no `-o`, `-z`) and they name no file to read
  (`cat roots.list`, `sort file`, `grep pattern file` read the file, not the list: the list is then unreadable); a filter that
  selects lines can leave any line out, so each line is judged as a name of its own too. `env`, `nohup`, `nice`, `command`,
  `time`, `timeout` and the like in front of the producer are looked through. A program that rewrites a known list (`sed`, `tr`,
  `cut`, `head -c`, `grep -o`), a program that prints a path (`realpath`, `readlink`, `dirname`, `basename`, `stat`, `du`, `git
  rev-parse`, `git worktree`), a program that prints what its own text says (`awk`, `sed`, `perl`, `python`, a shell, `xargs`)
  and a find that formats its output make the list unreadable. A name that begins with `-` is an option to `rm`, `rmdir`,
  `unlink` and `shred` and is refused unless `--` stands before it.
- `xargs -I`, `-i` and `-iSTR` with names the reader proves read the template once for each name, with the replace string
  replaced in every word, in the text of a shell the template runs (`xargs -I{} sh -c 'rmdir ../{}'`) and in the program word
  itself, so the commands judged are the ones that run (`echo repo | xargs -I{} git worktree remove ../{}` removes `../repo`).
  With names the reader cannot read, a replace string in a word of `git` or `find`, or inside a word of `rm`, `rmdir`, `unlink`
  or `shred`, is refused (`ls | xargs -I{} rm ../{}`); the replace string as a whole word of a removal stays allowed
  (`ls | xargs -I{} rm {}`), as the issue allows `ls | xargs rm`.
- A shell that find or xargs runs (`sh -c`, `bash -c`) receives the operands as its positional parameters, not as operands of
  each command in its text: `echo ../repo | xargs sh -c 'rm build/old.o'` removes only what its text names and stays allowed,
  and `xargs sh -c 'rm "$@"' _` is judged with the names. A name the replace string puts in the text is judged where it stands.
  find substitutes `{}` in every word it runs, the text of a shell included, so a removal in that text with `{}` in a word is judged
  by find's start points and guard (`find ../repo -exec sh -c 'git worktree remove --force {}' \;`, `find .. -exec bash -c 'rm -rf {}' \;`,
  `find ../repo -exec sh -c 'rmdir {}' \;` are refused; `find ../repo -exec sh -c 'rm build/old.o' \;` has no `{}` and stays allowed).
  A text that holds `{}` (or the unread `-I` string) anywhere carries the wrapper's operands to every command in it, because `{}`
  can set the directory or a variable the rest uses: every removal in such a text is judged by find's start points, a `cd` to a word
  that holds the string leaves the directory unknown (`find .. -maxdepth 0 -exec sh -c 'cd {}; rm -rf repo' \;` moves to the slot
  and is refused), and the start points are judged from the directory find runs in as well as from the one the removal runs in. A
  word of a removal that find runs where `{}` stands after other text (`../{}`) or with a `..` component (`{}/../..`, `git -C {}/..`)
  names a path the start points do not bound, since `{}` is each path found at a depth the reader does not know, and is refused;
  `{}`, `./{}` and a suffix without `..` (`{}.tmp`) stay allowed.
- `git -C DIR worktree remove` behind xargs resolves the names from `DIR`.
- `echo "$X" | xargs rm`, `echo "$(cat list.txt)" | xargs rm` and `echo ~ | xargs rm` were allowed (the non-recursive rm was
  taken as file-only); port: fixed (an unknown name is unreadable and refused).
- `find ../repo -okdir rm -rf {} \;` is refused (the independent verifier); the same shape with `-ok` and `-execdir` and the
  recursive rm behind `find`, `xargs` and `parallel` stay refused as before (CRW-1028).
- The issue's allow controls stay allowed: `find build -delete`, `find . -type f -name '*.tmp' -exec rm {} +`,
  `find . -name '*.o' | xargs rm`, `git ls-files -z | xargs -0 rm` (with and without `-f`), `ls | xargs rm`, `xargs rm ./build`.
  `TestShellWriteBenignAccounting` over the 8020-command benign corpus counts the same (worktree gate allowed 5071, denied 878,
  unreadable 2071) before and after.

Known limits, kept on purpose:

- `parallel` is not modelled by the reader (CRW-1028): its program may come from its `:::` operands, so every `parallel` command
  is unreadable and refused in every gate, with or without a safe source (`echo ../repo | parallel rmdir` and `ls | parallel rm`
  alike). The issue asks for the `xargs` rules for `parallel` too; refusing all of it is stricter; port: kept.
- A recursive `rm` behind `xargs`, `find -exec` or `parallel` stays unreadable and refused even when the find start is inside the
  worktree and guarded (`find . -name x -exec rm -rf {} +`), because the reader cannot show what it removes; the non-recursive
  `rm` behind `find` with a test is allowed (the issue's control); port: kept (CRW-1028).
- A pipe producer that is not a plain command is refused when it feeds `xargs` a removal: a compound command, a subshell, a
  function, a shell or interpreter that runs further programs (`bash -c 'echo ../repo' | xargs rm`). A plain program that the
  text does not name the output of (`ls`, `git ls-files`, `cat list.txt`) names nothing and is allowed, as the issue asks for
  `ls` and `git ls-files`; `cat list.txt | xargs rm` is allowed while `xargs rm < list.txt` and `xargs -a list.txt rm` are refused
  (the issue lists `-a FILE` as unreadable); port: kept.
- A name with a glob (`echo ../re* | xargs rm`) is an unknown word to the reader and is refused.
- The directory the command runs in is the oracle's (a `cd` to an unrelated place moves what is protected along with it; the
  CRW-1028 known defect); an unknown directory (`cd "$X"`) makes a relative start or name an ancestor and refuses it.
- `find` as a producer lists its start points as the names; it does not see the files below them. `find . | xargs rm` names `.`, which
  the rule allows, and `find build | xargs rm` names a directory inside the worktree. A find that formats its output (`-printf`,
  `-ls`), runs a command, or reads its start points from a file (`-files0-from`) is unreadable as a producer.
- A name list of more than 512 candidates, or more than 64 names under `-I`, is refused for a removal.
