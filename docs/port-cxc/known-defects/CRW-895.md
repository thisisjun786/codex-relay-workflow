# CRW-895 — the worktree deletion guard does not judge find -delete, find -exec and xargs targets

Source: the CXC oracle `worktree-guard.ts` does not read `find` or `xargs` as a deletion command, so a deletion whose target
a find start point or standard input names passes (found by the CRW-726 second-generation verdict, 10-07, and re-checked on
dev 09e5c5bcc on 10-09). The port reads the command with the shared reader (`internal/pabcd/shellir`, CRW-1028); the verdict is
`internal/pabcd/hook/worktreedel_judge.go`. The tests that hold it are `internal/pabcd/hook/worktreedel_crw895_test.go`,
`internal/pabcd/shellir/feed_test.go` and the rows `CRW-895-*` in `internal/pabcd/hook/testdata/shellir/rows/18-crw-895.txt`
(indexed in `reproductions.tsv`), which give a verdict per gate for every shape.

Two items, both a security class that the oracle also allows:

- `find` with `-delete`, or with `-exec`, `-execdir`, `-ok` or `-okdir` running `rm`, `rmdir`, `unlink`, `shred` or
  `git worktree remove`, deleted the managed worktree when a start point named it (`find ../repo -delete`, `find .. -delete`,
  `find .. -exec rmdir {} +`, `find ../repo -exec git worktree remove {} \;`); port: fixed (security; the oracle also
  allowed it). The start points are judged: a start that resolves to an ancestor of the worktree (the slot root and
  everything above it) is refused whatever tests follow; a start that is the worktree itself (the checkout, the directory
  the command runs in, a directory between) is refused when no test stands before the action on every path that reaches it.
- `xargs` running `rm`, `rmdir`, `unlink`, `shred` or `git worktree remove` took its targets from standard input and deleted the
  managed worktree when the left of the pipe, a here-string or a here-document named it (`echo ../repo | xargs rm -rf`,
  `echo ../repo | xargs git worktree remove`, `echo ../repo | xargs rmdir`); port: fixed (security; the oracle also allowed
  it). A name that resolves to the worktree, its slot or an ancestor is refused when it is spelled other than `.`
  (`../repo`, an absolute path, `..`); a source the reader cannot read is refused (an unknown word such as `"$X"`, `$PWD`,
  `~` or a command substitution, `xargs -a FILE`, standard input from a file other than `/dev/null`, a producer the reader
  cannot trace).

Verdicts, as the issue and the 10-09 re-check and independent verification list them (before is dev 09e5c5bcc; the red
output is kept under `/state/crw/crw-895/evidence/`):

- `find . -name '*.o' -delete`, `find . -type f -delete`, `find . -newer x -delete`, `find ../repo -path '*/build/*' -delete`
  and `find {checkout} -name '*.o' -delete` were refused because `-delete` alone was judged; port: fixed (the issue's allow
  control: a start equal to the worktree with a test before the action is allowed). The tests are the primaries that
  test a file (`-name`, `-iname`, `-path`, `-regex`, `-type`, `-newer`, `-newerXY`, `-mtime`, `-size`, `-perm`, `-user`, `-empty`,
  and the rest of the GNU list); `-maxdepth`, `-mindepth`, `-prune`, `-print`, `-true` and an action are not tests. The
  expression is read as find reads it: `-o` and `,` start an alternative whose tests are its own, a parenthesised group
  guards an action after it only when every alternative of the group holds a test, and the operand of a primary
  (`-name -delete`) is not an action. A leading `-H`, `-L`, `-P`, `-D opts` or `-Olevel` does not hide the start points, and no
  start point is the current directory.
- `find .. -exec rmdir {} +`, `find ../repo -exec shred {} +`, `find ../repo -exec unlink {} \;` and `find ../repo -exec git worktree
  remove {} \;` were allowed (only a recursive rm behind find was refused); port: fixed (the program that find runs carries
  the find's start points and guard, and `rm`, `rmdir`, `unlink`, `shred` and `git worktree remove` are judged by them).
- `echo ../repo | xargs git worktree remove`, `xargs rmdir`, `xargs unlink`, `xargs shred` and the non-recursive `xargs rm` were
  allowed; port: fixed (the program that xargs runs carries the names of its standard input). The names are what `echo` and
  `printf` print (with the escapes printf and `echo -e` turn into separators), the body of a here-string or here-document,
  and the start points of a `find` that prints them; `cat`, `tee`, `sort`, `uniq`, `head`, `tail`, `tac` and `grep` pass the
  list of their standard input on, and `env`, `nohup`, `nice`, `command`, `time`, `timeout` and the like in front of the
  producer are looked through. A program that rewrites a known list (`sed`, `tr`, `cut`) makes it unreadable.
- `git -C DIR worktree remove` behind xargs resolves the names from `DIR`.
- `echo "$X" | xargs rm`, `echo "$(cat list.txt)" | xargs rm` and `echo ~ | xargs rm` were allowed (the non-recursive rm was
  taken as file-only); port: fixed (an unknown name is unreadable and refused).
- `find ../repo -okdir rm -rf {} \;` is refused (the independent verifier); the same shape with `-ok` and `-execdir` and the
  recursive rm behind `find`, `xargs` and `parallel` stay refused as before (CRW-1028).
- The issue's allow controls stay allowed: `find build -delete`, `find . -type f -name '*.tmp' -exec rm {} +`,
  `find . -name '*.o' | xargs rm`, `git ls-files -z | xargs -0 rm` (with and without `-f`), `ls | xargs rm`, `xargs rm ./build`.
  `TestShellWriteBenignAccounting` over the 8020-command benign corpus counts the same (worktree gate allowed 5071, denied 878,
  unreadable 2071) before and after.

Known limits, kept on purpose:

- `parallel` is not modelled by the reader (CRW-1028): its program may come from its `:::` operands, so every `parallel` command
  is unreadable and refused in every gate, with or without a safe source (`echo ../repo | parallel rmdir` and `ls | parallel rm`
  alike). The issue asks for the `xargs` rules for `parallel` too; refusing all of it is stricter; port: kept.
- A recursive `rm` behind `xargs`, `find -exec` or `parallel` stays unreadable and refused even when the find start is inside the
  worktree and guarded (`find . -name x -exec rm -rf {} +`), because the reader cannot show what it removes; the non-recursive
  `rm` behind `find` with a test is allowed (the issue's control); port: kept (CRW-1028).
- A pipe producer that is not a plain command is refused when it feeds `xargs` a removal: a compound command, a subshell, a
  function, a shell or interpreter that runs further programs (`bash -c 'echo ../repo' | xargs rm`). A plain program that the
  text does not name the output of (`ls`, `git ls-files`, `cat list.txt`) names nothing and is allowed, as the issue asks for
  `ls` and `git ls-files`; `cat list.txt | xargs rm` is allowed while `xargs rm < list.txt` and `xargs -a list.txt rm` are refused
  (the issue lists `-a FILE` as unreadable); port: kept.
- A name with a glob (`echo ../re* | xargs rm`) is an unknown word to the reader and is refused.
- The directory the command runs in is the oracle's (a `cd` to an unrelated place moves what is protected along with it; the
  CRW-1028 known defect); an unknown directory (`cd "$X"`) makes a relative start or name an ancestor and refuses it.
- `find` as a producer lists its start points as the names; it does not see the files below them. `find . | xargs rm` names `.`, which
  the rule allows, and `find build | xargs rm` names a directory inside the worktree.
