# CRW-1369 — the lane-lab tests read the caller's host memory threshold variables

Source: CRW's own lane lab (CRW-1277), not the CXC oracle (CXC v0.2.40, commit 3c1459ac): the oracle has no host memory bound for its scheduler's releases and no lab over it. The Go side is `internal/flow/cli/lanelab_test.go` (`newLaneLab`, `TestLaneLabIgnoresTheCallersHostThresholds`); the bound is `internal/relay/dagsched/hostmemory.go` (`HostMemoryFromEnvironment`), unchanged. Follow-up of CRW-1295.md, whose lab pinned the proc root only.

- `newLaneLab` set `CRW_DAG_HOST_PROC_ROOT` to a fixture but left `CRW_DAG_HOST_MIN_AVAILABLE_GIB`, `CRW_DAG_HOST_MAX_SWAP_PERCENT`, `CRW_DAG_HOST_MAX_PRESSURE_SOME_AVG60` and `CRW_DAG_HOST_MAX_PRESSURE_FULL_AVG10` to the caller's process environment, which `HostMemoryFromEnvironment` reads: a caller that exported `CRW_DAG_HOST_MIN_AVAILABLE_GIB=100` made the 64 GiB fixture short and every lab release `defer:host_memory`, and a value that is not a number failed the lab tests; port: fixed (`newLaneLab` sets the four variables to the empty string with `t.Setenv`, which the bound reads as unset, so the fixture is judged by the defaults whatever the caller exported; `dagsched/hostmemory.go` and the lane code are unchanged. Pinned by `TestLaneLabIgnoresTheCallersHostThresholds`, which exports a 100 GiB floor and a non-numeric value for each of the four variables before the lab is made and releases A-1; red on the earlier lab for all five cases. `TestBuildLaneAppliesTheHostMemoryBound` passes its own environment and is unchanged).
