- Supersedes known-defects.md, section "CRW-529 dispatch ledger library", item beginning "A created report is accepted before spawn issuance": now port: fixed (at the checked boundary a created report needs the attempt's recorded issuance; without it the report is refused and nothing is written, unless the caller takes the explicit reconciliation path below. The parity ledger `RunDispatch` keeps the oracle answer. Pinned by `TestDispatchReceiptCreatedRequiresIssuance`).
- Supersedes known-defects.md, section "CRW-529 dispatch ledger library", item beginning "Stored status validation coerces values to strings": now port: fixed (a stored dispatch or attempt status must be a literal enum string; a singleton array or an object is "invalid dispatch status" or "invalid attempt status" and the record is not rewritten. The recorded corpus cases `coerced dispatch status` and `coerced attempt status` of `internal/role/testdata/dispatch/oracle.json` are replayed as intentionally changed by `TestDispatchLedgerOracle`, and the `status coercion error` case of `TestDispatchLedgerStoredValidation` now expects the invalid status. Pinned by `TestDispatchReceiptStatusIsALiteralString`).
- Supersedes known-defects.md, section "Found by the CRW-574 created-check fix for archived children", item beginning "The created check proves a real child of this session": now port: fixed (the created check of an issued attempt ties the child to the issued native call by the host's own result of that call: the parent session's rollout, whose path the native database's `rollout_path` holds, records each collaboration tool call as an item of type `CollabAgentToolCall` whose `id` is the call's tool use id, the id the spawn hook received and recorded as `toolUseId`, and its `item_completed` event names the threads the call created in `receiver_thread_ids` (`createdCheckSpawnResult`). A completed result naming the reported `agentId` ties it (receipt correlation `spawn-result`); a completed result naming another child, or a failed call, refuses the report and writes nothing; no readable result (no tool use id, no parent row or rollout, the call not yet in it, a host that writes no such item) leaves the child `unverified`, which is recorded and waited on but cannot complete an independent review until a later created report ties it. The child's first user message (`first_user_message`) and the dispatch marker in it only refuse: a first message that carries no marker of this attempt refuses, and so does a child the spawn hook already saw with the attempt's marker when it issued the attempt (`IssueManagedSpawnEnv` records those as `priorChildren`, omitted when empty so the record stays the oracle's). The marker never ties a child, because the caller writes it into the call's message and a child made before the issuance or by another call (hook off) can carry it; an issuance that could not observe the host (the public `IssueManagedSpawn` without an environment, an older record, a host without a readable database) records nothing and so only loses that early refusal, never gains a tie. The created check reads the database and the rollout without the App Server, so the database-only path of CRW-653 keeps working. Pinned by `TestDispatchReceiptCorrelatesTheIssuedChild`, `TestDispatchReceiptOnlyTheIssuedCallsResultTiesTheChild`, `TestDispatchReceiptUnobservedIssuanceCannotProveAnOldChild`, `TestDispatchReceiptMarkerAloneDoesNotProveTheIssuedCall`, `TestDispatchReceiptUnverifiedChildCannotCompleteAReview` and, through the spawn hook's own issuance, `TestSpawnHookManagedIssuanceTiesOnlyTheCallsResult`).
- A created report names nothing of the native call, so a report could carry an arbitrary agent for an issued attempt whose recorded `toolUseId` belongs to another call (source `fallback-dispatch.ts:171-176`, which reads no tool id); port: fixed (a created report that names `toolUseId` must name the one the spawn hook recorded, else it is refused; a replay of the same report is idempotent and writes the same bytes, and a receipt already `spawn-result` for that child is kept as recorded when the host later shows less (the call's result, the first message or settings no longer visible), so the replay never weakens it. Pinned by `TestDispatchReceiptCorrelatesTheIssuedChild` and `TestDispatchReceiptReplayKeepsAConfirmedReceipt`).
- The ledger keeps the requested candidate, the issuance flag and the caller's `observedModel` as unrelated fields, so the record cannot tell what was requested, what was issued, which child the host witnessed and what the host shows from what the caller claims (source `fallback-dispatch.ts:171-176`); port: fixed (an accepted created report writes one `receipt` on the attempt: the candidate pair, the issuance with its tool id, the child with its parent and the witnessing host surface, the correlation (`spawn-result`, `unverified` or `unissued`), the caller's `observedModel` kept as a claim, and the model and effort the native thread row shows, or `unobservable`. Issuance is never read as provider or model proof).
- A child spawned while the spawn hook was off has no issuance and could only be adopted silently or left unrecorded (source `fallback-dispatch.ts:171-176`); port: fixed (a created report of an unissued attempt that carries `reconciliation` evidence records the real child of this session with receipt correlation `unissued`; nothing is deleted or spawned again, and such a child cannot complete an independent review (`createdCheckComplete` refuses a reviewer's complete whose receipt is not `spawn-result`). Pinned by `TestDispatchReceiptUnissuedChildIsReconciled`).
- The recorded fixture `cli__subagents__dispatch_created_complete` claimed by CRW-530 moves to this issue's notes file: its created step is now the issuance refusal, which precedes the host read.
