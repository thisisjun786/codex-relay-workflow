# CRW-783 — GitHub post guard

Source: CRW's own protection, no oracle. No CXC v0.2.40 (commit 3c1459ac) behaviour is recorded here,
because the guard is not a port. At 11:06 KST on 2026-10-06 a child of another project posted review
replies whose text it had placed inside a double-quoted shell command string, zsh ran the backticks as
commands, and a backticked word printed every shell variable into a public comment. The same unsafe
posting shape occurred three times in children's records between 10-03 and 10-06. The guard is a
PreToolUse leg of this repository's own runtime (`internal/pabcd/hook/githubpost.go`,
`internal/pabcd/hook/githubpost_scan.go`), registered as one row in `cmd/crw/component_hooks.go`, and
there is nothing in the oracle to keep or fix.

## Shapes the guard could not see, fixed here

An independent audit pass over the first head found six of these, and the pull request's one Codex
review then found ten more. All but the last were real, and each is fixed with its own red-first case:

- a title or body field after a clean `-F`/`--body-file`/`--input` was never judged, because `flags` and
  `api` returned on the first recognized option (`gh pr create -F body.md -t "Release $X"`); port: fixed.
- a gh post inside a command substitution in the outer text was neither split nor denied
  (`X=$(gh pr comment 1 -b "$TOKEN")`); port: fixed (the fail-closed rule covers the segment).
- the quoted heredoc body was taken from anywhere in the text, so an unrelated heredoc satisfied
  `--body-file -` and the posted text was never scanned; port: fixed (a heredoc belongs to the command
  line that introduces it, and every heredoc of that line is read, in the operators' order).
- single-quoted text was scanned as if unquoted, so a single-quoted title holding a dollar or a backtick
  was denied; port: fixed (the single-quote mode is entered, as the rule is an expansion outside single
  quotes).
- only the shellwrite reader's own wrapper list was stripped, so a post behind a runner prefix
  (`timeout`, `nice`, `nohup`, `X=1`) hid from the guard; port: fixed (the wrappers that run the rest of
  the line are stripped with their own options, option values and numbers).
- `--` did not end the options, so a word after it was read as a body flag (`gh pr comment 1 -- -b
  plain`); port: fixed (everything after the separator is an operand).
- a post wrapped in grouping or control words (`(gh pr comment 1 -b "$TOKEN")`, `{ gh ...; }`, `! gh
  ...`) was not recognised as a gh command; port: fixed (the grouping words are stripped).
- a body file the same command line rewrites (`printf x > body.md && gh pr comment 1 --body-file
  body.md`) was scanned before the shell overwrote it; port: fixed (a file the same line writes is
  refused as unreadable, reusing the shellwrite reader's destinations).
- a wrapper option's argument was read as the command (`env -u OLD gh ...`, `sudo -u root gh ...`);
  port: fixed (each wrapper's value-taking options are consumed with their value).
- the built-in create aliases `gh pr new` and `gh issue new` were not targets; port: fixed.
- a nested API key (`-F input[body]=...`) was not read as the body field; port: fixed (the terminal
  field of the key decides).
- `--fill`, `--fill-first`, `--fill-verbose` and `--template` post text the guard cannot inspect;
  port: fixed (denied as unreadable-github-post).
- a special parameter (`$1`, `$@`, `$?`, `$$`) was not read as an expansion; port: fixed.
- the recursion depth was spent by sibling programs rather than by nesting, so eight harmless `sh -c`
  segments exhausted it before a posting program; port: fixed (a copy of the scanner is decremented).

The tenth finding — that the row is not declared on the activation surface, so the guard does not run
until the switch is turned on — is not a defect of this change: the issue fixes the activation surface as
out of scope for this run and states that no hook JSON is added, and a separate issue carries this row.

## Accepted over-blocking

These are the guard's own judgements, stricter than the incident requires. They are kept because the cost
of the stricter judgement is a rewritten command and the cost of the looser one is a public secret:

- a title holding a key-shaped string is denied even when it is not a credential; port: kept (the scan
  reports only the rule and the place, so the author can rewrite the title, and telling a live key from a
  quotation cannot be done from the text alone).
- an inline body is denied whatever its text, including one that is plainly safe or fully single-quoted
  (`inline`, rule `inline-github-body`); port: kept (the issue fixes this as the rule, not as a
  heuristic: the fix for the incident is that GitHub-bound text never travels inside a shell string).
- `--body-file -` is denied unless the same command line carries a quoted heredoc the guard can read
  (`file`); port: kept (the guard cannot see what a pipeline before it would write, and an unquoted
  heredoc is expanded by the shell, so neither can be scanned).
- text the guard cannot split (an unbalanced quote) is denied when it mentions `gh` beside `pr`, `issue`
  or `api`, which a mention in a comment or a search pattern can do (`text`, rule
  `unreadable-github-post`); port: kept (the issue fixes fail-closed as the rule, and the reason names
  the rule so the author can requote).
- a `bash -c` or `eval` program holding a command substitution and mentioning `gh` beside `pr`, `issue`
  or `api` is denied even when the substitution is unrelated (`command`); port: kept (what the
  substitution produces is invisible, so a text the guard cannot read is refused rather than passed).
- `-F body=` and `--field body=` are judged as an inline body when the value does not start with `@`
  (`api`); port: kept (the issue fixes this shape; `-F body=@F` remains the way to pass a file).
- the target set is exactly the issue's: `gh` with `pr create|edit|comment|review`, `issue
  create|comment|edit`, or `api` with a body or title field. Other GitHub surfaces that publish text
  pass unguarded — `gh release create --notes`, `gh pr merge --subject` or `--body`, `gh issue close
  --comment`, `gh gist create`, `gh repo edit --description`; port: kept (the boundary is the issue's
  own list, and widening it is a scope decision for a later issue).
