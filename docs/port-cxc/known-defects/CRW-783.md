# CRW-783 — GitHub post guard

Source: CRW's own protection, no oracle. No CXC v0.2.40 (commit 3c1459ac) behaviour is recorded here,
because the guard is not a port. At 11:06 KST on 2026-10-06 a child of another project posted review
replies whose text it had placed inside a double-quoted shell command string, zsh ran the backticks as
commands, and a backticked word printed every shell variable into a public comment. The same unsafe
posting shape occurred three times in children's records between 10-03 and 10-06. The guard is a
PreToolUse leg of this repository's own runtime (`internal/pabcd/hook/githubpost.go`,
`internal/pabcd/hook/githubpost_scan.go`), registered as one row in `cmd/crw/component_hooks.go`, and
there is nothing in the oracle to keep or fix.

## Shapes the guard could not see, fixed here

An independent audit pass over the first head found six of these, and the pull request's one Codex
review then found ten more. All but the last were real, and each is fixed with its own red-first case:

- a title or body field after a clean `-F`/`--body-file`/`--input` was never judged, because `flags` and
  `api` returned on the first recognized option (`gh pr create -F body.md -t "Release $X"`); port: fixed.
- a gh post inside a command substitution in the outer text was neither split nor denied
  (`X=$(gh pr comment 1 -b "$TOKEN")`); port: fixed (the fail-closed rule covers the segment).
- the quoted heredoc body was taken from anywhere in the text, so an unrelated heredoc satisfied
  `--body-file -` and the posted text was never scanned; port: fixed (a heredoc belongs to the command
  line that introduces it, and every heredoc of that line is read, in the operators' order).
- single-quoted text was scanned as if unquoted, so a single-quoted title holding a dollar or a backtick
  was denied; port: fixed (the single-quote mode is entered, as the rule is an expansion outside single
  quotes).
- only the shellwrite reader's own wrapper list was stripped, so a post behind a runner prefix
  (`timeout`, `nice`, `nohup`, `X=1`) hid from the guard; port: fixed (the wrappers that run the rest of
  the line are stripped with their own options, option values and numbers).
- `--` did not end the options, so a word after it was read as a body flag (`gh pr comment 1 -- -b
  plain`); port: fixed (everything after the separator is an operand).
- a post wrapped in grouping or control words (`(gh pr comment 1 -b "$TOKEN")`, `{ gh ...; }`, `! gh
  ...`) was not recognised as a gh command; port: fixed (the grouping words are stripped).
- a body file the same command line rewrites (`printf x > body.md && gh pr comment 1 --body-file
  body.md`) was scanned before the shell overwrote it; port: fixed (a file the same line writes is
  refused as unreadable, reusing the shellwrite reader's destinations).
- a wrapper option's argument was read as the command (`env -u OLD gh ...`, `sudo -u root gh ...`);
  port: fixed (each wrapper's value-taking options are consumed with their value).
- the built-in create aliases `gh pr new` and `gh issue new` were not targets; port: fixed.
- a nested API key (`-F input[body]=...`) was not read as the body field; port: fixed (the terminal
  field of the key decides).
- `--fill`, `--fill-first`, `--fill-verbose` and `--template` post text the guard cannot inspect;
  port: fixed (denied as unreadable-github-post).
- a special parameter (`$1`, `$@`, `$?`, `$$`) was not read as an expansion; port: fixed.
- the recursion depth was spent by sibling programs rather than by nesting, so eight harmless `sh -c`
  segments exhausted it before a posting program; port: fixed (a copy of the scanner is decremented).

The tenth finding — that the row is not declared on the activation surface, so the guard does not run
until the switch is turned on — is not a defect of this change: the issue fixes the activation surface as
out of scope for this run and states that no hook JSON is added, and a separate issue carries this row.

## Quoting forms the failure-class audit found unread, fixed here

The management failure-class audit of 2026-10-06 (class 7, shell and program readers, and class 8, fail
open) was run against the head before the handoff. It found five shapes a shell or an interpreter accepts
that the guard read past, each of which let a post through unjudged. Every one is fixed with its own
red-first case, and the reading now refuses what it cannot read instead of passing it:

- a here-string (<<<) was read as a heredoc operator, so its word satisfied a later --body-file - and
  the posted text was never scanned (tee /dev/stderr <<< 'x' | gh pr comment 1 -F -); port: fixed (a
  here-string is skipped as a word, so the file stays unreadable and the post is denied).
- a program read from standard input, which is the quoted heredoc that feeds a shell with no -c
  (bash <<'EOF' ... EOF), was never read; port: fixed (the shell's own line's first quoted heredoc is
  its program and is read one level down).
- env --split-string / env -S carries a whole command line env splits and runs, and the guard read it
  as an ordinary word; port: fixed (its value is read as a program text).
- su --command / su -c, with the value separate, attached or inside a bundle, runs the target user's
  shell and was read as an ordinary command; port: fixed (its value is read as a program text).
- a one-line program in a language the guard cannot read (python -c, node -e and -p, perl, ruby, lua,
  php -r, awk's program operand) that names a post was passed; port: fixed (it is denied as
  unreadable-github-post, because its text never goes through the shell reader).
- the recursion depth bound was a pass: a text nested deeper than the guard reads was allowed because
  the budget ran out; port: fixed (a program the guard can no longer read is refused when it names a
  post, and one that names none is still nothing to judge).

## Accepted over-blocking

These are the guard's own judgements, stricter than the incident requires. They are kept because the cost
of the stricter judgement is a rewritten command and the cost of the looser one is a public secret:

- a title holding a key-shaped string is denied even when it is not a credential; port: kept (the scan
  reports only the rule and the place, so the author can rewrite the title, and telling a live key from a
  quotation cannot be done from the text alone).
- an inline body is denied whatever its text, including one that is plainly safe or fully single-quoted
  (`inline`, rule `inline-github-body`); port: kept (the issue fixes this as the rule, not as a
  heuristic: the fix for the incident is that GitHub-bound text never travels inside a shell string).
- `--body-file -` is denied unless the same command line carries a quoted heredoc the guard can read
  (`file`); port: kept (the guard cannot see what a pipeline before it would write, and an unquoted
  heredoc is expanded by the shell, so neither can be scanned).
- text the guard cannot split (an unbalanced quote) is denied when it mentions `gh` beside `pr`, `issue`
  or `api`, which a mention in a comment or a search pattern can do (`text`, rule
  `unreadable-github-post`); port: kept (the issue fixes fail-closed as the rule, and the reason names
  the rule so the author can requote).
- a `bash -c` or `eval` program holding a command substitution and mentioning `gh` beside `pr`, `issue`
  or `api` is denied even when the substitution is unrelated (`command`); port: kept (what the
  substitution produces is invisible, so a text the guard cannot read is refused rather than passed).
- `-F body=` and `--field body=` are judged as an inline body when the value does not start with `@`
  (`api`); port: kept (the issue fixes this shape; `-F body=@F` remains the way to pass a file).
- a text that combines a command word the shell would expand with a read-only `gh` command
  (`$EDITOR notes.md && gh pr view 1`) is denied too, because the fail-closed test reads the whole
  command text and cannot tell a read-only `gh pr view` from a posting one (`command`); port: kept (the
  same fail-closed rule the correction generation 2 fixed; a text that names no post still passes, and
  the guard's own target test leaves `gh pr view|list|checks|diff` alone when no expansion is involved).
- the target set is exactly the issue's: `gh` with `pr create|edit|comment|review`, `issue
  create|comment|edit`, or `api` with a body or title field. Other GitHub surfaces that publish text
  pass unguarded — `gh release create --notes`, `gh pr merge --subject` or `--body`, `gh issue close
  --comment`, `gh gist create`, `gh repo edit --description`; port: kept (the boundary is the issue's
  own list, and widening it is a scope decision for a later issue).
- a command name that reaches the shell only through the environment of an earlier tool call (an alias,
  a function or a variable exported by a previous Bash call) is outside what one command text can show:
  the guard reads one PreToolUse payload's own text, so a name it cannot see is neither judged nor
  refused; port: kept (the boundary is the unit the guard is given, and a session-level rule would need
  a state the PreToolUse payload does not carry).
- the exact body-file identity reading is out of this issue: the guard refuses a body file any part of
  the command text may have written, rather than resolving which bytes gh would read (a shell program
  read from a file, `bash post.sh` or `source post.sh`, is the same class: the file's text is not in the
  payload); port: pending (CRW-875, blocked by this issue, carries the exact identity reading and shell
  programs read from a file).

## The correction generation 2 found, fixed here

The parent's ruling on the first handoff (failure class 7, fail-open in a security guard) found one more
shape: a simple command whose command word the shell would expand was passed unjudged, because the guard
read the word as written and compared it with gh. A command word holding an expansion after quote
removal ($NAME, ${...}, $(...) or a backtick) names a command the guard cannot read, so the text it
runs is now judged as unreadable-github-post against the whole command text being judged (the segment
alone may not hold the word gh the fail-closed test needs):

- a command word holding an expansion (G=gh; $G pr comment 1 --body x, GH=gh; "$GH" api ... -F
  body=@f, ${GH} pr comment 1 --body x, a backticked command word, and one behind a wrapper such as
  sudo $G) was passed unjudged; port: fixed (a command word that holds an expansion after quote removal
  is refused as unreadable when the text names a post, and a text that names none still passes).
- a command the guard cannot read whole to the end was passed: a loop (for, while, until, select), a
  conditional (if, case), a function definition (name() {, function name {), a background job (&), a
  subshell or brace group, an and/or list, source or a dot script, eval, an inner shell (bash -c and
  every other place that runs a shell), and a command name built from a variable or a substitution;
  port: fixed (the command is read after those words, at a lone & each part is judged on its own, and a
  part that cannot be decomposed into judged commands is refused, so a post inside it is never passed).
- a body file an earlier line of the same command writes or changes (a redirection, tee, cp, mv, sed -i
  or any other destination the shell-write reader reads) was scanned from its pre-run bytes, so a post
  could carry text the guard never saw; port: fixed (the write destinations of every line are read
  before the line is judged, and a body file any part of the command text writes is refused).
- a command whose verb the guard does not read was passed when its text named a post: a wrapper's
  duration word the guard could not read (timeout 30s), a command that runs its arguments (ssh, watch,
  parallel), and any unknown program; port: fixed (the wrapper reads timeout's duration word with its
  optional s, m, h or d suffix and exec joins the wrappers, and a simple command that is not gh, not a
  find -exec, and not a program the guard reads one level down is refused as unreadable-github-post
  when its text names a post, unless its verb is on the allow list of commands that never run their
  arguments: echo, printf, true, false, :, test, [, ls, cat, head, tail, wc, grep, egrep, fgrep, rg,
  and git for its reading subcommands with no -c, --config or alias word).
- a process substitution (`<(...)`, `>(...)`) counted only in the command-text check, so a part holding
  one that named a post was never judged; port: fixed (a process substitution counts like a command
  substitution when the part-level check reads it, so cat <(gh pr comment 1 -b plain), source <(echo
  'gh pr comment 1 -b plain') and bash < <(gh pr comment 1 -b plain) are denied).
- a body file written through a spelling the old test did not compare (`> "$PWD/body.md"`, an absolute
  path, another directory's file with the same last element, or any write after a cd) was scanned from
  its pre-run bytes; port: fixed conservatively (a relative name is refused when any part writes a
  destination with the same last path element, or a destination holding an expansion, or when a part
  changes directory; an absolute name is refused for a destination that holds an expansion or cleans to
  the same path).
