# CRW-783 — GitHub post guard

Source: CRW's own protection, no oracle. No CXC v0.2.40 (commit 3c1459ac) behaviour is recorded here,
because the guard is not a port. At 11:06 KST on 2026-10-06 a child of another project posted review
replies whose text it had placed inside a double-quoted shell command string, zsh ran the backticks as
commands, and a backticked word printed every shell variable into a public comment. The same unsafe
posting shape occurred three times in children's records between 10-03 and 10-06. The guard is a
PreToolUse leg of this repository's own runtime (`internal/pabcd/hook/githubpost.go`,
`internal/pabcd/hook/githubpost_scan.go`), registered as one row in `cmd/crw/component_hooks.go`, and
there is nothing in the oracle to keep or fix.

The defects recorded here are therefore the guard's own accepted over-blocking: a judgement stricter
than the incident requires, kept because the cost of the stricter judgement is a rewritten command and
the cost of the looser one is a public secret.

An independent audit pass over the first head also found six shapes in which a real GitHub post reached
gh unjudged, or a passing command was refused. Each was fixed in this issue, with its own red-first case
(the guards are named as they stand now):

- `flags` and `api` returned on the first recognized option, so a title or body field after a clean
  `-F`/`--body-file`/`--input` was never judged (`gh pr create -F body.md -t "Release $X"`); port:
  fixed (every option is read, and the first denial is the one reported).
- A gh post inside a command substitution in the outer text was neither split nor denied
  (`X=$(gh pr comment 1 -b "$TOKEN")`); port: fixed (a segment holding a substitution the guard cannot
  read is judged by the fail-closed rule).
- The quoted heredoc body was taken from anywhere in the text, so an unrelated heredoc satisfied
  `--body-file -` and the posted text was never scanned; port: fixed (a heredoc body belongs to the
  command line that introduces it).
- Single-quoted text was scanned as if unquoted, so a single-quoted title holding a dollar or a backtick
  was denied; port: fixed (the single-quote mode is entered, as the rule is an expansion outside single
  quotes).
- Only the shellwrite reader's own wrapper list was stripped, so a post behind a runner prefix
  (`timeout`, `nice`, `nohup`, `X=1`) hid from the guard; port: fixed (the wrappers that run the
  rest of the line are stripped with their own options and numbers).
- `--` did not end the options, so a word after it was read as a body flag
  (`gh pr comment 1 -- -b plain`); port: fixed (everything after the separator is an operand).

- A title that holds a key-shaped string is denied even when it is not a credential (any text matching
  the key prefixes or the `NAME=value` shape of `githubpost_scan.go`, scanned by
  `githubPostInlineSite`); port: kept (the scan reports only the rule and the place, so the author sees
  where to look and can rewrite the title; telling a live key from a quotation cannot be done from the
  text alone, and the cost is not symmetric).
- An inline body is denied whatever its text, including one that is plainly safe and one that is fully
  single-quoted (`githubPostInlineSite`, rule `inline-github-body`); port: kept (the issue fixes this as
  the rule rather than as a heuristic: the fix for the incident is that GitHub-bound text never travels
  inside a shell command string, so there is no text for which the rule is unnecessary).
- `--body-file -` is denied unless the same command carries a quoted heredoc whose body the guard can
  read (`githubPostFileSite`); port: kept (the guard cannot see what the pipeline before it would write,
  and an unquoted heredoc is expanded by the shell, so neither can be scanned; the reason names the place
  `command` because there is no file to name).
- Text the guard cannot split (an unbalanced quote) is denied when it mentions `gh` beside `pr`, `issue`
  or `api`, which a mere mention in a comment or a search pattern can do (`githubPostTextSite`, rule
  `unreadable-github-post`); port: kept (the issue fixes fail-closed as the rule; the shape that reaches
  it is a command the guard could not read at all, and the reason names the rule so the author can
  requote).
- A `bash -c` or `eval` program that holds a command substitution and mentions `gh` beside `pr`, `issue`
  or `api` is denied even when the substitution is unrelated to the post (`githubPostProgramSite`);
  port: kept (what the substitution produces is invisible to the guard, so a text it cannot read is
  refused rather than passed; the shape is rare because the guard reads the program directly whenever
  the shell text spells it out).
- `-F body=` and `--field body=` are judged as an inline body when the value does not start with `@`,
  including a value that is empty or that the caller intended as a literal path (`githubPostAPISite`);
  port: kept (the issue fixes this shape; `-F body=@F` remains the way to pass a file, and the reason
  states it).
- The target set is exactly the issue's: `gh` with `pr create|edit|comment|review`, `issue
  create|comment|edit`, or `api` with a body or title field. Other GitHub surfaces that also publish
  text are outside it and pass unguarded — `gh release create --notes`, `gh pr merge --subject` or
  `--body`, `gh issue close --comment`, `gh gist create`, `gh repo edit --description` — so a
  secret placed in one of them is not stopped; port: kept (the boundary is the issue's own list, and
  widening it is a scope decision for a later issue rather than for this one).
