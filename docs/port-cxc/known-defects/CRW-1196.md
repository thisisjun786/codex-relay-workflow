# CRW-1196 — the LEAF sentence and the spawn grant on an engine thread

Source: CRW's own design (0.5.0-alpha, issue F02), not the CXC oracle: the flow engine has no counterpart in CXC v0.2.40 (commit 3c1459ac). The CXC side is the four role definitions the port keeps byte for byte in `internal/role/agents/architect.toml`, `executor.toml`, `explorer.toml` and `reviewer.toml` (CRW-365), pinned to their cut by `TestEmbeddedAgentsUnchanged` in `internal/flow/roles/roles_test.go`. The Go side is `internal/flow/roles/` (the overlays `<role>.md` and `Prompt`), `internal/bridge/execution/agentroles.go` (the `agent-roles` and `agent-aliases` sections of the execution policy) and `internal/flow/engine/policy.go` (`PolicyFromExecution`).

- The CXC role definitions forbid every native spawn: "You are a LEAF agent: do NOT spawn sub-agents ... the spawn-attach hook DENIES recursive spawns unless your dispatcher's task message contains CRW-SUBSPAWN-ALLOWED" (`executor.toml` line 13, `reviewer.toml` line 14, `explorer.toml` line 15; the architect definition has no such sentence). An engine thread is a root thread with its own cwd, where that sentence is wrong in two ways: it forbids the one explorer helper the spawn policy allows (SP-NAT-1: one for `executor`, `executor-t1`, `architect`, `reviewer` and `reviewer-final`, none for `explorer` and the QA capture call), and it names a grant that mints nothing on a flow-bound thread; port: kept (the definitions stay unchanged and `internal/flow/roles/<role>.md` is appended after them. The overlay names the sentence by its opening words, says that for this engine call it does not apply, and states the helper count and the `explorer` type that apply instead, plus that `CRW-SUBSPAWN-ALLOWED` has no effect. The count is enforced by the spawn hook (F14) through the run's binding, not by this text. Pinned by `TestOverlayReplacesLeafSentence`).
- The QA procedure of `crw-qa` section 5 (`Reviewer passes`) has the executor dispatch two parallel read-only reviewer passes with `spawn_agent`; on the flow path a QA capture call that did so would be a second native spawn the hook refuses; port: kept (the QA overlay `executor-qa.md` tells the call not to start the passes and to list its captures in the receipt field `captures`; the run starts the two passes itself (SP-QA-2) from that list. Pinned by `TestQAOverlayForbidsOracleSpawn`. The receipt schema that carries `captures` belongs to the final-gate issue).
- The execution policy refuses a key it does not know and lists the keys it supports; the oracle's list is `allowed`, `exceptions` and `roles`. The list now also names `agent-aliases` and `agent-roles`, the CRW sections of this issue, so a file with a stray key is told the truth about what the reader accepts; port: fixed (`internal/bridge/execution/policy.go`; the three goldens of `TestLaunchPolicy_resolution_is_pythons_for_every_declaration` in `internal/relay/service/testdata/golden` were recorded from the Python answer and are rewritten with `CRW_GOLDEN=update`, the Python implementation having left the repository with todo 44).
- The `schema` of a Claude workflow script is the schema the model is asked to answer in, and none of the real scripts of this host states `additionalProperties: false` or lists every property in `required`; the engine refuses such a call (`schema_not_strict`) before any thread starts, whatever its role. In the parity corpus (`testdata/flow/parity/real-*`, original bytes) every call that carries a schema is therefore recorded as refused with that reason and with the role, sandbox and requested pair it resolved to, and the scripts that loop on the verdict of such a call or nest a workflow behind it do not reach those branches on the fake backend; port: deviation, kept visible (the golden records the refusal and `TestParityCorpus` accepts no other refusal for a real original; the loop and the nested workflow are covered by the written reductions beside them. The real build→verify→fix original, `real-security-build-verify-fix`, stops at its schema-bearing build in the same way, so its `agentType: 'ocx-gpt-6-1-sol'` verification step is resolved from the original's own options by `TestParityCorpusRoles` (role `reviewer`, the requested effort `high` kept apart from the policy pair) rather than observed on a run, and the completed form of the loop is the reduction `build-verify-fix`. Whether a Claude schema is normalised to a strict one or the script author is told to write one belongs to the engine's schema rules, not to this issue).
- A Claude script that builds or fixes with `model: 'opus'` edits the checkout it runs in, but the alias table sends `opus` to `architect`, whose thread is read-only; a port that adds only `isolation` or `agentType` keys cannot give such a call a write cwd; port: kept (the corpus holds no real original that builds on `opus` among the calls it runs on the fake backend (the fix rounds after the first of `real-security-build-verify-fix` are on `opus` and are not reached), and a build that falls to a read-only role fails `TestParityCorpus`; an opus build in a script is a script change, as the alias table is designed).
- `crw flow lint` (CRW's own, no CXC counterpart) after its pre-merge evaluation: the static rules read the script body without the names its header imports, so an import named like an engine global (`import { now as Date } ...`) was judged as the global; a `break` or `continue` with a label always went to the nearest loop; and a lifecycle call counted as complete where it was invoked, so `crw.review(...)` without `await` let `crw.land` follow. The body is now analysed with the imported names declared (`script.Program.Imports`, declared on the wrapper's first line so no line moves), labels name the loop, switch or statement they label (through `finally`), and a lifecycle call completes only where its promise is awaited, returned or read; port: fixed (`TestLintImportedNamesAreScriptBindings`, `TestLintLabeledJumps`, `TestLintLifecycleCompletionNeedsTheAwait`). A promise passed to another function or collected in a container counts as read, because the text cannot show it unread. The post-evaluation of that correction found the completion rule only looked at a call that was a whole statement (or its `void`), so `const x = void crw.review(...)`, `(crw.review(...), 1)` and `await void crw.review(...)` still counted as reviews, an awaited assignment `await (p = crw.review(...))` and a read through `{ p }` did not, and a call whose promise was dropped left no trace, so `crw.land(...)` dropped then returned was not a land twice and a dropped `crw.commit` after the review let the land follow; the use of a value now goes down the expression by its operator (`consume` in `internal/flow/lint/walk.go`), `{ p }` is a read, and a started land or commit counts as started; port: fixed (`TestLintLifecyclePromiseContexts`, `TestLintLifecycleCountsTheInvocation`). Its verification found a held review promise of an earlier round that settled after a started land or a new commit still set the node to reviewed, so `crw.land(...)` then `await oldReview` then another land was no land twice and `crw.commit(...)` then `await oldReview` let the land follow; a pending lifecycle event now belongs to the node's generation, a started build, commit or land begins a new one, and a completion of an earlier generation leaves the phase where it is (where only some paths began a new generation, the node may be in either phase); port: fixed (`TestLintPendingEventCannotUndoAStartedOne`). The verification of that change found the join of two paths kept only the first branch's pending call of a name, so `let r = crw.review(...)`, then a new round on the first branch and `r = crw.review(...)` on the second, then `await r` and `crw.land`, was a land without review although the second branch reviewed the current head, and swapping the branches made it clean; a name now keeps, where paths meet, every call it may hold, each with its own generation, and reading it unites the phases of all of them; port: fixed (`TestLintPendingAlternativesAtABranchJoin`, `TestStateJoinIsOrderFree`, and every script the lint tests check is checked again with each if statement and conditional expression in the other branch order, `sameAcrossBranchOrders`).
- A pair's `autoCompactTokenLimit` in the `agent-roles` section was accepted by the reader and dropped when the flow role table was built; port: fixed (`RoleSpec`, `ThreadSpec` and `crw flow roles` carry it; `TestAutoCompactTokenLimitReachesTheThreadAndTheReport`). Sending it to the host as `model_auto_compact_token_limit` is the real backend's, which this issue does not ship (the engine's backend here is the fake).
