# CRW-1318 — the preflight facts and issue-ready refused a reversible step, so a new orchestrator's first run needed --force

Source: CRW's own design, not the CXC oracle (CXC v0.2.40, commit 3c1459ac): the oracle has no `crw flow start` preflight and no release-gate command. The Go side is `internal/flow/cli` (`preflight.go`: `Fact`, `StoreProber`; `start.go`: the preview and the start; `spec.go`: the run's spec) and `internal/skill` (`issue_ready.go`, the help in `command.go`). Found by the 10-13 field trial (CRW-1315 items 22 and 11, D5, D6, L5): both runs started with `--force` because `thread_reachable`, `waits_deliverable` and `idle_wake_observed` failed, and a `not_ready` answer of `crw skill issue-ready check` exited 1 and held the release while its help did not name the exception keys, so the parent got the exception wrong twice.

- `crw flow start` refused a run when any preflight fact failed, and `--force` was the only way past, so forcing became routine (item 22); port: fixed (a fact has a level, `pass`, `warn` or `fail`, and a `reason` for a level that is not pass; the start never refuses on a fact: the preview prints every fact, stderr names the ones that did not pass, the run's spec records them as `preflight` with their readings and reasons, and the run starts; `--force` is accepted and changes nothing; `--preview` exits 0; the `blocked` refusal (a build without the lane operations, a lane without its compiled milestone) is unchanged. Pinned by `TestStartPreviewListsFivePreflightFacts`, `TestStartFirstRunOfANewThreadStartsWithWarnings` and, over the built binary without `--force`, `TestStartRunsARealDetachedProcess`).
- `thread_reachable` failed when the store held no `recipient_lifecycle` or `authorized_settings` row of the thread, which a new orchestrator thread has not yet (the lifecycle row follows the first delivery or supervisor send, the settings the managed start or registration), and `waits_deliverable` inherited the fail; port: fixed (no lifecycle reading, or no authorized settings, is `warn` with that reason; an archived or undeliverable reading and an unreadable store are `fail`; `waits_deliverable` passes when the three facts above it pass, fails when `thread_reachable` fails and is `warn` otherwise, naming the facts that did not pass. Pinned by `TestStartPreviewListsFivePreflightFacts`).
- `idle_wake_observed` counted `delivery_wakes` rows with `spent_at` set, which `delivery.Service.spendWake` deletes in the transaction that answers the woken attempt, so on the normal path the count was 0 and the fact could not pass (the test passed only by inserting such a row by hand); port: fixed by demotion (no record of an answered wake survives: the relay writes no journal row for a wake and deletes the row, so the fact now counts every wake row the store holds, spent or not, passes on one and is `warn` without one, with that reason, and fails only when the table cannot be read; the fact id is kept for CRW-1316, which decides the thread facts of the orchestrator thread. Pinned by `TestStartPreviewListsFivePreflightFacts`).
- `crw skill issue-ready check` exited 1 on `not_ready` and `design_first` and the crw-run skill and the release gate told the parent not to release (item 11); port: fixed (both exit 0 with the decision unchanged in the report and each reason printed on stderr as `crw skill issue-ready: warning: <issue> is <decision>: <reason>`; an input that cannot be read and an exception that names no approver, issue, date or statement still exit 2; the crw-run skill and `release-gate.md` state the warn rule: the parent records the reasons beside the launch, supplies what it can and otherwise releases with the warning recorded. The night-batch selection (`internal/manage/batch.go`, `skill.CheckIssueReady`) is unchanged and still selects only ready issues. Pinned by `TestIssueReadyHeldIsAWarning` and the held cases of the `TestIssueReady*` tests).
- The help of `crw skill issue-ready` did not name the exception's JSON keys (`issue_size.go` `sizeException`); port: fixed (`crw skill issue-ready --help` and `crw skill issue-ready check --help` name `exception.issue`, `exception.approved_by`, `exception.approved_on` as YYYY-MM-DD and `exception.statement`. Pinned by `TestIssueReadyHeldIsAWarning`).
- Deviation: the run spec's `forced` field is gone (a run spec written before this change still reads; the field is ignored), the preview's `refused` field is gone, and a caller that read exit 1 of `issue-ready check` as a hold now reads the `decision`; port: kept (a reversible step is warned and recorded, not refused, Jun 10-13).
- Supersedes CRW-1205.md, item beginning "The five preflight facts are read from what the relay records": now port: fixed (a fact is pass, warn or fail with its reason and never stops the start; the spec records the facts that did not pass as `preflight`, `--force` is inert, and `idle_wake_observed` counts the wakes the store holds, as the bullets above say).
