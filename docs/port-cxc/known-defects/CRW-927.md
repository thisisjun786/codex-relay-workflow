# CRW-927 — reset link judgement: the search question at every dot component, no open during the judgement, in-root failures are absent

Source: CXC v0.2.40 (commit 3c1459ac) `plugins/codexclaw/components/cxc-ops/src/reset.ts:16,35-42`
(`existsSync` and `rmIfExists`; the judgement reproduces the kernel's answer for the link rather than
calling it). Go port: `internal/pabcd/reset/reset.go` (`resetPin`, `resetLinkTargetExistsWith`,
`resetLinkWalkTarget`, `resetLinkWalkSearchable`, `resetLinkWalkReadlink`).

- Supersedes CRW-822.md, item beginning "A multi-component dot-ending target such as": now port:
  fixed (the judgement opens no file and no directory — the descriptor is taken once by `resetPin`
  and every judgement step is an `fstatat(AT_SYMLINK_NOFOLLOW)` or `readlinkat` relative to it — so
  the intermediate directories of a target such as `keep/sub/..` are resolved by the kernel, which
  needs no read permission and issues no `openat`; a search-only (0111) directory now answers as
  the kernel does; pinned by `TestResetLinkPermJudgesLikeStatInSearchOnlyDirectories`).
- The oracle resolves `keep/../.` with the kernel's own walk, so with `.crw/keep` at mode 000 it
  answers EACCES and `rmIfExists` keeps the link (`reset.ts:16,35-42`); the port asked the search
  question only at the last component of the target and removed the link. The walk now asks it at
  every `.` and `..` component it passes, through the pinned descriptor; port: fixed (pinned by
  `TestResetLinkPermKeepsASearchDeniedMiddleDot`).
- The oracle answers ELOOP for a link loop and a chain past the kernel's 40 traversals, and EACCES
  for a directory it cannot search, so `rmIfExists` keeps the link (`reset.ts:16,35-42`); the port
  handed those in-root failures to the root-path judgement, which refuses with "reset directory
  changed while judging a link" once the pinned directory has been renamed and stops the reset
  before the remaining candidates. Such a target is now decided by the walk and is absent, and only
  a target that really leaves the root keeps the descriptor stat and the root-path judgement; port:
  fixed (pinned by `TestResetLinkPermInRootFailuresAreAbsentInARenamedPin` and
  `TestResetLinkPermTenLinkChainIsRemovedWithAndWithoutARename`).
- Residual race, recorded because the issue names it: a component the walk has seen to be a
  directory can be swapped for a link between that observation and the `fstatat` that resolves the
  concatenated path, so the stat answer can describe a different file than the walk saw. Only the
  verdict is affected; the removal still acts on the leaf through the pinned descriptor
  (`os.Root.Remove` refuses a name that escapes the root), so no path outside the workspace is
  removed; port: kept.
- The first revision of this pull request read a link target with a single `readlinkat` and retried
  only on `ERANGE`, which `readlinkat` does not report: it fills the buffer and returns the size, so
  a target of 128 bytes or more was judged on a cut-off path, and the verdict could differ from
  `existsSync` in either direction. The read now repeats while the buffer comes back full, as
  `os.Readlink` does; port: fixed (found in the Devin and Codex reviews of this pull request; pinned
  by `TestResetLinkPermReadsALongTargetWhole`, which compares the verdict with `os.Stat` on the same
  link for a live target longer than the first buffer and for a dangling one whose first buffer's
  worth of bytes names a real file).
- A `.crw` that may be searched and written but not read (mode 0311) cannot be opened, so `reset`
  refuses before removing the candidate it names, where the oracle's path-based `existsSync` and
  `rmSync` would remove it. The refusal is the safe direction and is not new: `resetPin` already
  opened the directory through `os.Root` before this issue, and both the baseline and this revision
  answer `openat .crw: permission denied` for `RunReset(workspace, Generated)`. Removing the
  requirement needs the pin's descriptor to be an `O_PATH` handle and a separate readable handle for
  the sessions listing, which is a change to `resetPin`'s contract rather than to the link
  judgement; port: kept (reported in the Devin review of this pull request; a follow-up candidate).
- Supersedes the expectation of `internal/pabcd/reset/reset_linkdot_test.go`'s
  `TestResetLinkDotTargetSkipsTheRootStat` row `plain_keep_keeps_the_descriptor_path`: now the walk
  alone decides every in-root target, dot-ending or not, so the row is renamed
  `plain_keep_is_decided_by_the_walk` and expects no descriptor-path stat; port: fixed (the
  expectation changed with the answer, not a defect of the oracle).
- The 40-hop ceiling was applied on every platform, where XNU allows 32, so an in-root chain of 33 to
  40 links that ends at an existing file was judged present by the walk on Darwin where `stat` answers
  ELOOP and `rmIfExists` would keep the link; the walk decides in-root targets that the descriptor
  stat decided before this issue, so the difference was reachable there; port: fixed (see the
  Supersedes line below; found in the Codex review of this pull request).
- Supersedes CRW-927.md, item beginning "The 40-hop ceiling is the answer this issue fixes": now
  port: fixed (`resetLinkWalkLimit` returns 32 on darwin and 40 elsewhere, the ceilings the two
  kernels apply to one resolution, so a chain of 33 to 40 links is absent on darwin where `stat`
  answers ELOOP; pinned by `TestResetLinkPermCeilingFollowsThePlatform`, and the boundary rows of
  `TestResetLinkWalkCountsTheCandidateLinkInTheCeiling` still compare against `os.Stat` on Linux;
  found in the pre-merge evaluation of this pull request).
- A candidate link whose target cannot be read through the pinned descriptor was still handed to the
  root-path judgement, so an in-root access error could refuse the whole reset — and it used the
  directory-opening path the judgement must not use — where the kernel cannot resolve such a link
  either and the oracle keeps it. Such a target is now absent, and the root-path judgement is reached
  only for a target the walk proved leaves the root; port: fixed (found in the pre-merge evaluation of
  this pull request; pinned by `TestResetLinkPermAnUnreadableTargetIsAbsentNotARefusal`, which also
  renames the pinned directory so the old path would have refused).
- `TestResetLinkWalkKeepsADotEndingLinkWhenSearchIsDenied`'s `RunReset` half could not fail: the
  candidate `b.json` was created under `.crw/sessions` with a target relative to the workspace root
  (`keep/.`, `keep/sub/..`), so it named no `keep` beside it, was dangling in every row, and reset
  kept it whatever the judgement answered. The row is pre-existing (`git show 9a7fcae2` has the same
  shape) and this issue touches the file only to adapt its helper, so the vacuous assertion is not
  introduced here; the fix mirrors the tree under `.crw/sessions` and asserts
  `errors.Is(linkErr, os.ErrNotExist)` for the rows whose target exists, which a mutation making every
  directory searchable now fails on exactly the four denied rows; port: fixed (found in the
  independent review of this pull request).
