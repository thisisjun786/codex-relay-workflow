# CRW-1222 — the 0.5.0-alpha extension of the skills: the second managed surface of DISPATCH-MANAGED-01, the spawn policy, the flow wording and the completed inventory

Source: CXC v0.2.40 (commit 3c1459ac) `plugins/codexclaw/skills/pabcd/references/dispatch-surfaces.md:25-31`, `pabcd/SKILL.md` (Delegation model) and `loop/SKILL.md`, `loop/references/lane-dispatch.md` for the ported files `plugins/crw/skills/crw-pabcd/references/dispatch-surfaces.md`, `crw-pabcd/SKILL.md`, `crw-loop/SKILL.md` and `crw-loop/references/lane-dispatch.md` (recorded in `port/cxc/records/crw-pabcd.json` and `crw-loop.json`); the rest is CRW's own: `plugins/crw/skills/crw-canon/references/{spawn-policy,flow,hierarchy}.md`, `crw-run`, `crw-run-initiative`, `crw-plan`, `crw-add-issue` and `crw-status`, and the engine they describe (`internal/flow/ops/rules.go`, `internal/flow/compile`, `internal/flow/cli`, `docs/flow/reporting.md`). This is the human note of the extension; the machine record of the ported edits is the two JSON files above.

How it relates to CRW-1130: CRW-1130 made DISPATCH-MANAGED-01 start every dispatch from the binding, with one managed surface (the independent relay child started through `crw-run`) and a project parent that uses read-only and review helpers only. This issue keeps all of that and adds the second surface the flow engine brought: a Linear issue or DAG node may also be a flow executor call of the project orchestrator's run, recorded in the relay. Nothing CRW-1130 forbids is allowed by this: a managed issue is still never a desktop `create_thread` lane, the relay's duplicate-assignment and capacity refusals are still followed, an unresolved binding is still not permission to go unmanaged, and a native helper's record is still neither an acceptance nor a receipt (it is also no flow executor call).

- The CXC reference and the first CRW port name no engine-started executor, so a project orchestrator that runs a milestone through a flow run met a rule that told it every implementation is an independent child's (`dispatch-surfaces.md` DISPATCH-MANAGED-01 and its three entry points); port: fixed (the Managed bullet has two surfaces, the independent relay child and the flow executor call of the run, and says the choice is the project orchestrator's plan; `crw-pabcd`, `crw-loop` and `crw-loop`'s lane-dispatch reference say the same in one clause; the required wording of `TestDispatchSurfaces_ManagedBindingComesFirst` and `TestDispatchSurfaces_EntryPointsStartFromTheBinding` is updated in the same change).
- The spawn decisions of the engine (which agent call a run makes, which signal adds one, what is done inline, the two kinds of refusal) lived in `docs/flow/script.md` and the design only, so a skill could not point at them and the rule ids could drift from the code (duplicateContent[6]); port: fixed (`crw-canon/references/spawn-policy.md` holds them, `crw-pabcd` and `flow.md` point at it, and `TestSpawnPolicyRulesMatchEngine` compares its rule ids and its numbers with `internal/flow/ops/rules.go`).
- The control ownership of a flow-managed node was in no skill: nothing said that the run owns phases, audit and evidence, that the executor and an oversized child start no PABCD state machine, or in which order a C4 issue is built (the design audit by a reviewer of another model family before any executor, then the candidate reviews, then the final gate and reviewer-final, which does not replace the audit); port: fixed (`flow.md`, "Who owns control in a flow-managed run", pinned by `TestFlowControlOwnershipTableWording`; `crw-dev` already carried the C4 sentence).
- `crw-run` told a project orchestrator how to dispatch issue children and nothing about a run, and the one claim it names (`dag-coordinator-claim`) fences a plan the run already holds; port: fixed (the section "Run a milestone with a flow run": one run per milestone, the preview before the start, escalations and `crw flow apply` for an oversized child's receipt as the thread's only work, no claim of the epoch of a plan a run holds, an out-of-band `dag-*` transition raised as an escalation; pinned by `TestRunProjectNeverClaimsRunEpoch`, with the command sequence test adjusted for the one named claim).
- The planning skills carried no `size_fit`, `size_reason`, issue-size answer or `group`, forbade them in their tests ("a later issue brings in"), and the closing check did not run the compiler; port: fixed (`crw-plan` "Set the size fields" with the closed sets and the rule that a count alone never divides an issue or sends it to a child, "Write the Orchestration section of the project" and "Hand the plan to the run"; the closing check gains step 5, `crw flow compile --dry-run`, with the refusal rules the compiler writes; `crw-add-issue` writes the fields and points to the table; pinned by `TestSizeFitClosedSet`, `TestPlanClosingCheckRunsCompile` and `TestPlanSizeFieldsAndOrchestrationWording`).
- `crw-run-initiative` did not read the milestone reports a run sends, and `crw-status` read no run; port: fixed (`crw flow reports --unread`, `crw flow report-ack` after a judgment with `crw-check`, and an initiative lead that never operates a run; `crw-status` reads `crw flow ps`, `show`, `watch`, `crw relay journal-tail` and the unread reports and acknowledges none; `hierarchy.md` has the issue executor row, which is no fifth level; pinned by `TestRunInitiativeReadsReports`, `TestStatusReadsRunStateAndUnreadReports` and `TestHierarchyNamesTheIssueExecutor`).
- Every `crw flow <sub>` a skill writes is a subcommand of the built binary; port: fixed (`TestSkillCommandsExist` collects them from the skill texts and compares them with `crw flow --help`).
- The inventory map has no open row; port: fixed (`duplicateContent[6]` is done with its asserts and `inventoryCompletionMode` is true, so `TestSkillInventoryMapComplete` fails for any open row).
- Not changed: the spawn policy page names `SP-REV-2` (the candidate batch of CRW-1225) as a rule of the engine that the project lane shipped today does not yet use for batching; the page says so beside the rule instead of describing a batch the lane does not make. The page is the one place to update when a lane starts using it; port: kept.
