# CRW-1255 — what a SIGKILL leaves in the sessions directory is an allowed leftover, not a defect

Source: CRW's own design on top of the CXC state writes (CXC v0.2.40, commit 3c1459ac, `plugins/codexclaw/components/pabcd-state/src/state.ts` `withSessionLock` and `writeState`; the pointer is the port). The Go side is `internal/pabcd/state/lock.go` (`WithSessionLock`, `placeSessionLock`, `sessionLockOwnerGone`), `internal/pabcd/state/write.go` (`ensureState`, `writeState`, `OrphanStateTemp`) and `internal/pabcd/reset/reset.go` (`resetSessions`). Found by the real-environment trial r1 (S4 C, `S4-C-kill-2`: after a process-group SIGKILL two seconds after `thread.started` one `.lock` or `.tmp` was left beside a valid state file and a parseable ledger; the script recorded neither name, owner pid nor age).

- A process killed by SIGKILL at any step of the first nine rows of the table below, the steps of the lock and of the normal state writes, leaves a file the next acquirer takes over or the explicit maintenance command removes, and no state read or write waits for it; the plan's "lock/tmp leftover 0" (plan.md lines 98 and 104) holds only after that takeover or sweep. No form in those rows is never taken over or never removable, so no production code changed (port: kept by design, CRW-1094). The allowed leftover after a SIGKILL is defined as: the owner process is gone; the file has one of the names of the first nine rows; the next `WithSessionLock` takes a `<key>.json.lock` over at once (no wait, no time-based breaker) and removes it on release, or `crw pabcd reset --state` (`resetSessions`, via `OrphanStateTemp`) removes a `.tmp` whose pid in the name is gone; a hook never sweeps. The last two rows are outside that definition: they are the known best-effort limit of the in-place fallback (below), which leaves a state file that can be empty.

  | Killed at | Left in `.crw/sessions` (`<pid>` is the killed process, `<uuid>` random) | State file | Gone by |
  | --- | --- | --- | --- |
  | lock staged, record not written (`placeSessionLock`) | `<key>.json.lock.<pid>.<uuid>.tmp` | previous | reset |
  | lock staged with record, not at the path | `<key>.json.lock.<pid>.<uuid>.tmp` | previous | reset |
  | inside `WithSessionLock` (any critical section) | `<key>.json.lock` (`<pid> flock`) | previous | next acquirer |
  | taking over a dead owner's lock, record not written | `<key>.json.lock` and `<key>.json.lock.<pid>.<uuid>.tmp` | previous | acquirer and reset |
  | `writeState`, temp written, before fsync, and before the rename | `<key>.json.lock`, `<key>.json.<pid>.<uuid>.tmp` | previous | acquirer and reset |
  | `writeState`, after the rename, before the directory fsync | `<key>.json.lock` | new | next acquirer |
  | `ensureState`, before the hard link | `<key>.json.<pid>.<uuid>.tmp` | none | reset |
  | `ensureState`, after the hard link | `<key>.json`, `<key>.json.<pid>.<uuid>.tmp` | default | reset |
  | `ensureState` without hard links, second temp file written or before the rename | two `<key>.json.<pid>.<uuid>.tmp` | none | reset |
  | `ensureState` without hard links or a no-replace rename, in-place create, before the write | `<key>.json` (empty), `<key>.json.<pid>.<uuid>.tmp` | empty, unreadable | reset |
  | same, after the write, before the fsync | `<key>.json`, `<key>.json.<pid>.<uuid>.tmp` | default, whole | reset |

  The last two rows are `ensureState` on a filesystem with neither hard links nor a no-replace rename (the hard link answers EPERM and the no-replace rename ENOSYS, EINVAL, EPERM or the like), where `publishWithoutLink` creates the final path in place after removing its second temp file (`write.go`, comment of `publishWithoutLink`; the limit is also in the CRW-445 entry above: "a kill part-way still leaves" a partial file). A kill between that create and the write leaves an empty `<key>.json` (a strict read says unreadable, and `EnsureState` does not repair an existing file) beside the first temp file; a kill after the write, before the fsync, leaves a whole default state, which a kill cannot lose because the data is in the page cache. Neither is taken over by an acquirer, and a lock holder's write is not a repair on that filesystem: a fresh `WithSessionLock` there cannot create its lock either, because `placeSessionLock` needs the no-replace rename or the hard link (`lock.go`), and `UserPromptSubmit` skips an unreadable state. `crw pabcd reset --state` removes the state file and the temp file, and it is the only recorded repair. No production change: only a filesystem without both calls reaches the route, the file is the default state of a session that just began, and reset is the recorded repair (port: kept, as in CRW-445).

  `crw pabcd reset --state` removes `*.json` and the orphan `.tmp` files but not a `<key>.json.lock`; a dead owner's lock stays until the next acquirer takes it over and releases it, which is by design (CRW-1094) and is not a stuck lock. A temp file whose pid is alive stays (the pid may be reused; the writer may still rename it). Pinned by `TestSigkillLeftoverNamesAndNextAcquirer`, `TestSigkillLeftoverIsRemovedByResetAndTheLockByTheNextAcquirer` and `TestSigkillLeftoverInPlaceStateFileIsNotRepairedByEnsureButByReset` in `internal/pabcd/state/sigkill_leftover_test.go` (a child process per step killed with SIGKILL; the two in-place rows run no acquirer, because the test filesystem has the calls the row lacks; the same test turned red when the takeover was disabled); port: kept.
- The real-trial script's leftover check (`S4.sh`, any `*.lock` or `*.tmp`) judged the allowed leftover above as a failure, and it recorded no name, pid or age. The script is outside the repository; the second trial is to print each leftover's name, owner pid (the pid in the name or the `<pid> flock` record) and age and to judge it by the definition above (fail only a `.lock` whose next `WithSessionLock` does not enter, or a `.tmp` that `reset --state` does not remove); port: kept.
