# CRW-754 — a Python program passed to exec, eval or compile

Source: `plugins/codexclaw/components/pabcd-state/src/shell-write-destinations.ts` at v0.2.40 (commit 3c1459ac) —
`scriptWriteDestinations` :535-549 and `pythonNodeWriteDestinations` :505-533, whose Python patterns read only a quoted
positional first argument of `open(...)`; the port in `internal/pabcd/hook/shellwrite_verbs.go`
(`shellWriteExecScan`, `shellWriteExecCallee`, `shellWriteExecProgram`, `shellWriteFStringOpenWritesRunes`) and
`internal/pabcd/hook/memorygate.go` (the shell branch of `memoryGateClassify`).

- A write inside a plain string passed to `exec`, `eval` or `compile` is not read:
  `python3 -c "exec('open(file=\"<m>/a\", mode=\"w\")')"` is allowed with no destination (the positional form is
  caught only by the regex fallback), and the oracle misses it the same way (source `shell-write-destinations.ts:535-549`);
  port: fixed (a security fix under the parity rule revision of 2026-10-03: the walk reads the decoded value of a string
  literal first argument of `exec`, `eval` or `compile`, called directly or through `builtins.`/`__builtins__.`, as program
  text at depth 32, and fails closed through `shellWriteExecUnreadableWhat` when that argument is no literal; no recorded
  corpus fixture drives this, so none is tagged intentionally-changed).
- Accepted over-blocking of this fix: a bytes literal whose program declares a source encoding (PEP 263) is treated as
  unreadable, because Python decodes it under a codec this reader does not model, and an exec of a read() result is
  denied while the gate is on (the issue states that one); port: fixed.
- Other dynamic execution routes stay unread: `getattr(builtins, 'exec')(...)`, `importlib`, `os.system` and
  `subprocess` are outside this issue's scope (source `shell-write-destinations.ts:535-549`); port: pending.
- Supersedes known-defects/CRW-741.md, item beginning "A write inside a plain string passed to `exec`, `eval` or
  `compile` is not read": now port: fixed (CRW-754).
