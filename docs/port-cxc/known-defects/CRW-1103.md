# CRW-1103 — the D-close row guards read whole ledgers, more than once, while the close holds its locks

Source: CXC v0.2.40 (commit 3c1459ac) `plugins/codexclaw/components/pabcd-state/src/orchestrate-cli.ts`
`readJsonlObjects`, `hasGoalplanRow` and `hasPabcdCloseRow` (:431-453), called by the bound close at :985-1000,
and `plugins/codexclaw/components/pabcd-state/src/hook.ts` (:623-645, the chat close's copies). The port is
`internal/pabcd/cli/orchestrate_dclose.go` (`orchestrateDcloseScanJSONL`, `orchestrateDcloseHasGoalplanRows`,
`orchestrateDcloseHasPabcdCloseRowOpen`) and `internal/pabcd/hook/prompt_dclose.go` (`promptDcloseScanRows`,
`promptDcloseHasGoalplanRows`, `promptDcloseAnyRowOpen`). Cases: `internal/pabcd/cli/orchestrate_dclose_stream_test.go`
and `internal/pabcd/hook/prompt_dclose_stream_test.go`; the dev build's reads, counted with strace, in
`/state/crw/crw-lane-orchestrate-atomicity/evidence/CRW-1103/`.

- `readJsonlObjects` reads the whole ledger, splits it and keeps every object, and the bound close with a
  successor asks the plan's ledger twice (`workphase_done`, then `workphase_started`) and the workspace ledger
  once more, each a full read, while it holds the session and goalplan locks; the time and the memory grow with
  the history, and the lock is held for that time (`orchestrate-cli.ts`:431-453, :985-1000; `hook.ts`:623-645);
  port: fixed (each guard streams its ledger one line at a time and keeps no row: the plan's ledger is read once
  for all of the close's goalplan questions, before any of those rows is appended, and the workspace ledger once
  for the close row; a retry does the same; `TestOrchestrateDcloseReadsEachLedgerOnce`,
  `TestPromptDcloseReadsEachLedgerOnce`, `TestOrchestrateDcloseGuardHoldsNoRows`, and the strace counts: the
  plan's ledger read twice on dev, once here, on both surfaces).

What stays as it was: the CLI reads every line, a line after a match included, and refuses a line `JSON.parse`
cannot read or a bare `null` (CRW-756), while the chat close skips a malformed or non-object line (CRW-797);
the two policies are kept apart (`TestOrchestrateDcloseDamagedLineAfterAMatchStillFails`,
`TestPromptDcloseStreamedGuardSkipsDamagedLines`). Each line is decoded as UTF-8 on its own with
`source.DecodeUTF8`, which equals decoding the whole file because a line feed never belongs to an invalid
sequence; a lone surrogate escape stays a lone surrogate (`pyjson` with `Surrogates`), an absent key is still
not a null one, and the started row still names the successor the marker records. No line length is capped,
so no receipt row that used to be read is skipped. A close whose finalization lock fails keeps its recovery
marker and the pending text over a large history, and the same D request finishes it with one row of each kind
(`TestOrchestrateDcloseLargeHistoryKeepsTheMarkerThroughARetry`; the cancellation cases of CRW-922 pass
unchanged). No index is persisted. The answers and the rows the closes write are unchanged; this is no oracle
behaviour a fixture records.

The outbox that records the close rows appends to a workspace ledger the process may write and not read (mode 0200) as
the appender always did (the pre-merge evaluation of 3fceb240; CRW-1097,
`TestLedgerOutboxAppendsToAWriteOnlyLedger`), except for a row whose presence could not be looked up when it was
prepared (the chat all-done close with an unreadable ledger), which waits for a ledger it can search
(`TestPromptDcloseUnreadablePabcdLedgerWarnsOnAllDoneClose`).
