# CRW-741 — f-string replacement field write reading

Source: `plugins/codexclaw/components/pabcd-state/src/shell-write-destinations.ts` at v0.2.40 (commit 3c1459ac) —
`scriptWriteDestinations` :535-549 and `pythonNodeWriteDestinations` :505-533; the port in
`internal/pabcd/hook/shellwrite_verbs.go` (`shellVerbOpenWritesIn`, `shellWriteTripleScanRegion`,
`shellWriteFStringRegion`) and `internal/pabcd/hook/memorygate.go` (the shell branch of `memoryGateClassify`).

- `shellWriteDestinations` reads only a quoted positional first argument of `open(...)` by pattern, so `open(file=...)` is
  never named, inside an f-string replacement field or outside one, and the memory gate allows the write; the port's own
  region rule (`shellWriteTripleScanRegion`) then skipped the whole f-string literal, so a field's `open()` call was never
  reached (`python3 -c "f'{open(file='<m>/a', mode='w')}'"` names nothing; source `shell-write-destinations.ts:535-549`);
  port: fixed by CRW-741 (a security fix, by decision under the parity rule revision of 2026-10-03: the reader walks an
  f-string body as Python reads it and reads each replacement field's expression with the same reader, so an `open()` call
  in a field names its path, and the gate's shell branch fails closed through `shellWriteFStringUnreadable` when a field
  cannot be read; no recorded corpus fixture drives this, so none is tagged intentionally-changed).
- A write inside a plain string passed to `exec`, `eval` or `compile` is not read:
  `python3 -c "exec('open(file=\"<m>/a\", mode=\"w\")')"` is allowed on dev and the oracle is the same
  (source `shell-write-destinations.ts:535-549`); port: pending (a follow-up issue).
- Supersedes known-defects.md, section "Found by the shell write verb port (CRW-517)", item beginning "An interpreter fed
  its program by a heredoc or herestring": now port: pending (follow-up CRW-765; CRW-741 keeps the four-file edit region and
  leaves the heredoc-body strip and the standard-input program gap as they are).
