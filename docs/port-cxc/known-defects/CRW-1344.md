# CRW-1344 — the skills and references name the tracking repository, not Linear: tracking-model.md replaces linear-model.md

Source: CRW's own design, not the CXC oracle (CXC v0.2.40, commit 3c1459ac, tracks work in Linear and has no tracking repository). The decision is the local policy draft `/scratch/sion-eval/POLICY.md` (one GitHub repository tracks the work, a milestone is the unit of one project session, issues, sub-issues, labels, `Blocked by:` lines and the `[layer · session]` comment header). The adapter is `internal/tracking` (CRW-1342) and the setting is `internal/crwconfig/tracking.go`; there is no `crw tracking` command, so the skills use `gh` and `crw flow plan-input`. The documents are `plugins/crw/skills/` (72 files named Linear at the base), the tests `internal/dev/ci/tracking_wording_test.go` and `internal/skill/issue_input_help_test.go`.

- The skills told agents to use Linear tools, Linear documents and Linear statuses; port: fixed (`crw-canon/references/linear-model.md` is replaced by `tracking-model.md`: the tracking repository and the code repository are apart, a milestone is the unit of one child, an issue is the unit of work, sub-issues split it, `Blocked by:` lines order it, labels carry priority, kind and area and state is only open or closed, the comment header is `[layer · session]`; the sections keep their anchors where the rule stands (`#issue-to-pr-mapping`, `#record-writes-and-returned-proposals`, `#resolve-the-implementation-repository`, `#implementation-done`, `#where-each-document-type-is-canonical`, `#classify-an-existing-document`, `#keep-the-two-sides-consistent`, `#when-the-implementing-repository-changes`) and are renamed where the old name was the tracker (`#tracking-operating-model`, `#tracking-holds-canonical-documents`, `#milestone-description-standard`, `#use-the-tracking-access`); the initiative body standard is the milestone description standard, because there is no layer above a milestone). The Linear tool calls of crw-run, crw-plan, crw-add-issue, crw-check and crw-status are `gh` commands (`gh issue view|create|comment|edit|close`, `gh api`) or `crw flow plan-input --milestone OWNER/NAME#N`; the coordination record of a milestone is a coordination issue; the thread title's product family is the `family:NAME` label of the milestone's issues (the prefix is the group, so a flat label list no longer lacks its provenance). Pinned by `TestSkillsNameNoLinearTracker` (revert-red against the base text: 295 lines; mutation fixtures in the test) and by the rewritten pins of `skill_canon_test.go`, `orchestration_skills_test.go`, `scaffolding_wording_test.go`, `interview_retired_test.go`, `size_rules_test.go`, `run_split_test.go` and `internal/relay/dagsched/outbox_docs_test.go`.
- `crw skill issue-ready check` and `crw skill issue-size check` named "the Linear tools" as their input; port: fixed (the help says the input is a GitHub issue mapped by `gh issue view N --repo OWNER/NAME --json url,title,body,labels --jq '{id: .url, title: .title, description: .body, labels: [.labels[].name]}'`, the command of tracking-model.md; the keys the checks read are unchanged, so no code path changed). Pinned by `TestIssueChecksHelpTakesAGitHubIssue` (red first, `evidence/crw-1344-red-issue-checks-help.log`), `TestIssueChecksReadTheMappedGitHubIssue` and `TestIssueChecksHelpAndTrackingModelGiveOneMapping`.
- The tracking section's kind `linear` is the one read-only archive setting; port: kept as the only line of the skills that names Linear (`tracking-model.md`, the line that also names the label `from-linear` of a moved issue). `rg -il linear plugins/crw/skills` still lists the design skills (`crw-dev-frontend`, `crw-dev-uiux-design`) and one table row of `crw-dev-backend`, where the word is the CSS keyword `linear` (`linear-gradient`, the linear timing function), the adverb, or the product Linear named as a design reference, and `crw-canon/references/delivery.md`, where the sentence belongs to the pull request and landing paragraph of lane pr-landing-1355; the test lists the first group with what it says and the second as pending; the end condition as written cannot be met without changing CSS in the design references.
- The summary outbox protocol of `references/relay.md` (the coordinator's own write, the DAG plan's summary queue) assumed an atomic conditional patch of a Linear document; port: changed, gap kept (the procedure writes one comment of the milestone's coordination issue with `gh api -X PATCH`, which does not compare the comment with the text read; the claim token keeps two writers apart and the readback decides; the relay code and `docs/relay/dag-outbox.md` still describe the Linear patch and are not part of this change).
- `crw manage batch plan` and `crw manage checkpoint --linear-export` still read Linear-shaped issue JSON (a state value `Backlog`, an id and an identifier) and `internal/relay` still names a Linear document for the summary; port: kept (code, not skill text; the skills describe the command as it is, without the tracker's name).
- Not changed: `README.md` outside the one link to the renamed model, `AGENTS.md` outside the two sentences that named Linear for documents and writes, the pull request and landing paragraphs of `AGENTS.md`, `README.md` and `delivery.md` (lane pr-landing-1355), historical records, and the plugin version line.
