# CRW-383 — the loop CLI's mutating verbs (steer, add-criterion, add-work-phase, add-task, complete-task, meet-criterion, ask, decide)

Source: CXC v0.2.40 (commit 3c1459ac) the oracle's goalplan-cli.ts (CXC v0.2.40, outside this tree):
`runSteer` (:296-352), `runAddOp` (:354-420), `runDecision` (:525-560) and `runLifecycle` (:562-699), with the
dispatch in `runGoalplanCli` (:810-826). Ported into `internal/pabcd/cli/loop_mutate.go`; the seam CRW-646 left
in `internal/pabcd/cli/loop.go` is removed. The replay seam is `stampWritten` in
`internal/dev/cxccorpus/engine.go`.

- `add-criterion` and `add-work-phase` print the plan after `applySteeringBatch` answered applied and drop the
  transaction's warning (:386-405), so a ledger row that could not be written after the plan was committed is
  invisible to the caller, and the same holds for the durability warning of a plan directory that could not be synced
  (CRW-793); port: fixed (the answer carries the warning on a line of its own after the plan text, as `steer` already
  does with its two-space form; test TestLoopAddVerbsReportTheLedgerWarning).
- A plan write of `ask`, `decide`, `add-task`, `complete-task` or `meet-criterion` that published at its final path and
  then failed to sync the plan's directory is an error in the oracle (`writeGoalplan` throws, :554, :680), although
  the plan on disk has already moved and a retry would then answer "nothing to do"; port: fixed (the verb answers its
  usual success with the same published-but-unsynced warning that `init`, steering and review-round open give, a
  failure before the rename stays an error; the helper is `cliPublishedGoalplanWarning`).
- The oracle's session checks differ per verb (steer spells the non-canonical id with an em dash, the add and
  lifecycle verbs with a hyphen, ask and decide say only "session id is not canonical"), and a blank `--session` is
  "required". The generic pre-dispatch guard CRW-646 added for the read verbs is therefore not applied to the eight
  mutating verbs, whose own checks (trimmed value, as the oracle) run in the oracle's order and wording; port: kept.
- `steer` reports a batch that is not JSON as `batch is not valid JSON (<message>)`; the message is Go's
  `encoding/json` wording, not V8's (`Unexpected token ...`), and a file that cannot be read is spelled as Node spells
  the errno (`ENOENT: no such file or directory, open '<path>'`) through `nodeErrorMessage`. A caller that parses the
  parser's message sees a different sentence; the prefix and the exit code are the oracle's; port: kept (the message
  is a runtime diagnostic of two different parsers; steering.test.ts asserts only the `not valid JSON` prefix).
- The ledger-append warning of the lifecycle verbs ends with Go's error text where the oracle prints
  `err.message`; port: kept (same reason: a runtime diagnostic).
- The corpus fixture `cli__loop__held_goalplan_lock_refuses_write` shows a held lock with `ageMs=0` because the oracle
  runs under a frozen clock that every file the run writes is newer than; a Go replay reads the real clock, where a
  fresh lock is a few milliseconds old and the fractional age is never reproducible. The dev corpus engine now stamps a
  file a write step creates, and the directory that holds it, one hour ahead of the real clock (`stampWritten`), so the
  clamped age reads 0 again; no Go build code is involved and the fixture is claimed identical; port: fixed
  (test TestStampWrittenSetsTheFileAndItsDirectoryAheadOfTheClock; the other claimed write-step fixtures still pass).
