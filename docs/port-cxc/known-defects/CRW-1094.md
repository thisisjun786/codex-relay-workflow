# CRW-1094 — the session lock is owned through the kernel, a dead holder's lock is taken over, and a chat command under a busy lock says so

Source: CXC v0.2.40 (commit 3c1459ac) `plugins/codexclaw/components/pabcd-state/src/state.ts:672-690` (withSessionLock: an exclusive create holding the pid, about 250 ms of retries, release by path, no stale-lock breaker), `:626-639` (writeState's temp file) and `plugins/codexclaw/components/pabcd-state/src/hook.ts` (the UserPromptSubmit turn stamp whose failure answers nothing). The Go side is `internal/pabcd/state/lock.go` (`WithSessionLock*`, `trySessionLock`, `sessionLockOwnerGone`, `ProcessGone`), `internal/pabcd/state/write.go` (`OrphanStateTemp`), `internal/pabcd/reset/reset.go` (`resetSessions`) and `internal/pabcd/hook/prompt_submit.go` (`promptSubmitNotApplied`). Found by the 10-10 isolated trial r1 S4-F2: 300 SIGKILL runs of the UserPromptSubmit leg (124 killed) left `<session>.json.lock` and 13 `*.tmp`; with the lock left, chat `orchestrate A` answered nothing after about 0.26 s, the phase stayed P and no ledger row was written, until the file was removed by hand.

- Decision on the mechanism: the lock is an flock(2) on the lock file, not a pid plus process-start record judged by time. The kernel drops a holder's lock when its descriptor closes, at the release or when the process dies, so no acquirer has to decide from a record whether a holder is alive, and two acquirers can never both judge one lock stale and enter together, which is why the oracle has no breaker. A record is still written ("<pid> flock") for people and for the one judgement the kernel cannot make: the oracle's bare-pid record, written by a holder that took no kernel lock (an older binary). The release removes the file while it still holds the kernel lock, and an acquirer checks after locking that the path still names the file it locked, so a waiter that locked a released file opens again. The repository already builds for Linux and Darwin only (`internal/pabcd/crwdir` uses flock), where flock is available.
- `withSessionLock` never reclaims the lock of a process that died, so a hook killed inside its critical section leaves `<session>.json.lock` and every later state write of the session, the chat `orchestrate` commands included, exhausts its retries until someone removes the file by hand (source `state.ts:672-690`; trial r1 S4-F2); port: fixed (an acquirer takes the file over at its first attempt when its owner is known to be gone: a record of this protocol, whose writer held the kernel lock until it died, or the oracle's bare pid of a process that no longer exists (kill(pid, 0) answers ESRCH). The takeover renames a complete record file over the gone owner's file while it holds that file's kernel lock. A live holder, the oracle's pid of a live process, an empty record and a record or a path it cannot judge (a directory, a link, a FIFO, other text) are never taken over and still give up after the oracle's schedule with the busy error; there is no time-based breaker. The empty record is not judged because it is exactly what the oracle's live holder shows between its exclusive create and its pid write, and this protocol never shows one at the path: its lock file is staged beside the path as `<key>.json.lock.<pid>.<uuid>.tmp`, locked and given its record, and only then put at the path by a rename that refuses to replace (link(2) where the filesystem has no such rename). Pinned by `TestALockWhoseOwnerIsGoneIsTakenOverAtOnce` (a dead pid, a dead holder's record, and a child killed while it holds the lock), `TestALiveOrUnknownOwnersLockIsNeverTakenOver` (an empty record among them), `TestALiveOracleHolderBeforeItsPidWriteIsNeverTakenOver` (the oracle's create with its descriptor still open and no pid yet), `TestTheLockPathNeverNamesAnEmptyRecord`, `TestProcessesContendingForTheLockLoseNoUpdate`, `TestGoroutinesTakeTurnsOnTheLock` and `TestChatOrchestrateTakesOverTheLockOfADeadHook`; the recorded `lock_held_exhausts` is replayed with a live pid, since its 424242 is now taken over when no such process exists).
