# CRW-1319 — the verifier found crw-dev and Go only on the login PATH

Source: CRW's own design, not the CXC oracle (CXC v0.2.40, commit 3c1459ac): the oracle has no flow lane and no `crw-dev ci local` verifier. The Go files are `internal/crwconfig/verifier.go` (`VerifierTools`, `LoadVerifierTools`, `VerifierTools.Command`, `crw config verifier`), `verifier_probe.go` (`ProbeVerifierTools`, the Go root candidates) and `config.go` (the reading of the file records the warning of a section the verifier cannot use), `internal/flow/cli/preflight_verifier.go` (the fact `verifier_prerequisites`), `internal/flow/ops/verify_ci.go` (`CILocalVerifier.Tools`, `RunCommand` with an environment), `internal/flow/ops/lane_build.go` (`verifier_note`), `internal/flow/cli/laneops.go` (`laneVerifierTools`, `CILocalIntegration`) and `internal/runtime/doctor/verifier_tools.go` (the `verifierTools` entry of `crw doctor`). Found by the 10-13 field trial (CRW-1315 items 23 and 45, L6): a bridge-created Codex task has neither `go` nor `crw-dev` on its `PATH`, the verifier ran `crw-dev` from `PATH` (`verify_ci.go:76-96` at a41dbb807), so the verification could not start, and the orchestrator needed a relay decision for a wrapper (`GOTOOLCHAIN=local`, a scratch `XDG_STATE_HOME`) that the management layer approved.

- The node verifier and the integration batch verifier ran `crw-dev` from the login `PATH`, and the steps of `crw-dev ci local` ran whatever `go` that `PATH` held (a `/tmp/go-sdk` go1.25.5 breaks CRW lint); port: fixed (the `verifier` section of the crw configuration names the Go toolchain root (`go_root`) and how crw-dev runs (`crw_dev`: `tree` or an absolute path; empty is `tree` when `go_root` is set). With a root the verifier runs `<go_root>/bin/go run -tags dev ./cmd/crw-dev ci local ...` in the verified tree with `<go_root>/bin` first on `PATH`, `GOROOT=<go_root>` and `GOTOOLCHAIN=local`; with a binary it runs that binary with the same `PATH`. Pinned by `TestVerifierCommand`, `TestCILocalVerifierRunsThroughTheConfiguredTools` and `TestCILocalIntegrationRunsTheMergedTreesOwnCrwDev`, each with neither tool on `PATH`).
- The merged tree of an integration batch was verified by whichever `crw-dev` the `PATH` held, not by the engine the merged tree carries; port: fixed (in `tree` mode the batch runs the merged worktree's own `cmd/crw-dev`, so the merged tree verifies itself; a tree without `cmd/crw-dev` does not start, with a reason naming `verifier.crw_dev`. Decision: the tree's own crw-dev, because an installed binary would verify a changed engine with the old one and the engine check of `crw-dev ci local` already binds a `go run` build to the verified commit's bytes; an installed `crw_dev` makes that check hold every head whose engine source differs from the binary's (`engine_differs_from_commit`)).
- A verification that could not start said only `exec: "crw-dev": executable file not found in $PATH`; port: fixed (the reason, which holds the node or stops the batch on a host error, names the configuration file and the `verifier.go_root` setting to add (`TestCILocalVerifierWithNothingConfiguredFallsBackToPath`, `TestCILocalIntegrationWithNothingConfiguredIsAHostError`)).
- With nothing configured the verifier still takes `crw-dev` and `go` from `PATH`; port: kept (fail-open, so a host that has both on `PATH` keeps working; the node verifier records the note on the `crw.verify` row as `verifier_note` (`TestVerifyRecordsTheVerifierNote`) and the integration verifier writes it to standard error as a `[crw note]` line, because a batch verifier answers only an error).
- Nothing recorded the tools and nothing showed them; port: fixed (`crw config verifier --go-root <dir> [--crw-dev tree|<path>]` is the installation step that records the section, every other key of the file and of the section kept, writing through a configuration file that is a symbolic link, and refuses a root whose `bin/go` is not executable (`TestConfigVerifierRecordsTheSetting`, `TestConfigVerifierWritesThroughASymlinkedFile`, `TestConfigVerifierKeepsTheSectionsOtherKeys`, `TestConfigVerifierRepairsAMalformedSection`); a section the verifier cannot use stops no other reader of the file: the reading ignores it with the warning `verifier_section`, the relay state selection, the tool roots and the lane go on, and the verifier falls back to `PATH` with a note that names the ignored section (`TestAMalformedVerifierSectionStopsNoOtherReader`, `TestLaneVerifierToolsComeFromTheConfiguration`); the plain `crw doctor` report carries `verifierTools`: the go the verifier runs, where it came from and its version, and whether crw-dev runs, every problem a warning, an ignored section included (`TestDoctorReportsTheVerifierTools`); with no root configured it finds the Go toolchain roots on the host (the root of the go on `PATH` and the usual install locations, never one below `/tmp` or `/var/tmp`, by its path or the path its links resolve to; the tests name a temporary directory of their own through `crwconfig.ProbeOptions`, so they hold with any `TMPDIR`) and its warning names the command that records the first (`TestVerifierProbeFindsAGoRoot`, `TestVerifierCandidateSkipsATemporaryRoot`, `TestDoctorNamesAGoRootCandidate`)). The installation itself does not run the command on its own: the doctor and the preflight fact name it with the root they found; port: deviation (recording stays an installation step, so a host's root is chosen, not guessed).
- The preflight did not look at the verifier's prerequisites (`preflight.go:20-30` at a41dbb807: the facts read only the relay store); port: fixed (`crw flow start` lists the fact `verifier_prerequisites` after the five: `pass` when crw-dev runs with the configured or `PATH` tools, the go is not older than the repository's `go.mod` asks and a `tree` verification's repository has `cmd/crw-dev`, otherwise `warn` with the reason, never a refusal of the start (`TestStartShowsTheVerifierPrerequisitesAsAWarnFact`, `TestVerifierPrerequisitesFact`)).
