# CRW-646 — the loop CLI's read verbs (init, show, validate, ready)

Source: CXC v0.2.40 (commit 3c1459ac) `plugins/codexclaw/components/pabcd-state/src/goalplan-cli.ts`:
`runReady` (:461-525) and the init/show/validate/ready branches of `runGoalplanCli` (:751-865), with the
`loop` dispatch in `src/cli.ts` (:169-180). Ported into `internal/pabcd/cli/loop.go`,
`internal/harness/pabcd_cli.go` and `internal/harness/pabcd.go`.

- The oracle guards a non-canonical `--session` id for the `ready` verb alone (:802-810), so
  `show --session a/b` and `validate --session a/b` address the state file of session `a-b` (state paths
  sanitize the id) and print or judge a plan the caller never named (:821-839; `internal/pabcd/cli/loop.go`,
  the ready-only guard against the shared ResolveLoopSlug path); port: kept.
- Supersedes this file, item beginning "The oracle guards a non-canonical": now port: fixed. The pull
  request's Devin review raised it as a finding of kind security, and the parity revision fixes a security
  finding during the port rather than closing it as parity. The guard now covers every verb that resolves a
  plan through `--session`, and a test covers show, validate and ready. No corpus fixture drives a
  non-canonical `--session`, so no fixture is tagged intentionally changed for this deviation.
- The init binding reads the session state with the strict reader and writes it back, and that reader
  rebuilds records it cannot keep whole, so the write-back replaced stored records with the cut ones:
  a receiptClaimed was cut to state.MaxReceiptClaimLen, an unverified list stopped at
  state.MaxUnverifiedSubagents, the interview tracker arrays were capped at interview.MaxTrackerArray, and a
  legacy D-close marker lost its distinction (:795-798 against `state.ts`); port: fixed (data loss: the
  binding now asks loopStateRewritable, a copy of the hook package sessionHookStateRewritable and
  sessionHookInterviewKeepsStored, before any write and again under the session lock, and refuses with
  "holds records a rewrite would change", leaving the file byte for byte, as every other Go writer of the
  session state already does; test TestLoopInitRefusesToRewriteASessionStateItCannotKeep).
- The oracle asks only whether a plan LOADED, so a truncated or structurally invalid
  `<cwd>/.crw/goalplans/<slug>/goalplan.json` reads as absent and `writeGoalplan`'s rename replaces its
  bytes while a `created` ledger row is appended to the replacement (:764-767); port: fixed (data-loss
  class: the port refuses when slug's plan file is there but did not load, so the bytes stay for repair; a
  path the slug resolver itself refuses still reaches the write path and reports that refusal as the oracle
  does).
- The oracle binds a slug with `readState` then `writeState`, and `readState` answers a fresh IDLE state for
  a session file it cannot decode, so `loop init --session <id>` replaces a damaged session state with a
  default and loses the original bytes (:795-798 against `state.ts`); port: fixed (data-loss class: the
  port reads the state with the strict reader under the session lock and refuses an unreadable file).
- The oracle's `ready --json` is `JSON.stringify`, which leaves `<`, `>`, `&`, U+2028 and U+2029 as they
  are, while the first version of the port encoded that document with Go's `json.Marshal` and escaped
  them; port: fixed (the port now uses the package's JSON.stringify encoder, so the bytes agree with the
  oracle for any plan text).

No other defect was found in this issue's ranges: the ported units reproduce the oracle's answers through
the corpus replayer (19 fixtures, `contract/notes/cxc/CRW-646.json`) and through the ported TypeScript
cases.

## Completion: the three defects of the post-merge evaluation of #660

The post-merge evaluation of this issue's first pull request (#660) found three defects inside this
issue's own promise (loop init, show, validate, ready), all confirmed in dev code and fixed by the
completion pull request of the same issue. The oracle pointers are the init branch of
`plugins/codexclaw/components/pabcd-state/src/goalplan-cli.ts` (:751-800) and `resolveSlug`
(:277-289) at v0.2.40 (commit 3c1459ac); the Go pointers are the completion head's
`internal/pabcd/cli/loop.go`, `internal/pabcd/cli/loop_args.go` and
`internal/pabcd/goalplan/lock.go`.

- Two concurrent `loop init` calls on one slug let the later one replace the plan the earlier one
  published: the oracle checks absence (`:764-767`) and only then publishes, and `writeGoalplan`'s
  rename replaces its destination, so both inits pass the check and the second plan's bytes and
  criteria overwrite the first's (`internal/pabcd/cli/loop.go`, the outer check against
  `internal/pabcd/goalplan/write.go`'s publication); port: fixed (data loss: the absence re-check and
  the publication are now one critical section under that slug's goalplan write lock,
  `goalplan.WithGoalplanCreationLock`, so exactly one init creates the plan and the other is refused
  with the existing "a plan already exists at slug ..." text and writes nothing; the replacing rename
  is never reached for an existing plan; case
  `TestLoopInitCreatesThePlanExclusivelyUnderConcurrency`).
- With `--session` the plan and its `created` ledger row were written before the session lock was
  taken, so a session lock that could not be taken left an unbound plan behind and the same init's
  retry was refused with "a plan already exists", while the session stayed unbound
  (`:795-798`, the plan and row before the binding); port: fixed (init now takes the session lock
  FIRST and holds it across the plan creation, the created row and the binding — the bound D-close's
  order, session lock outside and goalplan lock inside — so a lock it cannot take writes no plan, no
  ledger row and no state; case `TestLoopInitWritesNothingWhenTheSessionLockIsHeld`).
- A `--session` value that is empty after trimming skipped the canonical check, which tested the
  trimmed value, and then resolved through the RAW value: `SanitizeKey` turns blanks into `missing`,
  so `show`, `ready` and `validate` printed or judged the plan bound to the `missing` session, a plan
  the caller never named (`:802-810` guards only `ready` and tests the raw value, `:277-289`
  `resolveSlug` reads the raw value); port: fixed (the canonical guard runs before the verb dispatch
  for every verb including init and keys on the trimmed value, and `ResolveLoopSlug` resolves through
  the same trimmed value; case `TestLoopBlankSessionIsRefusedOnEveryVerb`).

The pre-merge evaluation of this completion pull request found two more defects inside the same
critical section, both fixed here with a red case each.

- The absence predicate that c1's fix installed tested `IsRegular()`, and the plan reader refuses a
  symbolic link through `O_NOFOLLOW`, so a plan path that was a link read as "absent" at both the
  outer check and the in-lock re-check and `WriteGoalplan`'s rename replaced the link and its
  target's bytes (the oracle has the same shape: it asks only whether a plan loaded); port: fixed
  (data loss: the predicate now counts any non-directory entry at the plan path as present, so a link
  is refused with the existing "refusing to overwrite it" text and the link and its target survive;
  case `TestLoopInitRefusesALinkedPlanFile`).
- When the creation lock's wait budget ran out with another holder's lock directory still there, the
  loser of a concurrent creation answered the lock's own busy message even when the winner had
  published the plan inside that window, so c1's promised "a plan already exists at slug ..." answer
  did not hold for that path; port: fixed (the timed-out path re-checks the plan before answering, so
  a plan now at the slug produces the criterion's refusal; case
  `TestLoopInitAnswersAlreadyExistsWhenTheLockTimesOut`).
- Taking the session lock first (c2's fix) creates the state directory, so a bound cycle the
  workspace cannot close — no resolvable git source identity — left a fresh `.crw` behind while the
  command answered "Nothing was written" (the oracle checks the source identity before any write);
  port: fixed (the source-identity gate now runs before the lock as well, and the check inside the
  lock stays authoritative; case `TestLoopInitWritesNothingWhenTheBoundCycleIsRefused`).

The pre-merge evaluation of the corrected head found two more, both fixed here with a red case each.

- The loser of a concurrent creation could still answer the creation lock's "is busy" message instead
  of the criterion's "a plan already exists at slug ...": the lock's own wait budget (5+10+20+40 ms)
  can run out while the winner is still publishing (its plan write stages a file, fsyncs it and
  fsyncs the directory after the rename), and the same could happen when the loser waits on the
  session lock rather than the goalplan lock; port: fixed (the timed-out creation path re-attempts the
  lock a bounded number of times, re-checking the plan each round, and a session lock whose wait ended
  re-checks the plan before reporting its own error; cases
  `TestLoopInitAnswersAlreadyExistsWhenTheLockTimesOut` and
  `TestLoopInitAnswersAlreadyExistsWhenTheSessionLockTimesOut`).
- A plan write that published at the final path and then failed a step after the rename aborted init
  before the created row and the binding, leaving a visible goalplan with no row, no binding and a
  retry that answers "a plan already exists" (the oracle's init has the same shape: `writeGoalplan`
  throwing ends the branch); port: fixed (the published-but-unsynced plan is a written plan, so the
  created row and the binding still run and the durability failure is carried as a warning on the
  answer, as steering and review-round open already do — CRW-793/CRW-823; case
  `TestLoopInitCarriesOnWhenThePlanWriteOnlyFailedItsDirectorySync`).

The pre-merge evaluation of the corrected head found three more, all fixed here with a red case each.

- The source-identity gate ran before the session lock on the fresh-directory branch, so a refusal
  could return without the check ever being serialized against another writer of the same session,
  contrary to c2's "every pre-write check runs inside the lock" (and the earlier correction for the
  state directory the lock creates); port: fixed (every session pre-write check, the source gate
  included, now runs inside the lock, and a refused bound init takes back only the state-root pieces
  that call itself created — see the correction below, which drops that removal; case
  `TestLoopInitWritesNothingWhenTheBoundCycleIsRefused`).
- The loser of a concurrent creation could still answer the lock's busy message when the winner
  published after the loser's whole lock budget had run out, on both the goalplan-lock and the
  session-lock paths; port: fixed (both paths now wait a bounded time for the plan to appear and
  answer the criterion's "a plan already exists at slug ..." refusal when it does, reporting the
  shared lock's own busy message only when it never appears; cases
  `TestLoopInitAnswersAlreadyExistsWhenTheLockTimesOut` and
  `TestLoopInitAnswersAlreadyExistsWhenTheSessionLockTimesOut`).
- The two timeout cases did not exercise a winner that publishes after the loser's budget: the
  session-lock case published the plan synchronously before acquisition even began, so it passed
  without covering the wait, and the goalplan-lock case published inside the acquisition window; port:
  fixed (both cases now schedule the competing publication for after the loser's budget has run out,
  and each asserts the winner's publication succeeded, so the case cannot pass on a race that never
  happened).

The next pre-merge evaluation found two more, both fixed here with a red case each.

- The refusal cleanup could delete another creator's state root: the pre-lock `Stat` results do not
  prove this call created `.crw` or its `.gitignore` (a concurrent creator can make them in the
  window), so a refused bound init could remove a `.gitignore` another init had just written, or an
  empty `sessions` directory another writer had just ensured, leaving that writer's next file open
  with `ENOENT` (a safety and data-loss class, introduced by the previous correction); port: fixed
  (the removal is gone: the refusal names only the artifacts it did not write — the plan, the created
  row and the binding — and the state root the session lock itself needs stays, exactly as the oracle
  leaves it; case `TestLoopInitWritesNothingWhenTheBoundCycleIsRefused`, which now asserts the
  artifacts init owns are absent rather than a byte-identical tree).
- The bounded waits were still too short to cover a live creator: a slow but live competing init
  (a stalled fsync, a slow source capture) could outlast the wait and be mistaken for an abandoned
  lock directory, so the loser answered the busy message rather than the criterion's "a plan already
  exists at slug ..."; port: fixed (both waits now give a loser about 15 s of grace, far beyond any
  plan write, while a lock whose holder is truly gone still ends in the busy message that lock
  documents; cases `TestLoopInitAnswersAlreadyExistsWhenTheLockTimesOut` and
  `TestLoopInitAnswersAlreadyExistsWhenTheSessionLockTimesOut`).

The next pre-merge evaluation found two more, both fixed here with a red case each.

- A state root that was a symbolic link was written through before the session check refused it:
  taking the session lock creates `.crw/sessions` and the lock file, and those creates follow a
  link, so a linked `.crw` sent them outside the workspace while the answer still claimed nothing

  `TestLoopInitRefusesALinkedStateRootBeforeWriting`).
- The loser's wait was a fixed grace period, not the competing creator's lifetime: a live winner
  stalled longer than the period (a paused process, a stalled pre-rename fsync) still outlasted it
  and the loser answered the busy message; port: fixed (the wait now follows the holder's own
  liveness — the goalplan lock's `owner.json` pid and the session lock file's pid are checked each
  round — so a live competing init is never mistaken for an abandoned lock, with a backstop for a
  holder that lives but never finishes; cases `TestLoopInitAnswersAlreadyExistsWhenTheLockTimesOut`
  and `TestLoopInitAnswersAlreadyExistsWhenTheSessionLockTimesOut`).
