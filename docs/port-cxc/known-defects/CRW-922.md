# CRW-922 — the D close's pre-write cancellation checks, and its goalplan lock-wait answer

Source: CXC v0.2.40 (`3c1459ac`) `plugins/codexclaw/components/pabcd-state/src/orchestrate-cli.ts`
`runOrchestrateCli` :466-1131 (the D close, :726-1064: the receipt check :726-736, the unbound close
:737-750, the goalplan-locked close :752-1015, the finalize :1016-1064) and `goalplanWriteLock` :806-873,
ported to Go as `internal/pabcd/cli/orchestrate_dclose.go` (the close) and
`internal/pabcd/goalplan/lock.go` (`WithGoalplanWriteLock`). The defects below are the port's own, not
the oracle's: the oracle's terminal branch is a short-lived process with no signal path, so a SIGINT ends
it at once and none of these questions arises there (the CRW-871 record states that departure). They were
found by the operator's pair evaluation of CRW-871's pull request and by the pre-merge evaluation of this
issue's pull request, and are fixed here under the port's rule for a defect that loses state (a cancelled
close wrote a state and a ledger row the operator had interrupted).

- The port ran the pre-write cancellation check of CRW-871 only at the goalplan callback's entry
  (`orchestrate_dclose.go` :348 at that revision), so a SIGINT that landed after the close had read and
  parsed the whole PABCD ledger (`orchestrateDcloseHasPabcdCloseRow`, the oracle's `hasPabcdCloseRow`
  :442-453, called from the all-done branch) was answered by completing the close: the C -> IDLE row was
  appended and IDLE was published under a cancelled invocation, which answered 0; the check now runs
  immediately before every durable effect that can be this invocation's first — the unbound state write,
  the all-done row, the recovery marker, the plan publication, the plan's own ledger rows, the IDLE state
  write and the finalization's row and marker clear — after the reads that precede each of them, and a
  close whose first write has started still finishes and answers as before; port: fixed.
- The port's D close never read `ctx.Err()` when `goalplan.WithGoalplanWriteLock` gave up with
  `Kind: locked` or `Kind: unreadable` (`orchestrate_dclose.go` :569-574 at that revision), so a
  cancelled invocation answered the busy or unreadable text with code 1 where CRW-871's other paths, and
  `orchestrateCommitPublish` for the ordinary edge, answer 130 with no output; both branches now read the
  context before they answer; port: fixed.
- The close's second goalplan write lock, the finalization pass, had the same gap and it is the one that can
  fail first for an invocation that has written nothing of its own: on a recovery retry whose session is
  already IDLE the state write before that lock does not run, so the lock's `Kind != "ok"` branch answered
  the pending text with code 0 (`orchestrate_dclose.go` :726-732 at that revision) although the invocation
  had been cancelled. That branch now reads `ctx.Err()` when this invocation has not started a write of its
  own and answers 130 with no output, as the first lock's give-up does; once it has written, the code-0
  pending answer stands, because its effects are visible and the marker the next request resumes from is on
  the session; port: fixed.
- The pre-write check's placement at the IDLE state write (the all-done retry whose row is already recorded)
  and at the finalization pass's own PABCD row had no test, so a refactor could have moved either check
  without a test failing; both are now pinned by a test that fails when its check is removed; port: fixed.
- This record's third bullet repeated the tail of the second one (`context before they answer; port:
  fixed.`) as an orphan fragment, and the second bullet's `orchestrateCommitPublish` line lost its list
  indentation; both are corrected; port: fixed.
- The session lock's give-up reported the acquisition failure (fs.ErrExist, which the caller turns into
  code 1 with an error line) even when the invocation's context had been cancelled as the wait ended, so a
  cancelled orchestrate verb that had taken no lock and written nothing answered the busy error instead of
  130 with no output; the give-up now reads the context once more before it reports the failure
  (internal/pabcd/state/lock.go, orchestrateInterruptLockContext), which is the same rule the D close's
  goalplan locks follow and the third clause of the issue's answer; a caller with no context is unchanged;
 port: fixed.
  It is pinned by `TestWithSessionLockContextCancelledAtTheGiveUpAnswersInterrupted` (the cancelled
  give-up) and `TestWithSessionLockContextGiveUpWithALiveContextKeepsTheBusyError` (the live control), and
  by the D close's own lock-wait tests for the goalplan locks.
- The finalization-row cancellation test pinned its timing by counting the invocation's pre-write checks
  rather than by the pass's own ledger read, so it still passed with the check moved in front of that read;
  it now cancels from the seam that runs immediately after the read, like the all-done case, and fails on
  that wrong-place variant; port: fixed.
- The session lock's two new give-up tests reached the give-up by exhausting the oracle's real retry schedule
  (about 250 ms each), so the cancelled case and its live control burned real waits even though the issue's
  test rule pins every timing through a seam and never a sleep, and the record's own claim that the cases
  need no sleep was therefore wrong; `orchestrateInterruptLockContext` now takes the retry schedule as a
  parameter (the two exported entries pass nil and keep `LOCK_RETRY_DELAYS_MS`), and both cases pass an
  empty schedule, so they reach the give-up on the first failed create and run in microseconds; port: fixed.
  It is pinned by the same two tests, which now assert the give-up window with no wait at all.
- The cancellation test for the IDLE state write cancelled from the all-done branch's ledger-read seam, so
  it pinned that check after the ledger read but not after the recovery state read that immediately precedes
  the IDLE write on the path it exercises, and a check moved in front of that read still passed it; the test
  now cancels from a seam that runs immediately after the recovery read, and fails on that wrong-place
  variant; port: fixed.
- The control that pins the post-write answer (a cancellation after this invocation's first write finishes
  the close) asserted only the success text, the IDLE phase and the PABCD row count, so a regression that
  skipped the plan publication, either goalplan ledger row, the cursor move or the marker clear for a
  cancelled context would still have satisfied it; it now also asserts the closed phase stays done, the
  successor is activated and becomes the cursor, both goalplan rows land in order, and the recovery marker
  and its check epoch are cleared, and it fails on a variant that skips the started row; port: fixed.
