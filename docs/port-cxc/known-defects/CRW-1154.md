# CRW-1154 — recall index ingest decided from a cursor read outside its transaction

Source: CXC v0.2.40 (commit 3c1459ac) `plugins/codexclaw/components/recall/src/ingest.ts:164,213-224` and `index-db.ts` (`msgs` has no (path, ord) uniqueness constraint); the Go side is `internal/recall/ingest.go` and `internal/recall/indexdb.go`. Found by the 10-10 CXC improvement review, A8-01.

- The oracle reads every known file's cursor before the per-file `BEGIN` and hands that read to `ingestFile`, so two refreshes that read the same cursor each append the same new lines: 2,001 messages became 4,001 rows (two rows per (path, ord)), with the cursor naming the committed count of only one of them; the duplicates skew recall results and the repeat penalty (source `ingest.ts:164,213-224`; Node v24.20.0 and the Go build both exited 0 with 4,001 rows; the preserved oracle-state `index.sqlite` held 4,001 rows for 2,001 distinct (path, ord)); port: fixed (`ingest` still lists the home and compares fingerprints without any lock, and skips the files that match, but a file that needs work gets its own `BEGIN IMMEDIATE` transaction, and `ingestLocked` reads that file's cursor and the file's state again inside it, then decides skip, append or rebuild. A refresh that waited for the write permit finds the other refresh's commit and skips; a file pruned and restored between the snapshot and the lock is rebuilt from its start; a file that vanished before the lock is skipped and left to the prune. Pinned by `TestIngestConcurrentAppendKeepsOneRowPerOrdinal`, `TestIngestAppendLandingAfterTheDecisionIsStillOneRowPerOrdinal`, `TestIngestConcurrentFirstIngest`, `TestIngestAppendAfterPruneRebuildsFromTheFileStart` and `TestIngestFileRemovedBeforeItsLockIsSkipped`).
- The cursor was trusted as given. An append now also requires the committed rows of the file to equal the cursor (`last_ord` rows, highest ordinal `last_ord - 1`); a file whose rows and cursor disagree is rebuilt from the rollout instead of continued, so a uniqueness conflict is repaired rather than reported as a failure; port: fixed (`ingestLocked`).
- `msgs` carried only a non-unique index on `path`; port: fixed (schema version 3 creates `CREATE UNIQUE INDEX idx_msgs_path_ord ON msgs(path, ord)`, which also serves the old lookups by path. A database of an older version holds only derived rows: `initializeIndex` reads the version before it applies the schema, drops `msgs`, `files`, `meta` and the two FTS tables when it differs, and re-creates them, so existing duplicates disappear and the next refresh rebuilds every file from its rollout. `recall_hit_counts` and the rollouts are not touched. Pinned by `TestIndexOpenRepairsDuplicateRows`, `TestIndexVersionResetPreservesHistory`, and `TestIndexOracle`, which applies the recorded schema change to the oracle recording).
- Enumeration of the home takes no lock, so parallel recall searches are not delayed by a refresh that is still walking the tree; the write permit is held for one file at a time, with the connection's five second busy timeout; port: fixed.
