# CRW-1198 — dispatch intents and the reconcile pass: what the decided design left to the code

Source: CRW's own design (0.5.0-alpha, issue F05), not the CXC oracle: the flow engine has no counterpart in CXC v0.2.40 (commit 3c1459ac). The rule it keeps is the bridge's own, `internal/bridge/bridge.go:186-193` (a mutation of which a byte was sent is `outcome_unknown` and is never sent again), and the creation grace is the value of `internal/relay/managed/reconcile.go` (`DefaultCreationGrace`, two minutes), which the body names. The Go side is `internal/flow/engine/{recon,recover,recovercli,resume,call,engine,tierstep}.go` (the pass, the recovery, the resumed run), `internal/flow/backend/agent/{dispatch,reconcile}.go` (the host side), `internal/bridge/appserver/fakehost/{threads,seed}.go` and `internal/bridge/appserver/testdata/schema-0.154/v2/` (the fake host and its schema copies), and `internal/bridge/appserver/{client,records}.go` (`Client.ConnectionID`). `docs/flow/script.md` describes the pass.

- The body's edit regions do not list `internal/bridge/appserver/client.go` and `records.go`, but the closed-connection proof of a lost `thread/start` needs to know which connection carried the frame, and the client is the only place that knows; port: deviation, kept visible (two fields and one accessor, `Client.ConnectionID`: ids are never reused and 0 means no connection; the backend reads it in the send hook, just before the frame is written, so a request that was never written leaves no record and is `CreationUnsent`).
- The body says a creation is sent again when a second complete listing taken at least two minutes after the connection closed is still empty. A process that did not see the close (a later run process, the cause of most of these cases) cannot know the instant the connection closed, so the pass records when it first saw the connection closed (flow row `creation_closed_seen`) and counts the grace from that sighting; the real close was earlier, so the wait is never shorter than the body's; port: deviation, conservative. A request the backend knows it never wrote needs no grace; a request of another process is closed when that process is gone (`Config.OwnerAlive`; the default compares the pid and the kernel start time in `/proc` and calls a process it cannot prove gone alive), and an intent that names no owner proves nothing.
- While the connection that carried a `thread/start` is alive and its answer pending, the body says the engine waits. The pass polls for `ResumeOptions.OpenWait` (30 s by default) and, if nothing changed, leaves the call open without an `outcome_unknown` row (the answer may still come) and holds the node for the run only; the next resume looks again; port: kept.
- A live run whose backend declares `engine.Reconciled` leaves a call whose request got no answer open (F04) and now also stops its node for the rest of the run (`recovery_hold`), but writes neither `outcome_unknown` nor the `dispatch_unknown` escalation: the outcome is not decided yet, and a call that reconcile then adopts must not have escalated. The fake backend, which has no reconcile, writes both at once. A call that finds its node in `recovery_hold` ends `held` with the new reason `recovery_hold` (nothing was sent); the body names no status for it, `held` with `input_state` is the shape the other stops use; `docs/flow/script.md` lists the reason; port: deviation, kept visible.
- `crw.tierStep(node, ...)` for a node in `recovery_hold` (or one stopped by `restore_snapshot_mismatch`) throws a TypeError before it takes a position or writes a row, so the run ends `script_error` unless the script catches it; the body says only that no tier step is taken; port: kept.
- `crw flow recover` exists in `engine.RunCLI` (`recover [--run RUN] CALL (--adopt THREAD|TURN | --absent)`), with the proofs and the evidence rows the body names, but this build keeps the journal in memory (F06), so a second process has no journal to open: `engine.RecoverEnv` is a hook that nothing installs yet and the command says so (exit 2). `cmd/crw/main.go` is unchanged: `flow` already reaches `engine.RunCLI`; port: deviation, kept visible (F06 installs the hook with the stored journal and the App Server connection).
- `--absent` never sleeps: when the grace has not passed it refuses and tells when the second listing is due, and the sighting of the closed connection is the one row a refused recovery leaves. `--adopt THREAD` checks the identity (the call's cwd, a root thread, the recorded source for a fork) and records the history it found, but leaves the judgement of that history to the operator, so it can adopt a thread that reconcile calls foreign; `--adopt TURN` refuses a turn whose readable marker is another operation's; port: kept.
- A resume replays a call the journal ended `completed`, `null_model`, `refused` or `outcome_unknown` when the prompt, the schema and the pair are the same (`Config.Resume`), and runs every other call live. That is the part of the resume rule (F07) that the F05 scenarios need to be true (a completed build is not sent again when its fix turn is recovered); the effect proofs, the working snapshots, the joins and rule (g) are F07's, so a held call is not replayed and runs as a call of its own in this build (`TestHeldCallNotReconciled` proves only that the first step reads nothing of the host); port: deviation, kept visible.
- A call that has a `thread_started` or `fork_started` and no turn, written by a process that died, is superseded by the resume (the body: "nothing to decide for it") and the position runs again on a thread of its own; only a thread that reconcile or an operator adopted (`recovered: true`) goes on to its first turn. The superseded thread stays on the host unused; port: kept.
- A new attempt (a call that starts a thread of its own) first ends the calls the previous process left open on its node (and the call's own earlier rows when its input changed) as `superseded` (`superseded_by_attempt`); a turn they may still run is interrupted and the interruption confirmed with `thread/read` first, and a turn that cannot be confirmed holds the new call. The new `prepared` row is written before the old call's `superseded` row (the allocation of the new attempt is decided from the journal), so the order the body asks for - the old turn ended, then the new thread - holds for the host and for `thread_requested`, not for `prepared`; port: kept.
- The tokens a recovered call reports (`CallResult.meta.tokens`) are those of the turns the recovering process read; the turns of the dead process were never added up because their usage notifications died with it (`tokensUnmeasured` marks a harvested turn); port: kept.
- The fake host is extended with the answers the scenarios need and no field the 0.154 host lacks: `DropAck` (the host acts on a `thread/start`, `thread/fork` or `turn/start` and the connection is closed instead of answered; the turn of such a request keeps running, as a host's turn does), `Seed` (a thread another caller made, or one placed late, with its turns, `forkedFromId`, `createdAt` and source), `thread/archive`, `thread/list` with the `sourceKinds`, `archived` and `cwd` filters and a capped page size, `Clock`, `TurnPlan.NotLoaded` and `Detached`, and the thread status `active` while a turn runs. `TestFakehostThreadMatchesSchema` validates every one of them against the pinned 0.154 schema copies, to which `ThreadArchiveResponse.json` and `TurnInterruptResponse.json` were added unmodified from `codex app-server generate-json-schema` output.
