# CRW-1260 — a created report names the V2 child by its agent path

Source: CXC v0.2.40 (commit 3c1459ac) `plugins/codexclaw/components/subagent-config/src/fallback-dispatch.ts` (the dispatch ledger's
`report`, whose `agentId` is checked as an identifier); the Go port's `dispatchReport` and `dispatchID` (`internal/role/dispatch_ledger.go`),
`createdCheckReporter`, `createdCheckComplete`, `createdCheckStop` and `createdCheckTie` (`internal/role/created_check.go`) and the new
`internal/role/created_agent_path.go`. Found by the 10-11 placement study, prep round 2 (`/state/crw/mgmt/placement-study/HARNESS.md`,
"Prep round 2", cells recorded as `refused_invalid_agent_id`).

- Under multi-agent V2 `spawn_agent` returns the child's agent path (`{"task_name":"/root/<task>"}`) and no thread id, and the dispatch
  helper's `created`, `complete`, `failed` and `stopped` reports accepted only a thread id (`invalid agentId`), so no V2 child could be
  recorded and the review that followed could not complete ("this child is not tied to its issued spawn"). The oracle has no V2 spawn
  contract at all; port: fixed (an `agentId` written as an agent path, a string that starts with `/` and has one or more
  `[A-Za-z0-9_-]` segments, is resolved at the start of the report to the thread id in the host's native thread database: the thread whose
  `threads.agent_path` is the path and which is a `thread_spawn_edges` child of the report's session, or, for a host database without that
  edge table, whose spawn source names the session as its parent. The report then runs on the thread id exactly as it does for V1: the
  record holds the thread id, never the path, so the receipt, the child tie, the cleanup and every later report (by id or by path) are
  the ones of a V1 child. A path that names no child of the session, a database without `agent_path`, a database that cannot be read, a
  path of several children none or more than one of which carries the attempt's marker, and a malformed path (`invalid agentId`) are
  refused with their reason and the usual correction, and write nothing. A task name the session used twice is narrowed by the attempt's own
  evidence, strongest first: the child the attempt already records, the child the host's result of the issued call names, and the one
  thread whose first message carries the attempt's marker (a partial-fork child inherits the parent's first message, so the marker
  cannot name it); anything else stays ambiguous and is refused. Pinned by `TestCreatedAgentPathReceiptMatchesThreadId` (V1 by id and V2 by path, fresh and partial
  fork), `TestCreatedAgentPathRefusals`, `TestCreatedAgentPathReusedNameIsNarrowedByMarker`, `TestCreatedAgentPathReusedNameOfPartialForkChildren` and
  `TestCreatedAgentPathFailedAndStoppedReports`).
- A child forked from the session starts with a copy of the history it was forked from, so the native database's `first_user_message` of a
  partial-fork child is the parent's first message and carries no marker of the attempt; the created check refused every such child
  ("its first message carries no marker of this attempt"), in V1 as in V2; port: fixed (the marker refusal is not applied to a child whose
  rollout's first line, the `session_meta`, names the session as `forked_from_id`; only the host's own result of the issued spawn call ties such a
  child, and without it the receipt stays `unverified`, which cannot satisfy independent review. A child forked from another thread, or
  not forked, keeps the refusal. Pinned by `TestCreatedForkedChildFirstMessageExcuseIsNarrow` and the partial-fork rows of
  `TestCreatedAgentPathReceiptMatchesThreadId`). The first message of a forked child was read from the rollout's metadata recorded in
  the study's evidence, not from the real database, which no test reads; a live probe of a partial-fork child's `first_user_message`
  is open (the change is harmless if it already carries the marker).
- A managed spawn of a full-history fork is denied by the hook ("managed fallback requires a fresh context", the oracle's rule,
  `fallback-dispatch.ts`), so a full-fork child is never issued and its created report is accepted only with reconciliation evidence
  (receipt correlation `unissued`, which cannot satisfy independent review), by agent path as by thread id; port: kept (pinned by
  `TestCreatedAgentPathFullForkRecordsOnlyByReconciliation`; the full-fork acceptance row "receipt verified" of CRW-1260 therefore stays
  with the hook's fresh-context rule).
- The placement study saw a V2 child on `inferhub/kimi-k3` without an effort when only `agent_type "reviewer"` was given and took it for a
  pool default. It is the configured reviewer role (`~/.crw/subagents.json`: model `inferhub/kimi-k3`, effort null) which the hook filled
  in; the hook already applies a role's pair to a V2 input that names only `agent_type` (a fresh or partial-fork child, with or without
  the native task ciphertext), keeps the pair the caller picked, and fills nothing into a full-history fork (codex-rs rejects model and
  effort there); port: kept (no hook change; pinned by `TestSpawnHookV2AgentTypeOnlyTakesTheRolePair`). A role left on the main model has
  no pair to fill and the hook sets neither field, in V2 as in V1 (`TestSpawnHookV2RoleOnMainModelFillsNothing`); whether a fresh V2
  child then inherits the parent's pair is the host's and stays with the F14 design (flow-bound helper pairs) and a live probe.
- The host's result of a V2 spawn call is not the V1 `CollabAgentToolCall` item: `spawn_agent` is a plain `function_call` of the
  parent's rollout whose `function_call_output` is `{"task_name":"/root/<task>"}` alone, and the thread it created is named by an
  `event_msg` `item_completed` of type `SubAgentActivity` (kind `started`, `id` the call's id, `agent_thread_id`, `agent_path`) of the
  session. The created check reads that event as the call's completed result, alongside the V1 item, so a V2 child (fresh or partial
  fork) is tied to the issued call (`spawn-result`) and a reviewer's complete is accepted; a call with no such event stays `unverified`
  and one that made another thread refuses the report. Pinned by `TestCreatedAgentPathV2ResultOfTheIssuedCallOnly` and the V2 rows of
  `TestCreatedAgentPathReceiptMatchesThreadId`, whose fixture is the line shapes of the study's rollouts
  (`/scratch/crw/placement/_smoke/prep2b/`); port: fixed.
- A native V2 task is host ciphertext, so the dispatch marker the claim handed out is invisible to the spawn hook and no managed
  source resolved: the call was never issued and its created report was refused (only reconciliation, which cannot satisfy independent
  review). The call's plaintext `task_name` is what the hook can read, so a V2 call names its dispatch there, and the claim opts the
  attempt in to that (`{"action":"claim",...,"v2TaskName":true}`: the attempt records `v2TaskName: true`, omitted otherwise so a claim
  without it keeps the oracle's record, and the claim's answer adds `taskName`, the dispatch id; a value that is not a boolean is
  refused). The hook issues a fresh or partial-fork call whose message has the shape of a native ciphertext (never a full-history fork)
  to the current claimed attempt of the active dispatch of the session whose id is the call's `task_name`, when that attempt opted in and
  its role is one the call's `agent_type` can carry (worker or executor: executor; architect or reviewer: that role; explorer: explorer,
  reviewer or architect, since a `CRW-ROLE` header in the task wins over an explorer type and the delegation reference transports a
  reviewer or architect that way where the live schema has no such type; any other or no type: any role), exactly as it issues the
  attempt a marker names (the second call that names the same attempt is refused "attempt already issued to another native call", a
  redelivered event keeps its attempt, and a tool use id an earlier attempt of the dispatch was issued to is not the current attempt's).
  The ciphertext is passed on unchanged and the attempt's candidate replaces the model and effort as for a marker-carrying spawn; the
  created check then ties the child to the issued call by the host's result of that call. Every other call is allowed unmanaged, as
  before: one that names no dispatch of the session waiting for its spawn, one whose record cannot be read, and one whose `task_name`
  equals the id of a claimed dispatch whose claim did not opt in. That last is a direct native call (the user may ask for one, and any
  name is valid for it): it keeps its own model and effort and consumes no issuance, and an attempt already issued to another call does
  not deny it. The hook resolves the dispatch root (`git rev-parse --show-toplevel`) only when an entry the `task_name` can name exists
  under the workspace or one of its parents, so a ciphertext call that names no record runs no git, as in the CXC hook (the corpus case
  `hook__pre-tool-use-attaching-skills__v2_ciphertext_preserved_with_routing` replays its recorded calls unchanged;
  `TestManagedSpawnNamedRunsNoGitWithoutARecord`). The session's other records are never a reason to issue a call that did not name its dispatch: an earlier form of this fix
  issued an unnamed call to the session's one claimed attempt, and an unrelated partial fork spawned while a review was claimed was then
  tied to the review by its own call's result and completed it (the call's result proves the call made the child, not that the call was
  the attempt's), and two unrelated parallel calls that both picked the attempt had the second one denied; the next form bound a call by
  its `task_name` alone, which turned a direct call that happened to use a claimed dispatch's id into a managed one (its model and effort
  replaced, the issuance consumed). Pinned by `TestSpawnHookV2CiphertextSpawnIssuesTheAttemptItsTaskNameNames` (claim, the hook on a
  ciphertext input naming the dispatch while another dispatch is claimed, the V2 result, created by path, complete; the `fork_turns
  none` row is a fresh child whose first message is checked for the marker, one without it refused, and the `fork_turns 2` row a partial
  fork), `TestSpawnHookV2CiphertextSpawnLeavesAnUndecidedCallUnissued`, `TestSpawnHookV2UnnamedCiphertextCallCannotSatisfyTheReview`
  (a default-type, reviewer-type or untyped partial fork that does not name the dispatch is not issued and its child cannot satisfy the
  review), `TestSpawnHookV2ParallelUnnamedCallsAreNotDenied`, `TestSpawnHookV2TwoCallsNamingTheDispatch`,
  `TestSpawnHookV2TaskNameAloneDoesNotManageADirectCall`, `TestSpawnHookV2ExplorerTransportIssuesTheNamedDispatch` and
  `TestDispatchClaimV2TaskNameOptIn`; port: fixed (what the oracle never had). Whether codex accepts every dispatch id as a task name (the
  dispatch id's characters are the ones its agent-name check names) is open for a live probe.
- The V2 rule of the managed path reached the caller only through the delegation reference: the SessionStart notice and the reminder a
  direct spawn of a role with a fallback gets carry the oracle's guidance (prepend the marker), which a V2 caller cannot follow, and the
  dispatch card's V2 example uses `task_name:"model_probe"`. Port: fixed by a CRW sentence, `role.V2TaskNameNote` ("CRW V2: claim with
  v2TaskName:true and spawn with task_name equal to the dispatchId."), said after the CRW-1257 sentence in the SessionStart notice and
  after the guidance in the direct-spawn reminder of a V2 call (a V1 call's reminder stays the oracle's text, as the contract fixture
  records it). The oracle's guidance and card are unchanged; the sentence is short because the notice, the guidance and the card share
  the oracle's 4096-unit budget (with every role on a fallback and the longest card the notice is under 4096 units). Pinned by
  `TestFallbackNoticeStatesTheV2TaskNameRule` and `TestSpawnHookV2DirectCallReminderStatesTheTaskNameRule`; the recorded oracle answers
  that change are the startup notices (`internal/role/testdata/fallback/notices.json`, the contract note `CRW-1180.json` with its
  guidance digest) and the two recorded route steps of a direct V2 spawn (`route: fallback notice` step 4, `route: v2 ciphertext` step 5,
  `spawnRouteV2Note` in `hook_route_test.go`), whose expected answer is the recorded one with the sentence after the guidance.
