# CRW-692 — the pump's DAG, capacity and audit alert sources

Source: CRW's own design, not the CXC oracle (CXC v0.2.40, commit 3c1459ac, has no management pump). The predecessor is the management tools' `mgmt_pump.py` (`dag_events`, `capacity_events`, `eval_events`), which this issue replaces in Go. The Go files are `internal/manage/pump_signals.go` (the three sources), `internal/manage/pump.go` (the registry, the two settings, the dry flag and the commit step) and `internal/manage/capacity.go` (`capacityEvaluate`, `capacityEvaluation.Commit`, the alert epoch).

Settings (Section "pump" of manage.json, both optional, a missing or non-positive value keeps the default): `dag_review_seconds` (default 600) is the interval between DAG reviews; `capacity_seconds` (default 1800) is the interval between capacity judgements. The audit queue `<state_dir>/audit/alerts.jsonl` is read every round, from the byte offset kept in the pump state (`offsets.signal_audit`).

- The predecessor kept the last DAG text and the last capacity text and sent again whenever the wording changed, and a failed or unmeasured review read as "no anomalies" (the `info` event); port: fixed (the DAG key is the sorted set of anomaly tuples kind, plan, node, issue, kept with a change counter under `cursors.signal.dag.*`, so a reworded anomaly is not sent again, an error round or a review with an unmeasured check never clears, a review with an unmeasured check can add an anomaly but drops none, and A, clear, A is three events `signal_dag#1..3`; the review runs with `dagHostNoState(ctx, true)` so its rollout offsets are not saved before the pump's pending events are, see CRW-688; pinned by the `TestPumpSignalDag*` tests).
- The predecessor's capacity state moved before its alert was recorded, so an alert could be lost to a pump that ended between the two; port: fixed (decision of the coordinator after the CRW-692 judge: `Capacity` is split into `capacityEvaluate`, which reads and writes nothing, and `Commit`, which saves the alerted state; the pump order is evaluate, save the pending events, commit; an event id is `signal_capacity#<plan>@<alert epoch>:<waiting digest>`, the epoch counts a plan's alerts from the last committed state, so an evaluation whose commit was lost is judged again under the same epoch and the same id and the pending/sent dedupe absorbs it, while a `realert_hours` re-alert is the next epoch; a failed commit is logged and isolated and the next read repeats it; pinned by the `TestPumpSignalCapacity*` tests, among them the crash between the pending write and the commit, each save failing, the periodic re-alert and the dry run). The waiting-set digest in the id is an addition to "plan and epoch": a waiting set that changed before a lost commit was repaired is a new alert rather than one the sent set swallows. Two guards were added after the verification of the first head. The capacity state file carries a `version`, and a commit is made under a lock and only against the version its evaluation read: a commit that arrives after the command line (or another evaluation) saved a newer state is refused with `errCapacityStateMoved`, logged, and the next read judges the newer state, so a late commit can never roll an epoch back (`Capacity` itself judges again, at most three times). The epoch in an event id comes from the pump's own record per plan (`cursors.signal.capacity.epoch.<plan>`: the state epoch the alert was judged on, the epoch used, the waiting digest, whether the commit was made), saved with the pending events: a judgement repeated over an uncommitted record reuses its epoch, and any other alert takes an epoch above the record's, so a plan removed from the settings and registered again, or a lost `capacity-state.json`, alerts under a new id instead of the id already sent (pinned by `TestPumpSignalCapacityRemovedAndReaddedPlanAlertsAgain`, `LostStateFileAlertsUnderANewId`, `StaleCommitKeepsTheNewerState` and `DelayedCommitDoesNotRollBackTheCommandLine`).
- The audit alert queue is read by byte offset like the predecessor's `eval_off`, from the start of the file the first time (the queue is consumed, so the backlog is not history), and an event is one low event per complete line with the id `signal_audit#<start offset of the line>`; port: kept in shape, fixed in the edges (a half-written last line is skipped and the offset stays at its start, two identical lines are two events, a blank or malformed complete line is passed over, and a file that shrank, or whose identity (device and inode of the open file, kept as `cursors.signal.audit.file`) changed whatever its size, restarts at its start under a new epoch so its ids cannot collide with the old file's; the supported rotation is a rename or truncate of the queue file, a state that predates the identity adopts the file it finds, and an in-place rewrite that keeps both the inode and a size at least the read offset is not detected; an alert names at most three defects, each cut at 200 characters, as the predecessor did).
- One source failing is logged in `pump.log` and its read is made again on the next round; it blocks no other source (`Sources[name]` stays the read status alone; pinned by `TestPumpSignalOneSourceFailingDoesNotBlockTheOthers` and `TestPumpSignalCapacityFailingDoesNotBlockDagAndAudit`).
- The issue's end condition "PR CI all green" is replaced by the integration gate: the integrator's `crw-dev ci local` on the merged tree (`verification-record/1` PASS) is the end condition, together with `go test -count=1 ./internal/manage`, vet, gofmt and `crw-dev ci validate`; internal work opens no pull request.
