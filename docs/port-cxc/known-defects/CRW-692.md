# CRW-692 — the pump's DAG, capacity and audit alert sources

Source: CRW's own design, not the CXC oracle (CXC v0.2.40, commit 3c1459ac, has no management pump). The predecessor is the management tools' `mgmt_pump.py` (`dag_events`, `capacity_events`, `eval_events`), which this issue replaces in Go. The Go files are `internal/manage/pump_signals.go` (the three sources), `internal/manage/pump.go` (the registry, the two settings, the dry flag and the commit step) and `internal/manage/capacity.go` (`capacityEvaluate`, `capacityEvaluation.Commit`, the alert epoch).

Settings (the `pump` object inside the `manage` object of the selected CRW configuration file: `--config`, else `CRW_CONFIG`, else `${XDG_CONFIG_HOME:-$HOME/.config}/crw/config.json`, i.e. `{"manage": {"pump": {"dag_review_seconds": 600, "capacity_seconds": 1800}}}`; a standalone `manage.json` is not read, and a top-level `pump` is ignored. Both are optional, a missing or non-positive value keeps the default): `dag_review_seconds` (default 600) is the interval between DAG reviews; `capacity_seconds` (default 1800) is the interval between capacity judgements. The audit queue `<state_dir>/audit/alerts.jsonl` is read every round, from the byte offset kept in the pump state (`offsets.signal_audit`).

- The predecessor kept the last DAG text and the last capacity text and sent again whenever the wording changed, and a failed or unmeasured review read as "no anomalies" (the `info` event); port: fixed. The standing anomalies are kept as the sorted set of tuples kind, plan, node, issue and, for a parent's duplicated tool results, the call id, with a change counter under `cursors.signal.dag.*`, so a reworded anomaly is not sent again, an error round or a review with an unmeasured check never clears, a review with an unmeasured check can add an anomaly but drops none, and A, clear, A is three events `signal_dag#1..3`. The one check that is unmeasured for good does not count (CRW-1272): `released_before_predecessor` is unmeasured in every review over a store that holds a plan, because the scheduler exports no edge reading with the time an edge became satisfied, and no anomaly of its kind is ever reported, so it says nothing about the round; counting it would keep every set from being cleared once the store holds a plan (`dagReviewCheckIsStandingGap`). The alternative, letting only the unmeasured checks that concern an anomaly kind in the set block the clear, was not taken: a check name (`parent_rollout:<id>`, `child_turn:<id>`, `dag_review_state`, `host_scope`) does not name the anomaly kinds it could have hidden, so a map from checks to kinds would be a second rule to keep in step with the review, while a check that is unmeasured only for the round (a failed read, a rollout that could not be read, an ambiguous node, a table the store predates) keeps blocking the clear exactly as before (pinned by `TestPumpSignalDagClearsWithARealPlanPresent`, a real `DagReview` over a store with a plan, and `TestPumpSignalDagTransientUnmeasuredStillBlocksClear`). A parent's relay call is recognized by its program word: a bare parameter expansion such as `$RELAY`, `codex-session-relay` by basename, or `crw` followed by `relay`, each also after `exec` or inside a list, a pipeline or a substitution. A wrapper script that runs the relay inside (`/tmp/s6r dag-accept ...`, `bash -c '...'`) is not recognized, and the refusal the parent got through it is not reported: the review cannot tell what the script runs, and reading every output that carries a refusal envelope would report the refusals of commands that are not the relay's (pinned by `TestDagHostRelayCommandFormsAreTheDocumentedOnes`). A parent's relay refusal is not a standing anomaly but an occurrence: the host reader gives every refusal of a parent the same kind and issue and an empty plan and node, so a set could hold one refusal for good and hide every later one. The review therefore keeps its rollout offsets and reported call ids in the pump's own state (`cursors.signal.dag.refusal_offsets`, handed to `DagReview` through a context offset store instead of its `dag-review-state.json`), saved in the same write as the pending events, and each round's new refusals are one urgent event `signal_dag_refusals#<n>` (the counter is `cursors.signal.dag.refusals`) that is never part of the set; a rollout seen for the first time reports none of its history, a review that fails after it moved the offsets gives them back, and the pump takes no state-directory lock or offset file of the review's own. The first-sight boundary (the size at which a rollout's history ends) is not the size at each reading that finds no offsets: it is written once to `<state_dir>/pump-dag-pins.json` (atomic, fsynced, never through a symlink, never in a dry run) before the first reading classifies any refusal against it, and dropped once the saved pump state holds the rollout's offsets. The boundary's size, the rollout's identity (device and inode, compared by inode, since a remount may renumber the device of the one file system a path is on) and the scan come from one open descriptor, and the boundary is kept with that identity, so a rollout renamed over or cut short between the stat, the pin and the scan cannot lend one file's boundary to another's reading; a boundary of the same file is never past what a first-sight reading's own size would be, so writing it before the pending events can only make a reading report more. A kept boundary of another file, or one past the end of the file the path now holds (a replaced or shortened rollout), is not applied: the new file's boundary becomes 0 and every refusal it holds is reported (a boundary written before identities were is taken for the file the path holds while it is not past its size). Saved offsets carry the identity too (`files`, in the pump's offsets and in `dag-review-state.json`): a path that holds another file is read from its start whatever its size, and a reading whose file ends before the size it started at (cut short while read) is unmeasured and moves nothing. A rollout line without its newline is still being written and is not parsed even when it holds complete JSON: the call it answers stays pending, the resume offset stays at the call line, and the refusal is reported once the newline is there, also after a restart. A pump that ends, or whose state save fails, before its offsets reach disk therefore reads again against the same boundary, so a refusal appended during or after the first reading is reported by the next round instead of being taken for history. A boundary that cannot be written (or a boundary file that cannot be read) leaves that rollout's refusal reading unmeasured and records no offsets for it. The limits that remain are the definition of history itself (a refusal whose answer was complete at the size the first durably written boundary records is history) and an in-place rewrite of a rollout that keeps its inode and grows back past a kept boundary or offset between two readings, which is not detected (Codex appends to a rollout and never rewrites it). Pinned by the `TestPumpSignalDag*` tests, among them `LaterRefusalOfTheSameParentIsReported`, `IdenticalRefusalsAreEachReported`, `LaterDuplicateOutputIsReported`, `FailedReviewKeepsTheRefusalOffsets`, `FirstSightRefusalSurvivesALostPendingWrite`, `RefusalAfterAFailedFirstSaveIsReported`, `HistoryStaysOutAcrossALostState`, `UnwritablePinTakesNoRefusalReading`, `DryRunWritesNoPin`, `PinIsDroppedOnceTheOffsetsAreSaved`, `RefusalOfAFailedRoundIsSavedUnderTheSameId`, `BoundaryPastTheEndIsTakenAgain`, `RefusalWithoutItsNewlineWaitsForIt`, `RefusalWithoutItsNewlineSurvivesAFailedSave`, `ReplacedRolloutNeverTakesTheOldBoundary` (rename before and after the pin, truncation after the pin, each with and without a failed first save) and `ReplacedRolloutLongerThanItsOffsetIsReadFromItsStart`.
- The predecessor's capacity state moved before its alert was recorded, so an alert could be lost to a pump that ended between the two; port: fixed (decision of the coordinator after the CRW-692 judge: `Capacity` is split into `capacityEvaluate`, which reads and writes nothing, and `Commit`, which saves the alerted state; the pump order is evaluate, save the pending events, commit; an event id is `signal_capacity#<plan>@<alert epoch>:<waiting digest>`, the epoch counts a plan's alerts from the last committed state, so an evaluation whose commit was lost is judged again under the same epoch and the same id and the pending/sent dedupe absorbs it, while a `realert_hours` re-alert is the next epoch; a failed commit is logged and isolated and the next read repeats it; pinned by the `TestPumpSignalCapacity*` tests, among them the crash between the pending write and the commit, each save failing, the periodic re-alert and the dry run). The waiting-set digest in the id is an addition to "plan and epoch": a waiting set that changed before a lost commit was repaired is a new alert rather than one the sent set swallows. The digest is the whole SHA-256 of the waiting set, in the id and in the pump's record alike: a prefix of it is shared by different sets (the first eight hex digits of `[CRW-109982, CRW-509982]` and of `[CRW-117419, CRW-517419]` are both `35c15e01`), and with the prefix a changed set whose first alert's commit was lost was taken for that alert and absorbed into the id already sent (pinned by `TestPumpSignalCapacityWaitingSetsSharingADigestPrefixAreTwoAlerts`). Two guards were added after the verification of the first head. The capacity state file carries a `version` and a `revision` (a random token drawn for every write), and a commit is made under a lock and only against the generation its evaluation read (absent file, version and revision, or the digest of an undecodable file; a file that cannot be read matches nothing): a commit that arrives after the command line (or another evaluation) saved a newer state, or after the file was lost and written again from nothing to the same version, is refused with `errCapacityStateMoved`, logged, and the next read judges the newer state, so a late commit can never roll an epoch back (`Capacity` itself judges again, at most three times). The lock is taken without blocking and retried for at most 200 ms; a lock another writer holds longer fails that commit with `errCapacityStateBusy`, which the pump logs as the source's commit failure while the round goes on to the other sources, the delivery and the parent queue, and the next read converges on the same id (pinned by `TestCapacityCommitIsRefusedAcrossAStateFileGeneration`, `TestCapacityCommitOverAnUnreadableState` and `TestPumpSignalBusyCapacityLockDoesNotHoldUpTheRound`). The commit's conflict check and the alert's identity are separate. The check is against every write of the file (version and revision, above); the identity follows the plan alone: each plan entry of the capacity state carries a `lifecycle`, a random name (`crypto/rand`) drawn once when the entry is made and carried forward by every save that keeps the entry; it is never derived from a stamp of the file, so a plan registered again or a state file lost or written again without the plan makes the entry anew under a name no earlier entry had. For a plan the state holds no lifecycle for (absent, or an entry written before entries carried one), the pump writes the lifecycle its evaluation proposes to its own state (`cursors.signal.capacity.lifecycle.<plan>`: the name, whether the entry was held, and the generation of the state it was proposed on: the stamp, the lineage and the version) in the same save as the pending events, so before the commit that stores exactly that name, and proposes it to every later evaluation, which takes it only while it holds. To tell, the state file carries a `lineage` (a random name drawn by the write that makes the file from nothing, i.e. over no file, an undecodable one or one without a lineage, and carried by every later write), the `origin` (the stamp of the file that write replaced) and `removed` (per plan, the version of the write that removed the plan's entry; a write that makes the entry again drops it), and a file without a revision is stamped by its content. The proposal holds for the same case (still absent, or still held without a lifecycle) on the generation it was proposed on, or on a later write of that lineage (for a proposal made on a file without a lineage, the lineage that started over that very file) of no older version that removed no entry of the plan since; a proposal made on no file never holds, since a file made and lost again leaves nothing to tell it by. The pump therefore makes no proposal on a state without a lineage: when plans are configured, its read first writes such a state (no file, one that cannot be decoded, one written before files carried a lineage) again as it reads, which changes no entry, persistence clock, alerted set or epoch and only starts the lineage (`capacityStateEstablishLineage`; never in a dry run, never with no plan configured), and judges on that. A file lost, or lost and written again byte for byte (an empty file, a file an older `crw` wrote), then takes a lineage of its own at the next read and is not the generation the proposal was made on. A state the pump cannot use is not a failed read: the write that would give it a lineage fails (another writer holds the lock past 200 ms, the lock cannot be opened or written), or nobody can read it (a directory at its path, a file without read permission as a run under another user leaves it). Its plans are judged on the state as far as it could be read (one that cannot be read reads as empty), the read is logged, the source's status stays `ok` and no commit is made over it. Each alert so judged carries the pump's own identity for such a state, the lifecycle `unusable-state:<SHA-256 of the plan and the whole waiting digest>` (a lifecycle a state holds is a random base32 name, which holds no colon), and the pump's record of the plan is matched by the waiting set alone: a record of the same set that is unsettled (this alert judged on an earlier read, or the pump's alert whose commit has not landed) or that was first judged inside the `realert_hours` window (an alert committed before the state became unusable; the record keeps that time as `at`) gives its epoch and stays as it is, so the event carries the id already pending or delivered and the pump's dedupe absorbs every repeat; any other alert (no record, another waiting set, a record whose plan left the settings, which clears its time) takes the next epoch, first judged at that read. While the state stays unusable the same set is not alerted again, whatever `realert_hours` says; a set that changes is a new alert, and one that comes back after another is alerted again, as on a usable state. The first judgement on a usable state takes such an alert over: an unsettled record of the same waiting set judged while the state could not be used, first judged inside the `realert_hours` window, on a state that records no removal of the plan's entry since it last made it (`removed`), keeps its epoch and its id, and the record takes the state's lifecycle and base, so the commit stores the alert and every retry continues under the state's lineage; the alert is not delivered again. A plan whose entry the command line made and removed meanwhile, or that left the settings while the state could not be used, is a new generation and alerts under a new id; a record of an unusable state's alert is settled by the first usable read past its `realert_hours` window, and the same set alerted at the first usable read past that window is the periodic re-alert falling due. Under the default `persist_minutes` a state that cannot be read never alerts, since it cannot keep the persistence clock; a state without a lineage that can be read but not written alerts on the clock it holds. The pump's send path settles the repeats before Deliver: `pumpCollect` adds no event whose id is pending or in the sent set (which is never pruned), and a batch's logical id is the digest of its event ids (`pumpBatchID`), under which Deliver reconciles an attempt whose outcome is unknown instead of sending it again. A batch the ledger proves refused is sent again under `<id>-m<count>` (CRW-1273, the rule of the parent queue) and parked after three refusals of one id. Round 9 judged nothing on such a state, so the alert reached nobody until the state could be used again, and before round 9 the pump sent the same unchanged alert again under the next epoch at every read while the commit kept failing (pinned by `TestPumpSignalCapacityUnusableStateAlertsExactlyOnce` over a lock that is a directory, a lock without write permission, a directory at the state path and a file without read permission, each four reads and then two usable reads through the real Deliver path to a fake bridge that is asked for one send, `TestPumpSignalCapacityAlertMadeBeforeTheStateBecameUnusableIsNotSentAgain` for an alert committed before the fault and one whose commit is still failing, `TestPumpSignalCapacityUnusableStateKeepsTheAlertGenerations` for the plan leaving the settings, the command line making and removing the entry, its no-op save, a changing waiting set, a hold that outlives the window and an outage past `realert_hours`, `TestPumpSignalCapacityAbsentStateWhoseCommitKeepsFailingAlertsOnce` with a writer holding the lock, a lock that cannot be opened and a process that ends before every commit, and `TestPumpSignalCapacityUnreadableStateAlertsOnce`, both requiring exactly one id while the state cannot be used, `TestPumpSignalCapacityStateWrittenAgainByteForByteEndsTheProposal` for a file without a revision, an empty file and a revision without a lineage, `TestPumpSignalCapacityLineageIsWrittenOnlyBeforeAJudgement` and both bases of `TestPumpSignalBusyCapacityLockDoesNotHoldUpTheRound`). So a commit that was refused because a write in between left the plan's entry alone (the command line's no-op save, or one that made and removed another plan's entry) or never made (a crash, a failed save) is retried under the same lifecycle, while a proposal whose plan entry was made and removed in between (the command line registering, then dropping the plan before the pump's retry), or whose state file was lost, or written again from nothing, does not hold: the evaluation draws a fresh lifecycle and the alert takes a new id instead of being absorbed into one already sent. Whatever does not hold can only send an alert again under a new id, never absorb one. The proposal is dropped once the state holds a lifecycle for the plan (the commit succeeded, or a later read finds one) and when the plan leaves the settings, and each measured read writes it again with the generation it was taken on (pinned by `TestPumpSignalCapacityEntryMadeAndRemovedByTheCommandLineEndsTheProposal`, `RefusedCommitThenEntryMadeAndRemovedEndsTheProposal`, `StateLostBeforeTheFirstCommitEndsTheProposal`, `ProposalOutlivesWritesThatLeaveTheEntryAlone`, each on a committed and a pre-revision empty state, `TestCapacityCommitKeepsTheLineageAndRecordsRemovedEntries` and `TestCapacityLifecycleProposalHolds`). The epoch in an event id comes from the pump's own record per plan (`cursors.signal.capacity.epoch.<plan>`: the state epoch and the plan's lifecycle the alert was judged on, the epoch used, the waiting digest, whether the alert is settled), saved with the pending events: only a retry of the same alert (an unsettled record, the same lifecycle, base epoch and waiting set) reuses its epoch, so a pump commit refused because the command line saved in between without alerting the plan (a no-op or unrelated save) converges on the pending or sent id at the next read; a record whose alert a later read finds in the state (a commit whose record save was lost, or the command line's own alert) is settled, a plan the report no longer judges has its record settled, and any other alert takes an epoch above the record's, so a plan removed from the settings and registered again, or a lost `capacity-state.json`, alerts under a new id instead of the id already sent, also when the first alert's commit had failed (pinned by `TestPumpSignalCapacityRemovedAndReaddedPlanAlertsAgain`, `UncommittedAlertIsNotReusedByALaterGeneration`, `LostStateFileAlertsUnderANewId`, `LostStateAfterALostCommitMarkerAlertsUnderANewId`, `StaleCommitKeepsTheNewerState`, `DelayedCommitDoesNotRollBackTheCommandLine`, `NoopCommandLineCommitKeepsTheAlertId`, `NewPlanKeepsItsAlertIdAcrossANoopCommandLineCommit` and `CommitFoundInTheStateSettlesTheRecord`). The capacity state is written like the pump state: the temporary file is fsynced before the rename and the directory after it (a sync that fails is an error and leaves the previous state), so a commit the pump records as made is not rolled back by a power loss beside that record (pinned by `TestCapacityCommitIsDurableWhenItReturns` and `TestCapacityStateWriteWithAFailedSyncKeepsThePreviousState` over a recording file-system seam). A write whose directory sync fails after the rename is an error although the file was renamed, so a power loss can still take it back; the pump's capacity read therefore syncs the state directory before it builds on what it read (settles an alert record, drops a proposal), and a sync that fails makes the read unmeasured: a commit that is not durable is not taken for made, and if a power loss takes it back the retry is under the same proposal and id (pinned by `TestPumpSignalCapacityUnsyncedCommitIsSettledOnlyOnceDurable`, with the sync failing again and recovering). The command line prints the report of such a write all the same, with the sync failure as a warning on stderr and exit 0: the renamed state already records the alerts the report carries, so the pump's next read finds them alerted, and a report dropped with exit 3 left them reported to nobody until `realert_hours`; a write refused before its rename still prints no report and exits 3 (pinned by `TestCapacityCommandLineReportsAnAlertWhoseDirectorySyncFailed`). What remains: (1) a state file lost (or lost and written again, by any writer and with any bytes) before the pump's first commit of a plan's entry lands is a new lineage, so the alert judged on it is sent again under the next epoch: a duplicate by design, once for each loss, since a lost state file is how a plan's alert generation restarts. It matters only with `persist_minutes` 0, the one setting under which the read that makes an entry can also alert. A state file lost after an alert of the plan was committed and then not written again for a while (its write fails) is the same loss: the unusable state's judgement takes the alert for the one already sent while it stays inside its `realert_hours` window, and the first usable read, on a new lineage, sends it again under the next epoch. (2) A state file put back by hand from a copy of the same lineage is told only by its version: a copy older than the proposal ends it, and a copy of the very generation the proposal was made on (the same random revision, which only a copy of that file carries) is taken for that generation. (3) The command line making the entry of a plan (or giving a lifecycle to an entry written before entries carried one) between the pump's evaluation and its commit gives the entry the command line's lifecycle, so the pump's pending alert is followed by the same alert under the next epoch: a duplicate, never a loss. (4) An alert judged on a state the pump cannot use is not sent again while that state lasts, however long, so the periodic re-alert waits for the first usable read; an alert taken over by that read is committed then, so its next periodic re-alert counts from the commit. A removal of the plan's entry recorded before the state became unusable, and not undone since, also stops the takeover, so the first usable read sends the alert again under the next epoch: a duplicate, never a loss.
- The audit alert queue is read by byte offset like the predecessor's `eval_off`, from the start of the file the first time (the queue is consumed, so the backlog is not history), and an event is one low event per complete line with the id `signal_audit#<start offset of the line>`; port: kept in shape, fixed in the edges (a half-written last line is skipped and the offset stays at its start, two identical lines are two events, a blank or malformed complete line is passed over, and a file that shrank, or whose identity (device and inode of the open file, kept as `cursors.signal.audit.file`) changed whatever its size, restarts at its start under a new epoch so its ids cannot collide with the old file's; the supported rotation is a rename or truncate of the queue file, a state that predates the identity adopts the file it finds, and an in-place rewrite that keeps both the inode and a size at least the read offset is not detected; an alert names at most three defects, each cut at 200 characters, as the predecessor did).
- The capacity read runs before the round saves its pending events, so it is bounded: each `gh` call is cut off after 30 seconds (`capacityExecTimeout`, also for `crw manage capacity`; the lane count is then unknown, as for any gh failure) and its output pipes are released two seconds after it was killed (`WaitDelay`, so a gh that left a child holding them cannot hold the call), the relay helper the read runs (the same executable) releases them one second after it ended or was killed (`relayHelperWaitDelay`, for every relay helper run of the package), and the pump gives the whole read 90 seconds (`pumpSignalCapacityBudget`); a read past the budget is unmeasured, moves nothing, is logged and made again on the next round (also a read that returns a report only after the budget ran out or the round was cancelled: the evaluation absorbs a failed signal read as an unknown signal, so such a report is not a judgement, and it records no event, read time, alert record or commit), while the round saves and delivers the other sources' events. Pinned by `TestPumpSignalStuckCapacityReadDoesNotHoldUpTheRound`, `TestPumpSignalTimedOutCapacityEvaluationIsUnmeasured`, `TestPumpSignalTimedOutCapacityReadWithoutPlansIsUnmeasured`, `TestCapacityMergeCountIsBoundedByItsOwnDeadline`, `TestCapacityExecKillsAStuckChildAndItsOutputPipe` and `TestRelayHelperRunReturnsAtItsDeadlineDespiteAnOpenPipe`. The DAG review runs before that save too, and it first asks the relay doctor for the store's state directory: the pump bounds that doctor call at 30 seconds (`pumpSignalDagDoctorBudget`; the doctor is the same helper run, killed at the deadline and released by its wait delay). A doctor that does not answer in time is a failed review: unmeasured, logged, no read time recorded and the refusal offsets as they were, so the review is made again on the next round while the round saves and delivers the other sources' events (pinned by `TestPumpSignalDagHangingDoctorDoesNotHoldUpTheRound`).
- One source failing is logged in `pump.log` and its read is made again on the next round; it blocks no other source (`Sources[name]` stays the read status alone; pinned by `TestPumpSignalOneSourceFailingDoesNotBlockTheOthers` and `TestPumpSignalCapacityFailingDoesNotBlockDagAndAudit`).
