# CRW-840 — the harness root scan and the manifest-target walk

Source: the oracle's shared validator `plugins/codexclaw/components/cxc-ops/src/manifest-targets.ts` at CXC
v0.2.40 (commit 3c1459acadeb1906d97c00a598e1457327ae372d): `escapesRoot` (:105-117), which calls
`realpathSync` on both paths and falls back to `resolve` when either throws. The port is
`internal/runtime/doctor/manifest_targets.go` (`manifestTargetsRealpath` and `manifestTargetsFollow`,
which stand in for `realpathSync`) and `internal/runtime/doctor/harness_run.go`
(`harnessRunRootScan`, the port's own root discovery; the oracle takes its root from its module path,
`plugins/codexclaw/components/cxc-ops/src/cli.ts:27-31`, so that scan has no oracle counterpart).

- `manifestTargetsFollow` read a symlink component's target with `os.Readlink` and resolved it without
  first stat'ing the link, which Node's `realpathSync` does before `binding.readlink` (source
  `manifest-targets.ts:106-117`, the `realpathSync` call). A link whose target passed through a component
  that does not exist therefore answered a resolved path where the oracle answers ENOENT, and
  `targetEscapesRoot` skipped its paired lexical fallback: `root/bad.json` ->
  `../outside/missing/../hook.json` reported `manifest hook file escapes plugin root` where the oracle
  answers `manifest hook file missing: ./bad.json` (found by the pair evaluation of PR #667, reproduced on
  dev 09ca6388); port: fixed (the link is stat'ed before its target is read, as Node's `binding.stat` does,
  so a target that cannot be reached is that error and both paths take the lexical fallback. The target is
  still joined to the remaining components with a lexical Clean, which is what `pathModule.resolve` does in
  the oracle; the earlier plan to join it without cleaning would have walked `..` physically and diverged
  from `realpathSync` for a `..` inside a link target, for example `root/bad.json` ->
  `sublink/../hook.json` with `root/sublink` -> `../outside/deep`, where the oracle answers
  `root/hook.json` and the kernel's physical walk answers `outside/hook.json`).
- `harnessRunRootScan` counted a cached crw version when `os.Stat` on its
  `.codex-plugin/plugin.json` succeeded, whatever the mode, so a version whose manifest path was an empty
  directory counted as an installed root and the command refused with `2 installed crw plugin roots`
  instead of diagnosing the one regular manifest beside it (found by the pair evaluation of PR #719
  (CRW-683), reproduced on dev 09ca6388); port: fixed (the version counts only when the stat's result is a
  regular file; a directory, a FIFO, a device or any other non-regular file contributes nothing, as an
  absent path does, while a manifest link and a link version directory that resolve to a regular file still
  count and a dangling link stays absent).
- Supersedes known-defects/CRW-652.md, item beginning "Supersedes known-defects.md, section \"CRW-555 —
  lone surrogates in doctor manifest paths\", item beginning \"The oracle's containment test compares
  resolved path spellings\"": now port: fixed (that line's `fixed` covered the spelling the walk returns,
  not the link stat; the walk read a link target without the `binding.stat` the oracle makes first, so a
  link target that passed through a missing component resolved where the oracle answers ENOENT. The spelling
  behaviour that line describes is unchanged; the link stat is the oracle's as of this issue).

No other defect was found in this issue's ranges. The two cases above were reproduced on the baseline with
the Go tests in `internal/runtime/doctor/harness_run_root_test.go` and
`internal/runtime/doctor/manifest_targets_realpath_test.go`, and the walk's answers were recorded with Node
24 against that commit's `dist/manifest-targets.js` (`realpathSync` on a link target naming a missing
component answers ENOENT, and on a `..` inside a link target it answers the lexically resolved path).
