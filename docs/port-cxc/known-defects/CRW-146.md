# CRW-146 — a way to release a goalplan slug bound by mistake

Source: CXC v0.2.40 (`3c1459ac`) `plugins/codexclaw/components/pabcd-state/src/orchestrate-apply.ts` `clearedIdle` (the reset and close rows spread the state, so
`slug` stays), `goalplan-cli.ts` (no verb clears `state.slug`) and `goal-gate.ts:201-299` (the goal-complete gate). The Go side is `internal/pabcd/fsm/apply.go`
(`unbindResult`, `Unbound`), `internal/pabcd/cli/loop_unbind.go` (`loopUnbind`), `internal/pabcd/hook/prompt_orchestrate.go` (the chat command) and the
`unbind` entries of `internal/pabcd/cli/loop_args.go`. Found by the CRW-29 investigation (a coordination parent that bound a goalplan by mistake had no honest exit).

- A session that binds a goalplan slug by mistake has no verb that releases it: `orchestrate reset` copies the state with `clearedIdle`, which keeps `slug`, and no other command clears it, so the
  goal-complete gate keeps judging the session by that goalplan's E8 integrity and a session whose bound root has no source delta can neither pass B to C (SOURCE-DELTA-01) nor complete its goal; the only
  ways out the oracle leaves are forging evidence or editing the state file by hand (source `orchestrate-apply.ts` `clearedIdle`, `goal-gate.ts:250-299`; no recorded case, the verb is absent); port: kept
  as the oracle behaves, plus a CRW addition (new verbs, not a replacement of any oracle behaviour): `crw pabcd loop unbind --session <id>` and the chat command `orchestrate unbind` release the slug.
  They write the session state without `slug` and without `stopBlockWorkPhaseId` (the work-phase pointer the Stop guard keeps for that slug), and append one row to the transition ledger
  (`ledger.jsonl`: `from` IDLE, `to` IDLE, `reason` `unbound`, `evidence` `released goalplan slug <slug>`). Nothing else changes: the goalplan file and the goalplan's own ledger are not read for
  writing, no other field of the session is touched, and reset, the D-close, the E8 check, SOURCE-DELTA-01 and the gate texts are exactly as before. After it `update_goal` complete takes the gate's
  no-slug branch.
- The verb runs from rest only. A session in any phase but IDLE (and an IDLE that still holds a check epoch or a D-close marker, which reset treats as work to clear) is refused with the way out and
  nothing written, so the release never orphans a running cycle. This is the coordinator's decision for CRW-146, and it is why the stranded case of the issue (X2: phase B, slug bound, no source delta) is
  recovered in two steps and not one: `crw pabcd orchestrate reset --session <id>` closes the cycle (the phase and the cycle bindings go, the slug stays, one `reset` row is appended), then
  `crw pabcd loop unbind --session <id>` releases the slug (one `unbound` row). The gate's own order is why one step could not work: it refuses a cycle in flight before it looks at the slug, so clearing
  the slug at B would not let `update_goal` complete pass. A repeat of the verb, and the verb on a session with no state file or no slug, succeed and write nothing, and the verb on an unreadable session
  state, or one holding records a rewrite would not keep, is refused with the file left as it is. The chat command judges the same way: its "no goalplan is bound" answer is made only after a strict read of the
  session file, and a damaged file is answered with the refusal `unbind: the session state is unreadable; refusing to overwrite it. Nothing was written.` (the prompt entry's reader turns such a file into a
  default IDLE without a slug, which the answer must not take for a session that binds nothing), with a turn id, without one and with a remember request in the same prompt
  (`TestPromptOrchestrateUnbindRefusesAnUnreadableSessionState`).
- The release writes the session state and one transition row and nothing else, on both paths. It drains the session's ledger outbox for rows only (`hook.DrainSessionLedgerRows`), so an event an earlier writer
  left pending with a followup (a P>A re-plan's plan-audit cleanup, which rewrites the goalplan and appends `review_round_superseded` rows to its ledger) keeps its followup pending for a writer that may
  run it; the chat command does the same in its own drains and in the prompt entry's locked writes (`promptSubmitDrainFor`), and it publishes the state the transition produced as it is, without the
  phase-move bookkeeping (injection cursor, injected turns, Stop stagnation reset), so every field but `slug` and `stopBlockWorkPhaseId` is kept. The prompt entry's own per-turn Stop guard stamp
  (`stopBlockTotal`, `stopBlockTurnId`, `stopBlockCapNotified`) is made for every prompt and is not part of the command. A `checkEpoch` stored on an IDLE file with no D-close marker is not returned by
  the state reader (it keeps the epoch only for phase C or an IDLE holding a marker), so such a file is the normalised rest: the verb releases it, as reset finds nothing to clear in it either. Pinned by
  `TestVerifyLoopUnbindPreservesGoalplanWithPendingCleanup`, `TestVerifyLoopUnbindTreatsAStoredIdleCheckEpochAsRest`, `TestVerifyUnbindChatPreservesUnrelatedState`,
  `TestVerifyUnbindDoesNotWriteGoalplanThroughPendingCleanup` and `TestVerifyUnbindDoesNotWriteGoalplanWhenThePromptAlsoAsksToRemember`.
- "Ledger bytes unchanged" in the issue is read as the goalplan's ledger (`.crw/goalplans/<slug>/ledger.jsonl`), which no part of the verb opens for writing. The transition ledger (`.crw/ledger.jsonl`) is
  append-only and gets exactly the one `unbound` row, written through the session's ledger outbox like every other transition row (CRW-1097), so a writer that dies after the state is published has its
  row recorded by the next writer of the session.
- The usage block of `crw pabcd loop --help` and the unknown-verb list `init|show|...|decide` are recorded oracle bytes (`TestLoopHelpOracle`, the `cli-help__loop__*` fixtures), so neither names `unbind`; the
  verb is documented in `plugins/crw/skills/crw-loop/references/durable-goalplan.md`. The oracle's orchestrate usage and unknown-verb text are likewise unchanged: the pairing of this verb is the chat
  command `orchestrate unbind` with the CLI `loop unbind` that the issue names, and `crw pabcd orchestrate` has no `unbind`. The chat command is not refused by the SOURCE-ROOT check the phase verbs run,
  as status and reset are not: a broken source binding is a reason to release the slug. Pinned by `TestLoopUnbindRecoversTheStrandedX2Session`, `TestLoopUnbindRefusesEveryPhaseButIdle`,
  `TestLoopUnbindRefusesAPendingClose`, `TestLoopUnbindNeedsACanonicalSession`, `TestLoopUnbindOfASessionWithoutStateWritesNothing`, `TestLoopUnbindRefusesAnUnreadableSessionState`,
  `TestLoopUnbindFlags`, the fsm cases `TestUnbind*` and the chat cases `TestPromptOrchestrateUnbind*`.
