# CRW-1179 — `crw pabcd orchestrate I` is refused while a host goal is active

Source: the 10-10 isolated real-use trial r2 (S2R2-F4, real session t3: the ledger held IDLE→I with reason cli, then an I→P override). CXC v0.2.40 (commit 3c1459ac) `plugins/codexclaw/components/pabcd-state/src/orchestrate-cli.ts:549-1131` (the transition path of `orchestrate`) and `hook.ts` (the goal-mode Interview firewall of the UserPromptSubmit, PostToolUse, PreToolUse and Stop handlers). The Go files are `internal/pabcd/cli/orchestrate_transition.go` (`orchestrateTransitionApply`, `orchestrateTransitionGoalStatus`, `orchestrateTransitionGoalRefusal`), `internal/pabcd/hook/prompt_orchestrate.go` (the chat command's own check, unchanged), `internal/pabcd/hook/stop.go` (unchanged) and `plugins/crw/skills/crw-pabcd/SKILL.md` (How It Works).

- The oracle's `orchestrate I` reads no host goal: the Interview firewall lives only in the hook handlers (the I hint, the chat command, `request_user_input`, the post-answer rescan), and `fsm.ts` allows IDLE→I whatever the goal state. An agent under an active goal could therefore enter I by running the CLI command, and then had to leave by the I→P override (`orchestrate-cli.ts` I>P soft gate), against crw-pabcd (How It Works) and crw-loop ("Do not enter Interview while a host goal is active"); port: fixed (the transition half reads the goal status of the session's thread from the goals database the hooks read, `CODEX_SQLITE_HOME`, else `CODEX_HOME`, else the account home, once per entry to I, before the SOURCE-ROOT check and before any write. An active goal, or a goals database that cannot be read or resolved (fail closed, as `host.SuppressesInterview` does for every hook; the CLI reads the status with `host.GoalActiveStatusFailClosed`, which also treats a goals path the process cannot inspect, EACCES on a directory without search permission, ELOOP, ENOTDIR, as unreadable, and only an absent file or directory as no goals), refuses the command with code 1 and "The session state was not changed.": the state file keeps its phase and the refusal appends no transition row. The session lock's recovery of an earlier writer's pending ledger row (CRW-1097) runs before the check, as it does for every transition, so an older row can be recorded before the refusal; that is recovery of an earlier transition, not part of this one. The refusal gives the goal-mode next command: `crw pabcd orchestrate P --session <id>` from IDLE, and "Continue the <phase> phase of the current cycle" from P, A, B, C or D, because those phases reach I by the same edge. Only the entry to I is judged: leaving I (the I→P override and ready paths, reset) is never refused, so a goal started during an interview does not trap the session. A paused or completed goal, no goals database, and a goal row of another thread are no active goal and enter I as before. Pinned by `TestOrchestrateTransitionRefusesInterviewUnderAnActiveGoal`; its red run is kept under the lane's evidence directory).
- Stop in phase I (checked, unchanged): `StopHandle` releases in phase I before it reads the goal (`stop.go:95-96`, "the autonomous Stop loop is PABCD-only; the Interview is HITL-only and Stop never drives it"). With the entry refused, phase I under an active goal is reachable only when the goal was created while an interview was open; Stop then neither blocks nor writes, so the session is not forced to continue an interview that needs user answers, and the I→P edge stays open. Already pinned by `TestStopReleasesForInterviewUnreadableGoalAndCorruptState`; port: kept (a block in I would drive the Interview autonomously, which the firewall exists to prevent).
- The crw-pabcd skill said the Interview can be returned to "from any phase" and, in the same paragraph, that it never fires under a goal. The sentence now reads "With no active host goal, you can return to Interview (I) from any phase", and states that the CLI refuses `orchestrate I` under an active goal (or an unreadable goals database) with the goal-mode next command, and never refuses leaving I.
- `getGoalActiveStatus` answers `inactive` on any error of its `existsSync` (the known defect recorded in the main list: a goals database inside a directory the process cannot traverse hides an active goal), and the hooks keep that answer (`host.GoalActiveStatus`, port: kept). The CLI entry to I is a new write gate with no oracle behaviour to keep, and its promise is fail closed, so it does not inherit the gap; port: fixed for `orchestrate I` only (`host.GoalActiveStatusFailClosed`; `TestGoalActiveStatusFailClosedTellsAbsenceFromAnInspectionFailure`, and the symlink-loop case of `TestOrchestrateTransitionRefusesInterviewUnderAnActiveGoal`; their red run is kept under the lane's evidence directory, red2-host.log and red2-cli.log). The hooks' gap is unchanged and stays recorded.
