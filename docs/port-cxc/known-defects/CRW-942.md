# CRW-942 — the install subpackages' executable writes take the fork lock too

Source: no CXC v0.2.40 source or corpus fixture is involved. The defect this issue fixes is in the
port's own test write path, exactly as [CRW-834's record](CRW-834.md) says of the write it added, so
the pointers are the Go files of the port:
`internal/runtime/install/execwrite.go` (the fork-locked helper CRW-834 added),
`internal/runtime/install/configguard/selfheal_report_test.go:243` and `:273` (the two helpers that
still wrote with `os.WriteFile`), and
`internal/runtime/install/configguard/selfheal_report.go:263` (the `exec.CommandContext` that runs
what they wrote, in the same process).

- CRW-834's answer 2 asked the install package and its **subpackages** to write every file they then
  run through the fork-locked helper, but the helper stayed unexported in `package install`, and
  `package install` imports `configguard` (`internal/runtime/install/config_cmd.go:8`,
  `internal/runtime/install/features.go:18`), so `configguard` could not import it back; its two
  fake-codex helpers therefore kept writing with `os.WriteFile`
  (`internal/runtime/install/configguard/selfheal_report_test.go:243` and `:273`), and a fork landing
  inside such a write inherited the descriptor and left the path unexecutable until the child exec'd
  (ETXTBSY, golang/go#22315); port: fixed (the body moved to the new
  `internal/runtime/install/execfile.WriteExecutable`, which both subpackage helpers now call;
  `install.writeExecutable` is a thin call to it, so `archive.go:373` and the existing install test
  call sites are unchanged; `O_EXCL` is not weakened, no retry, no sleep and no test reordering was
  added, and product behaviour is unchanged. `TestSelfHealReportWriteFakeCodexWaitsForTheForkLock`
  in `internal/runtime/install/configguard/execwrite_lock_test.go` pins it, and
  `TestWriteExecutableSurvivesConcurrentForks` and `TestWriteExecutableKeepsItsCallersContract`
  keep their assertions).
