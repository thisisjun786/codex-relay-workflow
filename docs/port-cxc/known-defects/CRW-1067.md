# CRW-1067 — the add-criterion retry of a recorded key without its criterion

Source: CRW-383 follow-up (Linear CRW-1067), the narrow path left after the CRW-383 pre-merge evaluations (CRW-383 final head 5bfb37555, merged into dev at 40087ef64). The defect is the port's own. CXC v0.2.40 (commit 3c1459ac) derives the add-criterion key from the scenario alone and answers a recorded key as "already applied" for any options (goalplan-cli.ts `runAddOp`, :354-420). The Go file is internal/pabcd/cli/loop_mutate.go (loopAddOpConflict).

- A retry of `add-criterion` whose recorded key has no criterion in the plan (the state an old command left behind) and that names a non-default `--surface` or `--presented` was answered as a code 0 "already applied" duplicate, although the requested surface or presentation was never stored and nothing in the plan could show it differed; port: fixed (the retry is refused with code 1, `a criterion with scenario "X" has a recorded key but is not in the plan, so its --surface and --presented cannot be checked against what was registered`, and the plan and ledger stay unchanged. The default retry, logic with no presentation, stays the code 0 no-op, the same rule the add-work-phase legacy key follows. Pinned by TestLoopAddCriterionLegacyKeyRefusesOtherOptions).

- Supersedes CRW-383.md, item beginning "`add-criterion` and `add-work-phase` derive the idempotency key from the scenario": now port: fixed for the add-criterion legacy key (this record; the CRW-383 item's test list is unchanged).
