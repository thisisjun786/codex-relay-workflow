# CRW-1267 — the way back to a newer runtime after a rollback

Source: CRW's own design, not the CXC oracle (CXC v0.2.40, commit 3c1459ac, has no additive DAG zone and no swap gate route for it; decision 74, D-01, is the Go side). The Go side is `internal/runtime/swapgate/swapgate.go` (`SchemaCell`, `DeclaredSchema`, `namedZone`) and `internal/runtime/install/install.go` (`take`). Found by the real-environment trial r2 S10 (CRW-161 R3, evidence `/state/crw/mgmt/real-trial-r2/ev/S10/20261011T201815Z/`, cells L2 to L4b).

- The swap gate decided which schema objects are the additive zone's from the zone statements of the `crw` that asked, not from the candidate. The update to v0.4.0-8311-gdd11cba60 ran with that archive's own `crw`, which knows its zone, and read `EXTENDS_ZONE`, released by `--backup-state-to` (L2; the trial's summary showed `storeSchema` null because it read `swapGate.storeSchema` and not `swapGate.cells.storeSchema`). After the rollback, `crw install rollback <8311 dir> --backup-state-to b4b` ran with the installed v0.4.0-7982-g4a31ea9de `crw`, whose zone lacks the objects 8311 appends (`flow_*`, `dag_agent_*`, `dag_zone_rowid_marks` and the guard triggers), and read the same arrival as a plain `EXTENDS`, which the backup does not release (L4b). The update's allowance itself is the design: no install command opens the store for writing, and the candidate creates the zone on its first write-open (`store.Open`, `installDAGZone`); port: fixed (the candidate names its zone in `crw doctor declared-schema --json` as `zone`, and `SchemaCell` counts the zone the candidate names together with the asking build's, so the same store and candidate give the same answer whichever `crw` asks; a `zone` that is not a list of object keys leaves the cell unreadable. Pinned by `TestTheCandidatesDeclaredZoneDecidesWhatIsTheZoneWhicheverBuildAsks`, `TestAZoneTheCandidateNamesUnreadablyIsNotGuessed` and `TestTheDeclaredSchemaNamesItsZone`).
- After a rollback, `crw install update` from the same archive refused with `stagingDecision: KEEP` (the runtime directory exists, finished and selected by nothing) and named no way back (L4); port: fixed (the refusal carries `repair`, naming `crw install rollback <dir>` and `--backup-state-to DIR`; docs/runtime-install.md "Rolling back" names that rollback as the one way back. Pinned by `TestARolledBackHostReturnsToTheSameNewerRuntimeWithOneCommand`: install, update with the zone arriving and the store not migrated, rollback, the update refused with the repair, `rollback <dir>` refused without the backup and done with it, the pointer and the record on the newer runtime, and the state directory byte for byte as before with its one relationship and one journal row).
- A `crw` that does not read the zone a candidate names, or a candidate that names none, still leaves the asking build's zone alone to decide; port: kept (such a `crw` and such a candidate exist already; docs/runtime-install.md says to run the command with the newer runtime's own binary then, `<dir>/bin/crw` for a rollback to `<dir>`).
