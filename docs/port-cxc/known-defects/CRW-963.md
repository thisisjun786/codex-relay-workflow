# CRW-963 — audit pr: a target that always fails no longer holds the --max place of an older one

Source: CRW's own design, not the CXC oracle (CXC v0.2.40, commit 3c1459ac, has no post-merge pull request audit; the pointer is the port). The Go side is `internal/manage/audit_pr.go` (`auditPRSelect`, `auditPRRunWith`), `internal/manage/audit_pr_failures.go` and `internal/manage/audit_report.go`. The defect was found in the review of CRW-934 (#862, Devin) and predates it.

- `auditPRSelect` cut the target list to `--max` before anything was resolved or graded, and only a ledger row took a target out of the next selection. A target that failed (its relay child read, its patch, its criteria or its bundle build) left no row, so it was chosen again every run, and with `--max 1` the older pull requests behind a newest target that always fails were never audited; port: fixed (a failure is one line of the new append-only `audit/audit-pr-failures.jsonl` (target, head, at, reason; the ledger keeps its ok rows and graded results only). The selection puts the targets that never failed at their head first, newest first, and the ones that did fail after them, the one whose last failure is oldest first; the cut to `--max` is made on that order. Pinned by `TestCRW963AlwaysFailingNewestTargetDoesNotStarveAnOlderOne` and `TestCRW963SelectOrdersFailedTargetsAfterFreshOnes`).
- A target that failed three times at one head is left out of the selection and takes no `--max` place until its head changes; the run names it on stderr and the report lists it under "Skipped pull requests" as `skipped: failed 3 times at <head>`. A failure at another head is not counted, so a changed head makes the target a candidate again; port: fixed (pinned by `TestCRW963ThreeFailuresAtTheSameHeadSkipTheTarget`, `TestCRW963ANewHeadMakesTheTargetACandidateAgain`). A skipped target is not a failure of the run, so a run whose only problem is skipped targets exits 0.
- The failure line is appended with `O_APPEND` and the torn-tail guard the ledger uses, is capped at 500 bytes of reason, and a dry run writes none (`TestCRW963TheFailureRecordIsAppendOnly`); port: fixed.
- A target that is graded but not ok (invalid, timeout) still writes a ledger row and is audited once, as before; this issue does not change that; port: kept.
- The targets are resolved before `--max` cuts them: the run takes the candidates in the selection order (never failed first, newest first; then the ones that failed, oldest last failure first), resolves each against the relay, and a target whose resolution fails is named, recorded as a failure and left out while the next candidate takes its place, until `--max` targets are resolved or the candidates are used up. The list is read on only when the candidates read so far are used up, so the order does not depend on how many windows were read. A failure after resolution (its patch, criteria or bundle build) uses that run's place and the next run moves the target behind the ones that never failed; port: fixed (pinned by `TestCRW963ResolveBeforeMax`).
