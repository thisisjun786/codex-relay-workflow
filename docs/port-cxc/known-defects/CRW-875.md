# CRW-875 — a script of clean GitHub posts is allowed; CDPATH does not hide an absolute or ./ cd

Source: Linear CRW-875 (the GitHub post guard reads a program a shell receives from a file, a CRW-783 split) and the management
re-check of 2026-10-09 on dev 2eb3066c1 (probe sources under /state/crw/mgmt/recheck-20261009/g2/, summary.json under CRW-875, and
/state/crw/mgmt/activation-readiness-shell-reader-20261009.md section 5, rows 1 and 2). The issue's own reading (a shell, source or `.`
reads a file; the file is read and judged; an unreadable file is refused; a script without a post is not a target) was redone by CRW-1028
on the shared reader; the first branch (PR #845, f30490c14) held the old reader and is not resumed. This change answers what the
re-check still found on the new reader. The oracle is CRW's own protection (CRW-783 has no CXC oracle). The Go files are
internal/pabcd/hook/githubpost_judge.go (the script judge), internal/pabcd/hook/githubpost.go (the form A reads) and
internal/pabcd/shellir/shellir.go (the cd of the walk). The reproductions are rows CRW-875-22-01 to 27 in
internal/pabcd/hook/testdata/shellir/rows/22-crw-875-post-scripts.txt, indexed in reproductions.tsv, and TestCdUnderCDPATH
(internal/pabcd/shellir/cdpath_test.go). The red output on dev is /state/crw/crw-875/evidence/red-rows.log (rows) and
/state/crw/crw-875/evidence/red-cdpath-unit.log (the unit test).

- A script file that holds only clean `gh pr comment --body-file` lines, run by `bash post.sh`, `sh`, `source`, `.` or by path, was
  refused as unreadable-github-post as soon as it held two commands: the guard allowed a post only as the one simple command of the
  whole text, and a script is a list. The issue's rule is per line: a script that mentions a post is allowed when every command line is
  form A or exception B. port: fixed (a script file that holds a gh post is read by the line rule: every command line is a plain line,
  not in a list, pipe, loop, conditional, substitution or background, and is a gh post in form A, judged by the same rules as a post on
  the command line, or a command of exception B; a script without a post is still not judged). Exception B here is a program named by a
  bare word on literal words only: rg without --pre or --pre-glob, grep, egrep, fgrep, cat, head, tail, wc, ls, echo and printf. Rows
  CRW-875-22-01 to 03b allow the clean scripts; 22-04 to 22-05, 22-12 to 22-14 refuse the lines that are neither (a gh read, cd, an
  assignment, git, a script, a path, an unknown word, rg --pre, a post in a loop, conditional or background).
  The old frozen row PR845-ef89e0ed-d6 (gh auth status before a clean post) is unchanged and still refused.
- The files a post of a script reads were not checked against the writes of the text. In a script the posts are no longer the whole text,
  so the guard also asks whether a write of the script, of a script it ran before, or of the text that runs it can land on a file a
  post read (the file by any name, a link or a hard link, a directory a copy fills, or a destination the reader cannot name): then
  the post is unreadable. This closes a hole that dev already had for a one-line script: `echo x > $TMP/b.md; bash post.sh` was allowed
  with a clean post.sh, and the post then sent the rewritten file (row CRW-875-22-11). port: fixed (security). Rows CRW-875-22-07 to
  22-11. A write is known to the guard as the memory gate knows it (redirections, tee, cp, mv, ln and the rest of the verb list, scripts
  read to any depth); a program the reader does not model as a writer (a build tool, an interpreter script) can write a body file
  between two posts of a script; port: kept (the same boundary as the memory gate; the closed rule on the command line refuses a post
  next to any other command, so the boundary is new only for scripts).
- `CDPATH=/x; cd /abs/sub; bash clean.sh` and `CDPATH=/x; cd ./sub; bash clean.sh` were refused by all three gates because the walk made
  the directory unknown on a CDPATH assignment and every later cd under CDPATH. Bash and zsh never search CDPATH for a target that
  begins with / or ./, so those cds resolve as without CDPATH. port: fixed (an assignment of CDPATH no longer moves the directory; a cd
  under CDPATH is unknown only for a target that is not absolute and does not begin with ./: a bare name, `.`, `..` and the rest). The
  rows that make the directory unknown stay: CDPATH=/x; cd sub, cd ../sub, and a bare name after an absolute cd (rows
  CRW-875-22-24 to 26; PR845-f30490c1-d2b). Rows CRW-875-22-20 to 23.
- Residual, port: pending: the lower-case zsh array `cdpath=(/x)` is not read as an assignment of CDPATH, so a bare-name cd after it is
  resolved as without CDPATH. It was so on dev and no issue row asks for it.

Boundaries (not defects of this change):

- curl, wget and the like that write to api.github.com directly are outside this guard, which reads gh only (the issue's item 7).
- A `gh api --input F` file that is not valid JSON is scanned as text and allowed; that is CRW-917 S3 and recorded in CRW-1028.md.
- `case x in a|b) echo hi;; esac` (a plain command with a | in a case pattern, no script and no post) is allowed; the re-check probe expected a
  refusal, but a command that runs no script and no post is not judged (the CRW-1028 principle).
- The shell reads of the issue's items 1 to 6 (bash, sh, zsh, dash, ksh with a script operand, source, `.`, a missing or over-1-MiB
  script refused, `--input -` and `-F body=@-` refused, a link out of the temporary root refused, wrappers, prefixes, lists and
  direct execution) were answered by CRW-1028 and are pinned by rows CRW-875-01 to 26 and PR845-*; this change re-ran them on its head
  (the 04 and 08 row files) and none was allowed.
