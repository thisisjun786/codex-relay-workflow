# CRW-875 — GitHub post guard: a shell program read from a file

Source: CRW's own protection, no oracle. No CXC v0.2.40 (commit 3c1459ac) behaviour is recorded here,
because the guard is not a port. The guard is the PreToolUse leg of this repository's own runtime
(`internal/pabcd/hook/githubpost.go`, `internal/pabcd/hook/githubpost_scan.go`), registered as one row in
`cmd/crw/component_hooks.go`. This change extends the closed rule CRW-783 fixed, so every row below is a
judgement of that rule and not an oracle difference.

## The gap this change closes

CRW-783's rule reads the payload's command text. A shell that takes its program from a file (`bash
post.sh`, `sh post.sh`, `zsh post.sh`, `dash post.sh`, `ksh post.sh`, `source post.sh`, `. post.sh`)
shows no post verb in that text, so a posting script was never read or judged (the defect class CRW-783's
third-generation independent review named as type 7). The guard now reads the program file and applies
the same closed rule to it:

- a shell program read from a file whose text names a post was passed unjudged; port: fixed (the file is
  read, and it is allowed only when every executable line on its own satisfies form A or exception B;
  otherwise it is refused as unreadable-github-post at the file and the line).
- a shell program file that cannot be read (absent, over 1 MiB, a read error, a directory) was passed
  unjudged; port: fixed (it is refused as unreadable-github-post at the file name).
- a `gh api` standard-input body (`--input -`, `-F body=@-`, `--field body=@-`) was read as a file
  named `-` under the payload's working directory, so a post whose body came from standard input was
  judged only by accident, and passed when a readable file named `-` sat there; port: fixed (the three
  shapes are refused as inline-github-body at command, explicitly, as `--body-file -` already was).
- a body file reached through a symbolic link was contained-checked on the link's own path rather than
  on the file the kernel would read, so a link under a temporary root pointing outside it (for example
  `/tmp/link` to `/proc/self/environ`) passed the check; port: fixed (the path is resolved through its
  links before the containment check, and the roots are resolved the same way, so a real path outside
  them is refused).
- the script mention gate used only CRW-783's mention test, whose posting-verb list is comment, create,
  edit and review, so a script that posts through the built-in create aliases (`gh pr new`,
  `gh issue new`) named no post by that gate and was passed as a script that names none, one word away
  from the issue's own red test; port: fixed (the gate is the mention test or the canonical post test the
  closed rule already uses for a text that is not one simple command, which reads `new` because it is
  outside the read list).
- a plus-prefixed shell option was read as the program file, so a valid invocation (`bash +o errexit
  post.sh`, `bash +x post.sh`) was refused at the option word instead of the script; port: fixed (a
  plus-prefixed word is an option, and `+o` and `+O` take the next word as their value, as `-o` and
  `-O` do).
- a value-taking option's value was read as the program file when the option sat inside a bundle
  (`bash -eo errexit post.sh` read `errexit`); port: fixed (`o` and `O` take the next word as their
  value wherever they sit in a single-dash bundle).
- the `--` separator was ignored, so a program file whose name begins with a dash (`bash -- -post.sh`)
  was never read; port: fixed (every word after the separator is an operand, and the first one is the
  program file).
- the first operand was read as the program file even when the shell takes its program from standard
  input, so `bash -s clean.sh` was judged on `clean.sh`, which bash never runs (it becomes the first
  argument); port: fixed (a `-s` bundle keeps the operand from being the program, as a `-c` bundle
  does, so no wrong file is read).
- the judgement ended as soon as the script named no post, which skipped the command-level mention
  check: `bash runner.sh gh pr comment 1 -b plain`, where `runner.sh` holds `"$@"` and runs the post in
  its arguments, was allowed, though the same command was refused before this change (a regression);
  port: fixed (a script that names no post leaves the command text to the closed rule, so the post in
  the arguments is refused as unreadable-github-post at command).
- the program path was opened before checking that it was a regular file, so a FIFO (`bash
  program.fifo`) made the hook wait for a writer instead of denying the command; port: fixed (a path
  that is not a regular file is refused before the open).
- a `source` or `.` name with no slash was read only in the payload's working directory, where a shell
  searches `PATH` first, so a clean working-directory copy could hide a posting script that `PATH`
  resolves first; port: fixed (the first regular file of that name on `PATH` is judged as well as the
  working-directory one, and either one failing refuses the command; a `PATH=` word the command itself
  sets decides the search, and the guard's own `PATH` is used only when the command sets none).
- generation 1 read a shell program file only when the whole command text was one simple command whose
  program word was the shell itself, so the commonest ways a shell takes a posting script file as its
  program were still passed: a wrapper prefix (`timeout 30 bash post.sh`, `sudo bash post.sh`,
  `sudo -u root bash post.sh`, `timeout -s KILL 30 bash post.sh`, `env X=1 bash post.sh`,
  `nohup bash post.sh`, `X=1 bash post.sh`, `command bash post.sh`, `exec bash post.sh`,
  `nice bash post.sh`, `time bash post.sh`), a list (`cd . && bash post.sh`, `true; bash post.sh`,
  `bash post.sh &`) and a shell in quote pieces (`'timeout' 30 bash post.sh`, `'bash' post.sh`);
  port: fixed (D1: each command of a list is cut at `;`, `&&`, `||`, `&`, `|` and a newline, its
  leading assignments and wrapper commands with their options are dropped with the same reader the
  gh-post decomposition uses, and the program that remains is judged by the generation-1 rule; a wrapper
  whose option makes it run nothing, such as `command -v`, is not a target).
- a wrapper's own `--` separator (`timeout 30 -- bash post.sh`) was kept as the program word, so the
  shell that ran the words after it was not read; port: fixed (the separator is skipped after the
  wrapper reader runs, and the words after it are judged).
- an attached-value shell option (`zsh -oerrexit post.sh`, `bash -Oextglob post.sh`) consumed the
  script operand as the option's value, so the file the shell ran was not read; port: fixed (`o` and `O`
  take their value from the next word only when they end the bundle).
- the grouping close was stripped after quote removal, so a quoted operand ending in `)` or `}`
  (`bash 'evil.sh)'`) was read as the trimmed name; port: fixed (the close is stripped from the token as
  written, so a quoted operand keeps it).
- a `#!` script with a NUL byte later in its first 4 KiB was classified a binary and left unread, though
  the shebang interpreter runs it; port: fixed (a file is a binary only when it has a NUL and does not
  start with `#!`).
- a pathname was collapsed with Clean or Join before its symlinks were resolved, so a link in the
  middle of the name (bash decoy/link/../post.sh) inspected a different file than the kernel opens;
  port: fixed (the name is joined without cleaning, and the kernel resolves the .. against the real tree).
- a quoted standard-input sentinel (--body-file -, --input -, -F body=@-) was compared as the raw token,
  so a decoy file named - was read instead of refusing the standard-input body; port: fixed (the token is
  read as the shell builds it before the sentinel test).
- the letters inside an attached option value were read as flags (zsh -ocorrect post.sh has no c), so a
  shell that ran a posting script was declared a program string; port: fixed (a bundle is read as the
  shell reads it, and o or O ends the flags at their attached value).
- D2's open-handle check compared two pathname stats rather than the opened handle; port: fixed (the
  handle's own stat is compared with os.SameFile, as the other two readers do).
- a quoted operand was unquoted twice (bash "'post.sh'" read post.sh), so the guard read a different
  file than the shell ran; port: fixed (a token from the list tokenizer is already unquoted and is not
  stripped again, and the grouping close is removed from the raw text before tokenizing).
- the list path read its words with the tolerant tokenizer and decoded them again, so a quote-piece
  program (ba'sh' post.sh) was not the shell word and a quoted operand was unquoted twice; port: fixed
  (the strict reader keeps the quote characters and the shell removal is applied exactly once, with the
  tolerant tokenizer only for a part the strict reader refuses).
- a cd before the command was dropped, so a relative operand was read in the payload's directory rather
  than the one the shell moved to (cd sub && bash post.sh); port: fixed (a literal cd moves the directory
  the later commands are read in).
- a command word that is a path was stripped as a wrapper by its last element (./env, ./sh), so the file
  the shell ran was not read; port: fixed (a path in command position is judged as a file, not as the
  wrapper command its last element spells).
- the script readers opened the path blocking, so a FIFO swapped in between the regular-file check and
  the open could hang the hook; port: fixed (the open is non-blocking and the handle is checked).
- the body file's containment was verified against the path resolved before the open, so a link or a
  parent directory swapped in between could move the opened file outside the roots; port: fixed (the
  name is resolved and containment-checked again after the open, and the handle is compared with it).
- generation 1 never read a script the shell runs directly, so `./post.sh` and `scripts/post.sh` were
  passed; port: fixed (D2: a command word that is a path holding `/` is read as a script — a regular
  file whose first 4 KiB hold a NUL byte is a binary the shell does not run, and it is the one shape that
  is not a target; any other regular file is text the shell runs with `sh`, judged by the generation-1
  line rule; a non-shell shebang script that names a post is refused because its posting line cannot be
  form A or exception B).
- an already-split argv array had its body-file values decoded a second time, so a quote character the
  shell would pass as part of the file name was removed and the guard read a different, clean file than
  the command named (`--body-file 'body.md'`, `--body-file='body.md'`, `--input 'body.md'`,
  `-F body=@'body.md'` and `--field body=@'body.md'` with an argv payload); port: fixed (a value from an
  argv array is the string the shell already built, so it is passed to the file reader unchanged, while a
  value read from shell text is still decoded once).
- the path-is-not-a-wrapper rule was applied only to the first token, so a path reached after a wrapper
  was dropped again as the wrapper command its last element spells (`command ./env`, `env ./env`,
  `nice ./env`, `timeout 5 ./env`, `sudo -u root ./env`, `exec ./sh`) and the file the shell ran was never
  read; port: fixed (the prefix walk returns the words from a path in command position at any depth, so
  the path is judged by D2 wherever it sits after the wrappers).
- the gh form's `handled` result returned before the direct-execution read, so a path whose last element
  is `gh` was trusted as the gh program whatever the file held (`./gh pr view 1` with an executable
  `./gh` that posts); port: fixed (a command word that is a path and names a readable text script is read
  and judged by D2 before the form trusts the name; a path that is absent or a binary still lets the form
  judge the command as before).
- a `source` or `.` search used the guard's own `PATH` after the command's leading assignments were
  dropped, so a command that set its own `PATH` (`PATH=/evil:/usr/bin:/bin source lib.sh`) had a clean
  working-directory copy read instead of the file the shell searched first, and a plain `PATH=dir` word
  was itself refused as an unreadable program file; port: fixed (a leading `PATH=` word is the shell's
  own assignment, it is not a command, and the file rule searches the `PATH` the command sets, falling
  back to the guard's own environment only when the command sets none).
- one `cwd` was carried across a subshell, so a `cd` inside `( )` was treated as moving the directory for
  the commands after the group and a later relative operand was read in the wrong directory
  (`(cd sub); bash post.sh`); port: fixed (a subshell's `cd` is restored when the group closes, while a
  brace group's `cd` runs in the current shell and persists, so both are read where the shell reads them).
- a wrapper's own directory option was consumed and discarded, so the program file was read in the
  payload's directory rather than the one the wrapper moved to (`env -C sub bash post.sh`,
  `env --chdir=sub bash post.sh`, `env -Csub bash post.sh`); port: fixed (the option's directory is
  joined with the command's directory, and an attached value — `env -Csub` — is read as its value too).
- a quoted option name was classified as a positional word, so a line that spells the option in quote
  pieces (`gh pr comment 1 '--body-file' private.md`, `'--input'`, `'-F' 'body=@file'`) never read the
  body file and the secret in it passed; port: fixed (the option name is the word the shell builds, so it
  is decoded once before it is classified, and its value is decoded once as well).
- the shell state was carried across every list segment, so a `cd` whose execution was not certain
  (`false && cd sub; bash post.sh`, `true || cd sub; …`, `cd sub | cat; …`, `cd sub & …`) moved the
  directory the next relative operand was read in and a clean decoy hid the posting script; port: fixed
  (the directory and the PATH move only when the command certainly ran in the current shell, and a
  subshell group is restored at its close).
- quote removal happened before the redirection test, so a quoted word that only spells a redirection
  (`bash '>post.sh'`, `bash '<post.sh'`) was skipped as an operator and the file it names was never read;
  port: fixed (the redirection test reads the word as written, so a quoted operand is a program file and
  an unquoted operator is still a redirection).
- a PATH set by an earlier command of a list was dropped, so `PATH=dir; source lib.sh` and
  `export PATH=dir; source lib.sh` searched the guard's own environment and read a clean copy;
  port: fixed (the PATH a command sets, a bare assignment or an assignment builtin's operand, carries to
  the commands after it in the same shell).
- the sourced-path search collapsed a PATH entry with `filepath.Join`, so an entry holding `..` behind a
  link resolved to a different file than the kernel opens; port: fixed (the entry is joined without
  cleaning, as the program-file operand already is, so the kernel resolves the `..` against the real
  tree).
- a path command word named `gh` that the guard could not read as a text script (over the bound, a read
  error) was exempted from the direct-execution refusal and trusted by the gh form, so an oversized
  executable script escaped; port: fixed (an existing regular text file the guard cannot read is refused
  at the name, and only a name that is not a regular file at all, or a binary, leaves the form to judge).
- a line of a script that runs a path named `gh` was judged by the gh form on the program's basename, so
  the file the line runs was trusted whatever it held; port: fixed (such a line is judged by the
  direct-execution read, with the script-in-script walk bounded at `githubPostScriptMaxDepth` and a chain
  past the bound refused rather than followed).
- the shell state was carried across every list segment, so a `cd` whose execution was uncertain (a
  short-circuited `&&`/`||`, a `while` or `if` body, a pipeline or a background job) moved the directory a
  later relative operand was read in, and a clean decoy in the directory the guard read hid the posting
  script the shell actually ran; port: fixed (the state is now a set: a `cd` that certainly ran replaces
  it, an uncertain one keeps both directories possible, and the operand is judged in each).
- a wrapper's own option leaked into the shell state, so `env -C sub true; bash post.sh` was refused for a
  file in `sub` the shell never reads, and `env PATH=<dir> true; source lib.sh` was refused for a `PATH`
  the next command does not have; port: fixed (the command's own state is judged for that command, while
  only a bare `NAME=value` word or an assignment builtin's operand persists to the commands after it).
- a command word that is a path whose last element names a wrapper the reader peels was always treated as
  the script file, so `/usr/bin/env bash post.sh` (a real binary wrapper) was judged only as a file and the
  program after its options was never read; port: fixed (a path that is a binary and whose name is a
  wrapper the reader peels is peeled as that wrapper, while a text path stays a file the shell runs).
- the strict word reader refused a whole list segment when any word in it held a redirection, so the
  fallback tokenizer decoded every word and a quoted operand beside a redirection (`bash '>post.sh'
  2>/dev/null`) was read as the operator rather than the file it names; port: fixed (a list part is read
  in a mode that keeps every word as written, so quoting survives and an unquoted operator is still told
  apart from a quoted operand).
- a program-file operand that the shell expands (`bash "$SCRIPT"`) was read as the literal name, so a
  decoy file of that spelling stood in for the script the shell runs; port: fixed (an operand holding an
  expansion or a glob is refused as unreadable-github-post, fail closed, as the record already said).
- `env -S` and `env --split-string` re-read their value as shell words and run them, and that value was
  dropped, so the command they run was never judged; port: fixed (the value is judged as the command text
  it is, and a value that runs a post is refused as unreadable-github-post at command).
- a backslash that escaped a space was written without its escape and the word ended at the following
  space, so `bash post.sh\ extra` was judged as the decoy `post.sh\` instead of the file `post.sh extra`
  the shell runs; port: fixed (the list reader keeps the escaped character in the same word).
- an unquoted redirection operator was written into the neighbouring word instead of ending it, so
  `bash post.sh>out` was judged as the decoy `post.sh>out` rather than `post.sh` with its output
  redirected, and a leading `>out bash post.sh` was judged as a program named `>out`; port: fixed (an
  unquoted operator is a token of its own in the list reader, and the prefix walk skips a redirection the
  shell would perform before the program).
- the `env -S` / `env --split-string` value was judged in the payload's directory rather than the
  wrapper's own (`env -C sub -S 'bash post.sh'`); port: fixed (the value is judged with the state the
  prefix walk computed, so `env -C` and a PATH assignment both apply).
- a `PATH=` word in front of a command was treated as persisting in the shell, and a standalone
  assignment after `&&` or `||` was treated as not running at all; port: fixed (a prefix assignment is
  that command's temporary environment, a standalone one persists, and an uncertain one leaves both
  PATHs possible, so the sourced file on either is judged).
- the state set was truncated at a fixed bound, which silently dropped a directory the shell may have
  been in and could leave only clean decoys to inspect; port: fixed (a set past the bound is refused as
  unreadable-github-post at command rather than judged in a subset).
- an expansion or glob character that quoting protected (`bash 'cash$.sh'`, `bash cash\$.sh`) was read as
  a live expansion, so a readable, non-posting script was refused; port: fixed (the operand is scanned as
  written, so a quoted or backslash-escaped character is a literal the shell passes on, while a live
  expansion is still refused).
- a path command word named `gh` that is absent, a directory or a FIFO fell through to the gh form and
  was allowed, though the direct-execution rule refuses such a path; port: fixed (the path is refused as
  unreadable-github-post at its name, while a shape the gh form itself denies keeps the form's own rule).

- a `cd` in a conditional or loop body (`if false; then cd sub; fi; bash post.sh`, `while false; do cd sub; done; bash post.sh`) replaced the directory the shell stays in, so a posting script in the payload's directory was not read; port: fixed (a command in a conditional body keeps the states it could leave the shell in beside its own).
- a file descriptor glued to its redirection (`2>/dev/null bash post.sh`, `bash 2>/dev/null post.sh`, `&>out bash post.sh`) was split off as a program word, so the shell and its file were never read; port: fixed (a number or an ampersand stays with its operator).
- a wrapper's directory operand the shell expands (`env -C "$DIR"`, `env --chdir="$DIR"`, `sudo -D "$DIR"`) was read as a literal directory of that spelling, so a decoy directory stood in for the one the shell selects; port: fixed (the state is unknown when the operand expands, and a program file run from it is refused).
- a `cd` with no operand, a `cd -`, a `popd`, and a relative `cd` under CDPATH (set in the environment or on the command) moved the state to a directory the guard guessed; port: fixed (those states are unknown, and a program file run from them is refused).
- a backslash-escaped `)` was trimmed as a group close, and a backslash-newline was kept as a newline, so the file the shell opens was not the one read; port: fixed (an escaped close is part of the word, and a backslash-newline is a line continuation).
- a command with no script or poster position in an unknown directory (`cd "$PWD" && make`, `cd "$DIR" && ls`) was refused, and a script whose text names issue, pr or release without gh was taken as a post target (`echo issue` then `make`); both were introduced by this change; port: fixed (only a shell or a path program is refused from an unknown state, and the canonical post test needs the word gh).

## Boundary

- A non-`gh` poster that writes to api.github.com itself — `curl`, `wget` and the like — stays outside
  this guard. The rule reads a `gh` program's own text, so a command that names no `gh` program is not
  a target, and every HTTP client that can carry a body is beyond what one command text can show;
  port: kept (the boundary is the issue's own list, and widening it to arbitrary HTTP clients is a scope
  decision for a later issue).
- A shell program whose file is named only through an expansion (`bash "$SCRIPT"`) is read as the literal
  name the text spells (`$SCRIPT`), which is not a file, so the command is refused as
  unreadable-github-post at that name. The guard does not expand the variable; a text whose expansion
  could build a post is already refused by the expansion rule; port: kept (fail closed, and the cost is a
  rewritten command).
- A shell that runs the file as a program string rather than as a file (`bash -c post.sh`, `sh -c
  'bash post.sh'`) is not read as a file: `-c` takes the program as its own word, so there is no file
  operand. The text it spells is still judged by the closed rule, and `bash -c post.sh` runs the string
  `post.sh` (a command name), not the file; port: kept (the boundary is the shell's own `-c` form, which
  the issue does not list).
- An interpreter the issue does not name (`python post.py`, `perl post.pl`, `node post.js`) stays
  outside the guard's file rule: the issue's list is the shell programs and `source`/`.`. A directly
  executed file with a non-shell shebang that names a post is still refused by D2's line rule; port: kept
  (the boundary is the issue's closed list).
- A program that comes from standard input through a redirection (`bash < post.sh`) is not read:
  the redirection operator and its target are skipped as a program operand, and the guard reads a program
  file only when the command names it as the operand. The file is in the command text, so a later change
  could read it; recorded as a follow-up candidate rather than added here, because the parent's
  generation-2 answer names the script operand (D1) and a directly executed path (D2), not a redirection
  target; port: kept.
- A script named inside a command substitution (`X=$(bash post.sh)`, `echo $(bash post.sh)`) is not
  read: the file rule walks the outer text's commands, and a substitution's inner command is a text the
  closed rule reads only for a gh post mention. The base passes this shape too; recorded as a follow-up
  candidate; port: kept.
- A runner the closed rule does not peel (`ssh host bash post.sh`, `xargs -n1 bash post.sh`,
  `watch bash post.sh`, `find . -exec bash post.sh \;`, `docker run ... bash post.sh`) is not read: D1
  uses the same decomposition as the gh-post reader, and that reader removed its runner reader in
  generation 5, so these words are not peeled here either and the text names no post. The base passes
  them too; port: kept.
- A shell that runs the file as a program string (`bash -c 'bash post.sh'`, `eval 'bash post.sh'`,
  `sh -c 'bash post.sh'`) is not read as a file, and the string it spells names no post, so it is not a
  target. The base passes it too; port: kept.
- A runner the closed rule does not peel and a program-string form it does not read (`eval 'bash post.sh'`,
  `post() { bash post.sh; }; post`, `strace -f bash post.sh`, `gdb --args bash post.sh`, `xargs bash`)
  is not read: D1 uses the same decomposition as the gh-post reader, and that reader does not peel these,
  so the words name no post. The base passes them too; port: kept.
- One level of indirection (a clean `wrapper.sh` whose only line is `bash post.sh`) passes: the wrapper
  file names no post, so it is not a target (issue item 3), and the guard reads one file, not a chain;
  port: kept.
- A path command word that is not a regular file (an absent name, a directory, a FIFO) is refused as
  `unreadable-github-post` at the name. The parent's D2 lists an absent name among the unreadable text
  scripts, and refusing is fail-closed; the cost is a rewritten command against one that could not have
  run the file anyway; port: kept.
- A wrapper command the write reader refuses as running nothing (`command -v`, `sudo -l`, `sudo -V`)
  is not a target, because the shell runs no command under it and so there is no file to read; port: kept.
- A shell that takes a non-executing option with a script operand (`bash -n post.sh`) is read and
  refused like an executing one, because the guard reads the operand and does not model which option
  decides execution; port: kept (fail-closed, and the cost is a rewritten command).

- A `case` whose pattern holds a `|` (`case x in a|b) bash clean.sh;; esac`) is refused as unreadable, because the list reader cuts at the `|` and the branch body that runs cannot be read from the command text; port: kept (fail closed; the cost is a rewritten command, and a case with a pipe pattern is rare).

## Superseded rows

  body-file identity reading is out of this issue": now port: fixed (a shell program read from a file —

  CRW-875 carried. The exact body-file identity reading the item also named was dropped by the operator's

  needed).

  words and a clean decoy was read instead of the file the program runs (`bash` with the single operand
  `post.sh extra`); port: fixed (an argv array is walked as it is, never re-split).
- a directly executed path the shell expands (`./"$SCRIPT"`) was read as the literal spelling, so a decoy
  file of that name stood in for the script the shell runs; port: fixed (a path holding a live expansion

  file was read in the directory the guard happened to stand in; port: fixed (such a state is marked
