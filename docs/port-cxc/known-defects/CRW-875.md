# CRW-875 — GitHub post guard: a shell program read from a file

Source: CRW's own protection, no oracle. No CXC v0.2.40 (commit 3c1459ac) behaviour is recorded here,
because the guard is not a port. The guard is the PreToolUse leg of this repository's own runtime
(`internal/pabcd/hook/githubpost.go`, `internal/pabcd/hook/githubpost_scan.go`), registered as one row in
`cmd/crw/component_hooks.go`. This change extends the closed rule CRW-783 fixed, so every row below is a
judgement of that rule and not an oracle difference.

## The gap this change closes

CRW-783's rule reads the payload's command text. A shell that takes its program from a file (`bash
post.sh`, `sh post.sh`, `zsh post.sh`, `dash post.sh`, `ksh post.sh`, `source post.sh`, `. post.sh`)
shows no post verb in that text, so a posting script was never read or judged (the defect class CRW-783's
third-generation independent review named as type 7). The guard now reads the program file and applies
the same closed rule to it:

- a shell program read from a file whose text names a post was passed unjudged; port: fixed (the file is
  read, and it is allowed only when every executable line on its own satisfies form A or exception B;
  otherwise it is refused as unreadable-github-post at the file and the line).
- a shell program file that cannot be read (absent, over 1 MiB, a read error, a directory) was passed
  unjudged; port: fixed (it is refused as unreadable-github-post at the file name).
- a `gh api` standard-input body (`--input -`, `-F body=@-`, `--field body=@-`) was read as a file
  named `-` under the payload's working directory, so a post whose body came from standard input was
  judged only by accident, and passed when a readable file named `-` sat there; port: fixed (the three
  shapes are refused as inline-github-body at command, explicitly, as `--body-file -` already was).
- a body file reached through a symbolic link was contained-checked on the link's own path rather than
  on the file the kernel would read, so a link under a temporary root pointing outside it (for example
  `/tmp/link` to `/proc/self/environ`) passed the check; port: fixed (the path is resolved through its
  links before the containment check, and the roots are resolved the same way, so a real path outside
  them is refused).
- the script mention gate used only CRW-783's mention test, whose posting-verb list is comment, create,
  edit and review, so a script that posts through the built-in create aliases (`gh pr new`,
  `gh issue new`) named no post by that gate and was passed as a script that names none, one word away
  from the issue's own red test; port: fixed (the gate is the mention test or the canonical post test the
  closed rule already uses for a text that is not one simple command, which reads `new` because it is
  outside the read list).
- a plus-prefixed shell option was read as the program file, so a valid invocation (`bash +o errexit
  post.sh`, `bash +x post.sh`) was refused at the option word instead of the script; port: fixed (a
  plus-prefixed word is an option, and `+o` and `+O` take the next word as their value, as `-o` and
  `-O` do).
- a value-taking option's value was read as the program file when the option sat inside a bundle
  (`bash -eo errexit post.sh` read `errexit`); port: fixed (`o` and `O` take the next word as their
  value wherever they sit in a single-dash bundle).
- the `--` separator was ignored, so a program file whose name begins with a dash (`bash -- -post.sh`)
  was never read; port: fixed (every word after the separator is an operand, and the first one is the
  program file).
- the first operand was read as the program file even when the shell takes its program from standard
  input, so `bash -s clean.sh` was judged on `clean.sh`, which bash never runs (it becomes the first
  argument); port: fixed (a `-s` bundle keeps the operand from being the program, as a `-c` bundle
  does, so no wrong file is read).
- the judgement ended as soon as the script named no post, which skipped the command-level mention
  check: `bash runner.sh gh pr comment 1 -b plain`, where `runner.sh` holds `"$@"` and runs the post in
  its arguments, was allowed, though the same command was refused before this change (a regression);
  port: fixed (a script that names no post leaves the command text to the closed rule, so the post in
  the arguments is refused as unreadable-github-post at command).
- the program path was opened before checking that it was a regular file, so a FIFO (`bash
  program.fifo`) made the hook wait for a writer instead of denying the command; port: fixed (a path
  that is not a regular file is refused before the open).
- a `source` or `.` name with no slash was read only in the payload's working directory, where a shell
  searches `PATH` first, so a clean working-directory copy could hide a posting script that `PATH`
  resolves first; port: fixed (the first regular file of that name on `PATH` is judged as well as the
  working-directory one, and either one failing refuses the command; the guard's own `PATH` is used
  because the payload carries none, so the set judged is a superset of what the shell reads).
- generation 1 read a shell program file only when the whole command text was one simple command whose
  program word was the shell itself, so the commonest ways a shell takes a posting script file as its
  program were still passed: a wrapper prefix (`timeout 30 bash post.sh`, `sudo bash post.sh`,
  `sudo -u root bash post.sh`, `timeout -s KILL 30 bash post.sh`, `env X=1 bash post.sh`,
  `nohup bash post.sh`, `X=1 bash post.sh`, `command bash post.sh`, `exec bash post.sh`,
  `nice bash post.sh`, `time bash post.sh`), a list (`cd . && bash post.sh`, `true; bash post.sh`,
  `bash post.sh &`) and a shell in quote pieces (`'timeout' 30 bash post.sh`, `'bash' post.sh`);
  port: fixed (D1: each command of a list is cut at `;`, `&&`, `||`, `&`, `|` and a newline, its
  leading assignments and wrapper commands with their options are dropped with the same reader the
  gh-post decomposition uses, and the program that remains is judged by the generation-1 rule; a wrapper
  whose option makes it run nothing, such as `command -v`, is not a target).
- a wrapper's own `--` separator (`timeout 30 -- bash post.sh`) was kept as the program word, so the
  shell that ran the words after it was not read; port: fixed (the separator is skipped after the
  wrapper reader runs, and the words after it are judged).
- an attached-value shell option (`zsh -oerrexit post.sh`, `bash -Oextglob post.sh`) consumed the
  script operand as the option's value, so the file the shell ran was not read; port: fixed (`o` and `O`
  take their value from the next word only when they end the bundle).
- the grouping close was stripped after quote removal, so a quoted operand ending in `)` or `}`
  (`bash 'evil.sh)'`) was read as the trimmed name; port: fixed (the close is stripped from the token as
  written, so a quoted operand keeps it).
- a `#!` script with a NUL byte later in its first 4 KiB was classified a binary and left unread, though
  the shebang interpreter runs it; port: fixed (a file is a binary only when it has a NUL and does not
  start with `#!`).
- a pathname was collapsed with Clean or Join before its symlinks were resolved, so a link in the
  middle of the name (bash decoy/link/../post.sh) inspected a different file than the kernel opens;
  port: fixed (the name is joined without cleaning, and the kernel resolves the .. against the real tree).
- a quoted standard-input sentinel (--body-file -, --input -, -F body=@-) was compared as the raw token,
  so a decoy file named - was read instead of refusing the standard-input body; port: fixed (the token is
  read as the shell builds it before the sentinel test).
- the letters inside an attached option value were read as flags (zsh -ocorrect post.sh has no c), so a
  shell that ran a posting script was declared a program string; port: fixed (a bundle is read as the
  shell reads it, and o or O ends the flags at their attached value).
- D2's open-handle check compared two pathname stats rather than the opened handle; port: fixed (the
  handle's own stat is compared with os.SameFile, as the other two readers do).
- a quoted operand was unquoted twice (bash "'post.sh'" read post.sh), so the guard read a different
  file than the shell ran; port: fixed (a token from the list tokenizer is already unquoted and is not
  stripped again, and the grouping close is removed from the raw text before tokenizing).
- generation 1 never read a script the shell runs directly, so `./post.sh` and `scripts/post.sh` were
  passed; port: fixed (D2: a command word that is a path holding `/` is read as a script — a regular
  file whose first 4 KiB hold a NUL byte is a binary the shell does not run, and it is the one shape that
  is not a target; any other regular file is text the shell runs with `sh`, judged by the generation-1
  line rule; a non-shell shebang script that names a post is refused because its posting line cannot be
  form A or exception B).

## Boundary

- A non-`gh` poster that writes to api.github.com itself — `curl`, `wget` and the like — stays outside
  this guard. The rule reads a `gh` program's own text, so a command that names no `gh` program is not
  a target, and every HTTP client that can carry a body is beyond what one command text can show;
  port: kept (the boundary is the issue's own list, and widening it to arbitrary HTTP clients is a scope
  decision for a later issue).
- A shell program whose file is named only through an expansion (`bash "$SCRIPT"`) is read as the literal
  name the text spells (`$SCRIPT`), which is not a file, so the command is refused as
  unreadable-github-post at that name. The guard does not expand the variable; a text whose expansion
  could build a post is already refused by the expansion rule; port: kept (fail closed, and the cost is a
  rewritten command).
- A shell that runs the file as a program string rather than as a file (`bash -c post.sh`, `sh -c
  'bash post.sh'`) is not read as a file: `-c` takes the program as its own word, so there is no file
  operand. The text it spells is still judged by the closed rule, and `bash -c post.sh` runs the string
  `post.sh` (a command name), not the file; port: kept (the boundary is the shell's own `-c` form, which
  the issue does not list).
- An interpreter the issue does not name (`python post.py`, `perl post.pl`, `node post.js`) stays
  outside the guard's file rule: the issue's list is the shell programs and `source`/`.`. A directly
  executed file with a non-shell shebang that names a post is still refused by D2's line rule; port: kept
  (the boundary is the issue's closed list).
- A program that comes from standard input through a redirection (`bash < post.sh`) is not read:
  the redirection operator and its target are skipped as a program operand, and the guard reads a program
  file only when the command names it as the operand. The file is in the command text, so a later change
  could read it; recorded as a follow-up candidate rather than added here, because the parent's
  generation-2 answer names the script operand (D1) and a directly executed path (D2), not a redirection
  target; port: kept.
- A script named inside a command substitution (`X=$(bash post.sh)`, `echo $(bash post.sh)`) is not
  read: the file rule walks the outer text's commands, and a substitution's inner command is a text the
  closed rule reads only for a gh post mention. The base passes this shape too; recorded as a follow-up
  candidate; port: kept.
- A runner the closed rule does not peel (`ssh host bash post.sh`, `xargs -n1 bash post.sh`,
  `watch bash post.sh`, `find . -exec bash post.sh \;`, `docker run ... bash post.sh`) is not read: D1
  uses the same decomposition as the gh-post reader, and that reader removed its runner reader in
  generation 5, so these words are not peeled here either and the text names no post. The base passes
  them too; port: kept.
- A shell that runs the file as a program string (`bash -c 'bash post.sh'`, `eval 'bash post.sh'`,
  `sh -c 'bash post.sh'`) is not read as a file, and the string it spells names no post, so it is not a
  target. The base passes it too; port: kept.
- A runner the closed rule does not peel and a program-string form it does not read (`eval 'bash post.sh'`,
  `post() { bash post.sh; }; post`, `strace -f bash post.sh`, `gdb --args bash post.sh`, `xargs bash`)
  is not read: D1 uses the same decomposition as the gh-post reader, and that reader does not peel these,
  so the words name no post. The base passes them too; port: kept.
- One level of indirection (a clean `wrapper.sh` whose only line is `bash post.sh`) passes: the wrapper
  file names no post, so it is not a target (issue item 3), and the guard reads one file, not a chain;
  port: kept.
- A path command word that is not a regular file (an absent name, a directory, a FIFO) is refused as
  `unreadable-github-post` at the name. The parent's D2 lists an absent name among the unreadable text
  scripts, and refusing is fail-closed; the cost is a rewritten command against one that could not have
  run the file anyway; port: kept.
- A wrapper command the write reader refuses as running nothing (`command -v`, `sudo -l`, `sudo -V`)
  is not a target, because the shell runs no command under it and so there is no file to read; port: kept.
- A shell that takes a non-executing option with a script operand (`bash -n post.sh`) is read and
  refused like an executing one, because the guard reads the operand and does not model which option
  decides execution; port: kept (fail-closed, and the cost is a rewritten command).
