# CRW-875 — GitHub post guard: a shell program read from a file

Source: CRW's own protection, no oracle. No CXC v0.2.40 (commit 3c1459ac) behaviour is recorded here,
because the guard is not a port. The guard is the PreToolUse leg of this repository's own runtime
(`internal/pabcd/hook/githubpost.go`, `internal/pabcd/hook/githubpost_scan.go`), registered as one row in
`cmd/crw/component_hooks.go`. This change extends the closed rule CRW-783 fixed, so every row below is a
judgement of that rule and not an oracle difference.

## The gap this change closes

CRW-783's rule reads the payload's command text. A shell that takes its program from a file (`bash
post.sh`, `sh post.sh`, `zsh post.sh`, `dash post.sh`, `ksh post.sh`, `source post.sh`, `. post.sh`)
shows no post verb in that text, so a posting script was never read or judged (the defect class CRW-783's
third-generation independent review named as type 7). The guard now reads the program file and applies
the same closed rule to it:

- a shell program read from a file whose text names a post was passed unjudged; port: fixed (the file is
  read, and it is allowed only when every executable line on its own satisfies form A or exception B;
  otherwise it is refused as unreadable-github-post at the file and the line).
- a shell program file that cannot be read (absent, over 1 MiB, a read error, a directory) was passed
  unjudged; port: fixed (it is refused as unreadable-github-post at the file name).
- a `gh api` standard-input body (`--input -`, `-F body=@-`, `--field body=@-`) was read as a file
  named `-` under the payload's working directory, so a post whose body came from standard input was
  judged only by accident, and passed when a readable file named `-` sat there; port: fixed (the three
  shapes are refused as inline-github-body at command, explicitly, as `--body-file -` already was).
- a body file reached through a symbolic link was contained-checked on the link's own path rather than
  on the file the kernel would read, so a link under a temporary root pointing outside it (for example
  `/tmp/link` to `/proc/self/environ`) passed the check; port: fixed (the path is resolved through its
  links before the containment check, and the roots are resolved the same way, so a real path outside
  them is refused).
- the first draft of the script mention gate used only CRW-783's mention test, whose posting-verb list is
  comment, create, edit and review, so a script that posts through the built-in create aliases
  (`gh pr new`, `gh issue new`) named no post by that gate and was passed as a script that names none,
  one word away from the issue's own red test; port: fixed (the gate is the mention test or the canonical
  post test the closed rule already uses for a text that is not one simple command, which reads `new`
  because it is outside the read list).
- the first draft read a plus-prefixed shell option as the program file, so a valid invocation
  (`bash +o errexit post.sh`, `bash +x post.sh`) was refused at the option word instead of the script;
  port: fixed (a plus-prefixed word is an option, and `+o` and `+O` take the next word as their value,
  as `-o` and `-O` do).
- the first draft read a value-taking option's value as the program file when the option sat inside a
  bundle (`bash -eo errexit post.sh` read `errexit`); port: fixed (`o` and `O` take the next word as
  their value wherever they sit in a single-dash bundle).
- the first draft ignored the `--` separator, so a program file whose name begins with a dash
  (`bash -- -post.sh`) was never read; port: fixed (every word after the separator is an operand, and
  the first one is the program file).
- the first draft ended the judgement as soon as the script named no post, which skipped the command-level
  mention check: `bash runner.sh gh pr comment 1 -b plain`, where `runner.sh` holds `"$@"` and runs the
  post in its arguments, was allowed, though the same command was refused before this change (a
  regression); port: fixed (a script that names no post leaves the command text to the closed rule, so the
  post in the arguments is refused as unreadable-github-post at command).
- the first draft opened the program path before checking that it was a regular file, so a FIFO
  (`bash program.fifo`) made the hook wait for a writer instead of denying the command; port: fixed (a
  path that is not a regular file is refused before the open).
- the first draft read a `source` or `.` name with no slash only in the payload's working directory,
  where a shell searches `PATH` first; port: fixed (both files are judged, and either one failing refuses
  the command, so a clean working-directory copy cannot hide a posting script that `PATH` resolves first).
- the first draft read the first operand as the program file even when the shell takes its program from
  standard input, so `bash -s clean.sh` was judged on `clean.sh`, which bash never runs (it becomes the
  first argument); port: fixed (a `-s` bundle keeps the operand from being the program, as a `-c`
  bundle does, so no file is read and the command is judged by its own text).
- the first draft stopped at the first word that did not begin with `-`, so a value-taking option inside
  a bundle (`bash -eo errexit post.sh`) had its value read as the program file; port: fixed (`o` and
  `O` take the next word as their value wherever they sit in a single-dash bundle).
- the first draft did not honour the `--` separator, so a script whose name begins with a dash
  (`bash -- -post.sh`) was skipped and the command passed; port: fixed (every word after `--` is an
  operand, and the first one is the program file).
- the first draft ended the judgement when the script named no post, so the command text's own arguments
  were never judged: `bash runner.sh gh pr comment 1 -b plain`, where `runner.sh` holds `"$@"`,
  passed; port: fixed (a script that names no post leaves the command text to the closed rule, so a post
  in the arguments is refused as unreadable-github-post at command).
- the first draft opened the program path before checking that it was a regular file, so a FIFO
  (`bash program.fifo`) made the hook wait for a writer instead of denying the command; port: fixed (a
  path that is not a regular file is refused before the open).
- the first draft returned an allow as soon as the script named no post, which skipped the command-level
  mention check: `bash runner.sh gh pr comment 1 -b plain`, where `runner.sh` holds `"$@"` and so runs
  the post in its arguments, was allowed, though the same command was refused before this change; port:
  fixed (a script that names no post leaves the command text to the closed rule, so the arguments are
  judged and the post is refused as unreadable-github-post at command).
- the first draft read a `source` or `.` name with no slash only in the payload's working directory,
  where a shell searches `PATH` first; port: fixed (both files are judged, and either one failing
  refuses the command, so a clean working-directory copy cannot hide a posting script that `PATH`
  resolves first).
- the first draft returned an allow as soon as the script named no post, which skipped the command-level
  mention check: `bash runner.sh gh pr comment 1 -b plain`, where `runner.sh` holds `"$@"` and so runs
  the post in its arguments, was allowed (and the same command was refused before this change, so the
  draft was a regression); port: fixed (a script that names no post leaves the command text to the closed
  rule, so the arguments are judged and the post is refused as unreadable-github-post at command).
- the first draft read a `source` or `.` name with no slash only in the payload's working directory,
  where a shell searches `PATH` first; port: fixed (both files are judged, and either one failing
  refuses the command, so a clean working-directory copy cannot hide a posting script that `PATH`
  resolves first).

## Boundary

- A non-gh poster that writes to api.github.com itself — `curl`, `wget` and the like — stays outside
  this guard. The rule reads a `gh` program's own text, so a command that names no `gh` program is not a
  target, and every HTTP client that can carry a body is beyond what one command text can show;
  port: kept (the boundary is the issue's own list, and widening it to arbitrary HTTP clients is a
  scope decision for a later issue).
- A shell program whose file is named only through an expansion (`bash "$SCRIPT"`) is not read: the
  command text is not one simple command of literal words, so the closed rule refuses it as
  unreadable-github-post when it names a post, and passes it when it names none; port: kept (the
  fail-closed rule already covers the text the guard cannot read).
- The shell program file is read only when the whole command text is one simple command whose program
  word is the shell itself. A shell behind a wrapper prefix (`timeout 30 bash post.sh`, `sudo bash
  post.sh`, `env X=1 bash post.sh`, `xargs bash post.sh`) or inside a longer text (`cd /tmp && bash
  post.sh`, `sh post.sh; true`) is not read, because the closed rule reads the text as a whole and the
  wrapper reader was removed with the rest of the generation-1-to-4 readers; port: kept (the issue's
  answer names the bare forms only, and reaching a command inside a larger text or behind a wrapper is a
  command-decomposition change of its own, not this issue's file-reading change; recorded as a follow-up
  candidate rather than decided here).
- Executing the script itself (`./post.sh`), a shell given the file as a string (`bash -c post.sh`), and
  an interpreter the issue does not name (`python post.py`, `perl post.pl`) stay outside the guard: the
  command text names no shell program taking a file, and none of them is a form the issue lists; port:
  kept (the boundary is the issue's closed shell list, and widening it is a later scope decision).
- A shell whose program comes from standard input (`bash -s < post.sh`, `cat post.sh | bash -s`) is not
  read: the program is not in the command text and there is no operand to read, which is the same boundary
  as `bash < post.sh`. The guard reads a program file only when the command names it as the operand;
  port: kept (the closed rule judges the text and leaves a text that names no post alone, so refusing this
  shape would be a new rule the issue does not name; recorded as a follow-up candidate).
- A `source` or `.` name with no slash is resolved against the payload's working directory only, where
  a shell also searches `PATH` first. The issue's answer fixes the rule ("a relative path is joined with
  the payload cwd"), so the guard follows it; a `PATH` entry earlier than the working directory is a
  divergence the guard does not read, and the file it does not read is refused only when the working
  directory holds no such name; port: kept (the resolution rule is the issue's, and adding a `PATH`
  search is a new rule the issue does not name; recorded as a follow-up candidate).
