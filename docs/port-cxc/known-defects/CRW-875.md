# CRW-875 — a script of clean GitHub posts is allowed; CDPATH does not hide an absolute or ./ cd

re-check of 2026-10-09 on dev 2eb3066c1 (probe sources under /state/crw/mgmt/recheck-20261009/g2/, summary.json under CRW-875, and
/state/crw/mgmt/activation-readiness-shell-reader-20261009.md section 5, rows 1 and 2). The issue's own reading (a shell, source or `.`
reads a file; the file is read and judged; an unreadable file is refused; a script without a post is not a target) was redone by CRW-1028
on the shared reader; the first branch (PR #845, f30490c14) held the old reader and is not resumed. This change answers what the
re-check still found on the new reader. The oracle is CRW's own protection (CRW-783 has no CXC oracle). The Go files are

- A script file that holds only clean `gh pr comment --body-file` lines, run by `bash post.sh`, `sh`, `source`, `.` or by path, was
  refused as unreadable-github-post as soon as it held two commands: the guard allowed a post only as the one simple command of the
  whole text, and a script is a list. The issue's rule is per line: a script that mentions a post is allowed when every command line is
  form A or exception B. port: fixed (a script file that holds a gh post is read by the line rule: every command line is a plain line,
  not in a list, pipe, loop, conditional, substitution or background, and is a gh post in form A, judged by the same rules as a post on
  the command line, or a command of exception B; a script without a post is still not judged). The text of such a script is also read
  as written: every statement is a plain call on a line of its own, with no assignment before it, no redirection, no trailing ;, no
  list, declaration (export, declare), loop, conditional, function or group, and only literal words (the execution records of the
  reader cannot show the assignments of a declaration, a prefix assignment or the separators of a line). Exception B here is a program
  named by a bare word (or by an absolute path in /bin, /usr/bin, /usr/local/bin or /opt/homebrew/bin) on literal words only: rg
  without --pre, --pre-glob or --hostname-bin (each runs a program; ripgrep does not abbreviate long flags), grep, egrep, fgrep, cat,
  head, tail, wc, ls, echo, printf with a format of text, escapes and plain conversions only (% with flags, a decimal width and
  precision and one of s d i o u x X f F e E g G a A c b q, or %%; not a first word that is an option: printf -v assigns a variable,
  and zsh printf %n stores the count printed so far in the variable it names, so `printf '%n' PATH` sets PATH to 0; a positional
  %1$, a * width and %(...)T are refused too), and git log, show, diff, grep and status with no option before the subcommand
  (CRW-783 generation 5; git commit is not one of them, it runs the hooks of the repository), except an option that writes a file or
  runs a program on the text: --output and --open-files-in-pager in any abbreviation git accepts, and a short -O. A short bundle is read option by option as git reads it: an option that takes a value
  ends the bundle (the O of `git log -SOrder` or `git grep -eOpen` is a value, and `git grep -e -O` gives -O as the pattern), while
  `git grep -lO` and `git grep -3O` hold the option -O. A long option written without = may take the next word as its value
  (`--src-prefix --`), and that word may be the --, so a -- after a long option that is not on the list of options without a value
  (--oneline, --stat, --numstat, --cached, --no-index and the like) is not the end of the options: `git diff --no-index --src-prefix --
  --output=F a b` is refused (port: fixed; TestGitHubPostGitLongOptionValue). Rows 22-40 to 40d (printf), 22-42 to 42d (git bundles). Rows CRW-875-22-01 to 03b and 22-32, 32b, 22-34 allow the clean scripts; 22-04 to 22-05, 22-12 to 22-14 and
  22-30 to 22-33d, 22-34b refuse the lines that are neither (a gh read, cd, an assignment or export, git with an option before the
  subcommand, another git subcommand, git --output, a script, a relative path, an unknown word, rg --pre or --hostname-bin, a list
  or a redirection on a post line, a post in a loop, conditional or background).
  The old frozen row PR845-ef89e0ed-d6 (gh auth status before a clean post) is unchanged and still refused.
- The files a post of a script reads were not checked against the writes of the text. In a script the posts are no longer the whole text,
  so the guard also asks whether a write of the text that runs the script (a line of the script cannot write: a redirection refuses the line) can land on a file a
  post read (the file by any name, a link or a hard link, a directory a copy fills, or a destination the reader cannot name): then
  the post is unreadable. This closes a hole that dev already had for a one-line script: `echo x > $TMP/b.md; bash post.sh` was allowed
  with a clean post.sh, and the post then sent the rewritten file (row CRW-875-22-11). port: fixed (security). Rows CRW-875-22-07 to
  22-11. A write is known to the guard as the memory gate knows it (redirections, tee, cp, mv, ln and the rest of the verb list, scripts
  read to any depth); a program the reader does not model as a writer (a build tool, an interpreter script) can write a body file
  between two posts of a script; port: kept (the same boundary as the memory gate; the closed rule on the command line refuses a post
  next to any other command, so the boundary is new only for scripts). A program that configuration, not the text, makes run is not
  inside that boundary: git (a hook, a textconv or external diff driver, core.fsmonitor, core.pager of the repository) and rg (a
  --pre in a configuration file) may write any file, so a git or rg command counts as a write to every file from the point it runs:
  a post that reads a file after one (in the script, in the text that runs it, or in a script that text runs before it) is refused,
  while a git or rg line after the last post, or a script whose posts read no file, is allowed; git commit, which runs hooks, is
  not exception B at all. port: fixed (security; rows 22-54 to 56e, githubPostWrites.hooked). The text of the script cannot set the
  configuration, since an assignment or declaration refuses the script. Nor can the text that
  runs the script: RIPGREP_CONFIG_PATH (a config whose --pre runs a program), GIT_EXTERNAL_DIFF, GIT_CONFIG_PARAMETERS,
  GIT_CONFIG_COUNT, GIT_CONFIG_GLOBAL and GIT_CONFIG_SYSTEM are code-bearing environment names of the reader (the closed list of
  CRW-1028.md), so `RIPGREP_CONFIG_PATH=cfg bash post.sh`, `export RIPGREP_CONFIG_PATH=cfg; bash post.sh` and `env
  RIPGREP_CONFIG_PATH=cfg bash post.sh` are unreadable to every gate. port: fixed (security; rows 22-41 to 41e, TestAuditRows rows
  E-RIPGREP_CONFIG_PATH to E-GIT_CONFIG_SYSTEM; the benign accounting is unchanged).
- A script run with CDPATH set (`CDPATH=/x bash entry.sh`, `export CDPATH=...; bash entry.sh`, `env CDPATH=... bash entry.sh`,
  `CDPATH=/x source entry.sh`) is read with CDPATH set: its `cd sub` may land in a CDPATH directory, so the script it then runs
  cannot be proven and is refused by all three gates. The record of a script run or of a program (shellir.Exec.Cdpath) carries
  whether CDPATH may be set there, and shellir.AnalyzeScript starts the body's walk with it; the GitHub post guard, its write
  collector and the worktree deletion guard read bodies that way. port: fixed (the first fix of this issue dropped the old
  unknown-directory assignment and so let the body be read without the state; rows 22-50 to 51, TestAnalyzeScriptCdpath).
- The zsh array `cdpath=(/x)` and every other way a text names CDPATH (a lower-case assignment, `read CDPATH`, `printf -v CDPATH`,
  `for CDPATH in`, `declare -n r=CDPATH`, an export of a name built at run time, a carried text) set the search path: the walk takes
  the name anywhere in a text, or among the words of a builtin that assigns variables, as an assignment of CDPATH. port: fixed (rows
  22-52 to 53, TestCdpathNames).
- `CDPATH=/x; cd /abs/sub; bash clean.sh` and `CDPATH=/x; cd ./sub; bash clean.sh` were refused by all three gates because the walk made
  the directory unknown on a CDPATH assignment and every later cd under CDPATH. Bash and zsh never search CDPATH for a target that
  begins with / or ./, so those cds resolve as without CDPATH. port: fixed (an assignment of CDPATH no longer moves the directory; a cd
  under CDPATH is unknown only for a target that is not absolute and does not begin with ./: a bare name, `.`, `..` and the rest). The
  rows that make the directory unknown stay: CDPATH=/x; cd sub, cd ../sub, and a bare name after an absolute cd (rows
  CRW-875-22-24 to 26; PR845-f30490c1-d2b). Rows CRW-875-22-20 to 23.
- A script run by an absolute path (`/tmp/post.sh`, `timeout 30 /tmp/post.sh`) was never read: the direct-execution rule (D2 of the
  issue) excluded absolute paths as installed programs. A word with a / in command position is now read whatever its directory: a
  binary (a NUL in the first 4 KiB and no #! line: /usr/bin/git, a Go toolchain) is not a script, a link is followed to the file it
  names, a path with no file runs nothing and is not a script, and any other file is judged as the shell text it is (a script of
  another interpreter that spells a gh command is refused). The write check that refuses a script the text may have rewritten counts
  a write to a destination the reader cannot name only for a script, not for a binary named by an absolute path. port: fixed (rows
  22-57 to 57e, TestGitHubPostAbsoluteScript). The cost is that an absolute script whose body the reader cannot read (an unknown
  program word, an assignment to PATH, a glob as program) is refused, as the same text is refused under `bash file` and `./file`: 47 of
  the 8020 benign corpus commands (all run an absolute .sh path) are denied by the GitHub guard that dev allowed
  (/state/crw/crw-875/evidence/round3/benign-lost-vs-dev.txt); the memory and worktree counts are unchanged.
- A refusal inside a script is reported at script-file:line (the script as written and the line of the command, or of the statement
  that breaks the plain-line layout), `post.sh:3`, `./run.sh:4`; a refusal inside a script that another script runs is reported at the
  innermost one. Before, every refusal in a script was at `command`. port: fixed (shellir.Exec.Line; TestGitHubPostScriptRefusalPlace,
  TestExecLines). A refusal that already names a file (an unreadable or secret-bearing body file) keeps that place.
- `gh api ... --input -`, `--input=-`, `-F body=@-` and `--field body=@-` read standard input: refused as inline-github-body at
  command, the rule `--body-file -` of form A1 already had; they were refused as unreadable-github-post only because the file named
  `-` could not be read. port: fixed (TestGitHubPostAPIStdinIsInline).
- Supersedes CRW-783.md, section "Accepted over-blocking", item beginning "the exact body-file identity reading is out of this issue":
  now port: fixed for the shell program read from a file (`bash post.sh`, `sh`, `zsh`, `dash`, `ksh`, `source`, `.`, a script run by a
  relative or absolute path, with wrappers, prefixes and lists; CRW-1028 on the shared reader, completed here) and for the files a
  script's posts read (a write of the script or of the text around it that may reach one makes the post unreadable). The exact
  body-file identity reading the item also names stays unneeded: the closed rule fixes the body file under a temporary root and
  refuses what the text may have written. Supersedes CRW-783.md, section "Superseded rows", the sentence "Shell programs read from a
  file (bash post.sh, source post.sh) stay CRW-875's": they are read by CRW-1028 and CRW-875.

Boundaries (not defects of this change):

- curl, wget and the like that write to api.github.com directly are outside this guard, which reads gh only (the issue's item 7).
- A `gh api --input F` file that is not valid JSON is scanned as text and allowed; that is CRW-917 S3 and recorded in CRW-1028.md.
- `case x in a|b) echo hi;; esac` (a plain command with a | in a case pattern, no script and no post) is allowed; the re-check probe expected a
  refusal, but a command that runs no script and no post is not judged (the CRW-1028 principle).
- The shell reads of the issue's items 1 to 6 (bash, sh, zsh, dash, ksh with a script operand, source, `.`, a missing or over-1-MiB
  script refused, a link out of the temporary root refused, wrappers, prefixes, lists and direct execution by a relative path) were
  answered by CRW-1028 and are pinned by rows CRW-875-01 to 26 and PR845-*; this change re-ran them on its head (the 04 and 08 row
  files) and none was allowed. The pre-merge evaluation of e6fed1659 found three left open there (a script run by an absolute path, a
  refusal reported at `command`, `--input -` refused by accident), which are fixed above.
