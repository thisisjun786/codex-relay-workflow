# CRW-1275 — steer-only management needs no turn-start settings, stranded closes spend no refusal budget, and parent queue ordinals avoid delivery retries

Source: CRW's own design, not the CXC oracle (CXC v0.2.40 has no management pump). Follow-up to [CRW-1273](CRW-1273.md); that entry describes the current management contract. The Go files are `internal/manage/config.go`, `internal/manage/pump.go`, `internal/manage/pump_queue.go` and the shared delivery core in `internal/manage/deliver.go` and `internal/manage/deliver_send.go`. The core is outside the issue's edit region: it chooses between steering and starting a turn, so only it can keep a steer-only delivery from starting one.

- An empty `settings.management` was refused regardless of how management batches are sent; port: fixed. Every management batch goes through `Deliver`, which starts a turn on an idle thread with `send_message_to_thread`, and that tool requires `expected_settings`. A configuration declares a pump that only steers with `manage.pump.steer_only: true`. `coreDeliverSettingsProblem` does not judge it, so `crw manage config` and pump start accept it with an empty `settings.management`. Default delivery still requires both keys. The steer-only pump forms a batch only while its own probe finds an active turn on the management thread. The delivery core (`Message.SteerOnly`) steers an active turn and never starts one, so a thread that goes idle between the probe and the core's own observation is sent nothing. A steer-only request id reaches the outbox only right before `steer_thread` is called with it. An observation that finds no active turn, an observation that fails, or a record that cannot be written leaves the outbox as it was, and the call answers unknown with the status `waiting`. Nothing is reconciled with `get_operation`, no `-r` retry id, refusal or ordinal is spent, and the frozen attempt keeps its id and body. A `management_thread` change before any steer leaves no record of the old thread, so the frozen batch goes to the configured thread under its own id, with no stranded close. A dispatched steer follows the delivery core's contract. An uncertain reply is reconciled. A `not_delivered` refusal retries under a new id into the turn the call observed, without a second observation, so every request id the outbox holds was handed to the bridge. A definitive refusal is a refusal the bridge made and is counted, for example `thread_idle` or `expected_turn_mismatch` when the turn ends between the observation and the steer. Parent and supervisor queues keep their own delivery rules. Pinned by `TestManageConfigAcceptsSteerOnlyWithoutManagementSettings`, `TestPumpSteerOnlyNeverStartsAnIdleTurnAfterTheProbe`, `TestDeliverSteerOnlyUnmeasuredRaceKeepsWaitingWithoutRetries`, `TestPumpSteerOnlyObservationWaitNeverParksAndRecovers`, `TestPumpSteerOnlyObservationTransportFailureNeverParks`, `TestPumpSteerOnlyUnsentAttemptFollowsAManagementThreadChange`, `TestDeliverSteerOnlyRetrySteersTheObservedTurnWithoutObservingAgain` and `TestPumpSteerOnlyKeepsUnknownAttemptFrozen`.
- A stranded close advanced the count that parks a batch after three bridge refusals; port: fixed. `mgmt_refused.ordinal` advances for both closes and proven refusals, while `count` advances only for proven refusals. One close followed by two refusals remains pending; the third actual refusal parks, with a log line that accurately names three refusals. A state lacking the new ordinal uses its existing count as the floor, preserving already spent ids; historical closes in that count cannot be identified retroactively. Pinned by `TestPumpStrandedCloseDoesNotCountAsARefusal`, `TestPumpManagementOrdinalReadsLegacyRefusalCount` and the existing stranded-close tests.
- Parent queue refusal ordinals collided with `Deliver` retry request ids; port: fixed. An outage spends `B`, `B-r1` and `B-r2`, each kept by the bridge's ledger with its argument fingerprint. After the parent reasoning settings are corrected, a refusal ordinal `B-r1` reaches the ledger with another fingerprint, the bridge answers a conflict, and the batch stays frozen although the bridge has recovered. Refusal batches go out under `B-m1`, then `B-m2`, through the ordinal helper the management batch uses (`pumpMgmtOrdinalID`). Existing frozen pins keep their exact logical ids and are reconciled before any fresh batch is formed. Pinned by `TestPumpQueueRefusalOrdinalNeverCollidesWithDeliverRetryIDs` (recovery and exactly-once archival on the fingerprint ledger fake), `TestPumpQueueRefusedBatchRetriesWithOrdinalThenMovesAside` and the existing parent queue pin and reconciliation tests.

- A lost `not_attempted` steer receipt froze a management batch if the active turn changed before recovery; port: fixed. The bridge fingerprints `expected_turn_id`, so reusing that request id for the new turn conflicts with the recorded arguments. After `get_operation` confirms non-delivery, steer-only recovery selects a fresh `-r<n>` id within the existing two-retry cap, even for a `not_attempted` receipt. The ordinal comes from the persisted dispatched id, so it remains bounded across calls and restarts. Idle observations leave that record unchanged and spend no retry. An uncertain receipt still freezes the attempt without any resend. The original body is delivered once on the recovered turn and later management events drain. Default and parent delivery retain their existing reconciliation rules. Pinned by `TestDeliverSteerOnlyLedgerRejectsChangedTurnAfterNotAttempted` (the actual bridge ledger), `TestDeliverSteerOnlyLostRefusalRecoversOnANewTurn` (including idle recovery and accepted replay), `TestDeliverSteerOnlyLostRefusalRecoveryRespectsRetryCap`, `TestPumpSteerOnlyLostRefusalDrainsFrozenBatch` (the fingerprint-ledger fake and a later event), and the existing uncertain-attempt tests.

These are source and temporary fake-bridge and isolated bridge-ledger checks, not installation or live delivery evidence.
