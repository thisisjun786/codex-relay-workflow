# CRW-1038 — the integration queue runner as a product command

Source: CRW's own host tooling, not the CXC oracle (CXC v0.2.40, commit 3c1459ac, has no integration queue). The reference is the shell runner `cc-queue-runner.sh` with `integrate_git.sh` and `resolve_plugin_version.py` (outside the repository, read and never modified); the Go side is `internal/integrator` and `internal/manage/integrate.go` (`crw manage integrate`, [docs/relay/integrator.md](../../relay/integrator.md)). The port keeps the shell runner's behaviour on the plain-head path (queue directories, lock, gate recheck, ordered `merge --no-ff`, version-line-only conflict resolution then re-derivation, verification hook, fast-forward push, exit codes 0/2/3/4/5, one batch retry then one run per head) and records where it deliberately differs. Each line below is a defect of the shell runner or a deviation found while porting.

- A head that was already in the branch (`left_out` `already-in-dev`) was moved to `conflict/` by the runner, which reads any left-out head as a conflict, so an owner was asked to refresh a head that had landed; port: fixed (the head goes to `done/`; the run's status stays 5 when nothing else was merged).
- The runner matched a left-out head by `grep` of `crw-<number>` in the summary line without an end mark, so issue 10 matched `crw-100`, and issue 1 matched `crw-10`; port: fixed (the queue is moved from the run's structured lists, never from the summary text).
- The runner moved a pending file by name after the run, so a file the coordinator had refreshed during the eight-minute verification was moved to `done/` with the new, unmerged head; port: fixed (a file moves only while it still holds the head the run worked on; otherwise it stays in `pending/` and the log says so).
- `resolve_plugin_version.py` returned success for a conflicted file that held no conflict markers (a modify/delete conflict leaves the file in place), and the runner then added and committed it, resolving a semantic conflict silently; port: fixed (`ResolveVersionConflict` refuses a file without a conflict block, and a conflict is resolved only when the one unmerged path is the plugin manifest and every block is one `"version"` line on each side).
- A merge that failed without stopping for conflicts (no `MERGE_HEAD`, for example a missing committer identity) was reported as `conflict` for every head; port: kept as a left-out head with the reason `merge-error`, which moves to `conflict/` like the shell's but is named for what it is.
- The runner decided on the lock before the gate and then let `integrate_git.sh` take it; a run that started between the two was refused after the gates had already moved heads to `blocked/`; port: fixed (the lock is held for the whole pass and taken before any gate runs or any file moves; the queue is listed once before it only to tell an empty queue from work, as the shell runner's `ls` did, and read again under it).
- `integrate_git.sh` left `/scratch/crw/integration/tmp-<tag>` behind on every run that re-derived the version line; port: fixed (the run's private temporary directory is removed with its worktree, and only a directory the run created itself: `mkdir` fails on an existing `tmp-<tag>`, which ends the run with status 2 and is never deleted, where the shell's `mkdir -p` and cleanup shared it).
- The solo-mode state lived in the runner process, so a restart during a failed batch's one-at-a-time passes went back to batching; port: fixed (`solo-heads` in the queue directory; a rollback to the shell runner ignores the file); the state names the heads that are owed a run, so a member's retry cannot use up another member's run, which a bare count did.
- Two passes in one minute shared the tag `cc-qMMDDHHMM`, so the second found the first's worktree path in use and ended with status 2; port: fixed (the tag has seconds, and is reserved by creating its log exclusively, so a second pass in the same second takes `<tag>-2` instead of overwriting the first run's summary, verification log and record).
- `integrate_git.sh` ignored the status of `git add` and `git commit` of the re-derived version line, then verified the worktree and pushed `HEAD`, so a refused commit (a hook) verified one tree and pushed another; port: fixed (a failed add or commit ends the run with status 2, and the worktree must be clean before the verification, so the verified tree is the pushed commit).
- A gate that exited non-zero but whose last line began with `PASS` counted as passing, because only the last line of the pipeline was read; port: fixed (the status must be 0 as well).
- Not ported, by decision: the relay is neither read nor written (`merged` marks, reach observation, relationship and child clean-up stay with the parent), the generated-file resolvers (refactor-backlog assemble, dispatch-cases, refusal-reason block) are not part of the version-only rule, and the shell scripts stay the live runner until the explicit switch described in the integrator document.
- The runner had no notion of a termination signal: a signal during a gate, a merge or the verification surfaced as a failing gate, a conflict or a failed verification, and during the second fetch or the push as `dev-moved` or `push-failed`, and so blocked or retried heads that were never judged; port: fixed (a cancelled pass is `cancelled`, status 2, at any of these points, including right after a verification that passed, and leaves every undecided head in `pending/`; a gate that cannot run is likewise no verdict).
- The record and verification commands inherited the caller's `GIT_DIR` and `GIT_WORK_TREE`, so a command that asked Git for its repository could read or change the shared checkout instead of the private worktree; port: fixed (the environment is cleaned of Git routing variables, `record_version_env` is applied after).
- The runner pushed the commit it had captured before the verification, so a verification command that repaired the source, staged a file, committed or amended the worktree and exited 0 had verified one tree and pushed another; port: fixed (after a passing verification HEAD must be the verified commit and `git status --porcelain` empty, otherwise status 2, nothing is pushed and the heads stay pending).
- The shell runner checked the pending file and moved it by name in two steps, so a refresh that landed in between moved the new, unprocessed head to `done/` (the earlier fix narrowed the window, it did not close it); port: fixed (the file is renamed first to a private name in the destination directory and its head is read from the moved file; another head is put back as `pending/<name>` without replacing a newer file, and only the processed head replaces the destination). A writer that changes the same file in place after the rename is not detected; the coordinator replaces files atomically. A put-back that fails for another reason than a newer file in `pending/` keeps the private file (never removed while it is the only copy), and the next pass puts it back before it reads the queue.
