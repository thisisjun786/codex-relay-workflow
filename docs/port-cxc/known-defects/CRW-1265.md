# CRW-1265 — a sandboxed Codex runs only in a dedicated root: never the account home, a directory above it, or a directory above a project root

Source: not an oracle behaviour. CXC v0.2.40 (commit 3c1459ac) starts no sandboxed Codex of its own and has no counterpart of the rule; the defect is the port's own product paths, found on 2026-10-11 when `/home/jun/.git` appeared and vanished 63 times in 140 seconds and an account-wide backup failed. The Codex linux sandbox (bubblewrap) makes and removes an empty `.git` mount target in a working root that has none (openai/codex PR #17734, issues #26463 and #37318). The Go files are `internal/sandboxroot` (the rule, `testdata/cases.json` the table the coordinator's Python guard runs too), `internal/crwconfig` (`paths.go` `sandbox_root`, `config.go` `sandbox.project_roots`), `internal/bridge` (`create.go`, `worktree.go`, `mutations.go`, `sandboxroot.go`), `internal/relay/adapter/transport.go` (`guardedSend`), `internal/manage` (`childresume.go`, `relay.go`), `internal/role/managed_spawn.go`, `internal/relay/service/launch.go`, `internal/runtime/install/unit.go` and `internal/dev/laneparity/realhost.go`.

- `create_thread` checked only that `cwd` was an absolute, existing directory, and no other product path judged where a sandboxed thread ran: a `workspace-write` or `read-only` thread could be created, resumed (bridge send, child-resume, relay delivery) or spawned (managed spawn) with the account home, a directory above it or a directory above other projects as its working root or writable root. Every such path now asks `sandboxroot.Check` (working root), `CheckWritable` (writable roots: the App Server `runtimeWorkspaceRoots`, the sandbox policy's `writableRoots`, `sandbox_workspace_write.writable_roots`) or `CheckDestination` (a worktree that does not exist yet) before the App Server or Codex is called; a refusal sends nothing and leaves no success record. port: fixed.
- A sandbox that is off (`danger-full-access`, `dangerFullAccess`, the bypass flag) is outside the rule and runs as before; a sandbox that cannot be determined counts as on, and `externalSandbox`, which creates no bubblewrap mount but is not named by the decision, counts as on too. port: kept (decision C names only the modes that create no sandbox).
- `CheckDestination` takes the sandbox as well as the destination (`CheckDestination(destination, sandbox)`; the issue text has one argument), because a worktree thread started with `danger-full-access` is outside the rule and its destination must not be refused. port: deviation from the issue's signature, same behaviour for a sandboxed run.
- A resume whose cwd cannot be determined (the host reported none and the request named none) has no working root to judge; its writable roots are still judged, and `thread/resume` reports the cwd it runs at. A real host always reports one. port: kept.
- A relay delivery, a bridge send and child-resume judge the cwd the resume will run at (the request's, else the one `thread/read` reports) under the sandbox the request states, else the host reported, else the recorded settings; a thread made in the account home before the rule existed is therefore not run again there (`sandbox_root_refused`, nothing sent, retry-safe in a relay delivery). The writable roots they judge are every root the thread would keep: the request's, the recorded settings' (also in a settings-free resume, which sends none but inherits them) and the ones `thread/read` reports (`runtimeWorkspaceRoots`, the sandbox policy's `writableRoots`), so a safe cwd does not hide the account home among the roots (`sandboxroot.RootsOf`). `create_thread` also judges the writable roots the host's answer to `thread/start` reports (`sandboxroot.RootsOf` of the answer and of its thread; `createdRefusal`), because a creation that states no policy and no roots inherits the host configuration's `sandbox_workspace_write.writable_roots`: an account home among them withholds the title and the initial prompt, and the thread stays retained (a worktree thread states its whole policy, so a root the host adds is a settings finding already). `crw manage child-resume` judges, besides the record, what `thread/read` reports for the loaded child (cwd, runtime roots, policy and config roots, under the reported sandbox and the recorded mode; nothing is sent, the dry run included) and what `thread/resume` answers with (no turn is started). `send_message_to_thread` also judges what `thread/resume` answers with, before `turn/start` (`resumedRefusal`: the cwd and the `sandboxroot.RootsOf` roots of the answer and its thread, under the stated, else reported, sandbox), because a send that states no policy resumes the thread under the host configuration's writable roots and only the resume answer reports them (`thread/read` does not): an account home among them fails the send with `sandbox_root_refused` and "the thread was resumed but no turn was started; message withheld", for a `notLoaded` and an `idle` thread alike (`TestSendMessageRefusesHomeRootsOnlyTheResumeAnswerReports`). The subscription-only resume (`HoldThread`: `threadId` and `excludeTurns` only) starts nothing and is not judged; `TestSubscriptionResumeSendsNoCwdSandboxOrTurn` pins its fields. port: fixed.
- A managed spawn's child works in the parent's cwd and the host sets its sandbox, which the dispatch record does not carry, so it counts as on: a parent session opened in the account home, above it, above a project root or outside every dedicated root cannot spawn a managed child, and the denial names the rule. Both ways to name the dispatch are judged: the marker in the task (`ManagedSpawnResolver.Preview`) and, for a native V2 spawn whose task is ciphertext, the opted-in `task_name` (`ManagedSpawnResolver.Named`, `spawnHookManagedCiphertext`), which denies the call instead of leaving it unmanaged and allowed; a V2 call that names no dispatch of the session is nobody's business of the rule. `internal/role/spawn` runs its tests under `sandboxroottest` too. port: fixed.
- The relay supervisor and worker (`Service.launch`), every relay command `crw manage` runs with an existing `--state` directory, and the systemd user unit that `register-service` writes (`WorkingDirectory=<state directory>`, which every non-dry-run `register-service` makes, a repeated one too) run in the relay's state directory instead of the directory they were started from (the paths a caller names relative to its own directory, `--socket` and an execution policy that `CODEX_THREAD_BRIDGE_EXECUTION_POLICY` names for the service, and `--socket`, `--cwd`, `--backup-state-to`, `--settings @file`, `CODEX_THREAD_BRIDGE_EXECUTION_POLICY` and `CODEX_SESSION_RELAY_SCOPE_DIR` for the manage commands, are joined below the caller's directory as raw text first (also when `service run` hands its worker the environment: `Service.environment`), so they keep naming the same files, a symbolic link followed by `..` included, and the supervisor reads the policy digest its launch checked); before, a relay started from a login shell or a user unit had the account home as its cwd. A unit written before this line existed is still recognised as the installer's own for `--remove`, but `register-service` on it answers `unit_differs` (it never overwrites a unit it did not just render): remove it and register again. port: fixed.
- `crw-dev parity realhost` runs `codex exec` with `sandbox_mode = "read-only"` in every cell; its scratch directory (default: the temporary directory) and each cell's work directory are now checked before Codex is started, so a scratch outside the sandbox base (`paths.sandbox_root`, default `/scratch/crw`) is refused and the run names `--scratch`. port: fixed (a behaviour change for a default `TMPDIR` of `/tmp`).
- Test fixtures that named a thread's cwd or roots by a path that does not exist (`/w`, `/parent`, `/workspace/example/...`) now name real directories of the test tree; the goldens keep their recorded names through substitutions (`internal/relay/adapter`). Each test package whose product code reaches the rule installs `sandboxroottest` in `TestMain`, with a fake account home, a fake Codex home and a fake crw configuration, so no test reads the real home, the real `~/.codex` or the real configuration. port: kept (test-only).
- `CODEX_HOME` is a path the kernel resolves, so the rule reads `config.toml` and derives the Codex worktree base below it as raw text (`crwconfig.JoinRoot`), a link followed by `..` included; a base that does not exist and holds a `..` element names nothing. port: fixed (`TestCodexHomeLinkFollowedByDotDotNamesTheKernelsDirectory`).
- `sandbox_root` is the one host path the product names: its default `/scratch/crw` (`crwconfig.DefaultSandboxRoot`) is decision C's answer, while CRW-958's `TestNoHostPathOrDeviceNameInProduct` forbids host paths in product text. The scan allows exactly that constant line and no other (the comments that named the path now say "the host's scratch disk"); a host that keeps its scratch disk elsewhere overrides `paths.sandbox_root`. After merging dev 67061b2e, `sandbox_root` is the last root `crw config paths` lists, after the CRW-958 tool roots, `log_root` and `relay_state`; the register-service unit carries both `WorkingDirectory=<state directory>` and, when a registration named a configuration file, `Environment=CRW_CONFIG=` (a unit with either line missing is still recognised for removal), and the manage relay helper runs in the state directory with the configuration file, the tool roots and the caller's relative policy together. port: kept (merge of two decided behaviours, `TestRelayHelperInStateDirectoryKeepsConfigAndPolicyEnvironment`, `TestRenderUnitSetsWorkingDirectoryToState`).
