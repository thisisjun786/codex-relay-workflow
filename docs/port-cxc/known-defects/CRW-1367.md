# CRW-1367 — the session call's recovery re-sent a repair, overwrote a stray ref and a close file, and lost what a step write or a crash left

Source: CRW's own design (CRW-1316 design sections 3.1 to 3.3, 5 and 6.3; follow-ups of CRW-1331, lane S2a, from its independent and final verifications), not the CXC oracle (CXC v0.2.40, commit 3c1459ac): the oracle has no flow engine, and its role calls are subagents of the session that runs them. The Go side is `internal/flow/engine` (`session.go`: `sessionRecover`, `sessionBind`, `sessionTaken` and `sessionFind` new, `rowTokens` new, `sessionChecks`; `sessionhost.go`: `StrayRef`, `HeadKeeper`; `stepbus.go`: `CloseName`, `Step.File`, `FileStepBus.Steps`; `journal.go`: `EvStepUnwritten`), `internal/flow/backend/agent/git.go` (`Allocator.KeepRef`) and `internal/flow/cli/next.go`.

- A repair (`send_input`) step the subagent had already taken was looked up nowhere when a resumed run went on from its `step_published` row: the marker search and the find ticker ran for spawn steps only, so a run that died after the owner sent the repair and before its `turn_started` row was stored (over the SQLite journal, also when the row was stored in a batch the death lost) published the same repair again, and the owner sent it a second time; port: fixed (a resumed step, and a waiting one every sixth poll, is looked up on the host: for a `send_input` the turn that carries its marker on the subagent it was for is bound, and the repair is never sent again. Pinned by the `repair sent before the report` and `repair turn_started` cases of `TestSessionRunDeathAtEachRow`, over both journals).
- The stray ref of an executor that committed was `refs/crw/flow/<run>/stray/<node>/a<attempt>`, written with `git update-ref` and no old value, so the second executor call of one allocation (its fix round, in the same worktree) moved the ref and the first call's record was lost; port: fixed (the ref is `refs/crw/flow/<run>/stray/<node>/a<attempt>-<call>`, one per call, and `Allocator.KeepRef` creates it by a compare-and-swap against no ref, keeps a ref that already holds the commit and refuses to move one that holds another. Pinned by `TestSessionSecondExecutorCallKeepsItsOwnStrayRef` and `TestAllocatorKeepRefNeverOverwrites`; `TestAllocatorKeepsAStrayHead`, `TestSessionExecutorThatCommitted` and the proof tests of `internal/flow/ops` read the new name).
- A resumed call that goes on from its `turn_started` row (a bound stage) never passes the bind, so the step file the dead process left stayed published and `crw flow next` kept handing it out; port: fixed (the resume retracts the step of the bound turn, and of a lost attempt, before it goes on. Pinned by the leftover-step check of every case of `TestSessionRunDeathAtEachRow`).
- A step whose packet or file could not be written (a full disk) ended the call `outcome_unknown` with `dispatch_unknown`, a `dispatch_unknown` escalation and a recovery hold of the node, although nothing had been sent; port: fixed (warn and record: the flow row `step_unwritten`, `input_state` `not_delivered`, once, and the step is written again every poll until it can be or the turn ends; the call is never ended for it. Pinned by `TestSessionStepBusWriteFailureIsNotDispatched`).
- A close step's file was `steps/<call>/close-a<n>.json`, named by the attempt alone, so a `pair_mismatch` close and the close after the harvest in the same attempt were one file and the later overwrote the earlier before the owner took it; port: fixed (`close-a<n>-<agent>.json`, one file per subagent; the call is the directory; `crw flow next` removes the file it read, so a close file written before the change is handed out once too. Pinned by `TestStepBusClosesOfOneAttemptAreKeptApart` and the two closes of one attempt in `TestNextHandsOutTheStepsOfTheBus`).
- A recovered `send_input` turn started its token count at zero, so the rollout's running total counted the turns before it again in the process that recovered it (the measured budget over-counted); port: fixed (a `send_input` step's `step_published` row records `tokens_seen`, the rollout total the turns before it counted, and `call_tokens`, the call's tokens; a resumed call restores both, so the completed row records the rollout's total and the process counts only what the turn added. Pinned by the token checks of the repair cases of `TestSessionRunDeathAtEachRow`).
- The session crash tests ran over the memory journal only, which stores every row it is given; the SQLite journal commits an intent at once and batches the other rows, so a death loses the `thread_started` and `turn_started` a bind writes together, and nothing tested that; port: fixed (the death cases of `TestSessionRunDeathAtEachRow` and `TestSessionResumeAfterThreadStartedAdoptsTheRecordedAgent` run over both journals, the SQLite one opened again over what the store holds; the same final rows, one `thread_started` per attempt. Found by them: a resumed step answered the dispatch report the dead process never answered only after it had published the step again, so the owner spawned a second subagent for the attempt; the resumed step now answers a waiting report of its own first (`sessionTaken`). A subagent the host no longer knows is never bound over the SQLite journal, and the step it publishes again is taken by a new subagent for the same attempt, with no lost row: nothing recorded the first subagent).
- Deviation: the stray ref carries the call in its name instead of keeping the old name with a compare-and-swap alone; port: kept (with one name per allocation attempt a compare-and-swap would refuse the fix round's record, which is the record to keep beside the first; refs of a run written before the change keep their names, and the proof reads the completed row's `executor_head_moved`, never the ref's name).
- Deviation: the close file carries the subagent, not the call: the call is the directory the file is in, and the closes that collided were of one call and one attempt with two subagents; port: kept.
