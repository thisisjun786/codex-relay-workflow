# CRW-1269 — dag-restart names the command that takes each unresolved call (R07 × F05)

Source: CRW's own design (0.5.0-alpha; found at the last verification of CRW-1215, head 0ac62aa7), not the CXC oracle. The Go side is `internal/flow/callstate`, `internal/relay/dagsched/agent_lifecycle.go` (`agentCallStates`, `resumeOfAgent`), `internal/flow/engine/{recon,resumecli}.go`, `internal/flow/journal/resumeenv.go` and `cmd/crw/main.go`; the tests are `internal/relay/dagsched/agent_lifecycle_test.go`, `internal/flow/callstate/callstate_test.go`, `internal/flow/engine/recon_fix_test.go` and `internal/flow/journal/resume_cli_test.go`.

- `agentCallHeld` judged a call unresolved when its newest event was not completed, null_model, refused or superseded, and named `crw flow recover` for all of them. Since CRW-1198 `crw flow recover` accepts only a call whose last terminal row is an unknown outcome with reason `dispatch_unknown` that nobody has cleared (`callState.held()`), so dag-restart named a command that refuses an unanswered dispatch intent, a call whose hold was cleared, and a call that ended held for an engine pause or a host failure. dag-restart now reads the call's rows with `callstate.Classify`, which `callState.held()` of the engine uses too, so the two cannot disagree: a call in recovery hold gets `crw flow recover`, every other unresolved call gets `crw flow resume`, and the report's detail names the arguments (`CALL (--adopt THREAD|TURN | --absent)`, `RUN SCRIPT`). A node with a call in recovery hold and another unresolved call is told to recover first. Pinned by `TestRestartNamesTheCommandOfEachCallState` (an unanswered intent, a started turn, a cleared hold, a held call, an unknown outcome of another reason, a hold) and `TestClassify`; port: fixed.
- The resume command did not exist: the action for a released node was the text `run resume`. `crw flow resume [--state DIR] [--socket PATH] [--repo DIR] [--args JSON | --args-file FILE] RUN SCRIPT` is defined by CRW-1200 (the resume walk): it opens the stored journal and the App Server (`engine.ResumeEnv`, installed by the binary like `RecoverEnv`), checks that the script and the arguments are the run's, and runs the walk. dag-restart's action for a released node is now `crw flow resume` too. Pinned by `TestGuidedCommandsAcceptEachCallState`: the built binary takes a call at an unanswered intent with `crw flow resume`, takes a call in recovery hold with `crw flow recover`, refuses it with `crw flow recover` once it was cleared (exit 1, not in recovery_hold) and takes it with `crw flow resume`, and exits 2 for a script, arguments or run that are not the run's; port: fixed.
- The dag-restart report calls every unresolved call `held` (state) and `reconcile` (resume value), as before; the state of a node whose call only waits for the run's resume stays `held`. port: kept.
- An edited script is not a resume of the run (`crw flow run W --resume-from RUN` of the design is not here); `crw flow resume` refuses a script or arguments whose digest is not the one on the run's `started` row. port: pending.
- Supersedes CRW-1215.md, item beginning "A recovery hold writes nothing": now port: fixed (the sentence "A held node needs `crw flow recover`, a released one `run resume`" is replaced: a node whose call is in recovery hold needs `crw flow recover`, a node with any other unresolved call or none needs `crw flow resume`; held is still derived from the journal, per call, by `callstate.Classify`).
- Supersedes CRW-1215.md, item beginning "`dag-restart` prints an `agent` object": now port: fixed (the released action is `crw flow resume`, and the `reconcile` action is `crw flow recover` for a call in recovery hold and `crw flow resume` for any other unresolved call).

- Follow-up (end condition of the third state): the decided answer said a call that ended held for another reason gets "that reason's resolution command". There is no such command per reason, and none is needed: `crw flow resume RUN SCRIPT` is the resolution for every reason a call ends held, so dag-restart names the same command for all of them. A held call has no outcome to prove: unlike `dispatch_unknown`, nothing about it can be true on the host without the journal knowing (the request was refused, never sent, or answered with a failure), so no operator input (`--adopt THREAD|TURN`, `--absent`) is asked for. What a hold needs is the condition outside the run to be gone (the budget, the host's availability, the engine pause, which does not outlive its process) and a process that goes on with the call. The resume walk does that for every reason (`heldInPlace`): the call keeps its attempt, a `hold_cleared` row is written, and the reason decides only what the process sends - the original packet for a call held before its thread existed (`budget_exhausted`, a refused `thread/start`), the fixed continuation instruction for a delivered turn (`host_infra_*`, `engine_paused`) - and only where the walk cannot go on in place (`worktree_failed`, a worktree whose files are not the hold snapshot, a thread that is not idle again for `host_infra_activeTurnNotSteerable`) the call runs again as a new attempt; the command is still the same. A resume run while the condition still holds ends the call held again with a new row, never a refusal of the command. Pinned end to end by `TestGuidedCommandsAcceptEachCallState` (`internal/flow/journal/resume_cli_test.go`): the first process is the engine on the fake host, and a call held for `budget_exhausted`, for a refused `thread/start` (`host_infra_usageLimitExceeded`) and for a failed turn (`host_infra_serverOverloaded`) is read as unsettled by `callstate.Classify` (the reading dag-restart and `crw flow recover` share, so dag-restart names `crw flow resume`), refused by the built binary's `crw flow recover` (exit 1, not in recovery_hold) and taken by its `crw flow resume` (exit 0, `hold_cleared`, the same attempt ends completed); the dag-restart side is pinned by `TestRestartNamesTheCommandOfEachCallState` (held and other unknown outcome -> `crw flow resume`); port: kept (a deviation from the wording of the issue: one resolution command for all held reasons, with this reason).
