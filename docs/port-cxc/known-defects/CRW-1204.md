# CRW-1204 — what goes up from a flow run: escalations, report-up, the receipt of an oversized issue, the plan summary hand-off (F11)

Source: the 0.5.0-alpha design issue F11 (CRW-1204). CXC v0.2.40 (commit 3c1459ac) has no flow run, no upward report of a run and no `crw manage send-parent --role`; the oracle's `supervisorchannel.py` is untouched, so there is no oracle line for these rows. The Go files are internal/flow/apply (`Apply`), internal/flow/report (`Writer`, `RunHook`, `ReconcileSummary`, `ForeignAppender`), internal/flow/cli, internal/flow/engine/summary_hook.go, internal/flow/journal/journal.go (`SetOnCommit`), internal/flow/workflows/issue-lane.js, internal/manage/{sendparent,sendparent_supervisor,pump_supervisor,pump_flow_sources,summary_queue,supervisor_settings}.go and internal/manage/{pump,pump_queue}.go; the tests are in the same packages (`TestApply*`, `TestReportUp*`, `TestSummary*`, `TestSendParent*`, `TestSupervisorFlush*`, `TestPump*Notice`, `TestFakeOversizedReceiptApplyScenario`). The reading of the design is docs/flow/reporting.md.

- A command that writes into a run which may be alive cannot take the next sequence number of the run's journal: the journal counts in memory and the primary key of `flow_events` is `(run_id, seq)`, so a command that wrote `max(seq)+1` would make the run's next flush fail and end the run. The rows of a command (`crw flow apply`, `report-up`, `report-ack`, `report-delivered`) are numbered from `engine.ForeignSeqBase` (`1 << 40`), and the journal and the engine count after the largest number below the base (`journal.Open`, `lastRunSeq`). port: deviation from "seq counts up within a run" (a run's own numbers still do; the commands' rows are read back as flow rows of kinds the engine does not act on). Pinned by `TestForeignRowsNeverCollideWithTheRunsJournal`, `TestApplyPathReconcilesTheSummaryOfTheOrchestratorsRun` and `TestLastRunSeqIgnoresTheRowsOfCommands`.
- The issue body names `internal/flow/workflows/issue-lane.js` as an edit region and no earlier issue had made it: the file is made here. It runs one executor call (a fresh thread, then fix rounds on the same thread, three at most), commits and verifies the executor's snapshot with the lane's operations, and has a reviewer of another family rule on the head; it lands nothing and escalates with reasons that close no execution (`child_scope_gap`, `child_executor_null_model`, a configuration fault), because the child's run has no release of its own. Its plan is its argument (`args.issue`, the IssuePlan the project run released the child with). port: kept (the body fixes what the child coordinates, not the script; `crw.releaseChild` of the project lane is unchanged and starts nothing the script needs).
- `crw flow apply` needs a base for `base..head` and the relay event carries none: the base is `--base`, else the event's (the reader leaves it empty), else the commit the child's first executor worktree started from, which the journal records. The lab found the difference: the integration branch had moved before the child started, so the repository's first commit is not the base. port: kept.
- `--override` reaches the independence check only. The body says another judgment is allowed "only with --override and a recorded reason" and names no other; an unattributed commit or a criteria digest that differs is an integrity finding, not a judgment, and does not pass whatever the reason. port: kept (a reading of the body).
- A failing upward hook recursed. The engine's first form of `hookRun` released the hook and then appended the row that tells the failure, and in a journal that commits a batch for a row the append told the hook again, which failed again: stack overflow (found by `TestEngineCallsTheUpwardHookAtStartBatchesAndFinish`). The row is written before the hook is released and the hook runs one call at a time; a batch committed during a call is not told, because the call in progress or the next one reads the whole journal. port: fixed in the same change.
- The first form of the hook also deadlocked a hook that appends rows from `RunStarted`: the append committed a batch, the batch was told to the hook, and the hook waited for its own lock (found by `TestEngineHandsTheRunToTheHook`, which hung). Same single-flight rule. port: fixed in the same change.
- `unverified_pair_for_unloaded_thread` is not in `deliverRefusalCodes`, so the delivery core classes that bridge refusal `unknown`. The supervisor path reads the receipt's rpcError code itself and treats the code as the race it is (queue the notice, a new attempt id, no count against the refusal limit); the parent path keeps the core's classification. port: kept (the parent path, supervisor roles and the bridge's rejection rules are not changed, as the body says).
- A summary notice that the pump moved to `sent/` and that the run then asks for again would have been written into the queue a second time (the `--queue` path does not look at `sent/`), and a batch that the pump pinned and other notices later changed would have carried it twice. The summary path (logical ids that start with `summary-`) checks pending, pinned, `sent/` and `refused/` before it writes, the pump leaves a summary notice that `sent/` holds out of a batch, and each flush leaves a settlement file. The queue path of every other notice is unchanged. port: fixed for the summary notice, kept for the rest. Pinned by `TestSummaryNoticeQueueReplayDeliveredOnce` (three cases) and `TestPumpQueueDropsAQueuedCopyOfADeliveredSummaryNotice`; the parent queue by `TestPumpQueueParentNoticesUnchanged`.
- The red evidence: the tests were written with the code, not before it, so their red runs are made against the behaviour taken out. The apply tests ran against an `Apply` that returns "not implemented" (evidence/apply-red.log, eight failing), and the report, manage, engine and scenario tests against the writers, the hook, the sources, the supervisor path and the summary queue path stubbed out (evidence/report-up-red.log: 23 of the named tests fail; `TestSendParentDefaultRoleUnchanged`, `TestPumpQueueParentNoticesUnchanged` and `TestDeliverRequiresAConfirmedIdleObservation` pass, as they guard what the change leaves alone). The recursion and the deadlock above were found by tests, not by a red run.
- Verification round 1 (apply). The first form of `crw flow apply` reconciled the plan summary only after it recorded a verdict, so a `next_turn` (the normal end of an expired `--wait`) or a refusal reconciled nothing, and a run that died after its last batch was not recovered by the next apply the body names. `Apply` now calls `Deps.Reconcile` (was `AfterVerdict`) on every invocation that resolved the event, whatever the state; a failure of it is `summary_error` and changes neither the state nor the exit status. An event the relay does not hold calls nothing, and a hook with no child run falls back to the relationship's plan. port: fixed. Pinned by `TestApplyBringsTheSummaryUpToDateEveryTimeItRuns` (red: evidence/fix1-apply-red.log).
- The intent of a summary id is written by a check and a later flush, not in one transaction, when the writer is the live run (`JournalAppender`): the run and a concurrent `crw flow apply` (`ForeignAppender`, which does check and insert in one transaction) can each write a `summary_notice` for one summary id. The rows are harmless duplicates: `noticeRows` reads each summary id once, sends are idempotent by logical id, and the settlement is `AppendOnce`. A run-side store transaction would need the journal to write through the store directly; not done. port: deviation from "checked in the writing transaction" for the run-side writer, kept. Pinned by `TestSummaryDuplicateIntentRowsSendAndSettleOnce`.
- `run_dead` was judged by the last row of the run, and an agent turn writes none while it is in flight: a live run in a turn longer than `run_dead_seconds` was reported dead. A run with an open agent call (a `flow_calls` agent call with no terminal row) is now judged by the longer of `run_dead_seconds` and `pumpFlowOpenCallGrace` (6 hours); a run whose process died inside a turn is still reported, after that grace. port: fixed. Pinned by `TestPumpRunDeadWaitsForAnOpenAgentCall`.
- `send-parent --role supervisor` meeting the unloaded-thread refusal queued the notice with the next ordinal but raised no `report_undelivered`; only the pump's own observation did. The flush now raises it once for a notice whose `LoadRetry` is above zero (the direct path's mark), whether or not that attempt delivers. port: fixed. Pinned by `TestSupervisorFlushRaisesUndeliveredForADirectPathUnloadRefusal`.
- Where the tests stop: the summary hand-off crash tests (`TestSummaryHandoffCrash*`) use a fake `Sender`, so they pin the rows (intent, settlement `queued`) and the logical ids the run sends, not a bridge `send_message` count; the single send of one logical id through the real `send-parent --queue` is pinned in `internal/manage` (`TestSummaryNoticeQueueReplayDeliveredOnce`, `TestSendParentQueueWritesTheNoticeAndSendsNothing`, which reads the fake bridge's log and sees no call of any tool, `get_active_turn` included), and the report-up queued/delivered rows in `TestReportUpQueuedWhenSupervisorBusy`; `TestReportUpNotLoadedQueuesThenDeliversAfterLoad` pins the bridge calls and the argv of `crw flow report-delivered` (the only writer of delivery rows, which the flow tests pin). No single test runs `report.ManageSender` against the real send-parent and a fake bridge. port: kept.
- A child's issue-lane run is resumed with the child task as its actor, so the run's escalations go to the child's thread, not the orchestrator's; the orchestrator learns from the receipt and from `crw flow apply`, the manager from the pump. docs/flow/reporting.md says so. port: kept.
