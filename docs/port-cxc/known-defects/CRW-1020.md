# CRW-1020 — the crw review ledger: a kept copy that failed, the owner of a restored path, and the durability of the copy

Source: the CRW-590 post-merge evaluation of PR 604 (three P1 findings, read statically on dev a850a3fcc). The defects are the port's own: `crw review` has no counterpart in CXC v0.2.40 (commit 3c1459ac), whose `atomic-write.ts` (`renameWithRetry`) is the only oracle of the publish step. The Go files are internal/review/command/command.go (execute), keep.go (keep, restore, restoreWanted, ownerOf), internal/pabcd/crwdir/atomic.go (PublishDurable, SyncDir) and docs/review/crw-review.md (Files). The atomic-write helper did not move: it is still internal/pabcd/crwdir/atomic.go, not internal/crwdir.

- A kept copy that could not be written still produced the finished record: execute appended `finished` whatever `l.keep` returned, published the files, and reported the keep error only at the end (and not at all when a later publish failed), so a publish failure left a patch that was reviewed with no file and no copy to restore from, and a rerun answered `already_reviewed` without restoring anything (CRW-1020 item 1); port: intentionally-changed (coordinator decision D1: fail and retry. A copy that cannot be kept now returns the error naming its cause before the finished record is appended and before any file is published, records a `failed` line, and leaves the patch open, so the same command can be run again; one more model call is accepted over a finished record that points to a missing copy. Pinned by TestResultThatCannotBeKeptIsNotRecordedAsFinishedAndTheNextCallReviewsAgain, which also runs the patch again once the fault is gone, and by TestResultWhoseKeptCopyCannotBeMadeDurableIsNotRecordedAsFinished).
- A restore decided from the bytes at the path and not from the ledger: restoreWanted looked at the current file and the one earlier attempt of the same patch, so two patch-ids P and Q of one head and one `--out` (the artifact name is the head's) that restored in turn left Q's request with P's bytes treated as a foreign file, Q was not restored and the post check failed (CRW-1020 item 2); port: fixed (the path belongs to the result the ledger assigned to it last, of any patch: ownerOf. A missing path is restored from that result whichever patch asks, and bytes at the path that are exactly an earlier ledger result for it are replaced by the owner's; a foreign file is still never replaced and a checksum is still written only beside the recorded artifact. The ledger is read again once the run lock is held, since the owner may change while waiting. Pinned by TestRestoreOfASharedPathFollowsTheResultTheLedgerAssignedLast, and TestRestoreOfAnOlderResultLeavesTheNewerResultsChecksumAlone and TestRestoreReplacesOnlyTheUnavailableBytesOfARetryWhoseFilesWereNotWritten still pass).
- The kept copy was published with crwdir.Publish, whose rename is not followed by a directory fsync, and the ledger append syncs only its own file, so after a power failure the finished record could remain with no `results/<sha256>.json` entry (CRW-1020 item 3); port: fixed (crwdir.PublishDurable fsyncs the directory after the rename, and the kept copy is written with it before the record is appended; when `results/` is created in the same call the state directory is synced as well. A failed sync fails the call before the record. Pinned by TestPublishDurableSyncsTheDirectoryAfterTheRename, TestPublishDurableReportsAFailedDirectorySync, TestPublishDoesNotSyncTheDirectory and TestKeptCopyIsWrittenDurablyBeforeTheFinishedRecord).
- crwdir.Publish itself stays without a directory fsync, as its comment says, and so do the two output files that a restore or a review writes into `--out`: they are repaired from the kept copy, which is durable; port: kept (the oracle's rename has no directory sync either, and only the file a record depends on needs it).
- The ledger file's own directory entry (the first `ledger.jsonl` and the state directory) is not synced after it is created; a lost entry loses the record, which leaves the patch open for another review and never a record without its copy; port: kept (the fail-open direction costs one more model call at most).
