# CRW-1020 — the crw review ledger: a kept copy that failed, the owner of a restored path, and the durability of the copy

Source: the CRW-590 post-merge evaluation of PR 604 (three P1 findings, read statically on dev a850a3fcc). The defects are the port's own: `crw review` has no counterpart in CXC v0.2.40 (commit 3c1459ac), whose `atomic-write.ts` (`renameWithRetry`) is the only oracle of the publish step. The Go files are internal/review/command/command.go (execute), keep.go (keep, restore, restoreWanted, ownerOf), internal/pabcd/crwdir/atomic.go (PublishDurable, SyncDir) and docs/review/crw-review.md (Files). The atomic-write helper did not move: it is still internal/pabcd/crwdir/atomic.go, not internal/crwdir.

- A kept copy that could not be written still produced the finished record: execute appended `finished` whatever `l.keep` returned, published the files, and reported the keep error only at the end (and not at all when a later publish failed), so a publish failure left a patch that was reviewed with no file and no copy to restore from, and a rerun answered `already_reviewed` without restoring anything (CRW-1020 item 1); port: intentionally-changed (coordinator decision D1: fail and retry. A copy that cannot be kept now returns the error naming its cause before the finished record is appended and before any file is published, records a `keep_failed` line, and leaves the patch open, so the same command can be run again, the one more attempt of an unavailable review included: that attempt's `started` line is followed by the `keep_failed` line and does not spend it; one more model call is accepted over a finished record that points to a missing copy. Pinned by TestResultThatCannotBeKeptIsNotRecordedAsFinishedAndTheNextCallReviewsAgain, which also runs the patch again once the fault is gone, TestResultWhoseKeptCopyCannotBeMadeDurableIsNotRecordedAsFinished and TestRetryWhoseResultCannotBeKeptDoesNotSpendTheOneMoreAttempt. When the `keep_failed` line cannot be appended either, a first attempt's bare `started` closes nothing, and the attempt's `started` line stays in the ledger: the attempt called the model, so it counts toward the daily cap and the ledger is never cut back to forget it (an earlier version took the line back out and so refunded the cap slot; the evaluation of dad49862 found it). A first attempt's bare `started` closes nothing; the one more attempt's `started` spends that attempt, as a killed process does, and the error says that the attempt is spent as the ledger stands and gives the `started` line to check and the `keep_failed` line to append by hand, instead of telling the operator to run the same command again. Pinned by TestRetryWhoseResultAndKeepFailedLineCannotBeWrittenStillCountsTowardTheDailyCap (another patch of the same day is refused by the cap) and TestRetryWhoseLedgerTakesNoChangeAtAllNamesTheLineThatLeavesTheOneMoreAttempt, which follows the recovery the error gives; a process killed between the failed keep and the `keep_failed` line leaves a bare `started`, which spends the attempt as any killed retry does).
- A restore decided from the bytes at the path and not from the ledger: restoreWanted looked at the current file and the one earlier attempt of the same patch, so two patch-ids P and Q of one head and one `--out` (the artifact name is the head's) that restored in turn left Q's request with P's bytes treated as a foreign file, Q was not restored and the post check failed (CRW-1020 item 2); a post of the asking patch whose path was restored to the other patch's result failed its checksum check too; port: fixed (the path belongs to the result the ledger assigned to it last, of any patch: ownerOf. A missing path is restored from that result whichever patch asks, and bytes at the path that are exactly an earlier ledger result for it are replaced by the owner's; a foreign file is still never replaced and a checksum is still written only beside the recorded artifact. The ledger is read again once the run lock is held, since the owner may change while waiting. The summary comment of the asking patch is made from its own kept copy when the path holds the result the ledger assigned to it for another patch (assignedTo), while any other file is still refused. Pinned by TestRestoreOfASharedPathFollowsTheResultTheLedgerAssignedLast, TestPostOfASharedPathUsesTheAskingPatchsOwnResult, and TestRestoreOfAnOlderResultLeavesTheNewerResultsChecksumAlone and TestRestoreReplacesOnlyTheUnavailableBytesOfARetryWhoseFilesWereNotWritten still pass). The identity of the path is the physical one: the output directory is resolved (filepath.EvalSymlinks, through the nearest existing ancestor for a directory not made yet) before the artifact path is recorded and the path is matched on the resolved directory in ownerOf, restoreWanted, assignedTo and replaces (samePath), so `--out /alias` and `--out /real` of one directory share one history, and ledger lines written with the alias spelling count too. Pinned by TestSharedPathHistoryIsOneAcrossSymlinkAliasesOfTheOutputDirectory and TestOwnerOfMatchesRecordsOfAnAliasSpelling).
- The kept copy was published with crwdir.Publish, whose rename is not followed by a directory fsync, and the ledger append syncs only its own file, so after a power failure the finished record could remain with no `results/<sha256>.json` entry (CRW-1020 item 3); port: fixed (crwdir.PublishDurable fsyncs the directory after the rename, and the kept copy is written with it before the record is appended; the state directory is synced as well on every keep, not only when `results/` is created, since a first call whose sync failed leaves `results/` in place. A failed sync fails the call before the record. Pinned by TestEveryKeptCopySyncsTheStateDirectoryAndNotOnlyTheCallThatCreatedResults, TestPublishDurableSyncsTheDirectoryAfterTheRename, TestPublishDurableReportsAFailedDirectorySync, TestPublishDoesNotSyncTheDirectory and TestKeptCopyIsWrittenDurablyBeforeTheFinishedRecord).
- crwdir.Publish itself stays without a directory fsync, as its comment says, and so do the two output files that a restore or a review writes into `--out`: they are repaired from the kept copy, which is durable; port: kept (the oracle's rename has no directory sync either, and only the file a record depends on needs it).
- The ledger file's own directory entry (the first `ledger.jsonl` and the state directory) is not synced after it is created; a lost entry loses the record, which leaves the patch open for another review and never a record without its copy; port: kept (the fail-open direction costs one more model call at most).
