# CRW-930 — bound D-close: a refusal after a clean publication denied the published marker and plan

Source: CXC v0.2.40 (`3c1459ac`) `plugins/codexclaw/components/pabcd-state/src/hook.ts`, the bound
D-close `handleOrchestrateCommand` :1137-1286 and the resting state write it makes directly at
:1302-1321, ported to Go as `internal/pabcd/hook/prompt_dclose.go` (`promptDcloseClose`
:349-539, `promptDclosePlanWork` :545-690, `promptDcloseWriteLanded` :697-705,
`promptDcloseGoalplanPublishedWarning` :711-713, `promptDclosePartialRefusal` :727-748,
`promptDclosePublishedArtifacts` :121-124), with the new cases of
`internal/pabcd/hook/prompt_dclose_guard_partial_test.go`. No fixture in `contract/fixtures/cxc`
drives a bound chat D-close whose session file becomes unreadable between the plan commit and the
resting state write, so no recorded case is retagged and `contract/notes/cxc/CRW-930.json` is not
created (the CRW-845/CRW-797 convention's empty-claim file would claim nothing and is outside this
issue's edit scope).

- The oracle writes its resting state directly (:1302-1321) and has no rewritability check on that
  path, so it cannot refuse there and has no refusal text to get wrong. The port added the
  data-loss guard the other session writers use (`promptSubmitRewritable`,
  `internal/pabcd/hook/prompt_submit.go` :305-312, the CRW-609/CRW-786 rule), and its
  `promptDcloseClose` calls that guard immediately before `state.WriteState`
  (`internal/pabcd/hook/prompt_dclose.go` :397-403). The guard re-reads the session file, so it can
  refuse after an earlier step of the same close already published the recovery marker or the
  goalplan, and the port answered the bare `promptDcloseStateRefusal()` then, denying that anything
  was written and dropping the directory-sync warning the earlier bound-D-close fix (#802) added;
  port: fixed (the arm answers `promptDclosePartialRefusal`, the same text the state-write arm
  uses, so it names the published artifacts and their warnings, and returns the bare refusal byte
  for byte when nothing was published and no warning is outstanding;
  `TestPromptDcloseGuardRefusalNamesThePublishedPlan`,
  `TestPromptDcloseGuardRefusalWithoutAWarningIsUnchanged`).
- The refusal named only an artifact that carried a directory-sync warning, so a close whose marker
  and plan both published cleanly and then hit a later refusal still answered "Nothing was written."
  with both files on disk, and a refusal that named one artifact denied the other. The oracle has no
  such answer to preserve - it writes the resting state with no guard and no refusal text - so this
  is a port-owned gap, not a parity difference, and it is the promise CRW-869 left open; port: fixed
  (`promptDclosePlanWork` records which artifacts landed beside their warnings in
  `promptDclosePublishedArtifacts` (:545-690), and `promptDclosePartialRefusal` (:727-748) names
  every landed artifact with one fixed sentence - `promptDcloseMarkerPublishedSentence` or
  `promptDcloseGoalplanPublishedSentence` - while keeping each warning; a warned artifact is named
  by its warning alone, so no artifact is named twice. "Nothing was written." stays only when this
  close published nothing and no warning is outstanding. The three arms are the plan write failing
  after a clean marker (:666-674), the guard before the IDLE state write (:413-420) and the IDLE
  state write failing (:421-428);
  `TestPromptDcloseGuardRefusalNamesTheCleanlyPublishedMarkerAndPlan`,
  `TestPromptDclosePlanFailureAfterACleanMarkerNamesTheMarker`,
  `TestPromptDcloseStateWriteFailureNamesTheCleanMarkerAndPlan`).
- The partial refusal replaced the first "Nothing was written." in the refusal text, and the plan
  failure embeds the writer's own error before that claim: an error whose text contained the phrase
  made the refusal edit that inner copy and leave the false trailing claim, so the answer could still
  end by denying the marker it had just named. The oracle has no such answer (it writes the resting
  state with no refusal text), so this is a port-owned defect of the same concept; port: fixed
  (`promptDclosePartialRefusal` now rewrites the last occurrence - the claim the close owns - and
  leaves any phrase inside the writer's message alone;
  `TestPromptDclosePlanFailureWhoseReasonHoldsTheDenialKeepsTheTrailingClaim`).
- A marker-matched retry whose plan commit already landed rewrites nothing
  (`WorkPhaseCloseFixedAlreadyDone`), so the retry recorded no plan and a later refusal named only
  the inherited marker: "the recovery marker was published. Nothing else was written." although the
  first attempt of this same close had committed the goalplan. The oracle has no such answer, so the
  close's own accounting was incomplete; port: fixed (`promptDcloseRecoveryClose` reports the
  already-committed plan and `promptDclosePlanWork` records it as published for every refusal below;
  `TestPromptDcloseRecoveryAlreadyCommittedPlanIsNamedByALaterRefusal`).
- The recovery arm's own refusals (an open task added under the closed target, a target that turned
  blocked or lost a dependency, a corrupt marker, a gone successor) returned their text unchanged, so
  a retry of a close whose first attempt had published the marker and committed the goalplan still
  ended in "Nothing was written." The absent-target cleanup answer had the same gap on the way to the
  resting state write. The oracle has no such answer; port: fixed (every recovery refusal now names
  the inherited marker and the goalplan when the plan on disk carries the commit's effect, judged by
  `promptDcloseRecoveryPlanCommitted` plus the cleanup answer;
  `TestPromptDcloseRecoveryRefusalNamesTheCommittedMarkerAndPlan`,
  `TestPromptDcloseRecoveryCleanupNamesTheCommittedPlan`).
- Two further gaps of the same accounting, found by the pre-merge evaluation of the head that first
  added the recovery naming: a retry refused before the recovery arm (an unreadable goalplan, a lock
  failure, an integrity or empty-plan check) returned its text unchanged although the inherited marker
  was on the session, and the committed-plan judgement read the plan too loosely - it counted a plan a
  hand edit had merely marked done, and treated the absent-target cleanup answer as proof of a commit
  even when the marker recorded no successor. The oracle has no such answers; port: fixed (the early
  recovery refusals go through `promptDcloseRecoveryNaming`, and
  `promptDcloseRecoveryPlanCommitted` now requires the commit's own settled shape - the target done
  with the cursor cleared when no successor was recorded, or the recorded successor running on the
  cursor or already done;
  `TestPromptDcloseRecoveryEarlyRefusalNamesTheInheritedMarker`,
  `TestPromptDcloseRecoveryRefusalWithoutASuccessorNamesOnlyTheMarker`).
- Three further gaps of the same accounting, found by the pre-merge evaluation of the head that
  added the recovery naming: a marker that names the still-open target as its own successor was read
  as a committed plan, so a corrupt-marker refusal named a goalplan this close never wrote; the
  integrity and empty-plan refusals run before the recovery accounting and named the inherited marker
  alone, dropping a goalplan this same close had committed; and the busy goalplan lock returned its
  own text directly, naming neither the inherited marker nor the committed plan. The oracle has no
  such answers; port: fixed (`promptDcloseRecoveryPlanCommitted` refuses a self-successor marker
  before it judges the successor, `promptDcloseRecoveryCommittedPublication` reads the commit's
  settled shape for the refusals that run before the accounting, and `promptDcloseNotAppliedNaming`
  adds the publication sentences to the busy text while keeping the true "ledger were not changed";
  the plan is read for that refusal's text only, so no behaviour depends on it;
  `TestPromptDcloseRecoveryCorruptMarkerDoesNotClaimThePlan`,
  `TestPromptDcloseRecoveryIntegrityRefusalNamesTheCommittedPlan`,
  `TestPromptDcloseRecoveryBusyLockNamesWhatTheFirstAttemptPublished`, with a control for each).
- Three further gaps of the same accounting, found by the pre-merge evaluation of the generation-2
  head: the committed-plan judgement accepted a recorded successor that was merely running on the
  cursor, so an operator who started it by hand while the target stayed open made a refusal claim a
  goalplan this close never committed; the lock's "unreadable" answer covers a plan that read
  cleanly but would lose an unknown field on revival, and every pre-accounting refusal treated that
  as "no plan evidence" and named the marker alone; and the session lock the bound close itself
  takes was a second refusal layer that named neither artifact. The oracle has no such answers;
  port: fixed (`promptDcloseRecoveryPlanCommitted` requires a still-present target to be done,
  `promptDcloseRecoveryPublishedAt` reads the plan for every pre-accounting refusal so the
  committed goalplan is named even when the lock could not supply it, and the bound handler's own
  lock-error return names what the retry's first attempt published;
  `TestPromptDcloseRecoveryStartedSuccessorDoesNotProveACommit`,
  `TestPromptDcloseRecoveryUnreadablePlanStillNamesTheCommittedPlan`,
  `TestPromptDcloseRecoveryBusySessionLockNamesWhatTheFirstAttemptPublished`, with a control for
  each).
