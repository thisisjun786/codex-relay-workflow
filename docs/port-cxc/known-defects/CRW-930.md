# CRW-930 — bound D-close: a refusal after a publication denied it, and a retry that could not tell who wrote the plan

Source: CXC v0.2.40 (`3c1459ac`) `plugins/codexclaw/components/pabcd-state/src/hook.ts`, the bound
D-close `handleOrchestrateCommand` :1137-1286 and the resting state write it makes directly at
:1302-1321, ported to Go as `internal/pabcd/hook/prompt_dclose.go` (`promptDcloseClose` :383-573,
`promptDclosePlanWork` :579-721, `promptDcloseWriteLanded` :728-736,
`promptDcloseGoalplanPublishedWarning` :742-744, `promptDclosePartialRefusal` :758-787,
`promptDcloseRecoveryPublishedAt` :819-827, `promptDcloseRecoveryPublishedForPrompt` :834-840,
`promptDcloseRecoveryClose` :853-936, `promptDcloseRefusalNaming` :1179-1190,
`promptDclosePendingText` :1068-1090, `promptDcloseMarkerPublishedSentence` :193-195,
`promptDcloseGoalplanPublishedSentence` :200-202, `promptDcloseGoalplanUnknownSentence` :210-212,
`promptDclosePublishedArtifacts` :121-135), with the new cases of
`internal/pabcd/hook/prompt_dclose_guard_partial_test.go`. No fixture in `contract/fixtures/cxc`
drives a bound chat D-close whose session file becomes unreadable between the plan commit and the
resting state write, so no recorded case is retagged and `contract/notes/cxc/CRW-930.json` is not
created (the CRW-845/CRW-797 convention's empty-claim file would claim nothing and is outside this
issue's edit scope).

- The oracle writes its resting state directly (:1302-1321) and has no rewritability check on that
  path, so it cannot refuse there and has no refusal text to get wrong. The port added the
  data-loss guard the other session writers use (`promptSubmitRewritable`,
  `internal/pabcd/hook/prompt_submit.go`), and its `promptDcloseClose` calls that guard
  immediately before `state.WriteState`. The guard re-reads the session file, so it can refuse
  after an earlier step of the same close already published the recovery marker or the goalplan,
  and the port answered the bare `promptDcloseStateRefusal()` then, denying that anything was
  written and dropping the directory-sync warning the earlier bound-D-close fix (#802) added;
  port: fixed (the arm answers `promptDclosePartialRefusal`, the same text the state-write arm
  uses, so it names the published artifacts and their warnings, and returns the bare refusal byte
  for byte when nothing was published and no warning is outstanding;
  `TestPromptDcloseGuardRefusalNamesThePublishedPlan`,
  `TestPromptDcloseGuardRefusalWithoutAWarningIsUnchanged`).
- The refusal named only an artifact that carried a directory-sync warning, so a close whose marker
  and plan both published cleanly and then hit a later refusal still answered "Nothing was written."
  with both files on disk, and a refusal that named one artifact denied the other. The oracle has no
  such answer to preserve - it writes the resting state with no guard and no refusal text - so this
  is a port-owned gap, not a parity difference, and it is the promise CRW-869 left open; port: fixed
  (`promptDclosePlanWork` records which artifacts landed beside their warnings in
  `promptDclosePublishedArtifacts`, and `promptDclosePartialRefusal` names every landed artifact
  with one fixed sentence - `promptDcloseMarkerPublishedSentence` or
  `promptDcloseGoalplanPublishedSentence` - while keeping each warning; a warned artifact is named
  by its warning alone, so no artifact is named twice. "Nothing was written." stays only when this
  close published nothing and no warning is outstanding. The three arms are the plan write failing
  after a clean marker, the guard before the IDLE state write and the IDLE state write failing;
  `TestPromptDcloseGuardRefusalNamesTheCleanlyPublishedMarkerAndPlan`,
  `TestPromptDclosePlanFailureAfterACleanMarkerNamesTheMarker`,
  `TestPromptDcloseStateWriteFailureNamesTheCleanMarkerAndPlan`).
- The partial refusal replaced the first "Nothing was written." in the refusal text, and the plan
  failure embeds the writer's own error before that claim: an error whose text contained the phrase
  made the refusal edit that inner copy and leave the false trailing claim, so the answer could still
  end by denying the marker it had just named. The oracle has no such answer (it writes the resting
  state with no refusal text), so this is a port-owned defect of the same concept; port: fixed
  (`promptDclosePartialRefusal` now rewrites the last occurrence - the claim the close owns - and
  leaves any phrase inside the writer's message alone;
  `TestPromptDclosePlanFailureWhoseReasonHoldsTheDenialKeepsTheTrailingClaim`).
- The recovery arm read the goalplan's publication off the plan's shape, and that inference was wrong
  in both directions: a marker that recorded no successor was read as an authoritative "no
  successor", so a hand edit that left the committed shape made a refusal claim a goalplan this
  close never committed; a marker naming the still-open target as its own successor was read as a
  commit; a recorded successor that was merely running on the cursor was read as a commit although
  an operator could have started it by hand after a marker-only failure; and a plan the retry could
  not read at all lost a real publication, so the refusal named the marker alone and appended a
  false "Nothing else was written." The oracle has no such answers; port: fixed (the settled-shape
  inference was removed rather than tuned, per the parent's generation-2 decision on d2/d3:
  `promptDcloseRecoveryPublishedAt` records the inherited marker as published and the goalplan as
  unknown, and every refusal of a retry that did not write the plan itself carries
  `promptDcloseGoalplanUnknownSentence` - "the goalplan may already hold this close's commit from
  the first attempt; read it before retrying." - instead of a definite claim or denial. A fresh
  close still names exactly what it published itself, definitely. No trailing "Nothing else was
  written." is appended when the goalplan's publication is unknown, because that sentence is itself
  a denial of a goalplan write;
  `TestPromptDcloseRecoveryRefusalLeavesThePlanUnknown`,
  `TestPromptDcloseRecoveryCleanupDoesNotClaimThePlan`,
  `TestPromptDcloseRecoveryCommittedPlanIsNotClaimedByALaterRefusal`,
  `TestPromptDcloseRecoveryIntegrityRefusalDoesNotClaimThePlan`,
  `TestPromptDcloseRecoveryBusyLockNamesTheMarkerAndLeavesThePlanUnknown`,
  `TestPromptDcloseRecoveryUnreadablePlanDoesNotClaimThePlan`,
  `TestPromptDcloseRecoveryUnreadablePlanLeavesThePlanUnknown`,
  `TestPromptDcloseRecoveryChangedSuccessorLeavesThePlanUnknown`,
  `TestPromptDcloseRecoveryAbsentTargetHandStartDoesNotClaimThePlan`,
  `TestPromptDcloseRecoveryCorruptMarkerDoesNotClaimThePlan`,
  `TestPromptDcloseRecoveryStartedSuccessorDoesNotClaimThePlan`,
  `TestPromptDcloseLegacyMarkerDoesNotClaimACommittedPlan`,
  `TestPromptDcloseRecoveryRefusalWithoutASuccessorDoesNotClaimThePlan`,
  `TestPromptDcloseRecoveryUnreadableRereadNamesTheMarkerAndLeavesThePlanUnknown`,
  `TestPromptDcloseRecoverySourceRootRefusalNamesTheMarkerAndLeavesThePlanUnknown`, with a control
  for each fresh-close path).
- The recovery arm's own refusals (an open task added under the closed target, a target that turned
  blocked or lost a dependency, a corrupt marker, a gone successor) returned their text unchanged, so
  a retry of a close whose first attempt had published the marker still ended in "Nothing was
  written."; the pre-accounting refusals (an unreadable goalplan, a lock failure, an integrity or
  empty-plan check) did the same; the session lock the bound close itself takes and the strict
  session reread inside the handler were two further layers that named neither artifact; and the
  SOURCE-ROOT entry gate, which runs before the bound handler, answered its own text alone. The
  oracle has no such answers; port: fixed (every one of those refusals now goes through
  `promptDcloseRecoveryPublishedAt` or `promptDcloseRecoveryPublishedForPrompt`, so it names the
  inherited marker and leaves the goalplan unknown;
  `TestPromptDcloseRecoveryEarlyRefusalNamesTheInheritedMarker`,
  `TestPromptDcloseRecoveryRefusalLeavesThePlanUnknown`,
  `TestPromptDcloseRecoveryBusySessionLockNamesTheMarkerAndLeavesThePlanUnknown`,
  `TestPromptDcloseRecoveryUnreadableRereadNamesTheMarkerAndLeavesThePlanUnknown`,
  `TestPromptDcloseRecoverySourceRootRefusalNamesTheMarkerAndLeavesThePlanUnknown`, with a control
  for each fresh-close path).
- The Stop-budget stamp takes the session lock before the bound close's own acquisition, so a lock
  that is already busy fails there and the close never runs: that return named no artifact at all,
  although a matching retry's first attempt had already published its marker. The oracle has no such
  answer; port: fixed (`internal/pabcd/hook/prompt_submit.go` now answers
  `promptDcloseRefusalNaming(promptDcloseNotApplied(reason), promptDcloseRecoveryPublishedForPrompt(...))`
  for a bound D, so a retry names the inherited marker and leaves the goalplan unknown while a fresh
  close keeps the bare busy text; this file is outside the issue's declared edit regions and is
  listed under "Files edited outside the declared regions" in the handoff;
  `TestPromptDcloseBusyStopBudgetStampNamesTheInheritedMarker`,
  `TestPromptDcloseBusyStopBudgetStampFreshCloseKeepsTheBareText`).
- The refusal's task listing was unbounded, and the harness cuts an answer over MaxContext (32000
  UTF-16 units) at 31936 and appends "[truncated]". Because the port appends this close's
  publication accounting after the listing, a retry with a very large task listing could lose
  exactly the part the operator has to act on: the hook answer reached the model without the marker
  or the goalplan sentence. Found by the pre-merge evaluation of the generation-2 head; port: fixed
  (`promptDclosePendingText` bounds the listing at a stated budget in UTF-16 units and names the
  tasks it left out by their number, so the accounting survives the cut;
  `TestPromptDcloseHugePendingListKeepsThePublicationAccounting`).
- The state-moved refusal (the session moved between the leading read and the close's own locked
  read, so the close writes nothing) was the last refusal arm of the bound handler that answered the
  bare "Nothing was written." although a matching retry's first attempt had already published its
  marker. The oracle has no such answer; port: fixed (both arms - the moved-state check and the
  re-applied transition - now go through \`promptDclosePartialRefusal\` with
  \`promptDcloseRecoveryPublishedAt\`, so a retry names the inherited marker and leaves the goalplan
  unknown while a fresh close keeps the bare text;
  \`TestPromptDcloseRecoveryMovedSessionNamesTheInheritedMarker\`).
- The busy refusals appended the publication sentences to the busy text without a separator, so an
  answer naming two artifacts ran two sentences together ("...were not changed.the recovery marker
  was published."). Found by the independent review of an earlier head; port: fixed
  (`promptDcloseRefusalNaming` inserts the sentences after the busy text's own final period, with
  a space between them; `TestPromptDcloseBusyRefusalSeparatesThePublicationSentences`).
