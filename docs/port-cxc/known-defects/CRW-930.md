# CRW-930 — bound D-close: the IDLE-write guard's refusal hid the published marker and plan

Source: CXC v0.2.40 (`3c1459ac`) `plugins/codexclaw/components/pabcd-state/src/hook.ts`, the bound
D-close `handleOrchestrateCommand` :1137-1286 and the resting state write it makes directly at
:1302-1321, ported to Go as `internal/pabcd/hook/prompt_dclose.go` (`promptDcloseClose`
:262-330, `promptDclosePlanWork` :441-548, `promptDclosePartialRefusal` :584-592), with the new
cases of `internal/pabcd/hook/prompt_dclose_guard_partial_test.go`. No fixture in
`contract/fixtures/cxc` drives a bound chat D-close whose session file becomes unreadable between
the plan commit and the resting state write, so no recorded case is retagged and
`contract/notes/cxc/CRW-930.json` is not created (the CRW-845/CRW-797 convention's empty-claim
file would claim nothing and is outside this issue's edit scope).

- The oracle writes its resting state directly (:1302-1321) and has no rewritability check on that
  path, so it cannot refuse there and has no refusal text to get wrong. The port added the
  data-loss guard the other session writers use (`promptSubmitRewritable`,
  `internal/pabcd/hook/prompt_submit.go` :305-312, the CRW-609/CRW-786 rule), and its
  `promptDcloseClose` calls that guard immediately before `state.WriteState`
  (`internal/pabcd/hook/prompt_dclose.go` :312-317). The guard re-reads the session file, so it can
  refuse after an earlier step of the same close already published the recovery marker or the
  goalplan, and the port answered the bare `promptDcloseStateRefusal()` then, denying that anything
  was written and dropping the directory-sync warning CRW-869 added; port: fixed (the arm now
  answers `promptDclosePartialRefusal(refusal, warnings)`, the same text the state-write arm uses,
  so it names the published artifacts and their warnings, and returns the bare refusal byte for byte
  when no earlier warning is outstanding;
  `TestPromptDcloseGuardRefusalNamesThePublishedPlan`,
  `TestPromptDcloseGuardRefusalWithoutAWarningIsUnchanged`).
- Recorded limitation of the same arm, not fixed here: `warnings` names only an artifact that
  published and then failed a step after its rename, so a close whose marker and plan both landed
  cleanly and then hit a guard read failure still answers "Nothing was written." although both are on
  disk. The recovery marker makes the same D request finish the close, which bounds the harm. The
  state-write arm below the guard carries the same limitation, so widening it is a change to the
  CRW-869 sentence contract across both arms, outside this issue's concept; port: kept.
