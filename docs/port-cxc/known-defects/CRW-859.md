# CRW-859 — goalplan parity for a malformed plan: duplicate work-phase ids and the empty cursor

Source: package audit p65-m75-audit-r1 (grader gpt-6-astra xhigh, head 80d26ad1; parent triage /state/crw/p-crw-65-m1-run1/audit-r1-triage.md, items G2 and G3). The oracle is CXC v0.2.40 (commit 3c1459ac) goalplan.ts: closeFixedWorkPhase (2020-2023, the map over the target id) and advanceWorkPhase (2217, the truthiness test of the effective id). The Go files are internal/pabcd/goalplan/workphase.go (workPhaseCloseFixed, workPhaseAdvance) and workphase_cursor.go (EffectiveActiveWorkPhaseID, workphaseCursorText). The red tests are TestCRW859_* in internal/pabcd/goalplan/workphase_audit_test.go; the red output is /state/crw/crw-lane-m75-audit-fixes/evidence/red-CRW-859-goalplan.log.

- The oracle's close maps every work phase whose id equals the target to done (goalplan.ts:2020-2023). The port marked only the first phase with that id done, so a duplicate pending phase of the same id was re-activated by the close (G2, a malformed plan with duplicate work-phase ids); port: fixed (workPhaseCloseFixed marks every phase with the target id done, and the advance door takes the same path. Pinned by TestCRW859_CloseFixedClosesEveryPhaseWithTheTargetID and TestCRW859_AdvanceClosesEveryPhaseWithTheCursorID).
- The oracle's advance answers no_active when its effective work-phase id is falsy, which includes the empty string (goalplan.ts:2217). The port's effective id can be a non-nil pointer to the empty string (a phase with an empty id), and the advance checked only nil, so it closed that phase (G3); port: fixed (workPhaseAdvance answers no_active for an empty effective id, as the oracle does. Pinned by TestCRW859_AdvanceTreatsAnEmptyEffectiveCursorAsNoActive; the explicit empty cursor is already unset and is pinned by TestCRW859_EmptyExplicitCursorFallsThroughToTheNextPhase).
