# CRW-1214 — the node-scoped readers read both sides of a node: release, execution, acceptance and integration of an agent node

Source: the 0.5.0-alpha design issue R06 (CRW-1214). This is the port's own addition: CXC v0.2.40 (commit 3c1459ac) has no agent execution kind, so there is no oracle line for it. The Go files are internal/relay/dagsched/agent_union.go (activeAcceptanceOf, tolerantAcceptanceOf, CurrentExecution, CurrentAcceptance, ExecutedNodes, AgentAcceptanceIntegrated, the helpers the readers share), nodestate.go (stateOf, agentAccepted), edges.go (agentStanding, consumedStanding, recordedEvidence, integratedAt, the artifact and integrated edges), progress.go, progress_replay.go (through Progress), activity.go, landingresult.go, measure.go, optimism.go, bundles.go, liveheads.go, livesweep.go, mergeorder_derive.go, release_recovery.go, lifecycle.go, stagnation.go, invalidation.go, baserefresh.go, mergejudge.go, accept_refresh.go, inputs.go, manifest.go, integration_stale.go and targets.go, internal/relay/acceptance/stand.go (OwnOfAgent), internal/relay/dag/manifest.go (the agent artifact input), internal/manage/capacity_branches.go, checkpoint.go, dagreview.go, dagreview_store.go and relayread.go, and docs/relay/agent-execution-readers.md (every node-scoped row is migrated).

- Supersedes CRW-1213.md, section "What stays for R06" (the item beginning "What stays for R06"): now port: fixed (`staleOf` and `consumedStanding` read the acceptance of either side and judge an agent acceptance by its manifest, its criteria and its execution; `integratedEdge` reads `acceptanceOf` and an edge out of an agent node is satisfied by the three facts of its landing, the ref move, the agent marked row and the observation of the head; the conflict sweep reads an agent node's worktree head and its accepted head). One part stays pending: the sweep that a receipt or a landing owes automatically is a writer's (accept.go, integration.go), and is not started for an agent node; `dag-sweep` run by hand measures it. port: pending (the writer side, with the lifecycle of R07).
- An agent acceptance is read by the readers that need only the fields the two kinds share in the shape of `Acceptance` (`AgentAcceptance.record`, with the unexported `agent` field naming the row), so one code path serves both; the readers that differ ask `agent` (`standOf`, `integratedAt`, `standing`, `recordedEvidence`, `acceptedEntries`, `currentAcceptanceHead`). The fields only a relationship has stay empty. port: kept.
- An agent acceptance stands on itself (`acceptance.OwnOfAgent`): no base refresh is recorded for it, `dag-base-refresh` refuses it, and the merge judgement refuses it (`mergeAcceptanceOf`), since an agent node lands through dag-integrate on a commit route and never as a pull request or a merge turn (the classification keeps the relationship-scoped readers unchanged). port: kept. Pinned by TestAgentAcceptanceVisibleToReady, TestAgentIntegratedEdgeSatisfied.
- `standing` for an agent acceptance (`agentStanding`) checks what it can: the row is what its id says (`AgentAcceptanceID` of the plan, node, execution, head and criteria), it is whole (manifest, execution, criteria, reviewer call, author and time; an implementation node also its head, repository, verification and pre-merge digests), it is tied to an execution row of the node, and its criteria are the plan's. It has no relationship, so there is no registered criteria set to agree with, and no revalidation (a change of the criteria is a new acceptance). The execution it was made on must still be the node's current execution or one it continues (`agentExecutionStands`), else the artifact edge is `blocked:stale_head`. port: kept.
- The input of an artifact edge out of an agent node names the acceptance and the execution (`execution_id`, `surface` = `agent`; `dag.InputSurfaceAgent`) instead of the relationship, generation, event and revision, which an agent acceptance does not have; `dag.CheckManifest` accepts that form and requires `acceptance_id` and `execution_id` of it. The manifest of an input that rests on a relationship is checked as it was. An artifact edge that is not a code pin has no list of artifacts to take from an agent acceptance (it names a commit), so the node that follows reads it as an input that is missing (B-17, `blocked:input_missing`); the plan validator already requires the pin on an edge out of an implementation node, so only an edge out of a non_pr agent node reaches it. port: kept (the manifest schema is a port addition; `internal/relay/dag/manifest.go` is not among the edit regions of the Linear body, and is edited for this form only).
- A node that holds a current execution or acceptance on both sides (cross_kind_execution, cross_kind_acceptance) is read as neither by the readers whose failure would take the reading of a whole plan down: its state is `ambiguous` with `blocked:ambiguous_head`, its edges are blocked with the same reason, and its facts show no acceptance; the readers that act on a node (`acceptanceOf`, the integration batch) keep their refusal. port: kept. Pinned by TestAcceptanceOfAtMostOneCurrentAcrossKinds.
- `release_recovery.go` skips an agent row explicitly: `OpenReleaseNodes` does not list a node an agent execution holds, `dag-release-close` for such a node is refused (`disposition_conflict`, detail `live_agent_execution`) and writes nothing, and the manifest an agent execution or acceptance rests on is counted by the reliance check that keeps a frozen copy. port: kept. Pinned by TestReleaseRecoverySkipsAgentRows.
- `dag-progress` lists the executions of an agent node in the `executions` link (`relationship_id` null, `execution_generation` the attempt, `kind`, `execution_id`, `surface`), and the entry of a relationship keeps its three keys, so the document of a plan without an agent node, and every golden of it, is as it was; the nodes whose agent acceptance left the plan count in `outside_denominator.with_acceptance`. port: kept. Pinned by TestAgentReleaseVisibleToProgress.
- `crw manage` reads the union through exported readers of dagsched (`ExecutedNodes`, `CurrentAcceptance`, `AgentAcceptanceIntegrated`, `CrossKindHeld`): the branch candidates leave a node an agent runs out and drop a landed agent node from the graph, the checkpoint counts a landed agent acceptance as an integration at the instant of its observations, and the review reads the agent node's executions, acceptances and observations. The review's link from a node to its relationship (`dag_node_executions`) stays a relationship's: an agent node has no child. port: kept. Pinned by TestAgentReleaseVisibleToManage and TestAgentAcceptanceVisibleToManage.
- Not done here, and not a defect of the readers: the route of a stale agent node (`routeOf` still reads `currentRelationshipOf` and would call a stale agent node's route a redefinition of an ended relationship) and the correction of an agent node belong to R07 (`agent_correction`, invalidation's route); `capacity.go` needs no change (the slot of an agent release is an `execution_slots` row the capacity and `slotOf` already count). port: pending (R07).
