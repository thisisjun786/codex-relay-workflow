# CRW-797 — whole chat D-close of a session bound to a goalplan (D3b+D3c)

Source: CXC v0.2.40 (`3c1459ac`) `plugins/codexclaw/components/pabcd-state/src/hook.ts`
`handleOrchestrateCommand` :875-901, :939-989, :990-1136, :1137-1286, :1256-1258, :1302-1354 and
:1394-1396, with `readJsonlObjects` / `hasGoalplanRow` / `hasPabcdCloseRow` /
`HookDcloseCommitHooks` :628-654, ported to Go as `internal/pabcd/hook/prompt_dclose.go` with the
chat D-close cases of `hook.test.ts` as `internal/pabcd/hook/prompt_dclose_test.go` and
`internal/pabcd/hook/prompt_dclose_recovery_test.go`. No fixture in `contract/fixtures/cxc` drives
a chat bound D-close, so `contract/notes/cxc/CRW-797.json` claims none and this port makes no
recorded case pass on its own.

- The command reads the session state, changes fields and writes the whole state back with no lock,
  three times (the recovery marker :1229-1239, the resting state :1309-1322, the marker cleanup
  :1344), so an update a participating writer — another hook of the same session, the memory gate,
  the idle-edit counter — lands between the two is overwritten by the stale copy and lost, and each
  write-back rebuilds the state from the reader's normalised value, so a stored record the reader
  cannot keep is lost with it; port: fixed (a data-loss defect, the class the parity rule revision of
  2026-10-03 fixes during the port: the whole close runs under one `state.WithSessionLock`, the
  state is re-read strictly inside it, the close is applied to that read, and every write passes the
  rewrite guard the other session writers use; `TestPromptDcloseRefusesARewriteTheReaderWouldLose`,
  `TestPromptDcloseKeepsTheExistingStateFields`).
- The oracle holds no session lock, so two concurrent closes of one session interleave their state
  reads and writes, and the second overwrites the first; port: fixed (the same lock: a close whose
  state moved between the leading section's read and the lock refuses with nothing written;
  `TestPromptDcloseBusySessionLockWritesNothing`).
- `hasGoalplanRow` and `hasPabcdCloseRow` parse every line of their ledger with `JSON.parse`
  (`readJsonlObjects`, :623-626), so one damaged line throws out of the handler, which `cli.ts`
  answers with silence, and the same D request can never finish; port: fixed (a line that is not a
  JSON object matches nothing, so the worst outcome is one duplicate ledger row rather than a request
  that can never complete).
- The resting state is written at :1309-1322 before the PABCD close row and the marker cleanup at
  :1329-1345, so a crash between them leaves an IDLE session whose marker still describes a close
  that already happened; port: kept (the oracle has a repair path — the same D request matches the
  marker and finishes the cleanup — and the port keeps it, with the finalization-pending text at
  :1347-1354 when the second lock cannot be taken;
  `TestPromptDcloseStoppedCloseIsFinishedByTheSameRequest`).
- The all-done close writes its PABCD row inside the first goalplan lock and skips the second
  critical section entirely (:1145-1149), because an all-done plan leaves no marker for a failed
  second lock to resume; port: kept (the row is written in the same place, with `closedWorkPhaseId`
  null and the session's own check epoch; `TestPromptDcloseAllDoneRecordsTheNullCloseKey`).
- The recovery marker records the successor the close chose from the plan it just computed (:1237,
  `closeResult.plan.activeWorkPhaseId`), and a resume names that recorded successor in its
  `started` row (:1256-1258) rather than the cursor it recomputed; port: kept
  (`TestPromptDcloseRecoveryActivatesTheRecordedSuccessor`).
- The close's `noop` field reaches the persisted state through the oracle's spread of
  `result.state`, so the oracle's state file can carry a stray `noop` key on a bound D-close write;
  port: kept (the port's `state.State` has no such field, so the key is not written; nothing in the
  oracle reads it).
- The `D-close was not applied` text names only the goalplan lock, because the oracle holds no
  session lock at all; port: fixed (the port's own session lock answers the same text with its busy
  reason, and nothing is written; `TestPromptDcloseBusySessionLockWritesNothing`).
- A marker cleanup the reader would not keep whole — a stored record the write-back would drop —
  cannot be cleared after the cycle is already closed; port: fixed (a data-loss defect: the cleanup
  passes the same rewrite guard and the close answers the finalization-pending text instead, so the
  marker stays and the operator can repair the file).
