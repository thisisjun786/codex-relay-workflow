# CRW-1355 — PR-unit landing: a milestone reaches dev as one pull request the dev queue merges after verification and review

Source: CRW's own design, not the CXC oracle (CXC v0.2.40, commit 3c1459ac): the oracle has no DAG plan, no milestone integration branch, no dev queue and no pull request landing. The design is section 18.5 of the CRW-1316 design and the 10-14 04:3x judgment (item 8 of the coordinator's open questions): flow's `crw.integrate` stays as it is and its target becomes the milestone integration branch, the project session opens the dev-ward pull request, and the dev queue merges it after verification. The Go side is the pull request side of the tracking adapter (`internal/tracking/pullrequest.go`, with `ParseCarries` beside `ParseBlockedBy`), the command `crw flow pr` (`internal/flow/pullrequest`, wired in `cmd/crw/main.go`), the pull request path of the dev queue (`internal/integrator/pr.go`, with the entry kind in `queue.go`, the pass in `pass.go` and the review step in `integrate.go`) and `crw manage integrate --enqueue-pr` (`internal/manage/integrate.go`). The tests run against the adapter's fake GitHub (`internal/tracking/trackingfake`) and local bare remotes, never a real GitHub.

- The flow path does not change: a plan whose target `base_ref` names a milestone integration branch lands its nodes there with the merge commits, the verification and the compare-and-swap it uses on `dev`, and a plan whose target is `dev` keeps the direct landing; port: kept (no code change in the flow path; pinned by `TestMilestoneBranchTargetLandsTheRunsNodesThere`, which compares the two landings commit by commit and tree by tree, and by the existing landing tests of `internal/flow/cli`).
- The tracking adapter opens a pull request from a branch of its repository toward another, naming the issues it carries on one `Carries:` line (at least one issue; a fork head `owner:branch`, a full ref, the base as head and a title over several lines are `ErrInvalidPullRequest` before anything is sent), reads a pull request (state, merged, draft, head commit, head and base branch, head repository, carried issues) and judges the check runs and commit statuses of its head together (`none`, `pending`, `success`, `failure`); `Issue` still refuses a pull request with `ErrNotIssue`; port: fixed (pinned by `TestOpenPullRequestPostsHeadBaseTitleAndTheCarriedIssues`, `TestOpenPullRequestRefusesWhatItCannotSend`, `TestPullRequestReadsStateHeadBaseAndCarriedIssues`, `TestChecksJudgeTheCheckRunsAndStatusesOfTheHead`, `TestPullRequestOperationsNameTheRepositoryAndComeBackTyped` and `TestReadingAnIssueStillRefusesAPullRequest`).
- `crw flow pr open --push DIR` pushes the head branch of the checkout to the remote, never forced, before it opens the pull request, and a push the remote refuses opens nothing; without `--push` the branch has to be on the remote already, and GitHub refuses the pull request otherwise; port: kept (pinned by `TestOpenPushesTheMilestoneBranchAndOpensOnePullRequestCarryingItsIssues` and `TestOpenRefusesWhatCannotBeOpened`).
- The pull request is not merged on GitHub. The dev queue lands it alone, one per pass and before the issue heads: it reads the pull request again (merged: `done/`; closed or a head that moved since the enqueue: `conflict/`; another base, or a head branch in another repository: `blocked/`), merges its head with `merge --no-ff`, verifies the merged tree, runs the configured `review_command`, and moves `dev` only after both, with the second fetch and the push that is never forced; port: fixed (pinned by `TestPassLandsAPullRequestAfterVerificationAndReview`, `TestPassChecksThePullRequestBeforeItMerges`, `TestPassReviewsNothingWhenTheVerificationFails`, `TestPassKeepsAPullRequestPendingWhenDevMovesDuringTheReview` and `TestPassLandsAPullRequestAloneBeforeTheIssueHeads`).
- The compare-and-swap of `dev` is the queue's existing one: the remote is fetched again after the verification and the review, a branch that is no longer at the verified base ends the run `dev-moved`, and the push names no plus and no `--force`, so a remote that moved in the window after that fetch refuses it unless the move is an ancestor of the verified commit, in which case nothing is lost; port: kept (a `--force-with-lease` push was not chosen, so the queue never uses a force form).
- `needs_changes` in the review's verdict file refuses the merge (status 6, `review-needs-changes`), moves the entry to `blocked/` with the verdict file's path and pushes nothing; no `review_command` is a warning and a record (`review not configured`) and the pull request lands on the verification-record alone, and a configured review that cannot start or leaves no readable verdict (a timeout, a quota) is recorded and warned the same way, since the verification-record is the gate (CRW-1306) and a landing on `dev` can be reverted; port: fixed (the decided default of the lane; pinned by `TestPassRefusesAPullRequestTheReviewSaysNeedsChanges`, `TestPassWithoutAReviewCommandWarnsRecordsAndLands` and `TestPassWithAReviewThatGivesNoVerdictWarnsAndLands`). A coordinator that wants a missing verdict to stop the merge configures a review command that writes `needs_changes` when it has no verdict.
- The review command runs only for a pull request; an issue head is reviewed before it is queued (the pre-merge gate) and its path through the queue is the one it always had; port: kept.
- The record of a landing is against the pull request: `runs_dir/<tag>.pr.json` (`crw-pr-landing/1`: the pull request, number, head, carried issues, `dev_before`, `dev_after`, the merged commit, the result, the verification-record with its sha256 and status, the review with its verdict and verdict file, the warnings) and the same record as a comment on the pull request headed `[dev queue · <tag>]`. A comment GitHub refuses after `dev` moved does not undo the landing: the file says why the comment is missing and the runner log warns; port: kept.
- A pull request GitHub does not answer (a token, the network, a rate limit) is no verdict: it stays in `pending/`, the pass lists it under `held` and goes on with the issue heads, so an unreachable GitHub does not stop direct landing; a queue without `pull_request_repo` takes no `pr-<N>` file and reports it as ignored, as before; port: fixed (pinned by `TestPassWithAPullRequestThatCannotBeReadKeepsItPending`, `TestPassHoldsAnUnreadablePullRequestAndLandsTheIssueHeads` and `TestAQueueWithoutAPullRequestRepoTakesNoPullRequest`).
- The enqueue is the project session's step, `crw manage integrate --enqueue-pr OWNER/NAME#N`, which reads the pull request and writes its head atomically; a pull request the queue cannot land (another repository, closed, another base, a fork's head, no head commit) is refused and writes nothing. The queue does not look for pull requests on GitHub by itself, so a pull request nobody enqueued is never merged; port: kept (pinned by `TestEnqueuePRRefusesAPullRequestTheQueueCannotLand` and `TestIntegrateEnqueuesAPullRequestOfTheConfiguredRepository`).
- End to end, two issues of one milestone land on the milestone branch through a run, one pull request carries both, one pass of the queue verifies, reviews with a fake review command and fast-forwards `dev` on a local bare remote, and the record and the comment name the pull request, the verdict and the verification-record, with no human step; port: fixed (pinned by `TestPRUnitLandingEndToEnd`).
- CRW-1226 (the pull request landing of one agent node, with Devin's review coming back) was cancelled on 10-14 and is no route: an agent node is accepted on its commit and lands on the plan's local target branch, `dag-accept` still refuses a pull request for an agent node, and a pull request carries agent nodes only as a milestone's pull request under PR-unit landing. Devin or any hosted review on that pull request is not read by the queue; the review the queue reads is the configured command's verdict file; port: kept.
- `crw flow pr show --checks` reads the checks of the head, but the queue does not wait for them or read them: the gate is the verification-record of the merged tree, and hosted checks are the place of record only (CRW-1306); port: kept.
- The field trial on `thisisjun786/crw-work` (CRW-1346) is not part of this change; its steps are prepared outside the repository; port: pending.
