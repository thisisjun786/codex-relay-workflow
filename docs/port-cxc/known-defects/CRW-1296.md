# CRW-1296 — a relay child whose sandbox cannot reach the daemon

Source: CRW's own design, not the CXC oracle. A relay child reports only through the relay daemon's
`control.sock` (CRW-1286.md). The Go side is `internal/bridge/create.go` (`refuseReadOnlyChild`, called by
`create_thread`, the relay's managed start through it, and `create_worktree_thread` in
`internal/bridge/worktree.go`) and `internal/relay/hook/control_child.go` (`ForwardChild`).

Reaching the socket is a network permission, not a filesystem one. Measured on codex-cli 0.154.0 with a temporary
`CODEX_HOME`: `codex sandbox` ran a probe that connects to an AF_UNIX listener outside the workspace and writes
outside it, then `crw relay emit` built from the lane head (the listener is not a daemon, so a child that connects
ends with an unknown report outcome):

| Child sandbox | `connect` | Write outside the workspace | `crw relay emit` |
| --- | --- | --- | --- |
| `:read-only` | `EPERM` | `EROFS` | exit 3 naming the sandbox |
| read-only filesystem, network restricted (the r2 F0-2 profile) | `EPERM` | `EROFS` | exit 3 naming the sandbox |
| read-only filesystem, network enabled | connects | `EROFS` | reaches the listener |
| `:workspace` | `EPERM` | `EROFS` | exit 3 naming the sandbox |
| `workspace-write`, `network_access` off (the default) | `EPERM` | `EROFS` | exit 3 naming the sandbox |
| `workspace-write`, `network_access=true` | connects | `EROFS` | reaches the listener |
| `:danger-full-access` | connects | written | reaches the listener |

- `create_thread` (and the managed start through it) and `create_worktree_thread` refuse a `child` role whose
  sandbox cannot reach the daemon, before starting a thread or creating a checkout: a `read-only` sandbox, an
  explicit `readOnly` policy, and a `workspace-write` sandbox whose `expected_sandbox_policy` does not grant
  `networkAccess`. An explicit `readOnly` policy is refused even with `networkAccess`, which connects: a relay
  child writes its work. The refusal names the two sandboxes that reach it (`danger-full-access`, or `workspace-write`
  with `networkAccess`) and asks to recreate the child; the sandbox is never silently changed, and other roles
  keep their sandbox behavior (`TestCreateThreadRefusesAnUnworkableChildSandbox`,
  `TestCreateThreadRefusesARelayChildThatCannotReachTheDaemon`, `TestCreateWorktreeThreadRefusesAReadOnlyChild`;
  the schema-default `read-only` through the MCP tool: `TestCreateThreadWithTheDefaultSandboxRefusesARelayChild`;
  the relay's managed start, before the app-server starts a thread: `Test28_ManagedStartRefusesARelayChildThatCannotReachTheDaemon`);
  port: fixed in source.
- A child whose sandbox refuses the connect ends each child command (`emit`, `intent-claim`,
  `intent-disposition`) with exit 3 that names its sandbox and the sandboxes that report; it records nothing and
  writes nothing (`TestAChildWithoutNetworkAccessIsToldItsSandboxCannotReport`); port: fixed in source.
- A child created outside that refusal (a thread without the `child` role, or one registered through
  `relay register --child-settings`) in a sandbox without network access still cannot report: the bridge MCP
  route, which runs outside the child's sandbox, is not implemented (CRW-1297), and `register --child-settings`
  does not refuse such a sandbox while `doctor`'s `offlineCommands` still lists the three child commands
  (CRW-1298); port: kept.
