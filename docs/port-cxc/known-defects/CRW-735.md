## Found while fixing the guard text (CRW-735)

- The managed dispatch refusal's Node spelling is applied only to a DIRECT `*os.PathError`. `errors.As` would find one inside a wrapper, but the port wraps some failures with text of its own — a dispatch-lock-clear's "(a dispatch-lock-clear of this session is running)" (`dispatch_ledger.go` `lockWith`) and a lock abandon's "lock ... left behind" (`dispatch_lock_clear.go` `lockAbandon`) — and rewriting the whole message from the inner PathError would drop that text. Those wrappers have no oracle counterpart (the oracle's `lstatSync` throws an unwrapped error), so the port keeps their Go wording; the oracle-reachable failure (`dispatchRead`'s `os.Lstat`) is converted (source `spawn-attach-hook.ts:892-907`; `TestSpawnParityNodeError`); port: kept (a port-side choice, not an upstream defect).

- The six corpus fixtures that carry the LEAF guard text (full_history_fork_skips_model_keeps_prompt,
  global_model_effort_injection_and_caller_fields, guard_dedupe_needs_exact_prefix,
  prompt_override_between_guard_and_task, root_recursion_request_mints_coordinator_grant,
  v2_surface_guard_inline_affordance) also hold the skills-catalog limitation CRW-634 recorded as a
  separate defect (the bullet beginning "The skills catalog and the mention inlining"): their expected
  stdout ends with the recording machine's installed plugin skills listing, which a replay against this
  repository's `plugins/crw/skills` cannot produce because that directory holds crw-check, crw-define, …
  while the oracle's leaf-safe allowlist names crw-dev, crw-kwrite, crw-search, …. The guard text itself is
  now identical in all six; the remaining difference is that catalog, which this issue's scope does not
  change and the activation surface forbids (source `spawn-attach-hook.ts:650-667` and `:816-820`; the
  fixture expectations); port: kept (unchanged from CRW-634, which already records it).
