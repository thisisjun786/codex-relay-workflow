# CRW-386 — the loop is withheld from a verified coordinating seat by every hook leg that gives it

Source: CXC v0.2.40 (commit 3c1459ac) `plugins/codexclaw/components/pabcd-state/src/hook.ts` `handleStop` (:1805-1873) and `buildGoalIdleBlock` (:1694-1738), and `plugins/codexclaw/components/cxc-ops/src/map-affordance.ts` (`runMapAffordanceSessionStart`, the loop pointer and the PostCompact restore of `runUserPromptAffordance`). None of them reads a session role: the oracle has no registry. The Go files are `internal/pabcd/hook/stop.go` (`StopHandleWithRole`, `stopGoalIdleBlock`), `internal/affordance/hook.go` (`RunMapAffordanceSessionStartWithRole`, `RunUserPromptAffordanceWithRole`), `internal/pabcd/hook/detect.go` (`PromptRole`, `Coordinates`) and `internal/harness/prompt_role.go` (`RegistryPromptRole`). The rule is decision 6 (a non-implementing seat does not run PABCD) and `plugins/crw/skills/crw-run/references/goal-mode.md` (the project parent never follows the crw-loop or crw-pabcd procedure).

- The Stop hook answers the goal-idle block (arm `orchestrate P`, or close the goal) to any session with an ACTIVE host goal, a bound goalplan with remaining work and no cycle in flight, so a project parent that holds a goal for its coordination was told to run a PABCD cycle it must not run, and a parent with a bound goalplan (the CRW-146 case) was blocked up to the three-per-phase and 24-per-turn caps (hook.ts:1805-1873, 1694-1738); port: fixed (the Stop leg takes the read-only registry reader `StopHandleWithRole` and, once every other release has been decided and only the goal-idle block is left, asks it once for the payload's session: a session whose live scope bindings are only a parent seat, or only a supervisor seat, is released with no output, no counter write and no state write, whether or not a goalplan is bound, unless it took an explicit request to implement a task in the current session (see the implementer exception below), which is the oracle's block for it and reads no registry. A dispatched task (child), an unbound session, a session with two or more roles (parent and child, parent and supervisor), a store that cannot be selected or read within the 2 s read budget, and a leg with no reader keep the oracle's block byte for byte. The registry is read only for a Stop that would answer the goal-idle block, so a Stop with no goal, no bound plan, a decision wait, a context-pressure recovery, the total cap or a cycle in flight reads nothing, and the in-flight continuation of a parent that started a cycle itself is the oracle's. Pinned by `TestStopGoalIdleBlockIsSkippedForACoordinatingSeat` (parent and supervisor released and the state bytes unchanged, task and unknown and no reader equal to the reader-less block, in a git and a non-git workspace), `TestStopGoalIdleBlockKeepsTheLoopForAnExplicitImplementer` and `TestStopLegGoalIdleKeepsTheBlockForAnExplicitImplementer` (the implementer exception, direct and through the wired leg), `TestStopReadsTheRoleOnlyForAGoalIdleBlock` and, through the wired leg against a seeded registry, `TestStopLegGoalIdleFollowsTheRegistryRole` and `TestStopLegInFlightBlockIsNotRoleDependent`; red output `/state/crw/crw-lane-role-hooks/evidence/red-stop-386-145.txt`).
- The SessionStart map affordance gives every session the loop pointer ("Loop contract: for actual loop work load $crw:crw-loop + $crw:crw-pabcd ..."), a pointer that tells an implementer how to arm and run a loop (map-affordance.ts `runMapAffordanceSessionStart`); port: fixed (the leg asks the reader for the payload's session when it names one (any non-empty id: the role is the registry's to decide, as for Stop and UserPromptSubmit, so an id with a dot, a leading underscore or more than 128 characters, which the pointer's own print rule would not put into the binding line, still gets its role) and a reader is given, and a verified parent or supervisor that took no explicit current-task request gets the list without the loop pointer, in the answer and in the record of what the session was given (CRW-1146), so its own resume still re-issues the binding only. Every other pointer, the binding and the PATH banner are unchanged; a task, an unknown role, a missing session id and malformed input get the whole list as before. `RunMapAffordanceSessionStart` keeps the reader-less behavior. Pinned by `TestSessionStartLoopPointerFollowsTheRegistryRole`, `TestSessionStartReadsNoRoleWithoutASession`, `TestCoordinatingSeatResumeKeepsTheRecord` and, through `RunHook` against a seeded registry, `TestWiredHooksReadTheRegistryRole`; red output `/state/crw/crw-lane-role-hooks/evidence/red-affordance-386.txt`).
- The PostCompact restore (`runUserPromptAffordance`) renders the loop pointer unconditionally when it consumes the compaction marker, so SessionStart withholding it from a parent would have been undone by the first prompt after any compaction (the verifier's correction of the triage); port: fixed (`RunUserPromptAffordanceWithRole` consumes the marker as before and, only then, asks the reader; the restore of a coordinating seat that took no explicit current-task request omits the loop pointer, every other section and the single-consumer marker semantics are unchanged, and a prompt with no marker reads no registry. Pinned by `TestCompactRestoreLoopPointerFollowsTheRegistryRole`, `TestImplementingSeatKeepsTheLoopPointer` (the implementer exception for this restore and for SessionStart) and the compaction half of `TestWiredHooksReadTheRegistryRole`, which also seeds parents named `thread.parent`, `_parent` and a 129-character id; red output `/state/crw/crw-lane-role-hooks/evidence/red-round1.txt`).
- The role reader knew a parent and a child only; a supervisor seat (role `supervisor`, scope kind initiative or store) was an unknown role (the verifier's correction of the triage: `PromptRole` had no supervisor); port: fixed (`PromptRoleSupervisor` is added, `RegistryPromptRole` maps a session whose only live binding is a supervisor seat to it, and `PromptRole.Coordinates` is the one question every leg asks: parent or supervisor. UserPromptSubmit asks it too, so a verified supervisor's loop request gets the scope pointer (without the parent-only sentence, which says "registered as a project parent") and an explicit current-task implementation keeps the recipe as for a parent. A supervisor that also holds another seat is no role. The L0 manager is not a role this reader reports: it reads parent, supervisor and child bindings only. Pinned by the supervisor cases of `TestLoopArmScopeCases` and `TestPromptSubmitLegReadsTheRegistryRole`).
- The registry role is what a session is bound as, not what it is doing now: `plugins/crw/skills/crw-run/references/goal-mode.md` lets a registered parent or supervisor implement one task in the current session on the user's explicit request (the one exception to "the parent never follows the loop procedure"; the session is then that task's implementer, with its own goalplan and loop), and UserPromptSubmit keeps the loop-arm recipe for that request whatever the registry says and records it as `loopArmSeen` (a coordinating seat's scope pointer arms nothing and does not). Withholding the loop by the role alone would drop the goal-idle continuation between the work-phases of that implementer's goalplan and its loop pointers after a start and a compaction; port: fixed (every leg that withholds the loop from a coordinating seat asks both questions: the role is parent or supervisor (`PromptRole.Coordinates`) and the session has not taken the current-task request (`loopArmSeen` of its own state, `state.State.LoopArmSeen`, read through `ImplementsHere` for SessionStart and the compaction restore and from the state Stop already read). A seat with the request is treated as the oracle treats any session: Stop's goal-idle block (with its budget), the loop pointer of SessionStart and of the compaction restore. A seat that never took the request is released as before, and `orchestrate reset` clears `loopArmSeen` and with it the exception. A session that set `loopArmSeen` before it was registered as a seat is treated the same way, as an implementer. Pinned by `TestStopGoalIdleBlockKeepsTheLoopForAnExplicitImplementer`, `TestStopLegGoalIdleKeepsTheBlockForAnExplicitImplementer` and `TestImplementingSeatKeepsTheLoopPointer`; red output `/state/crw/crw-lane-role-hooks/evidence/round3/red-before-fix-9201598e.log`).
