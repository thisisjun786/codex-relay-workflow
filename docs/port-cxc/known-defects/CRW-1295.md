# CRW-1295 — the lane-lab tests read the host's memory and failed with defer:host_memory under load

Source: CRW's own lane lab (CRW-1277), not the CXC oracle (CXC v0.2.40, commit 3c1459ac): the oracle has no host memory bound for its scheduler's releases and no lab over it. The Go side is `internal/flow/cli/lanelab_test.go` (`newLaneLab`, `labProcFixture`, `TestLaneLabIgnoresAShortHost`); the bound is `internal/relay/dagsched/hostmemory.go` (`EnvHostProcRoot`), unchanged.

- The lane lab made its world with the process environment as it was, so the host memory bound that `dag-release` applies (BuildLane, laneops.go) sampled the real `/proc` of the machine the tests ran on; on a loaded host (28G of swap, parallel lanes, 10-14 04:24) a release was deferred (`defer:host_memory`) and `TestProjectLaneTwoMilestonesOnTempStore`, `TestRunClaimsPlanEpochAndStopsWhenLost`, `TestSchedRelayAcceptIntegrateCloseOnTempStore`, `TestNightBatchStartsFromDecisionOnTempStore`, `TestRunUnderLaneOperationsCallsBatchCommitted` and `TestSchedRelayPlanChangedNamesTheRevisionsAndReturnsTheSlot` failed, which blocked an unrelated lane's integration verification (internal/flow/cli lanelab_test.go `newLaneLab`); port: fixed (`newLaneLab` sets `CRW_DAG_HOST_PROC_ROOT` with `t.Setenv` to a test-only proc fixture with 64 GiB MemAvailable, no swap and zero memory pressure, so no lane-lab test reads the host's memory; the bound and the lane operation code are unchanged and the bound's own tests, `TestBuildLaneAppliesTheHostMemoryBound` (which passes its own environment) and the `HostMemory` tests of internal/relay/dagsched, still exercise the deferral. Pinned by `TestLaneLabIgnoresAShortHost`, which names a 1 GiB proc root before the lab is made and releases A-1).
