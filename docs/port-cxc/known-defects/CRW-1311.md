# CRW-1311 — a parent cannot instruct again, within a generation, a child that finished its turn and was unloaded (unverified_pair_for_unloaded_thread)

Source: CRW's own bridge and relay, no CXC oracle (CXC v0.2.40, commit 3c1459ac, has no execution policy with several pairs per role). The evidence is the 10-13 r2 F0-2 run (20261013T050105Z, install d777b8d1), `ev/S8/20261013T050105Z/coordinator-f02-readings.json` of the real-trial record. Go file `internal/bridge/mutations.go` (`SendMessageToThread`, `comparePair`); the texts are `plugins/crw/skills/crw-run/references/relay.md` (the managed start sequence), `plugins/crw/skills/crw-run/SKILL.md` (Return corrections to the existing task), `plugins/crw/skills/crw-run/references/bridge.md` and `docs/role-execution-policy.md`. No relay schema, receipt status, refusal code or skill is added.

- A child unloads about a minute after its turn ends (`notLoaded`), and the bridge's `send_message_to_thread` refused every send to an unloaded thread of a role that declares several pairs (`unverified_pair_for_unloaded_thread`, nothing resumed), so in all three F0-2 runs the parent could not pass the re-send request to its child; in F0-2-1 the documented standby start (create, standby turn, register, dispatch) left the standby child unloaded before the work arrived, and the parent worked around it with a new child and `--supersedes`; port: fixed (the caution of the 10-13 decision is in the crw-run skill where the child start and the corrections are described, and in `docs/role-execution-policy.md`: put all of a child's work in its first work turn, do not start it with a standby turn, and open the next generation with `needs_changes` when something must be fixed).
- The behaviour (decided default: resume, then compare, the route relay delivery takes for such a role); port: fixed. For a send naming a role whose request pair is authorized as `role_pair` but not pinned (the role lists several pairs) to a thread the host reports `notLoaded`, the bridge resumes the thread without transmitting the pair (no `model`, no `model_reasoning_effort`; the other requested settings and the pair's `model_auto_compact_token_limit`, which is no pair, go out as before), reads the model and effort the host reports for the resumed thread, and starts the turn only when both equal the request's. Any other answer, another pair or a field the host did not report, starts no turn and is refused as `unverified_pair_for_unloaded_thread` with a message naming both pairs; the receipt's `pairCheck` (`requested`, `reported`, `transmitted: false`, `match`) records what the host reported, for a match too. A role with one pair (still resumed with its pair and judged by the settings findings), the MCP-profile branch (a role that declares profiles still needs `expected_settings.mcp_profile` before resume), and a supervisor's or an exception's pair (still refused before any resume) are unchanged. Pinned by `Test_a_pair_of_a_role_that_lists_several_is_sent_to_an_unloaded_thread_only_when_the_host_reports_it` (both pairs of the role, the one-pair role unchanged) and `Test_a_pair_of_a_role_that_lists_several_is_not_sent_to_a_thread_the_host_has_not_loaded` (the old test's name, now the different case: the role's other pair, another effort, no pair reported, a model without an effort); `Test_test_a_named_supervisor_the_host_has_not_loaded_is_not_resumed_at_all` and `Test_test_an_exception_is_not_evidence_that_a_pair_matches_its_roles_policy` keep their refusal and now say why.
- `crw manage child-resume --dry-run` ended with `disabled_servers_unset` in the same run (05:47:57, and `child-check` alike). The facts: child-resume reads the MCP servers it switches off on the resume (`mcp_servers.<name>.enabled = false`, then checked as disabled through `mcpServerStatus/list`) from the `child_check.disabled_servers` list of the crw config file (`internal/manage/childcheck.go`, `childCheckDisabled`), and refuses with exit 2 before any relay or host read, the dry run included, when the list is missing or blank (`internal/manage/childresume.go`, `resumeRun`). The trial's `crw-config.json` had no `child_check` section; no installer writes one and no document names it, so every host meets the refusal until it is configured by hand. Even with the list, a dry run of a `notLoaded` thread ends `settings_unverified` (the host reports no settings for a thread until it is resumed), so the dry run cannot have shown the unloaded case. With the bridge route above, child-resume is not on the path this issue repairs: the parent's own send now reaches an unloaded child of a multi-pair role. Options for the coordinator: (a) read a missing list as no server to switch off, with a warning and a record (the 10-13 rule for a reversible condition); (b) keep the refusal and document `child_check.disabled_servers` in the crw config reference, the refusal naming the file and the key; (c) leave it; port: pending (not changed here; for the coordinator).
- Named limits. (1) The comparison is the host's report at the resume, not a guarantee about the turn: another client can change the thread's settings between the resume and `turn/start`, as for every send (the receipt's `observationLimits`). (2) The resume still sends the matched pair's auto-compaction limit, as relay delivery sends the recorded pair's; a thread found on another pair refuses after the resume, so that thread keeps the limit until its next resume. (3) The evidence is fake-host tests, not a live host run of this change.
