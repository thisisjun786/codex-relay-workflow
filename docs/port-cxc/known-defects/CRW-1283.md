# CRW-1283 — readable forwarding scripts and assigned PATH

- The command reader treated a script's `"$@"` as an unknown option even when the invocation supplied literal arguments. The GitHub guard refused an unrelated forwarding wrapper, and the memory guard refused the same readable shell file with `unknown-destination`; port: fixed. Shell-file records carry their positional arguments into the bounded body reader. Exact quoted forwarding exposes the real command through `ionice`, `nice`, `env` and `timeout`; transformed parameters, unknown programs, unreadable files, stale files and excessive nesting remain refused. Direct forwarding scripts are read by the memory and managed-worktree guards too. New shells get their own arguments, source inherits the appropriate arguments, and function bodies and runtime operand feeds do not borrow a caller's harmless argument list. A script that may change its positional parameters before `"$@"` (`set` with an operand, `--` or `-`; `shift`; `eval`, `source`, `trap`, `alias`; an assignment to zsh's `argv`) does not forward the arguments it was given, so `"$@"` after it is unknown and refused; `set` with options alone (`set -euo pipefail`) keeps them.
- Every PATH assignment used to be refused without resolving the program it selected; port: fixed for scalar `PATH`. Prefix assignments, literal exports (including quoted assignments) and `env PATH=...` resolve external programs against the assigned search path. Executable shell files selected there are read, rather than trusted merely because their basename resembles an installed program. The system-program option grammar is used only for a bounded binary header in a system bin directory. Program names still retain their target policy: a shadowed `gh` does not turn a post into an allowed operation. A builtin name is exempt from the search only where the shell runs it itself and the text has not run `enable`, `disable`, `eval` or a sourced file that may disable it (then a file of that name on the PATH is read, and only a name no directory holds is the builtin); behind `env`, `exec`, `nice`, `timeout`, `nohup`, `xargs`, `find -exec` and the other launchers (all wrappers but `command` and `builtin`) the name is searched on the assigned PATH and the file found is read. A program found outside the system directories is read as the same program run by its absolute path (by its name, and a shell file by its body); a binary there is not identified by its name (a copy of a shell named `check` runs its `-c` text), so it is admitted only when the PATH the shell starts with (the hook's own environment) runs the same file for the name, as for `PATH=<go>/bin:$PATH go version`, and refused otherwise with the advice to run it by its absolute path. A PATH assignment in front of a command lasts for that command only, and what a regular builtin does to the shell (`cd`, `read`, `printf -v`) stays; in front of a POSIX special builtin, `exec` without a program or a function call it outlasts the command in some shells, so it is refused with the advice to assign PATH in a statement of its own. An unknown PATH is harmless for an absolute program or a shell builtin that does not search it, but an external program with an unprovable search path remains refused. An unknown, unset or branch-dependent PATH cannot recover an earlier environment value. Bare source searches after a PATH change, lower-case/array path assignments and unresolved external programs remain refused.
- A refusal recommended a readable script file even when another guard could not read that file; port: fixed. The parent recovery names a direct command with a literal program and absolute paths, states that a script must pass the same checks, and requires reviewed file input for GitHub text. Leaf recovery still reports the blocked command to its parent. No authorization or grant is implied by a reader failure.
- Security boundary: real inline GitHub posts, posts concealed in newly readable wrappers or PATH-selected shell files, memory writes and protected worktree removals remain denied. Git push inside a newly admitted script or behind assigned PATH is refused; unrelated existing direct push commands retain their previous policy. The four named regressions are `TestGithubPostGuardAllowsAWrapperThatNamesNoPost`, `TestMemoryWriteGateReadsAReadableScriptFile`, `TestCommandReaderPathAssignmentResolvesTheProgram` and `TestGuardRefusalNamesAPathAnotherGuardAllows`. Additional argument/environment isolation regressions and the three-guard rows in `internal/pabcd/hook/testdata/shellir/rows/49-crw-1283.txt` pin the refusal cases. Existing security rows and their recorded deviations are unchanged.

The memory and managed-worktree guards also read a direct shell file when an assigned PATH accompanies its invocation, even if the file has an absolute name and does not forward arguments. `TestCRW1283AssignedPathDoesNotHideADirectScript` pins this boundary: ignoring PATH for an absolute program must not mean ignoring the script's own protected writes or removals.

The security review of the relaxations (opusverify-e4c54cc3-r1) pins the forms they must not open as refused rows `CRW-1283-review-*` in the same row file and as `TestReview1283PositionalMutation`, `TestReview1283ExternalBuiltinName`, `TestReview1283PathBinaryAlias`, `TestReview1283PathGitAlias`, `TestReview1283PathPrefixKeepsShellState` and `TestReview1283PathBinaryOfTheStartingPath`, each against the memory, GitHub and worktree guards. A copied or linked binary run by its absolute path, or by a bare name the starting PATH finds, is still read by its name; that reading predates this issue and is not widened by it. So does the reading of a PATH a builtin assigns by name (`read PATH`, `printf -v PATH`): such a text is read as before this issue, by program names; marking PATH unknown there refuses existing benign and security-table rows (CRW-875-22-31d, CRW-1178, CRW-1187), so it is left as it was.

The memorygate fuzz seeds `crw650-open-triple-quote` and `crw857-memorygate-codex-home-expansion` pin the revised Go recovery text. Both still deny, their inputs and original oracle bytes are unchanged, and their intentionally-changed records name this diagnostic-only update.

These are source-reader guarantees, not evidence that a particular host script, installation or live hook has run. A script with locks, generated filenames or other destinations the reader cannot prove still fails closed; replacing its invocation with `bash file.sh` is not an unconditional workaround.
