# CRW-1283 — program wrappers, readable script files and assigned PATH

The CRW command guards (GitHub post, memory write, managed-worktree removal) read the commands of a Codex session through the shared shell reader. The reader read every `"$@"` as an unknown option, every PATH assignment as unreadable, and the guards' refusals recommended a readable script file that another guard then refused; port: fixed as decided by Sion (plan C, 10-13).

- Program wrappers. `ionice`, `nice`, `env`, `timeout` and the other program wrappers are read by their option grammar, and the command after them is judged: `ionice -c3 nice go version` passes every guard, `ionice -c3 nice gh pr comment ...` is a GitHub post, and a memory write or a removal of the managed checkout behind them is refused.
- Script wrappers that forward `"$@"`. The reader does not follow the arguments a script forwards. A script whose body forwards `"$@"` (the shape of `.omo/mgmt/tools/heavy_slot.sh`) is refused by every guard whose target the forwarded arguments may carry, run by a shell (`bash f.sh ...`, `zsh f.sh ...`, `. f.sh`) or by its path; the memory and worktree guards read such a script run by its path for this. The GitHub guard's reason names the path the user can follow, which no guard blocks: run the forwarded command directly, with `ionice` and `nice` in front of it if wanted. This is a named limit: the real `heavy_slot.sh` is refused, and a registry of trusted wrappers (path and sha256, granted and recorded) is the follow-up CRW-1290.
- Readable script files. The memory gate reads a readable script file run as `bash f.sh` or `sh f.sh` and judges its writes; a script whose destination it cannot place is refused with the advice to use a direct command with a literal program and absolute write paths, which the GitHub and worktree guards allow for a command without their targets.
- PATH assignments. A PATH assignment is read only when its value is literal (no expansion: `PATH=<dir>:$PATH` and `PATH=$D` are refused), the hook knows the PATH the shell starts with (its own environment), and the walk follows it in the order the shell runs it: a statement or a prefix of the command itself, `export`, a quoted assignment word, `env PATH=...`, and a declaration builtin reached as a command (`X=1 export PATH=...`). In a script file's body (a sourced file changes the shell that sources it), a loop (a later iteration runs after it), a pipeline (zsh runs the last element in the current shell), a function (zsh runs `TRAPDEBUG`, `chpwd`, `precmd` by name, and a trap runs one later) or a text run later or again (`trap`, `eval`, `xargs`) it is refused, as every PATH assignment was before this issue; so is an array or lower-case `path`, and a PATH assignment in front of a POSIX special builtin, `exec` without a program or a function call (it outlasts the command in some shells). A PATH the reader cannot follow afterwards (`unset PATH`, a branch, a variable-clobbering builtin after an assignment) is unknown, and an external program or a name only some shells run themselves is then refused.
- Programs on an assigned PATH. Program names resolve on the assigned PATH and the resolved program is judged: a shadowed `gh` is still a GitHub post, `git push` behind an assigned PATH or inside a script is refused, and a shell file the PATH finds is read like a script run by its path. No directory name or file header identifies a program: a binary, and a script under an interpreter's name (`python3`, `perl`, `node`, `awk` and the others read by name), are admitted only when the starting PATH runs the same file for the name. The `env` interpreter of a script's `#!` line is resolved on the assigned PATH under the same rule. A name is exempt from the search only where every modelled shell (sh and dash, bash, zsh, ksh) runs it itself: a function the text defines, a POSIX special builtin, `cd`, `command`, `getopts` and `read`, while the text has not run `enable`, `disable`, `eval` or a sourced file; a builtin or keyword of some shells only (`printf`, `echo`, `test`, `time`, `let`, `declare`, `[[`, `coproc`, `select`, `function` and the rest) is searched, `((...))` is refused, and behind `env`, `exec`, `nice` and the other launchers every name is searched. Bare `source` after a PATH assignment is refused.
- Refusal wording. The GitHub guard's reader refusal says `The reader cannot tell whether the command posts to GitHub.` instead of `It names no GitHub post.` (Sion decision 1); the CRW-1178 wording tests and the two memorygate fuzz seeds `crw650-open-triple-quote` and `crw857-memorygate-codex-home-expansion` pin the revised texts, their decisions unchanged.

The four named regressions are `TestGithubPostGuardAllowsAWrapperThatNamesNoPost`, `TestMemoryWriteGateReadsAReadableScriptFile`, `TestCommandReaderPathAssignmentResolvesTheProgram` and `TestGuardRefusalNamesAPathAnotherGuardAllows`. The forms the security reviews and the Opus verifications found are refusal tests (`crw1283_review_test.go`, `crw1283_probe_test.go`, `crw1283_identity_test.go`, `crw1283_loop_test.go`, `crw1283_zshparam_test.go`, `crw1283_planc_test.go`) and the three-guard rows of `internal/pabcd/hook/testdata/shellir/rows/49-crw-1283.txt`. `TestCRW1283GuardFuzz` composes the wrapper, PATH, script, program-file and out-of-order PATH forms around each guard's target and asserts that every form carrying a target is refused; its doc comment gives the differential against c007bd50. Existing security rows and their recorded deviations are unchanged.

Limits that predate this issue and are not widened by it: the memory and worktree guards do not read a script run by its path unless its body forwards `"$@"` (pinned by the fuzz as class ownlimit; follow-up CRW-1287); a `#!` interpreter named by an absolute path is read by its basename; a copied or linked binary run by its absolute path, or by a bare name the starting PATH finds, is read by its name; a PATH a builtin assigns by name (`read PATH`, `printf -v PATH`, a name reference) is read as before, by program names. These are source-reader guarantees, not evidence that a host script or a live hook has run.
