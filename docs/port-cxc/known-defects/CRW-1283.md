# CRW-1283 — readable forwarding scripts and assigned PATH

- The command reader treated a script's `"$@"` as an unknown option even when the invocation supplied literal arguments. The GitHub guard refused an unrelated forwarding wrapper, and the memory guard refused the same readable shell file with `unknown-destination`; port: fixed. Shell-file records carry their positional arguments into the bounded body reader. Exact quoted forwarding exposes the real command through `ionice`, `nice`, `env` and `timeout`; transformed parameters, unknown programs, unreadable files, stale files and excessive nesting remain refused. Direct forwarding scripts are read by the memory and managed-worktree guards too. New shells get their own arguments, source inherits the appropriate arguments, and function bodies and runtime operand feeds do not borrow a caller's harmless argument list. A script that may change its positional parameters before `"$@"` (`set` with an operand, `--` or `-`; `shift`; `eval`, `source`, `trap`, `alias`; an assignment to zsh's `argv` or to a positional parameter such as `1=gh`, a loop over one) does not forward the arguments it was given, so `"$@"` after it is unknown and refused; `set` with options alone (`set -euo pipefail`) keeps them. Only `eval` reads its text with the positional parameters of the text around it: a `trap` text runs later, after they may have changed, and a shell that reads its program from standard input (`bash -s`, a here-document or here-string), from a descriptor alias (`bash /dev/fd/3`) or as `su -c` starts with parameters of its own, so `"$@"` there is unknown. A file sourced with operands (`. file.sh true`) gets them in bash and zsh and keeps the caller's in dash, so its `"$@"` is unknown; a file sourced without operands inherits the caller's. Operands that `xargs`, `find -exec` or `parallel` append at run time leave a script's `"$@"` unknown, whether the script is run by a shell or by its path.
- Every PATH assignment used to be refused without resolving the program it selected; port: fixed for scalar `PATH`. Prefix assignments, literal exports (including quoted assignments) and `env PATH=...` resolve external programs against the assigned search path. Executable shell files selected there are read, rather than trusted merely because their basename resembles an installed program. No directory name and no file header identifies a program: `/usr/bin`, `/bin` and `/usr/local/bin` are not trusted as such. Program names still retain their target policy: a shadowed `gh` does not turn a post into an allowed operation. A name is exempt from the search only where every modelled shell (sh and dash, bash, zsh, ksh) runs it itself: a function the text defines, a POSIX special builtin (`:`, `.`, `break`, `continue`, `eval`, `exec`, `exit`, `export`, `readonly`, `return`, `set`, `shift`, `times`, `trap`, `unset`) and `cd`, `command`, `getopts` and `read`, while the text has not run `enable`, `disable`, `eval` or a sourced file that may disable it. A name that is a builtin or keyword in some shells only (`printf`, `echo`, `test`, `true`, `time`, `let`, `declare`, `typeset`, `local`, `pushd`, `mapfile`, `readarray`, `chdir`, `source`, `builtin`, `[[`, `coproc`, `select`, `function` and the rest) is searched on the assigned PATH: dash has no `let`, `time` or `[[`, bash has no `chdir`, zsh has no `readarray`, and a strict POSIX shell runs the `printf` the PATH finds. A file of such a name the assigned PATH holds is read (a declaration, `let`, `time`, `[[`, `coproc`, `select` or `function` clause whose word a file on the PATH holds is refused unless the PATH the shell starts with runs that same file), and a name no directory holds is read as the builtin. `((...))` behind an assigned PATH is refused: dash runs the word inside as a program; behind `env`, `exec`, `nice`, `timeout`, `nohup`, `xargs`, `find -exec` and the other launchers (all wrappers but `command` and `builtin`) the name is searched on the assigned PATH and the file found is read. A program an assigned PATH finds, in any directory, is read as the same program run by its absolute path (by its name, and a shell file by its body); a binary there, with a NUL in its head, is not identified by its name or by the directory it stands in (a copy of a shell named `check` runs its `-c` text), and a script under an interpreter's name (`python3`, `perl`, `node`, `awk` and the other interpreters the reader reads by name) is read as the interpreter's inline program or module, not as the script. Either is admitted only when the PATH the shell starts with (the hook's own environment) runs the same file for the name, as for `PATH=<go>/bin:$PATH go version`, and refused otherwise. A PATH assignment in front of a command lasts for that command only, and what a regular builtin does to the shell (`cd`, `read`, `printf -v`) stays; in front of a POSIX special builtin, `exec` without a program or a function call it outlasts the command in some shells, so it is refused with the advice to assign PATH in a statement of its own. A declaration builtin the walk reaches as a command (`X=1 export PATH=/dir`) assigns PATH as a declaration clause does; the differential fuzz found that the reader had not noticed it (c007bd50 allowed it too). An unknown PATH is harmless for an absolute program or a name every shell runs itself, but an external program, or a name that is a builtin in some shells only (`echo` included), with an unprovable search path remains refused. An unknown, unset or branch-dependent PATH cannot recover an earlier environment value. Bare source searches after a PATH change, lower-case/array path assignments and unresolved external programs remain refused.
- The GitHub guard refused a command it could not read with the words `It names no GitHub post.`, a refusal that says the command does not touch its target (Sion decision 1); port: fixed. The command reader's refusal of a text that spells no `gh` post now says `The reader cannot tell whether the command posts to GitHub.`; the rule ID, the decision and the GitHub wording of a text that spells a post are unchanged, and the CRW-1178 wording tests pin the new sentence.
- A refusal recommended a readable script file even when another guard could not read that file; port: fixed. The parent recovery names a direct command with a literal program and absolute paths, states that a script must pass the same checks, and requires reviewed file input for GitHub text. Leaf recovery still reports the blocked command to its parent. No authorization or grant is implied by a reader failure.
- Security boundary: real inline GitHub posts, posts concealed in newly readable wrappers or PATH-selected shell files, memory writes and protected worktree removals remain denied. Git push inside a newly admitted script or behind assigned PATH is refused; unrelated existing direct push commands retain their previous policy. The four named regressions are `TestGithubPostGuardAllowsAWrapperThatNamesNoPost`, `TestMemoryWriteGateReadsAReadableScriptFile`, `TestCommandReaderPathAssignmentResolvesTheProgram` and `TestGuardRefusalNamesAPathAnotherGuardAllows`. Additional argument/environment isolation regressions and the three-guard rows in `internal/pabcd/hook/testdata/shellir/rows/49-crw-1283.txt` pin the refusal cases. Existing security rows and their recorded deviations are unchanged.

The memory and managed-worktree guards also read a direct shell file when an assigned PATH accompanies its invocation, even if the file has an absolute name and does not forward arguments. `TestCRW1283AssignedPathDoesNotHideADirectScript` pins this boundary: ignoring PATH for an absolute program must not mean ignoring the script's own protected writes or removals.

The security review of the relaxations (opusverify-e4c54cc3-r1) pins the forms they must not open as refused rows `CRW-1283-review-*` in the same row file and as `TestReview1283PositionalMutation`, `TestReview1283ExternalBuiltinName`, `TestReview1283PathBinaryAlias`, `TestReview1283PathGitAlias`, `TestReview1283PathPrefixKeepsShellState` and `TestReview1283PathBinaryOfTheStartingPath`, each against the memory, GitHub and worktree guards. A copied or linked binary run by its absolute path, or by a bare name the starting PATH finds, is still read by its name; that reading predates this issue and is not widened by it. So does the reading of a PATH a builtin assigns by name (`read PATH`, `printf -v PATH`): such a text is read as before this issue, by program names; marking PATH unknown there refuses existing benign and security-table rows (CRW-875-22-31d, CRW-1178, CRW-1187), so it is left as it was.

The second security review (opusverify-b2ae50e0-r1, probes compared against c007bd50) found forms the relaxations had opened in all three guards: `"$@"` read in a `trap` text, a `bash -s` or `sh -s` program, a descriptor alias, a file `.` sources with operands under dash and after a zsh positional assignment; builtin and keyword names (`time`, `chdir`, `printf`, `let`, `pushd`, `declare`, `mapfile`, `readarray`) shadowed by a file on the assigned PATH; and a script the assigned PATH finds under an interpreter's name. Each is withdrawn as above (Sion decision 5) and pinned, with the forms found while fixing them (`xargs` feeds, zsh `argv=(...)` and `for 1 in`, a here-string program, `[[`, `((`, `coproc`, `select`, `function`), by `TestReview1283ProbeForms` against each guard that refused the form before the relaxations and by the rows `CRW-1283-r2-*`; `TestReview1283ProbeControls` keeps a forwarding wrapper, a PATH of system directories and `cd` behind an assigned PATH allowed. The rows `CRW-1283-review-shadowed-printf-memory` (formerly a control: `PATH=<dir> printf` whose shadowing file writes memory is now read) and `CRW-1283-path-direct-memory` (an `echo` under an unknown PATH is refused by every guard) record the narrowed exemption. The memory and worktree guards do not read a script run by its path from the command itself unless its body forwards `"$@"`, before and after this issue; a body whose `"$@"` is inside a quoted string (`trap '"$@"' EXIT`, a quoted here-document) is therefore read by the GitHub guard alone.

The memorygate fuzz seeds `crw650-open-triple-quote` and `crw857-memorygate-codex-home-expansion` pin the revised Go recovery text. Both still deny, their inputs and original oracle bytes are unchanged, and their intentionally-changed records name this diagnostic-only update.

These are source-reader guarantees, not evidence that a particular host script, installation or live hook has run. A script with locks, generated filenames or other destinations the reader cannot prove still fails closed; replacing its invocation with `bash file.sh` is not an unconditional workaround.

`TestCRW1283GuardFuzz` (internal/pabcd/hook/crw1283_fuzz_test.go) composes the wrapper, PATH, script and program-file forms around the payloads of the tests above and asserts that every form carrying a guard's target is refused; its doc comment gives the command that records the decisions of c007bd50 and of the head for comparison (a form the base refuses and the head allows must not carry a target). The memory and worktree guards' unread script run by its path is a limit of c007bd50 and of the head alike; the test pins the number of such forms it allows.

The evaluation of deb45bd1 found two P0 defects the PATH relaxation had introduced, both in the promise of no regression (Sion decision 5), and both are withdrawn. First, a program an assigned PATH found in `/usr/bin`, `/bin` or `/usr/local/bin` with a NUL in its head was taken for the program its name says, so a renamed shell (`check -c '...'`, a copy or a link of `/bin/sh`) had its `-c` text read by no guard; the directory test is gone, and such a binary is admitted only when the PATH the shell starts with runs the same file for the name, like any other. `TestReview1283SystemDirectoryNameDoesNotIdentifyAProgram` pins it with `/usr/bin/static-sh` (busybox) under a starting PATH that lacks it, and the rows `CRW-1283-r3-bin-dir-*` pin the shapes in fixture directories named like system ones, behind a link and a chain of links. Second, a script run by its path, or selected by the assigned PATH, whose `#!` line launches its interpreter through `env` was read as the shell text of its body while `env` ran the file the assigned PATH selects for the interpreter's name (`#!/usr/bin/env bash` with a `bash` earlier on the PATH). The interpreter is now resolved on the assigned PATH and judged like any other program (`shellir.EnvShebang`, read through `githubPostReadDirectExec` by the GitHub, memory and worktree guards): it must be the file the starting PATH runs for that name, and an `env` option the reader cannot follow (`-i`, `-u`, `-P`, `--`, `NAME=value`) or an interpreter the PATH does not hold refuses the execution; `-S` is followed. `TestReview1283ShebangInterpreterOnAssignedPath` and the rows `CRW-1283-r3-env-shebang-*` pin it, with controls for a script whose interpreter the PATH leaves to the system. The fuzz has a `shebang` and a `binhdr` family for the two shapes.

A script whose `#!` line names an interpreter by an absolute path (`#!/tmp/dir/bash`) is read by the basename of that path, before and after this issue; the file at the path is not read. This does not depend on an assigned PATH and is not changed here.

The final verification of 418273ef found two defects in how a loop treats `"$@"`; both are fixed (`TestReview1283LoopPositionalChange`, `TestReview1283LoopWrapperForwardsArguments`, `TestReview1283LoopWrapperMemoryAndWorktree`, `TestCRW1283LoopArgumentsFollowPositionalChangesOnly`, the fuzz mutants and wrapper bodies of the loop shapes). A loop is judged twice before its body is read: for the variables and for the positional parameters. A loop whose statements only assign variables by name (the `start=`, `rc=` and `for i in $(seq ...)` of `.omo/mgmt/tools/heavy_slot.sh`) forwards the same `"$@"` in every iteration, so the wrapper is read with the arguments it was given; the issue's own reproduction (`GOFLAGS=-p=4 TZ=UTC TMPDIR=... heavy_slot.sh go version`) is read by the GitHub and worktree guards, and a protected command forwarded the same way is still refused. A loop that can change the positional parameters leaves `"$@"` unknown from its first statement on, because a later iteration runs the changed arguments: `set` with operands, `shift`, `eval`, `source`, `trap`, `alias`; a zsh positional assignment word (`1=x`, `2+=x`, `argv=(...)`, `argv[1]=x`); a positional loop variable; a builtin (`read`, `printf -v`, `getopts`, `unset`, `let`, `declare`, `typeset`, `local`, `export`, `readonly`, `wait -p`), a declaration, an arithmetic assignment or a `${1:=x}` default that names a positional parameter or a name the text does not show; a name reference; an unknown program word. The positional assignment word was missing from that list and let the first iteration's arguments stand for all of them. The memory guard still refuses the whole of `heavy_slot.sh`: it opens its lock files with `exec 8>"$DIR/owner-$okey.lock"`, a destination built from a command substitution that the memory gate cannot place outside its root (`unknown-destination`), a refusal of the redirection and not of the forwarded command.
