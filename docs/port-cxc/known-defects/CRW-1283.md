# CRW-1283 — readable forwarding scripts and assigned PATH

- The command reader treated a script's `"$@"` as an unknown option even when the invocation supplied literal arguments. The GitHub guard refused an unrelated forwarding wrapper, and the memory guard refused the same readable shell file with `unknown-destination`; port: fixed. Shell-file records carry their positional arguments into the bounded body reader. Exact quoted forwarding exposes the real command through `ionice`, `nice`, `env` and `timeout`; transformed parameters, unknown programs, unreadable files, stale files and excessive nesting remain refused. Direct forwarding scripts are read by the memory and managed-worktree guards too. New shells get their own arguments, source inherits the appropriate arguments, and function bodies and runtime operand feeds do not borrow a caller's harmless argument list. A script that may change its positional parameters before `"$@"` (`set` with an operand, `--` or `-`; `shift`; `eval`, `source`, `trap`, `alias`; an assignment to zsh's `argv` or to a positional parameter such as `1=gh`, a loop over one) does not forward the arguments it was given, so `"$@"` after it is unknown and refused; `set` with options alone (`set -euo pipefail`) keeps them. Only `eval` reads its text with the positional parameters of the text around it: a `trap` text runs later, after they may have changed, and a shell that reads its program from standard input (`bash -s`, a here-document or here-string), from a descriptor alias (`bash /dev/fd/3`) or as `su -c` starts with parameters of its own, so `"$@"` there is unknown. A file sourced with operands (`. file.sh true`) gets them in bash and zsh and keeps the caller's in dash, so its `"$@"` is unknown; a file sourced without operands inherits the caller's. Operands that `xargs`, `find -exec` or `parallel` append at run time leave a script's `"$@"` unknown, whether the script is run by a shell or by its path.
- Every PATH assignment used to be refused without resolving the program it selected; port: fixed for scalar `PATH`. Prefix assignments, literal exports (including quoted assignments) and `env PATH=...` resolve external programs against the assigned search path. Executable shell files selected there are read, rather than trusted merely because their basename resembles an installed program. The system-program option grammar is used only for a bounded binary header in a system bin directory. Program names still retain their target policy: a shadowed `gh` does not turn a post into an allowed operation. A name is exempt from the search only where every modelled shell (sh and dash, bash, zsh, ksh) runs it itself: a function the text defines, a POSIX special builtin (`:`, `.`, `break`, `continue`, `eval`, `exec`, `exit`, `export`, `readonly`, `return`, `set`, `shift`, `times`, `trap`, `unset`) and `cd`, `command`, `getopts` and `read`, while the text has not run `enable`, `disable`, `eval` or a sourced file that may disable it. A name that is a builtin or keyword in some shells only (`printf`, `echo`, `test`, `true`, `time`, `let`, `declare`, `typeset`, `local`, `pushd`, `mapfile`, `readarray`, `chdir`, `source`, `builtin`, `[[`, `coproc`, `select`, `function` and the rest) is searched on the assigned PATH: dash has no `let`, `time` or `[[`, bash has no `chdir`, zsh has no `readarray`, and a strict POSIX shell runs the `printf` the PATH finds. A file of such a name the assigned PATH holds is read (a declaration, `let`, `time`, `[[`, `coproc`, `select` or `function` clause whose word a non-system file on the PATH holds is refused), and a name no directory holds is read as the builtin. `((...))` behind an assigned PATH is refused: dash runs the word inside as a program; behind `env`, `exec`, `nice`, `timeout`, `nohup`, `xargs`, `find -exec` and the other launchers (all wrappers but `command` and `builtin`) the name is searched on the assigned PATH and the file found is read. A program found outside the system directories is read as the same program run by its absolute path (by its name, and a shell file by its body); a binary there is not identified by its name (a copy of a shell named `check` runs its `-c` text), and a script under an interpreter's name (`python3`, `perl`, `node`, `awk` and the other interpreters the reader reads by name) is read as the interpreter's inline program or module, not as the script. Either is admitted only when the PATH the shell starts with (the hook's own environment) runs the same file for the name, as for `PATH=<go>/bin:$PATH go version`, and refused otherwise. A PATH assignment in front of a command lasts for that command only, and what a regular builtin does to the shell (`cd`, `read`, `printf -v`) stays; in front of a POSIX special builtin, `exec` without a program or a function call it outlasts the command in some shells, so it is refused with the advice to assign PATH in a statement of its own. An unknown PATH is harmless for an absolute program or a name every shell runs itself, but an external program, or a name that is a builtin in some shells only (`echo` included), with an unprovable search path remains refused. An unknown, unset or branch-dependent PATH cannot recover an earlier environment value. Bare source searches after a PATH change, lower-case/array path assignments and unresolved external programs remain refused.
- The GitHub guard refused a command it could not read with the words `It names no GitHub post.`, a refusal that says the command does not touch its target (Sion decision 1); port: fixed. The command reader's refusal of a text that spells no `gh` post now says `The reader cannot tell whether the command posts to GitHub.`; the rule ID, the decision and the GitHub wording of a text that spells a post are unchanged, and the CRW-1178 wording tests pin the new sentence.
- A refusal recommended a readable script file even when another guard could not read that file; port: fixed. The parent recovery names a direct command with a literal program and absolute paths, states that a script must pass the same checks, and requires reviewed file input for GitHub text. Leaf recovery still reports the blocked command to its parent. No authorization or grant is implied by a reader failure.
- Security boundary: real inline GitHub posts, posts concealed in newly readable wrappers or PATH-selected shell files, memory writes and protected worktree removals remain denied. Git push inside a newly admitted script or behind assigned PATH is refused; unrelated existing direct push commands retain their previous policy. The four named regressions are `TestGithubPostGuardAllowsAWrapperThatNamesNoPost`, `TestMemoryWriteGateReadsAReadableScriptFile`, `TestCommandReaderPathAssignmentResolvesTheProgram` and `TestGuardRefusalNamesAPathAnotherGuardAllows`. Additional argument/environment isolation regressions and the three-guard rows in `internal/pabcd/hook/testdata/shellir/rows/49-crw-1283.txt` pin the refusal cases. Existing security rows and their recorded deviations are unchanged.

The memory and managed-worktree guards also read a direct shell file when an assigned PATH accompanies its invocation, even if the file has an absolute name and does not forward arguments. `TestCRW1283AssignedPathDoesNotHideADirectScript` pins this boundary: ignoring PATH for an absolute program must not mean ignoring the script's own protected writes or removals.

The security review of the relaxations (opusverify-e4c54cc3-r1) pins the forms they must not open as refused rows `CRW-1283-review-*` in the same row file and as `TestReview1283PositionalMutation`, `TestReview1283ExternalBuiltinName`, `TestReview1283PathBinaryAlias`, `TestReview1283PathGitAlias`, `TestReview1283PathPrefixKeepsShellState` and `TestReview1283PathBinaryOfTheStartingPath`, each against the memory, GitHub and worktree guards. A copied or linked binary run by its absolute path, or by a bare name the starting PATH finds, is still read by its name; that reading predates this issue and is not widened by it. So does the reading of a PATH a builtin assigns by name (`read PATH`, `printf -v PATH`): such a text is read as before this issue, by program names; marking PATH unknown there refuses existing benign and security-table rows (CRW-875-22-31d, CRW-1178, CRW-1187), so it is left as it was.

The second security review (opusverify-b2ae50e0-r1, probes compared against c007bd50) found forms the relaxations had opened in all three guards: `"$@"` read in a `trap` text, a `bash -s` or `sh -s` program, a descriptor alias, a file `.` sources with operands under dash and after a zsh positional assignment; builtin and keyword names (`time`, `chdir`, `printf`, `let`, `pushd`, `declare`, `mapfile`, `readarray`) shadowed by a file on the assigned PATH; and a script the assigned PATH finds under an interpreter's name. Each is withdrawn as above (Sion decision 5) and pinned, with the forms found while fixing them (`xargs` feeds, zsh `argv=(...)` and `for 1 in`, a here-string program, `[[`, `((`, `coproc`, `select`, `function`), by `TestReview1283ProbeForms` against each guard that refused the form before the relaxations and by the rows `CRW-1283-r2-*`; `TestReview1283ProbeControls` keeps a forwarding wrapper, a PATH of system directories and `cd` behind an assigned PATH allowed. The rows `CRW-1283-review-shadowed-printf-memory` (formerly a control: `PATH=<dir> printf` whose shadowing file writes memory is now read) and `CRW-1283-path-direct-memory` (an `echo` under an unknown PATH is refused by every guard) record the narrowed exemption. The memory and worktree guards do not read a script run by its path from the command itself unless its body forwards `"$@"`, before and after this issue; a body whose `"$@"` is inside a quoted string (`trap '"$@"' EXIT`, a quoted here-document) is therefore read by the GitHub guard alone.

The memorygate fuzz seeds `crw650-open-triple-quote` and `crw857-memorygate-codex-home-expansion` pin the revised Go recovery text. Both still deny, their inputs and original oracle bytes are unchanged, and their intentionally-changed records name this diagnostic-only update.

These are source-reader guarantees, not evidence that a particular host script, installation or live hook has run. A script with locks, generated filenames or other destinations the reader cannot prove still fails closed; replacing its invocation with `bash file.sh` is not an unconditional workaround.
