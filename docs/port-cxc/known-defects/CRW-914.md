# CRW-914 — the policy recovery guidance on a version 2 record this installer did not write

Source: CRW's own design, not the CXC oracle (CXC v0.2.40, commit 3c1459ac, has no `register-mcp`, no wiring record and no policy screen). The Go files are `internal/policystore/policy.go` (`Locate`), `internal/policystore/running.go` (`AppliedActions`), `internal/runtime/install/mcp.go` (`UpdateRegisteredPolicy`) and `internal/pluginwiring/launch.go` (`ReadBridgeRecord`, `RecordComplaints`). The defect was handed over by the CRW-890 verdict (Codex P2 4202770042): `Locate` read a meaningful but non-canonical version 2 record as registered while `crw install register-mcp --re-register-policy` refused the same record as `record_not_canonical`, so the repair the policy API names could not repair that record.

- `Locate` read a semantically valid version 2 record in another spelling as registered, and the re-registration the policy API names as the repair refused it as `record_not_canonical` (CRW-890 verdict, Codex P2 4202770042); port: fixed for the spelling case (CRW-931 removed the refusal on dev: the re-registration judges the record by the launcher's own `pluginwiring.RecordComplaints` and `ExecComplaints` and replaces only the `executionPolicy` member's value bytes. `Locate` and the installer both decode the record through `pluginwiring.ReadBridgeRecord`, so a spelling that decodes is read the same way by both; they do not share one acceptance judgement. CRW-914 adds no code; it pins the promise end to end with TestTheRecoveryGuidanceRunsAgainstARecordThisInstallerDidNotWrite: for two hand-written spellings the policy read reports `needs_user_action` with `AppliedActionReregister`, the guidance run as spelled answers `record_updated`, every byte outside the `executionPolicy` value is the record's own, and the next read is registered at the new digest and applied).
- Port deviation, recorded and not changed: the installer's `launcherComplaints` additionally refuses what `Locate` does not check - an exec argument that cannot be encoded or holds a NUL byte, and an argument list that starts with the plugin-launch flag - so a version 2 plugin record with `args: ["--plugin-launch"]` is read as registered by `Locate`, and the re-registration the policy API names for it answers `record_malformed` (the installer's own tests in `internal/runtime/install/mcp_policy_rawbytes_test.go` pin that refusal). Such a record is one the launcher itself would not start, so the refusal is correct and the policy read's repair guidance for it is the gap; bringing `Locate` to the same checks is a separate change to `Locate`, not part of the spelling defect this issue handed over.
- The decision CRW-914 left open (guide a fresh `register-mcp --owner plugin ...` write, or have `Locate` report a separate "re-registration needed" state) is closed by the first option not being needed: the record is accepted as it is, so no new state exists; port: fixed (no `Located` or `Applied` state was added).
