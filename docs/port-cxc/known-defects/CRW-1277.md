# CRW-1277 — the run process's scheduler adapter: what the decided answers left to the code

Source: CRW's own design (the decided answers (a) to (h) of the issue, after F12 moved the adapter out on 10-12), not the CXC oracle: the flow engine has no counterpart in CXC v0.2.40 (commit 3c1459ac). The Go side is `internal/flow/cli/schedrelay.go` (`SchedRelay`, the `ops.Relay` over `internal/relay/dagsched`), `internal/flow/cli/laneops.go` (`SchedulerLane`, `BuildLane`, the run's journal), `internal/flow/cli/world.go`, `start.go`, `spec.go` and `nightbatch.go` (the pinned handoff), `cmd/crw/main.go` (`OpsFor`), `internal/flow/compile` (`milestones[]`), `internal/manage/batch_decide.go` (`--handoff`), `internal/relay/dagsched/integration_deps.go` and `internal/relay/integrate/cli.go` (the shared dag-integrate wiring).

- Supersedes CRW-1201.md, item beginning "`ops.Relay` is the interface of the scheduler the lane uses": now port: fixed (`SchedRelay` implements it over `dagsched.Scheduler` and the shipped binary installs it; `TestProjectLaneTwoMilestonesOnTempStore`).
- Supersedes CRW-1205.md, item beginning "The run process opens the world `ProductionWorld` makes": now port: fixed for the shipped binary (`cmd/crw/main.go` assigns `cli.OpsFor = cli.SchedulerLane`, so `crw flow start project-lane` and `night-batch` are not blocked; a build that installs none is still refused as before; `TestShippedBinaryInstallsLaneOps`).
- The decided answer (h) names what `OpsFor` returns (the operations, the prover, the input snapshot) and the old signature handed it the request and the journal. The scheduler needs the run's store, the run record (the pinned revision and the epoch nonce of a resumed run, read from `flow_runs`), the role table and the host's threads, and the World needs back the base of a node's first worktree (the tip of the plan's target branch, not the repository's HEAD) and the journal the engine appends to, so `OpsFor` takes a `LaneRequest` and answers a `LaneWorld`; nothing assigned the old one; port: deviation, kept visible.
- The edit regions of the issue do not list `internal/relay/integrate/cli.go`, which now calls the exported `dagsched.CommandVerifier`, `UpdateIntegrationRef` and `IntegrationDeps` instead of its own copies (the issue says to factor the wiring out of the relay CLI), nor `plugins/crw/skills/crw-canon/references/flow.md`, the operator reference of `crw flow start --handoff` and `crw manage batch decide --handoff`; port: deviation, kept visible.
- The relay's agent acceptance reads two things of the run's calls that the journal does not record by itself (`dagsched/accept_agent.go`): the execution a call belongs to (the journal carries a node's execution only once a call's own row named it, so the calls after a release in the same process carried none) and the criteria digest the reviewer's input carried (no row of the engine names it). The run process stamps both through its journal (`runJournal`: the execution of the node's latest `crw.release` on the node's prepared rows, the `criteria=` of the call's input snapshot on a reviewer's completed row) and stores the buffered rows before it asks for an acceptance; the journal and the engine themselves are unchanged (their issues own them); port: deviation, kept visible.
- The execution row records its worktree once, at the release, before the lane has allocated one, and a node can be built in a later attempt worktree (a null_model rebuild, a resume's restore). The run records a link under its directory (`<state>/flow/<run>/node-wt/<node>`) and points it at the node's newest worktree in the journal before it asks for the acceptance, so the relay reads the head of the node's work from git, never from the call; port: deviation, kept visible.
- The plan's target is the handoff's `target`: an absolute local checkout and a branch name. The agent path integrates locally (the pull request landing of an agent node is CRW-1226's), so a target that is not a local path is refused, and the batch moves the target branch itself (`--integration-ref` and `--base` are the same branch); the merged tree is verified with `crw-dev ci local --commit --base --record --runner local`, the command `docs/relay/dag-scheduler.md` gives `--verify`; port: deviation, kept visible.
- A refused release is a hold-back (`released: false`, not an error) when the scheduler holds the node back: `capacity_exhausted`, `capacity_unmeasured`, `region_overlap`, and the `disposition_conflict` of a node the reading does not find ready (the reason is the reading's, `wait:...` or `defer:...`); every other refusal is an error of the op; port: kept.
- The epoch is claimed at the first fenced write (a release, an acceptance, an integration or a close), not when the world opens, so a run that writes nothing (a night batch whose milestone is not the selection) takes no plan; the session nonce is the run id. A write after another session claimed the plan is the error `ErrEpochLost` with the relay's `stale_coordinator_epoch`; `project-lane.js` (F09's) takes an acceptance error as `land_refused` and the escalation's close fails the same way, so the milestone ends `incomplete` with the reason in the journal rather than the run failing (`TestRunClaimsPlanEpochAndStopsWhenLost`); port: deviation, kept visible.
- The rule version's skills digest is the digest of the installed crw plugin's `skills` directory (`PLUGIN_ROOT`, else the one crw version under `<CODEX_HOME>/plugins/cache`); a host where none or several are found records `unresolved:` and why instead of stopping the release. The run applies no host memory bound to its releases (`dag-release` reads it from the environment); port: deviation, kept visible.
- `ReleaseChild` refuses with `refused:child_release_unwired:` (answer g): the host settings of a managed child start (SP-CHILD-1) are a follow-up the coordinator opens; port: pending (follow-up).
- `AcceptState` names the acceptances the run made by its own `crw.accept` rows (plan and node): `dagsched` exports no reader of an acceptance by id, and this issue exports only the integration wiring and the offering order from it. An acceptance is active while it is the node's current agent acceptance and stale once the plan's node carries other criteria or left the plan; port: kept.
- `crw flow start` blocks a workflow that reads its milestone (`crw.milestone`) when the run names no handoff, and a night batch decision names its handoff (`crw-night-batch/1` `handoff {path, sha256}`), refused by `crw manage batch decide` without it and by `start` when the file changed since the decision; port: kept.
- The milestone report goes up through the reporter of F11 (CRW-1204, merged into the lane with F12): `ProductionWorld` builds `report.Reporter` over the run's store and journal (`JournalAppender`) with `crw manage send-parent` on the relay the run is in (`ManageSender`), as answer (h) says ("F11's, if it exists"); port: kept.
- The run's journal under the lane (`runJournal`) forwards the commit notice of the journal it wraps (`SetOnCommit`, `engine.CommitNotifier`): without it the engine never registered its batch notice and the upward hook of CRW-1204 (plan summary and escalations sent while the run lives) was never called in a run of the shipped binary; port: fixed (`TestRunJournalForwardsTheCommitNotice`, `TestRunUnderLaneOperationsCallsBatchCommitted`).
- `BuildLane` answers an empty lane world for a workflow that calls no `crw.*` operation (`LaneOperations`), so a role table without the executor and reviewer pairs does not fail a script workflow that never reaches the lane; a workflow that calls one still refuses such a table (`TestBuildLaneOfAWorkflowWithoutLaneOperations`); port: fixed.
- `Integrate` treats a refused batch as the replay of a landing (the head is on the target branch, the observation may be missing) only for the acceptance that is the node's current one; any other refusal stands even when the branch holds the head (`TestSchedRelayAcceptIntegrateCloseOnTempStore`); port: fixed.
- The run still ends as `incomplete` and not at the next fenced write after the epoch was lost: `ErrEpochLost` reaches `project-lane.js` as the refusal of the operation it maps to `land_refused`, and ending the run on it (a distinct error kind) is a change of F09's `project-lane.js`, which this lane does not edit; no later fenced call writes anything after the loss (`TestRunClaimsPlanEpochAndStopsWhenLost`); port: deviation, follow-up for the coordinator.
