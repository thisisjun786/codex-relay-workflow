# CRW-1140 — a resume at another cwd opens an empty IDLE state machine beside the work in flight

Source: CXC v0.2.40 (commit 3c1459ac) `plugins/codexclaw/components/pabcd-state/src/state.ts:327` (every state path is `cwd/.codexclaw/sessions/<id>.json`) and `plugins/codexclaw/components/pabcd-state/src/hook.ts:604-612` (`handleSessionStart` runs `ensureState` in the payload cwd); the resume side is CRW's own (the oracle has no relay). The Go side is `internal/pabcd/stateroot` (`Check`, `Guard`, `Bootstrap`, the anchor under `<CRW_HOME>/state-roots/`), `internal/pabcd/hook/session_hooks.go` (`SessionHookSessionStart`), `internal/bridge/mutations.go` (`SendMessageToThread`), `internal/manage/childresume.go` (`resumeRun`) and `internal/relay/adapter/transport.go` (`guardedSend`). Found by the 10-10 combined review (B2-03).

- PABCD state is addressed by cwd and the SessionStart bootstrap creates a fresh IDLE state in whatever cwd the payload names (state.ts:327, hook.ts:606), so a thread resumed at another cwd gets an empty IDLE state machine beside the one it left in flight, and its phase, epochs and bound goalplan are detached from the session it runs in; port: fixed for relay-managed threads (the canonical root of a thread is the cwd the host reports for it before anything is resumed. Every CRW resume path — `send_message_to_thread`, `crw manage child-resume` including its dry run, and the relay's delivery — compares the cwd it would send with that root before thread/resume and refuses `state_root_conflict` when the root holds the thread's state in a work phase or a state file that cannot be read; the refusal names the preserved state file, nothing is moved or copied, and no newest copy is chosen. A symbolic-link alias of the root is the root. A bound source worktree is never taken for the root, so a session whose source is a linked worktree B keeps its state at A. Every CRW resolution of a thread records the root it is on before the resume as its anchor, whether or not a state file exists yet, so the first resume of a thread is already guarded when its first SessionStart and its first work phase follow. A thread without an anchor is always recorded, whatever its root (the process's own cwd included). A resume whose root must be recorded and cannot be (an unwritable or unresolvable CRW home) is refused `state_root_anchor_unrecorded` before anything is sent, since its SessionStart could not be guarded; an anchor that already names the root needs no write. The resume paths and the SessionStart bootstrap share one root: the anchored root while it holds work in flight, whatever cwd the host reports now (an external resume may have moved that cwd), and the host's cwd otherwise; a resume that sends no cwd is judged at the host's cwd. The anchor follows a thread to a new cwd only once the host took the resume (or a SessionStart bootstrap went ahead there from a root with nothing in flight), never at the check, so a resume the host rejects leaves the protection where the work is. The SessionStart bootstrap of an anchored thread creates no state in a cwd that is not the anchored root while that root holds work in flight, answering a SessionStart context that names the preserved state and the `--cwd` to use; a state file that already exists at that cwd (a legacy IDLE one, or another in flight) does not exempt it, so the bootstrap and the resume to that cwd judge alike. The relay's refusal happens before anything is sent, so it is recorded as not attempted and retry-safe: the same request ID is checked again once the conflict is resolved. The anchor is a local file, so no hook needs a running relay; a thread without one, a standalone terminal session, bootstraps in its payload cwd as the oracle does. A host that reports no cwd for the thread gives no root to compare, and the resume goes ahead as before. Relocation is an explicit handover to a thread started at the new cwd. The anchor is trusted only when it is a regular file of at most 4096 bytes (opened without blocking and judged by fstat, so a FIFO or device linked at its path refuses at once), a version 1 record of this thread naming an absolute cwd; an anchor that exists and fails that is a refusal `state_root_anchor_unreadable` on every resume path and at SessionStart (never an absent anchor, never overwritten), and a thread with no file at all is still standalone. The anchor moves only to the cwd the host reports in its answer to the resume (an answer without a cwd moves nothing, and a host that ran the thread elsewhere than asked is followed there), and a move whose record cannot be written withholds the turn that would follow (`state_root_anchor_unrecorded` after the resume). The SessionStart bootstrap of an anchored thread moves the anchor to its cwd before it creates the state there and creates none when the anchor cannot follow, so no state exists at a cwd the anchor does not track. The UserPromptSubmit handler and the idle-edit advisory of such a thread at a cwd other than its in-flight root read and write nothing there (the memory marker, the Stop-budget stamp and the trigger bookkeeping would otherwise publish an empty IDLE state beside the work) and answer with the root.
