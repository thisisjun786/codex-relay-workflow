# CRW-1073 — the chat D-close's ledger guards read a missing key as null and a lone surrogate as U+FFFD

Source: CXC v0.2.40 (commit 3c1459ac) `plugins/codexclaw/components/pabcd-state/src/hook.ts`
`readJsonlObjects` (:623-627), `hasGoalplanRow` (:628-632) and `hasPabcdCloseRow` (:634-645). The port is
`internal/pabcd/hook/prompt_dclose.go`, `promptDcloseAnyRow` with `promptDcloseHasGoalplanRow` and
`promptDcloseHasPabcdCloseRow`; the cases are pinned by `prompt_dclose_ledger_test.go`. No deviation from
the oracle is recorded: the port now does what the oracle does.

- `hasPabcdCloseRow` compares `row.checkEpoch === checkEpoch` and `row.closedWorkPhaseId === closedWorkPhaseId`
  with `===`, so a row that lacks a key (`undefined`) never equals the null key of an all-done close, while
  the port read a missing map key as nil and matched `closedWorkPhaseId: null`. The all-done close then
  skipped the C -> IDLE row it owed, left the session in IDLE without a marker, and the same D request
  could not be retried (`illegal transition IDLE->D`): a lost record row (`hook.ts`:639-643); port: fixed
  (a lost-record defect, fixed under the parity rule revision of 2026-10-03: `promptDcloseRowMatchesKey`
  checks that the key is present before it compares, the meaning of the CLI's `orchestrateDcloseRowMatchesKey`).
- `readJsonlObjects` parses each line with `JSON.parse`, which keeps a lone surrogate escape, while the
  port parsed it with `encoding/json`, which folds `\ud800` into U+FFFD; a stored `"closed wp-\ud800"`
  goalplan row and a stored `"closedWorkPhaseId":"wp-\ud800"` PABCD row then matched a close of the id
  `wp-<U+FFFD>`, and the close skipped both rows it owed (`hook.ts`:623-643); port: fixed (the same defect
  and the same fix as CRW-850 in the CLI reader: `promptDcloseAnyRow` decodes the bytes with
  `source.DecodeUTF8` and parses each line with `pyjson.Loads(Surrogates: true, Map: true, Numbers:
  SpelledNumbers)`; a line that does not parse or is not an object still matches nothing (CRW-797), and an
  unreadable ledger is still unreadable, not absent (CRW-869)).

The raw-byte half of the reader is pinned too: the case "raw incomplete multi-byte prefix E0 A0" of
`TestPromptDcloseLoneSurrogateRowIsNotTheReplacementCharacterRow` stores `wp-` plus the bytes E0 A0 in both
ledgers; Node reads that prefix as one U+FFFD, so the close of `wp-<U+FFFD>` writes nothing, and a reader
without `source.DecodeUTF8` (two replacements) appends both rows again.
