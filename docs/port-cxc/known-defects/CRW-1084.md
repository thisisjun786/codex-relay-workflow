# CRW-1084 — a loop request that names a project gets the scope pointer, not the implementation recipe

Source: CXC v0.2.40 (commit 3c1459ac) `plugins/codexclaw/components/pabcd-state/src/hook.ts:236-322` (the detectors: `detectLoopArmRequest`, `requestLines`), `:491-532` (`loopArmDirective`) and `:700-746` (the loop-arm branch of `handleUserPromptSubmit`). The Go files are `internal/pabcd/hook/detect.go` (`DetectLoopArmRequest`, `unfencedLines`, `ClassifyLoopArmScope`), `internal/pabcd/hook/directives.go` (`LoopArmDirective`, `LoopScopeDirective`) and `internal/pabcd/hook/prompt_submit.go` (the loop-arm branch). The canonical routing is `plugins/crw/skills/crw-run/references/goal-mode.md` and `plugins/crw/skills/crw-loop/SKILL.md` (a `$crw-loop` request with a Linear project scope and coordination intent is Run goal mode's, and the project parent never follows the crw-loop or crw-pabcd procedure).

- The loop-arm branch answers the implementation recipe (get_goal / create_goal, `loop init`, `orchestrate P`) for every un-negated loop request, with no look at its scope: a request such as "Start crw-loop for the migration project." from the project parent was told to create an implementation goalplan and FSM that the routing forbids it (`hook.ts:700-746`); port: fixed (the recipe leads with a project-coordination branch, and a request that names a project or a coordination, or that a session the registry reports as a project parent makes, gets the short scope pointer `LoopScopeDirective` instead: crw-run for the coordination, crw-loop and crw-pabcd only for an explicit implementation of a task in this session, ask or take the smaller scope when unclear. The pointer carries no recipe step and no command, starts no goal, goalplan or FSM, and arms nothing: `loopArmSeen` stays false and only the turn is recorded. The explicit current-task implementation exception (an implement verb with a this/current session, task or issue), the single-task loop (a request that names no project), a session the registry reports as a dispatched task, the existing negation, plan-only, read-only and quoted-example filtering, and the `!orchestrationActive` state check keep the recipe or their silence as before. A project link or the word project never makes a session a parent: the role comes only from the registry seam `promptDcloseSeams.role`, which CRW-386 fills with the verified registry read; a production run holds no reader, so the role is unknown and the lexical scope decides. Pinned by `TestLoopArmScopeCases` (each case's emitting owner, commands and state), `TestLoopArmRecipeRoutesProjectCoordinationFirst`, `TestLoopScopePointerNamesTheOwnersAndNoRecipeStep`, `TestLoopScopePointerComposesWithAgbrowse`, `TestLoopScopeWithoutARoleReaderReadsNoRole`, `TestClassifyLoopArmScope`, the leg replay in `TestPromptSubmitLegAnswersThroughTheEnvelope`, and the recorded fixtures `hook__user-prompt-submit-checking-pabcd-trigger__loop_arm_request` and `__korean_plan_request`, which `contract/notes/cxc/CRW-1084.json` now claims as intentionally changed).
- The oracle recognised only the backtick fence, so a request written inside a tilde fence ("~~~" example) was read as a live request (`hook.ts:236-322`, `requestLines`); port: fixed (`unfencedLines` opens a fence on three or more backticks or tildes and closes it on a line of the same character, at least as long, with nothing else; the other fence character inside is text. Pinned by `TestRequestLinesKnowsTildeFences` and the tilde cases of `TestLoopArmScopeCases`; the two oracle-derived tilde cases of `TestDetectorsOracle` and `TestRequestLines` now expect no request).
