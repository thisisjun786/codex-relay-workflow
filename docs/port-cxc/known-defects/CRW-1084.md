# CRW-1084 — a loop request that names a project gets the scope pointer, not the implementation recipe

Source: CXC v0.2.40 (commit 3c1459ac) `plugins/codexclaw/components/pabcd-state/src/hook.ts:236-322` (the detectors: `detectLoopArmRequest`, `requestLines`), `:491-532` (`loopArmDirective`) and `:700-746` (the loop-arm branch of `handleUserPromptSubmit`). The Go files are `internal/pabcd/hook/detect.go` (`DetectLoopArmRequest`, `unfencedLines`, `ClassifyLoopArmScope`), `internal/pabcd/hook/directives.go` (`LoopArmDirective`, `LoopScopeDirective`) and `internal/pabcd/hook/prompt_submit.go` (the loop-arm branch). The canonical routing is `plugins/crw/skills/crw-run/references/goal-mode.md` and `plugins/crw/skills/crw-loop/SKILL.md` (a `$crw-loop` request with a Linear project scope and coordination intent is Run goal mode's, and the project parent never follows the crw-loop or crw-pabcd procedure).

- The loop-arm branch answers the implementation recipe (get_goal / create_goal, `loop init`, `orchestrate P`) for every un-negated loop request, with no look at its scope: a request such as "Start crw-loop for the migration project." from the project parent was told to create an implementation goalplan and FSM that the routing forbids it (`hook.ts:700-746`); port: fixed (the recipe leads with a project-coordination branch, and a request that names a project or a coordination, or that a session the registry reports as a project parent makes, gets the short scope pointer `LoopScopeDirective` instead: crw-run for the coordination, crw-loop and crw-pabcd only for an explicit implementation of a task in this session, ask or take the smaller scope when unclear. The pointer carries no recipe step and no command, starts no goal, goalplan or FSM, and arms nothing: `loopArmSeen` stays false and only the turn is recorded. The explicit current-task implementation exception (an implement verb with a this/current session, task or issue in the same request clause, with no negation governing the verb: a negation word right before it or a few filler words apart, or a Korean negation after it; an unrelated negation earlier in the clause, as in "no questions, please implement this task in this session", does not govern it), the single-task loop (a request that names no project), a session the registry reports as a dispatched task, the existing negation, plan-only, read-only and quoted-example filtering, and the `!orchestrationActive` state check keep the recipe or their silence as before. The scope is read after the plainly introduced examples are dropped (`scopeText`: a parenthesis opening with an example marker, the rest of a line from "Example:", "for example", "for instance", "e.g.", "sample:", "such as", "예:", "예시", "예를 들어", "예컨대", "가령" or "이를테면", and the next line after a bare "Example:"), so an unquoted example of the exception does not trigger it. The word project counts unless it only names the place of a single-task fix ("in this project", "of the project", "이 프로젝트에서" in a clause with its own ungoverned implement verb), so "Use crw-loop to fix the failing test in this project" keeps the recipe while "Start crw-loop for this project" and a named project ("in the migration project") get the pointer; a child process or subprocess is not a coordination word. A project link or the word project never makes a session a parent: the role comes only from the registry seam `promptDcloseSeams.role`, which CRW-386 fills with the verified registry read; a production run holds no reader, so the role is unknown and the lexical scope decides. Pinned by `TestLoopArmScopeCases` (each case's emitting owner, commands and state), `TestLoopArmRecipeRoutesProjectCoordinationFirst`, `TestLoopScopePointerNamesTheOwnersAndNoRecipeStep`, `TestLoopScopePointerComposesWithAgbrowse`, `TestLoopScopeWithoutARoleReaderReadsNoRole`, `TestClassifyLoopArmScope`, the leg replay in `TestPromptSubmitLegAnswersThroughTheEnvelope`, and the recorded fixtures `hook__user-prompt-submit-checking-pabcd-trigger__loop_arm_request` and `__korean_plan_request`, which `contract/notes/cxc/CRW-1084.json` now claims as intentionally changed).
- The oracle recognised only the backtick fence, so a request written inside a tilde fence ("~~~" example) was read as a live request (`hook.ts:236-322`, `requestLines`); port: fixed (`unfencedLines` opens a fence on three or more backticks or tildes and closes it on a line of the same character, at least as long, with nothing else; the other fence character inside is text. Pinned by `TestRequestLinesKnowsTildeFences` and the tilde cases of `TestLoopArmScopeCases`; the two oracle-derived tilde cases of `TestDetectorsOracle` and `TestRequestLines` now expect no request).
- The scope words are read from the request clauses `requestLines` keeps (a first version read every unfenced line), so a negated clause ("Do not implement this task."), a backtick or quoted example, a listed or tilde-fenced example and an implement verb and a this/current task in different clauses no longer activate the current-task exception; a project request that carries any of them keeps the pointer and `loopArmSeen` false. Pinned by the added cases of `TestLoopArmScopeCases` and `TestClassifyLoopArmScope`.
- The pointer's project bullet routes a requested parent goal to crw-run's goal-mode lifecycle (create or reuse a parent native goal only where one was asked for) and bars only the implementation goalplan and FSM, matching `goal-mode.md` rules 1-2; an earlier wording barred every goal while also pointing at the requested goal mode. Pinned by `TestLoopScopePointerNamesTheOwnersAndNoRecipeStep`.
- OPEN (not done here): the production hook entry point `PromptSubmitHandle` passes no role reader, so a session the registry reports as a bound project parent or a dispatched task is read as an unknown role and decided by the prompt's scope words alone ("Run crw-loop for this task" from a bound parent still gets the recipe). The registry-role branches are pinned only through the injected `promptDcloseSeams.role` seam. The verified read-only registry role reader, and the mapping from a hook session to a registry task it needs, belong to CRW-386 (Backlog, in `internal/relay/registry` and the hook entry point); this change does not invent one, and the parent and dispatched-task conditions of CRW-1084 are complete only when CRW-386 connects its reader to `promptSubmitRole`.
