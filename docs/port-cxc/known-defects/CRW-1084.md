# CRW-1084 — a loop request that names a project gets the scope pointer, not the implementation recipe

Source: CXC v0.2.40 (commit 3c1459ac) `plugins/codexclaw/components/pabcd-state/src/hook.ts:236-322` (the detectors: `detectLoopArmRequest`, `requestLines`), `:491-532` (`loopArmDirective`) and `:700-746` (the loop-arm branch of `handleUserPromptSubmit`). The Go files are `internal/pabcd/hook/detect.go` (`DetectLoopArmRequest`, `unfencedLines`, `ClassifyLoopArmScope`), `internal/pabcd/hook/directives.go` (`LoopArmDirective`, `LoopScopeDirective`) and `internal/pabcd/hook/prompt_submit.go` (the loop-arm branch). The canonical routing is `plugins/crw/skills/crw-run/references/goal-mode.md` and `plugins/crw/skills/crw-loop/SKILL.md` (a `$crw-loop` request with a Linear project scope and coordination intent is Run goal mode's, and the project parent never follows the crw-loop or crw-pabcd procedure).

- The loop-arm branch answers the implementation recipe (get_goal / create_goal, `loop init`, `orchestrate P`) for every un-negated loop request, with no look at its scope: a request such as "Start crw-loop for the migration project." from the project parent was told to create an implementation goalplan and FSM that the routing forbids it (`hook.ts:700-746`); port: fixed (the recipe leads with a project-coordination branch, and a request that names a project or a coordination, or that a session the registry reports as a project parent makes, gets the short scope pointer `LoopScopeDirective` instead: crw-run for the coordination, crw-loop and crw-pabcd only for an explicit implementation of a task in this session, ask or take the smaller scope when unclear. The pointer carries no recipe step and no command, starts no goal, goalplan or FSM, and arms nothing: `loopArmSeen` stays false and only the turn is recorded. The explicit current-task implementation exception (an implement verb with a this/current session, task or issue in the same request clause, with no negation governing the verb: a negation word right before it or a few filler words apart, or a Korean negation after it; an unrelated negation earlier in the clause, as in "no questions, please implement this task in this session", does not govern it), the single-task loop (a request that names no project), a session the registry reports as a dispatched task, the existing negation, plan-only, read-only and quoted-example filtering, and the `!orchestrationActive` state check keep the recipe or their silence as before. The scope is read after the plainly introduced examples are dropped (`scopeText`: a parenthesis opening with an example marker, the rest of a line from "Example:", "for example", "for instance", "e.g.", "sample:", "such as", "예:", "예시", "예를 들어", "예컨대", "가령" or "이를테면", and the next line after a bare "Example:"), so an unquoted example of the exception does not trigger it. The word project counts unless it only names the place of a single-task fix ("in this project", "of the project", "이 프로젝트에서" in a clause with its own ungoverned implement verb), so "Use crw-loop to fix the failing test in this project" keeps the recipe while "Start crw-loop for this project" and a named project ("in the migration project") get the pointer; a child process or subprocess is not a coordination word. A project link or the word project never makes a session a parent: the role comes only from the registry seam `promptDcloseSeams.role`, which the harness fills with the read-only scope-binding reader (below); a session with no verified binding is an unknown role and the lexical scope decides. Pinned by `TestLoopArmScopeCases` (each case's emitting owner, commands and state), `TestLoopArmRecipeRoutesProjectCoordinationFirst`, `TestLoopScopePointerNamesTheOwnersAndNoRecipeStep`, `TestLoopScopePointerComposesWithAgbrowse`, `TestLoopScopeWithoutARoleReaderReadsNoRole`, `TestClassifyLoopArmScope`, the leg replay in `TestPromptSubmitLegAnswersThroughTheEnvelope`, and the recorded fixtures `hook__user-prompt-submit-checking-pabcd-trigger__loop_arm_request` and `__korean_plan_request`, which `contract/notes/cxc/CRW-1084.json` now claims as intentionally changed).
- The oracle recognised only the backtick fence, so a request written inside a tilde fence ("~~~" example) was read as a live request (`hook.ts:236-322`, `requestLines`); port: fixed (`unfencedLines` opens a fence on three or more backticks or tildes and closes it on a line of the same character, at least as long, with nothing else; the other fence character inside is text. Pinned by `TestRequestLinesKnowsTildeFences` and the tilde cases of `TestLoopArmScopeCases`; the two oracle-derived tilde cases of `TestDetectorsOracle` and `TestRequestLines` now expect no request).
- The scope words are read from the request clauses `requestLines` keeps (a first version read every unfenced line), so a negated clause ("Do not implement this task."), a backtick or quoted example, a listed or tilde-fenced example and an implement verb and a this/current task in different clauses no longer activate the current-task exception; a project request that carries any of them keeps the pointer and `loopArmSeen` false. Pinned by the added cases of `TestLoopArmScopeCases` and `TestClassifyLoopArmScope`.
- The pointer's project bullet routes a requested parent goal to crw-run's goal-mode lifecycle (create or reuse a parent native goal only where one was asked for) and bars only the implementation goalplan and FSM, matching `goal-mode.md` rules 1-2; an earlier wording barred every goal while also pointing at the requested goal mode. Pinned by `TestLoopScopePointerNamesTheOwnersAndNoRecipeStep`.
- The production role reader (post-evaluation, port: fixed): `PromptSubmitHandle` passed no role reader, so a session the registry reports as a bound project parent or a dispatched task was read as an unknown role. The harness now hands `PromptSubmitHandleWithRole` the read-only reader `registryPromptRole` (`internal/harness/prompt_role.go`), which resolves the relay state directory as every relay command does and reads `store.SessionScopeRoles` (`internal/relay/store/session_roles.go`) through `ReadOnlyRows`, so no store is created or migrated and the file read is the one at the pathname: the roles of the live scope bindings (status active or paused, not replaced; the same predicate as the registry's `boundRole`) whose task id or recorded CXC session is the hook's session id. Only parent alone is a project parent and only child alone is a dispatched task; no binding, both roles, any other role, an unselectable or unreadable store, or the two-second read budget ending is an unknown role, and the lexical scope decides. A project link or the word project still never makes a session a parent. The read happens only for an un-armed loop request that is not an explicit current-task implementation. Pinned by `TestPromptSubmitLegReadsTheRegistryRole` (the wired leg against a seeded store: a child keeps the recipe for a project-worded request, a parent gets the parent pointer for a single-task request, a replaced binding, two roles, an unbound session and an absent store are unknown) and `TestSessionScopeRoles`. The identity is the Codex thread id the registry calls the task id (`docs/relay/protocol-v1.md`, `managed/run_steps.go` registers the child with its task id as `cxc_session`); the match is pinned against seeded stores only and has not been run against a live host. CRW-386 keeps the parent-role branches of the Stop and SessionStart hooks; the UserPromptSubmit read it was to supply is this one.
- The noun "coordinate" (post-evaluation, port: fixed): the coordination words matched `coordinate(s)` anywhere, so "Use crw-loop to fix rounding of coordinate values in the parser" got the project pointer instead of its recipe. The bare forms count now only in a verb position (at the start of a clause or after to, and, then, will, would, should, must, can, please, also, just, help, let's); `coordinating` and `coordination` still count. Pinned by the added cases of `TestClassifyLoopArmScope` and `TestLoopArmScopeCases`. Not changed: the Korean `조정` is read as coordination wherever it appears.
- Who implements (post-evaluation, port: fixed): the current-task exception needed only a this/current session and an implement verb in one clause, so "Run crw-loop in this session to coordinate the migration project while child tasks implement their assigned issues" was read as this session implementing and got the recipe the oracle also gave it. An implement verb that follows children, a worker, a subagent, others, they, "child <noun>" or "other agent/session/task/thread" (Korean 자식, 하위, 워커) by at most three words of the same clause belongs to that agent and does not count, so the clause is a coordination. Pinned by the added cases of `TestClassifyLoopArmScope` and `TestLoopArmScopeCases`.
