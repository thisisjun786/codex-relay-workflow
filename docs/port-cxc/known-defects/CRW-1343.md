# CRW-1343 — the plan input is built from a tracking milestone; what the mapping leaves to the issue author and the planner

Source: CRW's own design, not the CXC oracle (CXC v0.2.40, commit 3c1459ac): the oracle has no DAG plan, no flow compile and no tracking milestone. The Go side is the new package `internal/flow/planinput` (`planinput.go` `Build` and the warnings, `body.go` the issue body mapping, `cli.go` the command `crw flow plan-input` and `ReadScopes`), wired in `cmd/crw/main.go`; it reads through `internal/tracking` (CRW-1342) and writes the handoff of `internal/flow/compile`, which it does not change. The tests are `internal/flow/planinput/planinput_test.go` against an httptest GitHub and `live_test.go` (build tag `live`, read-only, not run by CI). Work tracking stays on Linear until Jun says the switch is done; `thisisjun786/crw-work` is the read-only test target.

- Before this change the project key of a plan came from the Linear project by hand and a wrong key ran 41 minutes before the first claim refused it (CRW-1317); port: fixed (`crw flow plan-input --milestone OWNER/NAME#N` prints the handoff with the milestone ref as the project key and one issue line per open issue, keyed by its ref, with `after` from the `Blocked by:` lines inside the milestone; the output decodes strictly and compiles with `crw flow compile --dry-run` unchanged. Pinned by `TestBuildMapsTheMilestoneToTheCompileInput`, `TestBuildReadsOnlyThroughTheTrackingAdapter` and `TestCLIPrintsTheCompileInput`).
- The project key is compared with the live parent bindings of the owner thread (`--thread`, default `CODEX_THREAD_ID`) when the handoff is built, with the same reading `crw flow start` makes (`dag.LiveParentScopes`); a key the thread holds no binding of is the warning `project_key_bound` naming both keys, an unreadable relay store or a missing thread is `project_key_unchecked`, and neither refuses (Jun's rule that a reversible step is warned and recorded); port: fixed (the Linear issue asks for a refusal "on the spot"; the decided default of 10-14 is warn and record. Pinned by `TestProjectKeyIsComparedWithTheOwnersBinding`, `TestCLIEnvelopeRecordsTheWarnings` and `TestReadScopesReadsTheLiveParentBindings`). Only an input error refuses (exit 2, with what to pass): a ref that is not `OWNER/NAME#N`, a milestone that does not exist, a token the repository refuses. Pinned by `TestBuildInputErrors` and `TestCLIRefusesOnlyAnInputError`.
- The warnings are printed on stderr and, with `--envelope`, kept in the `warnings` array of `{schema, milestone, input, warnings}`; the bare input has no place for them because `crw flow compile` reads its input strictly and the compile package is not changed; port: kept (a caller that wants the record uses `--envelope` and passes `.input` to compile, or reads stderr).
- The issue body is read from a fixed set of headings (criteria: `끝 조건`, `Done when`, `Acceptance`, `Acceptance criteria`; regions: `수정 범위`, `Edit regions`, `Regions`; size: `크기`, `Size`, `Size fit`), documented in `plugins/crw/skills/crw-canon/references/flow.md`; an issue written in another form gets the title as its one criterion with `criteria_missing`, which makes the issue pass compile without a real criterion; port: kept (the planner fixes the body; the warning is the signal).
- The command builds no milestone entries (`Project.Milestones`, the title, criteria, surfaces, grade and required commands of a run milestone), no group, no `kind` other than implementation and no `issue_size` beyond the body line; a project that needs them adds them to the printed input by hand; port: kept.
- A blocker that is closed, in another milestone or repository, or the issue itself is a warning and is left out of `after`, so a prerequisite outside the milestone is not an order of this plan; port: kept (a closed blocker is already done and the other milestone's plan holds its own).
- An order between two issues needs the project's target for compile (`--target-repository` the absolute path of the checkout and `--base-ref` the branch); the command does not read the target from the tracking repository's settings (CRW-1363 is not part of this change) and warns `target_missing` when an order exists and no target is given; port: kept.
- The mapping reads only open issues of the milestone, as the adapter lists them (pull requests are left out); sub-issues are not read, so a parent issue and its sub-issues are lines of the plan only when each is in the milestone; port: kept.
- The live check needs a token and the network, so it is behind `-tags live` and CI does not run it; its transport refuses any method but GET; port: kept.
