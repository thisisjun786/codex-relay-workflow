# CRW-652 — doctor manifest targets keep the original string

Source: the oracle's shared validator `plugins/codexclaw/components/cxc-ops/src/manifest-targets.ts` at CXC
v0.2.40 (commit 3c1459acadeb1906d97c00a598e1457327ae372d): `escapesRoot` (:105-117), `checkTarget`
(:119-139), `validateManifestTargets` (:148-205) with `String` of a non-string `hooks` entry (:157)
and the `TargetParseError` path (:81). The port is `internal/runtime/doctor/manifest_targets.go`. The
oracle's containment test and every finding it reports work on JavaScript strings, which keep a lone UTF-16
surrogate; only `existsSync`, `realpathSync` and `statSync` see Node's UTF-8 encoding of such a
string, where a lone surrogate is one U+FFFD.

- Supersedes known-defects.md, section "CRW-555 — lone surrogates in doctor manifest paths", item beginning
  "The oracle's containment test compares resolved path spellings": now port: fixed (the escape judgement keeps
  the original string, and the paired fallback compares those strings, which is the oracle's `catch`
  branch. The success path also matches: Node's `realpathSync` resolves symlinks with a JavaScript walk
  that returns each component as the caller spelled it — only `realpathSync.native` answers the on-disk
  name — so the port's own `manifestTargetsRealpath` keeps the caller's spelling for the components before
  the first symlink and follows a link by restarting at its target. With a root holding U+FFFD and the target
  `../plugin-\ud800/missing.js` the answer is `manifest hook file escapes plugin root` as the oracle
  has it, and with the leaf present under the U+FFFD name it is the same escape for the hook entry, the
  mcpServers file, an mcp `.js` argument and a hook command target, where answering the on-disk name from
  both sides would have reported no finding).
- Supersedes known-defects.md, section "CRW-555 — lone surrogates in doctor manifest paths", item beginning
  "A lone surrogate in a finding message is kept by the oracle": now port: fixed (every finding message and
  `TargetParseError.Path` keep the original string, so a writer that follows `JSON.stringify` writes a
  lone surrogate as its `\udXXX` escape, as the oracle's report does; the port's message held U+FFFD in
  both before this change).
- The report writer still spells a string's bytes through `encoding/json` at this base, so a finding message
  that now holds a lone surrogate's WTF-8 bytes is written as three U+FFFD where the oracle writes one
  `\udXXX` escape, and the text report writes those three bytes where the oracle's UTF-8 encoder writes one
  U+FFFD (source `plugins/codexclaw/components/cxc-ops/src/cli.ts:83-84` and `doctor.ts:648-661`; port
  `internal/runtime/doctor/harness_run.go` `harnessRunWriteJSON` and `harness_report.go`
  `RenderHarnessReport`); port: pending, those two files are another issue's edit region and its concurrent
  change gives them the WTF-8 spelling, so this issue does not touch them.

No other defect was found in this issue's ranges. Every expectation in the issue's tests was recorded from the
oracle with Node 24 against that commit's `dist/manifest-targets.js`: a lone surrogate in a manifest
hook file, an mcpServers file, an mcp `.js` argument, an mcp server name, a non-string `hooks` entry, a
hook command target and the parse-error path, each with the leaf absent and with it present under the U+FFFD
name, and the containment judgement with U+FFFD in the root, in a parent, in a symlink name and in the target.
