# CRW-1139 — the GitHub post guard leg leaves no hook observation record

Source: none in CXC v0.2.40: the GitHub post guard is CRW's own protection (no oracle leg; see `CRW-392.md`). Its siblings record through `hook-observation.mjs` `recordHookInvocation` (ported as `harness.RecordInvocation`, `internal/harness/observation.go`), which the oracle's legs call before they judge. The Go files are `cmd/crw/component_hooks.go` (the `pre-tool-use-guarding-github-post` row) and `internal/pabcd/hook/githubpost.go` (`GitHubPostInput`, `GitHubPostJudge`, `GitHubPostAnswer`); the tests are in `cmd/crw/component_hooks_test.go`. Found by the isolated real-use trial r1 (F2): the observation store held records for the worktree-guard and memory-write PreToolUse legs and none for the GitHub guard.

- The row went straight from the input to the guard's answer and left no invocation record, so the observation store (and the doctor's hook-execution check that reads it) never saw this leg run; port: fixed (the row reads the payload within the guard's 1 MiB bound, leaves the metadata-only record `pre-tool-use-github-post` for the session before the guard judges, then judges. The record keeps no payload and decides nothing; a payload over the bound, one that is not JSON with a usable session id, and a leg cancelled before its input arrived leave none, and the answer of each is what it was: the deny for an over-bound or cancelled leg, the guard's own answer otherwise. A payload that arrives after the leg was cancelled is neither recorded nor judged, because the leg has already answered the deny. Pinned by TestGitHubPostGuardLegLeavesObservation and TestGitHubPostGuardLegLeavesNoObservationForInputThatArrivesAfterCancel in `cmd/crw/component_hooks_test.go` (red on 6a5851f4f; the late-input case waits on the input goroutine, not a sleep).)
