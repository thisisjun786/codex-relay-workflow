# CRW-1101 — hook transport failures and explicit protection policy

Source: CXC v0.2.40 `pabcd-state/src/cli.ts:83-117`; port:
`internal/harness/envelope.go`, `hook.go` and `legs.go`.

- Read errors used to discard a valid prefix and dispatch empty input, allowing
  protection handlers to release without a decision. port: fixed. `ReadInput`
  distinguishes success, overflow and read error and never exposes failed data.
- Slug-based overflow handling missed the managed deletion guard. port: fixed.
  Each leg declares its input failure policy. PreToolUse Guard and FailClosed
  legs deny with a native envelope and exit 0 regardless of recording slug.
  Advisory and Permission legs release silently; Stop overflow blocks remain.
- Both failures precede observation, state and handler work. Successful empty
  input, JSON decoding and first-interrupt status 130 retain their existing paths.

`TestGuardInputFailuresDenyBeforeEffects` tests EIO after a valid prefix,
a directory fd, overflow and renamed slugs for deletion, memory, automation
and goal-complete legs. `TestAdvisoryInputFailuresReleaseBeforeEffects` covers
SessionStart, edit advisory and PermissionRequest. The recorded oracle corpus
remains intact; CRW-415's claims now describe the two changed overflow fixtures.

The actual GitHub post protection is a separate component row, registered in
`cmd/crw/component_hooks.go`, not the automation ownership row in harness.Legs.
`hook.GitHubPostAnswer` already bounds physical input at 1 MiB+1 and denies
overflow, but returned silence on read failure. port: fixed (CRW-owned ingress,
not an oracle divergence): read failure returns the same native unreadable-post
deny. `TestGitHubProtectionIngressFailuresDeny` checks prefix+EIO, EISDIR and
overflow through the real component registration, with exit 0. Its cancellation
deny and successful empty/malformed-input behavior remain unchanged. Keeping the
reader in hook avoids an import cycle with harness, which imports the handlers.
