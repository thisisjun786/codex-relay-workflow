# CRW-385 — chat orchestrate command handler (D3a)

Source: CXC v0.2.40 (`3c1459ac`) `plugins/codexclaw/components/pabcd-state/src/hook.ts` `handleOrchestrateCommand` :860-874, :896-937, :1287-1300 and :1355-1399, with `chatPlanBinding` :105-126 and `mintCheckEpoch` :128-130, ported to Go as `internal/pabcd/hook/prompt_orchestrate.go` with the chat-command cases of `hook.test.ts` as `internal/pabcd/hook/prompt_orchestrate_test.go`. The four corpus fixtures this range drives (`chat_orchestrate_p_enters_plan`, `chat_orchestrate_a_free_pass_from_p`, `chat_orchestrate_illegal_edge_refused`, `codexclaw_cxc_override_in_directive`) replay identical and are claimed in `contract/notes/cxc/CRW-385.json`.

- The command reads the session state unlocked, changes fields and writes the whole state back unlocked (source :861 `state` argument against the write at :1360 and :1378), so an update a participating writer - another hook of the same session, the memory gate, the idle-edit counter - lands between the two is overwritten by the stale copy and lost, and the write-back rebuilds the state from the reader's normalised value, so a stored record the reader cannot keep is lost with it; port: fixed (a data-loss defect, the class the parity rule revision of 2026-10-03 fixes during the port: the write goes through `promptSubmitWriteState`, which holds the session lock, re-reads strictly, re-applies the transition to that read and refuses the whole command when the state moved or the rewrite would not keep a stored record; `TestPromptOrchestrateKeepsAParticipatingWritersUpdate`, `TestPromptOrchestrateRefusesARewriteTheReaderWouldLose`).
- The command's contract says it returns null or the context, yet three paths of the ported range let an exception escape: the source resolution of every verb but status and reset (:875), the B entry capture (:1291) and the B>C capture (:929); port: fixed (the Go port has no throw, so the resolver's error is answered with the SOURCE-ROOT refusal that names it and a failed capture refuses the command with nothing written, rather than the silence cli.ts gives a throw; `TestPromptOrchestrateSourceRootRefusal`).
- The state write's "the session state changed" refusal is a port addition, not an oracle behaviour: the oracle has no such check and would have applied the command to the state it read, which is the loss above; port: fixed (the refusal text is the one the issue fixes, and the command writes nothing at all when it fires).
- The `keepBinding` arm of the plan binding (:1298) and the "staying in C" arm of the check epoch (:1372) can never run from a chat command: no legal chat edge is A>A or C>C, so a session at A or C reaches neither through `handleOrchestrateCommand`; port: kept (both are ported as they are, in `promptOrchestrateFields`; the staying-in-C arm is reachable only from the field builder itself, which `TestPromptOrchestrateCheckEpochIsMintedKeptAndDropped` drives directly).
- The bound D-close (:939-1429) is not ported by this issue: `promptOrchestrateBoundDclose` answers unhandled, so a bound `orchestrate D` in chat falls through to the loose detector and injects the phase directive for the phase the session is in while the close is silently not applied - the same shape the seam had on `dev` before this issue; port: pending (the successor issue that ports the bound D-close fills the seam; `TestPromptOrchestrateBoundDCloseHandsToTheSeam`).
- The D-close recovery branches (`matchesDcloseRecovery`, :884-895 and the recovery arms of :980-1270) are not ported here either, so a session carrying a `dcloseRecovery` marker gets the ordinary path's treatment on the chat surface; port: pending (the issue that ports the D-close recovery branches closes it).
- The `noop` field of `ApplyResult` reaches the persisted state through the oracle's `{ ...result.state, ... }` spread, so the oracle's state file can carry a stray `noop` key on a `done` write; port: kept (the port's `state.State` has no such field, so the key is not written; no recorded fixture observes it and nothing in the oracle reads it).
