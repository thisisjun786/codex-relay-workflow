# CRW-1268 — the F05 follow-up: a call is claimed or superseded, `crw flow recover` in the shipped binary, and the turn count of a new attempt

Source: CRW's own design (0.5.0-alpha, issue F05 and its last verification of CRW-1198 at caad2558), not the CXC oracle. The Go side is `internal/flow/engine/{engine,resume,recovercli}.go`, `internal/flow/journal/recoverenv.go` and `cmd/crw/main.go`; the tests are in `internal/flow/backend/agent/{reconcile_test,reconcile_fix_test}.go` and `internal/flow/journal/recover_test.go`.

- A resumed script that reached an old position only after an await, while a parallel path started a new attempt on the same node, got two terminal rows for the old call (`superseded`, then `held`) and lost the work: the supersede decision (execute goroutine) and the claim (script loop) were not ordered. Both are now decided under one lock: whichever comes first stands. A claim of a call a new attempt superseded, or is superseding, is refused and the position runs as a call of its own (the same call id, a new `prepared` row, a thread of its own); a new attempt that finds the call being superseded by another waits for that end; a supersede of a call that was claimed is skipped. Pinned by `TestSupersedeAndLateClaimGiveOneTerminalRow`; port: fixed.
- The shipped `crw flow recover` always exited 2 because nothing installed `engine.RecoverEnv`. The binary now installs it (`cmd/crw/main.go`, `journal.RecoverEnv`): the relay store of the run (`--state`, `CODEX_SESSION_RELAY_STATE` or discovery) and the App Server control socket (`--socket` or the default one), the run found by the call (or `--run`), and every row of the recovery committed as it is appended. `RecoverEnv` now takes the request (run, call, state, socket) and returns a setup with the run and a close. Pinned by `TestBuiltCrwFlowRecoverReachesTheStoredJournal` (the built binary accepts a call when the host shows the proof, refuses when it does not, and exits 2 only for a command line, a store or a call it cannot use); port: fixed.
- The two supersede tests did not count turns per operation, and a new attempt keeps the call id of its position and so its `<call_id>/t1` marker, which makes a marker count unable to tell a resend from a new attempt. The marker is kept (the attempt is told apart by the thread: one thread never receives a marker twice, and two threads with the same marker are two attempts) and the tests count `turn/start` per thread and operation: `TestSupersedeInterruptsLiveTurnFirst` and `TestNewAttemptSupersedesAnUnclaimedRunningCall` assert the exact number of requests and one request for each thread and operation, as does the new test; port: fixed (by the test, the marker format is unchanged).
