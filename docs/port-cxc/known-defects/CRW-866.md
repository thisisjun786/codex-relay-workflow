# CRW-866 — the remaining config.toml writers take the CRW lock

Source: CXC v0.2.40, commit `3c1459acadeb1906d97c00a598e1457327ae372d` —
`plugins/codexclaw/components/config-guard/src/config-set.ts` (`applyManagedKey`, :64-159, the
read at :87 and the backup-then-write at :102-103 / :133-135),
`.../src/deactivate.ts` (`deactivate`, pass 1, the read at :61 and the write at :155) and
`.../src/multi-agent-v2.ts` (`setMultiAgentV2State`, the read at :49, the pre-image at :102, the
post-image at :106 and the repair write at :109). Port:
`internal/runtime/install/configguard/configset.go` (`ApplyManagedKey`),
`internal/runtime/install/configguard/deactivate.go` (`Deactivate`,
`deactivateTableKeys`) and `internal/runtime/install/configguard/multiagentv2.go`
(`SetMultiAgentV2State`).

## Defects

- The oracle's `applyManagedKey` read config.toml, computed the new document and wrote it back with
  no lock, so a `retrust` or an activation that published between its read and its write was
  overwritten with content built from the pre-change bytes and neither command reported it (source
  `plugins/codexclaw/components/config-guard/src/config-set.ts:87,102-103,133-135`); port: fixed
  (the issue's answer: `ApplyManagedKey` takes `crwdir.LockConfig` before the read and holds it
  across the read, the decision, the backup and the `activationPublish` of config.toml, the shape
  of `activate.go`'s `activationSetKeyLocked`; pinned by `TestConfigSetTakesTheConfigLock`).
- The oracle's `deactivate` pass 1 read config.toml, restored the owned table keys and wrote the
  result with no lock, with the same lost-update window against retrust and the activation (source
  `plugins/codexclaw/components/config-guard/src/deactivate.ts:61,155`); port: fixed (the drift
  check, the read and the restore are one critical section under `crwdir.LockConfig`; pinned by
  `TestDeactivateTakesTheConfigLock`).
- The oracle's `setMultiAgentV2State` read the pre-image, ran `codex features enable/disable
  multi_agent_v2` (which rewrites config.toml itself) and then published a repair computed from that
  pre-image, all with no lock, so a concurrent CRW writer's publication was overwritten by the repair
  (source `plugins/codexclaw/components/config-guard/src/multi-agent-v2.ts:49,102,106,109`); port:
  fixed (the pre-image read, the injected runner, the repair and its publish are one critical section
  under `crwdir.LockConfig`; pinned by `TestMultiAgentV2SetTakesTheConfigLock`).
- The oracle's `applyManagedKey` read the install manifest before it wrote anything, so two
  overlapping commands each built their ownership record from the manifest the other had already
  replaced: the later manifest describes a value that is no longer live and a later `unset`
  restores the wrong prior value (source
  `plugins/codexclaw/components/config-guard/src/config-set.ts:37,44,64-159`); port: fixed
  (CRW-866's review: the manifest read, its update and its publish are inside the same critical
  section as the config.toml read-modify-write, so the record is never built from a stale manifest —
  failure class 3, the check-then-act race; pinned by
  `TestConfigSetReadsTheManifestInsideTheLock`).
- The oracle's `deactivate` restored the owned keys and only then ran the `codex features disable`
  calls, which rewrite config.toml themselves, so a CRW writer that published between the restore and
  the CLI's own read-modify-write had its change discarded by the CLI (source
  `plugins/codexclaw/components/config-guard/src/deactivate.ts:155-190`); port: fixed (the injected
  CLI calls that rewrite config.toml are inside the same critical section as the restore; pinned by
  `TestDeactivateTakesTheConfigLock`). The lock is taken only when the command will write
  config.toml, so an uninstall with nothing to restore and no flag CRW enabled is not gated on it
  (pinned by `TestDeactivateWithNothingToWriteTakesNoLock`), and an explicitly empty config path
  names no file and gets no sidecar (pinned by `TestEmptyConfigPathTakesNoLock`).
- The activation's own `codex features enable` calls (`activate.go`'s `Activate`, :201-213) run
  before `activationSetKeyLocked` and rewrite config.toml outside the sidecar lock, so a CRW writer
  that publishes during one of them has its change discarded by the CLI (source
  `plugins/codexclaw/components/config-guard/src/activate.ts`); port: pending (found by CRW-866's
  Codex review. `activate.go` is CRW-844's file and outside this issue's edit region, so the same
  boundary this issue widens for the three writers it names is left un-widened there; the follow-up
  is named in the pull request's handoff).

## Supersedes

- Supersedes known-defects/CRW-844.md, section "Guarantee statement (CRW-844, carried verbatim from
  the issue body)", item beginning "(a) Between CRW writers that take the lock": now port: fixed
  (CRW-866 completes the guarantee for the writers it names. CRW-844's sentence claimed the CRW
  writers of config.toml are serialized, but only retrust and the activation took the lock;
  `configset.go`, `deactivate.go` and `multiagentv2.go` now take it, each holding it across its
  whole config.toml read-modify-write and the injected `codex` CLI calls that rewrite the same file
  within that command. The activation's own `features enable` calls remain outside the lock, the
  pending defect above).
- Supersedes known-defects/CRW-844.md, section "Defects", item beginning "The oracle had no lock, so
  two of its writers could interleave": now port: fixed (the sidecar lock is taken by retrust, by the
  activation and, with CRW-866, by `ApplyManagedKey`, `Deactivate` and `SetMultiAgentV2State`;
  pinned by the tests above beside CRW-844's
  `TestHookTrustRetrustCASRefusesWhileAnotherWriterHoldsTheLock` and
  `TestActivateTakesTheConfigLock`).
