# CRW-1074 — loop steer, memory allow-write and scan record end on the first SIGINT

Source: CXC v0.2.40 (`3c1459ac`) `plugins/codexclaw/components/pabcd-state/src/cli.ts` :143-189 (the terminal rows), `goalplan-cli.ts`
`runSteer` :296-352, `memory-cli.ts` and `scan-cli.ts` `runScanCli` :211-417. Ported to Go as `internal/pabcd/cli/loop_mutate.go`
(`loopSteer`, `loopReadBatch`), `internal/pabcd/cli/memory.go` (`RunMemoryCLIContext`), `internal/pabcd/cli/scan_record.go`
(`RunScanCliContext`), `internal/pabcd/goalplan/lock.go` (`GoalplanWriteLockOptions.Context`) and the `loop`, `memory` and `scan` rows of
`internal/harness/pabcd.go` / `internal/harness/pabcd_cli.go`. Found by the oracle-based review of the 0.2.40 port on 2026-10-10 (U07-001, U08-01).

- The oracle's terminal branch is a short-lived process with no signal handler: the first SIGINT ends it at once with empty streams and nothing
  written. The port's `loop`, `memory` and `scan` rows were registered with `Run`, so the invocation context `cmd/crw serve` cancels on the
  first SIGINT never reached them. `loop steer --batch-json /proc/self/fd/0` on an unfinished pipe stayed in `os.ReadFile` and, once `x` and
  EOF arrived, printed a JSON error and exited 1; `memory allow-write` and `scan record` waited out a session lock the test then released
  (`state.WithSessionLock` used `context.Background`) and published `memoryWriteGrant`, or the tracker and the `scan_completed` row, with
  exit 0 (port-introduced, not an upstream defect: the lock and the context are this port's own); port: fixed (the three rows take
  `RunContext`, as the orchestrate row does since CRW-871. `memory` and `scan` pass the context to `state.WithSessionLockContext` and read it
  once more with the lock held, immediately before the first write: the grant write, and the `scan_completed` append. `loop steer` reads its
  batch under the context, in a goroutine so a blocked pipe does not hold it, takes the goalplan write lock with the new
  `GoalplanWriteLockOptions.Context` (the wait ends with the context, and the context is read once more with the lock held and the plan read,
  before the steering transaction's first write, which the transaction re-reads once more after the batch is prepared, immediately before the plan write). In all three, an ended context takes precedence over every answer reached before the first write began, refusal or error alike: a malformed batch, a symlinked plan, a lock or path error, or an unreadable, interview or verdict refusal of the session state read under the lock. A run they end answers `Interrupted` (130) with nothing printed and nothing written; one
  already past its first write finishes and answers as before. Every uninterrupted run, and every other caller of these functions, is
  unchanged). The result matches the oracle, so this is not a recorded deviation.
- Supersedes `known-defects/CRW-758.md`, item beginning "The row is registered with `Run`": the `memory`, `scan` and `loop steer` rows now
  take the context (port: fixed, above). The other mutating loop verbs (add-criterion, add-work-phase, add-task, complete-task,
  meet-criterion, ask, decide) and the `freeze`, `plan`, `evidence`, `review-round`, `reset` and `config` rows are still `Run` rows; port: pending.
