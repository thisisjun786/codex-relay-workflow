# CRW-1178 — a pycache locked out repeated test runs, and unreadable refusals read as policy refusals

Source: the CRW memory and GitHub post guards, and CXC v0.2.40 `memory-write-gate.ts` (the oracle has no command reader and never refused these commands). Go files of the port: `internal/pabcd/shellir/modules.go`, `env.go`, `shellir.go`, `internal/pabcd/hook/memorygate.go`, `memorygate_analysis.go`, `githubpost.go`, `githubpost_judge.go`. Found by the isolated trial r2 (S2R2-F1, S2R2-F2, S2R2-F5, S3-R2-F1).

- The module inventory of `python3 -m unittest` and `-m pytest` refused every `.pyc` under the working directory with a fixed text, so a run that left a `__pycache__` locked out every later run (`-B`, `PYTHONDONTWRITEBYTECODE=1` and `env PYTHONDONTWRITEBYTECODE=1` forms included) in both guards with no cause and no way past it; port: fixed in the wording, the decision kept (a deviation from the issue's plan, which skipped the cache of a readable source). Python loads a cache entry instead of its source whenever the entry's header agrees with the source (a timestamp entry with the source's modification time and size, or a checked-hash entry with the source's hash), and the header is no proof that the code was compiled from that source: a crafted entry beside a harmless `test_calc.py` runs code the reader never read (it wrote below the memories root in the verification). No property of an entry judged before the run survives the run either: code inside it (a test module or conftest calling `os.utime('calc.py', (T, T))`, or rewriting a source to the recorded size) can make a stale entry current before the module it belongs to is imported, and verification round 8 ran a crafted entry that way end to end in both guards. So every `.pyc` of the inventory stays refused, stale or not, and the reason names the file and the route: `module imports compiled code that is not read (__pycache__/calc.cpython-312.pyc); remove __pycache__ in a separate command first, then run with python -B (PYTHONDONTWRITEBYTECODE=1) so no new cache is written`. After a separate `rm -rf __pycache__`, repeated `-B` runs leave no cache and stay allowed, with a log redirection such as `> out.log 2>&1` too; removing it in the same command (`rm -rf __pycache__ && python3 -B -m unittest`) is refused because the entry is still there when the command is read. A `.pyc` outside a `__pycache__` (the sourceless import path) names the file and says to remove it in a separate command; `.pyd` and `.so` files and links are refused with the file as before. A command that runs `touch` on a module source, or copies or moves a path naming `__pycache__`, before the run is refused as a rewrite of module imports, as before. The reader's reason is bounded at 320 bytes in the hooks (it was 200 in this lane), so the file and the route are never cut.
- `PYTHONPYCACHEPREFIX` makes the interpreter read and write every cache entry under `<prefix>/<physical source directory>/`, even with `-B`, and the inventory never walks there, so a current entry under the prefix ran code neither guard read (verification round 8, end to end, with no `__pycache__` in the project); the reader only modelled the variable as a cache write; port: fixed (security; the gap predates this lane). A module run (`unittest`, `pytest`, `py_compile`, `json.tool`) is refused when the run assigns the variable (`PYTHONPYCACHEPREFIX=... python3 -B -m unittest`, empty included), when the text names it anywhere (`export`, `declare -x`, a plain assignment after `set -a`, `env PYTHONPYCACHEPREFIX=...`, an `eval` or carried text), when a declaration or a variable-setting builtin has a name the reader does not know or builds the name from parts (`export "$N"`, `export ${N}PREFIX=...`, a name reference), when an expansion assigns through such a name (verification round 9: under `set -a`, `N=PYTHONPYCACHE; N+=PREFIX; : ${!N:=../pfx}` exports the variable and ran unread bytecode end to end, though the text never spells it; an indirect `${!N:=x}` or `${!N=x}` is refused, and so is an arithmetic evaluation that may assign a name the text does not spell: bash evaluates a variable's value in arithmetic as an expression of its own, so `x=PYTHONPYCACHE; x+=PREFIX=7; (( x ))`, `[[ x -eq 1 ]]`, `let "$N=7"`, an array subscript, a slice offset or a `declare -i` variable assign it; every name an arithmetic expression reads must hold a value the walk knows that is clear in turn, an expanded target of a parsed arithmetic assignment being a parse error already; `wait -p "$N"`, which assigns a process id to the name `N` holds, is read as a variable-setting builtin), and when the hook's environment sets it to a non-empty value (the memory gate reads its environment; the GitHub guard now reads this one variable from the hook process's environment, every other variable staying unset for it as before). The reason names the cause and the route: `PYTHONPYCACHEPREFIX is set in the environment; the interpreter loads compiled code from that cache, which is not read; unset PYTHONPYCACHEPREFIX in the environment and do not set it in the command, or run python -E -B`. With `-E` or `-I` the interpreter ignores every `PYTHON*` variable, so such a run is judged as before. A text that only spells the name (an `unset PYTHONPYCACHEPREFIX` in the same command included) is refused too, a conservative reading in the manner of CDPATH; a variable-setting builtin with an unknown word (`export PATH="$PATH:/x"` read without an environment) refuses a later module run for the same reason, and so does arithmetic over a name the walk holds no value for (`for ((i=0; i<3; i++))`, `[[ $# -eq 0 ]]`, an associative array key, `declare -i`). The interpreter reads the prefix for every import, the standard library included, so a plain script run (`python3 script.py`) under a prefix is the same exposure; it is outside this issue and left as an open item.
