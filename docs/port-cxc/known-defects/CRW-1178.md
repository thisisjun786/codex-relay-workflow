# CRW-1178 — a pycache locked out repeated test runs, and unreadable refusals read as policy refusals

Source: the CRW memory and GitHub post guards, and CXC v0.2.40 `memory-write-gate.ts` (the oracle has no command reader and never refused these commands). Go files of the port: `internal/pabcd/shellir/modules.go`, `internal/pabcd/hook/memorygate.go`, `memorygate_analysis.go`, `githubpost.go`, `githubpost_judge.go`. Found by the isolated trial r2 (S2R2-F1, S2R2-F2, S2R2-F5, S3-R2-F1).

- The module inventory of `python3 -m unittest` and `-m pytest` refused every `.pyc` under the working directory, so a run that left a `__pycache__` locked out every later run (`-B`, `PYTHONDONTWRITEBYTECODE=1` and `env PYTHONDONTWRITEBYTECODE=1` forms included) in both guards; port: fixed in part, a deviation from the issue's plan. Python loads a cache entry instead of its source whenever the entry's header agrees with the source (a timestamp entry with the source's modification time and size, or a checked-hash entry with the source's hash), and the header is no proof that the code was compiled from that source: a crafted entry beside a harmless `test_calc.py` runs code the reader never read (it wrote below the memories root in the verification). So a `.pyc` is skipped only when it is a stale timestamp entry (`__pycache__/<module>.<tag>[.opt-N].pyc`, the tag letters then digits such as `cpython-312`, flags 0, recorded time or size different from the regular `<module>.py` in the directory above), which the interpreter discards and recompiles from the source the inventory reads. Still refused: a `.pyc` in `__pycache__` whose name is not that shape (`calc.pyc` imports as the sourceless module `__pycache__.calc`, which the interpreter never compares with a source), an entry that agrees with its source, any hash-based entry, a `.pyc` outside a `__pycache__` (the sourceless import path), an entry with no readable source, a short or unreadable header, a link, and `.pyd` and `.so` files; the reason names the file and the route (`cache runs instead of <module>.py; remove __pycache__, use python -B`, after which repeated `-B` runs leave no cache and stay allowed). A command that runs `touch` on a module source, or copies or moves a path naming `__pycache__`, before the run is refused as a rewrite of module imports, and when a stale entry was skipped, any `touch`, `truncate` (or `xargs`, `find`, `parallel` running one, or with words the reader cannot evaluate) read earlier in the same text is refused (`module cache entry is stale only until the command runs touch`), because a time change through another name of a source (a hard link) could make the entry agree with its source after it was judged. With no cache entry skipped these commands are unchanged. Content writes to a source through an alias are not modelled by the module reader (dev has the same gap with or without a cache) and stay outside this entry. Other files below `__pycache__` are inventoried like any file. The decision for every refused shape is unchanged.
- The inventory replaced the walk error with a fixed text and dropped the cause; port: fixed. The reader's own reason now reaches the answer, with the file below the working directory (`module imports compiled code that is not read (foo.pyc: compiled module without a source)`).
- An unreadable program was denied as `[crw MEMORY-WRITE-GATE] ... a protected write has not been established`, and the GitHub guard added `unreadable-github-post; GitHub posting has not been established` for the same non-GitHub command, so one test command drew two policy refusals without a cause; port: fixed. No protected write was observed, so both guards now say `[crw command-reader] Cannot analyze this command (<rule>): <reader reason>` with one alternative (a readable script file; a leaf reports to its parent), and the GitHub guard adds `It names no GitHub post.` when the text spells no gh post. A text that does name a post keeps the GitHub wording and gains the reason. Rule IDs `unreadable-program` and `unreadable-github-post`, the decisions, the one-write grant spending and the leaf routing are unchanged; `MEMORY-WRITE-GATE` stays on every refusal of an observed or unverifiable protected write.
- With no working directory (or no session id, or a relative working directory) the refusal of a memory write offered `crw pabcd memory allow-write` and "remember this", which the gate never reads for such a call (it consults the state only with a session id and a working directory); port: fixed. The reason now says the call carries no absolute working directory and session id, and keeps `use an absolute path` for an unknown edit destination. With an absolute working directory and a session id the grant route is unchanged. The contract note `contract/notes/cxc/CRW-1157.json` records the changed empty-cwd note text.
- A freeform `apply_patch` (the patch text as a bare string `tool_input`) was never judged, while the same patch in `{command: ...}` was; port: fixed (security). The string is now judged as the patch of a record, so a freeform patch into the memories root is refused and a relative target with no working directory is an unknown destination, as for `Write`.
- Whether a GitHub guard refusal is about a post is decided by a shell word that is `gh` or a path ending in `/gh` (quotes and backslashes deleted, so `g""h`, `./gh` and `/usr/bin/gh` count; `high_priority`, `tests/ghost`, `missing/gh.sh`, `tests/gh.py` and the module `tests.gh` do not) in the text the refusal was found in, not by a substring of the outer command or by the outer command for a refusal inside a script; port: fixed. A script file that cannot be read (missing, no permission, too large, in an unknown directory, written earlier in the same command) is the reader's refusal with `script file cannot be read (<name>)` when its command spells no gh command, and keeps the GitHub wording when it does. The wording only; the decisions are unchanged.
- A failure of the operating system in the module inventory (a directory without permission) names the file or directory below the working directory, not only `open: permission denied`; port: fixed.
- `CRW-783.md` (generation 6) said a command word holding an expansion is refused "when the command names a post", against its generation-2 entry and the behaviour; the sentence now says it is refused as unreadable whether or not the text names a post.
- Tests: `TestCRW1178*` in `internal/pabcd/shellir` (untagged or malformed cache names refused, a time change beside a stale entry refused, stale cache of readable sources, a cache that agrees with its source and hash-based entries refused, refused shapes with their causes, source must be a regular file, no same-command refresh of a cache) and in `internal/pabcd/hook` (repeated test run in both guards, a real Python-written cache that runs unread code refused in both guards with the removal route allowed, causes in the wording, no grant route without a cwd, freeform apply_patch, gh substrings and gh file names in paths, unreadable script files, a refusal inside a script, the walk path). `TestCRW1157DenialCauses`, `TestCRW1157UnknownDestinationEditKeepsGrantRoute` and `TestMemoryGateUnreadableProgramDeniesAndSpends` move to the new wording.
