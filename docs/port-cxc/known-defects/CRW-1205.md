# CRW-1205 — the run surface: what the decided design left to the code

Source: CRW's own design (0.5.0-alpha, issue F12), not the CXC oracle: the flow engine has no counterpart in CXC v0.2.40 (commit 3c1459ac). The Go side is `internal/flow/cli` (the commands and the run process), `internal/flow/engine/control.go` (the pause from outside), `internal/flow/journal` (`LoadAfter`, `LoadLean`), `internal/flow/workflows/night-batch.js`, `internal/gui/runs_api.go` with `web/src/pages/Runs.tsx`, `internal/manage/batch_decide.go`, and `docs/relay/dag-scheduler.md`, `docs/flow/` and `plugins/crw/skills/crw-canon/references/flow.md` for the text.

- The body's edit regions do not list the files that a new hook declaration and a streamed GUI route cannot do without; the lane edits them and says so: `cmd/crw/main.go` (the `flow` mode hands the commands of `internal/flow/cli` to it before `shadow` and `lint`), `cmd/crw/component_hooks.go` (the `stop-showing-flow-status` leg) and its declaration test, `internal/dev/cxccorpus/shipped.go`, `internal/dev/laneparity/declare.go` and the counts of the shipped-hook, plugin and parity tests (the hook is one of CRW's own, after the GitHub post guard), `internal/gui/registry.go` and `server.go` (a prefix route for `/api/runs/<id>/...` and a `Response.Stream` for server-sent events), `internal/flow/engine` (`Control`), `internal/flow/journal` (`LoadAfter`, `LoadLean`) and the embedded GUI assets; port: deviation, kept visible.
- `internal/flow/cli` is a package of its own, and the body names `internal/flow/cli/` as an edit region only; CRW-1204 (F11) edits the same directory for `crw flow apply`, `report-up`, `reports` and `report-ack`. The commands are served from one table (`commands` in `cli.go`), so a command is a case more; port: kept.
- The decision record of CRW-718 has no members for the run, the node, the attempt and the question revision (CRW-718 B is not in dev). The binding is spelled in the members the record has (one `plan_node` entry of `blocking`, `<run>/<node>`, and a `source` of kind `flow_question` or `flow_jun_decision` with the ref `<question>@<revision>#<attempt>:<plan basis>`), read in one place (`BindingOf`), so CRW-718 B changes that function and nothing else; the question's revision is the ordinal of its escalation row among those of its node and ask, and the plan basis is the digest of the plan id and revision the run is pinned to; port: deviation, kept visible.
- `crw flow answer` is applied to the journal of a run no process holds (it takes the run lock, so the journal has one writer). A run a process holds is refused with `run_live`; the operator pauses it first. The wait `crw.decide` guards ends the lane's work for the run, so a run that has other lanes going on is paused by the answer's caller, not interrupted by the answer; the body says the answer "resumes only that wait", and the row appended is that wait's only change. Applying an answer does not mark the relay's record `applied`: the journal row is the evidence of the application, as the body says; port: kept.
- `crw flow watch` follows the cursor semantics of `crw relay journal-tail` (the `seq` of the last row, a wait that holds no transaction, a read-only store) over the run's own rows, `flow_calls` and `flow_events`. Those rows are not rows of the relay `journal` table, which `journal-tail` reads, so the command is not `journal-tail --kinds`; port: deviation, kept visible.
- The five preflight facts are read from what the relay records in its store (`StoreProber`): a live scope binding, a lifecycle reading no older than 15 minutes with a delivery that reached a turn, a deliverable thread with authorized settings, the waiting dispositions of the workflow (`crw.decide`, `crw.escalate`, also in the workflows it nests), and a spent delivery wake. The body names the facts and not their readings; these readings are the lane's. A fact that cannot be read fails with its reason. A run is not started over a failed fact unless `--force` is given, which the spec records (`forced`); the body shows the facts before the start and does not say what a failed one does; port: deviation, kept visible.
- The run process opens the world `ProductionWorld` makes (the relay store, the App Server and the allocator, as `crw flow resume` does) and the project lane's operations through `cli.OpsFor`, which nothing in this build installs: the scheduler-backed `ops.Relay` that `internal/flow/ops/seams.go` says belongs to the run process is not in dev. A workflow that calls a `crw.*` operation therefore ends in a script error on the shipped binary until that adapter is installed, and runs on the fake host and the scenario lab (the proofs of this issue); port: deviation, kept visible.
- `crw flow cancel` of a run no process holds appends the finished row (error kind `cancelled`) and returns no execution slot: giving a node's slot back is `AgentClose` with the `flow_cancel` reason (R07), a call the run process makes through the `Closer` seam. The row makes the run `cancelled`; the slots of its nodes are not returned by this command; port: deviation, kept visible.
- A pause interrupts the turns in flight (the engine's pause as a quota stop makes it), so the call in flight ends held `engine_paused`, not completed; `crw flow resume` goes on with it in place. The pause of a run at its deadline is the same pause with the reason `deadline`; port: kept.
- The night batch is the project lane over one milestone whose nodes are exactly the selected issues (`night-batch.js` checks it and releases nothing when it is not). The manager makes that milestone (the plan) and records the decision with `crw manage batch decide`, which refuses a decision without a token budget or with a deadline that passed. The decision is a `policy` record with the batch document as its context and the options `run` and `skip`; the digest cannot say what the journal does not show, so the model providers are reported as not observed; port: kept.
