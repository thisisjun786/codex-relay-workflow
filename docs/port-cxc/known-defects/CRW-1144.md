# CRW-1144 — one physical identity for the Codex home, the CLI and the config lock

Source: CXC v0.2.40, commit 3c1459ac — `plugins/codexclaw/components/config-guard/src/activate.ts` (`configPath` derived with `path.join(codexHome, "config.toml")` at :201) and `multi-agent-v2.ts` (:53-70); the CLI the commands run reads `CODEX_HOME` itself. The Go port is `internal/runtime/install/configguard/codexhome.go` (`ResolveCodexHome`, `configIdentityAfterRunner`), `activate.go` (`Activate`), `multiagentv2.go` (`SetMultiAgentV2State`), `internal/runtime/install/features.go` and `config_cmd.go`. The finding is the 10-10 CXC improvement review A7-09, from the items CRW-899.md and CRW-891.md keep.

- The config path was a lexical join of `CODEX_HOME`, while the CLI was handed the original `CODEX_HOME` and let the kernel resolve it, so a home spelled with a symlink followed by `..` made the CLI edit one config.toml and crw's managed-key edit, backup and manifest describe another (source `activate.ts:201`); port: fixed (`crw install features` and `crw install config` resolve the home once through the kernel, `ResolveCodexHome`, and hand that physical directory to the CLI as `CODEX_HOME` as well as to the edits, the backup, the manifest and the lock. An ordinary symlinked home is followed; a `..` after a directory that does not exist is refused before anything is written. Pinned by `TestFeaturesEnableUsesOneCodexHomeIdentity`, with two sentinel config files, and `TestResolveCodexHome`).
- When the CLI replaced the caller's config.toml during the activation or the multi-agent switch, the command kept publishing under the lock of the file the path named before, so another CRW writer that reached the new file could lock and write it at the same time; port: fixed (after the CLI runs, the directory of config.toml must still be the pinned one, and when the path now names a file the held lock does not guard, the command takes that file's lock too and re-proves it before it publishes. The check runs after every Codex run of the activation, before the next flag is enabled and before anything is published, so no later flag write goes ahead under the lock of the file that was left; a writer that holds it makes the activation wait and then stop without publishing more, with the intent kept for the explicit retry (CRW-1153) to record what the CLI did. Pinned by `TestActivateDoesNotPublishUnderALockItNoLongerHolds` and `TestLockIsCheckedAfterEveryRunnerBeforeTheNextEffect`; the existing hard-link refusal, case-alias and moved-parent tests (`config_lock_paths_test.go`, `config_lock_case_alias_test.go`, `config_lock_restore_identity_test.go`) and `TestConfigLockPathsActivateWritesThroughTheReplacedCallerPath` stay green).
- Supersedes known-defects/CRW-899.md, section "Defects", item beginning "The default config path is derived with `filepath.Join(CODEX_HOME, \"config.toml\")`": now port: fixed (see the first item).
- Supersedes known-defects/CRW-891.md, section "Defects", item beginning "The sidecar lock is keyed by the file the caller's path resolved to": now port: fixed for the window the runner opens (see the second item). An outside process that replaces the path between that re-check and the publish is the same-uid name-operation residual CRW-899 keeps; port: kept.
- The deactivation's own content path and `ApplyManagedKey`'s `lock.Target` (known-defects/CRW-899.md items beginning "The deactivation's own content path" and "`configset.go`") run no CLI between their read and their publish, so the runner window this issue closes does not open there; port: kept (unchanged).
- The deactivation ran its `codex features disable` calls one after another under the lock it took first, so a disable that replaced the linked config.toml left the next disables, and the manifest release, running while another CRW writer held the lock of the file the path named now; port: fixed (after every disable and after the read-back the deactivation re-proves the lock the activation re-proves, through the caller's spelling of config.toml: the directory must be the pinned one, and a file the held lock does not guard is locked too, or the deactivation stops before the next disable, releases nothing and keeps the ownership for a retry. Pinned by `TestDeactivateRechecksLockBeforeNextRunner`).
