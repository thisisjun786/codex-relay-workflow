# CRW-939 — skill-scripts-node changed-path check and the Node-run exception

Source: these are not oracle behaviours. They are defects of this repository's own CI, found while
evaluating the job CRW-353 added against CXC v0.2.40 (commit `3c1459ac`), whose own gate the job
follows. The port's files are `.github/workflows/ci.yml` (the `skill-scripts-node` job: its
checkout and its "Decide from the changed files whether the staged skills changed" step) and
`internal/dev/ci/workflow_test.go` (`pythonInWorkflow` and the tests that hold the job).

## Defects

- The job's changed-path check compared a pull request's base tip with its head directly
  (`git diff --name-only "${base}" "${head}" -- "${SKILLS_ROOT}"`), so a staged-skill change that
  only the base branch carried read as this pull request's, and a branch that carried the same
  staged-skill change as its base read as no change at all, ending the job before it installed Node
  and ran the tests (source: the two-tip comparison, not the oracle's shape; `.github/workflows/ci.yml`
  before this issue); port: fixed (a pull request is compared from its merge base with the three-dot
  range `"${PR_BASE_SHA}...${PR_HEAD_SHA}"`, a push still compares the commit it replaced with the
  one it added, a manual dispatch still runs the tests, and the job's checkout already fetched full
  history; pinned by `TestWorkflow_the_skill_paths_compare_a_pull_request_from_its_merge_base` and
  `TestWorkflow_the_skill_paths_keep_the_push_range_and_run_on_a_dispatch`).
- The workflow detector admitted a path below a skills root, and a skills-root value, in any
  workflow whose job happened to be named `skill-scripts-node`, because it tracked the job name
  alone and never the file, so a second workflow could run a skill script by copying the job's name
  (source: the name-only exception, not the oracle's shape; `internal/dev/ci/workflow_test.go`,
  `pythonInWorkflow` before this issue); port: fixed (the exception is keyed by file and job
  together — `.github/workflows/ci.yml`'s `skill-scripts-node` — pinned by
  `TestWorkflow_the_skill_scripts_exception_is_one_file_and_one_job`,
  `TestWorkflow_a_copied_skill_scripts_node_job_in_another_workflow_is_a_finding` and the
  `TestWorkflow_python_detector` rows).
- The broadened job-key reader reset the exception by skipping the line it matched, so the line's
  own content was never read: a workflow-level `env:` value whose key is `skill-scripts-node`, and
  a one-line flow job, share the two-space key shape and either can name or run a skill path
  (source: the detector's own reset, not the oracle's shape; `internal/dev/ci/workflow_test.go`,
  `pythonInWorkflow` before the second generation-2 correction, found by the pre-merge evaluation
  of head `aa9a6785`, item d1); port: fixed (the reader now resets the exception and still reads
  the line; pinned by the two extra rows of
  `TestWorkflow_every_yaml_job_key_resets_the_skill_scripts_exception`).
- The `--help` replacement check treated Python's execution order as the file's line order, reading
  only the lines above the textual `parse_args()`. That call sits inside `main()`, so a module-level
  import placed after it in the text still runs before the parse and makes `--help` fail without the
  parser deps (source: the check's own scope, not the oracle's shape;
  `port/cxc/skills/crw-repo-map/tests/repo-map-packaging.test.mjs`, `parserImportsBeforeParsing`
  before the second generation-2 correction, found by the same evaluation, item d2); port:
  fixed (the check now reads each line's code with strings and comments stripped and defers an
  import only inside a `def`/`class` body placed after the parse).
- A `skills-root` value under a quoted key was not seen, so a workflow could put
  `"SKILLS_ROOT": port/cxc/skills` in an `env:` and run the staged skill tests through the
  variable with no finding (source: the key pattern, which accepted only a bare key; unchanged from
  before this issue, but inside the exception boundary this issue owns;
  `internal/dev/ci/workflow_test.go`, `skillRootValue`, found by the pre-merge evaluation of head
  `7adfa1127`, item d1); port: fixed (the key may be a bare, single- or double-quoted name; pinned by
  the two quoted-key rows of `TestWorkflow_python_detector`).
- The jobs-block scope treated a column-0 comment as a top-level key, which ended the admitted job's
  exception and reported that job's own test run: YAML reads a `#` at column 0 as a comment, and a
  blank line is not a key either (source: the scope this issue added; `internal/dev/ci/workflow_test.go`,
  `pythonInWorkflow`, found by the pre-merge evaluation of head `7adfa1127`, item d2); port: fixed
  (a comment or a blank line leaves the scope alone; pinned by the comment and blank-line cases of
  `TestWorkflow_every_yaml_job_key_resets_the_skill_scripts_exception`).
- The `--help` check decided whether an import was deferred from its indentation alone, so an import
  under a module-level `if`/`try`/`with` after the parse — which runs while the module loads, before
  `main()` — was passed (source: the check this issue added;
  `port/cxc/skills/crw-repo-map/tests/repo-map-packaging.test.mjs`, `parserImportsBeforeParsing`,
  found by the pre-merge evaluation of head `7adfa1127`, item d3); port: fixed (the check walks the
  enclosing blocks and defers an import only inside a `def` body -- the `class` half of that rule
  was itself wrong and is corrected in the last entry of this list; pinned by
  `the parser-import check reads module-level imports placed after the parse`, with the deferred
  import and the real file's `try` shape as its controls).
- The skills-root assignment check required the colon directly after the key, so a blank before the
  colon -- which YAML reads as the same assignment (`SKILLS_ROOT : port/cxc/skills`) -- carried the
  root past the check, and a job outside the one admitted pair could then run the staged skill tests
  through the variable with no finding (source: the key pattern, which accepted no blank before the
  colon; unchanged from before this issue, but inside the exception boundary this issue owns;
  `internal/dev/ci/workflow_test.go`, `skillRootValue`, found by the pre-merge evaluation of head
  `2681d645`, item d1); port: fixed (a run of blanks before the colon is accepted for a bare,
  single- or double-quoted key; pinned by the two blank-before-colon rows of
  `TestWorkflow_python_detector`).
- The `--help` replacement check treated a `class` body as deferring an import the way a `def` body
  does, but a module-level class statement runs while the module loads, so an optional parser import
  in a module-level class body placed after the parse still ran before `main()` and broke `--help`
  without the parser deps (source: the check this issue added;
  `port/cxc/skills/crw-repo-map/tests/repo-map-packaging.test.mjs`, `deferredImport`, found by the
  pre-merge evaluation of head `2681d645`, item d2); port: fixed (a `class` header is stepped over
  like `if`/`try`/`with`, and only a `def` defers an import; pinned by the class cases of
  `the parser-import check reads module-level imports placed after the parse`).
- The Node-test detector required `--test` immediately after the `node` word, so a run with any
  option between them (`node --no-warnings --test`) named neither a skill path nor a skills root and was
  admitted outside the one file and job (source: the option-free pattern; unchanged from before this
  issue, but inside the exception boundary this issue owns; `internal/dev/ci/workflow_test.go`,
  `nodeTest`, found by the pre-merge evaluation of head `338a75f3`, item d1); port: fixed (options
  are allowed between the word and the flag, and a node binary named by path is read too; pinned by
  the option rows of `TestWorkflow_python_detector`).
- The `--help` replacement check treated every typed `except` clause as deferring, but a handler
  that can catch the `SystemExit` argparse raises for `--help` runs while it unwinds --
  `except SystemExit`, `except BaseException` and a tuple naming either (source: the check this issue
  added; `port/cxc/skills/crw-repo-map/tests/repo-map-packaging.test.mjs`, `deferredImport`, found by the
  pre-merge evaluation of head `338a75f3`, item d2); port: fixed (a clause that can catch it does not
  defer, one that cannot -- the real file's `except ImportError`, or `except Exception` -- still does,
  and a clause the reader cannot fully read counts as catching it; pinned by the handler cases of
  `the parser-import check reads module-level imports placed after the parse`).
- The new `the emitted receipt binds the bytes on disk` case carried a tautology of the form
  `assert.equal(resolve(a), resolve(a))`, which can never fail and blurred what the case holds (source:
  this issue's own test, found by the independent review of head `338a75f3`, a P3); port: fixed (the
  line is gone; the relativity the comment describes is held by the `startsWith("/")` assertion beside it,
  and the case's other assertions are unchanged).
- The exception boundary was enforced only through a skill path or a skills-root value, so a job that
  ran `node --test` without naming one -- a bare run that discovers the staged test files itself,
  or a root passed through an `export` prefix or an assignment sharing its line -- was admitted in
  any workflow and any job (source: the path-based detector, unchanged from before this issue, but
  inside the exception boundary this issue owns; `internal/dev/ci/workflow_test.go`, `pythonInWorkflow`,
  found by the pre-merge evaluation of head `5e74ab2d`, item d1); port: fixed (the run statement
  itself is read, and a root value is accepted after an `export`/`readonly`/`declare`/`local`
  prefix or with trailing text; pinned by the bare-run rows of `TestWorkflow_python_detector` and the
  admitted job's own bare-run control).
- The `--help` replacement check treated a `finally` body and a bare `except` clause as
  deferring an import, but both run while the parse unwinds: argparse answers `--help` by raising
  `SystemExit`, which a bare `except` catches and a `finally` runs through, so an optional
  parser import there still breaks `--help` without the deps (source: the check this issue added;
  `port/cxc/skills/crw-repo-map/tests/repo-map-packaging.test.mjs`, `deferredImport`, found by the pre-merge
  evaluation of head `5e74ab2d`, item d2); port: fixed (neither block defers an import; the real
  file's `except ImportError` cannot catch `SystemExit` and still defers; pinned by the
  `finally`/bare-`except` cases and the `except ImportError` control of `the parser-import check reads module-level imports placed after the parse`).
- The skills-root assignment check read a key only at the start of a line, so a skills root declared
  in a YAML flow mapping -- `env: {SKILLS_ROOT: port/cxc/skills}` -- was not seen, and a job outside
  the one admitted pair could then run the staged skill tests through the variable with no finding
  (source: the key pattern's line anchor; unchanged from before this issue, but inside the exception
  boundary this issue owns; `internal/dev/ci/workflow_test.go`, `skillRootValue`, found by the
  pre-merge evaluation of head `cef8dfa5`, item d1); port: fixed (the pattern also accepts a key
  after `{` or `,`, and a value that ends at `,`, a blank or `}`; pinned by the two flow-
  mapping rows of `TestWorkflow_python_detector`).
- The `--help` replacement check read an import only when the whole line began with `from` or
  `import`, so an import on a line that carries another statement first -- `os = 1; import networkx`
  or `if True: import networkx` -- was passed, though both run before the parse and break `--help`
  without the parser deps (source: the check this issue added;
  `port/cxc/skills/crw-repo-map/tests/repo-map-packaging.test.mjs`, `parserImportsBeforeParsing`,
  found by the pre-merge evaluation of head `cef8dfa5`, item d2); port: fixed (the check splits each
  line into the statements it carries and reads every one of them; pinned by the shared-line cases of
  `the parser-import check reads module-level imports placed after the parse`).
- The skills-root assignment check read a key only at the start of a line, so a skills root written
   as the body of a YAML block scalar (the bare value line of `SKILLS_ROOT: |`) was not seen, and a
   job outside the one admitted pair could then run the staged skill tests through the variable with
   no finding (source: the key pattern's line anchor; unchanged from before this issue, but inside
   the exception boundary this issue owns; `internal/dev/ci/workflow_test.go`, `skillRootValue`,
   found by the pre-merge evaluation of head `dfc1ac89`, item d1); port: fixed (a line that is
   nothing but a skills root, an optional trailing slash and an optional comment is the same value;
   pinned by the block-scalar rows of `TestWorkflow_python_detector`).
- The `--help` replacement check treated any import inside any function body as deferred past
   the parse. Only the function that calls `parse_args()` defers its imports: a helper defined
   beside it runs when something calls it, which may be before the parse, so a parser import there
   still breaks `--help` without the deps (source: the check this issue added;
   `port/cxc/skills/crw-repo-map/tests/repo-map-packaging.test.mjs`, `deferredImport`, found by the
   pre-merge evaluation of head `dfc1ac89`, item d2); port: fixed (the walk takes the nearest `def`
   above the import and defers it only when the `parse_args()` line lies in that same body;
   pinned by the helper cases of `the parser-import check reads module-level imports placed after the parse`).
- The skills-root assignment check read a root only when the key and the value shared a line, so a
  root written as a YAML block scalar's body (`SKILLS_ROOT: >-` with the root on the next line) or
  moved into a shell variable (`root=port/cxc/skills`) was not seen, and a job outside the one
  admitted pair could then run the staged skill tests through the variable with no finding (source:
  the key-and-value-on-one-line shape; unchanged from before this issue, but inside the exception
  boundary this issue owns; `internal/dev/ci/workflow_test.go`, `skillRootValue`, found by the
  independent review of head `cef8dfa5` and the pre-merge evaluation of head `dfc1ac89`,
  item d1); port: fixed (a line that is a skills root, an optional trailing slash and an optional
  comment is read whether it stands alone or follows a shell assignment; pinned by
  `TestWorkflow_a_skills_root_split_across_lines_is_still_a_finding` and the block-scalar rows of
  `TestWorkflow_python_detector`).
- The `qa-validate-evidence.test.mjs` port claimed that three oracle cases dropped with the
  TypeScript modules were covered by `internal/pabcd/gate/receipt_test.go`. Those Go tests build
  their receipts in Go, so nothing read the bytes `validate-evidence.mjs` itself writes back
  through the gate parser: a disagreement between the script's output and the parser would have
  stayed green (source: this issue's port, found by the independent review of head `cef8dfa5`);
  port: fixed (the case that can be checked in Node -- the emitted manifest binds the bytes on disk,
  the digest and the criterion IDs -- is kept in the port, and the header and the PR body state the
  split instead of claiming an equivalent; pinned by
  `the emitted receipt binds the bytes on disk, and an edit shows up`).
- The skills-root assignment check accepted a shell assignment only when the root stood unquoted, so
  `root="port/cxc/skills"` carried the root past it, and a job outside the one admitted pair could run
  the staged skill tests through the variable with no finding (source: the unquoted-value shape;
  unchanged from before this issue, but inside the exception boundary this issue owns;
  `internal/dev/ci/workflow_test.go`, `skillRootValue`, found by the pre-merge evaluation of head
  `a4e8d080`, item d1); port: fixed (the value may be single- or double-quoted, before or after the
  `=`; pinned by the quoted-assignment rows of `TestWorkflow_python_detector` and by
  `TestWorkflow_a_skills_root_split_across_lines_is_still_a_finding`).
- The `--help` replacement check closed a Python string at the next quote even when a backslash
  escaped it, so the real closing quote opened a second string and the rest of the line was dropped:
  an optional parser import after an escaped quote disappeared before the check read it (source: the
  check this issue added; `port/cxc/skills/crw-repo-map/tests/repo-map-packaging.test.mjs`, `codeLines`,
  found by the pre-merge evaluation of head `a4e8d080`, item d2); port: fixed (a string ends at the
  next quote that is not preceded by an odd run of backslashes; pinned by the escaped-quote cases of
  `the parser-import check reads module-level imports placed after the parse`).
