# CRW-1328 — the release gate reads the end condition, the record counts the tests, the flow path records the gate

Source: CRW's own design (the field trial of 10-13, items 35, 44 and 24 of CRW-1315), not the CXC oracle: CXC v0.2.40 (commit 3c1459ac) has no release gate over an issue body and no verification record. The Go side is `internal/skill/issue_ready_command.go` (`endConditionWarnings`, `goTestWarnings`, `fixedRunPattern`), `internal/skill/issue_ready.go` and `issue_ready_export.go` (`warnings`, `ReadyVerdict.Warnings`), `internal/dev/ci/local_testcount.go` and `local_record.go` (`testPackagesRun`), `internal/dev/ci/local.go` (the step's output), `internal/flow/ops/verify_ci.go`, `seams.go`, `lane_build.go` and `finalgate.go` (`TestPackagesRun`, `no_tests_run`), `internal/flow/compile/input.go` (`description`, `labels`) and `internal/flow/cli/issue_ready_fact.go` and `start.go` (the fact `issue_ready`); the skill text is `plugins/crw/skills/crw-add-issue/SKILL.md` and the references are `docs/flow/script.md`, `docs/CI.md` ("The verification record") and `plugins/crw/skills/crw-canon/references/flow.md`.

- `crw skill issue-ready check` read only that the done condition names a command and a result, so an end condition that passes having run no test (`go test ./internal/dev/ci` without `-tags dev`, CRW-1294; a `-run` that matches nothing, CRW-1295) was ready; port: fixed (the done condition's `go test` commands are read, never run: a package under `internal/dev` or `cmd/crw-dev` without `-tags dev` and a `-run` pattern that does not name its tests literally - names joined by `|`, at each subtest level, with optional `^`, `$` and parentheses; a placeholder, a shell variable or a wildcard is not - are each a warning of the report's additive `warnings`, of `ReadyVerdict.Warnings` and of stderr. The decision, its reasons, the exit code 0 of a held answer and the `CheckIssueReady` contract are CRW-1318's. `TestIssueReadyWarnsOnAnEndConditionCommandThatMayRunNoTest`).
- The one real run of the end condition's command (exit 0 and at least one test run) has a place: the design-stage explorer that answers the design's open questions runs it once and records the exit code and the tests it ran, a failure or no test being a warning in the design answer and the issue's record; it is not run when the issue is created and never blocks (`crw-add-issue`, "Check, write, read back"). Port: kept (a skill step, not an executable; no explorer packet carries the command yet, which is the explorer routing's, CRW-1347, and its result is read by the person or the orchestrator who reads the design answer).
- A verification record said whether its steps passed, never whether a test ran, and the flow's gate read only the exit code and the result; port: fixed (verification-record/1 gains the additive member `testPackagesRun`, the go test packages its steps ran tests in, read from the package result lines go test prints: `ok`/`FAIL <package> <time>` ran tests; `[no tests to run]`, `[no test files]`, `[build failed]` ran none. go test prints no per-test count without `-v`, so the count is of packages, and 0 still says no test ran. A record whose steps printed no go test result, and every record written before the member, has none, which `ciRecord`/`VerifyOutcome.TestPackagesRun` read as unknown (nil), never zero, so old records do not warn. A count of 0 is the warning `no_tests_run` on the `crw.verify` row (`test_packages_run`, `warning`) and the result's `warnings`, and the final gate lists it in `warnings` and on its evidence; pass and fail are the record's and the gate's as before. The relay's reader of the record (`dagsched.DecodeVerificationRecord`) decodes leniently and digests the bytes, so the member changes no acceptance. `TestVerificationRecordCountsTheTestPackagesThatRan`, `TestVerificationWithNoTestRunWarnsAndKeepsItsResult`).
- The flow engine never called the release gate: its compile input holds no issue body, so a `not_ready` issue was released on the flow path with nothing recorded (item 24); port: fixed where the handoff carries the body (an issue of `crw-flow-compile-input/1` may carry `description` and `labels`, additive and read by no compiler rule; `crw flow start --handoff` and the start of a night batch judge each issue of the milestone that carries one with `skill.CheckIssueReady`, the one implementation, and a held issue or an end condition warning is the warn fact `issue_ready` with the decision and the reasons, printed and recorded in the run's spec as every preflight fact is (CRW-1318, the recording CRW-1316 follows for its warn facts); the run starts and releases the issue. `TestFlowPathRecordsANotReadyIssueAsAWarning`). Named limit: crw-plan's skill text does not yet tell the planner to put the body in the handoff (that text is CRW-1340's), so a handoff written today carries none and its issues are not judged on the flow path; port: pending (follow-up: crw-plan writes `description` and `labels` of each issue, as it writes `issue_size`).
- The two paths' release rules differ: the flow path warns and records a held issue and releases it, while `crw manage batch plan` (`internal/manage/batch.go:345`) still holds a `not_ready` or `design_first` issue out of the night batch's selection; changing it breaks the batch plan's tests (`TestBatchPlanSelectsOnlyBacklogLabelledReadyIssues` holds CRW-4 and CRW-5 by the gate `ready`), so this lane leaves it; port: deviation, kept visible (follow-up: the night batch selection selects a held issue with its warning recorded beside the selection, and the batch plan tests change with it).
