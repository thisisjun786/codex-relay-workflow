# CRW-869 — bound D-close: ledger reads, published marker and plan writes, busy Stop-budget lock

Source: CXC v0.2.40 (`3c1459ac`) `plugins/codexclaw/components/pabcd-state/src/hook.ts`
`readJsonlObjects` / `hasGoalplanRow` / `hasPabcdCloseRow` :623-645, the bound D-close
`handleOrchestrateCommand` :1137-1286 and the leading section `handleUserPromptSubmit` :656-754,
ported to Go as `internal/pabcd/hook/prompt_dclose.go` and `internal/pabcd/hook/prompt_submit.go`,
with the new cases of `internal/pabcd/hook/prompt_dclose_published_test.go`. No fixture in
`contract/fixtures/cxc` drives a bound chat D-close whose ledger is unreadable, whose marker or plan
write fails after the rename, or whose session lock is busy before the handler runs, so no recorded
case is retagged and `contract/notes/cxc/CRW-869.json` is not created (the CRW-845/CRW-797
convention's empty-claim file would claim nothing and is outside this issue's edit scope).

- `readJsonlObjects` (:623-626) reads its ledger with `readFileSync`, which throws on any read error,
  and `JSON.parse`, which throws on a damaged line, so `hasGoalplanRow` and `hasPabcdCloseRow` throw
  out of the handler and `cli.ts` answers silence: the oracle never treats an unreadable ledger as an
  empty one, and it never appends a row it could not first prove absent. The port's
  `promptDcloseAnyRow` (`internal/pabcd/hook/prompt_dclose.go`) collapsed every `os.ReadFile` error
  into "no row", so a ledger readable by the appender but not by the reader (EACCES from mode 0200,
  which `O_WRONLY|O_APPEND` still accepts) made the second goalplan lock's dedup read the rows as
  absent, append both of them a second time and clear the recovery marker; port: fixed (a record-file
  data-loss defect, the class the parity rule revision of 2026-10-03 fixes during the port: the row
  reads now tell present, absent and unreadable apart, only `errors.Is(err, fs.ErrNotExist)` is
  absent, an unreadable ledger stops the finalization before any append and before the marker cleanup,
  a cycle close answers `promptDcloseFinalizePending(<reason>)` with its marker kept and an all-done
  close answers the success directive plus `promptDcloseLedgerWarning(<reason>)`;
  `TestPromptDcloseUnreadableLedgerKeepsTheMarker`,
  `TestPromptDcloseUnreadablePabcdLedgerWarnsOnAllDoneClose`,
  `TestPromptDcloseAbsentGoalplanLedgerStillGetsItsRows`).
- The oracle's marker write is `writeState(...)` (:1229-1239) and its plan commit is
  `writeGoalplan(...)` (:1242-1245); neither fsyncs a directory, so neither can report a failure after
  its rename and the oracle has no "published but not durable" case at these two call sites. The port
  added the directory fsync and reports a post-rename failure as `*state.PublishedError`
  (`internal/pabcd/state/write.go` :225-234, `internal/pabcd/goalplan/write.go` :330-345), which is a
  path the port made. Both writes answered "Nothing was written" for that error and stopped the close,
  although the artifact was already at its final path; port: fixed (a state-loss defect of the same
  class: `state.Published(err)` on the marker write or the plan write now counts as done, the close
  goes on, and the answer carries the directory-sync warning - the marker keeps
  `promptDcloseWriteLanded`'s session-state sentence, the plan write names the goalplan because it is
  a different file in a different directory;
  `TestPromptDclosePublishedMarkerWriteCompletesTheClose`,
  `TestPromptDclosePublishedPlanWriteCompletesTheClose`,
  `TestPromptDclosePrePublicationMarkerFailureStillRefuses`).
- The mixed-failure path this fix opened: a marker write that published and then failed the
  directory sync, followed by a plan write that failed before its own rename, made the refusal say
  "Nothing was written" although the recovery marker was already on disk; port: fixed
  (`promptDclosePartialRefusal` replaces the refusal's trailing claim with the accumulated
  durability warnings whenever an earlier write of the same close published its artifact, and the
  plain refusal is returned byte for byte when none did;
  `TestPromptDclosePartialRefusalNamesThePublishedMarker`).
- The oracle holds no session lock, so the leading section's Stop-budget stamp (:688-691) cannot fail
  for lock contention; the port runs every session write under `state.WithSessionLock`, which is a
  path the port made. When that stamp could not take the lock it answered `""` and returned before the
  parser path, so a bound `orchestrate D` never reached `promptOrchestrateBoundDclose` and its
  `promptDcloseNotApplied` busy refusal, and the operator saw silence instead of a reason; port: fixed
  (the stamp carries the lock failure's reason out through a new
  `promptSubmitWriteStateReason`, and on a goalplan-bound `orchestrate D` answers
  `promptDcloseNotApplied(<busy reason>)`; every other prompt keeps the oracle's silence;
  `TestPromptDcloseBusyStopBudgetStampAnswersTheBoundRefusal`).
