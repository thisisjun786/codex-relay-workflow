# CRW-879 — the state-copy apply judged a QA receipt by its name and inferred the write count from the destination

Source: the state-copy apply is CRW's own design, [docs/port-cxc/state-migration.md](../state-migration.md)
(the dependency order at :153, the failure output that must record exactly which writes completed at
:154,156, and the M3 slice at :184), and the code is the Go port in
`internal/runtime/install/migrate`: `apply.go` (`writeFiles`, `migrateApplyReviewReferences`,
`migrateApplyReviewSubRank`, `publishFile`) and `publish.go` (`Publish`, `publish`). The receipt the
order is derived from is read by `internal/pabcd/gate/receipt.go` (`ParseSourceBoundReceipt`, whose path
is the caller's chosen name at :104-115) and judged with `internal/pabcd/gate/manifest.go:89-143`
(`artifactManifest` of kinds `verdict` and `artifact-identity`). There is no CXC v0.2.40 oracle file
for this: CXC has no state copy, so the pointer is the design document and the port, and no corpus
fixture is claimed. Both were found by the operator's pair evaluation of the merged state-copy pull
request (thisisjun786/codex-relay-workflow#738, score 4, both P1) and confirmed by the parent on dev
f60a537b at `apply.go:364` and `apply.go:421` (the name test) and at `apply.go:469-472` with
`publish.go:105-112` (the equality test).

- The dependency order judged a receipt by its file name: the manifest scan and the late-publication key
  tested `strings.HasSuffix(source, "qa-receipt.json")`, but the receipt reader takes the name its caller
  chose (`gate/receipt.go:104-115`), so a valid receipt under any other name (`evidence/s/a.json`) and
  the artifact its `artifactManifest` names (`evidence/s/z/verdict.json`) kept the same sub-rank and plan
  order decided, publishing the receipt first; an interruption between the two publications then left the
  reference dangling (source `apply.go:364,421`, the design requires dependencies before their referencing
  records, `state-migration.md:153`); port: fixed (a planned written regular file whose content, read
  within the bound the receipt reader itself applies, is a JSON object with a non-empty
  `artifactManifest` array is a receipt whatever it is called, and both the scan and the ordering key use
  that one judgement; the bound is that reader's own, `gate.ParseSourceBoundReceipt` reading with
  `readFile(path, maxText)` (`internal/pabcd/gate/js.go:19-20`), so the ordering judgement and the
  receipt reader agree on what "cannot be read" means, with the bytes the decoder consumed compared
  against that bound so a trailing whitespace run cannot let a record past it be judged by content; a
  record that cannot be read or is over that bound
  keeps the place the `qa-receipt.json` name gave it, so an unreadable receipt still publishes after its
  dependencies; the cases are
  `TestMigrateApplyReviewFollowupPublishesTheArtifactOfAReceiptUnderAnotherName` for the order the issue
  names, `TestMigrateApplyReviewFollowupDemotesAReceiptUnderAnotherName` and
  `TestMigrateApplyReviewFollowupHoistsTheArtifactOfAReceiptUnderAnotherName` for the two halves of the
  judgement, since either half alone puts the artifact first and would hide the other reverting to the name
  test, and `TestMigrateApplyReviewFollowupKeepsTheNameOrderPastTheReceiptReadBound` with
  `TestMigrateApplyReviewFollowupKeepsTheQaReceiptOrder` and
  `TestMigrateApplyReviewFollowupKeepsPlanOrderWithoutAManifest` for the fallbacks).
- `publishFile` inferred the write count from the destination by equality: it counted a
  `ResultFailed` publication whose destination matched the plan, but `Publish` returns `ResultFailed`
  for a failure before this run's rename as well (a temporary that could not be created or filled), so a
  competing writer that published the plan's same bytes and mode in the window between `settle`'s look
  and this run's own create made a run that wrote nothing count one completed write and report "the final
  file is whole but its directory sync failed" (source `apply.go:469-472`, `publish.go:105-112`; the
  design's failure output must record exactly which writes completed, `state-migration.md:154,156`);
  port: fixed (`publish` reports whether this run's own no-replace rename completed, and `publishFile`
  counts `WritesCompleted` and records the directory-sync note from that flag alone, so a failure before
  the rename is never a write of this run whatever the destination holds while a rename that then lost its
  sync is still counted; the cases are
  `TestMigrateApplyReviewFollowupDoesNotCountAWriteItNeverRenamed` and
  `TestMigrateApplyReviewFollowupCountsARenameThatThenLostItsSync`).

- Defects this issue's own change introduced while it was being reviewed, and fixed here before the
  handoff. They are not CXC or CRW-812 defects: the first pass of the receipt-content judgement and its
  test coverage had them, and each is listed so a reader of this record knows the final shape is not the
  first one.
- The first pass read the manifest through a struct tag, so `encoding/json` matched a case-variant key
  (`ArtifactManifest`) that the receipt reader's own map lookup does not match, and kept the first of
  duplicate keys where the reader keeps the last, so this order could treat a record as a receipt that
  the reader would not (source `apply.go:465-471` at the previous head; the reader looks the key up by
  its exact spelling, `gate/receipt.go:109-140`); port: fixed (the record is decoded to an object and the
  key looked up by its exact spelling, and `TestMigrateApplyReviewFollowupBoundsTheRecordNotTheObject`
  pins the case-variant key as not a manifest).
- The first pass decoded the manifest from the reader with no byte count of its own, so a record that
  grew past the receipt reader's bound after the plan measured it (an object under the bound plus a
  trailing whitespace run, which `json.Decoder` consumes) was still judged by content where the receipt
  reader refuses it (source `apply.go:454-460` at the previous head); port: fixed (the bytes the decoder
  consumed are compared with the bound, and the boundary case fails when that check is removed).
- The first pass decided the receipt by the whole array's conversion, so one entry of an unexpected shape
  (`1`, or an object whose `path` is not a string) refused the receipt and dropped every reference its
  other entries named, publishing it by plan order where the content judgement would have placed it after
  its artifacts (source `apply.go:465-471` at the previous head); port: fixed (the judgement is the
  array's presence and length, and each entry is read on its own, so an entry this order cannot use names
  no dependency and never refuses the receipt; the cases are the `entry of another type`, `entry of the
  wrong shape` and `one good entry and one bad` rows).

- The first pass put a record that another receipt names at the referenced sub-rank before asking whether it was itself a
  receipt, and its own dependency took the same sub-rank, so a chain of receipts kept plan order: the middle record could
  publish before the artifact it names, which is the dangling reference this issue exists to remove (source `apply.go:369-375`
  at the previous head); port: fixed (each record's longest reference chain is the key inside the sub-rank, so a record comes
  after everything it names however long the chain is, and a cycle is broken at the record already on the path; the case is
  `TestMigrateApplyReviewFollowupOrdersAChainOfReceipts`, which fails when the key is removed).
- The first pass read an entry's `path` and `kind` through struct tags, so `encoding/json` accepted a case-variant field
  (`Path`, `Kind`) that the receipt reader's own map lookups do not accept, and a falsely spelled field could name a
  dependency the reader would never use and reorder the publications around it (source `apply.go:539-546` at the previous
  head); port: fixed (each entry's fields are read by their exact spelling, and
  `TestMigrateApplyReviewFollowupBoundsTheRecordNotTheObject` pins the `entry field of another case` row).
- The first pass ordered a chain of receipts by a depth walked from the records in the order Go's map handed them over, so
  a cycle in the receipt graph got one of two keys depending on which record the walk started from, and two runs of one
  plan then published that cycle in two different orders (source `migrateReviewFollowupDepths` at the previous head; the
  report must describe the order a run took, and a rerun of one plan must reach the same one); port: fixed (the walk starts
  from the records in sorted order, so the key a cycle gets is the plan's and not the map's, and
  `TestMigrateApplyReviewFollowupOrdersACycleTheSameWayOnEveryRun` fails when the entry points go back to map order).
- The first pass decoded the manifest from the record's raw bytes, where the receipt reader reads them through the UTF-8
  normalisation it applies (`source.DecodeUTF8`, `gate/js.go:36-53`), so a manifest path holding a byte sequence that is
  not UTF-8 named a file that is not in the plan and dropped the reference the reader itself resolves — the referenced
  record then kept plan order and published after the receipt that refers to it (source
  `migrateReviewFollowupDecodeManifest` at the previous head); port: fixed (the record is decoded from the reader's own
  text, and `TestMigrateApplyReviewFollowupReadsAPathAsTheReceiptReaderDoes` fails when it is decoded from the raw bytes).
- Reading a record as the receipt reader's own text was done by holding the whole record first, and this scan looks at
  every planned file under `evidence/` up to the receipt reader's bound (the size of the largest string the oracle could
  hold): one ordinary artifact of a few hundred megabytes was pulled into memory and expanded into text before the
  judgement found it held no manifest, so a run that had to copy such a file could exhaust memory and never finish its
  copy or its report (source `migrateReviewFollowupDecodeManifest` at the previous head, found by the pre-merge
  evaluation of that head); port: fixed (the record is walked as it arrives and only the `artifactManifest` member is
  kept, so the memory this costs is that member rather than the record; the member is the receipt reader's own text,
  through `source.DecodeUTF8`, so a manifest path holding bytes that are not UTF-8 still names the plan file the
  reader's text holds; a member past the cap this order will hold leaves the record a receipt with no known references,
  which is the place an unreadable record already keeps. The cases are
  `TestMigrateApplyReviewFollowupJudgesALargeRecordWithoutHoldingIt`, which measures the bytes the judgement allocates
  for five 16 MiB records — bytes that cannot be text, a non-object, leading whitespace alone, an object with no
  manifest, and a manifest past the cap — and
  `TestMigrateApplyReviewFollowupReadsAPathAsTheReceiptReaderDoes`, which pins the normalisation end to end).

- Supersedes `known-defects/CRW-812.md`, item beginning "Limitation of the ordering key, not a defect":
  now port: fixed (that paragraph recorded that a receipt under another name "still publishes after the
  other files of its rank", which is what this issue found to be wrong — such a receipt is now judged by
  its content and publishes after the artifacts its manifest names. What the paragraph also said stands:
  a receipt whose manifest this run could not read still takes the referrer's place, and ordering remains
  a dependency hint that never decides what is copied).
