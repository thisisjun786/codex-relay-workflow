# CRW-1380 — a flow run's reports went through send-parent and could not wake the management session above the project

Source: CRW's own design (CRW-1314 §3 and §7, lane D2; two session layers, management and project owner, Jun 10-14), not the CXC oracle (CXC v0.2.40, commit 3c1459ac): the oracle has no flow run and no direct message on the supervisor channel. The Go side is `internal/flow/report` (`relay.go` new: `RelaySender`; `report.go`, `hook.go`, `send.go`, `recipient.go`), `internal/relay/supervisor` (`flow_delivery.go` new: the settle's flow rows; `send.go` settle; `direct.go` the `flow_jun_decision_request` kind) and `internal/flow/cli` (`upward.go`, `report.go`, `world.go`, `apply.go`).

- The run's milestone report, its `project_blocked` report (CRW-1320) and `crw flow report-up`'s reports went through `crw manage send-parent`, which cannot wake an idle or unloaded management thread, and a report that fell to the store seat was recorded and never delivered (D1c d2); port: fixed (`report.RelaySender` stages each report as a direct message through `project:<project>` with its flow kind and the subject `<run>/<report id>`, so the message id is deterministic and a replay is the same message; the recipient is D1c's walk - the management seat, else a legacy lead, else the store seat, which is staged for too; the run hook's escalations and completion digest go the same way as `flow_escalation` and `flow_completion`). Pinned by `TestRelaySenderStagesTheReportForTheManagementSeatAndWritesOnlyQueued`, `TestRelaySenderStagesAStoreSeatReport`, `TestRelaySenderCarriesTheRunHooksNotices`, `TestCRW1320_BlockedRunReportsOnceThroughTheSupervisorChannel` and, over the scripted App Server with the daemon's own tick, `TestFlowReportE2EMilestoneCompletionWakesTheIdleManagement` (a milestone completion opens a new turn in the idle management thread, the delivery record says accepted, and no parent-queue file is written) and `TestFlowReportE2EStoreSeatReportIsDelivered`.
- The delivery result of a report was what the sending process saw (`accepted`, `queued`, `refused`, `unknown`), written apart from the transport that made it; port: fixed (staging writes only `queued`; the daemon's settle that moves a flow message to `dispatched` or holds it at a cap appends `report_delivery` `accepted` or `refused` - `message_delivery` for an escalation, a completion or a `run:` step wake - in the same transaction, once for its key and result; a row it cannot write is journaled `flow_delivery_unrecorded` and the settle commits). Pinned by `TestFlowReportE2EDaemonDeathAndResumeNeverWriteTheDeliveryTwice` (a daemon that dies before its settle leaves no row and the send is not repeated; one that dies after it leaves the one row; a second daemon and a resume write no second) and `TestFlowRunWakeE2ESettlesUnderTheSameRule`.
- A recipient that stayed busy was held at `busy_cap` by the busy deferral, before any transport call and outside the settle, so that hold wrote no `refused` row, and the daemon could settle a message (appending `accepted`) before the writer appended the `queued` row of its staging, so a report read `queued` and standing after it was accepted (evaluation d2 and d3 of a49bcbbc); port: fixed (the busy deferral that holds a flow message at `busy_cap` appends the `refused` row in its own transaction, once, as the settle's cap holds do; a `queued` row after an `accepted` one does not supersede it for the writer's replay, `crw flow reports` and the pump, `report.SupersedesDelivery`). Pinned by `TestFlowReportE2EBusyCapHoldWritesTheRefusedDelivery`, `TestFlowReportE2EASettleBeforeTheQueuedRowReadsAccepted` and `TestUnreadReportLastDeliveryIsAcceptedWhenTheQueuedRowCameAfter`.
- A decision only Jun can make that fell to the store seat was stored with no project while the sender resolved the project again and staged it with the evidence `crw flow reports --project <project> --unread`, which did not list it; and a store seat's report of a run whose plan names no project went through `crw manage send-parent` (Argon V5 F2 of 4d293b7b); port: fixed (the resolver records the plan's project for the store seat's decision too, the writer stages under the project the row records and resolves it no second time, and `RelaySender.Delivers` leaves a store seat's report with no project standing for the store seat's pump, which `crw flow reports --unread` lists). Pinned by `TestRelaySenderJunDecisionForTheStoreSeatIsListedByItsEvidence` (the evidence listing returns the row) and `TestRelaySenderLeavesAStoreSeatReportOfNoProjectStandingForThePump`.
- Deviation: `refused` is a message held at a cap (`busy_cap` by the settle or the busy deferral, `attempt_cap` by the settle): the transport has no refusal of its own, and a cap is where the channel stops retrying by itself; a hold released later and accepted adds the `accepted` row after it. A transport whose outcome is unknown (`held_uncertain`) writes no row and the report stands `queued`; port: kept (warn and record, fail open).
- Deviation: a decision only Jun can make goes up as the new direct kind `flow_jun_decision_request` (project relationship, the answer owed by the user), because D1a's `jun_decision_request` goes through `initiative:`; under a legacy lead it is not staged (a lead does not decide for Jun) and stands for the store seat's pump, as before; port: kept (a new `obligation_kind` value, no CHECK).
- Deviation: `ManageSender` stays as `RelaySender`'s fallback for what the channel has no kind for: the plan summary notice to the orchestrator thread (the run hook's summary and `crw flow apply`) and an escalation or completion of a run whose plan names no project; the old senders' tests (`TestReportUpStoreSeatFoldStaysStanding`, `TestJunDecisionReportIsARowForTheStoreSeat`, the CRW-1204 hook tests) describe that path and are unchanged; `flow_no_node_started` is declared and unused (the CRW-1320 report is a `project_blocked` report); the pump's own reading of jun decisions is D4's; the relay store's schema is unchanged (new `obligation_kind`, `flow_events.kind` and `journal.kind` values only, no CHECK); port: kept.
