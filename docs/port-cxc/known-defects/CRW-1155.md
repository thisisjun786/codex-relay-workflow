# CRW-1155 — a background job runs only under its record, and cancel says cancelled only for a job it saw stop

Source: CXC v0.2.40 (commit 3c1459ac) `plugins/codexclaw/components/bg-wake/src/spawn.ts:26-32` (newId), `:114-145` (runBackground: spawn, then the record) and `:150-176` (cancel), `registry.ts:111-148` (reconcile). The Go files are `internal/relay/job/spawn.go` (reserve, runBackground with its launch gate, cancel), `internal/relay/job/registry.go` (StatusCancelRequested, reconcile and settle), `internal/relay/job/lock.go` (the store lock and update) and `internal/relay/job/verbs.go` (cliCancel). The tests are in `internal/relay/job/spawn_owner_test.go`; the red run against the code before the change is `/state/crw/crw-lane-bg-job/evidence/red-1155/`. Each item is a deviation from the oracle under the security and record-loss classes of the parity rule.

- Supersedes known-defects.md, section "Found by the bg spawn port", item beginning "A job whose record was never written keeps running unmanaged": now port: fixed (the record is reserved under its id before anything starts, and the shell waits at a launch gate, `read` on descriptor 3, until the launcher has published its pid and start token and writes `go`; a record that cannot be published, a start identity that cannot be read and a reservation a cancel withdrew end the shell at the gate, and a caller that dies before it publishes closes the pipe, so the shell ends without running the command. Pinned by `TestRunBackgroundLeavesNoUntrackedJobWhenThePublishFails`, `TestRunBackgroundLeavesNoUntrackedJobWhenTheCallerDies` and `TestRunBackgroundRefusesAJobWithoutAStartIdentity`).
- Supersedes known-defects.md, section "Found by the bg spawn port", item beginning "`processStartToken` is read once, right after the shell has started": now port: fixed (a shell whose start token cannot be read is not run: `ErrNoStartIdentity`, the record is settled failed with the detail `start identity unreadable`; `cancel` no longer skips the owner check for a record without a token).
- Supersedes known-defects.md, section "Found by the bg spawn port", item beginning "`cancel` signals the group of the pid in a record whose startToken is null": now port: fixed (a pid outside 1 < pid <= MaxInt32, a record without a start token and a token that no longer matches are refused with `ErrOwnerUnproven` and nothing is signalled; the verb exits 1 with the record's status and says how to check the pid by hand, after which the next `get` settles the record. The pid can still be recycled between the token check and the signal, a window of one `ps` call).
- Supersedes known-defects.md, section "Found by the bg spawn port", item beginning "`cancel` writes cancelled whether or not a signal landed": now port: fixed (cancel records `cancellation-requested` before it signals the job's process group, returns a failed signal as a `SignalError` with the request kept, and records `cancelled` only once signal 0 to the group answers ESRCH, so a leader that ended while its descendants live is not taken for the job's end. It waits up to two seconds; a group still alive keeps the request, which `Reconcile` settles cancelled once the group has gone, and a second cancel sends SIGKILL to the group, also after the shell itself has ended on SIGTERM, since a process group id is not handed out again while the group has a member. The leader-only fallback after a failed group signal is gone: the group is the job, and a failure to signal it is reported, not retried on one process. Pinned by `TestCancelNeverSignalsAProcessItCannotProveIsTheJob`, `TestCancelReportsASignalThatFailed`, `TestCancelOfAJobThatIgnoresSIGTERMIsNotCancelledUntilItStops`, `TestCancelSaysCancelledOnlyOnceTheWholeGroupIsGone` and `TestCLICancelReportsTheRequestAndTheRefusal`; the replayed `cli__bg__cancel_running_job_kills_group` keeps its output, its two ledger rows and its three `ps` calls).
- Supersedes known-defects.md, section "Found by the bg spawn port", item beginning "The paths of `<id>.out` and `<id>.exit` are cleared before the start", its second half ("`recordExists` and the publication of the record are not one step"): now port: fixed (the id is drawn and the first record published in one step, a temporary file linked to `<id>.json`, which fails when the name exists; pinned by `TestRunBackgroundReservesTheIDBeforeTheStart`). The link half of that item stays with CRW-475.
- A record whose cancel was requested is not terminal: `IsTerminal` is unchanged, so the wake does not deliver it and `list` shows it without a delivery mark until it is settled; an agent waits for `cancelled` (or the job's own outcome). The oracle had no such state; port: fixed (recorded deviation).
- The lifecycle writes of a workspace (the start's publication, reconcile, cancel) take an exclusive `flock` on the bg directory and re-read the record before they write it, so one writer never puts back a snapshot another has changed (`update` in `lock.go`); no lock file is created. The oracle had no lock; port: fixed (recorded deviation, shared with CRW-1092).
