# CRW-856 — a goalplan write that finds another plan directory at its path after the rename

Source: the goalplan writer is `plugins/codexclaw/components/pabcd-state/src/goalplan.ts` `writeGoalplan`
at CXC v0.2.40 (commit 3c1459ac): it writes a temp file, publishes it with `renameWithRetry`, and
returns whatever the publication threw. The steering transaction is
`plugins/codexclaw/components/pabcd-state/src/steering.ts` `applySteeringBatch` :253-333. The Go port
is `internal/pabcd/goalplan/write.go` (`goalplanPublishedWritePublishAt`, `goalplanPublishedOptions`)
and `internal/pabcd/goalplan/open.go` (`boundFile`, `openAt`), with the caller
`internal/pabcd/goalplan/steering.go` (`steeringApplyLocked`). The oracle never syncs the published
file or its directory (`known-defects.md`, "Found by CRW-479 state publication durability"), so it has
no counterpart here.

- The port classified every post-rename directory-open failure as a published write, and one of those
  failures is not one: the post-rename open runs `boundFile`, which re-checks that the descriptor still
  resolves to the plan directory, so when the directory is renamed away or replaced between the
  `Renameat` and the open, the plan is not at the expected final path while `steeringApplyLocked`
  answered `applied` and appended its `steered` row through the current path — a ledger row for a plan
  that does not hold the batch's work, and a retry that cannot reconcile it because the key is not in
  the plan at the slug path (source `plugins/codexclaw/components/pabcd-state/src/goalplan.ts:915-942`,
  the oracle has no counterpart because it never syncs after the rename; reproduced by the parent on
  dev d9f30086 with a temporary post-rename hook); port: fixed (a data-integrity defect,
  fixed by decision: `boundFile`'s two identity failures — the wrong descriptor kind and the descriptor
  path that is not the expected one — are returned as the unexported type `goalplanRelocatedError` with
  their texts unchanged and `openAt` passes it through; `goalplanPublishedWritePublishAt` returns a
  plain error `goalplan '<slug>' directory moved after publication; the plan at its path is not the one
  written` when the post-rename directory open answers that type, so `ApplySteeringBatch` answers an
  error and appends no ledger row and a retry applies to the plan now at the path; every other
  post-rename open failure, `ErrPermission` included, and the directory fsync failure stay
  `*state.PublishedError`, so the CRW-793 published-but-unsynced path is unchanged; the seams are
  function fields of `goalplanPublishedOptions` (`AfterRename`, `OpenDir`), never package variables;
  the cases are `internal/pabcd/goalplan/goalplan_relocated_test.go`; no corpus fixture drives a
  post-rename failure, so none is retagged).
- Supersedes known-defects/CRW-793.md, item beginning "The port classifies every post-rename directory-open failure as a published write": now port: fixed (CRW-856 distinguishes the path-identity failure from a genuine open or sync failure; the two identity failures are `goalplanRelocatedError` and the writer returns the plain "directory moved after publication" error for them, while every other post-rename failure stays `*state.PublishedError`, exactly as this item's own follow-up proposed).
- Supersedes known-defects.md, section "Found by the steering batch port (CRW-643)", item beginning "The port's plan writer syncs the plan directory after its rename": now port: fixed (CRW-793 wrapped the post-rename directory-open and sync failures as CRW-744's `*state.PublishedError` and made `steeringApplyLocked` append its `steered` and `dependency_registered` rows as on success, so a genuine directory-sync failure no longer loses the row; CRW-856 narrows that classification so a path-identity failure at the same open is refused as a plain error instead of answered applied; the item's own "proposed as a follow-up" is discharged by the two).
