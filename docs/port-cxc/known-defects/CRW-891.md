# CRW-891 — multi-agent v2 repair reads and publishes through the caller's config path

Source: CXC v0.2.40, commit `3c1459acadeb1906d97c00a598e1457327ae372d` —
`plugins/codexclaw/components/config-guard/src/multi-agent-v2.ts` (`setMultiAgentV2State`, :52-80:
the caller's path resolved once at :53, the pre-image read at :60, the injected `codex features`
runner at :61, the post-image read at :67, the repair write at :70 and the reported state at :73).
Port: `internal/runtime/install/configguard/multiagentv2.go` (`SetMultiAgentV2State`) and the
sidecar lock it takes, `internal/pabcd/crwdir/swap.go` (`LockConfig`, `ConfigLock.Target`).

## Defects

- The port's `SetMultiAgentV2State` replaced its content path with `lock.Target`, the file the
  sidecar lock resolved to when it was taken (CRW-866, `multiagentv2.go:194` before this issue),
  so a caller path that is a symlink and an injected runner that atomically replaces that pathname
  left the post-image read opening the old target: `multiAgentV2Preserve` saw a post-image without a
  `[features.multi_agent_v2]` table, answered "no repair", and the command still reported
  `version = v2`, `changed = true` while the live config had no such table. The oracle read the
  caller's path at every step (source `multi-agent-v2.ts:53,60,67,70`), so this was a regression of
  the port, not an oracle behaviour; port: fixed (the issue's answer: the content path stays the
  caller's path — the pre-image read, the post-image read after the runner and the repair publish
  all use it — while the lock stays keyed by `lock.Target`, so two writers reaching one file through
  different spellings still share one lock; pinned by `TestMultiAgentCallerPathReadsTheReplacedPath`,
  `TestMultiAgentCallerPathRegularFileControl`, `TestMultiAgentCallerPathWriteThroughTheLinkControl`
  and `TestMultiAgentCallerPathKeepsTheLockKeyedByTarget`).
- The sidecar lock is keyed by the file the caller's path resolved to when the lock was taken, so
  when the injected runner replaces the caller's pathname the repair publishes to a file the lock
  no longer names: a concurrent writer that reaches the new file through the same caller path takes
  the same sidecar only after this command releases it, and one that reaches it through another
  spelling takes a different one (source `multi-agent-v2.ts:53,60,67,70` reads the path it resolved
  once, with no lock at all); port: kept (the issue's answer authorises recording this as a
  limitation of the repair path rather than fixing it here. The pre-image, the runner and the repair
  are still one critical section, so a CRW writer that reaches the old target is still serialized
  against this command; closing the window needs a lock keyed by the caller's path, which is a
  change to `crwdir` rather than to this writer).

## Supersedes

- Supersedes known-defects/CRW-866.md, section "Defects", item beginning "The oracle's
  `setMultiAgentV2State` read the pre-image": now port: fixed (CRW-866's lock span is kept — the
  pre-image read, the injected runner, the repair and its publish are still one critical section
  under `crwdir.LockConfig`, pinned by `TestMultiAgentV2SetTakesTheConfigLock` — and the
  content-path substitution that came with it is reverted: the read and the publish use the
  caller's path, as the oracle did, and only the lock is keyed by `lock.Target`).
