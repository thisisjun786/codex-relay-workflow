# CRW-1147 — crw map launcher: blank interpreter, help before bootstrap, a failed pip, the uv probe

Source: CXC v0.2.40 (commit 3c1459ac) `bin/codexclaw.mjs:335-358` (the ladder) and `:383-406` (the one-time venv bootstrap and the uv probe), read through `known-defects.md`, section "Found by the CRW-344 provider detection and map launcher port". The Go file is `cmd/crw/repomap.go` (`launchRepoMap`, `selectRepoMapCommand`, `bootstrapRepoMapVenv`, `repoMapBootstrapLock`); the tests are in `cmd/crw/repomap_test.go`. The four items below were kept by CRW-344 and found fixable by the 10-10 CXC improvement review (A8).

- Supersedes known-defects.md, section "Found by the CRW-344 provider detection and map launcher port", item beginning "A whitespace-only Python override": now port: fixed (`CRW_PYTHON` is trimmed once by `repoMapOverride`; a value of only whitespace is unset for the ladder, the fallback and the bootstrap alike, so it is no longer run as a literal command and no longer suppresses the bootstrap; a padded value runs trimmed. Pinned by TestRepoMapLadderFromBin/blank-bare, blank-venv, blank-help, padded-override and TestRepoMapBootstrapWithFakesOnly/blank-override-is-unset, red on 251d28887).
- Supersedes known-defects.md, same section, item beginning "Explicit bootstrap can create a venv and invoke pip even for help": now port: fixed (an explicit `--help` or `-h` is answered before the venv check, the bootstrap and the uv probe: the one command is the override or `python3` with the script, as the ladder already chose for help. Pinned by TestRepoMapBootstrapWithFakesOnly/help-skips-bootstrap and help-with-override).
- Supersedes known-defects.md, same section, item beginning "A failed pip run removes the whole rebuildable venv directory": now port: fixed (the bootstrap runs under an exclusive `flock` on the directory `<CRW_HOME>/venvs` (created for it), which holds the directory a failed attempt may remove and gets no file of its own; a run that opted into the bootstrap takes the lock before it looks for the interpreter, because `python3 -m venv` creates the interpreter before pip has installed anything, so a run that starts during the install waits and then finds the finished venv and builds nothing; the directory is removed after a failed pip only when it did not exist before this attempt, so another run's tree and an earlier partial one are left alone, and in a directory that was there before only the interpreter this attempt made is removed, because an interpreter marks a ready venv and one without its requirements would stop the next opted-in run from retrying pip; when the lock cannot be taken the bootstrap is skipped with a message and the run falls back. The wait ends with the process's context. Pinned by TestRepoMapBootstrapsAreSerializedAndLeaveTheOthersTree, TestRepoMapSecondRunWaitsWhileThePipInstallIsRunning (red on aac4e9ad4), TestRepoMapRetriesAFailedPipInAPreexistingVenvDir (red on c78ae781d), TestRepoMapBootstrapSkippedWhenTheLockCannotBeTaken and TestRepoMapBootstrapWithFakesOnly/pip-fails-preexisting-dir).
- Supersedes known-defects.md, same section, item beginning "The uv availability probe always runs": now port: fixed (no probe for help or for an explicit interpreter, the two runs that never use uv; the probe that remains is bounded to 5 seconds and counts as no uv when it does not answer. Pinned by TestRepoMapBootstrapWithFakesOnly/override and help-with-override, and TestRepoMapUvProbeIsBounded).
- No oracle (CRW-392's own plugin-installed skill lookup, `installedRepoMapDir`, issue comment of 10-10 from CRW-1080): the scripts directory of the plugin-installed `crw-repo-map` skill was fixed at `<plugin>/skills/crw-repo-map/scripts`; it is now read from the plugin manifest (`pluginSkillsDir`: the `"skills"` string of `<plugin>/.codex-plugin/plugin.json`, relative to the plugin root), for the active `PLUGIN_ROOT` and for each cached version, and falls back to `skills` when the manifest is absent, unreadable, over 1 MiB, or names an empty, absolute or outside path; port: fixed. Pinned by TestRepoMapReadsTheSkillsDirectoryFromThePluginManifest and the end-to-end TestRepoMapHelpRunsThePluginScriptWithRealPython (`crw map --help` with the real `python3` and the shipped `repomap.py` under a manifest-named directory), both red on 7d997d535.

The cxc replay claims for the three recorded `map` cases these changes touch are in `contract/notes/cxc/CRW-1147.json` (moved out of `CRW-344.json`, whose claim on a fixture cannot coexist with another): `cli-help__map__dash_h` and `cli-help__map__dashdash_help` no longer call `uv --version`, and `cli__map__codexclaw_python_runs_repomap_with_it` loses the first run's uv call and gains the `venvs` directory the bootstrap lock is held on.
