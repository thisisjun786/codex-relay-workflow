# CRW-1321 — the architect planned done conditions the executor cannot meet and decided questions above the run

Source: CRW's own design, not the CXC oracle (CXC v0.2.40, commit 3c1459ac): the oracle has no flow engine, no architect overlay and no design audit. The Go and script side is `internal/flow/roles/architect.md` (the overlay the engine appends to the embedded `architect.toml`, whose bytes `TestEmbeddedAgentsUnchanged` keeps), `internal/flow/workflows/lib/packets.js` (`designAuditPacket` and the header on input digests), and the facts the text states: `internal/flow/roles/executor.md` (the executor makes no commit), `internal/flow/ops/lane_build.go` (`crw.commit` commits with the message `crw <node> <call>`, a blank line and the request id), `internal/flow/ops/schemas.go` (the RECEIPT fields), `internal/dev/ci/gui_drift.go` (the drift check reads the tree of HEAD), `internal/flow/ops/lane_decisions.go` and `internal/flow/workflows/lib/lane.js` (the routing of an open question). Found by the 10-13 field trial (CRW-1315 items 39, 33 and 37).

- The architect overlay said nothing of the executor's contract, so a DESIGN asked for an exception's reason in the commit body (the run commits with a fixed message) and for `make gui` to pass after the executor committed its assets (the executor never commits and `crw-dev ci gui-drift` compares with HEAD); the audit caught it only in review and the design went round again (item 39); port: fixed (the overlay's `## Executor contract` section states that the executor never commits, the run's fixed commit message, the RECEIPT's fields, that a done condition is a check at the committed HEAD or a state of the worktree, and that a generated asset is planned with its generation and verification commands. Pinned by `TestArchitectOverlayExecutorContract` and, against the run's own commit and `ops.Receipt`, `TestArchitectContractMatchesTheRun`).
- The architect decided a policy question (an exception to the known-defects rules) itself and the run showed no ask (item 33); port: fixed (the overlay's `## Authority boundary` section names the four kinds of question the architect does not decide - an exception to a rule of the repository, the record of another issue, a policy decision, a prerequisite of the execution environment - and has them raised in `open_questions` with the plan on a stated assumption; a question does not stop the run and is not a hold. The section states the routing an open question takes today. Pinned by `TestArchitectOverlayAuthorityBoundary`).
- The design audit judged executability inside the edit regions and P0/P1 findings only, not done conditions against the executor contract nor decisions above the architect's authority; port: fixed (`designAuditPacket` approves only when every done condition can be met under the executor contract and no decision is outside the architect's authority, lists both, and makes either failure a P1 finding, so the verdict is `needs_changes`. Pinned by `TestDesignAuditPacketChecksExecutabilityAndAuthority`).
- An open question whose `files_needed` lists at most three files (`InlineFiles`), an empty list among them, is routed inline (the open questions of a DESIGN carry no edit regions, so the `inRegions` clause of the route does not apply to them, and the DESIGN schema requires `files_needed`, so the null list that sends a question to an explorer does not occur) and reaches the design audit with an empty answer, and only the questions beyond the milestone's explorer cap reach the orchestrator as a `design_question` escalation, so a question of the four kinds that the architect raises is recorded in the DESIGN and the explore rows but is not handed to the layers above (item 37; `TestExploreRouting` keeps the routing); port: pending (CRW-1316 decides the open-question path when the explorer becomes the orchestrator's subagent; the overlay tells the architect how the route behaves today, that no route but the escalation beyond the cap hands such a question above the run, and the design audit packet that a question raised with a stated assumption is no finding also when it reaches the audit unanswered).
- Named limit: the text of a packet is part of the input digest of its call, so a run that recorded its design audit under the earlier `designAuditPacket` text runs `design-audit:r1` live on a resume and `crw.designLedger` then refuses the first revision again; such a run is finished by the binary that started it or started anew. The overlay text is in no input digest and re-runs nothing; a turn on a thread started earlier keeps the instructions that thread started with. Pinned by `TestResumeAfterPromptTextChange`; port: kept (a resumed lane builds the packet it built, the rule of crw:lib/packets).
