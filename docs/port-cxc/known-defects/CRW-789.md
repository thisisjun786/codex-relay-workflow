# CRW-789 — the doctor runtime's subprocess streams: Node's UTF-8 decode at both seams

Source: CXC v0.2.40 (commit 3c1459acadeb1906d97c00a598e1457327ae372d)
`plugins/codexclaw/components/cxc-ops/src/doctor.ts` (the `spawnSync` probe that reads a child's
streams with `encoding: "utf8"`) and `plugins/codexclaw/components/cxc-ops/src/hook-trust.ts`
(`verifyCodexConfig` :387-410, whose `spawnSync` options carry `encoding: "utf8"` at :398), through
the port in `internal/runtime/doctor/harness_run.go` (`harnessRunExec`) and
`internal/runtime/doctor/hooktrust_retrust.go` (`hookTrustRetrustExec`).

Both seams spawn a program and read its stdout and stderr. Node decodes those bytes with its UTF-8
decoder before any JavaScript string sees them, so an invalid byte sequence is one U+FFFD per
maximal invalid subpart and can never be a lone surrogate. The port's `source.DecodeUTF8`
(`internal/pabcd/source/git.go:142-190`) implements that rule.

- The harness seam (`harnessRunExec`) already decodes both streams with `source.DecodeUTF8`
  (`internal/runtime/doctor/harness_run.go:478`); CRW-683 added it as a review finding of PR #719
  (commit `49f1ef88fa77d17bf0cb2a8730ebf2ac51fbe9a8`, merged
  `4dcc51700d25a2c1480d1dfb4c82f664efa27a1b` on 2026-10-06 22:23 +0900). The defect the CRW-789
  issue body records was reproduced on dev `8ad60bfa93af540af2226cbdaed414b36d7e51a9` (2026-10-06
  15:52 +0900), which predates that commit, so the behaviour is already parity and this issue pins
  it with regression tests instead of changing the code; port: fixed by CRW-683, pinned here (six
  cases in `harness_run_utf8_test.go`, which fail when the decode line is reverted; the failing
  output is retained as this task's evidence outside the repository).
- The retrust seam (`hookTrustRetrustExec`, `internal/runtime/doctor/hooktrust_retrust.go:452`)
  returned `HookTrustRetrustRun{Stdout: stdout.String(), Stderr: stderr.String()}`, the raw bytes,
  where the oracle's `verifyCodexConfig` reads the same streams through `spawnSync` with
  `encoding: "utf8"` (source `hook-trust.ts:398`). The raw bytes reached the printed failure text
  (`codex features list verification failed: <detail>`, `hooktrust_retrust.go:206-217`), so an
  invalid byte from codex appeared in `crw doctor retrust`'s stderr as the raw sequence where the
  oracle writes U+FFFD; port: fixed by CRW-789 (both streams go through `source.DecodeUTF8` at the
  seam, the same place as the harness precedent; the timeout, `WaitDelay`, exit-status and
  start-failure branches are unchanged. Pinned red first by `hooktrust_retrust_utf8_test.go`, whose
  failure on the base carries the raw bytes where the test wants the three U+FFFD).
