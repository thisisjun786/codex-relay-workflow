# CRW-813 - the state-copy apply decided directory ownership from a stale absence

Source: the state-copy apply is CRW's own design, [docs/port-cxc/state-migration.md](../state-migration.md)
(the preflight rules at :144-156, the whole-scope preflight at :148, the publication and mode rules at
:150-152, and the M3 slice at :184-200), and the code is the Go port in
`internal/runtime/install/migrate`: `roots.go` (`EnsureChild`, `EnsureDest`), `apply.go`
(`ensureRoots`, `ensureDestDir`, `finishModes`) and `publish.go` (`EnsureProjectRoot`). The oracle
has no state-migration command, so nothing here is a CXC v0.2.40 behaviour and no fixture is claimed;
the defect is Go-side and the same files fix it. Both were found by the operator's pair evaluation of
the merged state-copy PR (PR #652), and CRW-813 fixes both under its own scope.

- `EnsureChild` swallowed `EEXIST` and returned only the pinned child, so `apply` decided that a
  destination directory was this run's from an observation made earlier - `pair.Dest == nil` in
  `ensureRoots`, and `Dir.Child` returning `fs.ErrNotExist` in `ensureDestDir` - rather than from
  the result of its own `mkdir`. A directory another actor created in that window was therefore
  treated as this run's: `ensureDestDir` chmodded it to the private marker mode `0o1700`
  unconditionally, and `finishModes` finished it at the source mode, so a `.crw` or a child
  directory another actor made `0700` was left `0755` (source `roots.go:471-490`, `apply.go:255-267`,
  `apply.go:300-327`, `apply.go:575-616`; the design requires that a directory this migration did not
  create retains its mode and is reported, `state-migration.md:150`); port: fixed (`EnsureChild` and
  `EnsureDest` return whether their own `mkdir` created the directory, an `EEXIST` creation reports
  false, and `apply` gives the marker mode and records ownership only from that value; the cases are
  `TestMigrateOwnedDirKeepsAForeignProjectRootMode`,
  `TestMigrateOwnedDirKeepsAForeignUserRootMode` and
  `TestMigrateOwnedDirKeepsAChildDirectorysModeWhenARacerCreatesIt`).
- `ensureRoots` created the user destination root through `EnsureDest(applyTempRaw)` and left the mode
  to `mkdir`, so the marker the migration recognises its own directories by was never set explicitly
  on that root. `mkdirat(0o1700)` need not keep the sticky bit - Darwin drops it from a directory's
  creation mode, and a umask can mask the permission bits away - so a root this run created could come
  out without the marker. The rerun then read the root as an existing directory of another actor and
  never finished its mode, and the copy stayed broken at a permissionless root (source
  `apply.go:255-267`, `roots.go:471-490`; the design requires a directory this migration created, or
  one an interrupted run left at the private mode it creates directories with, to have its source mode
  finished on a rerun, `state-migration.md:150`); port: fixed (a destination root this run created, of
  the user scope as well as the project scope, is given `applyTempRaw` explicitly right after its
  creation, as `ensureDestDir` already did for a child; the cases are
  `TestMigrateOwnedDirCreatedUserRootCarriesTheMarkerBeforeAChild` and
  `TestMigrateOwnedDirRerunRecognisesAUserRootTheRunMade`).

Not a defect, recorded so the change of behaviour is not mistaken for one: the CRW-812 case
`TestMigrateApplyReviewRefusesAnIgnoreRaceInANewRoot` asserted that a root a racer created together
with a differing `.gitignore` was left at the private marker mode. That was the ownership defect
itself - the racer created the root, so the root is the racer's and this run must not touch its mode -
and the case now asserts that the racer's root keeps the mode the racer gave it. The initialization
race the CRW-812 case exists for is unchanged: the refusal still stops the copy before any state is
published, and the racer's `.gitignore` is still kept.

Limitations, not defects, recorded so each is a decision rather than a surprise:

- The marker is what a rerun reads to recognise a directory this migration made, so a crash in the
  window between a root's `mkdir` and its marker chmod can still leave a root that a rerun does not
  adopt. Closing that window needs a creation mode that is already the marker on every platform, which
  `mkdirat` does not provide; the run keeps the marker chmod immediately after the creation, before
  anything else can fail, so the window is one syscall wide.
- The Darwin half of the defect above - that Darwin drops the sticky bit from a directory's creation
  mode - is the behaviour the issue names and the reason the marker is set explicitly. It is not
  observed here: this host is Linux, and the probe in the pull request's evidence is Linux-only. The
  Linux half (a umask masking the permission bits away from `mkdirat(0o1700)`) is observed, and the
  Darwin half is carried as the issue states it rather than as a measurement.
- The adoption branch in `finishModes` recognises a directory by the raw marker mode plus
  `entriesExpected`, so a foreign directory that already carried exactly that marker mode and held
  only plan-named entries would be adopted and finished at the source mode. The marker is chosen to be
  one no other writer in this repository uses (`apply.go` `applyTempRaw`), which is what keeps this
  out of reach in practice.
- A temporary an older run left in a destination directory makes `entriesExpected` false for that
  directory, so its mode is never finished. That is the design's rule for older temporaries
  (`state-migration.md:152`: they are reported or ignored, never adopted or removed), recorded here so
  the consequence for the mode is known.
