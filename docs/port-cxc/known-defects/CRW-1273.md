# CRW-1273 — a management batch the bridge refused is sent again under the next ordinal of its id, and a configuration that cannot deliver is refused

Source: CRW's own design, not the CXC oracle (CXC v0.2.40, commit 3c1459ac, has no management pump). Found by the real-environment trial r2 S6 (evidence `ev/S6/20261012T050218Z`, installed head dd11cba60), where the pump sent no batch to the management thread. The Go files are `internal/manage/pump.go` (`pumpDeliver`, `pumpMgmtRefusalCount`, `pumpMgmtStrandedCount`, `pumpDeliverReason`, `pumpRun`), `internal/manage/deliver_send.go` (`deliverRecordStranded`, `deliverReconcileStranded`), `internal/manage/config.go` (`coreDeliverSettingsProblem`, `coreRunConfig`) and `internal/manage/pump_queue.go` (the rule this mirrors).

- A batch the bridge refused could never be sent again; port: fixed. The logical id of a management batch is the digest of its event ids (`pumpBatchID`) and its body carries the round's `HH:MM`. A refusal settles the id in the ledger and lifts the freeze, the events stay pending, and the next round formed the same id with a body of another minute, which `Deliver` answers with "already belongs to another message", or, inside the same minute, with the stored refusal; the batch was not delivered until a new event changed the id. The management batch takes the rule of the parent queue (CRW-991 rule 4, merged with CRW-957): a refusal the ledger proves (`pumpReview776QueueRefusalSettled`) is counted against the batch's base id in the pump state (`mgmt_refused`: the id and the count), and the next attempt of the same events goes out under `<id>-m<count>` (`pumpMgmtOrdinalID`), a new ledger record with its own body. The ordinal is `-m`, never `-r`: `Deliver` sends its own retries of one logical id under `<logical id>-r<n>` request ids, so after an App Server outage that spent `B`, `B-r1` and `B-r2` (each answered `not_attempted` / `not_delivered` and kept by the ledger) a logical id `B-r1` would reach the ledger as the request id of a retry that already holds another body, the bridge would answer ErrConflict, `Deliver` would classify it unknown, and every later round would reconcile `B-r1` to the stored `not_attempted` receipt and send under `B-r1` again: the attempt would never leave the freeze, and no new event would be delivered. A refusal the ledger does not prove is neither counted nor does it lift the freeze: a local refusal before any bridge call (an unset execution policy) says nothing about a frozen attempt that may already have been accepted, and a terminal refusal whose outbox record could not be written leaves the record unsettled, so the attempt keeps its id and body and the next round reconciles it with `get_operation`, as the parent queue keeps its pin (`pumpReview776QueueSettle`). The count of another base id restarts at one, and an accepted batch clears it. The limit is the queue's (`pumpQueueRefusalLimit`, 3): the third refusal of one id parks the batch's events. They leave pending so the events behind them flow, stay in the pump state with the bridge's last answer and the time (`parked`), are written to `pump.log` one line each (`management event <id> parked after 3 refusals: <reason>`), and are not collected again (`pumpCollect` treats a parked id like a pending one), as the queue moves a notice to `refused/`. The `HH:MM` head stays in the body: a frozen attempt keeps its body whole, and a refused attempt is never sent again under its own id, so the head is no part of the id's identity. Pinned by `TestPumpRefusedBatchIsDeliveredAfterTheSettingsAreFixed`, `TestPumpRefusedBatchAcrossAMinuteBoundary`, `TestPumpRefusedBatchIsParkedAfterTheLimit`, `TestPumpUnprovenLocalRefusalKeepsTheFrozenAttempt`, `TestPumpRefusalWithoutOutboxProofKeepsTheFrozenAttempt` and, for the missing-settings failure as the real bridge produces it (a tool error, reconciled with `get_operation`, retried under new request ids, refused at the retry cap, then delivered under the next ordinal once the settings are fixed), `TestPumpMissingSettingsToolErrorIsReconciledThenRecovered`.
- An empty `settings.management` was accepted and made every send fail; port: fixed. `Deliver` attaches `expected_settings` only when the model or the reasoning effort is set, and the bridge requires the argument (`contract/schema/bridge-mcp-tools.json`, `internal/bridge/mcp/schema.go`), so a configuration with a `management_thread` and an empty `manage.settings.management.model` or `reasoning_effort` was refused in argument validation on every send, three times each, without a word in `pump.log`. `crw manage config` now exits 2 on such a configuration and names the empty key, `crw manage pump` does not start on it (exit 2), and `crw manage pump --dry-run`, which sends nothing, only warns on stderr. A configuration without a `management_thread` delivers nothing to the management thread and is not judged. The parent thread's `settings.parent` is not judged here: the issue names the management settings. Pinned by `TestManageConfigRefusesEmptyManagementSettings` and `TestPumpStartRefusesEmptyManagementSettings`.
- The bridge's refusal was in the outbox only; port: fixed. The `deliver` line of `pump.log` for a batch that was not accepted ends with `reason=<the ledger's last answer for the logical id, on one line, at most 200 characters>`, or the delivery core's own error when the call wrote no attempt to the ledger (it refused before any bridge call, or the bridge did not start): an excerpt an earlier attempt of the frozen batch left in the outbox is never the reason of a call that did not write one (`pumpDeliverReason` compares the attempts the record holds before and after the call). Pinned by `TestPumpLogCarriesTheBridgeRefusal` and `TestPumpLogReasonIsTheCurrentLocalRefusal`.
- A frozen management attempt whose outbox record belongs to another thread never left the freeze; port: fixed. When `management_thread` is changed while an attempt is frozen with an undetermined outcome, `Deliver` refuses the attempt locally in every round ("the logical id ... already belongs to another message", the record's thread against the configured one) before any bridge call, so the attempt was neither reconciled nor lifted, and no event reached the new thread. The pump recognizes that record (`deliverRecordStranded`) and reconciles its request id with `get_operation` directly (`deliverReconcileStranded`; the bridge's lookup depends on no thread) instead of calling `Deliver`: an accepted answer settles the record accepted and the events are sent; a refusal, or an id the bridge holds nothing sent under, closes the record as refused, which the pump counts against the batch like any proven refusal (the batch then goes out under the next `-m` ordinal, or merged into a batch of new events). A receipt the bridge holds that places nothing (`in_progress_or_unknown`, which the bridge's ledger writes in `Begin` and never settles afterwards, or `outcome_unknown`) closes the record as stranded: the attempt went, if at all, to the old thread, the configured thread has never seen its events, and keeping the freeze would hold every later event back for good. The record is settled refused with an excerpt naming the old thread, `pump.log` carries `management attempt <id> closed as stranded: it may have reached thread <old>; its <n> events go to <new> under a new id`, and the events go to the configured thread under the next `-m` ordinal of the batch, or merged into a batch of new events. The close spends the ordinal but is no refusal of the bridge, so it never parks the events by itself (`pumpMgmtStrandedCount`). The cost is that the old thread may hold the message too; a second copy on the new thread is the only way the configured thread receives it. A `get_operation` that answers nothing (a transport failure or a tool error) proves nothing about the record and keeps the attempt frozen, and so does an unplaceable record of the configured thread under another text, because sending it again could reach the same thread twice. Nothing is ever sent from the reconcile. Pinned by `TestPumpFrozenAttemptSurvivesAManagementThreadChange`, `TestPumpUnplaceableFrozenAttemptIsClosedAfterAThreadChange` and `TestPumpStrandedCloseNeverParksTheEvents`, with a fake bridge that keeps a request-id ledger with argument fingerprints (`pump_ledger_test.go`), as the tests of the earlier rounds did not, together with `TestPumpManagementRefusalOrdinalNeverCollidesWithDeliverRetries`.
- The refusal of a configuration with an empty `settings.management` reached the policy API's reader; port: fixed. `crw manage config` refuses that configuration (exit 2), and the policy API's running-digest reader (`policystore.manageRelaySettings`) ran that command in process only to read the relay block, so it reported the digest unavailable with the delivery-settings sentence for a file whose relay it could read. The reader takes the report from `manage.ConfigReport`, the same file, precedence and refusals of a file the product cannot use, without the delivery judgement, which belongs to the commands that send. Pinned by `TestRunningDigestReadsTheRelayOfAConfigurationWithEmptyManagementSettings`.
