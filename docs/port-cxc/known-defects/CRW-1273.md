# CRW-1273 — a management batch the bridge refused is sent again under the next ordinal of its id, and a configuration that cannot deliver is refused

Source: CRW's own design, not the CXC oracle (CXC v0.2.40, commit 3c1459ac, has no management pump). Found by the real-environment trial r2 S6 (evidence `ev/S6/20261012T050218Z`, installed head dd11cba60), where the pump sent no batch to the management thread. The Go files are `internal/manage/pump.go` (`pumpDeliver`, `pumpMgmtRefusalCount`, `pumpDeliverReason`, `pumpRun`), `internal/manage/config.go` (`coreDeliverSettingsProblem`, `coreRunConfig`) and `internal/manage/pump_queue.go` (the rule this mirrors).

- A batch the bridge refused could never be sent again; port: fixed. The logical id of a management batch is the digest of its event ids (`pumpBatchID`) and its body carries the round's `HH:MM`. A refusal settles the id in the ledger and lifts the freeze, the events stay pending, and the next round formed the same id with a body of another minute, which `Deliver` answers with "already belongs to another message", or, inside the same minute, with the stored refusal; the batch was not delivered until a new event changed the id. The management batch takes the rule of the parent queue (CRW-991 rule 4, merged with CRW-957): a refusal the ledger proves (`pumpReview776QueueRefusalSettled`) is counted against the batch's base id in the pump state (`mgmt_refused`: the id and the count), and the next attempt of the same events goes out under `<id>-r<count>`, a new ledger record with its own body. A refusal the ledger does not prove is neither counted nor does it lift the freeze: a local refusal before any bridge call (an unset execution policy) says nothing about a frozen attempt that may already have been accepted, and a terminal refusal whose outbox record could not be written leaves the record unsettled, so the attempt keeps its id and body and the next round reconciles it with `get_operation`, as the parent queue keeps its pin (`pumpReview776QueueSettle`). The count of another base id restarts at one, and an accepted batch clears it. The limit is the queue's (`pumpQueueRefusalLimit`, 3): the third refusal of one id parks the batch's events. They leave pending so the events behind them flow, stay in the pump state with the bridge's last answer and the time (`parked`), are written to `pump.log` one line each (`management event <id> parked after 3 refusals: <reason>`), and are not collected again (`pumpCollect` treats a parked id like a pending one), as the queue moves a notice to `refused/`. The `HH:MM` head stays in the body: a frozen attempt keeps its body whole, and a refused attempt is never sent again under its own id, so the head is no part of the id's identity. Pinned by `TestPumpRefusedBatchIsDeliveredAfterTheSettingsAreFixed`, `TestPumpRefusedBatchAcrossAMinuteBoundary`, `TestPumpRefusedBatchIsParkedAfterTheLimit`, `TestPumpUnprovenLocalRefusalKeepsTheFrozenAttempt`, `TestPumpRefusalWithoutOutboxProofKeepsTheFrozenAttempt` and, for the missing-settings failure as the real bridge produces it (a tool error, reconciled with `get_operation`, retried under new request ids, refused at the retry cap, then delivered under the next ordinal once the settings are fixed), `TestPumpMissingSettingsToolErrorIsReconciledThenRecovered`.
- An empty `settings.management` was accepted and made every send fail; port: fixed. `Deliver` attaches `expected_settings` only when the model or the reasoning effort is set, and the bridge requires the argument (`contract/schema/bridge-mcp-tools.json`, `internal/bridge/mcp/schema.go`), so a configuration with a `management_thread` and an empty `manage.settings.management.model` or `reasoning_effort` was refused in argument validation on every send, three times each, without a word in `pump.log`. `crw manage config` now exits 2 on such a configuration and names the empty key, `crw manage pump` does not start on it (exit 2), and `crw manage pump --dry-run`, which sends nothing, only warns on stderr. A configuration without a `management_thread` delivers nothing to the management thread and is not judged. The parent thread's `settings.parent` is not judged here: the issue names the management settings. Pinned by `TestManageConfigRefusesEmptyManagementSettings` and `TestPumpStartRefusesEmptyManagementSettings`.
- The bridge's refusal was in the outbox only; port: fixed. The `deliver` line of `pump.log` for a batch that was not accepted ends with `reason=<the ledger's last answer for the logical id, on one line, at most 200 characters>`, or the delivery core's own error when the call wrote no attempt to the ledger (it refused before any bridge call, or the bridge did not start): an excerpt an earlier attempt of the frozen batch left in the outbox is never the reason of a call that did not write one (`pumpDeliverReason` compares the attempts the record holds before and after the call). Pinned by `TestPumpLogCarriesTheBridgeRefusal` and `TestPumpLogReasonIsTheCurrentLocalRefusal`.
