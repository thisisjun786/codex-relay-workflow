# CRW-838 — audit ledger: an immutable result copy per ok row, the bundle path as recorded, one audit run at a time

Source: CRW's own design, not the CXC oracle (CXC v0.2.40, commit 3c1459ac, has no audit ledger; the pointer is the port). The Go side is `internal/manage/audit.go` (`auditRecord`, `auditLedgerRow`), `internal/manage/audit_result_copy.go`, `internal/manage/audit_runlock.go`, `internal/manage/audit_drafts.go` (`auditDraftCollect`), `internal/manage/audit_pr.go` (`auditPRListPages`) and the `package` and `round start` runners. The defects were found in the review of CRW-695 (#744, Codex P1) and the verification of CRW-696 (#752). The decisions of 10-10 on the issue fix the shapes below.

- A ledger ok row named only the bundle directory, and grading the same directory again overwrote `grade.json`, so an older row lost its own result and pointed at the newest one (`audit drafts` guarded it by skipping the older row); port: fixed (a new ok row carries `id` = the first 16 hex characters of sha256(subject, "\n", head, "\n", graded_at, "\n", sha256 of the graded result bytes in hex), graded_at being the time of the grading, `result` (the path of its copy) and `result_sha256`; the copy `audit/results/<id>.json` is the `grade.json` bytes the grade read and validated (kept with the result, not read again after the batch, so a file another process changed or removed meanwhile cannot change or cost the row its copy; `TestCRW838BatchCopiesTheGradedBytes`, `TestCRW838BatchKeepsTheCopyWhenTheFileIsGone`), and a new ok row that has no result to copy is refused as `result_copy_unavailable` and not appended (`TestCRW838OKRowWithoutACopyIsRefused`), written to a temporary file, fsynced and linked to its name before the row is appended, and a copy is never replaced: graded_at has whole seconds, so two grades of one subject and head in the same second (a regrade, or bundles that name the same subject and head graded together) share it, and the result bytes in the id tell them apart. Other bytes give another id and a copy of their own; the same bytes give the same id and share one identical copy, and both rows are appended; graded_at is never moved, so the time-range filters and the round's `audited_at` see the real grading time (`TestCRW838SameSecondRegradeWithAnotherResultIsRecorded`, `TestCRW838SameSecondRegradeWithTheSameResultSharesOneCopy`, `TestCRW838SameSecondBatchOfOneTargetIsRecorded`). A file that already holds the id with other bytes cannot come from this digest and is a real error: the row is refused as `result_copy_conflict`, not appended, and the file is left as it was (`TestCRW838ACopyWithOtherBytesUnderTheIDIsRefused`, `TestCRW838TheCopyComesBeforeTheRowAndIsAtomic`). Pinned by `TestCRW838OkRowCarriesAnIDAndAResultCopy`, `TestCRW838RegradingABundleKeepsTheFirstCopy`, `TestCRW838TheCopyComesBeforeTheRowAndIsAtomic`).
- `audit drafts` reads the copy of a row that has one, checked against the row's digest, instead of the bundle: a bundle graded again, rebuilt or carrying an unrecorded grade no longer takes the row's defects away. A copy that is missing or does not match is named in `skipped` and nothing is drafted from it (`TestCRW838DraftsRefuseACopyThatDoesNotMatchTheRow`). The pull request report reads the ledger columns only and never read `grade.json`, so it has nothing to switch; port: fixed.
- Rows written before this change have no id and no copy and are left as they are: no copy is made for them, they serialize without the new keys, and the drafts surface reads their bundle with the guards it always had (graded again, bundle declares another audit, unrecorded grade) (`TestCRW838OldRowsAreReadAsBefore`, `TestCRW838OldRowsStillHonourTheBundleGuards`); port: kept. The four review-744 tests that pinned the loss for a row graded now (`TestAuditDraftsReview744RegradeFromAnotherCwdVoidsTheBundle`, `...FailedRecordVoidsTheBundle`, `...ResolvedBundleSurvivesItsLink`, `...RelativeBundleUnderSymlinkedCwdIsOneBundle`) now expect the row to be read from its copy.
- The issue says the engine wrote `--bundle` as it was given. On this tree the ledger already records the absolute directory the grade ran in: `auditBundleResolvedPath` joins the working directory to a relative path without cleaning it (so a ".." after a link keeps the kernel's meaning) and resolves it, and `auditGradeOne` records that. That part needed no change and is pinned now by `TestCRW838RelativeBundleIsRecordedAbsoluteAndTheGivenTextIsKept`; what was missing is the text the caller gave, which a new `bundleGiven` key now keeps; port: fixed. A relative path is not refused (the decision's answer).
- The key names follow the decision text: `id` and `bundleGiven` as written there, and `result`, `result_sha256` for the copy's path and digest in the ledger's snake case; the keys are absent from rows that do not have them (`omitempty`).
- Two audit runs at once could both read the ledger for their targets before either appended a row, pick the same pull request, empty each other's bundle directory and leave two rows; port: fixed (`audit pr`, `audit package` and `audit round start` hold a non-blocking flock on `audit/audit-run.lock` for the whole run, and a second run is refused at once with `another audit run holds <path>` and exit 1, the status the existing busy refusals use. `audit pr --dry-run` writes nothing and `audit round status` only reads the round file, so neither takes the lock and `round status` still works while a package run is going. Pinned by `TestCRW838ARunRefusesWhileAnotherHoldsTheRunLock`).
- The newest-200 window of `gh pr list` could be all in the ledger, so older unaudited pull requests were never reached; port: fixed. gh orders a search by creation, not by merge time, so a full answer (200 entries) says nothing about which merge times it covers: a pull request created early and merged late can be the one `--limit` cut, at any merge time in the range. A full answer is therefore never taken as part of the list: its merge-time range is split in two (an open range is halved between its start and the later of the clock and the newest merge time it answered) and both halves are read the same way, until every half answers short, which is the whole of that range in any order. The ranges are read newer half first, so the entries read so far are every pull request merged from some time on: a newer unaudited pull request is never passed over for an older one, and stopping once the targets that never failed number `--max` leaves out only older ones. There is no page cap, because a cap stopped the reading at the same newest windows on every run. A full answer for a single second cannot be split and is the named error `pr_list_stalled`, not a short list; a merge time that does not parse refuses the run by name. Pinned by `TestCRW838ACreationOrderedSearchDoesNotLoseALateMerge` (a pull request created first and merged last, outside a first full answer of 200 audited ones, is still the target, through `auditPRRunWith`), `TestCRW838TheTargetsAreNewestMergedFirstWhateverTheSearchOrder`, `TestCRW838TheWindowIsReadOnPastTwoHundredAuditedPullRequests`, `TestCRW838AShortWindowIsNotReadOnPast`, `TestCRW838PaginationPastTenThousandAuditedPullRequests`, `TestCRW838PaginationStallIsAnError`; the test gh answers in creation order, as gh does, not by merge time.
- Attributing a pull request to the child that delivered it by the `markHistory` of the assignment answer is left out, as the decision says: the field does not exist in the code, and no follow-up is opened; port: kept.
