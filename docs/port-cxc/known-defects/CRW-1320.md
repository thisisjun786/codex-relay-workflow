# CRW-1320 — a run that started no node looked completed, told the lead nothing, and show offered a resume to a live run

Source: CRW's own design, not the CXC oracle: CXC v0.2.40 (commit 3c1459ac) has no flow engine, so there is no oracle line. The Go side is `internal/flow/cli/runs.go` (`Summarize`, `Blocked`, `nodeStarted`, `ItemError`), `internal/flow/cli/read_cmds.go` (`printDetail`), `internal/flow/cli/digest.go` (`stoppedWhy`), `internal/flow/cli/upward.go` (`UpwardFactory`) and `internal/flow/report/hook.go` (`RunHook.reportBlocked`, `BlockedReportID`). Found by the field trial of 10-13 (CRW-1315, items 42 and 32, D10, L7): run-39ba54c04cc5 had both of its `crw.release` calls refused, ended with status `completed`, result `incomplete`, lanes `[null,null]` and no error kind, `crw flow show` printed `completed`, and the initiative lead was sent nothing. The code positions are those of origin/dev a41dbb807; `Summarize`'s state switch (runs.go:327-331 there) and the resume hint (read_cmds.go:107-108) had not moved.

- A run whose releases all failed was shown `completed`: a refused release is an operation error (`internal/flow/cli/schedrelay.go`, `internal/flow/ops/lane_design.go`), the lane thunk of `crw.dag` throws, `parallel` writes an `item_error` row and gives the item `null` (`internal/flow/engine/scriptvm.go`, `itemFailed`), `project-lane.js` returns `incomplete` as a normal value and the engine ends the run `RunCompleted`, and `Summarize` read no `item_error` row; port: fixed. `Summarize` reads the `item_error` rows of the run's last process into `item_errors` (the item key from the path, the path, the error) and derives the state `blocked` for a run whose last process finished `completed` with nothing left to go on with (not `held`), when no process of the run started a node (no completed `crw.release` row with `released: true`, no completed `crw.releaseChild` row, no completed `crw.integrate` row) and at least one item threw. The engine's status, the exit codes, resume and apply are unchanged; the reading uses the lane's operation rows only, never the thread or turn rows. `crw flow show` prints `blocked` on its first line, `no node started: ...` and one `item <key> failed: <error>` line for each item; `ps` and both JSON forms carry the state and `item_errors`. `blocked` is over (`Over`), like `failed`: it is listed by `ps --all`, and `crw flow pause` and `crw flow cancel` refuse it as they refused the `completed` run it was. Pinned by `TestCRW1320_RunThatStartedNoNodeIsBlockedWithItsReasons` and, over a project-lane run, `TestCRW1320_MilestoneWhoseReleasesAllFailIsBlockedAndReportsOnce`.
- Waits and partial runs keep their state; port: kept. A node the scheduler held back unreleased in the last process (a completed `crw.release` row of kind `executor` with `released: false` and no hold: capacity, memory, a region in use, a plan that changed, which a resume asks again, CRW-1201) keeps the run `completed`, and so does a run where any node was released, a child was released or a node landed (`internal/flow/scenario/lane2_test.go`, `tier_test.go` stay as they are). The wait rule reads every unreleased executor answer, not only the capacity reasons, because each of them is asked again by a resume. Pinned by `TestCRW1320_StartedOrWaitingRunKeepsItsState` and `TestCRW1320_CapacityWaitAndPartialStartAreNotBlocked`.
- A run that started no node told the initiative lead nothing (L7: no `milestone_report`, no `project_blocked`); port: fixed. `report.RunHook.RunFinished` asks `Blocked` (the reading `crw flow show` prints, installed by `UpwardFactory`, so the report and the shown state cannot differ) and, for a blocked run, makes one `project_blocked` report through `report.Writer.Up`, the writer `crw flow report-up` and the milestone report use (the report row first, the recipient found by the linkage walk, the delivery through `crw manage send-parent --role supervisor`). The subject is `no node started` and the body names each failed item with its error. The report id is `BlockedReportID(run)`, derived from the run alone, so a resume that ends the same way replays the report row and makes no second report; an `unknown` delivery is asked again under the same logical id, as for every report. The delivery itself is today's report-up path; CRW-1314 changes how a report reaches the lead. `project-lane.js` does not throw (night-batch keeps its value). Pinned by `TestCRW1320_MilestoneWhoseReleasesAllFailIsBlockedAndReportsOnce`.
- `crw flow show` printed `N call(s) to go on with: crw flow resume RUN` beside `process P holds the run lock` (item 32), although `crw flow resume` refuses a locked run (`resume.go`); port: fixed. The hint is printed only while no process holds the run lock; without the lock it is unchanged. Pinned by `TestCRW1320_ShowGivesNoResumeHintWhileTheRunLockIsHeld`.
- The night-batch digest said `every selected issue was worked on and the run completed` for such a run; port: fixed. It says `blocked: no node started (<item>: <error>; ...)`. Pinned by `TestCRW1320_DigestSaysABlockedRunStartedNoNode`.
- The web runs page (`web/src/runs-state.ts`, `isOver`) does not list `blocked` among the states that are over, so it offers cancel on a blocked run, which the command refuses as for any run that is over; the page shows the state as it is given. The bundle (`internal/gui/assets`) is not rebuilt by this issue; port: pending.
