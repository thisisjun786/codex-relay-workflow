# CRW-756 — the orchestrate D close and its recovery branch

Source: CXC v0.2.40 (commit 3c1459ac) `plugins/codexclaw/components/pabcd-state/src/orchestrate-cli.ts`
:424-453 (the commit-hook interface and the two ledger-row readers), :726-750 (the receipt check and the
unbound close), :752-1015 (the goalplan-locked bound close, recovery branch included) and :1016-1064
(the finalize lock and the two closing texts). The port is
`internal/pabcd/cli/orchestrate_dclose.go` with the D place of
`internal/pabcd/cli/orchestrate_transition.go`, the three exported wrappers at the end of
`internal/pabcd/goalplan/workphase.go`, and the tests `orchestrate_dclose_test.go` and
`orchestrate_dclose_recovery_test.go`.

- The §35-8 refusal `orchestrate D: current C check epoch is required` is unreachable for a bound,
  non-recovering close: `validateCheckReceipt` runs first and its own `this check cycle predates
  CHECK-BINDING-01` branch answers when `checkEpoch` is absent (`orchestrate-cli.ts`:731-736
  before :958-963). The oracle has the same ordering, so the branch is dead there too; port: kept (parity:
  the port keeps the branch where the oracle has it and `TestOrchestrateDcloseRequiresTheCheckEpoch`
  pins the answer a bound session without an epoch actually gets).
- `readJsonlObjects` parses every line unguarded, so a damaged ledger throws and takes the whole D
  close down; the two readers built on it (`hasGoalplanRow`, `hasPabcdCloseRow`) then cannot answer
  and the close fails (`orchestrate-cli.ts`:431-453). The port reproduces the failure rather than
  skipping the bad line: a skipped line would answer `false` for a row that is really there and append a
  duplicate; port: kept (the error reaches the caller as a Go error, which is the oracle's throw). The
  Codex review of this pull request found the one line the first draft let through - a bare `null`, whose
  property access is the TypeError the oracle's `.some()` callback throws - and that line is refused too
  now (`TestOrchestrateDcloseFailsClosedOnADamagedLedger`).
- The unbound close publishes IDLE before it appends its done row (`orchestrate-cli.ts`:739-749), so an
  append that fails leaves the session resting with no record of the close and no route back: the FSM has
  no IDLE -> D edge, so the same request is refused and the row is lost for good. The bound close does not
  have this shape, because its marker makes a retry possible. Reported by the Devin review of this pull
  request (`kind`: bug, red) as "Unbound close permanently loses done row"; port: kept (the order is what
  the oracle holds and what the recorded fixture shows, and this port's rule is that parity wins over a
  review finding: `TestOrchestrateDcloseUnboundOrderIsTheOracles` pins the shape so a later issue changes it
  deliberately).
- The all-done close appends its C -> IDLE row inside the first lock and publishes IDLE afterwards
  (`orchestrate-cli.ts`:891-908 and :1021-1029), so a state write that fails before the rename leaves a done
  row beside a session still at C. Reported by the Devin review of this pull request as "Failed all-done
  close records completion"; port: kept (parity: the oracle's §40 Z2 comment chooses this order so the row
  cannot be lost to a second lock, and the leftover state is one the same D request reconciles, which
  `TestOrchestrateDcloseAllDoneStateWriteFailureReconciles` covers).
- The unbound close publishes IDLE before it appends its done row (`orchestrate-cli.ts`:740-748), so an append
  that fails leaves the session resting with no record of the close and no route back: the FSM has no
  `IDLE -> D` edge, so the same request is refused and the row can never be written. The failure is returned
  as an error rather than swallowed, and the bound path does not share the shape because its marker makes the
  same failure retryable. Found by the Devin review of this pull request (`kind`: bug, red) as "Unbound close
  permanently loses done row"; port: kept (parity: the issue body names this order as the answer - "the
  unbound close (cleared IDLE write, done ledger row, its text)" - and this port's rule is that an oracle
  defect is recorded rather than silently fixed. `TestOrchestrateDcloseUnboundOrderIsTheOracles` pins the
  shape so a later issue changes it deliberately).
- The all-done close appends its C -> IDLE row inside the first goalplan lock and publishes IDLE afterwards
  (`orchestrate-cli.ts`:891-908 and :1021-1029), so a state write that fails before the rename leaves a done
  row beside a session still at C. The leftover state is one the same D request reconciles: the row guard
  finds the row, the retry skips it, and the state reaches IDLE with exactly one row. Found by the Devin
  review of this pull request as "Failed all-done close records completion"; port: kept (parity: the oracle's
  own §40 Z2 comment chooses this order so the row cannot be lost to a failed second lock, and
  `TestOrchestrateDcloseAllDoneStateWriteFailureReconciles` covers the reconciliation).
