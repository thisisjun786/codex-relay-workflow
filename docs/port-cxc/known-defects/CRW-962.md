# CRW-962 — audit drafts: a posted severity raise is reported once, then recorded in the ledger

Source: CRW's own design, not the CXC oracle (CXC v0.2.40, commit 3c1459ac, has no audit drafts; the pointer is the port). The Go side is `internal/manage/audit_drafts.go` (`auditDraftCollect`, the posted branch of `auditDraftsRun`, `auditDraftRunMarkPosted`) and `internal/manage/audit_escalation.go`. The defect was found in the review of CRW-940 (#865, Devin and Codex P2).

- `audit drafts` reported the higher severity of a posted draft in `posted_escalations` on every run, because the ledger is append-only, a run without a range reads all of it, and a posted draft may not be written to (CRW-940 answer 2); port: fixed (the raise is recorded as one appended ledger line `{"kind":"escalation_posted","target":<draft fingerprint>,"from":…,"to":…,"at":…,"ref":…}`, written by `crw manage audit drafts --mark-posted <draft id> [--ref REF]` under the drafts lock, and a run does not report a raise for a target that has a posted line at that severity or a higher one. A raise above the posted one is reported again, `from` being the severity the issue now stands at. The draft file is never written. Pinned by `TestCRW962PostedEscalationIsNotReportedAgain`, `TestCRW962MarkPostedAppendsOneLedgerRow`, `TestCRW962AHigherEscalationIsReportedAgain`).
- `--mark-posted` takes `to` from the audits: the highest severity any ok row of the ledger reports for the draft's defect, over every severity and the whole ledger. It refuses a draft that is not posted (`not_posted`) and a draft no audit reported above the severity its issue stands at (`no_escalation`), writing nothing; the same mark again, once the ledger covers the raise, succeeds and writes nothing (`TestCRW962MarkPostedRefusals`, `TestCRW962MarkPostedAppendsOneLedgerRow`); port: fixed.
- A ledger line with a `kind` is not a graded result. The readers of results (the report, `audit list`, the pull request selection, the drafts surface) skip it and do not count it as a torn line, so the existing rows are read as before; a kind this build does not know is skipped the same way (`TestCRW962ExistingLedgerRowsAreReadAsBefore`); port: fixed.
- The decision says that a code path of crw that posts a raise writes the line right after the post succeeds. No such path exists: the product never writes to Linear (`audit_drafts.go` header) and the management session posts raises through its own connector, so `--mark-posted` is the only writer; `auditEscalationAppend` is the function a future posting path calls; port: kept.
