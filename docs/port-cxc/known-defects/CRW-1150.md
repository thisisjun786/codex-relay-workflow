# CRW-1150 — the SessionStart self-heal probe: a shared deadline and verified evidence

Source: `plugins/codexclaw/components/config-guard/src/cli.ts:140-149,167-196` and `self-heal.ts:151-262` at v0.2.40 (commit 3c1459ac); the Go side is `internal/runtime/install/configguard/selfheal_report.go` (`RunSelfHealReportHook`, `SelfHealReportRunner`, `SelfHealReport`), `selfheal_evidence.go` and `internal/runtime/install/features.go` (the `enable` branch). Found by the 10-10 CXC improvement review (A7-05) and handed to this issue; CRW-977 fixed only the PATH and the cut-short listing.

- The oracle's probe is `spawnSync` with no timeout and its allEnabled cache is written by the hook itself; CRW's report-only hook (J4, 2026-10-06) writes nothing, so without a marker an unhealthy or merely unmarked session ran `codex features list` at every SessionStart, and the probe had only the hook's outer 20 second limit (K1): `WithCancel` and a pipe-only `WaitDelay` let a 30 second listing run past 21 seconds (source `cli.ts:140-149`, `selfHealReportRunOne`); port: fixed (every codex call of one round shares a `selfHealReportProbeDeadline` of 8 seconds, started in `RunSelfHealReportHook`, and the candidate search stops at it; the pipe cleanup `selfHealReportWaitDelay` is 2 seconds, so a probe, its child and a grandchild that left the process group end the round inside 10 seconds. An overrun is a failed measurement: the round is silent and exits 0. Pinned by `TestSelfHealReportStalledProbeEndsInsideTheHookLimit` and `TestSelfHealReportEscapedGrandchildEndsAtTheSharedDeadline`).
- Repeated SessionStarts with an unchanged codex and config re-ran the listing each time (the oracle's cache needs a hook write that J4 removed); port: fixed (the explicit `crw install features enable` runs one more verified `features list` after it activated and records, in the self-heal marker's `probeEvidence`, that state with the `codex --version` line and the sha256 of config.toml it was measured against, only when config.toml did not move while it measured. The hook reuses the record only while the version line and the digest still match what it reads now and the record covers every soft flag: all on is silent without a listing, and a soft flag off still gets its notice at every SessionStart, so a resumed or compacted session keeps the guidance. A changed version or config, a record without a readable version, or a measurement that failed gives a fresh listing; an explicit disable (opt-out) drops the record. The hook still writes nothing. The mtime decides nothing in the new path. Opt-out and decline stay silent. Pinned by `TestSelfHealEvidence*` and `TestFeaturesEnableRecordsVerifiedProbeEvidence`).
- The oracle's own mtime cache (`allEnabled` + `cachedKeys` + `configMtimeMs`, recorded cases `mtime_cache_hit_skips_codex` and the moved-mtime miss) is unchanged for a marker that carries no `probeEvidence`; port: kept (a marker an older CXC wrote still short-circuits as before; CRW writes no such marker). A marker that carries a `probeEvidence` field, parsed or not (an older form without `layersSha256`, a damaged record), is judged by the evidence alone: the legacy cache is not consulted, so it cannot vouch ahead of a newer explicit finding or survive a codex version change. Recording evidence, dropping it after a recording attempt that could not measure, and rewriting a marker that carried it all set the legacy `allEnabled` to `false` (the oracle's own cache miss), so the mtime cache never regains authority once an explicit command has tried to record; port: fixed (`TestSelfHealEvidenceLegacyCacheDoesNotOutrankTheEvidence`, `TestSelfHealEvidenceFailedRecordingCannotResurrectTheLegacyCache`, `TestSelfHealEvidenceUnparsableRecordDoesNotRestoreTheLegacyCache`).
- The evidence describes the effective configuration, not only the user-level `config.toml`: besides the codex version and the config digest it records `layersSha256`, a fingerprint of the layers codex reads for a run in the hook's working directory (`.codex/config.toml` of the working directory and each ancestor, `/etc/codex/{config,managed_config,requirements}.toml`, and the codex home's `managed_config.toml` and `requirements.toml`; an absent layer contributes nothing, so one appearing changes it). The explicit command records it for its own working directory and the hook reuses the record only when the fingerprint of its own working directory is the same, so a project soft flag changed after `enable`, or a session in a different project that has its own layer, gets a fresh listing. A working directory reached through a symbolic link is walked both as given (the hook's logical PWD) and as the physical directory it resolves to (the getcwd codex runs with), so a layer in a physical ancestor counts too. Every fingerprinted file (config.toml and each layer) is opened without blocking and must be a regular file of at most 8 MiB: a FIFO, a device or a directory there is a layer that cannot be read, never a read that waits past the hook's shared deadline. When the working directory is not known or cannot be resolved, or a layer cannot be read, nothing is recorded and nothing is reused. A record without `layersSha256` (written by the first form of this change) is no record. Environment-level overrides (`-c`, profiles) are not visible to a hook and are not fingerprinted; port: fixed (`TestSelfHealEvidenceProjectConfigChangeMeasuresAgain`, `TestSelfHealEvidenceDifferentProjectMeasuresAgain`, `TestSelfHealEvidenceAncestorProjectLayerMeasuresAgain`, `TestSelfHealEvidenceUnknownWorkingDirectoryIsNeverReused`, `TestSelfHealEvidenceSymlinkPhysicalAncestorChangeMeasuresAgain`, `TestSelfHealEvidenceFifoLayerHonorsTheDeadline`, `TestSelfHealEvidenceFingerprintRefusesFilesThatAreNotRegular`).
