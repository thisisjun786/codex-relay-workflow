# CRW-1353 — the child's skill and documents follow the session call path and the way a child works

Source: CRW-1316 design sections 13 and 18 (`/state/crw/mgmt/design-1316/design.md`, Jun's 10-14 04:3x decision relayed by Sion) and the carry-over d1 and d2 of the CRW-1352 evaluation (`/state/crw/mgmt/pre-eval/crw1352-8682efdb.json`), not the CXC oracle (CXC v0.2.40, commit 3c1459ac): the oracle has no flow run, no session call and no layer table. The skill is `plugins/crw/skills/crw-run/SKILL.md`; the code is `internal/role/dispatch_card.go` and `internal/flow/ops/rules.go`.

- crw-run made the dispatch of an independent child for each issue its whole procedure and gave a flow run one section whose thread "handles only two things": it did not say that a session run's agent calls are steps the child spawns as role subagents, nor how; port: changed (the opening makes the flow run with role subagents the default path and the issue child of an oversized issue, SP-CHILD-1, the exception; "Run a milestone with a flow run" carries design section 3.2's loop: `crw flow next RUN --wait 600 --json`, a `spawn` step as `spawn_agent` with the step's `agent_type`, `message`, `model` and `reasoning_effort` and `fork_context` false followed at once by its `crw flow dispatched` line, a `send_input` step, a `close` step as `close_agent`, `wait_agent` alternating with `next --wait`, `pair_mismatch` and `agent thread limit reached` leaving the step, no copied answer, the run resumed by `next`; the preview, epoch, apply and report-up rules are kept; "Independent implementation tasks" says it is the exception path and that the rule against a subagent standing in for an issue child holds on that path only, a role subagent being a step the run records). Pinned by `TestChildSkillRunsTheSessionLoop`, `TestChildSkillDefaultPathIsTheFlowRun` and `TestRunProjectNeverClaimsRunEpoch` (which now reads "the issue child of an oversized issue").
- The way a child works (design sections 18.2 to 18.5) was in no skill; port: changed ("How the child works" under the flow run section: the child splits the work and spawns subagents broadly, runs them in parallel and decides the next step from their results; inside a run the project lane decides by its results within `cap`, `--pool`, `after` and the edit regions, outside it the child's own helpers are allowed and recorded; the fixed sequence architect, design audit by another family, executors in parallel, a reviewer of another family, a fix round, verification and landing, with an explorer whenever it is needed; the child decides whether to use the DAG while CRW enforces the order, the gates and the records; `agents.max_threads` is the cap; ambiguity goes up as a decision request and never opens an interview; the pull request bundle is only named, with CRW-1354, CRW-1355 and CRW-1356 as the later places). Pinned by `TestChildSkillSaysHowTheChildWorks`.
- The canon's flow page had neither `crw flow next` nor `crw flow dispatched` and named the owner thread "the orchestrator thread"; port: changed (both commands are rows of the command table and a section of their own, `crw flow start` names `--backend` with session as its default, and the ownership table has a row for the step exchange of a session run). Pinned by `TestFlowPageNamesTheStepExchange`.

Pinned by `TestDispatchCardUsesRoleKeyWhenFlowBound`, which now also reads those words.
