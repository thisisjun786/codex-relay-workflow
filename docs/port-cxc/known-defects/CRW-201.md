# CRW-201 — the CRW/CXC switch: what the oracle's editors do not give back and what Codex does to the switched key

Source: the CRW-201 decision of 10-10 (Claude Code, coordinator). CXC v0.2.40 (commit 3c1459ac) has no switch: its config-guard touches only `[features]` (config-guard/src/toml-edit.ts, activate.ts, deactivate.ts, managed-keys.ts) and `memories.dedicated_tools`, and its activation of the plugin is Codex's own `[plugins."codexclaw@codexclaw"] enabled = true` (scripts/dev-install.sh does `codex plugin add` and the marketplace, nothing else); its role registration (subagent-config/src/role-registration.ts) refuses a role file it does not own. The Go files are internal/runtime/install/switch_cmd.go (`crw install switch`), internal/runtime/install/configguard/switch.go, switch_record.go, toml_exact.go and manifest.go (the `switch` section), internal/runtime/install/switchstate/switchstate.go (`<CODEX_HOME>/crw/switch.json`) and internal/role/owner.go.

- `restoreTableKey` writes the recorded prior value as `key = <value>` and `setTableKey` writes `key = <value>`, so a line the user spelled `enabled=true`, with tabs, or in a CRLF or mixed-ending file does not come back byte for byte; the file's line endings are also rewritten to the dominant one (toml-edit.ts setTableKey, restoreTableKey; port: kept for `features` keys and `memories.dedicated_tools`, whose records hold a value and not a line, and the oracle's fixtures pin it. For the switch the port records the key's line verbatim and puts exactly that line back with `ReadTableKeyLine`, `SetTableKeyExact` and `RestoreTableKeyExact`, touching no other byte of the file: fixed for the switch. Cases: TestSwitchRoundTripGivesTheConfigBackToTheByte (eleven spellings, CRLF, mixed endings, no final newline, a missing key, a missing table), TestExactEditGivesBackWhatTheOracleEditorNormalises, TestSwitchTwiceKeepsTheFirstValues).
- Codex CLI 0.154.0 turns the key back on: `codex plugin add codexclaw@codexclaw` run again for an installed plugin, after a version change and after `codex plugin remove` all leave `[plugins."codexclaw@codexclaw"] enabled = true` whatever the key held (measured in an isolated home against a fixture marketplace standing in for codexclaw 0.2.40; `codex plugin update` does not exist in this version and `marketplace upgrade` refuses a local marketplace; the log is the handoff's codex-plugin-measurement.log and the script is codex-plugin-measurement.sh); port: kept (a Codex behaviour the switch cannot prevent; `crw install switch status` reports `conflict` when `switch.json` says crw and the CXC plugin is on again, and `crw install switch crw` puts the key right and keeps the values from before the first switch. Cases: TestInstallSwitchStatusNamesConflictAndOff and, with a real Codex binary when one is on PATH, TestSwitchRehearsalReinstallThenReturn).
- `ApplyManagedKey` (`crw install config set`) refuses without an install manifest, as the oracle's config-set does, and `switch` writes a minimal manifest (version 2, no flags, no tableKeys, a `switch` section) when none exists, so a host that never ran `features enable` can then `config set` a managed key; `Deactivate` restores that key's record as it does for any other and never rewrites the manifest or the `switch` section; port: kept (the manifest is the one record of what crw changed in config.toml; Deactivate with a switch-only manifest reverts nothing and reports no flags).
- `Activate` builds a new manifest on every run, so a `switch` section written before `features enable` would have been dropped; port: fixed (Activate carries the prior section over unchanged; ApplyManagedKey parses and rewrites the manifest, so it keeps the section. Case: TestSwitchSectionSurvivesTheOtherManifestWriters).
- The decision orders the steps of `switch crw` as `switch.json` first, then the CXC key, then the role files, so for the length of the command the CRW hooks may read `active:"crw"` while the CXC plugin is still enabled in config.toml (Codex reads the key at session start); port: kept (the order is the decision's; a step that fails is undone, and a command that died leaves a `pending` section that running it again finishes from the recorded values).
- A role file is replaced only when it is owned: `# codexclaw-managed: <sha256 of the rest>` or `# crw-managed: <sha256 of the rest>` with a digest that matches. A file with another first line, or with a marker whose digest no longer matches the rest, is the user's and is kept (`kept-other`, `left-modified`), in both directions; the CXC backups `executor.toml.backup-<hash>` that CXC leaves in agents/ are not read or removed; port: kept (CRW-registration's `# crw-managed:` rule, extended to the CXC marker; name-substitution R17).
- `switch cxc` puts the recorded line back unconditionally, so a CXC key the user changed by hand after the switch is overwritten by the value from before the switch; port: kept (the command is the explicit return, and the config.toml copy `config.toml.crw-<ts>.bak` taken before the change keeps the bytes it overwrote).
- The hook-trust summary of `switch status` needs the installed CRW package: `--plugin-root`, `$PLUGIN_ROOT`, or exactly one `plugins/cache/*/crw/*` package with a manifest; with none or several it reports `available:false` and the reason, and reads no other path; port: kept.
- Round 1 of the verification (all fixed): the CXC role file's backup path was held in memory until the end, so a command that died after replacing a role file lost the way back; the backup is now recorded in the pending section before the file is replaced, a CRW role file with no recorded backup on the way back is an error, and the way back is pending too. A CXC plugin table that appeared after the first switch is switched off by the next `switch crw`. The manifest's `postActivateHash` follows the switch only while `config.toml` is the file the activation left (the pending section keeps the hash of the file about to be written, `configHash`), so a drifted file stays drifted for Deactivate. An existing CRW role file that differs from the build's template is kept (`kept-crw`), not rewritten without a backup. `switch status` counts the CRW side as on only when `crw@crw` is enabled. Cases: TestSwitchDiedAtEveryBoundaryIsFinishedAndReturnsToCXC, TestSwitchBackToCXCLeavesAPendingSectionWhenItDies, TestSwitchTakesUpACXCTableThatAppearedAfterTheFirstSwitch, TestSwitchKeepsTheActivationDriftHonest, TestSwitchKeepsAnExistingCRWRoleFile, TestInstallSwitchStatusReadsTheCRWPluginsOwnKey.
- Round 2 of the verification (all fixed): the oracle's key grammar sees only the bare `enabled`, so a table that spelled it `"enabled"` got a second `enabled` line Codex cannot read; the switch's exact editor reads both quoted spellings as the key, edits that line in place and refuses the key on two lines. A CXC role file that appeared after the first switch is recorded as the file to restore (`priorOwner`, backup) before it is replaced. A key that holds a value form crw will not rewrite is refused before any write on every run and in both directions, not only on the first `switch crw`, and the record stays. The way back inserts a recorded line the user deleted since, and refuses, keeping the record, when the table is gone. The way back removes or replaces a CRW role file only when its SHA-256 is the one the switch recorded when it installed the file. An `agents` directory that is a symlink is refused before any role file is read or written, as RegisterRole refuses it (the check is repeated before each write; like RegisterRole, the switch writes by path and not through a held directory descriptor). Cases: TestSwitchEditsAQuotedEnabledKeyInPlace, TestSwitchRestoresACXCRoleFileThatAppearedAfterTheFirstSwitch, TestSwitchRefusesAnUnsupportedValueAfterTheFirstSwitch, TestSwitchBackRestoresADeletedKeyLine, TestSwitchBackKeepsACRWRoleFileUpdatedSince, TestSwitchRefusesASymlinkedAgentsDirectory, TestExactRestorePutsADeletedLineBack.
