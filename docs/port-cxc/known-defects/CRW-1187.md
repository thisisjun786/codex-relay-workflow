# CRW-1187 — a module run executed code the inventory did not read: shadows of any standard-library name, writers beside the run, and sources that move the imports

Source: the CRW memory and GitHub post guards, not the CXC oracle (CXC v0.2.40, commit 3c1459ac, has no command reader and never read a module run). The Go files of the port are `internal/pabcd/shellir/modules.go`, `modules_names.go`, `modules_source.go`, `env.go` and `shellir.go`; both guards (`internal/pabcd/hook/memorygate.go`, `githubpost.go`) take the reading from there. Found by the independent verification of CRW-1178 (round 8, three P2 findings that were already at the base); the issue is CRW-1187.

- `python3 -m json.tool` and `-m py_compile` read no inventory and refused only a fixed list of local shadow names, so the modules Python 3.14 imports after it sets `sys.path[0]` (keyword, reprlib, fnmatch, dis, weakref, `_colorize`, annotationlib, compression, textwrap and more) ran from the working directory as `keyword.py` or `keyword.pyc` (end to end with the real interpreter: `keyword.py` writes the memory note under `python3 -B -m json.tool` and `-m py_compile`); port: fixed (security). For these two modules a file, a compiled file, an extension or a package of the working directory with the name of any standard-library module is refused (`stdlibModuleNames` in `modules_names.go`: the names of `sys.stdlib_module_names` and `sys.builtin_module_names` of Python 3.14.4, the modules of 3.8 and 3.9 that later versions removed, the site-startup names; and any name that starts with an underscore, which covers the private modules a version adds), unless the run leaves the directory out of `sys.path`. The reason names the file and the route (`run python -I -m json.tool ...` or move the file). `-I` is that exception; `-P` is it only when PYTHONPATH is proven unset (the text neither spells the name nor may build a variable name at run time, and the hook's environment does not set it), because `-P` alone keeps PYTHONPATH (checked with the real interpreter: `PYTHONPATH=. python3 -P -m json.tool` imports the shadow). Version handling: a public module a future version adds is not covered until the list is refreshed; `TestCRW1187StdlibListCoversTheHostInterpreter` fails when the interpreter on the host has a module name the reader would not refuse as a shadow. unittest and pytest keep the narrower list for the names their own imports use (their sources, packages and compiled files are walked and read by the inventory).
- The check for a writer to an import location (a carried program, an archive extraction, a redirection or a copy-like command to a code path or an unknown destination) looked only at the records before the module run. A record that runs at the same time can create the module a test imports later; port: fixed (security). The records of a text are now also judged when they run beside a module run: another stage of the pipeline it is in (`python3 -m unittest | tee late.py`), a background job or a coprocess on either side, and a process substitution. A command that runs after the module has ended (`;`, `&&`, a later statement) is not judged, so `python3 -B -m unittest; printf x > late.py`, `python3 -B -m unittest | tee out.log` and `sleep 1 & python3 -B -m unittest` stay allowed. Not modelled: a background job a text starts that outlives its own statement and is awaited elsewhere is judged by the same rule (refused when it can write a module file, on either side).
- A test module (or a conftest, a helper, a package initializer) read by the inventory could itself move the imports: `sys.path.insert`, `sys.pycache_prefix` (which `python -E -B` does not stop), importlib loaders by path, a `.pyc` copied and imported; the run then loaded code outside the inventory, and `-I` does not prevent it (the interpreter still lets the source change `sys.path`; end to end with the real interpreter: under `python3 -I -B -m unittest` the module's own `sys.path.insert` loaded a directory that wrote the memory note); port: fixed (security). The reader now scans the text of every source of a unittest or pytest run at token level and refuses, as unreadable with the file and the construct in the reason: any use of `sys.path`, `sys.pycache_prefix`, `sys.meta_path`, `sys.path_hooks`, `sys.path_importer_cache` or `sys.__dict__` (also through `import sys as s`, `from sys import path [as p]`, `from sys import *`, `getattr`/`setattr`/`vars` on the module, and `"sys"` fetched by name); any `importlib` attribute but `import_module`, `reload`, `invalidate_caches`, `resources` and `metadata` (also through `import importlib as il`), `importlib.machinery` and `importlib.util` and the loader and finder names (SourcelessFileLoader, SourceFileLoader, spec_from_file_location, ...); `__import__` and `import_module` (and a name given to them with `as`) called with anything but one plain module name, or mentioned other than in an import statement; `getattr`, `setattr`, `vars` on `sys`, `importlib` or `builtins`; `__path__` and `submodule_search_locations`; `imp`, `runpy.run_path`, `zipimport`, `marshal`, `compileall`, `py_compile`, `site.addsitedir`; PYTHONPATH, PYTHONPYCACHEPREFIX and PYTHONHOME in the text; and a name that ends in `.py`, `.pyc`, `.pyd`, `.so`, `.pth` or holds `__pycache__` together with a call that writes, copies, moves or links a file (`open` in a write mode, `write_text`, `shutil.copy`, `os.replace`, ...). The reason does not offer `python -I` as a route for these (it does not stop them): remove the construct from the test sources, or keep the code to run in the project files. py_compile only compiles its operands and imports nothing from them, so their text is not scanned. What stays allowed: an ordinary import, `importlib.import_module` and `importlib.reload`, `sys.argv`, `sys.exit`, `sys.modules`, `sys.executable`, `sys.stdout`, `mock.patch('sys.stdout')`, writes to files that are not module files, `copy.deepcopy`, `str.replace` next to a `.py` name. The reader's general limit stays: Python the text builds or reads at run time and runs with `exec` is not claimed. Measured with the real interpreter (`TestCRW1187EveryWorkingImportMechanismIsRefusedByBothGuards`, 37 mechanisms that load code from outside the project, among them `sys.path` in six forms, `getattr`/`vars`/`__import__`/`import_module` with a name built from pieces, a finder, `spec_from_file_location`, a sourceless loader, a copy, link, rename or write of the module into the project, `runpy.run_path`, a package's `__path__`, `site.addsitedir`, a subprocess with PYTHONPATH): every one is refused by both guards, except `exec(compile(open(outside).read(), ...))` and `exec` of a string built from pieces, which the memory gate refuses and the GitHub post guard does not (it does not refuse `exec` in any program, with or without a module run); port: kept (outside this issue).
- The friction of that scan, measured on the test-named Python files of the host (`/usr/lib/python3`, 1021 files of numpy, pytest, twisted, systemd and more; `/usr/lib/python3.14`, 69 test files): 91 of 1021 and 12 of 69 are refused, nearly all test infrastructure that sets `sys.path` or builds extension modules (34 `sys.path`, 30 file writes at an import location, 11 `sys` by name, 7 importlib.util or machinery, 3 PYTHONPATH). An application's own tests that import its package from the working directory are not touched. A project whose tests need `sys.path.insert` is refused and has to run those tests another way (a separate command that the guards judge, or a layout that needs no path change).
- Tests: `TestCRW1187*` in `internal/pabcd/shellir` (the shadows as source, compiled file, extension and package for json.tool and py_compile; `-I` and `-P` and the PYTHONPATH cases; the list against the host interpreter; every writer beside the run on either side and the sequential and harmless companions that stay allowed; the table of source constructs, each under unittest, `-I`, `-E -B` and pytest, with conftest, helper, package and ancestor sources; the ordinary sources that stay allowed; the kept runs: no cache, `-B` after a separate removal, `-E -B`) and in `internal/pabcd/hook` (both guards, with the real interpreter in a temporary home: the shadow and the module's own `sys.path` and `sys.pycache_prefix` ran before the change, are refused now, and the `-I` and plain runs the reasons lead to are allowed).
- Verification round 1 (four P0, one P1; all fixed). (a) Source scanning missed three static spellings of `sys.path.insert` (the interpreter ran the unread module in each): an explicit line join inside the chain (`sys.\` + newline + `path`), an alias spelled with characters Python folds to ASCII (`import sys as` a mathematical-script s; Python normalizes identifiers to NFKC), and a string with a bracket before the import statement that names the alias (the statement splitter counted the bracket of the string). The source is now lexed first (`pyLex` in `modules_source.go`): strings (single, double, triple, any prefix), comments, explicit line joins (read as a space), brackets, and statements split at a newline, semicolon or colon outside strings and brackets, so the statement after a compound header is its own (`if x:import sys as s`). The scans run on the text as written and on the text without comments and line joins; a character outside ASCII in code (outside a string and a comment) is refused with the reason, because Python folds it to a name the regular expressions cannot see (a byte order mark and non-ASCII text in strings, comments and docstrings stay allowed). The same lexer closes `sys` reached through another module (`os.sys.path`, `from os import sys as s`, `s = os.sys`): a `.sys` attribute in code (strings are blanked in the code view, f-strings are not) and a `sys` imported from any module but sys are refused. Not claimed: binding sys to a second name by assignment (`s = sys`) or passing the module as an argument; that is the reader's general limit (Python the text builds at run time). (b) `sort -o/--output FILE` in the pipeline of a module run was not seen by the writer check, so `python3 -B -m unittest | sort payload.txt -o late.py` created the module the test imports. The reading of sort's command line the write gate already had (every spelling getopt_long accepts) moved to `shellir.SortOutputDests` and both the gate and the module-run reader use it; the check also refuses a code-path operand of uniq, split, csplit, patch, rsync, gzip, bzip2, xz, zstd, zip and sed beside the run. (c) The GitHub guard did not read the hook's PYTHONPATH (`githubPostEnv` answered only PYTHONPYCACHEPREFIX), so `-P` was taken as safe while `PYTHONPATH=.` put the shadow back on the path (real interpreter: the shadow ran). It reads PYTHONPATH now, and a reading that is given no environment at all proves nothing for `-P` (only `-I` is safe then); the memory gate's reading without the session environment keeps PYTHONPATH from it, so its three readings agree. The worktree deletion guard, which reads with no environment, therefore refuses a `-P` run of json.tool or py_compile in a directory that holds a standard-library name (use `-I`). (d) The `-I`/`-P` exception applied only to names outside the fixed list, so `python3 -I -m json.tool d.json` was refused beside a `json.py` although the interpreter does not import it. A json.tool or py_compile run that leaves the directory out of `sys.path` (proved as before) now skips the shadow check for every name, fixed list included, packages and compiled files too; the writer checks (before and beside the run) and the unittest/pytest inventory are not excused by it. Tests: `TestCRW1187FixRound1*` in `internal/pabcd/shellir` and `internal/pabcd/hook` (the verifier's probes against the real interpreter, the spelling table through both guards, the sort spellings, the PYTHONPATH matrix with no, unset, empty and set environments, and the ordinary sources, `-I`/`-P` runs and sequential sorts that stay allowed). The existing `-P` rows of `crw1187_test.go` now run with an environment that is known and holds no PYTHON* variable.
- Verification round 2 (five P0; all fixed). Each ran `evil.py` from outside the inventory under `python3 -B -m unittest` with both guards allowing it. (a) `(sys).path`: the attribute scans required the dot right after the name. They now allow what a bracket around the name gives before the dot (`(sys)`, `((sys))`, `(s := sys)`, `(sys or x)`, `[sys][0]`, `(sys, x)[0]`, `{'k': sys}['k']`, across lines inside the bracket) for sys and for importlib and builtins, and `getattr((sys), ...)` is a `getattr` on sys. (b) `from builtins import __import__ as f` (and `from importlib import __import__ as f`) is a name given to `__import__` like `import_module as f`, so its calls get the same plain-name check; `getattr`, `setattr`, `delattr`, `vars`, `globals`, `locals`, `eval`, `exec` and `compile` imported from builtins under another name are refused, and `__builtins__` is read as builtins (`getattr(__builtins__, ...)`). (c) `(__import__)(...)`: a mention of `__import__` or `import_module` that is not called was allowed after `(` or `,` as if it stood in an import statement. It is allowed now only in a statement that is a whole import statement (`import ...`, `from ... import ...`), so a reference in brackets, a list, a tuple or an argument is refused. (d) A name Python folds to sys inside the replacement field of an f-string (`f"{ｓｙｓ.path.insert(0, LIB)}"`) was not seen, because the whole f-string was string text to the non-ASCII check. (e) Python 3.12 (PEP 701) lets the expression of a replacement field hold the quote of the f-string itself (`f"{d["k"]}{(s:=os.sys)}"`): the lexer closed the f-string at the inner quote and blanked the rest as a plain string, hiding `os.sys`. The lexer now reads f-strings and t-strings (3.14) by their replacement fields: the literal text, `{{`, the expression with its brackets and nested strings in any quote (an f-string inside one too), and the format spec with its own nested fields; a non-ASCII character in an expression is refused as in code, and a comment in a replacement field or a backslash before a brace or `N` (`\N{...}` is an escape in one string and a field in a raw one) is refused as a form the reader does not split. A string prefix is the whole name before the quote (`if"x"` is the keyword if and a plain string, no longer an f-string). Friction on the 821 test-named files of `/usr/lib/python3/dist-packages`: one more refusal than before the round (a numpy test that calls `getattr(__builtins__, ...)`); no f-string or import-reference refusal there. Tests: `TestCRW1187FixRound2*` in `internal/pabcd/shellir` (34 spellings refused, f-strings with non-ASCII text, nested quotes, specs and plain imports allowed) and `internal/pabcd/hook` (the verifier's five probes against the real interpreter, refused by both guards).
- Pre-merge evaluation of 9201b469 (three P0, three P1/regressions; all fixed). (a) `-P` with PYTHONPATH named from known parts (`N=PYTHON; M=PATH; printf -v "$N$M" '%s' .; python3 -P -m json.tool d.json`): the walk did not see the name, the lookup still answered the empty environment, and the run was taken as isolated, so a local `json.py` was executed unread. A word given to an assigning builtin that holds PYTHONPATH now counts as the text naming it (`pythonPathNamed`), as does a carried text; `-P` proves nothing then. (b) `-E` makes the interpreter ignore PYTHONPATH, so `-EP` leaves the working directory off `sys.path` whatever the environment holds (checked with Python 3.14 and 3.11: `PYTHONPATH=. python3 -EP -m json.tool` ignores a local keyword.py or json.py, `-P` alone and `-E` alone do not); `moduleSafePath` was ignoring -E and refused a safe `-EP` run when the inherited PYTHONPATH was non-empty, and with no environment. `-EP` is safe with any environment now. (c) The exported `MemoryGateCommandReadable` called `shellir.Analyze` with no environment while the gate reads `memoryPlainReading` (PYTHONPATH from the session), so the differential fuzz counted an allowed `-P` run as unreadable-not-refused; it uses the gate's reading now. (d) The module-source check knew os, shutil, posix and pathlib only under those names, so `import shutil as sh; sh.copy('payload.txt', 'late.py'); import late` copied unread text onto an import location (and imported it) with both guards allowing the run. Names the source gives to those four modules are matched against the writing attributes like the modules' own names (copy, copy2, copyfile, copyfileobj, copytree, move, rename, renames, replace, link, symlink, extract, open, fdopen, unpack_archive, make_archive), a path object moved onto a code name (`Path('x').rename('late.py')`, one operand that is a code name; `str.replace('.py', '')` has two) and `.extract(` are read as writers, and the rule keeps its condition that the source spells a name ending .py, .pyc, .pyd, .so, .pth or in `__pycache__`. Not claimed: a write through a name the source builds at run time (`'late' + '.py'` split across strings, `getattr(os, name)`), through `subprocess`, or by a library that writes a file of that name for another purpose; that is the reader's general limit. (e) The writer check beside a module run (a background job, a coprocess, a process substitution, the same pipeline) and before it ignored an operand it could not evaluate for uniq, split, csplit, patch, rsync, gzip, bzip2, xz, zstd, zip and sed (`read OUT <<< late.py; python3 -B -m unittest | uniq payload.txt "$OUT"` wrote the module the test imports). Such an operand is held against them as against cp, tee and sort now, and shuf, iconv, xxd, openssl, gpg, ar, cpio, bsdtar, 7z, jar, ed, ex and truncate join the list. A sed or awk with a program of its own was already refused beside the run. Not changed: git (`git checkout` rewrites files; the reader does not model it for module runs, as before). (f) The Python 3.12-only end-to-end probe (PEP 701, the quote of an f-string inside its field) is a syntax error on Python 3.11; the real-interpreter step is skipped there and the static refusals stay asserted (`crw1187PEP701`). Friction: no change on the 769 test-named files of `/usr/lib/python3/dist-packages` (evidence/fix3/friction-diff.txt is empty).
