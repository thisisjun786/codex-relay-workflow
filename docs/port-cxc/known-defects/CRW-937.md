# CRW-937 — the manifest-target walk keeps the kernel's component order

Source: the oracle's shared validator `plugins/codexclaw/components/cxc-ops/src/manifest-targets.ts` at CXC
v0.2.40 (commit 3c1459acadeb1906d97c00a598e1457327ae372d): `escapesRoot` (:105-117), which calls
`realpathSync` on both paths and falls back to `resolve` when either throws; and the oracle's doctor
drift check `plugins/codexclaw/components/cxc-ops/src/doctor.ts` (:543-596), whose `drift:mcp` branch
reads `join(pluginRoot, manifest.mcpServers)`. The port is `internal/runtime/doctor/manifest_targets.go`
(`manifestTargetsRealpath`, `manifestTargetsFollow`, `targetEscapesRoot`, `targetResolve`, `targetCheck`,
`ValidateManifestTargets`) and `internal/runtime/doctor/harness_drift.go` (`harnessDriftMCPCheck`).

- The oracle's `escapesRoot` resolves a symlink's target with Node's `fs.realpathSync`, whose JavaScript
  implementation resolves each link target LEXICALLY (`path.resolve(previous, linkTarget)`, modeled at
  `manifest_targets_realpath_test.go` `targetOracleRealpath`), so a `..` inside a link target is dropped
  against a lexical prefix. The port followed that shape, so with `root/sublink -> ../outside/deep` and
  `root/bad.json -> sublink/../hook.json` the walk answered `root/hook.json` while the kernel
  (`filepath.EvalSymlinks`) answers `<base>/outside/hook.json`: an outside hook JSON was judged inside
  the plugin root and read (found by the pair evaluation of PR #765 (CRW-840), score 5, reproduced on
  dev 9a7fcae2); port: fixed (the walk now splits a link target into its components without joining or
  cleaning them, puts them in front of the components still to walk and keeps walking, so a `..` climbs
  one level from the directory the walk has physically reached. The depth ceiling, the stat before the
  readlink and the paired lexical fallback stay as CRW-840 and CRW-652 left them. This is a deliberate
  divergence from the oracle: the oracle case is recorded as intentionally changed, and the port now
  agrees with `filepath.EvalSymlinks` on every reachable shape).
- The walk was not the only place that resolved a path. `targetResolve` built the target with
  `filepath.Abs(filepath.Join(root, rel))` and `manifestTargetsRealpath` began with `filepath.Abs(path)`,
  so a manifest target or a hook command whose own spelling named a link followed by `..`
  (`./sublink/../hook.sh`) had that `..` dropped before the walk saw it: the verdict described
  `root/hook.sh` while the command really opens `<base>/outside/hook.sh` (found by this pull request's
  pre-merge evaluation, defect d1); port: fixed (`targetResolve` concatenates instead of joining and
  `manifestTargetsRealpath` makes the path absolute with `manifestTargetsAbsolute`, which keeps the
  caller's spelling, so every component including `..` reaches the walk in kernel order. Only what the
  oracle's `path.resolve` drops for a path that holds no `..` -- `.` components, doubled separators and a
  trailing separator -- is dropped first (`manifestTargetsCollapseDots`), so a path with no link and no
  `..` is judged exactly as before. A `..` after a component that does not exist is now the kernel's
  ENOENT rather than the oracle's lexically resolved path, the same deliberate divergence as above).
- The oracle's `drift:mcp` reads `join(pluginRoot, manifest.mcpServers)`, and the port keeps the
  oracle's `path.join` trailing separator while deliberately refusing a reference that resolves outside
  the plugin root. It built that path with `filepath.Join` before the containment check, so a reference
  spelling a link followed by `..` (`./sublink/../mcp.json`) was cleaned to the inside `root/mcp.json`
  and read as a decoy while the manifest-target walk refused the same reference: two judgements of one
  manifest field disagreed (found by this pull request's pre-merge evaluation, defect d1); port: fixed
  (the reference is resolved with `targetResolve`, so the containment check walks every component in
  kernel order and the port's deliberate refusal of an outside reference sees the file the reference
  really names. The oracle's own lexical answer is unchanged for a reference that holds no link and no
  `..`; for one that does, the port now diverges from `path.join` the same way it diverges from
  `path.resolve` above).
- The walk accumulated the path it had already resolved and never compacted it, so a link target made of
  many `./` components (no `..` at all) grew the string until `os.Lstat` answered `ENAMETOOLONG`. The walk
  then returned an error, `targetEscapesRoot` took its paired lexical fallback, and a file outside the
  root was judged inside it (found by this pull request's own audit review, blocker B1); port: fixed
  (the already-walked prefix is compacted with `filepath.Clean` after its component is found not to be a
  symlink, which cannot change the answer because such a prefix's lexical parent is its physical parent,
  and a regression test pins it).
- The same class (a `Join` or `Clean` removing a `..` after a link) appeared the same day in CRW-923 and
  CRW-924, which cover `internal/manage` and do not touch this file; port: kept (their files are their
  own issues' edit regions, and this issue's scope is the doctor manifest-target judgement only).
- Supersedes known-defects/CRW-840.md, item beginning "manifestTargetsFollow read a symlink component's
  target": now port: fixed (that item recorded the lexical `Clean` of the link target as the oracle's
  behaviour and noted that the earlier plan to join it without cleaning would diverge from `realpathSync`.
  The containment check now walks the target's components in kernel order and the lexical Clean is gone,
  which is the divergence that item declined to take. The rest of that item -- the `os.Stat` before
  `os.Readlink` -- is unchanged).

Four further defects this pull request introduced and fixed inside the same pull request, found by its
own pre-merge evaluation and with no released state to record a port status for:

- The concatenation in `targetResolve` left a target's trailing separator and its `.` components on the
  `Stat` below, so an ordinary target with no link and no `..` (`./mcp.json/`, `./mcp.json/.`) was
  reported missing where the oracle's `path.resolve` drops them and finds the file. Fixed by
  `manifestTargetsCollapseDots`, which drops exactly what `path.resolve` drops for a `..`-free path and
  keeps `..`, with `TestManifestTargetsKernelOrderTrailingSeparator` pinning the mcpServers, hook command
  and mcp argument rows.
- Preserving the root's spelling in `targetResolve` while the manifest lookup still used
  `filepath.Join` mixed two plugin roots in one validation: a root spelled through a link and a `..`
  selected the manifest lexically and then judged its targets physically. Fixed by resolving the manifest
  path through `targetResolve` as well, so one root governs the whole validation, with
  `TestManifestTargetsKernelOrderOneRootGoverning` pinning it against two roots that declare different
  hook files.
- `targetResolve`'s absolute-path branch still ran `filepath.Clean`, so an absolute target spelling a
  link followed by `..` was cleaned to an inside decoy before the walk saw it. Fixed by
  `manifestTargetsCollapseDots` there too, with the `absolute_after_the_leading_dot_slash` row of
  `TestManifestTargetsKernelOrderCallerPathEscapes` pinning it (the row builds its spelling by hand and
  compares it with `filepath.EvalSymlinks`, so it fails when the lexical `Clean` is restored).
- The doctor assembly still read the manifest through `filepath.Join` while the validator now resolved
  its targets physically, so a root spelled through a link and a `..` produced ONE report describing TWO
  plugin packages: the inline manifest check, the gate that decides whether to run the target checks,
  the plugin version and the installed-root check read the lexical root, while target validation and
  `drift:mcp` read the physical one. If only the physical root held a manifest the gate also skipped its
  hook and mcp target checks entirely. Fixed by resolving the root once at the assembly
  (`RunHarnessDoctor`) and using that one root for every check, with
  `TestManifestTargetsKernelOrderDoctorAssemblesOneRoot` pinning both the version and the gate. This
  required `internal/runtime/doctor/harness_run.go` and, for the manifest read of the drift check,
  `internal/runtime/doctor/harness_drift.go`: files outside the issue's original edit regions, taken
  because one root has to govern the whole judgement and the alternative was two roots in one report.

No other defect was found in this issue's ranges. The walk's answers were compared against
`filepath.EvalSymlinks` over 84 hand-built shapes (directory and file links, chains, self-loops, dangling
links, absolute targets, `.` and `..` targets, long `./`-only targets) and 4,320 randomized shapes across
twelve seeds, with no disagreement, and each new test row drives the kernel comparison on the path as the
caller spelled it. The two remaining kernel differences are pre-existing and pinned elsewhere: the depth
ceiling of 40 links against the kernel's 255, and the mcp `.js` argument filter, which still takes the
argument text as written.
