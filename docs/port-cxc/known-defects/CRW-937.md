# CRW-937 — the manifest-target walk keeps the kernel's component order

Source: the oracle's shared validator `plugins/codexclaw/components/cxc-ops/src/manifest-targets.ts` at CXC
v0.2.40 (commit 3c1459acadeb1906d97c00a598e1457327ae372d): `escapesRoot` (:105-117), which calls
`realpathSync` on both paths and falls back to `resolve` when either throws. The port is
`internal/runtime/doctor/manifest_targets.go` (`manifestTargetsRealpath`, `manifestTargetsFollow`,
`targetEscapesRoot`, `targetResolve`, `targetCheck`, `ValidateManifestTargets`).

- The oracle's `escapesRoot` resolves a symlink's target with Node's `fs.realpathSync`, whose JavaScript
  implementation resolves each link target LEXICALLY (`path.resolve(previous, linkTarget)`, modeled at
  `manifest_targets_realpath_test.go` `targetOracleRealpath`), so a `..` inside a link target is dropped
  against a lexical prefix. The port followed that shape, so with `root/sublink -> ../outside/deep` and
  `root/bad.json -> sublink/../hook.json` the walk answered `root/hook.json` while the kernel
  (`filepath.EvalSymlinks`) answers `<base>/outside/hook.json`: an outside hook JSON was judged inside
  the plugin root and read (found by the pair evaluation of PR #765 (CRW-840), score 5, reproduced on
  dev 9a7fcae2); port: fixed (the walk now splits a link target into its components without joining or
  cleaning them, puts them in front of the components still to walk and keeps walking, so a `..` climbs
  one level from the directory the walk has physically reached. The depth ceiling, the stat before the
  readlink and the paired lexical fallback stay as CRW-840 and CRW-652 left them. This is a deliberate
  divergence from the oracle: the oracle case is recorded as intentionally changed, and the port now
  agrees with `filepath.EvalSymlinks` on every reachable shape).
- The same class (a `Join` or `Clean` removing a `..` after a link) appeared the same day in CRW-923 and
  CRW-924, which cover `internal/manage` and do not touch this file; port: kept (their files are their
  own issues' edit regions, and this issue's scope is the doctor manifest-target judgement only).
- Supersedes known-defects/CRW-840.md, item beginning "manifestTargetsFollow read a symlink component's
  target": now port: fixed (that item recorded the lexical `Clean` of the link target as the oracle's
  behaviour and noted that the earlier plan to join it without cleaning would diverge from `realpathSync`.
  The containment check now walks the target's components in kernel order and the lexical Clean is gone,
  which is the divergence that item declined to take. The rest of that item -- the `os.Stat` before
  `os.Readlink` -- is unchanged).

No other defect was found in this issue's ranges. The walk's answers were compared against
`filepath.EvalSymlinks` over 84 hand-built shapes (directory and file links, chains, self-loops, dangling
links, absolute targets, `.` and `..` targets, long `./`-only targets) and 4,320 randomized shapes across
twelve seeds, with no disagreement.
The two remaining kernel differences are pre-existing and pinned elsewhere: the argument-side `..` that
`filepath.Abs` cleans (CRW-840) and the depth ceiling of 40 links against the kernel's 255.
