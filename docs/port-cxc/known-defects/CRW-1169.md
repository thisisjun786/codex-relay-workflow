# CRW-1169 — the failure paths of the self-heal evidence recording share its deadline

Source: `internal/runtime/install/configguard/selfheal_evidence.go` (`RecordSelfHealEvidence`, `dropSelfHealEvidence`) and the `enable` branch of `internal/runtime/install/features.go`; the oracle (`plugins/codexclaw/components/config-guard/src/cli.ts` at v0.2.40) records no evidence at all. Follow-up of CRW-1150, found by the verification of a205074dc.

- After CRW-1150 the publication of a verified measurement was bounded by `featureEvidenceDeadline` (8 seconds), but the five failure paths of the recording (config digest unreadable, working directory unknown or layers unreadable, listing failed, version unreadable or changed, config or layers moved while measuring) called `dropSelfHealEvidence` synchronously. Its marker read, the wait for the marker lock (up to the lock wait) and the write were then outside the deadline, so a marker lock held by another writer or a stalled filesystem kept `crw install features enable` from rendering its success long after the deadline; port: fixed (`dropSelfHealEvidence` takes the recording's context, runs the read, the lock wait and the write in their own goroutine and the call returns nil when the context ends first, as the publication does. A drop that has not started by then writes nothing, so the older record stays; every use of a record is still gated by the version and the config and layer digests. A drop already running cannot be cancelled and finishes on its own under the lock. The command's result is unchanged: `enable` ignores the recorder's error, and an abandoned drop returns nil like an abandoned publication. Pinned by `TestSelfHealEvidenceFailedRecordingReturnsAtTheDeadlineWhileTheMarkerLockIsHeld`, which holds the marker lock past the deadline for each failure path).
