# CRW-1169 — the failure paths of the self-heal evidence recording share its deadline

Source: `internal/runtime/install/configguard/selfheal_evidence.go` (`RecordSelfHealEvidence`, `dropSelfHealEvidence`) and the `enable` branch of `internal/runtime/install/features.go`; the oracle (`plugins/codexclaw/components/config-guard/src/cli.ts` at v0.2.40) records no evidence at all. Follow-up of CRW-1150, found by the verification of a205074dc.

- After CRW-1150 the publication of a verified measurement was bounded by `featureEvidenceDeadline` (8 seconds), but the five failure paths of the recording (config digest unreadable, working directory unknown or layers unreadable, listing failed, version unreadable or changed, config or layers moved while measuring) called `dropSelfHealEvidence` synchronously. Its marker read, the wait for the marker lock (up to the lock wait) and the write were then outside the deadline, so a marker lock held by another writer or a stalled filesystem kept `crw install features enable` from rendering its success long after the deadline; port: fixed (`dropSelfHealEvidence` takes the recording's context, runs the read, the lock wait and the write in their own goroutine and the call returns nil when the context ends first, as the publication does. The deadline bounds the caller's wait, not the retirement: the goroutine does not look at the context, so a recording whose time ran out still drops the older record and retires the oracle's mtime cache (`allEnabled` false) when the marker lock is free and the process lives to see it, as the synchronous drop did, and a legacy-only `allEnabled` cache cannot vouch again for flags the command just changed. The caller returns at the deadline with no further wait (an earlier grace of 250ms after the context ended was removed: it pushed the failure path past the shared deadline). A drop still waiting for a lock held past the deadline is abandoned by the caller and finishes on its own later, under the lock and from the marker it reads there, so it never overwrites an opt-out; it can also end without writing when the separate marker-lock wait (`selfHealMarkerLockWait`, 2 seconds by default) runs out, when an I/O step fails, or when the process ends first, and it is not retried. In those cases the marker stays as it was: a record with probeEvidence is still gated by the version and the config and layer digests, but a legacy-only marker (no probeEvidence) is gated only by the oracle's config.toml mtime, as before CRW-1150, until a later writer retires it. The command's result is unchanged: `enable` ignores the recorder's error, and an abandoned drop returns nil like an abandoned publication. Pinned by `TestSelfHealEvidenceFailedRecordingReturnsAtTheDeadlineWhileTheMarkerLockIsHeld`, which holds the marker lock past a 200ms deadline and asserts the call returns within the deadline plus a 150ms scheduling margin, for each of the five failure returns (config digest unreadable; working directory unknown; listing failed; version unreadable or user config moved, which share a return; project layer moved) and by `TestSelfHealEvidenceFailedRecordingPastTheDeadlineStillRetiresTheLegacyCache`, which retires a legacy-only cache in the background after an ended deadline).
