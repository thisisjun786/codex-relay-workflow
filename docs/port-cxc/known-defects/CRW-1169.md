# CRW-1169 — the failure paths of the self-heal evidence recording share its deadline

Source: `internal/runtime/install/configguard/selfheal_evidence.go` (`RecordSelfHealEvidence`, `dropSelfHealEvidence`) and the `enable` branch of `internal/runtime/install/features.go`; the oracle (`plugins/codexclaw/components/config-guard/src/cli.ts` at v0.2.40) records no evidence at all. Follow-up of CRW-1150, found by the verification of a205074dc.

- After CRW-1150 the publication of a verified measurement was bounded by `featureEvidenceDeadline` (8 seconds), but the five failure paths of the recording (config digest unreadable, working directory unknown or layers unreadable, listing failed, version unreadable or changed, config or layers moved while measuring) called `dropSelfHealEvidence` synchronously. Its marker read, the wait for the marker lock (up to the lock wait) and the write were then outside the deadline, so a marker lock held by another writer or a stalled filesystem kept `crw install features enable` from rendering its success long after the deadline; port: fixed (`dropSelfHealEvidence` takes the recording's context and first tries the marker lock once, without waiting. When the lock is free, it drops the older record and retires the oracle's mtime cache (`allEnabled` false), and releases the lock, before the call returns, whether or not the deadline has ended (a slow codex may have used it up), as the synchronous drop did: these are a few local file operations, and `enable` renders and exits right after the call, so the retirement is never left to a goroutine the exiting process would kill, and a legacy-only `allEnabled` cache cannot vouch again for flags the command just changed. Only when another writer holds the marker lock does the drop wait for it, in its own goroutine, and the call returns nil the moment the context ends, with no further wait (an earlier grace of 250ms after the context ended was removed: it pushed the failure path past the shared deadline). That run's retirement is then skipped: the waiting drop finishes only if the process lives to see the lock free (under the lock and from the marker it reads there, so it never overwrites an opt-out), it ends without writing when the separate marker-lock wait (`selfHealMarkerLockWait`, 2 seconds by default) runs out or an I/O step fails, and it is not retried within the command; the next drop (the next `enable` whose recording fails) or the next publication (whose recorded evidence retires the cache) retires it. Until then a record with probeEvidence is still gated by the version and the config and layer digests, but a legacy-only marker (no probeEvidence) is gated only by the oracle's config.toml mtime, as before CRW-1150. The free-lock path is not bounded by the deadline: a filesystem that stalls on those few local operations still holds the caller, as it held the synchronous drop on dev. The command's result is unchanged: `enable` ignores the recorder's error, and an abandoned drop returns nil like an abandoned publication. Pinned by `TestSelfHealEvidenceFailedRecordingReturnsAtTheDeadlineWhileTheMarkerLockIsHeld`, which holds the marker lock past a 200ms deadline and asserts the call returns within the deadline plus a 150ms scheduling margin, for each of the five failure returns (config digest unreadable; working directory unknown; listing failed; version unreadable or user config moved, which share a return; project layer moved), and by `TestSelfHealEvidenceFailedRecordingPastTheDeadlineStillRetiresTheLegacyCache`, which asserts a legacy-only cache is already retired when a recording past its deadline returns with the lock free).
