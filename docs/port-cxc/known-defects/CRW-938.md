# CRW-938 — the worktreedel and spawn targets' inputs and isolation

Source: the CXC v0.2.40 oracles the two targets compare against — `pabcd-state/dist/worktree-guard.js`
(`handleWorktreeGuardPreTool` at 568, `evaluateCommand` 453, `evaluateSegment` 347) and
`subagent-config/dist/spawn-attach-hook.js` (`mentionedFolders` 832, `inferRole` 493,
`isFullHistoryFork` 520, `isV2SpawnInput` 534, `isSpawnToolName` 586, `isCollaborationToolName` 591)
— against the dev-only harness targets `worktreedel` and `spawn` in `internal/dev/cxcfuzz`
(`target_worktreedel.go`, `target_spawn.go`, `testdata/*/shim.mjs`, `testdata/*/cases.json`). Every
defect here is a harness defect: the target, its generator or its pinned case was wrong, never the
ported product code or the oracle. They were found while evaluating the merged CRW-704 change (pull
request #758).

- The spawn target's oracle worker `testdata/spawn/shim.mjs` answered under the caller's environment: it
  never read `request.root`, so HOME, CODEX_HOME, CRW_HOME, CODEXCLAW_HOME and TMPDIR stayed whatever
  `Campaign` handed the pool (`os.Environ()`, cxcfuzz.go:181-185, worker.go:80-82), where the echo,
  memorygate and doctor shims each put those five under the case root (`testdata/echo/shim.mjs` run(),
  `testdata/memorygate/shim.mjs` run(), `testdata/doctor/shim.mjs` isolate()); port: fixed (the shim now
  isolates every request under `request.root` and answers a non-object input, the pool's start-up
  handshake, with the refusal before it touches anything; it loads the oracle once at module scope so
  that load is charged to the worker's start-up budget rather than to a case's timeout, remembers a load
  that failed instead of dying on it, so a handshake is still answered when the oracle tree cannot be
  loaded, and retries per request so a tree that appears later is picked up).
  Supersedes this file, item beginning "The spawn target's oracle worker": now port: fixed (the reason
  above replaces one that read "it imports the oracle per request rather than at module load ... the
  oracle's own initialization runs under the case's homes rather than the caller's". A pre-merge
  evaluation of the head that carried it judged that shape a regression - record
  pr866-a9f956c3.json, finding d2 - because a per-request import moves the oracle's initialization from
  the worker's start-up budget to a case's timeout and can time out a worker that already answered its
  handshake; the load is at module scope again, and it is safe there because the oracle's module
  initialization does no home I/O, measured against the real v0.2.40 tree with the five homes pointed
  at a decoy directory: 12 ms, no file written, no environment variable changed, and the real
  `~/.codex` file set identical. Every case's own work still runs after `run()` has put the five homes
  under `request.root`).
- The worktreedel generator's continued-line command and the pinned case
  `crw-585-continued-line-inside-sh-c` held a bare line feed, so the shell's line-continuation path —
  the CRW-585 regression itself — was never exercised by either the generator or the case; port: fixed
  (both now carry a real backslash before the feed, and the case is re-recorded `intentionally-changed`:
  the oracle's own walk reads no backslash and allows the joined removal, while the port's extended walk
  denies it, the security class the CRW-498 section of `docs/port-cxc/known-defects.md` records).
- The spawn generator ignored its `size` argument and the pinned case `crw-614-deep-nesting` was a flat
  4,400-character `x` string, so no generated input and no pinned case carried any nesting at all; port:
  fixed (the generator now spends the `size` on the length of the mention text, with the total bytes
  computed from the size and capped before the string is built, and the pinned case is a long mention of
  a size this target carries, named `crw-614-long-mention`).
  Supersedes this file, item beginning "The spawn generator ignored": now port: fixed (the reason above
  replaces two earlier ones - "a really nested input whose depth follows size ... the depth drives the
  mention syntax" and "a case whose JSON containers nest as deep as the size it is given ... beside the
  MentionedFolders call the classifier still answers"; a bracket run inside one `skill://` folder name
  is ordinary string data to both readers, and a nesting the classifier never walks exercises no
  boundary).
  Supersedes this file, item beginning "The spawn generator ignored": now port: fixed (the corrected c3
  of 2026-10-08 removed the depth claim altogether: MentionedFolders and the other classifiers this
  target compares read strings, and the 4,400-level bound is the writer bound of `RunSpawnAttachHook`
  (`internal/role/spawn/hook_route.go`, `spawnHookRouteMaxDepth`), which a classifier comparison never
  reaches. A generator that nested the classifier's argument therefore built containers both harnesses
  unwrapped before the classifier ran - a depth neither side exercised - and the pinned case named a
  boundary it never drove. Both are gone: the generator builds no nesting, the pinned case claims no
  depth, and the red-first test `TestSpawnCasesCarryNoNestingTheClassifierMisses` fails while a
  generated or pinned case carries a chain the classifier does not receive. The bound stays covered by
  `TestSpawnHookRouteMaximumNesting` and `internal/role/spawn/testdata/hook/oracle.json`; a hook-route
  depth target is a separate follow-up, and this target makes no depth claim).
- The spawn target's oracle worker loaded the oracle at module scope, before any request had set the five
  home variables, so the oracle's import-time initialization ran under the caller's environment; port:
  fixed (before every import attempt the worker creates a fresh temporary root of its own under the
  harness TMPDIR, points HOME, CODEX_HOME, CRW_HOME, CODEXCLAW_HOME and TMPDIR at it, imports the oracle
  under that root and removes the root again in a `finally`, so the root's lifetime is exactly the
  import. The load still happens before the stdin listener exists, so its cost stays on the worker's
  start-up budget rather than a case's timeout, and a failed load is still remembered and answered; a
  start-up handshake still does nothing else. This closes the pre-merge evaluation of head 070737c6
  (record pr866-070737c6.json, finding d2, introduced): the import ran under the caller's HOME and
  CODEX_HOME, and the isolation test could not observe a read there).
  Supersedes this file, item beginning "The spawn target's oracle worker loaded": now port: fixed (the
  pre-merge evaluation of head 00a28fd51 - record pr866-00a28fd5.json - found three defects in the first
  shape of this fix and this line records the correction. d1 P0: one load-root pathname was kept and its
  directories recreated per attempt, so a shared writable TMPDIR could replace the removed pathname with
  a symlink and the retry would create directories through it outside the worker's own root; every
  attempt now calls `mkdtempSync`, which never reuses a name, so no import creates a directory through a
  path the worker does not own. d2 P1: `run()` set the case's five homes and then loaded the oracle,
  whose own root overwrote them and was removed before the classifier ran, so a case after a successful
  retry answered under the deleted import root; `run()` now consults the oracle first and puts the case's
  homes in place afterwards. d3 P2: the comments that still claimed a nesting-depth boundary, an
  initialization deferred to the first case, or initialization under the caller's homes are corrected).
  Supersedes this file, item beginning "The spawn target's oracle worker loaded": now port: fixed (the
  pre-merge evaluation of head 4f1d14b1 - record pr866-4f1d14b1.json - found three more defects in the
  load-root lifecycle and this line records the correction. d1 P1: the loader fell back to Node's own
  temporary directory and `/tmp` when the harness TMPDIR could not be used, which put the oracle's
  initialization outside the boundary the harness selected; the fallback is gone, an unusable TMPDIR is
  an initialization failure the worker remembers and answers, and the only fallback left is the process's
  own temporary directory when the caller named no TMPDIR at all. d2 P1: a retry made after the handshake
  was charged to the case timeout, so a healthy classifier request could be reported as a timeout only
  because the oracle appeared late; there is exactly one import attempt now, and a worker whose load
  failed keeps listening and answers every later request with the remembered error instead of trying
  again. d3 P2: a root created before a failure in the same call, or a startup SIGKILL that no
  `finally` can run under, could leave the root behind, and the record called the root's lifetime exactly
  the import; `makeLoadRoot` now removes a root it cannot complete before raising, and the record states
  the remaining limitations - a root can be left behind when the process is killed outright, or when its
  removal fails (the error is dropped, so an unremovable scratch directory never stops the worker), in
  both cases under the harness TMPDIR the caller chose).
- `home/link-into-slot` in the worktreedel layout named the managed checkout with a target relative to
  the link's own directory, so it resolved to `<root>/home/home/.codex/worktrees/zk3q/repo`, which does
  not exist; no cwd or command in the generator reached the link either, so the link-path judgement was
  never fuzzed; port: fixed (the target is the `${ROOT}`-prefixed absolute form, `home/link-into-slot`
  is in the cwd pool, and a removal through the link is pinned as a case both sides answer).
