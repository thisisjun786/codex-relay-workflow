# CRW-877 — the activation's enable calls and the deactivation's manifest read run under the config lock

Source: CXC v0.2.40, commit `3c1459acadeb1906d97c00a598e1457327ae372d` —
`plugins/codexclaw/components/config-guard/src/activate.ts` (`activate`, the `featuresToEnable`
loop at :233-250 and the managed-key pass that follows it) and
`.../src/deactivate.ts` (`deactivate`, the manifest read at :61 that also decides whether to write).
Port: `internal/runtime/install/configguard/activate.go` (`Activate`,
`activationSetKeyLocked`) and `internal/runtime/install/configguard/deactivate.go` (`Deactivate`).

## Defects

- The activation's own `codex features enable` calls (`activate.go`'s `Activate`, :201-213 before
  this change) ran before `activationSetKeyLocked` and rewrote config.toml outside the sidecar lock,
  so a CRW writer that published during one of them had its change discarded by the CLI (source
  `plugins/codexclaw/components/config-guard/src/activate.ts`); port: fixed (CRW-877's answer:
  `Activate` takes `crwdir.LockConfig` once, before its first config.toml access, and holds it
  across the pre-install read, the backup, the injected `codex features enable` calls, the
  managed-key read-modify-writes and the post-activation hash, so the CLI's own read-modify-write can
  no longer discard another writer's publication. `activationSetKeyLocked` keeps its name and its
  contract and loses its own lock, because taking it again inside the critical section would be the
  activation deadlocking on the lock it already holds. Found by CRW-866's Codex review, recorded
  there as port: pending, and closed by the Supersedes line below; pinned by
  `TestActivateHoldsTheConfigLockWhileItEnablesFlags`).
- The deactivation decided from the install manifest it read before it took the lock (`deactivate.go`
  :91-105), so an activation that published a new manifest while the deactivation waited left the
  restore computed from a manifest that no longer described the install (source
  `plugins/codexclaw/components/config-guard/src/deactivate.ts:61`); port: fixed (CRW-877's answer:
  the first reading keeps deciding whether and where to lock, and the drift hash, the table keys and
  the flags all decide from a second reading taken inside the lock; a manifest missing or unreadable
  at that second reading answers as the no-manifest branch does. Found by the parent's review of
  CRW-866 as P2; pinned by `TestDeactivateDecidesFromTheManifestInsideTheLock`).
- The oracle wrote config.toml with no sidecar at all, so it never left a `config.toml.crw-lock`
  behind on a path that failed before its first managed-key write; port: kept (the lock is now taken
  before the backup, so an activation that fails on a hard `features enable` or on an unreadable
  file leaves the sidecar in the Codex home where the baseline left none. The sidecar is created once
  and never unlinked by design (docs/port/decisions.md 7), so the difference is a file nothing reads
  and no fixture asserts; it is recorded here because the `cli__enable__*` CXC fixtures are still
  registered pending and their expectations would need this key when the issue that owns them
  replays them).

## Supersedes

- Supersedes known-defects/CRW-866.md, section "Defects", item beginning "The activation's own
  `codex features enable` calls": now port: fixed (CRW-877 takes the sidecar lock once in
  `Activate` and holds it across the whole flow, the defect above; pinned by
  `TestActivateHoldsTheConfigLockWhileItEnablesFlags`).
- Supersedes known-defects/CRW-866.md, section "Supersedes", the parenthetical sentence "The
  activation's own `features enable` calls remain outside the lock, the pending defect above": now
  port: fixed (that sentence described the state before CRW-877; those calls now run inside the same
  critical section as the managed-key write).
