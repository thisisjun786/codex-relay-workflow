# CRW-1297 — a relay child that cannot reach the daemon reports through the bridge

Source: CRW's own design, not the CXC oracle (the CXC bridge has twelve tools and no child report). A relay child
reports (`emit`, `intent-claim`, `intent-disposition`) only through the relay daemon's `control.sock`
(CRW-1286.md); Codex refuses that connect without network access (CRW-1296.md). The Go files are
`internal/bridge/mcp/report.go` (`reportChild`, `WithChildReports`, `RegisterChildReports`), `schema.go`, `server.go`
and `main.go` there; `internal/relay/adapter/cli.go` (`Register` wires `hook.ForwardChild` and `store.ResolveStateDir`
in at executable composition, so `internal/bridge/mcp` imports no relay package but the leaf `argparse` and
`internal/relay/store`'s tests, which import it, have no cycle); `contract/schema/bridge-mcp-tools.json` with
`descriptions_generated.go`; and, unchanged, `internal/relay/hook/control_child.go` (`ForwardChild`,
`handleChildCommand`) and `internal/relay/dispatch` (`OwnedChildState`, `ExecuteOwnedChild`).

- The bridge has a thirteenth tool, `report_child` (`command`: `emit`, `intent-claim` or `intent-disposition`;
  `arguments`: that command's own options). The bridge runs outside the child's sandbox, so it connects to
  `control.sock` where a readOnly child, or a workspace-write one without network access, cannot. It sends
  `crw <command> <arguments>` through `hook.ForwardChild`, and the daemon runs it on its own store through
  `handleChildCommand`: the same checks and record as a direct report. Exit 0 answers `exitCode`, `stdout`, `stderr`
  and, for a JSON object, `report`; a nonzero exit is an error result carrying the daemon's answer. An addition to
  the CXC bridge; port: fixed in source, a deliberate deviation. The frozen listing grew by that tool
  (`contract/schema/bridge-mcp-tools.json`, `descriptions_generated.go`, the golden of
  `Test_tools_list_is_the_frozen_listing`, regenerated with `CRW_GOLDEN=update`), and the tool counts in
  `internal/bridge/mcp/main_test.go` and `internal/runtime/integration/isolated_home_test.go` are thirteen;
  `get_capabilities` lists no tools and is unchanged.
- The daemon alone decides where the record goes (CRW-1299.md, held on this route). The bridge finds the daemon from
  its own configuration: the App Server socket it was started with (`""` for the default), resolved as `relay` resolves
  a state (`store.ResolveStateDir`: `CODEX_SESSION_RELAY_STATE` of the bridge's own environment, else the configured
  relay state or the directory discovery scopes by that socket). The call decides nothing: its arguments are read
  against the command's own options (`argparse.Parse`), and a `--state`, `--socket`, `--kind-module`, `--json` or
  `--help` (no options of a child command), an option the command lacks or a missing required one is refused by the
  bridge naming the argument, asking the daemon nothing; a path relative to the child passes that reading and the daemon
  refuses it naming its option (the CRW-1299 check); the child's argv, environment and working directory never reach the
  bridge. A bridge whose state has no daemon answers `relay daemon unavailable; child report was not submitted`, writes
  nothing and opens no store: there is no local fallback; port: fixed in source. Pinned by
  `TestABridgeToolCarriesANetworklessChildsReceiptAndBlockedReportToTheDaemon`,
  `TestABridgeReportCannotRedirectTheDaemonsRecord`,
  `TestABridgeReportWithoutADaemonIsAnExplicitErrorWithNoLocalStore`,
  `TestReportChildForwardsToTheDaemonOnTheBridgesOwnState`, `TestReportChildNeverTakesTheStateFromTheCall`,
  `TestReportChildAcceptsOnlyTheChildCommands` and `TestReportChildSaysWhyTheDaemonRefused`.
- The bridge and the daemon are configured for the same state: a bridge started with another one finds no daemon and
  every report ends with the explicit error above, writing nothing elsewhere. The child's MCP profile leaves it enabled.
- The create-time refusal (`internal/bridge/create.go`, CRW-1296.md) and the refusal of `register --child-settings`
  (CRW-1298.md) are kept: a relay child writes its work, so it is created under a sandbox that reaches the daemon. The
  tool is the safety net for a child created outside them, as CRW-1286 and CRW-1296 decided; port: kept.
