# CRW-812 — the state-copy apply's five post-merge evaluation findings

Source: the state-copy apply is CRW's own design, [docs/port-cxc/state-migration.md](../state-migration.md)
(the preflight rules at :144-156, the path-field table at :119, and the M3 slice at :184), and the code
is the Go port in `internal/runtime/install/migrate`: `apply.go` (`ensureRoots`, `applyRank`,
`writeFiles`, `publishFile`), `publish.go` (`Publish`, `settle`, `EnsureProjectRoot`) and
`attention.go`. The records it copies are written by the CXC v0.2.40 components named in the design's
inventory, and the reference graph a receipt is judged with is `internal/pabcd/gate/manifest.go:89-143`
(`artifactManifest` of kinds `verdict` and `artifact-identity`, `gate/receipt.go:35-36`). All five
were found by the operator's pair evaluation of the merged state-copy PR (the issue's six P1s; the
sixth, directory-creation ownership, needs `roots.go` and is a separate issue), and CRW-812 fixes all
five under its own scope.

- A source that moved between classification and publication was only checked immediately before its
  own write, and `SourceVerified` was `err == nil`, so a file whose bytes were already read could change
  while its temporary was being filled and the run still reported a verified source; a file published
  early could also move while a later file published and never be checked again (source
  `apply.go:353-381,70`, `publish.go:149-153`; the design requires a recheck of source and destination
  against the preflight inventory, `state-migration.md:152`); port: fixed (every source is re-read and
  compared with the plan's size, mode and hash after its own publication and once more for every copied
  file at the end of the run, and a mismatch fails that file as a changed source with `SourceVerified`
  false; the cases are `TestMigrateApplyReviewRefusesASourceThatMovedAfterItsPublish` and
  `TestMigrateApplyReviewRefusesASourceThatMovedDuringTheRun`).
- `ensureRoots` called `pair.EnsureDest` before `EnsureProjectRoot`, which set `pair.Dest` and made
  `EnsureProjectRoot`'s own pre-observation see the destination as already existing; a racer's
  `.gitignore` written while the root was created was therefore treated as a retained owner file, the
  `ReasonDiffers` refusal was swallowed and the state copy continued, losing the protection the
  initialization-race judgement exists for (source `apply.go:247-249`, `publish.go:205-224`; the design
  requires the root and its ignore before any state is copied and a conflicting initialization race to
  stop, `state-migration.md:150`); port: fixed (for the project scope `ensureRoots` calls
  `EnsureProjectRoot` before anything has created the root, keeping the `made` observation and the
  marker chmod, so a racer's differing `.gitignore` is refused and the copy stops; the case is
  `TestMigrateApplyReviewRefusesAnIgnoreRaceInANewRoot`, and `TestMigrateApplyReviewKeepsAnOwnersIgnore`
  pins that a pre-existing owner ignore is still retained).
- `applyRank` returned one rank per file and the sort used it alone, so inside a rank plan order
  decided: a QA receipt could publish before the `verdict.json` and `artifact-identity.json` its
  `artifactManifest` names, and in the Codex scope the install record published before the config
  backup its `backupPath` names (source `apply.go:114-128,331-333`, `gate/manifest.go:89-143`; the
  design requires dependencies before their referencing records, "artifacts/plans/backups first",
  `state-migration.md:153`); port: fixed (a second key inside a rank publishes the artifacts an evidence
  manifest names, resolved against the receipt's own directory, and the Codex config backups before the
  file that refers to them; `classify.go` is unchanged and the graph is derived at write time from the
  plan's items, so a receipt that cannot be read contributes no key and never fails the run; the cases
  are `TestMigrateApplyReviewPublishesEvidenceDependenciesFirst` and
  `TestMigrateApplyReviewPublishesTheBackupBeforeTheInstallRecord`).
- `publishFile` counted a completed write whenever a `ResultFailed` publication's destination was whole,
  but `Publish` also returns `ResultFailed` when `settle` found the destination already equal and only
  its directory sync failed, so a file this run never renamed or wrote was counted as a write and a pure
  sync failure was reported as a completed one (source `apply.go:370-375`, `publish.go:76-84,165-185`;
  the design's failure output must record exactly which writes completed, `state-migration.md:154,156`);
  port: fixed (`Publish` keeps `ResultAlreadyEqual` when the equal leaf's directory sync failed, and
  `publishFile` counts only the whole file of a `ResultFailed` rename, reporting the equal case as the
  sync failure alone while keeping the destination-mode diagnostic; the case is
  `TestMigrateApplyReviewDoesNotCountAnEqualFilesSyncFailure`).
- The attention report's `"session"` field row omitted `unverifiedSubagents[].receiptClaimed`, a field
  the design's path-field table lists, so a copied session holding only that old receipt path raised no
  `old-root-ref` and the stale reference went unreported (source `attention.go:51-53,165-177`;
  `state-migration.md:119`); port: fixed (the field is added to the row with no kind, so a value naming a
  source root raises `old-root-ref` through the existing scan and a value of another type stays opaque;
  the cases are `TestMigrateApplyReviewReportsAReceiptClaimedUnderTheOldRoot` and
  `TestMigrateApplyReviewIgnoresANonStringReceiptClaimed`).

Not a defect, recorded so the mode sequence is not mistaken for one: creating the project root through
`EnsureProjectRoot` means the root is now briefly created 0o777 (under the umask) by that call and
chmodded to the private marker mode in the same call stack, instead of being created at the marker mode
directly. The window is one call and the root ends at the marker mode before any state is published, so
no other writer can observe a widened root.

Limitation of the ordering key, not a defect: the key is applied to a copied record whose source name
ends in `qa-receipt.json`, the QA receipt name the final-gate convention uses
(`internal/pabcd/goalplan/finalgate_test.go:132-138`). A receipt under another name still publishes, in
plan order, and is reported by attention; ordering is a dependency hint and never decides what is copied.
