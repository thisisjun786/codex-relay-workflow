# CRW-975 — the A>B publication judges under the goalplan lock, an unreachable plan fails open, a withheld plan refuses (CRW-976 folded in)

Source: CXC v0.2.40 (`3c1459ac`) `plugins/codexclaw/components/pabcd-state/src/orchestrate-cli.ts` (`validateReviewBinding` :49-95 called at :688-691, the work-phase binding read :606-622, the A>B state write :1119) and `goalplan.ts` `withGoalplanWriteLock` (:806-873). Ported in `internal/pabcd/cli/orchestrate_transition.go` (`orchestrateCommitPublish`), `internal/pabcd/cli/orchestrate_review_binding.go` and `internal/pabcd/goalplan/lock.go`. Found by the evaluations of CRW-755 (`pr720`) and CRW-811 (`pr727`) and of CRW-794 (`pr706`, CRW-976, a duplicate of this issue).

- The review binding check read the goalplan without its lock, and the publication's lock callback revalidated only the work-phase binding, so a reviewer FAIL recorded under the lock between the check and the publication was ignored and A>B was published. The oracle has the same race (`validateReviewBinding` :688-691 and the A>B write both run without any lock), and CRW-755's entry did not record it; port: fixed (`orchestrateCommitPublish` judges the review binding again, through `orchestrateReviewBindingCheckPlan`, on the plan its lock callback read, after the work-phase binding and before the stale-round housekeeping and the state write, so a refusal there writes nothing, and the invocation's context is read once more after that re-check, whose re-hash does file I/O, and before the first durable effect, so a cancellation during it writes nothing and answers Interrupted (CRW-871; pinned by `TestOrchestrateCommitCancelDuringLockedReviewRehashWritesNothing`, ordered through the `interrupt` seam, no sleep). The unlocked first check stays in front for the oracle's refusal precedence. Pinned by `TestOrchestrateCommitRechecksTheReviewBindingUnderTheLock`, which orders the reviewer's write with the `lockGoalplan` seam, and the contrast `TestOrchestrateCommitReviewBindingUnderTheLockStillPasses`).
- `WithGoalplanWriteLock` returned a Go error for a plan directory it could not open or a plan file it could not look up (EACCES and the like: any non-absent `openPlanDir` or `Fstatat` error), while `ReadGoalplan` answers nil for the same directory and the oracle goes on when it cannot open the plan (:606-622, answer 4 of CRW-811). CRW-811 made the A>B publication stop on it, a regression; port: fixed (only an access failure, EACCES or EPERM, on those two steps is now `Kind: "unreadable"` with the reason, no Go error; a link or wrong kind of path found by the O_NOFOLLOW walk (`goalplanRelocatedError`, ELOOP, ENOTDIR), a relocated descriptor and every other failure stay Go errors, so a plan directory swapped for a symlink after the gate read publishes nothing, and `orchestrateCommitPublish` treats `unreadable` without `Refused` as the fail-open it always was and publishes outside the lock. The other callers of `WithGoalplanWriteLock` already refuse on `unreadable`, so for them a Go error becomes a refusal naming the reason. Pinned by `TestWithGoalplanWriteLockUnreadableDirectoryIsUnreadable`, `TestWithGoalplanWriteLockLinkedPlanDirectoryStaysAnError`, `TestWithGoalplanWriteLockPlanDirectoryNotADirectoryStaysAnError`, `TestOrchestrateCommitUnreachablePlanFailsOpen` and `TestOrchestrateCommitLinkedPlanDirectoryAfterTheGateIsNotFailOpen`).
- A plan the lock read but withholds from writers (bytes that are not UTF-8, a repeated key, a field this build cannot keep: the three `revivalLossRefusal` answers) came back as the same `unreadable` kind, and `orchestrateCommitPublish` published the state outside the lock with the work-phase binding it had read earlier, against CRW-811's answer 4; port: fixed (`GoalplanWriteLockResult.Refused` marks those three; the publication answers the lock's reason with "Nothing was written." and publishes nothing, no row. An absent or unreachable plan is not `Refused`. Pinned by `TestWithGoalplanWriteLockRevivalRefusalIsRefused` and `TestOrchestrateCommitWithheldPlanPublishesNothing`).
- CRW-976 (folded in): `goalplanLockVanished` took a held lock whose descriptor path was `<lock> (deleted)` for a released one on the name alone, so a live lock moved to a sibling literally named that was retried and a second writer entered the plan. The oracle has no descriptor check at all (`mkdirSync` is the lock), so the defence is the port's own and was to meet CRW-794's "any other path is an error"; port: fixed, and CRW-794's "port: kept (deliberate, recorded)" for the name-based recognition no longer holds (the recognition now needs the spelling and the identity: the kernel's `<lock> (deleted)` path, the held descriptor unlinked (`fstat` nlink 0), and the lock name in the plan directory absent (`fstatat` ENOENT) or another inode. A live lock moved under that name still has its directory entry and is refused with the descriptor path error. A lock removed and already retaken by another writer is a different inode at the expected path and is still retried. A directory renamed first and removed second keeps its refusal, as CRW-794's test pinned. Pinned by `TestLockVanishedLiveLockUnderTheDeletedNameRefused` and `TestLockVanishedRemovedAndReplacedRetries`; the CRW-794 cases still pass). Darwin is as CRW-794 left it: `F_GETPATH` fails for an unlinked directory, so the recognition never fires there (port: kept).
- The locked review re-hash read a plan file with a blocking, context-blind `ReadFile`, so a plan file swapped for a FIFO after the unlocked check kept the session and goalplan locks held until a writer appeared, and the cancellation check after it could not run; every other writer of the plan answered busy and a second SIGINT left the lock directory behind. The oracle's `readFileSync` blocks on a FIFO as well (and it holds no lock there); port: fixed, recorded deviation (`reviewRoundArgsBase.read` opens the entry through the directory handle with `O_NONBLOCK` and reads only a regular file, so a FIFO or other special file is an error at once: `Recomputed` hashes it as `missing`, which makes the re-hash refuse as "the plan changed after round ... approved it" and release the lock, and `review-round open` reports the read error. Pinned by `TestRecomputedReadsASpecialFileAsMissing` and `TestOrchestrateCommitLockedReviewRehashDoesNotBlockOnAFifo`, which fail by timeout on 50f1f3c2).
- `WithGoalplanWriteLock` answered `unreadable` without `Refused` for every read that returned no plan, so a plan the reader refused to revive because a write would lose stored text (an unpaired surrogate escape, bytes that are not UTF-8 or a repeated key in a file whose last value leaves the plan malformed) was treated as an absent plan and the A>B publication went on without either locked check; and a plan file that was a link, a FIFO or a relocated descriptor at the open after the lookup was `unreadable` as well. The oracle has no such guard (`JSON.parse` keeps the last value and the oracle cannot lose text it never re-encodes); port: fixed, same defence as the three `Refused` answers above (the reader returns the text it decoded and the open failure with the read, and the lock refuses with `Refused` for an unpaired surrogate, bytes that are not UTF-8 and a repeated key even when no plan could be built, and returns a Go error for an open failure that is not an absence or an access failure (EACCES, EPERM), so a swapped link or special file publishes nothing. A plan that is only invalid JSON or the wrong shape, with none of those, stays an absent plan and fail-open as the oracle's catch is. Pinned by `TestWithGoalplanWriteLockUnrevivablePlanThatLosesTextIsRefused`, `TestWithGoalplanWriteLockSpecialPlanFileStaysAnError`, `TestRevivalLossReadPlanLinkIsAPathSafetyFailure` and the two new cases of `TestOrchestrateCommitWithheldPlanPublishesNothing`).
