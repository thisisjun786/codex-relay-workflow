# CRW-975 — the A>B publication judges under the goalplan lock, an unreachable plan fails open, a withheld plan refuses (CRW-976 folded in)

Source: CXC v0.2.40 (`3c1459ac`) `plugins/codexclaw/components/pabcd-state/src/orchestrate-cli.ts` (`validateReviewBinding` :49-95 called at :688-691, the work-phase binding read :606-622, the A>B state write :1119) and `goalplan.ts` `withGoalplanWriteLock` (:806-873). Ported in `internal/pabcd/cli/orchestrate_transition.go` (`orchestrateCommitPublish`), `internal/pabcd/cli/orchestrate_review_binding.go` and `internal/pabcd/goalplan/lock.go`. Found by the evaluations of CRW-755 (`pr720`) and CRW-811 (`pr727`) and of CRW-794 (`pr706`, CRW-976, a duplicate of this issue).

- The review binding check read the goalplan without its lock, and the publication's lock callback revalidated only the work-phase binding, so a reviewer FAIL recorded under the lock between the check and the publication was ignored and A>B was published. The oracle has the same race (`validateReviewBinding` :688-691 and the A>B write both run without any lock), and CRW-755's entry did not record it; port: fixed (`orchestrateCommitPublish` judges the review binding again, through `orchestrateReviewBindingCheckPlan`, on the plan its lock callback read, after the work-phase binding and before the stale-round housekeeping and the state write, so a refusal there writes nothing. The unlocked first check stays in front for the oracle's refusal precedence. Pinned by `TestOrchestrateCommitRechecksTheReviewBindingUnderTheLock`, which orders the reviewer's write with the `lockGoalplan` seam, and the contrast `TestOrchestrateCommitReviewBindingUnderTheLockStillPasses`).
- `WithGoalplanWriteLock` returned a Go error for a plan directory it could not open or a plan file it could not look up (EACCES and the like: any non-absent `openPlanDir` or `Fstatat` error), while `ReadGoalplan` answers nil for the same directory and the oracle goes on when it cannot open the plan (:606-622, answer 4 of CRW-811). CRW-811 made the A>B publication stop on it, a regression; port: fixed (those two failures are now `Kind: "unreadable"` with the reason, no Go error, and `orchestrateCommitPublish` treats `unreadable` without `Refused` as the fail-open it always was and publishes outside the lock. The other callers of `WithGoalplanWriteLock` already refuse on `unreadable`, so for them a Go error becomes a refusal naming the reason. Pinned by `TestWithGoalplanWriteLockUnreadableDirectoryIsUnreadable` and `TestOrchestrateCommitUnreachablePlanFailsOpen`).
- A plan the lock read but withholds from writers (bytes that are not UTF-8, a repeated key, a field this build cannot keep: the three `revivalLossRefusal` answers) came back as the same `unreadable` kind, and `orchestrateCommitPublish` published the state outside the lock with the work-phase binding it had read earlier, against CRW-811's answer 4; port: fixed (`GoalplanWriteLockResult.Refused` marks those three; the publication answers the lock's reason with "Nothing was written." and publishes nothing, no row. An absent or unreachable plan is not `Refused`. Pinned by `TestWithGoalplanWriteLockRevivalRefusalIsRefused` and `TestOrchestrateCommitWithheldPlanPublishesNothing`).
- CRW-976 (folded in): `goalplanLockVanished` took a held lock whose descriptor path was `<lock> (deleted)` for a released one on the name alone, so a live lock moved to a sibling literally named that was retried and a second writer entered the plan. The oracle has no descriptor check at all (`mkdirSync` is the lock), so the defence is the port's own and was to meet CRW-794's "any other path is an error"; port: fixed, and CRW-794's "port: kept (deliberate, recorded)" for the name-based recognition no longer holds (the recognition now needs the spelling and the identity: the kernel's `<lock> (deleted)` path, the held descriptor unlinked (`fstat` nlink 0), and the lock name in the plan directory absent (`fstatat` ENOENT) or another inode. A live lock moved under that name still has its directory entry and is refused with the descriptor path error. A lock removed and already retaken by another writer is a different inode at the expected path and is still retried. A directory renamed first and removed second keeps its refusal, as CRW-794's test pinned. Pinned by `TestLockVanishedLiveLockUnderTheDeletedNameRefused` and `TestLockVanishedRemovedAndReplacedRetries`; the CRW-794 cases still pass). Darwin is as CRW-794 left it: `F_GETPATH` fails for an unlinked directory, so the recognition never fires there (port: kept).
