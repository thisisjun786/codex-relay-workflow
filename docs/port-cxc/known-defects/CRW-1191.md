# CRW-1191 — the record writer left the node pin out, so every record it sealed was refused by the pins judge

Source: CRW's own design, not the CXC oracle (CXC v0.2.40, commit 3c1459ac, has no verification record). A regression of CRW-1026 (d1): the judge (`dagsched.DeclaredToolPins`, `internal/relay/dagsched/verification_pins.go`, used by `crw manage runtime-upgrade` through `internal/manage/upgrade_steps.go` and by the commit-acceptance path) requires a pin for every tool the verified commit declares, and the record writer (`internal/dev/ci/local.go`, `local_tools.go`) read the pins through `dagsched.DeclaredToolchainPins`, which has no node. Found on 10-11 by `crw manage runtime-upgrade --dry-run --verification <record>` on release v0.4.0-7978-g2ad657728: `disposition_conflict: the verification record has no pin for node, which the verified commit declares as "24.20.0"`.

- The writer took go, staticcheck and gitleaks from the judge's reader and node from a reader of its own (`parseWorkflow`, the local plan's line reader of ci.yml), which on the repository's own ci.yml found no node-version: its `with:` block opens with a comment line, and the line reader ended the block at the first line it did not read as an entry, so the `node-version` after the comment was never seen. The record's `tools.node` was observed from the host (24.20.0) and its `pins` had no node, so the judge refused every record the integration left; port: fixed (the writer has no reader of its own for any pin: `localToolPinsFrom` is `dagsched.DeclaredToolPins`, node included, and `localPinsAt` (the reuse recomputation) and both call sites of the writer (the unsealed record and the sealed one) take the pins from it, so the writer and the judge cannot declare different sets again. A tree without a setup-node step has no node pin and its record is judged without one, as CRW-1026 decided; a ci.yml that mentions setup-node in a form the judge's reader cannot read is now an error of the writer too, where the writer's line reader dropped the pin silently. Pinned by `TestLocalToolPinsOfTheRepositoryTreeIncludeNode`, `TestLocalToolPinsCarryTheNodeOfAConditionalSetupNodeStep`, `TestLocalToolPinsOfATreeWithoutSetupNodeHaveNoNode` and the end-to-end `TestLocalRecordTheWriterSealsIsAcceptedByTheRuntimeUpgradeJudge`, which seals a record with `localVerify` and `writeRecord` and judges it with `dagsched.JudgeVerificationRecord` for the keys `dagsched.CommitVerificationKeys` reads from the commit).
- The same comment line hid the node-version from the local plan's own reading of ci.yml, so the per-job node comparison (`localNodeMismatch`) and the step digests ran without it on the repository's ci.yml: a changed `node-version` was neither a mismatch against the host nor plan drift; port: fixed (`parseWorkflow` skips blank and comment-only lines, which carry no key, instead of ending the open `with`/`env` block on them. Five `with` blocks of the repository's ci.yml open with a comment, so those five were read as empty and are now read in full (blocks that open with a key were read before and are unchanged): the three `actions/checkout` steps (validate step 2, skill-scripts-node step 2, gui step 2; zero-based, as in `localStepDigests`) regain their `fetch-depth` and `persist-credentials`, and the two `actions/setup-node` steps (skill-scripts-node step 4, gui step 5) regain their `node-version`. Those five digests of `localStepDigests` are regenerated, and a record sealed before this change has another plan digest and is not reused. Pinned by `TestLocalWorkflowNodeVersionsAreTheJudgesDeclaration`, which reads the repository's ci.yml with both readers and requires the same node-version, and by `TestLocalDigest_the_table_matches_the_real_workflow`).
- The local fixture workflow of the engine tests gave `node-version` to an `actions/checkout` step, which the judge's reader (rightly) does not take as a node declaration, and the tests that need a node pin passed only because the line reader took any `node-version` key; port: fixed (the fixture's node-version is on an `actions/setup-node` step).
