# The crw flow commands

`crw flow` is the command line of the flow engine: the process that runs a workflow script for one run, and the commands that start, show, follow, answer, pause, cancel, resume and recover a run. This page is the one reference of the commands; the script format is `docs/flow/script.md` in the CRW repository, the journal a run writes is `docs/flow/journal.md` in the CRW repository, and the scheduler a run asks for its slots is `docs/relay/dag-scheduler.md` in the CRW repository. The agent calls a run makes, and why, are the [spawn policy](spawn-policy.md).

A run is a process that lives for one run and loses nothing when it dies: every fact is a row of its journal in the relay store, the run lock (`<state>/flow/<run>/run.lock`) says whether a process holds the run, and `crw flow resume` or `crw flow recover` takes a run whose lock is free from the journal again. The orchestrator thread that started a run owns it; the Stop hook prints the run's status line in that thread only, at the end of its turns. While the thread is idle, the progress is read with `crw flow watch`, the GUI Runs page and Linear.

## The crw flow command table

| Command | What it does |
| --- | --- |
| `crw flow start WORKFLOW [--args JSON \| --args-file FILE] [--handoff FILE] [--child-host FILE] [--thread T] [--token-budget N] [--pool N] [--decision D] [--preview] [--force]` | Shows the preview (the nodes, the width, the role pairs, the budget and the level of each preflight fact: pass, warn or fail), then starts the detached run process (its own session, no inherited descriptors, the run lock) and prints the run id. `WORKFLOW` is a built-in workflow (`project-lane`, `night-batch`, `land-head`) or a script file; `land-head` lands a head the child made outside a run through the gates of a run (args `plan`, `milestone`, `issue`, `head` and `authors`, the subagent threads that wrote it: verification, a review by another model family than the authors, acceptance and integration; docs/flow/script.md, "Landing a head made outside a run"). `--decision D` starts `night-batch` from the parent's decision record D. `--handoff FILE` names the crw-plan handoff the plan's current revision was compiled from, which the project lane reads its milestone from; a milestone whose required commands the shipped verifier cannot run (anything but `crw-dev ci local`) is refused here. `--child-host FILE` names the host settings (`crw-flow-child-host/1`: `marker_root`, `parent {host_id, settings}`, `child {host_id, title, settings}`) a node sized for a child is started with; the run pins a copy, and without it such a node is refused `child_host_unset`. `--preview` stops after the preview; `--force` is accepted and changes nothing, because a fact never stops the start |
| `crw flow ps [--all] [--json]` | One line for each run: its state (`running`, `paused`, `dead`, `held`, `completed`, `blocked`, `cancelled`, `failed`), workflow, owner thread, calls and tokens (the total, then the cached input, the fresh input - the input minus the cached - and the output). Without `--all` it lists the runs that are not over |
| `crw flow show RUN [--json]` | The tree phase, then agent: for each agent call its role, node, thread, status and reason, the commits of its node, the review verdicts, the tokens (split into cached input, fresh input, output and reasoning), `recovery_hold` where a call's outcome is unknown, and the join items that threw |
| `crw flow watch RUN [--after SEQ] [--wait N] [--limit M] [--follow] [--json]` | The same tree as `show` with the cursor of the last row it was made of; with `--after SEQ` the rows of the run after that cursor, read as `crw relay journal-tail` reads the relay journal: the cursor is the `seq` of the last row, `--wait` waits for a row without holding a transaction, and the next call passes the cursor back. `--follow` keeps reading until the run is over or has no process. The rows are the run's own: a command that writes into a run (`crw flow report-up`, `apply`, `report-ack`, `report-delivered`) numbers its rows apart, and `crw flow reports` lists them |
| `crw flow answer --decision D --run RUN --node N --question Q --revision V [--answer-for DIGEST=TEXT ...] [--no-resume]` | Applies the parent's answer record D (the relay's user-decision record, answered with `crw relay decision-answer`) to the wait of a run: it compares the question and its revision, the node and its attempt, the run, the plan basis and the authority of the record with the run's journal, appends one `decision_applied` row, and resumes that wait. The same answer again appends nothing |
| `crw flow pause RUN` | Asks the run process to stop sending requests; the calls in flight end held (`engine_paused`) and `crw flow resume` goes on with them |
| `crw flow cancel RUN` | Ends the run: the calls in flight are cancelled and the run finishes `cancelled`; the executions the run released and still owns are given up and their slots returned |
| `crw flow resume RUN [SCRIPT] [--detach]` | Takes the run from its journal again with the same script and arguments, once its run lock is free |
| `crw flow recover [--run RUN] CALL (--adopt THREAD\|TURN \| --absent)` | Settles a call in `recovery_hold`: the only manual way out of a call whose outcome is unknown, and the rows it appends are the evidence it relied on |
| `crw flow digest RUN [--out FILE]` | The run digest of a night batch (`crw-batch-digest/1`) built from the run's journal: for each selected issue whether it was integrated (with the commit, acceptance and integration the journal shows), carried (with the reason: a held call, a recovery hold, a node that did not start), cancelled or left for a decision, why the run stopped, and the token budget spent with its split. `crw manage batch report --digest FILE` makes the morning report from it |
| `crw flow audit (--run RUN \| --acceptance ID) [--milestone M] [--json] [--no-record]` | The audit of the reviews behind the agent-path acceptances of a run, read back from the reviewer threads on the run's host (CRW-1206): each acceptance is `ok`, `mismatch` or `unobserved`, and the exit is 1 unless every one is `ok`. Once the run has finished the result is appended to its journal as a `crw.audit` row, unless `--no-record` is given |
| `crw flow apply`, `crw flow report-up`, `crw flow reports`, `crw flow report-ack`, `crw flow report-delivered` | What reaches up from a run (CRW-1204): the orchestrator applies a child's receipt, lifts a blocker or a decision request, and the parent reads and acknowledges the reports; `docs/flow/reporting.md` in the CRW repository. A run process hands its plan summary, its escalations and its completion digest to the same reporting, whether `crw flow start` or a resume started it |
| `crw flow status-line --thread T` | The one line the Stop hook prints, when thread T owns a run that is not over; it prints nothing for any other thread |
| `crw flow plan-input --milestone OWNER/NAME#N [--target-repository DIR --base-ref BRANCH] [--thread T] [--envelope]` | Builds the handoff of `crw flow compile` from one milestone of the tracking repository and prints it; it only reads. See [crw flow plan-input](#crw-flow-plan-input) |
| `crw flow run --backend fake`, `crw flow roles`, `crw flow compile`, `crw flow lint` | The fake run, the role table, the plan compiler and the script check of the engine |
| `crw flow trace export`, `crw flow shadow`, `crw flow measure` | The trace tools, which read store copies and trace files and call no agent |

## The commands

Exit statuses: 0 did what was asked; 1 refused with a reason (a start that is `blocked`, a record that does not hold, a run that is over, a run no process holds); 2 a command line, a store or a record it cannot use; 3 a process already holds the run lock. Every command takes `--state DIR` and `--socket PATH`; without them the relay's own selection is used.

### crw flow start

Shows the preview, then starts the run process: the same executable as `crw flow _run`, in a session of its own, with no descriptor of the caller's (a descriptor that cannot be kept out stops the start), no input and its output in `<state>/flow/<run>/process.log`. The spec it starts from (`<state>/flow/<run>/run.json`: the workflow, the arguments, the owner thread, the budget, the deadline, the repository) is written first and never replaced, so a resume runs the script and the arguments the run started with. The answer is the run id. A workflow that calls a `crw.*` operation (the built-in `project-lane` and `night-batch` do) is not started by a build that installs no such operations: the preview says so (`blocked`) and `--force` does not override it, because the run would end in a script error at its first call. The shipped binary installs them: the operations run on the relay's DAG scheduler, and the run is the orchestrator of its plan (it claims the plan's coordinator epoch before its first write, and a run whose epoch another session took has its next write refused, which ends the milestone `incomplete`). A workflow that reads its milestone (`crw.milestone`) needs the compiled milestone: `--handoff FILE` names the crw-plan handoff (`crw-flow-compile-input/1`, with an entry in `milestones[]` for each milestone: title, criteria, surfaces, grade, required commands) that produced the plan's current revision, and the run copies its bytes to `<state>/flow/<run>/handoff.json` and names that copy and its sha256 in its arguments, so a resume reads what the run started with; without it the preview says `blocked`. The plan's target in the handoff is the local checkout and the branch the run integrates its nodes into.

### crw flow ps

Lists the runs of the store. A run is `running` or `paused` while a process holds its run lock, `dead` when none does and the journal has no finished row after the last start, `held` when it finished but a call, a recovery hold or a question is left, and `completed`, `blocked`, `cancelled` or `failed` when it is over. `blocked` is a run meant to start the nodes of a plan (a run of `project-lane`, `issue-lane` or `night-batch`, or one whose arguments name a `plan`) that finished completed and started no node: no `crw.release` released one, no child was released and nothing landed, and items of its joins threw (a release that failed); the run reports itself to the parent as `project_blocked`. A node the scheduler held back unreleased (capacity) is a wait a resume asks again, and the run stays `completed`; so does another script run (a judge panel, a scout) whose item threw. `--json` gives each run's `item_errors` (the item, its path, the error).

### crw flow show

The tree of one run: its phases in the order the script opened them, the agent calls made in each (role, node, status and reason, thread, tokens), and under them what each node has: the commits, the review verdicts with the reviewer's call, the acceptance and the integration, the tokens. A call whose outcome is unknown, and the node it belongs to, are marked `recovery_hold`. Each join item that threw in the run's last process is a line `item <key> failed: <error>`, and a `blocked` run says that no node started. The line for the calls a resume goes on with (`crw flow resume RUN`) is printed only while no process holds the run lock: a run whose process is alive goes on by itself, and `crw flow resume` refuses it.

### crw flow watch

Without `--after`, the tree of `show` and the cursor it was made at. With `--after`, one read of the run's journal after that cursor: at most `--limit` rows, `--wait` seconds for a row when there is none, and the cursor line to pass back. `--follow` prints the tree, then keeps reading from its cursor until the run is over or has no process, one line for each row, and ends with the tree again. The rows carry no call results; the journal itself holds them.

### crw flow answer

See [How an answer names its question](#how-an-answer-names-its-question). The answer is applied to the journal of a run no process holds: a run a process holds is refused (`crw flow pause` first), the row is appended under the run lock, and the run is resumed in the background unless `--no-resume` is given. The refusals are `not_answered`, `bad_binding`, `other_run`, `other_node`, `unknown_question`, `stale_revision`, `stale_attempt`, `stale_plan_basis`, `out_of_scope_authority`, `already_applied`, `unknown_question_digest` and `answer_part_not_recorded`.

A design ask can join several questions (its evidence names their digests). `--answer-for DIGEST=TEXT`, once for each question, gives a question its own part of the recorded answer: the digest has to be one the ask joins (`unknown_question_digest` otherwise) and the text has to be text of the record's answer (`answer_part_not_recorded`), and the row keeps the parts by digest, so each question reuses its own part from the next audit round on. A question the answer gives no part takes the whole answer, as before, and the row and stderr carry the warning `single_answer_for_joined_ask`. An ask also carries the questions the run asked earlier that no answer reached and the current DESIGN no longer raises, so they stay answerable through the current ask.

### crw flow pause

Signals the process that holds the run lock (SIGUSR1): the detached run process and a foreground `crw flow resume RUN [SCRIPT]` answer it alike. The process stops sending: the turn in flight is interrupted and the calls that would send end held `engine_paused`; the run then finishes `held`, and `crw flow resume` goes on with those calls. A run no process holds is refused, since nothing runs.

### crw flow cancel

Signals the process (SIGTERM): the calls in flight are cancelled and the run finishes `cancelled`. A process whose lock names no pid is never signalled (a pid of 0 would be the caller's own process group); the command says so and the operator ends the process by hand. A run no process holds is cancelled by a finished row appended under the run lock, after the executions its journal shows it released and did not end have been closed with `flow_cancel` (the slot returns in the same transaction); when that fails the run stays as it was and the command can be repeated. An execution is given up only while it is the run's: its run id is the cancelled run's and it is the execution the run released (or follows it in the node's chain). A node that another run released again after this run's cancel keeps its execution and its slot, so the second cancel of a cancelled run never takes them. A run that is already cancelled is settled the same way once more and then refused as over.

### crw flow resume

Takes the run from its journal once its run lock is free: with the run's own spec (`crw flow resume RUN`, in the foreground, or `--detach`), or with a script and arguments given (`crw flow resume RUN SCRIPT`, the engine's command, which refuses a script or arguments that are not the run's). Both go on under the budget and the deadline of the run's spec (a night batch's are its decision's): `crw flow resume RUN SCRIPT` takes the spec's budget when no `--token-budget` is given, refuses a `--token-budget` of 0, below 0 or above the spec's (a lower one narrows it), and pauses the run at the spec's deadline. The budget is the run's, not the process's: a resume allows what the spec's budget leaves after the tokens the run's journal shows it spent (each call's terminal rows counted once), a `--token-budget` narrows that remainder, and a run with nothing left is not resumed and reports `budget_exhausted`; more budget is a new decision. Every call whose last row is an intent is looked up on the host before the script runs again; a call in recovery hold stays until `crw flow recover` settles it.

### crw flow recover

The engine's recovery of a call in `recovery_hold`, under the run lock of the run that holds the call. `--adopt THREAD|TURN` takes the thread or turn the operator names after the proofs of the call's cwd, source and history; `--absent` reads the host again and accepts the call only when the same proofs hold as for an automatic outcome. What it relied on is appended to the journal as `recovery_cleared` with its evidence.

### crw flow plan-input

Builds the handoff `crw flow compile` reads (`crw-flow-compile-input/1`) from one milestone of the tracking repository, so that `crw flow plan-input --milestone OWNER/NAME#N | crw flow compile --dry-run -` checks a milestone as it stands. A child takes one milestone: the plan's project key is the milestone ref `OWNER/NAME#N`, each open issue of the milestone is one issue line keyed by its ref, and the order is the `Blocked by:` lines of the bodies (a blocker that is an open issue of the milestone becomes `after`). The command reads through the tracking adapter with GET requests (the token is `GH_TOKEN`, `GITHUB_TOKEN` or `gh auth token`) and writes to neither GitHub nor Linear.

The ref is the identity, and the input spells it `OWNER:NAME:N` (`o/r#3` is `o:r:3`), because the relay dag reads a plan's project key, node ids and edge ids as identifiers (a letter or a digit, then letters, digits, `.`, `_`, `:` and `-`, at most 128 characters; the order edge of two issues is `e:FROM:TO`, so both keys fit in 125 characters together). A `:` cannot occur in a GitHub owner or repository name, so the form is unambiguous and reads back to the ref. The project key, the issue keys and `after` of the input, the scope key of the owner's parent binding and the comparison below all use this form; the envelope's `milestone` and `refs` and the warnings show the refs. A key the dag cannot hold, or an order edge over the limit, is an input error that names the refs and the limit; no key is shortened.

The body of an issue is read from a small fixed set of headings, matched without regard to case, level, bold marks and a trailing colon; a section runs to the next heading and a heading inside a code fence is not read.

| Field | Heading | Reading | When the section is missing |
|---|---|---|---|
| `criteria` | `끝 조건`, `Done when`, `Acceptance`, `Acceptance criteria` | the bullets (also numbered and checkbox items) | the title is the one criterion, with the warning `criteria_missing` |
| `regions` | `수정 범위`, `Edit regions`, `Regions` | each bullet names a path in backticks, else its first word; a trailing slash is a tree | no region; the compile default applies |
| `size_fit`, `size_reason`, `issue_size` | `크기`, `Size`, `Size fit` | lines `size_fit: V`, `size_reason: V`, `issue_size: V` with a value of the closed set | nothing; the compile defaults apply |

`--target-repository` (the absolute path of the checkout) and `--base-ref` (the branch) give the project its target, which compile needs for any order between issues. `--envelope` prints `{schema, milestone, input, refs, warnings}` instead of the bare input, so the warnings are recorded with it; `refs` maps each key of the input back to its `OWNER/NAME#N` ref.

Nothing the mapping cannot carry over refuses: it is a warning, printed on stderr as `crw flow plan-input: warning: [rule] ISSUE: detail` and kept in the envelope's `warnings`. The rules: `criteria_missing`; `region_invalid` (a path that is absolute, leaves the repository or is the root); `size_value` (a value outside the closed set); `blocker_closed`, `blocker_outside_milestone` and `blocker_self` (a `Blocked by:` line that names a closed issue, an issue of another milestone or repository, or the issue itself); `target_missing` (an order and no target); `milestone_closed`; `no_open_issue`; and the two comparisons of the project key with the live parent bindings of the owner thread (`--thread`, default `CODEX_THREAD_ID`, read from the relay store read-only, as `crw flow start` does): `project_key_bound` when the thread holds no live parent binding under the plan's project key (`OWNER:NAME:N`; the keys are compared exactly, as `crw flow start` and the first claim compare them, so a binding that differs only by case is another key, and the warning says so), naming the key, the milestone ref and the bound keys, and `project_key_unchecked` when there is no thread or the bindings cannot be read. Exit 0 built; 2 an input that cannot be used: a ref that is not `OWNER/NAME#N`, a milestone that does not exist, a token the repository refuses.

### crw flow status-line

The line the Stop hook prints, `crw flow <run> <state> · <phase> · <n> calls · ...`, for the runs of thread T that are not over, and nothing for any other thread.

### crw flow digest

The digest of a night batch; see [The night batch](#the-night-batch).

## Who owns control in a flow-managed run

A flow-managed node is an issue node that the child's run released to an executor, or the issue-lane run of an oversized child. In both the run is the one process that knows what happens next; no thread it starts holds that knowledge. A head the child made outside a run is landed by a `land-head` run, which releases the node to itself and holds the gates below (verification, an independent review, acceptance and integration) as a project lane does; the thread does not land it another way.

| Control | Owner | What it means |
|---|---|---|
| Phases and their order | the run: its script and its journal | Build, verify, review, land and close follow the workflow the run was started with. An executor builds and returns its receipt; it never decides the next phase. A resume goes on from the journal |
| Audit | the run | The run calls a reviewer of another model family for the design audit and for each head, and `crw flow audit` reads the reviews behind its acceptances back from the reviewer threads on the host |
| Evidence | the run | A verification record, a verdict, a pre-merge record or a QA receipt is made from calls the run owns and commands the run itself runs. What an executor writes about its own work, a skill-loading line or a quoted instruction is no evidence |
| Escalations and decisions | the orchestrator thread; Jun for what only Jun takes | The run raises an escalation and waits; `crw flow answer` applies the answer. The thread does not release, accept or integrate a node the run owns |
| Acceptance and integration | the run, through the relay's DAG scheduler | The run holds the plan's coordinator epoch, so a transition written by another hand is refused by the epoch fence (`stale_coordinator_epoch`) and raised as an escalation, and the run does not take it over |
| The PABCD state machine | nobody in a flow-managed node | The executor and an oversized child start no PABCD state machine. The standalone PABCD rules are unchanged: a task that is not a flow-managed node keeps its own phases |

### The high-risk procedure of a C4 issue

An issue that [crw-dev](../../crw-dev/SKILL.md) classifies as C4 runs in the flow in this order. The numbered steps are the run's own lane; none is a thread's choice.

1. The architect DESIGN of the milestone.
2. The pre-build design audit, by a reviewer of another model family than the architect, before any executor starts. `needs_changes` returns to the architect on its own thread, and a replan is audited again. Only an approved DESIGN reaches an executor.
3. The candidate review of each issue: a fresh reviewer, of another model family than the issue's authors, over each executor head that passed its verification.
4. After the issues are integrated, the final gate with full verification and the risk record, then reviewer-final over the integrated range.

Reviewer-final does not replace the pre-build design audit: it rules on a range that is already built, and step 2 exists to stop a flawed design before any executor writes it. Neither does it replace step 3.

## The preview and the five facts

`crw flow start` prints, before it starts anything, what the run will do and whether the way back to the orchestrator thread works. Each fact has a level and the reading behind it: `pass`, the records show the way works; `warn`, the records cannot tell yet and the reason says why; `fail`, the records show the way does not work or the fact cannot be read. The five facts: (1) `assignment_routed`, the assignment is routed to this thread (a live scope binding); (2) `delivery_ticking`, the delivery service has ticked and has delivered; (3) `thread_reachable`, the thread can be reached (its lifecycle reading and its authorized settings); a thread the delivery service has not read yet, or one with no authorized settings recorded yet, is `warn`, because those rows are written after the first delivery to the thread and at its managed start, so a new orchestrator thread's first run has neither; an archived or undeliverable thread is `fail`; (4) `waits_deliverable`, every disposition the run waits in can produce a delivery: `pass` when the three facts above pass, `fail` when `thread_reachable` fails, `warn` otherwise; (5) `idle_wake_observed`, the relay holds a wake of an idle thread in this store: `pass` on a wake row, otherwise `warn`, because the relay deletes a wake once its attempt is answered and keeps no other record of it. After the five, `project_key_bound` is listed only when it does not pass: the plan the arguments name is put under a project key that is not the `scope_key` of a live parent binding of the owner thread (the project's UUID), so the run's first claim would be refused `scope_role_mismatch`; it is a `warn` naming both keys, checked before the run process starts and so before any role call. A key the thread is bound to, and a plan with no revision yet, print nothing. `issue_ready` is listed the same way: an issue of the milestone whose body the handoff carries (`description`, `labels`) that `crw skill issue-ready check` holds (`not_ready`, `design_first`) or warns of is a `warn` with the decision and the reasons; the run starts and releases it.

A fact never stops the start. Under the rule that a reversible step is warned and recorded, not refused, `crw flow start` prints every fact, says on stderr which ones did not pass, writes them with their readings and reasons into the run's spec (`preflight` in `<state>/flow/<run>/run.json`) and starts the run; `--force` is accepted and changes nothing. Read the warnings and the failures before the run waits on its owner: a run that cannot reach its owner waits unseen. What stops a start is `blocked` (a build without the lane operations, a lane without its compiled milestone), which no fact and no flag changes.

After the five, `verifier_prerequisites` says whether the run's verifier can start `crw-dev ci local` with the tools the `verifier` section of the crw configuration names (the Go toolchain root and how crw-dev runs), or `PATH` when it names none. It is `pass` or `warn`, never a failure: a `warn` gives its reason (no go, a crw-dev that does not run, a go older than the repository's `go.mod` asks, a repository without `cmd/crw-dev` for a tree verification) and, when no root is configured, the Go toolchain root found on the host with the `crw config verifier --go-root` command that records it. It never stops the start; `crw doctor` shows the same reading as its `verifierTools` entry.

## Answers and waits

A wait for a decision (`crw.decide`) ends the lane's work for the run; the run goes on with that wait only when its journal holds the `decision_applied` row for the question. `crw flow answer` appends that row after it compared the record with the journal; the record (written by the parent with `crw relay decision-answer`) and the row (written for the run) are two facts. The journal holds the evidence of an applied answer, and the relay's `decision-apply` is for the oversized child's relationship only.

## The night batch

A night batch is a decision and a run. The parent selects the issues (`crw manage batch plan`, 1040a) and records the decision with `crw manage batch decide --plan FILE --flow-plan PLAN --milestone M --handoff FILE --token-budget N --deadline T`: a user-decision record (kind `policy`, options `run` and `skip`) whose context is the batch document (`crw-night-batch/1`: the label, the issues, the plan and milestone whose nodes they are, the token budget, the deadline, and the handoff the plan was compiled from by its path and sha256), raised and answered `run` through the relay's decision commands. `crw flow start night-batch --decision D` reads that record, refuses one that is not answered `run` or whose handoff file changed since the decision, pins the handoff, and starts the run for those issues with the decision's budget and deadline; `--token-budget` and `--deadline` may only lower the budget and bring the deadline forward, a larger budget, a later deadline and a negative budget are refused. The run is the project lane over the milestone, after a check that the milestone's nodes are exactly the selected issues; releases happen only inside it, so there is no freeze and no grant table. The run stops at its token budget (the calls that would send end held `budget_exhausted`) and pauses at its deadline; what did not land is carried, with the reason. A milestone whose nodes are not the selection releases nothing: the run asks the parent (`night_batch_selection`), stays `held`, and its digest lists every issue as needing a decision with the plan's difference. `crw flow digest RUN` and `crw manage batch report --digest FILE` make the morning report. A run whose process was killed is taken again by `crw flow resume RUN`, builds nothing it already landed, and goes on with the rest.

## How an answer names its question

The record binds the question it answers in the members the relay's record has: one `plan_node` entry of `blocking` (`<run>/<node>`), and a `source` of kind `flow_question` (an escalation answer) or `flow_jun_decision` (a decision only Jun takes, recorded by the parent) whose ref is `<question id>@<revision>#<attempt>:<plan basis>`. `crw flow answer` compares that with what the caller claims and with the run's journal: the run, the node, the question and its revision (the question must be the latest of its node and ask), the attempt of the node it was asked in, the plan basis (the digest of the plan id and revision the run is pinned to), and the authority. An escalation is answered by the orchestrator that holds the run (class `parent`, ref the owner thread), the parent (`delegated-management`) or Jun (`user`); a decision only Jun takes needs the `user` class and a way the user's answer arrives (`dots`, `direct-ask`, `file-import`, `management-message`), never the parent's report read back. The first difference is the refusal, and nothing is appended.
