# Execution roles

Here the parent (repository session, relay role `supervisor`) and the child (project session, relay role `parent`) are layers of [the level table](hierarchy.md#the-levels).

The roles a task or a helper runs as, named by their policy keys, and where each one's settings are decided. This file names no model and no reasoning effort: a document that carries one is a second source of truth beside the host's execution policy. The levels the keys belong to are in [hierarchy.md](hierarchy.md).

## Execution settings by role

Each level runs on the model and reasoning effort decided for its role, and which pair belongs to which role is a recorded product decision rather than something a task infers. Two roles may be decided onto the same pair; each is still read and checked as its own role. The model of the `supervisor` role is Jun's own selection and is never propagated, changed by automation, or copied to the level below it; the pairs of `parent` and `child` come from the role policy, which may declare more than one pair for a role.

Two kinds of key are in the table. The relay roles `supervisor`, `parent` and `child` are the levels of [hierarchy.md](hierarchy.md): a task bound to an initiative, a project or an issue. The agent roles `architect`, `executor`, `explorer` and `reviewer` are the helpers a task dispatches with `crw role helper dispatch`; their prompts are `internal/role/agents/<key>.toml`, and a helper is never a level. A `crw flow` run calls the same four and two flow-only roles, `executor-t1` (the executor's tier step) and `critic` (the audit of the architect's design). `reviewer-final` is a retired role key: no flow run calls it, old run records still name it, and a policy file or a helper role store that still holds it loads with the key ignored and named in one warning (`reviewer-final is a retired role key and is ignored`).

| Policy key | Kind | Role | Settings come from | Who decides |
|---|---|---|---|---|
| `supervisor` | relay role | the parent's management seat, through which the store seat is read once it registers, for a decision the user owes only ([hierarchy.md](hierarchy.md#the-levels)) | its own recorded setting | Jun, directly |
| `parent` | relay role | the child (the relay's `parent` names the child of [hierarchy.md](hierarchy.md#the-levels)) | the role policy's `parent` entry | the policy |
| `child` | relay role | `child` session | one of the pairs the policy declares for `child`, chosen per issue | the policy for which pairs exist; [Child pair by issue type](../../crw-plan/references/integrations.md#child-pair-by-issue-type) for which issue gets which |
| `architect` | agent role | proposes a design and checks a plan against the repository, read-only | the helper role store (`crw role helper`) | the operator, through `crw role helper` |
| `executor` | agent role | makes one bounded change inside a stated write scope | the helper role store (`crw role helper`) | the operator, through `crw role helper` |
| `explorer` | agent role | answers a scoped question about the code, read-only | the helper role store (`crw role helper`) | the operator, through `crw role helper` |
| `reviewer` | agent role | reviews a diff or a plan adversarially, read-only | the helper role store (`crw role helper`) | the operator, through `crw role helper` |
| `executor-t1` | agent role | flow only: the executor's tier step in a `crw flow` run | the helper role store (`crw role helper`) | the operator, through `crw role helper` |
| `critic` | agent role | flow only: audits the architect's design in a `crw flow` run's design loop, read-only | the helper role store (`crw role helper`) | the operator, through `crw role helper` |

Read the pair rather than remember it. The host's execution policy declares the pair of each relay role, or several pairs for a role, and `get_capabilities` reports what it declares, so a creation states a pair that policy reports for the relay role it is creating (for a role that lists several, one entry of its `pairs`) and passes the role itself so the host checks the answer. Never carry a pair from memory, from another project, or from a document, this one included: a pair here would be named by a model and an effort, and this file carries neither. That habit is what the failure was made of: a coordinator created a child on a model it remembered, and another retried a withheld send by changing the model and keeping the previous effort. Reasoning-effort names are catalog values belonging to their own model; two that look similar are not interchangeable, and nothing maps one onto another.

A relay role that lists several pairs ranks none of them. The policy says which pairs a task may run on and not which one it does run on; for `child` the issue decides, under [Child pair by issue type](../../crw-plan/references/integrations.md#child-pair-by-issue-type).

A relay role the host's policy does not declare, or a pair it does not list for the role, is a blocker to report, and its recovery is declaring it in that host's execution policy. There is no fallback pair, because a fallback is a default and a default is the second source of truth this arrangement exists to remove.

The agent roles are decided in the helper role store and nowhere else: all six keys sit in its one `roles` object, read, changed and reset with `crw role helper` (the list and the GUI show the four helper roles; `executor-t1` and `critic` are addressed by name, and `crw role helper reset reviewer-final` removes an entry of the retired key, which `get` and `set` refuse). The host's execution policy does not decide them: a `crw flow` run reads its six pairs from the store and never from the policy's `agent-roles` section, which `crw flow roles` and `crw doctor flow-roles` warn about while a policy file still declares it. A helper role with no setting inherits the main model, which is the store's own default and not a fallback pair; for a flow run that role is undecided and warned, and so is any of the six keys in mode default. Reading the store never refuses, but a workflow with a `crw.*` lane operation needs the executor's and the reviewer's pairs, and a run on the agent backend the explorer's and the reviewer's, so either refuses an undecided one with its reason. A flow-only key with no usable setting runs its compiled default, which `crw flow roles` marks and warns about. `crw flow roles` shows the six pairs a run will use, so read them there rather than from memory.

Changing an existing task's model is a user action plus a re-record, never something a message performs. After the user changes it, the authorization recorded for that task is re-recorded from a user-attributed source before the next send, because the record is what a send verifies against and a value observed on the host is evidence of what the task is running rather than a new approval. Until then the send is refused naming the record, and a task the host reports as not loaded is left alone rather than resumed under a pair that was never checked against its role.
