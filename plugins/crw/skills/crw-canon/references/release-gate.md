# Release gate

The one rule for when an issue is released to an issue child. `crw-add-issue` fills the items, `crw-plan` applies them, `crw-tidy` supplements what is missing and `crw-run` checks the issue before any packet; each links here and restates nothing.

## The release gate

The gate asks that an issue's body already holds what the child needs to start before it is released. Work released without a decided answer makes the child design while it implements, and the evaluations that follow find the same class of fault again and again. The gate judges five items, each under its own heading in the issue body (Korean first, the English heading is read the same):

| Item | Heading | What it must state |
|---|---|---|
| `criteria` | `## 기준` / Acceptance criteria | The registered acceptance criteria as a list. |
| `edit_region` | `## 편집 영역` / Edit regions | The files or directories the change edits, in backticks: a path with a directory or an extension, a root file such as `go.mod`, `go.sum` or `Makefile`, or a root directory written alone as the first token of an entry of this section (`web`). A path named in backticks in a `## 범위` (Scope) section, the criteria or the decided answer counts; one named only in the red tests or the done condition, or under an out-of-scope heading or any heading below it, does not. |
| `decided_answer` | `## 정한 답` / Decided answer | The answer to every design question, so the child implements and does not design. |
| `red_test` | `## 먼저 실패하게 쓸 시험` / Red tests | The test cases to write first and see fail. |
| `done_condition` | `## 끝 조건` / Done condition | Which command must give which result: the command in backticks or a code block, and the expected result beside it: text that says more than a label (`Command:` or `Run` is none), or an output line of the block (a comment, an arrow, an exit status or the test tool's verdict; a second command is none). A result with no command, or a command with no result, is no done condition. |

A heading with no entry under it, or one holding only `TBD` or a none entry (`없음`, `None`, `N/A`), states nothing as criteria, decided answer or red tests. A heading nested under another item's heading is read as its own item, so an open decisions or out-of-scope heading counts at any depth, and everything under an out-of-scope heading is excluded whatever its own heading reads. `crw skill issue-ready check` reads the issue as the Linear tools return it (id, title, description and labels, as JSON on stdin or in a file) and answers `ready`, `not_ready` or `design_first`. It names every missing item with the heading that supplies it, writes nothing and reads nothing from Linear, and the same issue gives the same bytes. Every answer exits 0: `ready` and `bypassed` release, and `not_ready` and `design_first` are a warning, the decision unchanged in the report and each reason printed on stderr. Exit 2 and 3 mean the issue was not read (exit 2 also for an exception that cannot be used).

**Design first.** A design question is a decision the child would otherwise take while implementing. An issue whose `## 열린 결정` (Open decisions) section lists one, or that carries the label `설계 먼저`, is held as `design_first`: it is not released as an implementation. Every list item and paragraph of that section is read; a placeholder such as `TBD` or `미정` is a decision not yet taken, and only an empty section or an entry that says none (`없음`, `None`, with at most a note in brackets after it) leaves nothing open. The design comes first, from an architect-role proposal that checks the repository's constraints (append-only triggers, package cycles) and the parent's decision. The parent writes the result into the decided answer section, empties the open decisions, removes the label, and only then releases. The label is what makes the state visible in Linear; whoever finds an open decision on an unreleased issue adds it with the Linear write authority the assignment already gives, and a missing label is a gap the [crw-tidy](../../crw-tidy/SKILL.md) pass supplements. Assigning the architect role or any model to the design is the execution settings' business, not this rule's.

**The warn rule.** Releasing an issue is a step that can be taken back, and such a step is warned and recorded, not refused: a held answer never stops the release. The parent writes the reasons into the coordination record beside the launch, reports them to the issue's owner, supplies what it can from the evidence at hand (a missing heading's content; for a `design_first` issue the design, written into the decided answer with the label removed) and runs the check again; otherwise the release goes on with the warning recorded. The gate is this rule, the command and the tidy check, and not a refusal inside the relay. The relay's release request carries fixed fields and no issue body, and a field there would be a change to the relay ([the record at release](../../crw-plan/references/integrations.md#the-record-at-release) makes the same choice for the pair). The parent runs the command before any packet, task, `managed-start` or DAG release ([Check the issue is ready before release](../../crw-run/SKILL.md#check-the-issue-is-ready-before-release)).

**The exception record.** The parent's explicit approval of a held issue is a record the command carries (`exception`: `exception.issue` the issue's id, `exception.approved_by` the approver, `exception.approved_on` the date as YYYY-MM-DD and `exception.statement`), turns the answer into `bypassed`, and the report returns it as `exception_record` with the items it was released without, and the parent writes that line into the coordination record beside the launch. The command can refuse a record that names no approver, issue, date or statement; whether the approver was the parent is the caller's to state truthfully. A child, a parent's own judgment that the issue is small and an earlier release of a sibling are not that approval.
