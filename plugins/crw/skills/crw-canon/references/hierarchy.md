# Hierarchy

The layers of the workflow, who owns what at each, the names used for them, and where the size of each piece of work is set. Every skill and document that names a layer links [the table below](#the-levels) instead of describing the layer again. The sections below are read together with [tracking-model.md](tracking-model.md) (what each layer writes in the tracking repository) and [execution-roles.md](execution-roles.md) (what each layer runs as).

How a layer names the work it points at is in [naming.md](naming.md).

## The levels

The work runs in two Codex session layers under a top session, and the lower one calls subagents. This table is the one place the names are fixed.

| Korean | English | Duty | Calls |
|---|---|---|---|
| 총괄 | top session | The topmost session; any agent can hold it (today Sion). It talks with Jun, keeps what only Jun decides, and settles a milestone and its issues before they are registered | one parent per repository, through App Server thread send and read |
| 부모 | parent (repository session) | The Codex session that represents one repository, through its management seat (CRW-1314): it decides the order of the repository's projects, which children run together, the answers to the decisions its children raise, and it reads their reports | the top session above it; its children below it |
| 자식 | child (project session) | The Codex session of one project: it takes one milestone at a time, runs it (a flow run of [crw-run](../../crw-run/SKILL.md)), verifies and integrates it, and reports to its parent | its parent above it, a peer child beside it, its subagents below it |
| 서브에이전트 | subagents (architect, executor, reviewer, explorer) | A LEAF the child spawns for one step of a run; the run records it | nobody: it answers the step it was given |

Instruction text uses the English names; the Korean names are Jun's own words, shown to a reader, and key nothing. The code keeps some names of its own, the role ids of a stored relationship among them. They are listed in [Names used only in code](#names-used-only-in-code) and no instruction text uses them.

A subagent is no layer. In a flow run the run hands the child a step and the child spawns the subagent for it; the subagent is not a Codex task of its own, holds no binding and no role id, and the run alone speaks to it through the step it records. What it returns is the answer the run judges, not a message to a layer. An oversized issue is not a subagent's work either: the run escalates it as a `size_split` (detail `child_retired`) and starts no thread for it.

Records written under earlier names (the known-defects, the port records, the recorded dispatch cases and old handoffs) are read through this table and are not rewritten.

## Names used only in code

코드 안에서만 쓰는 이름. The names below are read by the code (a stored row, a host's role policy, a flag, a CLI word) and name no layer in instruction text. This table maps each to the layers of [the level table](#the-levels).

| Relay role id | Names | Note |
|---|---|---|
| `supervisor` | the parent (repository session) | its management seat is registered with `crw manage supervisor register` (CRW-1314) |
| `parent` | the child (project session) | the id of the child, not of the parent |
| `child` | no layer | the relay role id of a per-issue work session; an old record kind that is read only |
| none | the top session and the subagents | neither holds a role id |

The relay role ids `supervisor`, `parent` and `child` are not renamed: a relationship store, a host's role policy, a flag and a CLI word keep them as they are, and changing one would change a stored format. Read them through the table above. The relay role id `parent` names the child, not the parent, and `supervisor` names the parent. The relay role id `child` names a per-issue work session, an old record kind that is read only: a Codex session bound to one issue ID that a child released for one oversized issue before that path was retired. No run releases one now: a node sized `child` (`size_fit`, the [spawn policy](spawn-policy.md)) goes up as a `size_split` escalation. The id is a name the code keeps, and it names no layer of the level table.

The parent holds a management seat (`crw manage supervisor register`, scope kind `management`, one per parent). A store seat is the `supervisor` role with the scope `store`: a parent that registers lays its store seat down, and the relay reads the store seat through the management seat. Read that way the store seat carries the parent only a decision the user owes (a `decision_request`, a `jun_decision_request` or `flow_jun_decision_request`, a fault notice of kind `decision`) and the answer to a decision record that names no management seat; every other message of a project no management seat stands above (a child that bound itself) does not reach the parent: it finds nobody above and stays standing, and one staged before the parent registered is held unaddressed, until a management edge above that project or a live store seat names someone (CRW-1486). A parent hears its own projects' reports through the edges it writes when it binds their children.

A service-management daemon of the operating system is a different thing that merely shares a name with the relay role `supervisor`.

## Scope of each level

Each layer is one Codex session bound by stable ID: the parent to its repository through its management seat and a child to one project ID. That binding is what makes a layer. A title, a folder, a branch or a chat link is not, so identity stays on the stable IDs under [OPS-7.1](../../crw-run/references/operations.md#ops-71-what-an-assignment-binds) and [OPS-7.4](../../crw-run/references/operations.md#ops-74-three-levels-and-their-routing-identity). Each scope has one active execution owner. A subagent acquires no ownership by receiving a step and an internal helper agent (the helper role policy's) is no layer.

Writing the names down settles what they are called and nothing else. A display name in either language keys nothing, so no relationship id, assignment, goal, worktree or task title is regenerated because this section spells them out, and each layer's title is the one [Thread titles](#thread-titles) gives it. A name is not a designation either: a request, a prompt, a title or a folder saying 부모, 자식, parent or child designates nobody, so what a session is stays something read from its binding rather than from what anyone called it.

| Layer | Bound to | Coordinates | Instructs |
|---|---|---|---|
| Parent | its repository (the management seat) | the repository's projects: their order, which children run together, cross-project dependencies, shared resources, and the order in which projects reach a shared target | its children |
| Child | one project ID | its project's milestones and issues: dependencies, sequencing, the run and its subagents, delivery verification and integration; and, directly with a peer child, the surface their projects share | its own subagents only; a peer child is asked, never instructed |

| Layer | Verifies | Merges | Updates in the tracking repository | Complete when |
|---|---|---|---|---|
| Parent | each child's reported milestone and project outcome against the project's finish condition | nothing; it decides cross-project order, never a landing ([OPS-9.3](../../crw-run/references/operations.md#ops-93-the-parent-integrates-and-does-not-release)) | the description of the milestones it opens, and its own decisions | the finish condition of the work it ordered holds on its children's verified outcomes |
| Child | each step's delivery, checks and review against the issue's accepted criteria | its own project's issues, into their intended target | the milestone record and the issues it owns | every obligation in the agreed project scope is delivered, integrated and reconciled |

The tables say what each layer answers for. Jun talks with the top session: it keeps what only Jun can decide and carries his decisions to the parent of the repository they concern; the initiative, project and issue records belong to the layers below it. What the parent spends its time on is the layer above the project tables: it orders the repository's projects, decides which children run together and starts a child only when its project's prerequisites hold and the caps allow it, answers what its children raise or hands a decision only Jun takes up to the top session, reads the milestone reports, runs the midpoint check, and writes the initiative's record. Its procedure is [the parent's section of crw-run](../../crw-run/SKILL.md#the-parent-the-repository-session). The work it never takes is divided by name rather than left to the layer below: the child runs its milestones and accepts each delivery against the issue's criteria and performs the integration; the parent tests each reported outcome against the finish condition and stops there. Holding no goal of its own narrows none of that: inside an execution approval still in force it moves the approved work and resumes the responsible child, which is what [the midpoint check](../../crw-run/references/midpoint-check.md) already describes.

Several ready projects mean several children, not several projects assigned to one child. Each layer reads the layer below by result and does not repeat its work. The parent does not redo its children's issue investigation, planning or runs, and a child does not redo a subagent's step; running the same enquiry once per layer is how one project's cost becomes three.

Instructions travel between adjacent layers, and only the owning child instructs its own subagents. A parent that wants a step changed says so to that child. Where reading a lower layer directly is genuinely necessary, the existing owner stays in place, and the route and its reason are recorded.

Each layer writes its own record and no other. The parent's record is the description of the milestones it opens and its own decisions: an authorized definition change follows the [milestone description standard](tracking-model.md#milestone-description-standard), decisions and dispositions are comments, and material progress is the latest comment of the issue. The child's records are the milestone and the issues it owns. The parent's authority to write that record comes from its own assignment exactly as a child's does; the binding identifies the scope and grants nothing. Accepted design text is preserved rather than rewritten. The same boundary holds for every other sub-task an owner opens and for every route a write could take; what a returned proposal carries, and what the owner does with it, are in [record writes and returned proposals](tracking-model.md#record-writes-and-returned-proposals).

Bind each child by its stable project ID. A project keeps one child however many initiatives name it, and the other initiatives reference its outcome instead of issuing it work, so no second session instructs that child. Preserve other project coordinators and route cross-project prerequisites by relation; do not absorb their issues. A project the parent has not ordered, and a standalone issue with no project, run exactly as they do today in a project- or issue-scoped task: do not invent an initiative, a project or an upper task to complete the shape. These roles describe relationships rather than ranks, so an issue-scoped task running without a child above it is the owner of its own scope rather than a delegated `child` session: a delegated `child` session leaves merging and the tracking record to its child, and a standalone owner carries those duties as far as its own assignment authorizes them. An explicit current-task implementation request keeps that mode and issue scope; it is not evidence that an independent `child` session was created. Reuse the responsible `child` session for the same issue's follow-ups, not for a new issue. Explicit project-focus switches preserve old bindings and active ownership before establishing the new one.

Approvals and limits travel down without widening. The user's restrictions, approvals, settings and pause or cancel hold in the scope they were given, and being linked to a layer above is neither an expansion of authority nor a new goal ([OPS-7.3](../../crw-run/references/operations.md#ops-73-isolation-between-parents)). The role decides what goal a task opens, never the other way round. The parent opens none and runs no automatic loop,  What a child opens is not this section's fact to hold: it is the decision [Start policy](../../crw-run/references/start-policy.md#roles-and-the-goal-each-one-opens) records, that record has already changed once, and it is read there rather than remembered. A coordination goal that does exist is its own and is never mixed with a `child` session's implementation FSM, and an absent goal says what a task is waiting on rather than which role it is.

This contract fixes the roles; it does not establish how a parent is instantiated. A session becomes the parent of a repository only by registering its management seat, and an initiative link by itself rebinds no existing child. The designation of the projects it orders, the completion boundary and the reuse of the children already running are in [Initiative supervision](../../crw-run/references/initiative-supervision.md). Start policy, creation authority and the limits that survive them stay where they already are in [crw-run](../../crw-run/SKILL.md#independent-implementation-tasks), and this section references them rather than keeping a second copy.

## Thread titles

Every Codex thread a layer runs in has a title, and this table is the one place each layer's title is fixed. The
session that creates a thread names it right after `thread/start` with App Server `thread/name/set`, before the
first turn, so the Codex app shows the title and never the first prompt sentence in its place.

| Layer | Title | Rule | Who names it, and when |
|---|---|---|---|
| 총괄 (top session) | none | CRW does not create it, and keeps no rule for it | nobody in CRW |
| 부모 (parent, the repository session) | `[CRW] 부모 · <owner>/<repo>` | the owner and name of the repository it represents, from its checkout's origin | its creator, `create_thread`, which takes the title from the checkout's origin when the caller gives none |
| 자식 (child, the project session) | `[<product family>] <project summary>`, as `[CRW] 실사용 첫 시험 (P-CRW-140)` | [Set the app presentation and record](../../crw-plan/references/integrations.md#set-the-app-presentation-and-record) | its creator, `create_thread`, with the title the parent writes by that rule |
| 서브에이전트 (subagents) | no title | the host lists no subagent thread in the app, and a step's marker identifies it | nobody |

A creation that cannot name its thread by this table warns and records and goes on: the creation's receipt
carries `titleWarning`, `title_unset` when no title was given or could be derived and `title_not_set` when the host
refused `thread/name/set`, the bridge writes the same warning to its standard error, and the thread's first turn
still starts. A creation is never refused for a name. A lost answer to `thread/name/set` is the creation's unknown
outcome rather than a naming failure, and the replay of the same request settles it. A title is a display name: it
keys nothing and designates nobody ([scope of each level](#scope-of-each-level)), and an explicit title the user
gives a thread wins over this table.

## The message both relations are read by

A parent instructs a child and a child reports back; a child instructs a `child` session and a `child` session reports back. The two relations carry different machinery and the same questions, so what identifies a message, what the recipient owes because it arrived, and how far it actually got are decided once. This section is the workflow rule: which occasion is which, what each form carries, and when the layer above is woken. The record form itself - the field names, the version, and what each state means to the code that builds a message - belongs to the relay, as `relay-envelope/1` in `docs/relay/envelope.md`, and is read there rather than copied here. The words below are the ones that document uses, so a child and a parent mean the same thing by them.

**What a message asks for.** A request owes an answer from the recipient. A decision owes one from Jun and from nobody else. A notification owes none. A status response answers a question somebody put. The word is fixed by the occasion rather than chosen: an initial project assignment, a midpoint check, a resume, a scope correction, a decision of Jun's carried down, and a user stop are all requests, because each leaves the child something to do. A decision Jun has already made is relayed as a request for exactly that reason - what is owed is the application, not another opinion. Upward, a completion and a block are notifications, a decision request is a decision, and a midpoint answer is a status response.

A message carries no authority of its own. Being told something does not widen a scope, approve an action, or open a goal; authority travels by the assignment, as [scope of each level](#scope-of-each-level) already says.

**Parent to child** names the request, the approved scope, the constraints, what changed in a decision already made, the result and the reporting condition expected, and who owns the next step. **Child to parent** names the result and what changed, the project and issue it is about, the evidence, what is blocked now and what that blocks, and the next action with its owner. A decision subject appears only when a user decision is genuinely needed, with the reason and what each choice costs. Technical judgment, ordinary review fixes and merge approval are the child's own work and are not handed upward; merge order between two children is [CRW-123 direct coordination](#direct-coordination-between-children).

**When the layer above is woken.** A completion, a new real block, and a decision only the user can make. Not a CI run changing, not an acknowledgement, not a wait that has not changed, not a step or a `child` session progressing normally. The parent holds no goal and every wake costs it a turn, so an automatic notification that carries no decision is a cost with no reader. A midpoint check is the other path and is answered on its own terms: it was asked for, so suppression of automatic notices is not a reason to leave it unanswered.

**Five things that are not each other.** A send the transport accepted, a message received, a request understood and agreed to, a change actually applied, and a result verified. Silence is none of them. A conditional acceptance is not an application, a delivery failure is not a refusal, and an unconfirmed or stale revision is not a current one. Where a relation has no mechanism for a stage - and the parent relation has one only for a report's send and its readback, and none above those - the answer is that there is nothing to look at rather than that nobody has looked yet.

**A report is not a record.** Producing a report, the transport accepting it, the recipient reading it and the tracking repository holding it are four facts. The obligation to report something upward is discharged by the record the parent reads, and a tracking write that failed leaves it owed however complete the report text reads. The same logical result reported twice converges on one identity rather than becoming two; a correction or a withdrawal preserves what it corrects and says which decision now stands. A recipient that is paused, archived or deliberately out of contact keeps every obligation it had and is not woken to collect them.

## Direct coordination between children

Children coordinate with each other directly, and that is the ordinary path rather than an exception. Two projects whose work meets in the same files, interfaces, data or behaviour settle between themselves what each will change and what must keep holding. A parent that relayed every message would become the bottleneck it exists to remove, so it decides only what a pair cannot settle alone: an agreement they cannot reach, a change that widens either project's scope, who owns newly discovered work, and shared resources, including the order in which projects reach a shared target. The resource decision and the merge order are two decisions and are recorded as two. Where the two projects belong to different repositories, and so answer to different parents, neither parent acquires authority over the pair and none is invented or rebound: the children record the unsettled part, hold only that part while their independent work continues, and raise that decision to the top session, which takes it to Jun. Two parents coordinate across their repositories by the same route and the same form, and neither acquires authority over the other's projects by using it: a requirement for a project one of them owns is raised with that project's own parent, which decides it.

Only the owning child instructs its own subagents and `child` sessions, and no child instructs another. A peer message is a request or an agreement: the child that receives it decides what its own issues and `child` sessions do about it, and it never reaches into the other project's `child` sessions. One child cannot assign work to another, and the parent is the only layer that can change who owns what. A peer message is not a delivery: it carries no receipt, no acknowledgement and no verdict, and it never enters another child's registered relationship ([OPS-7.3](../../crw-run/references/operations.md#ops-73-isolation-between-parents), [OPS-7.4](../../crw-run/references/operations.md#ops-74-three-levels-and-their-routing-identity)).

An agreement names its target issues, the revision it is based on, the exact area each side will change, the behaviour that must keep holding, the condition for accepting it, and who owns the next step. Owning a file for this change is not owning every future change to it. Where part of the surface is unsettled, hold that part and keep the independent work moving. When the base revision or the interface moves, the agreements that depended on it are confirmed again rather than assumed.

Five things are distinct and are recorded separately: the transport accepted the message, the recipient understood and agreed, the owning child instructed its `child` session or ran the step, the change was actually made, and the result was verified. Silence is not consent and a successful send is not agreement. A conditional acceptance is recorded as conditional, together with the condition that would make it applied, and it is never cited as applied evidence. Those facts are produced along one path that stays inside the ownership that already exists: the child that accepted a condition carries it to its own `child` session or run by the correction route it already uses, keeps the adoption evidence, which is the revision where the change took effect rather than an acknowledgement, and returns the outcome to the peer itself. An agreement between two children binds no third project: a follow-up proposal records its trigger, its acceptance condition and whether the next owner accepted, and it stays marked unassigned until that owner accepts it explicitly. Where the follow-up is a required dependency, unassigned is escalated as a blocker rather than left standing as an implied promise.

A merge turn and an edit agreement are different things. Agreeing on an edit grants no merge permission and creates no new project scope, and the merge itself stays with the owning child under [OPS-9.3](../../crw-run/references/operations.md#ops-93-the-parent-integrates-and-does-not-release). Use the shared [Coordination message](../../crw-run/references/task-packet.md#coordination-message), reference the values the existing relationship already holds instead of recopying them, and prefer one message carrying a real state change over a heartbeat carrying none.

## Sizes at each level

A size is set where the work it limits is shaped, and the numbers live there and nowhere else. [crw-define](../../crw-define/SKILL.md#size-rules) sizes what it registers. [crw-plan](../../crw-plan/SKILL.md#size-rules) sizes a project, a milestone and an issue, and asks `crw skill issue-size check` for every issue. [crw-add-issue](../../crw-add-issue/SKILL.md#tell-the-caller-about-the-limits) tells its caller when the issue it adds would pass a project's or a milestone's limit. A size is advice to the person shaping the work, except the project limit that the plan itself enforces.
