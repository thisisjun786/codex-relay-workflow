
## How an answer names its question

The record binds the question it answers in the members the relay's record has: one `plan_node` entry of `blocking` (`<run>/<node>`), and a `source` of kind `flow_question` (an escalation answer) or `flow_jun_decision` (a decision only Jun takes, recorded by the parent) whose ref is `<question id>@<revision>#<attempt>:<plan basis>`. `crw flow answer` compares that with what the caller claims and with the run's journal: the run, the node, the question and its revision (the question must be the latest of its node and ask), the attempt of the node it was asked in, the plan basis (the digest of the plan id and revision the run is pinned to), and the authority. An escalation is answered by the child that holds the run (class `parent`, ref the owner thread), the parent (`delegated-management`) or Jun (`user`); a decision only Jun takes needs the `user` class and a way the user's answer arrives (`dots`, `direct-ask`, `file-import`, `management-message`), never the parent's report read back. The first difference is the refusal, and nothing is appended.

A record may instead name the child's `project_decision_request` as its source: `--source report=<report id>`, no `blocking` entry needed (one `plan_node` entry, when given, must be `<run>/<node>` of the question). The report binds the question it names (`crw flow report-up --question <escalation id>` writes the question, its revision and its node into the report row); a report without one binds the question the caller claims only when it is the one question the run waits on. The attempt and the plan basis are then the journal's and the run's, and every other check is the same as for a `flow_question` record: a report whose question the run asked again since is `stale_revision`, and the authority is that of an escalation.
