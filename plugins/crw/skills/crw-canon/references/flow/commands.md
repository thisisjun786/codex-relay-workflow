
## The commands

Exit statuses: 0 did what was asked; 1 refused with a reason (a start that is `blocked`, a record that does not hold, a run that is over, a run no process holds); 2 a command line, a store or a record it cannot use; 3 a process already holds the run lock. Every command takes `--state DIR` and `--socket PATH`; without them the relay's own selection is used.

### crw flow start

Shows the preview, then starts the run process: the same executable as `crw flow _run`, in a session of its own, with no descriptor of the caller's (a descriptor that cannot be kept out stops the start), no input and its output in `<state>/flow/<run>/process.log`. The spec it starts from (`<state>/flow/<run>/run.json`: the workflow, the arguments, the owner thread, the budget, the deadline, the repository) is written first and never replaced, so a resume runs the script and the arguments the run started with. The answer is the run id. A workflow that calls a `crw.*` operation (the built-in `project-lane` and `night-batch` do) is not started by a build that installs no such operations: the preview says so (`blocked`) and `--force` does not override it, because the run would end in a script error at its first call. The shipped binary installs them: the operations run on the relay's DAG scheduler, and the run coordinates its plan (it claims the plan's coordinator epoch before its first write, and a run whose epoch another session took has its next write refused, which ends the milestone `incomplete`). A workflow that reads its milestone (`crw.milestone`) needs the compiled milestone: `--handoff FILE` names the crw-plan handoff (`crw-flow-compile-input/1`, with an entry in `milestones[]` for each milestone: title, criteria, surfaces, grade, required commands) that produced the plan's current revision, and the run copies its bytes to `<state>/flow/<run>/handoff.json` and names that copy and its sha256 in its arguments, so a resume reads what the run started with; without it the preview says `blocked`. The plan's target in the handoff is the local checkout and the branch the run integrates its nodes into.

### crw flow ps

Lists the runs of the store. A run is `running` or `paused` while a process holds its run lock; with none it is `paused` when its last process ended paused (a `run/paused` row after the last start: the operator paused it), and `dead` when the journal has no end row (`finished` or `run/paused`) after the last start; it is `held` when it finished but a call, a recovery hold or a question is left, and `completed`, `blocked`, `cancelled` or `failed` when it is over. `blocked` is a run meant to start the nodes of a plan (a run of `project-lane` or `night-batch`, an old run of a `child` session's lane, or one whose arguments name a `plan`) that finished completed and started no node: no `crw.release` released one, no child was released and nothing landed, and items of its joins threw (a release that failed); the run reports itself to the parent as `project_blocked`. A node the scheduler held back unreleased (capacity) is a wait a resume asks again, and the run stays `completed`; so does another script run (a judge panel, a scout) whose item threw. `--json` gives each run's `item_errors` (the item, its path, the error) and its `outcome`: what the script returned it came to (the milestone state, its reason, source, escalation and milestone, and the lanes that did not land; a `milestone` member that is an object without an `id` and with a non-empty string `state` is the wrapped result and its state wins, a `milestone` member that carries an `id`, or has no non-empty string `state`, is not read as one, and otherwise the top-level string `state` of a completed script is its outcome state; a value whose own `state` is not a non-empty string has no outcome), as the finished row of the run's current end carries it; a running, dead or paused run has none.

A command that holds the run lock for a moment to write a row (`crw flow audit`, `answer`, `cancel` and `recover`; the lock's record names the holder's command) is not a process of the run: `ps`, `show` and the status line read the run as they read it with a free lock, with no pid, `crw flow pause` signals nothing, and `crw flow cancel`, `answer` and `resume` wait up to 2 s for that hold to end before they take the lock (a run process's hold is refused at once, and a hold past the wait as before).

### crw flow show

The tree of one run: its phases in the order the script opened them, the agent calls made in each (role, node, status and reason, thread, tokens), and under them what each node has: the commits, the review verdicts with the reviewer's call, the acceptance and the integration, the tokens. A call whose outcome is unknown, and the node it belongs to, are marked `recovery_hold`. Each join item that threw in the run's last process is a line `item <key> failed: <error>`, a `blocked` run says that no node started, and a run whose finished row carries an outcome has the line `outcome <state>/<reason>` with a line for each lane that did not land. A paused run no process holds has the note `paused by <by: reason>; no process holds the run: crw flow resume RUN goes on`. The line for the calls a resume goes on with (`crw flow resume RUN`) is printed only while no process holds the run lock: a run whose process is alive goes on by itself, and `crw flow resume` refuses it.

### crw flow watch

Without `--after`, the tree of `show` and the cursor it was made at. With `--after`, one read of the run's journal after that cursor: at most `--limit` rows, `--wait` seconds for a row when there is none, and the cursor line to pass back. `--follow` prints the tree, then keeps reading from its cursor until the run is over or has no process, one line for each row, and ends with the tree again. The rows carry no call results; the journal itself holds them.

### crw flow answer

See [How an answer names its question](answer-routing.md#how-an-answer-names-its-question). The row is appended under the run lock, and the run is resumed in the background unless `--no-resume` is given. A run no process holds takes the answer at once (a command's short hold of the run lock is waited out, [crw flow ps](#crw-flow-ps)).

A run a process holds (the run process, or a foreground `crw flow resume`) is not paused first. The answer is judged on the run's journal before anything is asked: a refusal or a replay is the answer, and nothing is signalled. Otherwise the answer asks that process to stop at its next boundary (SIGUSR2): the turns in flight run to their end with their results (a session step the run published before the ask among them, so the owner keeps taking the steps, [crw flow next](#crw-flow-next-and-crw-flow-dispatched)), each call's next request ends held `engine_paused`, and a run that would then end completed ends `paused` by `answer` (a `run/paused` row and no completion notice; a run that ends otherwise keeps that end). A retry or another answer signals the process again, and the run writes no second row for it (a drain is asked once). The answer then waits up to `--wait` seconds (0 unless named: it asks and returns) for the run lock; once it holds it, it judges the claim again, on the decision record as the relay holds it then, and appends the row after every row the drained process stored. A decision withdrawn (`crw relay decision-withdraw`) or expired while the answer waited is refused `not_answered` with the record's reason: nothing is appended and nothing is resumed. Not taken in that time, the answer is refused `run_draining` (exit 1): the stop is asked, not known to be made (the JSON reply says `drain_asked`, and `drained` only once every process the answer asked let the run go within the wait). An accepted drain ends `paused` by `answer`, but a deadline or an earlier pause can make it a no-op. Keep taking steps while the process lives, then read `crw flow show RUN`: for a paused, dead, or held run, retry the same answer, which rechecks the question and the run's limits; if the answer already applied after the paused end, use `crw flow resume RUN`. Inspect a completed, cancelled, or failed run's outcome instead of waiting for a paused end. A process an older crw runs writes the same lock record but drops the ask and goes on as it would have: when `crw flow next` keeps reading it live without an accepted drain or an earlier stop, `crw flow pause RUN`, then the same answer. A holder that is not a run process, or a lock whose record names none, is never signalled: the answer is refused `run_live`. A refused or replayed answer, before or after a drain, resumes nothing: only the answer that appends the row resumes the run. So a run that asked its question again while it drained (a new revision) stays `paused` when the retry is refused `stale_revision`: the answer to the new revision applies and resumes it, or `crw flow resume RUN` goes on without one.

The refusals are `not_answered`, `bad_binding`, `other_run`, `other_node`, `unknown_question`, `stale_revision`, `stale_attempt`, `stale_plan_basis`, `out_of_scope_authority`, `already_applied`, `unknown_question_digest` and `answer_part_not_recorded`, and for a run a process holds `run_draining` and `run_live`. A record whose source is a report is `bad_binding` when the report is not a `project_decision_request` of the run, when its `plan_node` entry is not the question's, and when the report names no question while the run waits on other than one (`report-up --question` names it).

A design ask can join several questions (its evidence names their digests). `--answer-for DIGEST=TEXT`, once for each question, gives a question its own part of the recorded answer: the digest has to be one the ask joins (`unknown_question_digest` otherwise) and the text has to be text of the record's answer (`answer_part_not_recorded`), and the row keeps the parts by digest, so each question reuses its own part from the next audit round on. A question the answer gives no part takes the whole answer, as before, and the row and stderr carry the warning `single_answer_for_joined_ask`. The same decision applied again is a replay only with the parts it was applied with: other parts, parts where it was applied whole, or none where it had parts, are refused `already_applied`, naming the parts the row holds and the ones given (CRW-1397). An ask also carries the questions the run asked earlier that no answer reached and the current DESIGN no longer raises, so they stay answerable through the current ask.

### crw flow pause

Signals the process that holds the run lock (SIGUSR1): the detached run process and a foreground `crw flow resume RUN [SCRIPT]` answer it alike. The process stops sending: the turn in flight is interrupted and the calls that would send end held `engine_paused`. A run that would then end completed ends `paused`: its process writes a `run/paused` row (`by`, `reason`) and no `finished` row, exits 0, and sends no completion notice (the summary and the escalations are reconciled once more). `crw flow ps` and `show` read the run `paused` while no process holds it, `crw flow next` does not resume it, and `crw flow resume` goes on with those calls; `crw flow answer` then applies to it as to any run no process holds. A pause still interrupts while an answer drains the run: the turns the drain left to end are interrupted, the operator's pause names the end (`paused` by `operator`), `crw flow next` reads the run `paused` at once, and the answer, run again once no process holds the run, applies to that paused end and resumes it. A pause of the run's own limits (its deadline, its token budget, a quota or rate limit) is not the operator's: that run finishes completed with those calls held (`crw flow ps` reads it `held`), and its completion is told. A run no process holds is refused, since nothing runs; a command's short hold of the run lock (an audit, an answer, a cancel or a recover writing its row, [crw flow ps](#crw-flow-ps)) is no process, so pause signals nothing and refuses that run the same way.

### crw flow cancel

For a run started by this version, cancellation also releases its project binding after the executions are settled and its cancelled end is stored. The start pins the binding id, revision and tenure; a later start, a handover or a rebind keeps the newer owner. Another unfinished run, live assignment or open execution keeps the binding and the command reports why it could not release it. The relay records `scope_released` with the run and binding. New work must bind the project again deliberately. An older run with no pinned tenure keeps its binding; do not guess its owner from today's state. A cancelled end sends no completion or pending escalation notice to the upper layer. Notices already delivered before cancellation remain historical facts.

Signals the process (SIGTERM): the calls in flight are cancelled and the run finishes `cancelled`. A process whose lock names no pid is never signalled (a pid of 0 would be the caller's own process group); the command says so and the operator ends the process by hand. A run no process holds is cancelled by a finished row appended under the run lock, after the executions its journal shows it released and did not end have been closed with `flow_cancel` (the slot returns in the same transaction); when that fails the run stays as it was and the command can be repeated. An execution is given up only while it is the run's: its run id is the cancelled run's and it is the execution the run released (or follows it in the node's chain). A node that another run released again after this run's cancel keeps its execution and its slot, so the second cancel of a cancelled run never takes them. A run that is already cancelled is settled the same way once more and then refused as over. A run that ended otherwise (completed, blocked or failed) with executions it still holds, such as a land whose release was not given back, is settled the same way: its cancel gives them up and says so, and a run that ended with none is refused as over (CRW-1397). The executions a cancel gives up are those the run's rows show and those the relay records under the run's id that its rows do not name (a process killed between the relay's release and its release row).

A command that holds the run lock for a moment to write a row (an audit, an answer, another cancel, a recover) is not a process of the run: it is never signalled, and the cancel waits up to 2 s for its hold to end, then appends under the run lock; a hold past the wait is refused as a run a process holds, and the cancel can be repeated. The cancel reads the run's rows again under the lock: a run another cancel or its own end made over meanwhile gets no second end row, and the executions it still holds are given up (their slots go back) as for a cancel of an ended run. The finished row says `dead: true` only when those rows show a start with no end (docs/flow/journal.md in the CRW repository); a paused end or a held run is not dead.

### crw flow resume

Takes the run from its journal once its run lock is free: with the run's own spec (`crw flow resume RUN`, in the foreground, or `--detach`), or with a script and arguments given (`crw flow resume RUN SCRIPT`, the engine's command, which refuses a script or arguments that are not the run's). Both go on under the budget and the deadline of the run's spec (a night batch's are its decision's): `crw flow resume RUN SCRIPT` takes the spec's budget when no `--token-budget` is given or it is 0 (the remainder, as the flag's help says), refuses one below 0 or above the spec's (a lower one narrows it), and pauses the run at the spec's deadline. The budget is the run's, not the process's: a resume allows what the spec's budget leaves after the tokens the run's journal shows it spent (each call's terminal rows counted once), a `--token-budget` narrows that remainder, and a run with nothing left is not resumed and reports `budget_exhausted`; more budget is a new decision. Every call whose last row is an intent is looked up on the host before the script runs again; a call in recovery hold stays until `crw flow recover` settles it.

A run whose journal holds a row of the retired review paths (CRW-1429) is read and refused: an old run's `crw.review` or `crw.reviewerFinal` row, an agent call of the retired role key of the `crw.reviewerFinal` op in any run, a reviewer agent call of its lane, or the archive of the reviewer threads its close made after its audit (`crw.archive`). `crw flow show` and the summary read its records; every resume, an answer, and every command that would write a row to it (`crw flow cancel`, `pause`, `recover`, `dispatched` and the run's report up) refuse it with `legacy_issue_child_run`, naming the row and the retired path, and write nothing, as for an old run of a `child` session's lane; `crw flow audit` prints its results and records no row. `crw flow start` runs the workflow again.

A cancelled run is over and every resume refuses it (`crw flow start` runs the workflow again): `crw flow resume RUN --detach` and the resumes of `crw flow answer` and `crw flow next` before a process is started, the run process and `crw flow resume RUN SCRIPT` under the run lock, before any row. A run that ended paused or finished held is resumed as before. A detached resume acknowledges only its spawned process's committed start; a process that loses a race with cancel and refuses the run under the lock is reported as a failed resume. A command's short hold of the run lock ([crw flow ps](#crw-flow-ps)) does not refuse a resume: it waits up to 2 s for that hold to end; a run process's hold is refused at once.

### crw flow next and crw flow dispatched

The step exchange of a session run (CRW-1316): the run publishes a step for each turn of a role call, and the owner thread, the child, takes the steps with `crw flow next RUN --wait 600 --json`. A `spawn` step is `spawn_agent` with the step's `agent_type`, `message`, `model` and `reasoning_effort` and `fork_context` false, followed at once by the step's `crw flow dispatched RUN CALL --agent ID --k K --attempt N`; a `send_input` step is `send_input` to the step's agent, then `crw flow dispatched`; a `close` step is `close_agent`. While subagents work the child alternates `wait_agent` on the open ones with `crw flow next --wait`, and keeps that loop while an answer drains the run (`run_draining`) until the process ends, which need not be `paused` after a deadline or an earlier pause: the run reads a working subagent's turn from the host by itself, but it hands out every further step (the next turn's spawn or `send_input`, and each close) only through `crw flow next`, and a step nobody takes holds its call and the run. A finished subagent holds its slot of `agents.max_threads` until it is closed, so a spawn that fails with `agent thread limit reached` leaves its step to be shown again after the hint's closes. `dispatched` exits 0 when the run bound the subagent and 1 with what to do again when it did not; a late report of an attempt the run has given up is answered `close <id>`.

### crw flow recover

The engine's recovery of a call in `recovery_hold`, under the run lock of the run that holds the call. `--adopt THREAD|TURN` takes the thread or turn the operator names after the proofs of the call's cwd, source and history; `--absent` reads the host again and accepts the call only when the same proofs hold as for an automatic outcome. What it relied on is appended to the journal as `recovery_cleared` with its evidence.

### crw flow plan-input

Builds the handoff `crw flow compile` reads (`crw-flow-compile-input/1`) from one milestone of the tracking repository, so that `crw flow plan-input --milestone OWNER/NAME#N | crw flow compile --dry-run -` checks a milestone as it stands. A child takes one milestone: the plan's project key is the milestone ref `OWNER/NAME#N`, each open issue of the milestone is one issue line keyed by its ref, and the order is the `Blocked by:` lines of the bodies (a blocker that is an open issue of the milestone becomes `after`). The command reads through the tracking adapter with GET requests (the token is `GH_TOKEN`, `GITHUB_TOKEN` or `gh auth token`) and writes nothing.

The ref is the identity, and the input spells it `OWNER:NAME:N` (`o/r#3` is `o:r:3`), because the relay dag reads a plan's project key, node ids and edge ids as identifiers (a letter or a digit, then letters, digits, `.`, `_`, `:` and `-`, at most 128 characters; the order edge of two issues is `e:FROM:TO`, and `e:FROM:TO.2` after a re-plan, so both keys fit in 123 characters together). A `:` cannot occur in a GitHub owner or repository name, so the form is unambiguous and reads back to the ref. The project key, the issue keys and `after` of the input, the scope key of the owner's parent binding and the comparison below all use this form; the envelope's `milestone` and `refs` and the warnings show the refs. A key the dag cannot hold, or an order edge over the limit, is an input error that names the refs and the limit; no key is shortened.

The body of an issue is read from a small fixed set of headings, matched without regard to case, level, bold marks and a trailing colon; a section runs to the next heading and a heading inside a code fence is not read.

| Field | Heading | Reading | When the section is missing |
|---|---|---|---|
| `criteria` | `기준` (`Acceptance criteria`, `Criteria`), `정한 답` (`Decided answer`), `먼저 실패하게 쓸 시험` (`Red tests`), `끝 조건` (`Done condition`, `Done when`), using the same aliases as [issue-ready](../release-gate.md); legacy `Acceptance` is a done condition | bullets (also numbered and checkbox items), collected in that kind order with source order within each kind; out-of-scope headings and their descendants are excluded until the next peer or shallower heading. Legacy headings remain supported; bodies using only legacy headings retain their previous order. | the title is the one criterion, with the warning `criteria_missing` |
| `regions` | `편집 영역` (`Edit regions`), using the same issue-ready aliases; legacy `수정 범위`, `Regions` | each bullet names a path in backticks, else its first word; a trailing slash is a tree. The same out-of-scope exclusion applies. | no region; the compile default applies |
| `size_fit`, `size_reason`, `issue_size` | `크기`, `Size`, `Size fit` | lines `size_fit: V`, `size_reason: V`, `issue_size: V` with a value of the closed set | nothing; the compile defaults apply |

`--target-repository` (the absolute path of the checkout) and `--base-ref` (the branch) give the project its target, which compile needs for any order between issues. `--envelope` prints `{schema, milestone, input, refs, warnings}` instead of the bare input, so the warnings are recorded with it; `refs` maps each key of the input back to its `OWNER/NAME#N` ref.

Nothing the mapping cannot carry over refuses: it is a warning, printed on stderr as `crw flow plan-input: warning: [rule] ISSUE: detail` and kept in the envelope's `warnings`. The two key warnings (`project_key_bound`, `project_key_unchecked`) are also the `warnings` member of the project in the bare input, which `crw flow compile` carries into the plan's warnings, so a pipe records them. The rules: `criteria_missing`; `region_invalid` (a path that is absolute, leaves the repository or is the root); `size_value` (a value outside the closed set); `blocker_closed`, `blocker_outside_milestone` and `blocker_self` (a `Blocked by:` line that names a closed issue, an issue of another milestone or repository, or the issue itself); `target_missing` (an order and no target); `milestone_closed`; `no_open_issue`; and the two comparisons of the project key with the live parent bindings of the owner thread (`--thread`, default `CODEX_THREAD_ID`, read from the relay store read-only, as `crw flow start` does): `project_key_bound` when the thread holds no live parent binding under the plan's project key (`OWNER:NAME:N`; the keys are compared exactly, as `crw flow start` and the first claim compare them, so a binding that differs only by case is another key, and the warning says so), naming the key, the milestone ref and the bound keys, and `project_key_unchecked` when there is no thread or the bindings cannot be read. Exit 0 built; 2 an input that cannot be used: a ref that is not `OWNER/NAME#N`, a milestone that does not exist, a token the repository refuses.

### crw flow pr

PR-unit landing ([delivery](../delivery.md#pr-unit-landing)): a child that lands its milestone on a milestone integration branch (the plan's target `base_ref`) opens one pull request from that branch toward `dev`. `crw flow pr open --repo OWNER/NAME --head BRANCH [--base dev] --title T [--body TEXT | --body-file PATH] --issue REF... [--draft] [--push DIR [--remote origin]]` pushes the branch of the checkout DIR to the remote first (never forced: a push the remote refuses opens nothing), then creates the pull request through the tracking adapter; its body ends with one `Carries: REF, REF` line naming the issues (at least one; repeated or comma-separated `--issue`). `crw flow pr show --pr OWNER/NAME#N [--checks]` reads the pull request (state, merged, head commit, head and base branch, the carried issues) and, with `--checks`, the check runs and commit statuses of its head judged together as `none`, `pending`, `success` or `failure`. `crw flow pr branch --checkout DIR --milestone M [--base dev] [--name BRANCH]` makes the bundle's integration branch before the run starts: the local branch `--name` (`bundle/M` by default; the handoff's `base_ref` is the name to give) at the tip of the local base branch, created once; a branch that already contains that tip is reused, one that does not is refused (exit 2) and never moved, and nothing is fetched or pushed. A handoff whose project target names `pr_base` (the branch the pull request goes to) is a bundle: its `base_ref` is that integration branch, `crw flow compile` refuses a `base_ref` equal to `pr_base`, and `crw flow start` refuses a bundle whose branch is not in the target checkout, naming `crw flow pr branch`, before it writes a run. `crw flow pr open --run RUN --push DIR` (with `--repo`, `--head` and `--title`; `--state` and `--socket` select the relay store, read-only) takes the pull request from the run instead of a text: the run must have closed its milestone with a crosscheck verified at the close tip, the issues and the body come from the run, a title or body that leaks a host path, the host name or a thread, call or run id is refused (exit 2), and exactly the crosschecked tip is pushed, never forced. `--run` reads the crosscheck from the run's `crw.crosscheck` rows (CRW-1442) and is refused with `crosscheck_missing` where the run has none; the text form with `--issue` remains. A run script that calls the `crw.mergeRequest` op (not part of the built-in `project-lane`; it needs a lane wired with a pull request reader and a reporter that takes merge requests) asks the parent to merge that pull request when its crosscheck, its checks and its review comments allow, and asks once per head (`docs/flow/script.md` in the CRW repository, "The bundle's pull request"). The commands write nothing to the relay and nothing to the work tracker besides the pull request; the token is `GH_TOKEN`, `GITHUB_TOKEN` or `gh auth token`. Exit 0 done; 1 GitHub or git failed; 2 an input that cannot be used. The command never merges: the parent (repository session) first decides the pull request with `crw flow pr decide --pr OWNER/NAME#N --head SHA --release-impact TEXT`; the child's equivalent queue-entry command is `crw manage integrate --enqueue-pr OWNER/NAME#N --head SHA --release-impact TEXT`, using the same pinned head and release impact, and the queue merges its head onto `dev` after the verification and the repository's review, and writes the landing record on the pull request as a comment.

### crw flow status-line

The line the Stop hook prints, `crw flow <run> <state> · <phase> · <n> calls · ...`, for the runs of thread T that are not over, and nothing for any other thread.

### crw flow digest

The digest of a night batch; see [The night batch](night-batch.md#the-night-batch).
