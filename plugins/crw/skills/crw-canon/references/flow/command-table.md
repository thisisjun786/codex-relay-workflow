
## The crw flow command table

| Command | What it does |
| --- | --- |
| `crw flow start WORKFLOW [--args JSON \| --args-file FILE] [--handoff FILE] [--thread T] [--token-budget N] [--pool N] [--decision D] [--backend session\|app-server] [--preview] [--force]` | Shows the preview (the nodes, the width, the role pairs, the budget and the level of each preflight fact: pass, warn or fail), then starts the detached run process (its own session, no inherited descriptors, the run lock) and prints the run id. `WORKFLOW` is a built-in workflow (`project-lane`, `night-batch`, `land-head`) or a script file; `land-head` lands a head the child made outside a run through the gates of a run (args `plan`, `milestone`, `issue`, `head` and `authors`, the subagent threads that wrote it: verification, a unit check in the committed mode over `base..head` in a separate tool invocation (Codex review by default, Bugbot on a Codex quota; no reviewer call or agent thread id), acceptance and integration; an actually observed same-thread review is warning-only, recorded, and does not block; docs/flow/script.md, "Landing a head made outside a run"); its start warns with the fact `plan_live_run` when another run of the plan has not ended, since the land's release takes the plan's coordinator epoch from it. `--decision D` starts `night-batch` from the parent's decision record D. `--handoff FILE` names the crw-plan handoff the plan's current revision was compiled from, which the project lane reads its milestone from; a milestone whose required commands the shipped verifier cannot run (anything but `crw-dev ci local`) is refused here. `--backend` is `session` unless named: every agent call is a step the owner thread spawns as a role subagent (`app-server`, a thread for each call, is for tests and shadow runs). `--preview` stops after the preview; `--force` is accepted and changes nothing, because a fact never stops the start |
| `crw flow ps [--all] [--json]` | One line for each run: its state (`running`, `paused`, `dead`, `held`, `completed`, `blocked`, `cancelled`, `failed`), workflow, owner thread, calls and tokens (the total, then the cached input, the fresh input - the input minus the cached - and the output), and the outcome the script came to (`state/reason`, `-` without one). Without `--all` it lists the runs that are not over |
| `crw flow show RUN [--json]` | The tree phase, then agent: for each agent call its role, node, thread, status and reason, the commits of its node, the review verdicts, the tokens (split into cached input, fresh input, output and reasoning), `recovery_hold` where a call's outcome is unknown, and the join items that threw |
| `crw flow watch RUN [--after SEQ] [--wait N] [--limit M] [--follow] [--json]` | The same tree as `show` with the cursor of the last row it was made of; with `--after SEQ` the rows of the run after that cursor, read as `crw relay journal-tail` reads the relay journal: the cursor is the `seq` of the last row, `--wait` waits for a row without holding a transaction, and the next call passes the cursor back. `--follow` keeps reading until the run is over or has no process. The rows are the run's own: a command that writes into a run (`crw flow report-up`, `report-ack`, `report-delivered`) numbers its rows apart, and `crw flow reports` lists them |
| `crw flow answer --decision D --run RUN --node N --question Q --revision V [--answer-for DIGEST=TEXT ...] [--wait S] [--no-resume]` | Applies the parent's answer record D (the relay's user-decision record, answered with `crw relay decision-answer`) to the wait of a run: it compares the question and its revision, the node and its attempt, the run, the plan basis and the authority of the record with the run's journal, appends one `decision_applied` row under the run lock, and resumes that wait. A run a process holds is asked to stop at its next boundary first (the calls in flight end, the next ones are held, the run ends `paused` by `answer`); the answer waits `--wait` seconds (0 unless named) for the run lock and otherwise answers `run_draining` (the stop is asked, not known to be made), to be run again once the run is paused. The same answer again appends nothing |
| `crw flow pause RUN` | Asks the run process to stop sending requests; the calls in flight end held (`engine_paused`), the run ends `paused` (no completion notice) and `crw flow resume` goes on with them |
| `crw flow cancel RUN` | Ends the run: the calls in flight are cancelled and the run finishes `cancelled`; the executions the run released and still owns are given up and their slots returned, also for a run that has already ended and still holds some |
| `crw flow next RUN [--wait S] [--json]` | The owner thread's side of a session run's step exchange: the steps the run published (`spawn`, `send_input`, `close`), each with the host tool call to make and the `crw flow dispatched` line to run right after it, the run's state (`running`, `waiting_session`, `waiting_decision`, `paused`, `ended`; a run an answer drains reads `paused` only once no process holds it), the subagent slots (`agents.max_threads` and how many the run's subagents hold) and a hint. With `--wait` it waits up to S seconds for a step or a change of state. A run no process holds that is neither paused nor over is resumed (`crw flow resume RUN --detach`), and a missing owner binding is written again with a warning |
| `crw flow dispatched RUN CALL --agent ID --k K --attempt N [--wait S] [--json]` | Reports the subagent a step was spawned as (or the one `send_input` went to): written atomically into the run's inbox, then the run's answer is awaited. The run reads the subagent on the host and binds it when its parent thread, its first message's `crw-flow-op:` marker and its configured pair match; otherwise it says what to do again (`pair_mismatch: close <id> and spawn again with M/E`) and the step stays. A report to a run no process holds waits in the inbox for the resume |
| `crw flow resume RUN [SCRIPT] [--detach]` | Takes the run from its journal again with the same script and arguments, once its run lock is free; a cancelled run is over and every resume refuses it |
| `crw flow recover [--run RUN] CALL (--adopt THREAD\|TURN \| --absent)` | Settles a call in `recovery_hold`: the only manual way out of a call whose outcome is unknown, and the rows it appends are the evidence it relied on |
| `crw flow digest RUN [--out FILE]` | The run digest of a night batch (`crw-batch-digest/1`) built from the run's journal: for each selected issue whether it was integrated (with the commit, acceptance and integration the journal shows), carried (with the reason: a held call, a recovery hold, a node that did not start), cancelled or left for a decision, why the run stopped, and the token budget spent with its split. `crw manage batch report --digest FILE` makes the morning report from it |
| `crw flow audit (--run RUN \| --acceptance ID) [--milestone M] [--json] [--no-record]` | The audit of the reviews behind the agent-path acceptances of a run, read back from the reviewer threads on the run's host (CRW-1206): each acceptance is `ok`, `mismatch` or `unobserved`, and the exit is 1 unless every one is `ok`. Once the run has ended (a `finished` or `run/paused` row after its last start) and no process holds its run lock, the result is appended to its journal as a `crw.audit` row under that lock, unless `--no-record` is given |
| `crw flow report-up`, `crw flow reports`, `crw flow report-ack`, `crw flow report-delivered` | What reaches up from a run (CRW-1204): the child lifts a blocker or a decision request, and the parent reads and acknowledges the reports; `docs/flow/reporting.md` in the CRW repository. A run process hands its plan summary, its escalations and its completion digest to the same reporting, whether `crw flow start` or a resume started it |
| `crw flow status-line --thread T` | The one line the Stop hook prints, when thread T owns a run that is not over; it prints nothing for any other thread |
| `crw flow plan-input --milestone OWNER/NAME#N [--target-repository DIR --base-ref BRANCH] [--thread T] [--envelope]` | Builds the handoff of `crw flow compile` from one milestone of the tracking repository and prints it; it only reads. See [crw flow plan-input](commands.md#crw-flow-plan-input) |
| `crw flow pr branch --checkout DIR --milestone M`, `crw flow pr open --repo OWNER/NAME --head BRANCH (--issue REF... \| --run RUN) [--push DIR]`, `crw flow pr show --pr OWNER/NAME#N [--checks]` | Makes the bundle's integration branch, opens that branch's one pull request toward `dev` (from the run's journal with `--run`), naming the issues it carries, and reads its state and checks back; the dev queue merges it. See [crw flow pr](commands.md#crw-flow-pr) |
| `crw flow run --backend fake`, `crw flow roles`, `crw flow compile`, `crw flow lint` | The fake run, the role table, the plan compiler and the script check of the engine |
| `crw flow trace export`, `crw flow shadow`, `crw flow measure` | The trace tools, which read store copies and trace files and call no agent |
