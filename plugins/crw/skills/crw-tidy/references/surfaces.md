# Surfaces

Here the parent is a layer of [the level table](../../crw-canon/references/hierarchy.md#the-levels).

What each judged surface is measured against, and what exempts it. The rules themselves belong to
the [shared references](../../crw-canon/SKILL.md); these rows only say which test to apply (the Diagnose job) and, in the last column, when a gap is clear enough for the Supplement job to write.

| Surface | Applicable target | Not a defect | A clear supplement (Supplement job) requires |
|---|---|---|---|
| Code repository line | The `OWNER/NAME` (or URL) of the code repository, one per implementation issue, kept in the issue body ([Tracking operating model](../../crw-canon/references/tracking-model.md#tracking-operating-model)) | Non-development work and an unresolved target may leave it out; reference-only and legacy repositories belong in links; a preserved historical multi-repository case is not forced to a single value | Every input that names a repository names the same one, none of them disagrees, and at least one of the agreeing inputs is the current delivery (its pull request where one exists, otherwise its task branch) or the existing assignment. A majority is not agreement. Never copy a milestone's repository onto issues |
| Spelling of the repository address | The address is `OWNER/NAME` or the URL of the code repository ([Resolve the implementation repository](../../crw-canon/references/tracking-model.md#resolve-the-implementation-repository)) | The same non-development and unresolved-target cases; research or design with no code target needs no remote at all | The address is quotable from the current delivery (its pull request where one exists) or the assignment, and none of them disagree |
| Required body and linked documents | The milestone description's own definition ([Milestone description standard](../../crw-canon/references/tracking-model.md#milestone-description-standard)); an issue's accepted criteria and its one current delivery link (the pull request, where one exists); each linked canonical document resolves and carries the revision or updated-at the citing record claims ([Keep the two sides consistent](../../crw-canon/references/tracking-model.md#keep-the-two-sides-consistent)) | Reading density is a target rather than a length limit, so a compact record is not short of the rule; an issue write does not authorize a milestone description write; a link to a document correctly marked superseded, with its successor named, is history rather than a stale reference | The missing content exists in an accepted, linkable source and the target is inside this assignment's write authority; otherwise propose the passage |
| Milestone membership | Every implementation issue sits in the milestone its product and delivery scope belong to ([Tracking operating model](../../crw-canon/references/tracking-model.md#tracking-operating-model)); a repository, a product-family label or a `Blocked by:` line does not stand in for the milestone | A standalone issue the operating model allows outside a milestone; an issue whose membership is still an open classification decision recorded as such | The milestone is quotable from the issue's body, its current delivery (its pull request where one exists) or its existing assignment, or from an accepted plan, and every input that names a milestone names the same one; a majority is not agreement. Otherwise propose it and leave the choice to the decision a midpoint check surfaces: tidy never picks among candidate milestones |
| Unreflected approved decision | The canonical document carries the latest accepted decision or explicit user correction ([Tracking holds canonical documents](../../crw-canon/references/tracking-model.md#tracking-holds-canonical-documents)) | An issue status, an assistant proposal or a newer local draft is not a decision; unclear decision authority is a conflict rather than a gap | The decision carries a traceable source and date, either a tracking anchor by ref or the user's own later correction, and the passage it changes is unambiguous. Link that basis in the edit |
| Release readiness | An unreleased implementation issue carries the five items of the [release gate](../../crw-canon/references/release-gate.md#the-release-gate), and one whose open decisions section lists a question carries the `설계 먼저` label | Work already released, delivered or closed; research, design or operation with no code change (`crw skill issue-ready check` still reports it, and the disposition is an exception); an issue the child approved past the gate, with that record | Only the label: the open decisions section lists a question, the label `설계 먼저` exists in the tracking repository and the issue lacks it, so add the one label. A missing item is a proposal carrying the heading and the passage the owner would accept, because the answer, the test cases and the end condition are content tidy would have to compose. Run `crw skill issue-ready check` for the judgement and quote its `reasons`; never remove the label, which the design's owner does |

An issue whose current delivery and assignment name one repository, with the repository line absent
from its body, is the ordinary gap: add the one line and leave every other
field alone. An issue with no repository anywhere, on non-development work, is the ordinary
exception, because no line is what the rule asks for there.

Where the body names one repository and the current delivery sits in another, nothing in this table
decides which is right. Record both readings and the decision that would settle them. The same
holds when a body sentence is the only evidence: a note about where work might land is not the
execution evidence the first row asks for, so that item is unverified rather than a gap.

Separate the two quiet outcomes there. Where the record itself shows the target is still undecided,
that is the unresolved-target exception the rule already allows. Where the target may well be
settled but the corroborating evidence this table requires could not be read, or does not exist
yet, that is unverified: a definite body line with no current delivery and no assignment is the ordinary
case of it. Neither outcome is a defect, and neither licenses picking a value.
