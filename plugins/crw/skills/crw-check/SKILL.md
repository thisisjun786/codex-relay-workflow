# CRW Check

Check delivered work against what was agreed, using Linear as the canonical source of what was agreed. In an existing execution workflow, carry actionable findings into the authorized correction and recheck path instead of stopping at a proposal.

## Connect the workflow

Read [Integrations](../crw-plan/references/integrations.md), including its completion-follow-up rule. Use Linear tools for current documents and decisions, `cxc-recall` for missing historical decisions, and `cxc-dev` plus the relevant review/verification owner for code evidence. A standalone audit stays read-only; an existing execution task retains its authorized scope when this skill is used to check delivery.

Use `readchk` when the comparison is ambiguous, `ssotize` in audit mode to map conflicting sources, and `mandela` when acceptance evidence confirms the implementation's own assumptions. For an actual contradiction, use [crw-logic](../crw-logic/SKILL.md) as a bounded helper; it returns findings without replacing this requirement audit. Use `shower` when a substantial handoff needs a fresh reader. User-only Paperthin skills require their own explicit invocation as described in Integrations.

A sub-task or bounded helper called from here writes no Linear record itself: it returns the record ID, the revision it read, the reason, the smallest sufficient change and its evidence, and this assignment's own writer applies and reads it back, under [record writes and returned proposals](../crw-plan/references/integrations.md#record-writes-and-returned-proposals).

## Pin the comparison

Identify the Linear project/milestone/issues, canonical documents, original intent, subsequently accepted changes, and implementation revision. Read full criteria and relevant decisions, not just list summaries. Record exact IDs, source dates/revisions, baseline/final commits or a frozen diff bundle, and the observed delivery environment.

Whether a relay holds the assignment is determined and recorded once, not decided again here: see [Whether a relay holds this assignment](../crw-plan/references/integrations.md#whether-a-relay-holds-this-assignment). A check that decides it for itself can reach the opposite answer from the coordinator running the same assignment, and then one of the two is comparing against a store the other never registered in.

Where a relay holds the assignment, pin the comparison to the revision it reports as current, and register the issue's criteria as the canonical set so each verdict is recorded against agreed obligations and names the set it was reviewed against. A superseded revision is not the thing to certify, a newer revision arriving mid-check restarts the comparison at the new current revision rather than completing the old one, and a criteria edit after a review invalidates that review instead of passing it. Read the same revision again against the set now in force and rule on that same event; a fresh execution generation is for when the artifact itself has to change or the event is no longer the current revision. See [codex-session-relay](../crw-run/references/relay.md). Without a relay, compare as described above.

Treat memory and assistant proposals as locators. A newer document does not automatically override a user decision. A later explicit user correction or accepted decision can supersede the original requirement; cite that evidence. If authority is unclear, preserve both readings as unresolved rather than selecting whichever matches the implementation. Which side is canonical for the fact being compared, and whether a disagreement is a requirements change or an implementation mismatch, follows [Keep the two sides consistent](../crw-plan/references/integrations.md#keep-the-two-sides-consistent).

Inspect relevant code, tests, and result artifacts. Separate source existence, passing checks, integration, deployment, and observed behavior. If a live check is outside the authorized environment, leave that part unverified.

When the claim includes PR readiness or integration, assess CI and review evidence using [Merge readiness](../crw-run/references/merge-readiness.md). Entering review and being merge ready are different states owned by OPS-9.1 in [Operations contract](../crw-run/references/operations.md); judge the claim against that clause rather than reading a pull request's draft or ready flag as a verdict. Reuse valid coordinator evidence and return any gaps to that owner; a bounded audit does not take over the merge.

For implementation completion, use the shared
[Implementation Done](../crw-plan/references/integrations.md#implementation-done).
Match the issue to its current delivery PR, intended integration target and actual
merge evidence, or the reconciled legacy PR set and its combined issue coverage.
Preserve existing accepted operational criteria. Contrast partial, reference/replacement, wrong-branch and
closed-unmerged cases with a complete intended merge. An implementation merge does
not prove deployment; a verified non-PR result does not need an empty PR.

## Compare criterion by criterion

Break compound criteria into observable obligations and classify each:

| Classification | Required basis |
|---|---|
| Satisfied | Evidence at the relevant revision and required delivery level |
| Agreed change | Traceable accepted change and evidence for the revised obligation |
| Explicitly deferred | Recorded deferral and remaining condition or later scope |
| Missing or regressed | In-scope obligation contradicted by code or reproduced behavior |
| Unverified | Insufficient access/evidence, ambiguous authority, or an untested required surface |

Include significant implementation additions without agreed scope. Explain their impact without declaring every addition a defect. Do not count deferred work as completed, call absent evidence a proven defect, or rewrite criteria to make the result pass.

When recording the result, the three recordable per-criterion dispositions are verified, needs_changes, and unverified, and every classification above maps to one of them. Satisfied maps to verified. An agreed change maps to verified too, but only once the registered criterion itself carries the accepted wording, because a relay review binds to the criteria set as it stood at claim time: certifying the revised obligation against a criterion that still states the original one records a verdict for the wrong obligation. Register the revised wording before claiming. Once an event has been claimed, editing a criterion invalidates that review whether or not a verdict has settled, and claiming is idempotent with one exception: where the set moved under a review of the revision the assignment still stands on, and any verdict already recorded for it is `verified`, a second claim returns `proceed` and rebinds the review to the set now in force, so the same event is read again and ruled again. Where a verdict had already settled, that re-review names the set it read with `--expect-criteria-digest` and records only verified or needs_changes. Everywhere else the second claim still returns `already_claimed` and a fresh execution generation is the route, as [codex-session-relay](../crw-run/references/relay.md) describes. Missing, regressed, and unagreed-scope findings map to needs_changes with a note; insufficient access or authority maps to unverified with the reason. An explicitly deferred obligation is recorded as unverified with its deferral, never as verified. Leaving a required criterion unmapped is not neutral: a managed `verified` verdict needs every required criterion recorded verified and is refused otherwise. Stopping an assignment is aborted, which is an overall verdict recorded with its reason and never a per-criterion disposition; a re-review cannot record it, so stop the assignment on the relationship instead.

For suspected violations, state the expected rule, observation, smallest useful counterexample, user impact, and source anchors. Check a valid contrasting case so a correction does not reject normal behavior. Reuse valid proof; do not rerun a broad suite just to make a report look thorough.

## Judge progress against the schedule

Where the checked subjects, which the contract defines as projects, milestones and issues, carry agreed dates, compare them with delivery evidence as part of the same check. Pin the Schedule baseline, the Current target, the observation time, and the Timezone alongside the identifiers already pinned above, reading them from the [Schedule baseline contract](../crw-plan/references/integrations.md#schedule-baseline-contract) that [crw-plan](../crw-plan/SKILL.md) owns, under the field names and value words it fixes, and keep no second copy of any date. Mark what the schedule comparison covered and what it did not, for the whole request rather than only for the results that turned out to be decidable.

Classify each result as ahead, on plan, at risk, late, or undecidable, deciding by the reference's first-match order rather than by the order those names are listed in, so the same inputs always produce the same verdict. Ahead needs real early achievement at the delivery level that result's criteria require, not a fast source landing under criteria that require installation or live behavior, and never an issue count, a Done ratio, or a finished agent turn. On plan states only that results due by the observation are met; being before a deadline promises nothing about meeting it. A target date that has passed with the result unachieved is late, where a day target runs to the end of that day in its own timezone so today is never late early. Judge every result against both the baseline and the current date, show the source of a replan, a scope change, or a pause, and never let a moved date erase a delay already recorded. A Schedule baseline recorded `unconfirmed`, meaning a target exists and no Baseline record establishing it can be found, makes that axis alone undecidable and the scope partially checked; a subject that entered scope later still has its own Schedule baseline, set by the record that first gave it a target, and is judged on both axes with its Change source showing when it entered. Where the evidence needed to decide was not read at this observation and the result was not already settled when it was last read, that verdict is undecidable too. A result that already completed is different, but only as far as its evidence is a settled event: a landing that happened is reused without being gathered again, while achievement resting on a current state, such as an installation still being present, is observed again for a current verdict or the result is undecidable with the earlier observed-at. The verdict itself is always recomputed from that evidence against the current dates, because a target moved to before the achievement turns an earlier ahead into late. The schedule verdict is recorded in its own field and is never a fourth per-criterion disposition: a late schedule does not turn a satisfied criterion into `needs_changes`.

[Schedule judgment](references/schedule-judgment.md) holds the decision order, the date and timezone arithmetic, the closed list of risks with their wait classes, the aggregation rule, predecessor-based impact, the reusable judgment record, the full routing of a mismatch by the level that owns it, and the judgment cases. Read it before routing anything the two sentences above do not plainly cover.

Lead a progress or interim report with the schedule: the overall verdict with the query and judgment times, then the notable lead and delay with baseline dates and actual evidence, then the affected next steps, then internal coordination waits and user decisions. A completion check keeps the lead described below and places that block immediately after it.

Judging the schedule by default neither widens nor narrows this skill's authority. Return needed schedule changes to [crw-plan](../crw-plan/SKILL.md) and already accepted corrections to the existing owner; do not move a date, change a Done state, take over execution or a merge, build a second path that resumes work, or repeat a notification. A passed or approaching deadline never lowers a completion criterion or a review requirement. Equally, a checkpoint inside an approved initiative or project execution keeps the parent confirmation and already-approved successor work that approval covers, so being called here does not turn an approved continuation into an independent read-only audit: route the mismatch to the level that owns the ordering and settle continuation there, within the approval it already holds: a mismatch contained in one project goes to that project's parent, while one that orders work across projects goes through the supervisor owning both, or, where the projects share no supervisor or answer to different ones, through direct coordination between the parents with the unsettled pair-level decision raised to the user, because a project parent never decides whether another project proceeds and no supervisor acquires authority over a pair it does not own. Explicit report-only, read-only, pause, and no-contact limits still win. In the report, keep the correction request sent, the parent actually resuming, and a result actually verified as three separate facts.

## Resolve findings and report

For a completion check in an established execution workflow, send evidence-backed in-scope corrections to the existing responsible task through [crw-run](../crw-run/SKILL.md#return-corrections-to-the-existing-task). Include the violated criterion, reviewed revision, reproducible evidence, required outcome, and recheck. Do not make Jun relay the packet or ask again whether to send it. When called as a bounded audit helper, return this packet to the coordinator; the coordinator owns dispatch. A finding is returned by the caller's own level to the level below it. A parent returns an issue's finding to its responsible child, or handles it itself where the fix is the project's to decide. A supervisor returns a project's finding to that project's parent and never to its children, even when the finding is about one issue; it carries that finding in the [Coordination message](../crw-run/references/task-packet.md#coordination-message) rather than in the child correction procedure below, which is issue-scoped and, where a relay holds the assignment, addressed to a registered child this supervisor does not own. A standalone issue keeps its existing owner and no parent is invented for it. A check never sends a correction into another project's children, per [supervisor, parent and child scope](../crw-plan/references/integrations.md#supervisor-parent-and-child-scope).

Recheck the corrected revision against the original criteria and the reproduced failure. Missing evidence calls for a scoped verification request, not an invented defect or a speculative fix. Reuse valid evidence and keep the same correction scope until verified or a concrete blocker requires a decision.

Explicit read-only, report-only, or no-contact instructions take precedence. A standalone check without an established execution assignment returns findings; it does not create a worker or assume permission to change code. Route authorized roadmap changes to [crw-plan](../crw-plan/SKILL.md), and verified delivery to the coordinator's [delivery and integration](../crw-plan/references/integrations.md#default-dev-integration). A passing audit alone does not authorize requirement changes, issue closure, or deployment.

Lead the report with the verification result and action actually taken: correction sent, awaiting delivery, recheck passed, integrated, or blocked. Add a concise criterion/evidence table when useful. Under an existing management assignment, write the audit summary to the linked Linear coordination document and read it back. Use a separate audit document only when prior authorization or an explicit recording request covers that document; do not ask again for authorization already granted. A bounded helper returns the record to the coordinator. Keep sensitive raw evidence local and link a suitable summary.

Where a relay holds the assignment, it QUEUES that summary with the event, revision, and verdict it describes; the write itself is the coordinator's own connector operation, since the relay holds no credential. Confirm it by reading the document back and checking this job's own structured record rather than searching the text for words. A failed write is retried on its own and never re-runs the check or re-sends the correction.

Before finishing, verify every verdict has a source, accepted changes were considered, deferrals remain distinct from completion, and unverified delivery levels are explicit.

### Report delivery reach in the check result

Where the audited work is something a reader installs or runs, carry the chain from [Delivery reach and current usability](../crw-plan/references/integrations.md#delivery-reach-and-current-usability) into the result: the stages the delivery has evidence for in chain order, any first stage that is missing or unobserved, and the two closing lines. A per-criterion disposition and that chain answer different questions, since verified says the obligation was met at the reviewed revision and the chain says how far that revision travelled, so a verdict never promotes a stage. A criterion can be verified on a revision nobody has installed.

A parent sitting idle with no goal is not a finding. Since the goal-free default a project parent ends its turn when only waiting remains, so an idle parent whose recorded start policy and wake-path readiness hold is operating normally and its quiet is the design working. What turns that into a finding is the delivery side: a readiness fact that no longer holds, a delivery held terminally, or a recipient whose own goal status the relay treats as blocking. Check those before reporting a stalled parent, and keep the parent's idleness and its delivery path as two readings rather than one.

A check reads installation and runtime state; it does not install, start or restart anything to supply evidence it is missing. Record the missing state as unverified with the observation that would settle it, and carry it in the report and its closing next step rather than as a finding. Missing reach is not a criterion failure and the correction path above needs one: where a relay holds the assignment, a `needs_changes` verdict requires a registered criterion marked that way with a note, so an observation request sent through it is either refused or recorded as a criterion failing that nothing failed. Ask for the observation through that path only where a registered criterion or a separately authorized operation already covers it.
